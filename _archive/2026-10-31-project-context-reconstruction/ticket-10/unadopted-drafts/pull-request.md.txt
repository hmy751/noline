# 변경 근거로 PR 제목과 본문 작성

PR 제목·본문의 초안이나 수정을 요청받았을 때 사용한다. 리뷰어가 대화 이력 없이 문제와 최종 변경, 확인 범위와 남은 영향을 판단하도록 작성한다. 초안 작성은 커밋·push·원격 PR 생성 요청과 구별하며, 이미 사용자가 맡긴 실행 범위가 있으면 그대로 이어간다.

## 실제 비교 범위를 정한다

1. 사용자가 지정한 base/head·PR을 우선한다. 지정이 없으면 현재 브랜치, upstream과 저장소 기본 브랜치 정보를 확인한다. `origin/HEAD`는 기본값 후보이며 실제 PR 대상이라고 단정하지 않는다. 기본 브랜치 자체에서 작업 중이거나 비교 대상이 없으면 최근 커밋·작업 트리 등 요청한 범위를 확인하고 초안의 기준을 밝힌다.
2. 선택한 base와 HEAD의 merge-base부터 커밋·파일 목록·최종 diff를 읽는다. 아래 명령의 `BASE_REF`는 확인한 ref로 대체한다. refs가 없거나 로컬 정보가 오래됐으면 그 한계를 밝히고 필요한 조회만 수행한다. 읽기 때문에 브랜치를 바꾸거나 working tree를 초기화하지 않는다.

   ```bash
   git status --short --branch
   git branch --show-current
   git symbolic-ref --quiet refs/remotes/origin/HEAD
   git log BASE_REF..HEAD --oneline
   git diff BASE_REF...HEAD --name-status
   git diff BASE_REF...HEAD
   ```

3. 미커밋 변경과 새 파일은 별도로 확인하고, 포함한 초안이면 예정 변경임을 표시한다. 커밋 prefix와 통계는 탐색 단서이며 최종 동작의 근거는 실제 diff·사용처다. 중간에 시도했다가 사라진 변경을 최종 기능으로 서술하지 않는다.
4. 해당 변경의 실제 검사 결과·실패·미확인을 확인한다. 이전 판본의 검사라면 최종 변경에도 유효한 범위만 사용한다. 실행하지 않은 테스트를 완료로 표시하거나 문서 변경을 앱 동작 검증으로 확대하지 않는다.

## 문제와 최종 동작에서 작성한다

저장소 PR 템플릿이 있으면 필요한 항목을 따르고, 없으면 문제·결과·검증을 설명할 만큼 작성한다. 단순 변경은 짧은 설명과 관련 검증이면 충분하다. 파일 수·줄 수·커밋 수로 섹션 수를 고정하지 않는다.

- 제목은 최종 변경의 구체적인 목적을 표현한다. 본문 첫머리에 어떤 조건에서 무슨 문제가 있었고 변경 후 어떻게 달라지는지 쓴다.
- 중요한 설계 선택이 있다면 검토에 필요한 이유·절충을 설명한다. 모든 커밋이나 파일의 순서를 다시 나열하지 않는다.
- 사용자·호출자·저장 데이터에 호환성 영향이 있으면 필요한 전환, 배포 순서와 남은 조치를 적는다. schema·Router 키워드가 있다는 이유만으로 migration을 만들어 넣지 않는다.
- 확인에는 실제 실행과 결과, 남은 공백이 어떤 판단을 제한하는지를 적는다. 작은 PR에도 중요한 실패·미확인은 남기며, 향후 계획과 이번 필수 미완료를 섞지 않는다.
- 관련 이슈·결정은 리뷰에 도움이 되는 실제 접근 경로만 연결한다. 로컬 개인 파일·임시 로그·대화에 의존하는 설명은 본문에 필요한 의미로 풀고, 존재하지 않는 commit/PR 링크를 만들지 않는다.

변경 범위가 달라졌으면 제목과 본문을 최종 결과 중심으로 다시 맞춘다. 커밋 메시지·통계·초기 계획과 맞는다는 사실만으로 최종 diff와의 대조를 생략하지 않는다. 현재 근거로 작성 가능한 초안과 추가 확인이 필요한 주장도 구별한다.

Claude에서는 `/generate-pr`가 이 절차의 진입점이다. Codex에서는 PR 제목·본문 작성을 요청받으면 이 런북을 직접 적용한다. 명령 이름의 호환성을 위해 별도 제품 정책이나 다른 템플릿을 두지 않는다. 전환 이유는 [절차 통합 결정](../decisions/2026-10-31-development-document-workflow-integration.md)에 있다.
