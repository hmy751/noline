# 체계 지침의 역할과 구성

**체계 지침은 특정 영역의 구성요소가 어떤 역할을 맡고, 그것들을 어떻게 작성·사용·연결·변경할지 정하는 본문이다.** 문서 체계의 구성·작성·갱신 기준이나 개발 절차의 입력 선택·역할 연결처럼, 다루는 영역에 따라 내용은 달라진다. 문서의 충분성과 표현을 판단하는 기준도 그 문서 체계를 다루는 지침에 포함될 수 있다.

이 문서는 Noline에서 체계 지침의 성격을 구별하고, 진입 본문과 상세 지침의 책임·이름·연결을 정할 때 읽는다. 체계 지침을 새로 작성하거나 기존 지침의 범위·위치·분할을 바꾸는 사람이 적용한다. 개별 제품 작업에서 모든 체계 지침을 먼저 읽는 순서를 만들지는 않는다.

본문과 형성 자료의 구분·보존·읽기·갱신은 [CONTENT-POLICY](CONTENT-POLICY.md)가 소유한다. 이 문서는 체계 지침이 무엇이며 어떤 본문 역할을 유지해야 하는지를 설명하고, CONTENT-POLICY는 그 본문과 형성 자료를 함께 관리하는 방법을 설명한다. 이 구별을 만든 의도와 선택 이유가 필요하면 [형성 자료 안내](_background/system-guidance/README.md)에서 관련 맥락·기록·근거를 고른다.

## 다루는 대상과 맡은 판단으로 구별한다

체계 지침인지 판단할 때는 **무엇에 관한 기준을 정하며, 독자가 무엇을 하려고 이 문서를 읽는지**를 본다. 규칙이 있다는 사실, 문서의 중요도, 상위 폴더나 대문자 이름만으로 구별하지 않는다.

| 문서가 직접 답하는 질문 | 역할과 예 |
| --- | --- |
| 필요한 기준과 제품 계약을 어떻게 고르고 구현·검토·갱신으로 연결하는가 | [Work 지침](work/AGENTS.md)과 [실행 기준](work/workspaces/spec-and-tickets/EXECUTION-CRITERIA.md)의 수행 계약. |
| 현재 본문과 그 형성 자료를 어떻게 구성하고 함께 유지하는가 | [CONTENT-POLICY](CONTENT-POLICY.md)가 설명하는 체계 지침. |
| Project 내용을 어떤 기준으로 나누고 각 본문에 무엇을 담는가 | [REFERENCE/composition](project/REFERENCE/composition.md)이 설명하는 체계 지침. 소문자 상세 파일에서도 구성 기준을 직접 소유한다. |
| 읽는 사람이 판단을 이어갈 수 있도록 문서를 어떻게 작성·갱신하는가 | 참고 예시인 `DOCUMENT-WRITING.md`의 역할. [확인한 설명](_background/system-guidance/evidence.md#문서-작성-지침의-참고-예시)에서 이 문서가 답하는 질문을 볼 수 있다. |
| 여행 데이터의 Local/Remote 책임과 보존할 약속은 무엇인가 | [제품 의미](project/common/product.md)와 [Selective Local-First 결정](project/decisions/0001-selective-local-first.md)이 맡는 제품 본문. |
| 그 기준을 왜 택했고 어떤 조건에서 바꿨는가 | 관련 형성 맥락·기록·근거. 현재 적용할 지침과 구별해서 읽는다. |

예를 들어 계약서를 **어떻게 충분한 설명과 근거로 작성할지**는 문서 체계의 기준이고, 그 계약서에서 **어떤 제품 동작을 약속할지**는 제품 내용의 판단이다. 문서라는 형식만으로 모두 같은 역할이 되지는 않는다.

한 파일에 여러 역할이 함께 있을 수 있다. README가 공통 판단과 자료 안내를 함께 담거나, 기여 안내가 검토 절차와 코드 표현 규칙을 함께 담을 수도 있다. 각 내용이 맡는 판단을 먼저 구별하고, 읽거나 바꾸는 필요가 있을 때 분리를 판단한다. 모든 파일을 하나의 종류로 분류하거나 별도 폴더로 옮길 의무는 없다.

## 진입 본문과 상세 지침은 같은 내용을 다른 범위에서 맡는다

**체계 지침은 내용의 성격이고, 진입 본문은 그 내용을 찾아 읽는 역할이다.** 모든 체계 지침이 전체 체계의 입구일 필요는 없다.

진입 본문은 해당 체계를 다룰 때 찾아오는 위치에서 목적·적용 조건·공통 기준과 전체 관계를 직접 설명한다. 필요한 상세로 연결하더라도, 독자가 그 자리에서 이해해야 할 핵심을 여러 링크에서 다시 조립하게 만들지 않는다. 진입점이면서 실질 본문을 맡는 문서를 파일 목록이나 새 위치 안내로만 바꾸면 원래 맡던 설명이 사라진다.

상세 지침은 독립적으로 찾아 읽거나 다른 이유로 갱신할 내용을 나누어 맡는다. `REFERENCE/composition.md`처럼 소문자 파일이나 하위 폴더에 있어도 자기 범위의 현재 기준을 직접 설명한다. 상세로 나누었다는 이유로 효력이 약해지거나 형성 자료가 되지 않는다. 사례·조건별 절차 역시 현재 지침을 사용하는 내용이면 본문으로 다룬다.

기존 진입 본문을 나눌 때는 먼저 그 파일에 남을 공통 판단과 새 문서가 맡을 상세를 정한다. 원래 이름으로 찾아오는 독자는 여전히 담당 범위와 필요한 기준을 이해하고, 어떤 조건에서 상세를 읽을지 알 수 있어야 한다. 한 파일에 모든 내용을 유지하는 것도, 이름만 남기고 본문 전체를 다른 곳으로 보내는 것도 기본 해법은 아니다.

## 이름과 첫 설명에서 맡은 책임을 드러낸다

문서의 제목과 첫 설명에는 담당 영역, 독자가 적용할 상황, 이 본문이 정하는 기준을 밝힌다. “체계 지침”이라는 분류명만 붙이는 것으로 설명을 대신하지 않는다. 예를 들어 CONTENT-POLICY의 첫 설명은 본문·형성 자료의 구성과 수정이라는 범위를 직접 알리고, development 스킬은 맥락을 판단과 개발 결과로 연결하는 책임을 알린다.

대표로 찾아 읽는 체계 지침을 새로 만들 때는 `CONTENT-POLICY.md`, `SYSTEM-GUIDANCE.md`처럼 **담당 내용을 나타내는 대문자 파일명을 Noline의 기본 표기로 사용한다.** 대문자는 발견을 돕는 표시다. 일반 본문 묶음의 `INDEX.md`·`INDEX.<내용 이름>.md`에도 대문자를 사용하므로, 대문자만으로 체계 지침을 구별하지 않는다. 담당 내용과 진입·상세의 실제 역할을 함께 본다. 모든 체계 지침에 대문자를 요구하거나, 파일명의 대소문자로 권한·우선순위·필수 읽기를 결정하지 않는다. 기존 `composition.md` 같은 세부 지침과 유효한 이름을 일괄 개명하지 않는다.

기존 이름·위치가 사람이나 다른 지침에서 직접 찾아오는 경로라면 그 연결도 문서 역할의 일부다. 형성 자료를 추가하거나 주변 본문을 폴더로 묶는 작업만으로 이 경로를 옮기지 않는다. 진입 구조를 바꿀 필요가 있을 때는 실제 읽기 경로와 책임을 함께 판단하고, 변경이 정해진 범위에서 본문과 참조를 맞춘다. 위치 변경이 이미 요청된 작업에 승인 단계를 다시 추가하는 규칙은 아니다.

## 형성 자료를 가까이 두면서 본문 책임을 유지한다

체계 지침에도 의도·배경·목적과 중요한 선택·전환 이유가 필요하다. 현재 지침은 적용할 기준을 설명하고, 형성 자료는 그 기준이 왜 남았는지 이해하거나 수정·재검토할 때 읽는다. 일상 적용에 필요한 조건과 예외는 본문에 남긴다.

형성 자료를 가까이 두는 데 본체의 이동이 전제되지는 않는다. 이 문서는 `SYSTEM-GUIDANCE.md`에서 기준을 설명하고 `_background/system-guidance/`에서 형성 자료를 찾게 한다. CONTENT-POLICY도 같은 이름의 본문과 자기 형성 자료를 연결한다. 이는 현재 진입 책임을 유지한 배치이며, 모든 체계 지침에 같은 경로나 파일 수를 만드는 서식은 아니다. 자료별 역할과 갱신 조건은 [공통 관리 원칙](CONTENT-POLICY.md)을 따른다.

## 기존 체계에 적용할 때 확인한다

지침을 추가하거나 나누는 사람은 기존 본문과 들어오는 참조를 읽고, 어떤 설명을 어디에서 계속 소유할지 확인한다. 작성 뒤에는 그 문서를 처음 찾는 독자의 질문에서 출발해 담당 기준·적용 조건·필요한 상세를 실제 본문에서 찾을 수 있는지 살핀다. 의미나 적용 범위를 바꾸었다면 관련 형성 자료도 대조한다. 링크가 연결됐다는 사실과 내용을 이해하고 적용할 수 있다는 사실은 구별한다.

Noline의 **Work는 기존 current·Spec·Ticket·source·output·records와 갱신 제약을 유지한다.** 개발 실행과 기록은 [Work 지침](work/AGENTS.md)과 기존 Spec·Ticket 계약을 따른다. 체계 지침이라는 역할을 붙였다는 이유로 개인 기준·제품 계약·작업 기록의 소유 관계를 바꾸지 않는다.
