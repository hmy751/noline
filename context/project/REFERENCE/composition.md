# 내용 선별과 주제 구성

Project context를 작성·복원하거나 기존 본문을 합치고 나눌 때 읽는다. 목적은 조사 결과를 빠짐없이 쌓는 것이 아니라, 다음 관련 작업이 제품의 의미와 계약·현재 현실을 다시 추론하지 않고 판단할 수 있게 하는 것이다. 구조·권위는 [Project README](../README.md), 실제 변경 권한과 갱신 절차는 [관리 계약](../MAINTENANCE.md)을 따른다.

## 다음 작업이 반복해서 물을 질문에서 시작한다

먼저 누가 어떤 관련 작업에서 무엇을 이해해야 하는지 잡고, 그 질문에 답하는 본문을 구성한다. Ticket·회의·조사 파일·검증 묶음은 근거를 찾는 단위다. 파일뿐 아니라 본문 안의 절·목록·사례도 다음 독자가 이해할 관계에 따라 묶는다. 여러 Ticket 요약을 한 파일에 모았더라도 읽는 질문과 설명의 흐름이 원자료를 그대로 따라가면 주제별 본문으로 다시 구성해야 한다.

좁은 주제도 반복해서 찾을 이유가 분명하면 독립 문서가 될 수 있다. 반대로 여러 항목을 조사했다는 사실만으로 각각의 문서가 필요하지는 않다. 예를 들어 통화별 금액의 의미를 다루는 본문은 좁아도 유효할 수 있고, API 관련 작업의 계약은 여러 기능에 걸쳐 하나의 가이드에서 설명하는 편이 나을 수 있다. 이는 특정 파일명이나 배치를 요구하는 예시가 아니다.

## 남길 가치와 독립 문서의 필요성은 다르다

제품 목적, 채택한 의미와 제약, 선택 이유, 드러나지 않는 관례, 오해하기 쉬운 예외, 여러 구현 경로 사이의 관계는 다음 판단에서 다시 필요할 수 있다. 현재 지원·적용 범위나 검증의 한계도 다음 작업의 판단을 바꾸면 보존할 가치가 있다.

코드에 있는 내용이라고 일괄 제외하지 않는다. 함수 하나가 날짜를 문자열로 바꾼다는 사실은 쉽게 찾을 수 있지만, 여러 응답 경로에서 같은 표현을 지켜야 한다는 관계는 여러 파일을 종합해야 이해할 수 있다. 일반 조회와 기기 간 동기화에서 삭제된 데이터를 달리 취급하는 이유처럼, 구현에서 보이는 차이가 어떤 의미를 갖는지 설명하는 것도 가치가 있다.

한편 정확한 dependency 버전, 함수 목록, 당시 테스트 개수처럼 한 파일·명령·기록에서 쉽게 찾을 수 있는 사실을 계속 복제하면 별도 관리비용이 생긴다. 특정 버전 제약이 선택을 바꾸는 경우에는 제약과 이유를 남기고 실제 값의 Owner로 연결할 수 있다. 자기 범위를 충분히 설명한다는 이유로 모든 구현 세부와 실행 결과를 복제하지 않는다.

남길 가치가 확인돼도 기존 주제 본문에서 충분히 설명할 수 있는지 먼저 본다. 별도 파일은 읽는 상황, 의미 범위나 갱신 책임을 분리할 실제 이점이 있을 때 만든다. 파일 수의 최소화나 최대화가 목표는 아니다.

## 한 주제의 의미가 이어지게 쓴다

정의·규칙·이유·예외·주의점을 독자가 함께 이해할 수 있게 배치한다. 그 본문을 읽는 작업에 공통으로 필요한 설명은 본문에 두고, 일부 작업에만 필요한 상세는 읽을 조건을 밝혀 분리한다. 내용의 종류나 길이만으로 파일을 기계적으로 나누지 않는다.

문단은 설명을 발전시키고, 제목은 독자가 찾을 질문을 드러내며, 목록은 독립된 조건이나 순서를 보여 주게 한다. 조사 순서와 출처별 요약을 본문의 구조로 그대로 옮기지 않는다. 계약·이유·적용이라는 말을 모두 제목으로 만들기보다 주제에 맞게 연결해 설명한다.

기준 본문은 하나로 유지하되 다른 문서를 이해하는 데 필요한 전제를 짧게 재서술할 수 있다. 재서술은 두 번째 독립 정책이 아니며, 의미가 바뀌면 영향을 받는 설명도 맞춘다. 링크는 코드·상세 근거·다른 주제를 확인하는 경로다. 자기 범위의 뜻을 여러 링크에서 독자가 조립하게 맡기면 본문이 충분하지 않다.

### 작업 가이드의 구체성

예를 들어 API 가이드는 공유 schema를 지키라는 말만으로 끝나지 않는다. 요청·응답 검증과 데이터 변환의 책임, 기능별 적용, 관련 변경에서 함께 확인할 경계까지 이해할 수 있게 한다. Schedule과 Expense처럼 서로 다른 적용이 있다면 공통 계약에 이어 그 차이를 설명할 수 있다.

가령 일반 조회가 삭제된 일정을 제외하고 동기화는 삭제 사실을 다른 기기에 전달해야 한다면, 두 경로에 같은 필터를 적용하면 안 되는 이유와 변경 시 확인할 관계를 함께 설명한다. 이는 문서 구성의 설명용 사례이며 이 reference가 Noline의 새로운 API·삭제 정책을 채택하는 것은 아니다. 실제 제품 계약과 근거는 해당 주제의 Owner에서 확인한다.

관련 작업 대부분이 함께 읽어야 한다면 한 본문으로 두고, 기능별 상세 때문에 무관한 내용을 많이 읽게 된다면 공통 본문과 조건부 하위 자료로 나눌 수 있다. 모든 API를 한 문서로 합치거나 Entity별 파일을 반드시 만드는 규칙은 없다.

작업 방법을 설명하는 사례는 독자가 어떤 조건에서 판단을 달리해야 하는지 보여 주도록 고른다. 예를 들어 부분 실패 뒤 값을 보존하는 방법을 설명하려면 실패 시점과 남겨야 할 결과의 관계가 필요하다. 그 작업에서 바꾼 함수와 모든 실패 분기를 함께 싣는 것은 다른 목적이다. 사례를 더할 때에는 기존 설명에 없던 판단을 이해하게 하는지 보고, 같은 판단을 반복한다면 대표 사례에 통합한다. 해당 기능 자체의 계약을 설명하는 본문에서는 필요한 세부를 충분히 유지한다.

## 주 책임을 고르되 문장을 층별로 흩뜨리지 않는다

[세 층의 역할](../README.md#층별-책임)에 따라 본문이 주로 답하는 질문의 위치를 고른다. 두 층에 걸친 전제가 있다는 이유만으로 모든 주제에 세 문서를 만들지 않는다.

`common`과 `guidance`는 추상성과 상세함으로 구별하지 않는다. 제품·데이터 의미와 핵심 제약은 기술적이어도 common의 설명일 수 있다. 여러 API가 함께 지킬 개발 계약은 여러 곳에 공통이라는 이유만으로 common으로 올리지 않고, 관련 작업의 적용·변경 기준을 소유하는 guidance에 둘 수 있다. Guidance는 조언이나 순서만이 아니라 계약·이유·판단·구체적인 적용·검증을 포함하는 작업 가이드다.

`current`에는 현재 구현·지원·적용 관계와 그 지위, 다음 판단을 바꾸는 검증 범위 등을 설명할 수 있다. 완료된 구조와 지원 범위도 대상이며, 미정이나 결함 목록으로 한정하지 않는다. 별도 본문을 구성할 때에는 관련 가이드와 나란히 읽고, 독자가 current를 추가로 읽어 무엇을 더 판단할 수 있는지 확인한다. 가이드가 맡은 구체 적용을 현황이라는 이름으로 다시 설명하거나 한 코드 파일의 함수 흐름을 복제하는 데 그친다면 기존 본문에 통합하거나 코드로 연결한다. 여러 경로의 실제 연결·지원 범위·증거 관계를 함께 이해해야 한다면 그 추가 설명을 current에 둘 수 있다. 두 본문을 이해하는 데 필요한 짧은 전제 재서술은 허용하되, 같은 계약의 상세를 각각 관리하게 만들지는 않는다. 내용을 정리한 뒤 독립적으로 읽을 이유와 갱신 비용을 다시 판단하며, 편입 항목이나 크기를 미리 고정하지 않는다.

`decisions`는 중요한 선택의 이유·기각안·재검토 조건을 보존한다. 현재 본문에도 이해에 필요한 짧은 이유를 두고, 상세 선택 과정이 필요할 때 결정 기록으로 연결한다. 한 Workspace의 진행·시행착오·검증 이력은 그 Workspace의 기록에 남긴다.

## 근거와 열린 판단을 함께 설명한다

제품 의미의 근거는 코드뿐 아니라 채택한 제품 자료와 결정에도 있다. 초안·과거 계획·현재 구현이 있다는 사실만으로 요구나 지침을 새로 채택하지 않는다. 원자료의 유효한 뜻을 통합하고, 현재 의미를 바꾸려는 선택은 관리 계약의 결정권 경계를 따른다.

일부가 불확실하더라도 확인한 목적·사용자 장면·관계를 축소하지 않는다. 미정인 제품 선택, 확인하지 못한 사실, 서로 충돌하는 근거를 구별해 관련 설명 가까이에 남긴다. 세 층은 확실성 등급이 아니므로 불확실한 문장을 모두 current로 옮기거나 모든 문장에 상태 표시를 붙이지 않는다.

검증 근거는 적용 범위와 함께 서술한다. 대역으로 확인한 API 경계를 실제 인증·DB·배포까지 확인한 것으로 확대하지 않으며, 한계만 나열해 확인된 동작과 지원 범위를 지우지도 않는다. 과거 pass·실패와 당시 도구 오류는 현재 지원이나 다음 검증 선택에 영향을 주는 경우 그 관계와 재확인 조건을 설명한다. 구체적인 실행 이력은 근거 기록에서 찾게 한다.

본문의 적용 범위와 열린 판단은 편입 작업에 참여하지 않은 독자도 이해할 수 있게 제품·기능·경로의 말로 설명한다. 예를 들어 일부 API 경계만 확인했다면 확인한 경로와 남은 확인을 직접 밝힌다. “이번 Ticket 범위 밖”, “이번 Owner 이동에서 채택하지 않음”만으로 현재 의미를 대신하지 않는다. Ticket과 편입 이력은 출처·선택 이유를 확인하는 데 필요한 위치에서 연결하고, 확인하지 않은 범위를 설명하려고 관련 없는 후속 작업 전체를 조사하지 않는다.

## 문서와 읽을 조건을 함께 구성한다

각 본문에서 무엇을 설명하고 어떤 작업에서 읽을지 알 수 있어야 한다. 추가 링크는 상세 근거인지, 다른 의미를 확인할 때 읽을 문서인지 구분한다. 별도 YAML 항목이나 공통 목차를 요구하지 않으며, 일반적인 도입 문장과 링크 설명으로 충분하면 그대로 쓴다.

새로 구성한 본문은 [읽기 기준](reading.md)에 따라 관련 작업에서 찾아 보고, 그 본문만으로 맡은 의미를 이해한 다음 코드로 내려갈 수 있는지 확인한다. 모든 관리 기준을 제품 작업의 기본 입력에 넣어 이 문제를 해결하지 않는다.
