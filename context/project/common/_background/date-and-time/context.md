# 저장 형태와 사용자가 보는 날짜를 함께 보존했다

[날짜와 시각](../../date-and-time.md)의 선택 이유를 설명한다. 2026-10-02 경비 날짜·연결 결정, 2026-10-06 도시 시간대 결정과 후속 코드 대조를 바탕으로 구성했다. 새 제품 약속이나 날짜 명칭을 추가한 문서가 아니다.

## 같은 날짜 규칙을 저장 전 경계에서 적용했다

Expense entity의 date는 이미 YYYY-MM-DD였지만 수정 폼은 datetime을 보내 요청 검증에서 거부될 수 있었다. 이전 서버 serializer 통일은 DB row를 응답으로 바꾸는 단계였으므로 그 전에 거부되는 요청을 해결하지 못했다. 직접 HTTP 함수만 보정해도 Local 저장과 entity HTTP adapter를 거치지 않는 sync 전송이 남았다.

공유 schema가 날짜 의미와 legacy 호환을 소유하고 Repository 분기 전·서버 요청에서 같은 규칙을 적용하도록 정했다. 폼은 날짜를 만들고 serializer는 응답을 만드는 책임을 유지한다. 중복 보정은 줄지만 서로 다른 입력 경계가 같은 계약을 사용하는지 함께 확인해야 하는 비용이 있다.

기존 offset datetime은 기존 serializer와 동일한 UTC 날짜로 받는다. 예를 들어 2026-10-02T01:00:00+09:00의 호환 날짜는 2026-10-01이다. 입력자가 생각했던 현지 날짜를 복원하는 약속이 아니며, 원래 date-only는 이동시키지 않는다. 기존 Local 행은 읽을 때, 큐는 서버 입력에서 수용하고 PostgreSQL timestamp·응답 serializer를 유지해 일괄 데이터 migration을 하지 않았다. 결제일/사용일이라는 명칭과 날짜가 다른 일정 연결은 각각 별도 제품 의미다.

## UTC 저장을 유지하면서 도시 시간대를 명시했다

서울에서 계획한 여행을 현지나 다른 국가에서 열어도 같은 여행 날짜와 예약 시각을 보게 하려는 선택이다. Trip이 IANA timeZone을 소유하고 기간·Schedule의 ISO datetime 저장은 유지했다. 고정 offset은 날짜에 따른 DST를 설명하지 못하므로 도시 시간대 대신 저장하지 않는다.

Trip 기간까지 date-only로 바꾸는 대안은 채택하지 않았다. 저장 형태 전반을 개편하지 않고 기준 시간대를 명시해 표시·묶기·달력 계산을 맞출 수 있기 때문이다. 대신 폼·화면이 같은 Trip 시간대를 전달하고 없는 시간대·DST를 명시적으로 처리해야 한다. Expense date-only는 그대로 두고 기본 오늘과 연결 일정 표시만 도시 기준으로 얻는다.

기존 timestamp만으로 과거 작성자의 현지 날짜를 확정할 수 없어 nullable column을 추가하고 행·큐를 보존했다. 읽기용 UTC 호환 표시와 확인 안내를 제공하며 시간대 확인만으로 기존 시점을 이동시키지 않는다. 기간 교정은 사용자가 명시적으로 날짜를 편집하는 일과 구별한다. 새 client는 시간대를 요구하지만 서버는 과거 큐를 위한 더 넓은 호환 입력을 수용한다.

종료일은 마지막 포함 날짜이며 이후 도시 달력 7일을 온전히 주는 활성화 유예를 택했다. 기존 종료일 자정+7일처럼 마지막 날을 다 포함하지 못하는 계산과 구별한다. soft-delete 보존 기간·미전송 큐 보호를 바꾼 선택은 아니다. 자정 DST 공백에서는 날짜의 첫 유효 시점을 쓰는 현재 helper의 구체 경계를 본문에 보완했다.

## 시간대 조회 성공과 저장 권한은 다르다

도시 좌표로 시간대를 알아내는 공개 조회는 canResolveTimeZone, 생성·수정은 policy.trip.create/update로 구별한다. 인증이 만료돼 공개 조회가 가능하더라도 새 여행·비활성 여행 저장까지 허용되지는 않는다. 활성 여행은 저장된 시간대로 Local 편집할 수 있다. 시간대 준비·실패·재시도는 폼이, 최종 연결·인증·Debug 쓰기 차단은 Router가 확인한다.

조회 요청은 실제 관측 기준, 버튼·안내는 기존 display 정책을 사용한다. 정책의 pending·재확인 행동을 단순 문구로 줄이거나 연결·저장 실패 때문에 초안을 버리지 않는다. 이 선택은 새로운 권한 체계를 추가하지 않았다.

## 다시 판단할 조건

한 Trip의 여러 도시, 항공편의 출발·도착 시간대나 DST 반복 시각 선택 UI를 지원하게 되면 단일 Trip 시간대가 충분한지 다시 판단한다. 기존 시점의 의미를 보존하고 일정별 시간대가 필요한 이유를 정의한다. 과거 timestamp의 의도를 증명하는 자료가 생기면 해당 데이터 복원 범위만 별도로 검토한다. 현재 구현의 일부 경로 차이를 이유로 사용자에게 약속한 같은 도시 날짜·시각 표시를 축소하지 않는다.
