# 여행 중 일정과 경비를 이어가는 제품 기준

Noline의 목적·사용자 장면·활성 여행의 의미와 보존할 데이터 관계를 판단할 때 읽는다. 이 본문은 해당 제품 의미의 Project 정본이다. 관련 개발의 조회·표시·복구 계약은 [여행 접근](../guidance/travel-access/INDEX.md), 저장·동기화·준비와 정리의 개발 기준은 [데이터 수명](../guidance/data-lifecycle/INDEX.md)이 맡는다.

## 여행 하나를 준비해 연결이 끊겨도 기록을 이어간다

Noline은 여행 중 연결이 끊겨도 일정 확인·기록과 경비 관리를 이어가기 위한 iOS 앱이다. 사용자는 필요한 여행 하나를 활성화하여 기기에 데이터를 준비한다. 모든 여행을 로컬에서 관리하는 복잡도와 저장 부담을 늘리지 않고, 실제 사용할 여행에 오프라인 준비와 변경 보존의 책임을 집중한다. 이를 Selective Local-First라고 부른다.

Trip은 여행 단위이고 Schedule과 Expense는 그 여행의 일정·경비다. 활성 여행의 데이터는 Local SQLite가 읽기·쓰기의 기준이며 로컬 변경은 동기화 큐에 남긴다. 비활성 여행의 데이터는 Server API가 기준이다. 활성화하지 않은 여행의 오프라인 내용 조회·저장과 새 여행의 오프라인 생성은 지원 범위가 아니다. 다른 여행이 활성화되어 있어도 새 여행은 서버에서 비활성 상태로 생성한다.

제품이 지키려는 결과는 불안정한 연결 때문에 핵심 입력을 잃지 않고, 연결과 인증이 복구되면 보존한 변경을 서버와 맞출 수 있는 것이다. 로컬 저장 성공, 서버 반영, 지도·경로 준비는 서로 다른 완료다. 활성화 표시나 동기화 호출의 종료만으로 모든 준비와 반영의 성공을 판단하지 않는다. 계정 종료와 데이터 보존의 상세는 [앱 실행·데이터 보존](../current/app-runtime/INDEX.md)이 설명한다. 지도 pack·경로의 준비 상태와 여행별 cleanup은 각각의 실제 처리 결과를 확인해야 하며 활성화 표시 하나로 대체하지 않는다.

## 저장 위치와 사용할 수 있는 기능을 구별한다

Activation Router는 지금 데이터를 어디서 읽고 쓸지 선택한다. Policy는 현재 조건에서 사용할 수 있는 기능과 화면 모드를 정한다. 지도·장소 검색·길찾기는 Trip처럼 사용자가 소유해 동기화하는 데이터가 아니므로 외부 서비스의 네트워크 조건을 따른다. 활성화한 여행도 온라인에서는 검색과 온라인 지도를 사용한다.

| 여행과 연결 | 일정·경비 데이터 | 검색·지도와 작성 경험 |
| --- | --- | --- |
| 활성·온라인 | Local 조회·저장, 별도 sync | 온라인 장소 검색·지도 사용 |
| 활성·오프라인 | Local 조회·저장 | 일정은 장소를 직접 입력하고 경비는 Local 일정에 연결 가능. 지도·경로는 미리 준비된 범위에 의존 |
| 비활성·온라인 | Server 조회·저장 | 온라인 기능 사용 |
| 비활성·오프라인 | 내용 조회·저장 제한 | 기존 여행 기본 정보·선택과 열린 초안을 아래 조건으로 보존 |

활성 여행의 오프라인 사용에서는 일정의 장소명·시간 같은 기록과 경비의 금액 기록을 먼저 남기는 것이 중요하다. 좌표는 일정 기록을 위한 필수 조건이 아니므로 장소를 직접 입력해 저장할 수 있다. 다만 좌표 없는 일정은 지도 마커로 표시되지 않는다. 장소명이 남아 있으면 검색이 허용될 때 수정 화면에서 사용자가 장소를 검색해 보완할 수 있다. 기록 저장과 지도에서 사용할 준비는 이처럼 서로 다르다. 관련 구현과 적용 범위는 [수동 기록과 좌표 보완](../guidance/travel-access/INDEX.md#수동-기록과-좌표-보완)을 따른다.

이 표는 기본 관계다. 연결이 아직 확인되지 않은 unknown은 원격 기능을 열지 않지만 확정된 offline과 안내를 구별한다. 기기 세션을 확인하지 못한 상태와 같은 계정의 재인증 대기도 다르다. 재인증이 필요해도 같은 계정의 활성 여행 Local 이용은 유지하며, 인증이 필요한 서버 요청과 새 sync는 막는다. 세션의 정확한 상태와 복원·종료는 [앱 실행 기준](../current/app-runtime/INDEX.md)을 따른다. Mapbox를 선택한다는 사실은 native 지도 pack의 존재·완료 보장이 아니다.

## 연결이 끊겨도 서로 다른 것을 보존한다

여행 목록의 기본 정보와 선택은 사용자가 어느 여행을 보고 있었는지 이어 주는 맥락이다. 이미 성공한 목록을 연결 제한·재조회 실패만으로 지우거나 선택한 여행이 서버에서 삭제됐다고 판단하지 않는다. 새 목록 조회의 Local fallback은 활성 여행과 세션 조건을 따르므로, 기존 표시를 유지하는 일과 모든 비활성 여행을 새로 오프라인 조회하는 일은 다르다.

일정·경비의 읽기 화면은 비활성 여행이 offline/unknown이면 캐시를 남겨도 내용 공개와 새 조회를 제한한다. 반면 정책이 허용되는 상태의 갱신 실패는 이미 얻은 내용을 유지하고 실패를 해당 영역에 표시한다. 최초 실패를 빈 목록이나 0원으로 대신하면 아직 알 수 없는 결과가 정상 결과처럼 보이므로 구별한다.

이미 열린 작성 초안은 사용자가 입력한 미저장 값이다. 제품 기준은 연결이 바뀌어도 기본 입력과 기존 연결 설명을 유지하고, 장소 검색·후보 선택·저장처럼 실행할 수 없는 영역만 제한하는 것이다. 복구가 자동 제출을 뜻하지 않으며 다시 저장할 때 최신 실행 조건을 확인한다. 화면 안의 초안 보존은 앱 종료 뒤 복원 기능을 약속하는 것이 아니다. 현재 일정 수정 화면은 수정 정책이 막히면 입력 영역 전체를 제한 안내로 바꾸므로 이 기준을 충족하지 못한다. 확인된 구현 차이와 범위는 [작성 계약](../guidance/travel-access/INDEX.md#작성과-읽기의-제한을-구별한다)에 구분한다.

예를 들어 비활성 여행의 경비를 작성하다 연결이 끊기면 제목·금액·기존 일정 연결은 남지만 새 일정 후보 조회와 서버 저장은 제한된다. 활성 여행이라면 연결 후보가 Local 일정이므로 오프라인에도 경비 연결·저장이 가능하다. 이 차이는 경비 입력과 외부 장소 검색을 같은 온라인 기능으로 다루지 않는 이유다.

표시·조회 우선순위, 재확인/재조회의 차이와 연결 변화 중 초안 보존은 [여행 접근](../guidance/travel-access/INDEX.md)이 맡는다. 검색 후보·선택창의 수명과 폼 초기화·앱 종료 뒤 복원은 이 연결 보존 약속만으로 정하지 않는다.

## 함께 지킬 데이터 관계

Expense는 Trip에 속하고 같은 Trip의 Schedule 하나에 선택적으로 연결할 수 있다. 경비 날짜와 일정 날짜는 독립적이므로 날짜가 다른 일정에도 연결할 수 있으며, 경비 날짜를 바꿔도 연결은 유지한다. 활성 여행에서는 오프라인에도 Local 일정으로 연결·변경·해제할 수 있다. 경비 날짜의 입력·전송·표시는 `YYYY-MM-DD`로 맞추며 기존 datetime 호환과 서버 저장 표현은 [날짜와 시각](date-and-time.md)을 따른다. 날짜를 결제일이나 사용일 중 무엇으로 부를지는 이 연결·표현 계약과 별개로 열려 있다.

통화는 자동 환산 합계로 섞지 않고 통화별로 관리한다. 여행의 기본 통화와 각 경비의 통화, 표시 자릿수와 저장 정밀도는 [통화와 금액](currency.md)에서 구별한다.

로컬 변경과 `sync_queue` 기록은 같은 transaction에 둬 한쪽만 남는 상태를 막는다. Entity ID는 클라이언트의 `generateId()`로 만들고 서버가 수용한다. `@repo/schema`의 Zod 계약에서 client/server 타입을 추론한다. 한 시점을 나타내는 값은 timezone을 포함한 ISO 8601 datetime으로 저장·전송한다. Expense `date`의 date-only 계약과 기존 입력·저장 호환은 [날짜와 시각](date-and-time.md)에서 구별한다. 서버는 인증과 사용자 소유권을 확인한다.

삭제·비활성화는 미전송 변경과 soft delete·cleanup 조건을 지켜 아직 서버에 반영하지 않은 입력을 보존해야 한다. 현재 여행별 정리는 PENDING 중심이어서 이 보존 계약을 모두 충족하지 못한다. FAILED·IN_PROGRESS, 귀속 불명 작업과 재활성화의 차이는 [데이터 정리 기준](../guidance/data-lifecycle/INDEX.md#여행을-정리할-때-모든-미전송-상태와-현재-활성-여부를-확인한다)에서 구별한다. 정책상 제한은 기존 `useAppPolicy`, `PolicyErrorDisplay`, `NetworkStatusIndicator`를 통해 사용자에게 설명한다. 상세 규칙은 [rules](../../../.claude/rules/README.md)와 [guards](../../../.claude/guards/README.md)가 유지한다.

## 지원 범위와 갱신

특정 릴리스의 완성, 실제 동기화 성공, 외부 지도·OAuth·DB의 운영 상태와 사람 acceptance는 이 문서가 보장하지 않는다. 현재 구조·확인 범위는 [구현 지도](../current/architecture.md), 선택 이유는 [Selective Local-First 결정](../decisions/0001-selective-local-first.md)과 [여행 접근의 형성 맥락](../guidance/travel-access/_background/context.md)에 있다.

현재 배포 대상은 iOS이며 Android 설정의 존재를 동등한 배포·검증으로 보지 않는다. 제품·domain 의미를 바꾸는 책임자는 위 지원 경계·데이터 관계와 영향받는 상세 본문을 함께 갱신한다. 기존 설명과 충돌하면 채택한 제품 의미와 실제 구현의 차이를 먼저 확인한다. 작업별 이관·검사 실행 결과는 각 Workspace가 소유한다.
