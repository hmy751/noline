# Project context 관리 계약

이 문서는 Project context를 작성·복원·재구성·갱신할 때의 시점, 변경 권한과 영향 범위, 반영 완료 기준을 소유한다. 구조·층별 책임·권위는 [Project README](README.md), 내용 선별·주제 구성·분리는 [구성 기준](REFERENCE/composition.md)이 소유한다. 관리 작업을 수행하는 주체는 이 문서와 구성 기준을 직접 읽고 적용한다.

## 언제 무엇을 반영하나

여러 작업의 이해·판단·행동에 계속 영향을 줄 변화가 명확해지거나, 사용자가 기존 Project 맥락의 복원·재구성·승인된 Owner 이동을 요청하면 [update-project-context](../../.agents/skills/update-project-context/SKILL.md)를 사용한다. 명확해진 경계에서 수행하며 Workspace 종료를 기다리지 않는다. 작업 완료 자체는 새 Project 문서를 만들 근거가 아니다.

현재 Workspace와 요청에 필요한 source·record·output, 관련 제품 문서와 코드·테스트만 대조한다. 일시적인 방법·후보 전체·실행 이력은 Work에 남기고, 계속 필요한 의미는 기존 주제의 본문에 통합한다. 코드에 있다는 이유로 의미를 제외하거나 모든 구현 사실을 문서에 복제하지 않는 판단은 구성 기준을 따른다.

과거 자료는 현재 뜻과 대체 관계를 확인하는 근거다. 조사 범위에서 허용한 자료만 읽고, archive·source·기존 날짜별 record의 원문을 현재 답으로 덮어쓰지 않는다. 중요한 선택 이유를 별도로 남길지는 [decisions 기준](decisions/README.md)에 따른다.

## 근거와 결정 권한

현재 권위가 확인되었거나 사용자가 재구성을 허용한 기존 의미는 근거를 추적할 수 있게 복원한다. 확인된 사실의 재서술, 유효한 의미의 통합과 미정·미확인·충돌의 보존은 새 제품 결정을 내리는 것과 다르다. 초안·과거 계획·현재 구현만으로 제품 요구나 Project-wide 계약이 채택되지는 않는다.

새로운 제품 목적·핵심 domain 의미·중요 제약이나 상충하는 근거 사이의 선택은 사용자 또는 명시된 책임자가 결정한다. 이미 승인된 범위의 반영을 같은 결정 요청으로 되돌리지 않는다. 충돌 때문에 확정할 수 없는 부분만 구체적으로 남기고, 근거가 지지하는 나머지 목적·사용자 장면·계약·현재 관계는 충분히 서술한다.

문서와 코드가 다르면 문서의 권위, 채택한 결정과 실제 구현을 함께 대조한다. 구현 사실의 요약 오류는 직접 근거에 맞추되, 구현과 제품 기준의 차이를 제품 정책 변경으로 조용히 해소하지 않는다.

## 바뀐 의미와 실제 영향을 따라 갱신한다

변경된 의미를 소유한 기준 본문부터 맞춘다. 새 내용을 끝에 누적하기보다 기존 구성에 통합하고, 대체된 설명·조건·현재 상태는 함께 정리한다. 분리·통합할 필요는 구성 기준으로 판단하며 책임 층이나 원자료 수를 파일 수로 바꾸지 않는다.

이어 그 변화 때문에 설명·적용·판단·읽기 경로가 실제로 달라지는 문서를 맞춘다. 다른 본문의 짧은 전제 재서술도 영향을 받으면 갱신 대상이다. 단순히 링크로 연결됐다는 이유만으로 전부 수정하지 않는다.

다음은 영향 범위를 구별하는 예시이며 고정 수정 목록이 아니다.

- 내부 helper만 바뀌었다면 실제 위치·방식을 설명한 부분을 대조한다. 제품 의미나 변경되지 않은 API 계약까지 갱신하지 않는다.
- 공통 API 처리 계약을 바꿨다면 그 기준 본문과 영향을 받는 기능별 적용·검증 설명을 함께 맞춘다.
- 날짜의 제품 의미를 결정했다면 그 의미를 소유한 본문과 관련 작업 가이드를 맞춘다. 구현이 아직 따르지 못한 차이는 필요한 현재 맥락으로 보존하되, 반드시 별도 current 파일을 만들지는 않는다.

문서의 읽을 조건도 내용의 일부로 관리한다. 주제 범위·이름·경로가 달라지면 Project README와 해당 층의 색인, 실제 소비자의 선택 이유·주변 설명을 대조한다. 문서가 없는 상태를 링크만 남겨 완성된 경로처럼 보이지 않게 한다.

## 승인된 주제별 Owner 이동

기존 상세 Owner의 현재 의미를 Project로 옮기는 승인은 주제·책임 범위로 한정할 수 있다. 승인된 범위는 의미와 권위를 함께 전환하되 관련 없는 문서 전체 개편으로 넓히지 않는다.

1. 이동할 의미와 반복해서 읽을 작업, 기존 기준 본문과 현재 소비자를 확인한다.
2. 구성 기준으로 온전한 주제 본문을 구성하고 주 책임에 맞는 층에 둔다. 모든 주제에 세 층의 문서를 만들거나 분류를 위해 의미를 흩뜨리지 않는다.
3. 기존 자료의 유효한 뜻을 새 Owner에 통합한다. 제품 선택이 필요한 충돌은 구체적으로 열어 두고 나머지를 먼저 반영한다.
4. 이전 문서는 실제 남은 역할에 따라 구현 상세·근거·역사·호환 routing으로 좁히거나 현재 문서 규칙에 따라 이동·제거한다. 같은 현재 답을 독립적으로 소유하는 경쟁 canonical을 남기지 않는다.
5. 주제별 진입점과 영향받는 live Workspace의 선택·사람용 current·output을 [Workspace collection의 reconciliation 계약](../work/workspaces/README.md)에 따라 맞춘다. 과거 Workspace 전체를 역동기화하지 않는다.

새 파일이 존재한다는 사실만으로 이동이 끝나지 않는다. 선택된 본문에서 해당 의미와 적용·열린 판단을 이해할 수 있고, 이전 문서와 현재 권위 관계가 하나로 이어져야 한다.

## 반영 완료 확인

새로 구성하거나 크게 재구성했다면 [읽기 기준](REFERENCE/reading.md)으로 다음 독자가 맡을 대표 관련 작업을 정하고, Project README에서 필요한 본문을 찾아 적용해 본다. 그 작업은 본문이 실제로 답해야 할 제품 이해나 변경 판단이어야 한다. 해당 주제를 처음 보는 독자가 제품 이해라면 사용자 장면·목적·domain 관계를, 관련 개발이라면 계약·이유·구체적인 적용과 현재 범위·예외·확인할 근거를 선택한 본문에서 설명할 수 있는지 확인한다. 작성 중 읽은 원자료나 대화의 기억으로 본문의 빈칸을 대신하지 않는다. 모든 문서에 같은 항목이나 목차를 채우지는 않는다.

핵심 뜻을 상세 Owner에서 다시 조립해야 하거나 경로와 방어적 한계만 남았다면 미완성이다. 본문에서 의미를 이해한 뒤 실제 코드·자료와 대조하여 사실·권위·검증 범위가 맞는지 확인한다. 필요한 내용은 충분히 유지하면서 무관한 읽기를 늘리지 않았는지도 본다.

일반 갱신에서는 바뀐 기준과 그 기준을 소비하는 설명이 함께 맞는지 확인한다. 분리·통합했다면 관련 계약이나 구현이 달라지는 경우를 하나 짚어 어떤 본문을 왜 갱신할지 찾아본다. 필요한 내용을 놓치거나 같은 상세를 여러 곳에서 독립적으로 고쳐야 한다면 구성 기준에 따라 책임과 설명을 맞춘다. `current`는 관련 가이드와 코드를 읽은 뒤에도 그 본문이 추가로 가능하게 하는 판단과 갱신 비용으로 평가하며, 존재·축소·파일 수를 검증 결과처럼 미리 정하지 않는다.

Local link·diff·설치 검사는 경로와 형식을 확인할 뿐 의미 충분성이나 실제 읽기 효과를 증명하지 않는다. 확인한 대표 작업에서 본문으로 이해할 수 있었던 판단과 남은 부족함을 근거로 구성 결과를 평가한다. 파일 배치나 링크가 개선됐다는 사실만으로 본문 구성까지 완료됐다고 판단하지 않는다. 작성자의 대조, 다른 독자의 적용, 실제 제품 실행으로 확인한 결과를 구별하며 독립 검토를 매번 필수 절차로 추가하지 않는다. 문서 갱신을 제품 검증·acceptance·Workspace 완료로 확대하지 않는다.

## 실행 장치와 보고 경계

[update-project-context](../../.agents/skills/update-project-context/SKILL.md)는 위 계약을 실행한다. Workspace Maintain의 쓰기 범위는 Project로 넓히지 않는다. Project path·책임·권위 변경으로 live consumer가 영향받으면 Main은 Work 계약에 따라 reconciliation을 전체 작업 안에서 이어 간다. Skill 자체가 제품 코드·테스트나 Workspace의 machine 상태를 수정할 권한을 얻는 것은 아니다.

반영한 의미와 위치·근거, 통합·분리와 영향 범위의 중요한 이유, 남은 판단과 확인 한계를 보고한다. 근거가 있어도 반영하지 못한 내용은 이유를 밝힌다. 읽거나 수정한 모든 파일과 조사 항목을 보고 목차로 옮기지는 않는다.

Skill을 교체하거나 제거해도 사람이 이 계약과 각 내용 Owner를 따라 같은 갱신 책임을 수행할 수 있어야 한다. 호출 경로는 root [AGENTS.md](../../AGENTS.md)와 [운영 skill 색인](../../.claude/skills/README.md)이 연결한다. 설치·호출만으로 실제 반영이나 의미 판단의 충분성을 주장하지 않는다.

작성과 책임 배치에 `ai-system_instruction-clarity.md: 적용`, `ai-system_context-ownership-boundary.md: 적용`, `ai-system_responsibility-cohesion.md: 적용`, `ai-system_human-readable-structure.md: 적용`, `ai-system_behavior-responsibility-allocation.md: 적용`, `ai-system_harness-rippability.md: 적용`.
