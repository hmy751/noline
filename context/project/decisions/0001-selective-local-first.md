# 0001. Noline은 Selective Local-First와 Activation Router를 사용한다

- 상태: 채택
- Project common context 편입일: 2026-09-04

## 결정과 선택 이유

활성화된 여행의 sync-owned data는 Local SQLite를 기준으로 다루고, 비활성 여행은 Server API를 기준으로 다룬다. 모든 여행을 오프라인 편집 대상으로 만들기보다 사용자가 준비한 여행에 저장·동기화 책임을 집중한다. Trip·Schedule·Expense의 local/remote 선택은 Activation Router가 소유한다. 새 여행은 아직 활성화되지 않았으므로 서버에서 생성하고, 다른 여행의 활성 상태를 생성 위치의 근거로 쓰지 않는다.

지도·검색·길찾기는 사용자 소유 데이터를 동기화하는 책임과 다르다. 활성 여행의 데이터가 Local에 있다는 이유로 온라인 서비스까지 제한하지 않도록 Policy Layer가 네트워크 조건에 맞는 기능·표시 모드를 정한다. 클라이언트는 Entity ID를 만들고 서버는 이를 수용한다. Local mutation과 `sync_queue` 기록은 같은 transaction에 두며 `@repo/schema`는 client/server 계약의 원천이다.

## 모든 여행의 자동 Local 저장에서 선택적 준비로 바꾼 이유

2025-11-06 활성화 설계의 출발점은 모든 여행을 자동 Local 저장하던 구조에 오프라인 지도까지 붙일 때의 저장 공간 부담이었다. 당시 문서는 도시별 지도 용량을 크게 예상했고, 실제 사용 장면을 온라인에서 여러 여행을 계획한 뒤 출발 전에 필요한 여행을 준비하는 흐름으로 보았다. 전체 여행을 계속 저장하고 활성 여행에만 queue를 쓰는 대안은 저장 공간 문제를 해결하지 못했다. 여행 수를 제한하고 오래된 여행 삭제를 강제하는 대안은 임의의 제한과 데이터 손실 위험 때문에 거부했다. 필요한 여행의 상세 데이터와 지도만 선택적으로 준비하는 방향을 택했다. 당시 용량·기간 예상은 현재 저장량이나 성능의 실측 보장이 아니다.

비활성 여행에도 오프라인 편집을 허용하려던 초기안은 `temp_cache`와 서버 데이터의 merge, 버전 충돌, TTL과 cleanup을 함께 관리해야 했다. 원문에 기록된 사용자 판단은 “활성화을 위한 기능인데 비활성에 너무 많은 복잡도 투자”였다. 이 비용을 없애기 위해 비활성 여행의 상세 데이터는 서버에서 직접 다루고 온라인 연결을 요구하는 절충을 받아들였다. 목록에 필요한 metadata와 활성 여행의 전체 데이터를 구별한 것도 선택적 준비를 가능하게 하려는 설계였다. Metadata·상세·asset을 세 단계로 따로 관리하는 안은 당시 복잡도가 과하다고 보았고, 모든 자료를 활성화 때만 받는 한 단계 안은 목록용 metadata를 조회하지 못하는 문제가 있었다.

같은 날 후속 논의는 Router와 Sync를 종속 관계로 묶지 않았다. Router는 query/mutation 시점에 대상 여행의 저장소를 고르고, Sync는 Local 변경과 서버의 push/pull을 맡는다. 이 책임 구분은 활성화가 모든 동기화 동작의 이름으로 확장되는 것을 막는다. 현재 구체적인 동작·미전송 보호·준비 실패는 [데이터 저장·동기화·정리](../guidance/data-lifecycle/INDEX.md)에서 읽는다.

이 선택의 비용은 준비하지 않은 여행의 오프라인 편집을 제공하지 못하고 서버·네트워크에 의존한다는 점이다. 당시의 한 여행 제한, 종료 후 7일 자동 비활성화, 다운로드 시점은 설계안에 포함됐지만 같은 원문의 열린 질문이기도 했다. 이 문서는 이를 현재의 확정 수치나 구현 완료로 승격하지 않는다. [2025-11-06 설계 원문 보존판](../../../.claude/_archive/2026-10-31-project-context-reconstruction/history-integration/sessions/2025-11-06-activation-architecture-design.md.txt)은 당시 대안·예상·열린 질문을 추가 확인할 근거다.

## 비교했던 대안과 책임 경계

2025-11-20 Data/Service 분리 결정은 활성 여행에서 온라인 지도까지 제한되던 문제를 다뤘다. 온라인이면 데이터 Router도 Server 우선으로 바꾸는 대안은 미전송 변경과 데이터 소유권을 흔들 위험으로 기각했다. 사용자가 완전 온라인/오프라인 모드를 고르는 대안은 전환 판단의 복잡도를 사용자에게 넘긴다는 이유로 기각했다. 서비스 가용성과 데이터 소유권을 나누는 방식이 현재 선택이다. 당시 위험 판단과 현재 동작의 검증은 구별한다.

같은 날 Policy 책임 결정은 data hook 안에 UI 가용성 검사를 넣는 대안보다 화면·feature에서 Policy를 소비하고 data hook은 CRUD에 집중하는 구성을 선택했다. 이후 열린 초안 보존 계약에 따라 제한은 실행할 수 없는 영역에 적용한다. 당시의 전체 화면 교체 예시를 현재 폼에 그대로 적용하지 않는다. 선택의 최소 발췌와 후속 전환은 [여행 접근 형성 근거](../guidance/travel-access/_background/evidence.md)에 있다.

## 현재 이름이 뜻하는 것

2026-03-21 용어 정리는 모든 데이터가 Local 우선이라는 오해를 줄이기 위해 `Selective Local-First`를, 대상 여행의 활성 상태로 분기한다는 실체를 드러내기 위해 `Activation Router`를 선택했다. `Echo Protocol`은 클라이언트가 ID를 생성하고 서버가 수용하는 동작을 과하게 이름 붙인 표현으로 보고 `Client-Side ID Generation`으로 맞췄다. 오프라인 준비를 설명할 때의 ‘보험’은 준비의 의미이며 구독 결제 계약을 뜻하지 않는다. 과거 기록의 용어와 코드의 기존 파일·함수명을 일괄 바꾸는 결정은 아니었다.

## 현재 설명과 다시 판단할 조건

제품 장면과 보존할 데이터 관계는 [제품 기준](../common/product.md), 실제 책임 배치는 [현재 구조](../current/architecture.md), Router·여행 목록·Policy·화면 계약은 [여행 접근](../guidance/travel-access/INDEX.md)이 소유한다. 활성 여행의 범위, 비활성 여행의 오프라인 편집, 데이터와 서비스의 구분 또는 미전송 변경 보존을 바꾸는 요구가 생기면 이 선택과 해당 코드를 함께 재검토한다.

이 문서는 채택된 의미·이유를 보존하며 실제 sync·지도 준비·cleanup 성공이나 제품 검증 완료를 선언하지 않는다. 출처는 2025-11-06 활성화 설계, 2025-11-20 Data/Service·Policy 책임 결정, 2026-03-21 용어 결정과 이후 여행 생성·초안 보존 선택이며, 현재 읽기에 필요한 이유는 위 본문과 가까운 형성 근거에 담았다.
