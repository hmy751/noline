# 0003. Project는 세 층의 주제를 구성하고 의미·사실·읽기 경로를 따로 확인한다

- 상태: 채택. `current`의 독립 효용과 유지비용은 실제 관련 작업에서 계속 판단한다.
- 선택 시점: 2026-09-09, 2026-09-14의 후속 보완
- 통합 기록일: 2026-10-31

## 선택한 구조와 목적

Project는 다음 관련 작업이 제품 의미와 계약·현재 현실을 다시 추론하지 않고 판단하도록 구성한다. `common`은 제품·데이터·시스템의 의미와 핵심 제약, `current`는 현재 구현·지원·적용 관계와 판단에 필요한 증거 범위, `guidance`는 관련 작업의 계약·이유·구체적인 적용·검증을 맡는다. 세 층은 필수 물리 경계지만 모든 주제에 세 문서를 만들거나 모든 작업에서 순서대로 읽는다는 뜻은 아니다.

현재 구조·권위는 [Project README](../README.md), 내용 선별·분리는 [구성 기준](../REFERENCE/composition.md), 관련 작업의 선택·대조는 [읽기 기준](../REFERENCE/reading.md), 변경 권한·Owner 이동·완료는 [관리 계약](../MAINTENANCE.md)이 소유한다. 이 결정은 그 문서들이 왜 나뉘고 어떤 실패에 대응했는지 설명한다. 지침을 적용하는 스킬과 Workspace Maintain의 쓰기 범위를 새로 정하지 않는다.

## 분류·보관에서 다음 개발자가 이해할 본문으로 옮겼다

2026-09-09 보완은 지속 의미·현재 현실·조건부 기준을 물리 layer로 나눴다. 당시에는 기존 상세 Owner 전체를 다시 쓰면 승인 범위와 후속 리팩터링의 출발 상태가 불필요하게 바뀌므로 필요한 Project 재서술과 운영 연결만 바꾸었다. 이는 기존 상세 자료가 모두 최신이라는 판정이 아니었다. 09-10 후속 보완은 이전 flat 요약의 유효한 의미를 현재 layer에 통합하고, 현재 역할이나 호환 소비자가 없는 파일을 현재 경로에서 제거하는 방향으로 바꿨다. README의 구조·권위 안내와 MAINTENANCE의 관리 기준도 분리했다.

09-14 논의에서는 작업 결과의 주제별 책임은 보이지만 세부 current 문서가 늘고 계약·이유·구체 적용이 충분히 이어지지 않는 문제가 드러났다. 원문은 “작업 결과를 분류해 보존하는 것과 다음 관련 작업이 이해할 본문을 만드는 것은 다르다”고 구별했다. 사용자가 처음부터 guidance를 판단·적용을 포함하는 작업 가이드로 보았고 세 층을 의도적으로 요구했으므로, 폴더를 없애거나 guidance를 수행 순서로 좁히는 대신 반복해서 읽을 온전한 주제를 먼저 구성하기로 했다. 일부 작업에만 필요한 상세는 읽을 조건과 함께 나눌 수 있다.

그때 이미 만든 하위 제품 문서는 원복하고 지침부터 작업하기로 했다. 이는 제품 코드·Ticket·기존 기록의 원복이나 기존 본문과 코드의 전면 일치 확인이 아니었다. 후속 제품 본문화와 실제 수락을 지침 설치의 결과로 미리 선언하지 않은 이유다.

## 기준과 실행 장치를 나누되 추가 관리비용을 받아들였다

구성과 읽기는 소비 시점이 달라 REFERENCE의 별도 본문으로, 갱신 시점·권한·영향·완료는 MAINTENANCE로 나눴다. 스킬은 해당 기준을 적용하도록 했다. 사람이 직접 읽거나 다른 실행 장치가 적용해도 기준과 관리 책임이 남는 대신, 문서와 스킬·진입점의 연결을 함께 관리해야 한다.

09-14 원문에 기록된 외부 조사에서 Matt Pocock의 로컬 skills 자료는 쉽게 찾는 사실의 복제와 이유·관례·여러 경로의 관계를 보존하는 가치의 차이, 한 개념을 함께 설명하는 구성을 참고한 자료였다. Peter Steinberger의 로컬 agent-scripts 자료에서는 읽을 조건을 문서와 함께 관리하고 전제·계약·실행·검증을 연결하는 구성을 참고했다. 이 통합은 그 조사 기록에 의존하며 외부 저장소를 새로 검증한 결과가 아니다. 당시에도 `summary/read_when` 메타데이터나 문서 목록 도구를 도입하지 않았고, 외부 사례가 Noline의 세 층 크기나 관리 효과를 입증한다고 보지 않았다.

`current`는 미정·결함 목록만 담는 층으로 제한하지 않는다. 유용한 현재 정보가 있다는 것과 독립 파일이 필요하다는 것은 별도 판단이다. 가이드·코드에 더해 무엇을 판단할 수 있는지, 어떤 변화에서 다시 확인할지와 유지비용으로 평가하기로 했다. 편입 목록·문서 수·축소나 제거를 먼저 고정하는 선택은 보류했다.

## 첫 초안의 실패에서 확인 행동을 구체화했다

같은 09-14의 첫 적용은 기존 통화 의미를 누락하고, Expense 날짜의 사실 범위를 넓히고, 기존 runbook 연결을 놓쳤으며, current에 일회성 실행 이력을 쌓았다. 원실행 도구 기록이 없어 실행자가 무엇을 읽고 생략했는지는 확정하지 않았다. 기존 원칙에 이미 통합·코드 대조·읽기 경로·current 효용이 있었으므로 사례별 금지문을 더하는 대신, 초안 전 대조 기준과 초안 후 확인 행동을 연결했다.

- 기존 Owner의 보존할 의미·직접 확인할 구현 경계·새 결정이 필요한 선택·실제 소비 진입점을 쓰기 전에 파악하고, 초안 뒤 보존·갱신·의도적 제외를 대조한다. 짧아지거나 구조가 좋아진 사실은 의미 보존을 증명하지 않는다.
- 한 사실 문장이 form·request·local 저장·server response 등 여러 경계를 함께 설명하면 각 경계를 대조하거나 확인한 범위로 문장을 좁힌다. 구현 차이와 채택할 제품 의미를 구별한다.
- Project README뿐 아니라 같은 작업의 active runbook·workspace guide·호환 문서·skill 같은 대표 진입점에서 현재 Owner까지 따라간다. 링크의 존재만으로 본문 이해와 실제 적용을 증명하지 않는다.

이는 매번 고정 양식·모든 링크의 일괄 순회·독립 reviewer를 추가하는 선택이 아니다. 의미 보존, 사실 범위와 실제 읽기 경로가 서로 다른 실패이므로 한 번의 형식 검사로 합치지 않기로 한 것이다. 작업과 관계없는 실행 수치·당시 도구 오류는 Work 기록에서 찾도록 했다.

## 재시험이 지지한 것과 다시 판단할 조건

09-14 후속 결정은 제품 초안이 없던 기준의 격리 worktree에 수정 지침만 적용하고 별도 실행으로 재시험한 결과를 기록했다. 앞선 네 실패의 정답과 예상 파일명은 요청에 주지 않았다. 새 결과는 통화 의미를 이어받고, 날짜의 여러 구현 경계를 구별하고, 기존 consumer를 새 Owner로 연결하고, current에 다음 검증 선택과 재확인 조건을 남기는 네 관찰에서 개선을 보였다.

이 결과는 한정된 지침 효과의 근거다. 당시 하네스 전체 검사에는 기준 tree의 기존 누락 링크 실패가 남았고 제품 검사는 재실행하지 않았다. 재시험 산출물을 현재 제품 본문에 그대로 복사하거나 지침 설치·Recover 성공을 실제 host 자동 발견, 모든 문서의 수락, 이후 세션의 효과로 확대하지 않았다. 정확한 실행 조건·판본·검사 이력은 아래 보존판에 남아 있다.

다음 독립 갱신에서도 의미 누락, 미확인 경계의 일반화, README 밖 소비 경로 누락, 판단 효용 없는 실행 이력이 반복되면 문구만 더하지 않고 실행 단계의 검증 배치와 독립성 필요를 다시 판단한다. current의 추가 이해가 유지비용을 정당화하지 못하거나 주제 분리가 계약·이유·적용을 다시 조립하게 만들면 해당 본문 구성을 재검토한다. 문서 수나 검사 통과 수만으로 이 선택의 성공을 판정하지 않는다.

## 형성 근거

2026-09-09의 세 층 도입·09-10 후속 전환, 2026-09-14의 주제 구성·읽기·갱신 결정과 의미·사실·진입 경로 검증 재시험이 형성 근거다. 선택을 바꾼 당시 조건·최소 발췌·비교와 재시험의 한계는 위 본문에 직접 보존했다. 원래 기록은 Workspace 006의 역사 보존물이며 현재 판단의 정본은 이 문서와 앞서 연결한 관리·구성·읽기 본문이다.
