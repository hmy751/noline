# 앱 준비와 계정 보존을 함께 설명하는 이유

[현재 본문](../INDEX.md)의 역할 분리와 사용자 흐름이 형성된 이유를 설명한다. 아래 발췌는 002의 보존 기록에 담긴 사용자 발화이며 이번 작성에서 원 대화 전체를 다시 검증한 것은 아니다. 당시 제안·최종 채택·후속 구현을 구별하고 현재 소스와 대조했다.

## 앱 준비는 화면 진입 조건을 함께 소유한다

SQLite와 인증 저장소는 독립적으로 실패할 수 있다. 인증 정보가 있어도 SQLite를 열지 못하면 여행 데이터를 사용하는 화면을 준비됐다고 볼 수 없다. 사용자는 DB 실패 시 “실패 안내와 재시도 화면을 보여주고, DB 준비 성공 후 진입한다”를 선택했다. 처음에는 인증 저장소 실패도 비인증으로 복원을 마쳤지만, 후속 세션 정책은 기록 부재와 복원 실패를 `signed-out`·`restore-failed`로 구별했다. 로그인 화면으로 진행하되 데이터 보존과 재시도 의미를 남기는 쪽으로 구체화됐다.

초기 인증 실패 처리에서 사용자가 선택한 “일반적으로 가자”는 별도 복원 실패 화면 대신 로그인 화면을 보여주는 당시 선택이었다. 이후 저장된 계정을 확인하지 못한 경우와 기록이 없음을 확인한 경우를 구별해야 한다는 논의에서 사용자는 “그럼 마지막에 복원실패는 어떤상태로 두게? 저 세상태로 안두게? 애매한데?”라고 물었다. 그 결과 복원 실패와 명시적 재시도를 상태에 드러냈다. 초기 화면 구성을 단순하게 유지하려던 선택이 이 후속 구분이나 계정 검사를 없애라는 원칙은 아니다. 복원은 최초 시작과 실패 뒤 명시적 재시도에 한정하고, 탭 이동·앱 복귀·네트워크 변화마다 현재 작업을 막는 초기화를 반복하지 않도록 했다.

처음 layout 안에서 준비 상태를 정리한 뒤 사용자는 “preparation 과 auth init … 따로 구현된느낌”, “이니셜라이즈 앱 초기화의 의미더 생각하고”라고 지적했다. 이후 “일단 application 분리 하고 리뷰어 리뷰 고려해서 한번 작업 진행해봐”라고 요청했다. 함께 바뀌는 준비 순서·실패·재시도·Splash·네트워크 감지를 AppInitialization에 두고 layout은 화면과 후속 작업을 연결한다. 인증 Store는 하위 기능에서도 필요한 계정 상태를 소유하므로 application으로 올리지 않았다. 모든 내부 컴포넌트의 파일 분리나 범용 startup registry를 채택한 것은 아니다.

## 재로그인은 기존 여행을 유지하며 인증을 복구한다

인증이 만료됐다는 이유로 활성 여행의 로컬 작성을 막으면 오프라인에서 여행 기록을 이어간다는 목적을 잃는다. 논의 중 읽기 전용과 전체 로컬 차단도 제안됐지만 최종 채택안은 아니다. 읽기 전용은 타인의 열람을 막지 못하고, 두 제한 모두 기존 미전송 데이터의 보존·계정 귀속·같은 계정 복구 책임을 없애지 못한다. 잠깐 연결돼 서버 인증 만료를 확인했다는 이유로 여행 중 기록이 끊기는 비용을 고려해 기존 계정의 활성 여행 Local CRUD를 유지했다. 비활성 여행의 서버 이용이나 새 여행의 오프라인 생성까지 허용한 결정은 아니다. 재로그인이 지연되면 기기에만 남은 기록이 쌓일 수 있으므로 로컬 저장과 서버 전송 완료는 구별해야 한다.

이후 관리 부담을 줄이기 위해 선택한 것은 재로그인에서 다른 계정으로 즉시 전환하는 편의를 줄이는 방향이었다. 정상 재로그인이 인증 복구만 담당하면 DB 폐기·캐시 정리·새 계정 공개를 한 흐름에서 함께 처리할 부담을 줄일 수 있다.

사용자는 “로그아웃시 로컬 db 삭제가 부자연스럽다고 생각은 안해”라고 했고, 같은 계정 재인증과 명시적 로그아웃 뒤 다른 계정 로그인을 구별한 뒤 “그래 그걸로 가자 그게 자연스럽고 덜 복잡하고 좋은것 같아”라고 채택했다. 같은 계정 재로그인은 DB를 바꾸지 않고 인증을 복구한다. 반면 로그아웃 뒤에는 미전송 변경과 예전 오프라인 준비를 되돌릴 수 없다는 비용을 받아들였다.

서버 로그인 성공 후 기기 저장 실패를 설명하는 과정에서는 “이걸 또 따로 상태를 만들려고 물어본건가?”라는 우려도 있었다. 새 실패 상태를 늘리는 대신 저장 성공 전 상태를 보존하고 기존 오류 전달로 재시도하게 하는 방향을 택했다. 이 결정이 인증 저장소 복원 실패와 서버 인증 거절까지 한 상태로 합친다는 의미는 아니다.

## 기기 저장과 전체 종료는 서로 다른 순서를 보호한다

사용자는 인증 기준을 Store와 local-access 중 어디에서 읽는지 혼란스럽다고 했고, “동작 오류이거나 나눠야 하거나 책임을 분리해야하는 거면 인정”하며 점검을 요청했다. 이후 재현에서 동시 로그인 계정 검사, 늦은 refresh, 종료 확인 뒤 추가된 로컬 저장 등 실제 순서 문제가 확인됐다. 인증 ID를 한 번 읽어 전달하는 것만으로는 await 도중 세션 변경을 보호하지 못했다.

상태에 따른 계정 판단은 Store, DB 행과 큐의 귀속은 DB 접근 코드, 로그인·로그아웃·탈퇴 전체 순서는 session-lifecycle이 담당하도록 정리했다. Store의 큐는 refresh까지 포함한 기기 저장 순서를 보호한다. 별도의 세션 변경 조율은 sync·cleanup이 DB 작업을 끝낸 뒤 새 transaction을 막고 미전송 여부를 확인한다. 두 큐가 같은 책임을 중복하는 것은 아니다.

앱 준비 단계에서 사용자는 이미 “실행 중인 정리가 끝난 뒤 DB를 비우고 로그아웃”을 선택했다. 후속 구현에서 sync·cleanup·접수된 DB 작업의 종료 대기, FAILED를 포함한 종료 보류, DB reset의 rollback과 큐 원본 보존까지 연결했다. 종료를 기다리는 것과 성공적으로 전송하는 것은 계속 구별했다.

sync 종료 대기는 진행 중 실행이 DB 정리 뒤에 쓰는 충돌을 피하기 위한 선택이었다. 새 sync를 막고 기존 실행이 성공하거나 실패해서 끝난 뒤 세션과 DB를 정리하는 제안에 사용자는 “그래 그렇게 하자”라고 답했다. 이때 로그아웃 완료가 늦어지는 비용을 받아들였고, 진행 중 요청 취소나 새 timeout을 추가하는 안은 선택하지 않았다. 서버 로그아웃도 대기 뒤에 실행해 진행 중 sync가 사용하는 인증을 먼저 무효화하지 않는다. 이후 세션 조율은 pending cleanup과 접수된 DB 작업까지 기다리도록 구체화됐으며, 미동기화 변경 때문에 종료를 보류하면 일시 중단을 풀고 기존 이용을 이어간다.

## 앱 강제 종료 뒤 정리 재개는 명시적으로 제외했다

SecureStore와 SQLite를 정리하는 도중 앱이 종료되면 다음 실행에서 정리를 이어가는 장치도 제안됐다. 사용자는 설명 뒤 “로그아웃중 앱종료 냅둬”라고 답해 durable marker·journal·다음 실행의 정리 재개를 이번 구현에서 제외했다. 따라서 이 경계를 일반적인 실행 중 sync·cleanup 종료 대기나 오류 처리를 생략하라는 뜻으로 읽지 않는다. 서버·SQLite·SecureStore를 함께 정리하는 도중 프로세스가 끝났을 때의 복구를 보장하려면 이 제외 결정을 다시 검토해야 한다.

다중 기기 제어와 원격 세션 회수도 사용자가 “다른기기에서 이기기.. 이건 지금 고려할건 아니라고봐”라고 제외한 범위다. 일반적인 토큰 무효 응답을 원격 회수나 계정 삭제의 증거로 해석하는 정책은 채택하지 않았다. 반면 진행 중 토큰 갱신 응답이 세션 변경 뒤 도착하는 경우의 방어는 채택했다. 같은 계정으로 다시 로그인했더라도 요청 당시 세션과 다르면 적용하지 않는다는 경계다.

## 현재 본문으로 복원한 범위

앱 시작·인증·DB·sync를 따로 요약하면 다음 변경에서 데이터 보존 조건을 다시 조립해야 한다. 따라서 현재 본문은 시작, 기존 계정 이용, 세션 변경, 종료 후 남는 데이터라는 흐름으로 묶었다. architecture는 전체 위치와 이 본문으로의 진입을 맡고, transaction·Activation Router·Policy의 상세 Owner는 유지한다. 이 구성이 새 제품 정책이나 기존 상세 문서 전체의 Owner 이동을 뜻하지 않는다.

2026-10-30 현재 코드를 대조해 초기에 미완료였던 세션 동시성·DB 원자성·종료 조율의 후속 반영을 구별했다. 동시에 여행별 cleanup의 PENDING 한정 판정과 처리 수, 별도 지도 정리의 수명, 앱 강제 종료 후 정리 재개는 구현 전체로 보장되지 않는 경계로 남겼다. 여러 기록의 오래된 미완료 목록을 합쳐 현재 상태라고 쓰거나, 한 경로의 보호를 전체 cleanup으로 넓히지 않았다.

향후 다른 계정 즉시 전환이나 계정별 로컬 보관을 도입하면 재로그인·로그아웃의 데이터 보존 선택을 다시 판단해야 한다. 새로운 저장·백그라운드 실행 경로를 추가하면 기존 세션 조율에 참여하는지를 재확인한다. 이 자료는 그때의 선택 이유를 복원하며 현재 제품 변경의 승인을 대신하지 않는다.
