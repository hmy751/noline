# 전송 경계를 나누고 오류 통일을 별도 선택으로 남긴 이유

[API 계약](../../api-contracts.md)과 [오류 처리](../../error-handling.md)의 선택을 설명한다.

## 표현 변환·검증·접근은 다른 실패를 막는다

DB Date를 JSON의 ISO 문자열로 바꾸는 일과 그 값이 계약을 충족하는지 검사하는 일은 다르다. Serializer를 순수 변환에 한정하면 일반 목록·단건·Trip 하위 목록·activation·sync가 같은 표현을 쓰면서도 각자의 status·envelope·조회 조건을 유지할 수 있다. 반면 공유 serializer의 존재만으로 모든 response나 ownership이 검사됐다고 오해하기 쉬워 실제 소비 경로를 함께 설명한다.

일반 조회는 삭제된 row를 숨기지만 sync는 삭제 사실도 다른 기기로 보내야 한다. 하나의 query 조건을 모든 endpoint에 재사용하는 단순화는 이 의미를 깨뜨릴 수 있다. 클라이언트의 request 검사와 서버 검사, 입수 데이터의 Local 쓰기 전 검사도 서로 다른 신뢰 경계다. 타입 선언·한쪽 parse만으로 나머지 보호를 대신하지 않는 이유다.

경비 API의 가독성 작업은 로그를 남기고 같은 오류를 다시 던지는 catch를 덜어 요청·전송·응답의 흐름을 드러냈다. mutation hook의 기록과 화면 표시, React Query 오류 상태는 유지했지만 조회 API console은 사라졌다. 이 비용과 변화는 오류 객체·사용자 fallback 보존과 구별했다. 다른 API의 catch나 공통 오류 변환까지 일괄 삭제한 선택이 아니다.

## 인증 갱신은 일반 요청을 재귀 호출하지 않는 전송 경계를 둔다

2025-12의 결정은 `fetcher → auth-interceptor → auth-api → fetcher` 순환으로 런타임 오류가 났다는 기록에서 시작했다. interceptor 없는 authAxios와 일반 apiAxios를 따로 만드는 방식을 택해 기존 구조를 크게 바꾸지 않고 갱신 전송을 분리했다. 대안인 dynamic import는 지연·비동기 의존 추적을 추가하고, 전역 Axios는 interceptor와 설정의 분리를 어렵게 하며, 당시 제안된 dependency injection은 호출부 전달과 추상화 비용이 컸다는 판단이었다. 이는 그 대안이 모든 상황에서 열등하다는 규칙이 아니다. 두 instance의 설정 관리 비용을 받아들이며 순환을 피한 선택이다.

이후 refresh 전송은 auth-transport로 분리되었고 auth-api는 일반 apiClient도 사용한다. 현재 책임을 옛 파일 그림에 맞추지 않는다. 2026-09의 session 결정은 일반 API와 sync가 같은 갱신·거부 기준을 쓰도록 바꾸었다. Sync의 별도 instance·timeout·5xx retry는 유지하지만 옛 결정의 “401에서 갱신하지 않음”은 대체됐다. 갱신 실패의 5xx·통신 장애를 자격 증명 거부로 확정하지 않는 이유는 일시 장애 때문에 유효한 로컬 세션과 기록 접근을 잃지 않기 위해서다.

## 기존 오류 기준을 보존하면서 실제 예외를 드러낸다

옛 오류 가이드는 AppError/errorHandler, React Query 오류, Policy UI와 민감정보 미공개를 기본으로 삼았다. 동시에 API 문서는 Data route의 sendInternalError와 통일 방향의 미정을 명시했다. 현재 코드에서는 중앙 handler가 설치됐어도 AppError 생성 소비자가 없고 Data route가 자체 응답을 만든다. 문서가 서로 다른 현재 사실을 주장하던 부분을 바로잡되, 현재 예외가 많다는 이유로 AppError 기본 기준이나 공개 안전성을 폐기하지 않았다.

오류 가이드는 status와 envelope, 최상위·nested message/code를 APIError가 어떻게 받는지 설명한다. 원본 error.message를 공개하는 경로는 보호 공백으로 남긴다. 중앙 handler로 통일할지와 공개 schema/code는 새 선택이 필요하지만, 민감정보 미공개 자체는 이미 있던 기준이다. 표준화와 보호 공백 보완을 같은 대규모 변경으로 묶어야 한다는 뜻은 아니다.

서버 비동기 throw 예시와 존재하지 않는 tripService는 현재 전달·접근 경로를 오해하게 해 본문에서 제외했다. 책임 비교 표는 유지하되 실제 조건·차이를 넣었다. 오류 문서의 끝 체크리스트는 각 처리·변경 조건 가까이에 통합했다. API 계약을 오류까지 한 긴 문서로 확장하는 대신 실패 매핑을 바꿀 때 선택해서 읽는 본문을 분리했고, 인증·API 형성 이유는 한 묶음에서 관리한다. 통합은 링크 이동을 줄이는 장점이 있지만 정상 경계만 바꾸는 독자에게 모든 오류 분기를 읽히는 비용이 있다.

## 인증 여부와 행 소유권을 같은 요청 경계에서 구별했다

Auth/User Scope rule·Guard Map의 유효한 의미를 API 본문에 통합했다. `requireAuth`가 있다는 사실만으로 다른 사용자 행 접근을 막았다고 오인하지 않도록 인증 결과의 userId, 부모·연결 소유권과 실제 mutation 조건을 함께 설명한다. 당시 Expense 연결 검증·Trip mutation에서 찾은 공백을 기록했다. 이후 자식 쓰기는 부모 여행의 소유권과 삭제 여부를 잠금 안에서 확인하고, Trip 삭제는 자기 여행과 자식 행을 함께 처리한다. [현재 소유권 계약](../../api-contracts.md#사용자-데이터를-다루면-인증과-소유권을-각각-검사한다) Local 계정 분리는 세션·데이터 수명 Owner와 연결해 서버 규칙 하나에 계정 종료까지 복제하지 않았다. 정상 요청만 확인하는 것보다 다른 사용자·삭제된 부모·조작 필드가 필요한 이유도 본문 가까이에 두었다.

## 응답을 잃은 생성·삭제를 서버에서 판별한 이유

2026-10-31 개발 앱에서 서버가 저장을 마친 경비 CREATE의 응답이 앱에 닿지 않았다. 앱이 같은 ID로 다시 보내자 서버는 중복 키 500으로 거절했고, 이 실패가 queue 전체를 막았다. client ID를 서버가 수용한다는 계약만으로는 같은 요청을 다시 받아도 된다는 보장이 생기지 않았던 것이다. 삭제도 같아서, 이미 지운 행을 다시 지우라는 요청은 404였다.

당시 목표는 응답을 잃어도 같은 변경을 중복 적용하지 않는 것이었다. 생성 재전송은 같은 여행의 기존 행을, 삭제 재전송은 처음 삭제 시각을 반환한다. 이후 항목별 UPDATE에도 이 원칙을 적용했다. 더 뒤의 편집이 있으면 서버는 재전송 시점의 현재 행을 돌려준다. [전송·서버 판정 기록](../../../../work/workspaces/007-sync-failure-recovery/records/2026-11-13-15-stage-four-isolated-commit.md)

"이미 반영됐는가"와 "누구의 행인가"를 아는 쪽은 서버이므로 서버가 판단하게 했다. 비교한 대안과 기각 이유는 다음과 같다.

| 대안 | 진짜 실패와 구분 | 이미 설치된 앱 | 판단 |
| --- | --- | --- | --- |
| 그대로 (생성 500, 삭제 404) | 안 됨 | 계속 막힘 | 사고의 원인 |
| **서버가 같은 사용자의 재전송이면 200** | 됨 | 서버 배포만으로 적용 | 선택 |
| 앱이 409·404를 성공으로 간주 | 안 됨 | 앱 업데이트 필요 | 404는 "없음·다른 사용자·이미 삭제"를 같은 응답으로 숨기므로 진짜 실패까지 지운다 |
| 다시 보내기 전에 존재를 조회 | 사이에 끼어든 변경을 놓침 | 앱 업데이트 필요 | 요청이 두 배가 된다 |

11월 3일 당시 앱은 2xx로 전송 완료를 판단했다. 서버가 재전송에 200을 돌려주면 이미 설치된 앱도 다음 작업을 보낼 수 있었다. 이후 앱은 응답 본문까지 검사해 기기 반영과 요청 종결을 함께 확정한다.

11월 3일에 선택한 범위와 이후 달라진 동작은 다음과 같다.

- **쓰기 조건은 그대로 둔다.** 생성은 ID 충돌 시 쓰지 않고, 삭제는 `id + userId + deletedAt IS NULL`을 유지한다. 쓴 행이 없을 때만 `id + userId`로 다시 조회해 응답을 정하므로 정상 경로에 비용이 없고 다른 사용자 행을 읽거나 바꾸지 않는다.
- **다른 사용자나 다른 Trip의 같은 ID는 409다.** 소유 여부를 구별해 알리지 않는다. 다만 그 ID가 쓰이고 있다는 사실은 드러나며, 이는 받아들인 범위다.
- **생성 재전송의 body는 비교하지 않는다.** 같은 queue payload를 다시 보내는 한 body가 다른 경우는 버그뿐이고, 그런 요청을 거절하면 새로운 막힘이 생긴다.
- **삭제 재전송은 처음 삭제 시각을 돌려준다.** 행과 version을 다시 바꾸지 않아 다른 기기의 pull에 새 변경으로 보이지 않는다.
- **Trip 삭제는 당시 적용을 미뤘다.** 당시에는 재전송 때 200을 반환하면서 삭제 시각과 version을 다시 바꿨다. 같은 mutation의 소유권 조건도 보완해야 했기 때문이다. 현재는 자기 여행의 첫 삭제 시각을 유지한다.
- **Schedule 생성은 부모 Trip 확인을 기존 행 확인보다 먼저 한다.** 기존 행을 먼저 보면 지운 Trip 아래 재전송도 200이 되지만, 이는 부모 먼저라는 API 계약과 부딪히고 다른 기기와의 충돌 처리에 속한다. 그 시점에는 종결 규칙을 열어 뒀다. 이후 서버가 자기 여행의 삭제를 확인하면 410으로 알리고 앱은 해당 여행의 유효한 변경을 종결하도록 정했다. [현재 재전송 계약](../../api-contracts.md#큐-작업-재전송에는-이미-반영된-결과로-응답한다)

응답 status를 바꾸는 계약이므로 [오류 처리](../../error-handling.md)의 기준대로 본문과 테스트로 고정했다. 앱 코드에서 404·409를 따로 분기하는 곳은 찾지 못했다(2026-11-03 코드 검색).

## 동기화 실패의 관측 위치

서버 요청에 재시도 정보를 더하는 안은 기기에서 격리된 작업이나 앱 종료를 관측할 수 없었다. 사용자가 제시한 “로컬에서 전송하려다 격리되는것처럼 끊기는 작업”까지 구별하려고 앱에서 사건을 기록하고, 일반 서버 오류와 함께 조사할 수 있도록 Sentry를 선택했다. 로그아웃 뒤에도 SDK가 진단을 전달한 결과와 수집 서버가 도시 정보를 붙인 사례는 송신 시점의 정보 제한과 수신 결과를 따로 확인해야 하는 이유다. [선택과 범위](../../../../work/workspaces/007-sync-failure-recovery/current/memory/tickets/06-stalled-sync-visibility.md)와 [실제 수신 기록](../../../../work/workspaces/007-sync-failure-recovery/records/2026-11-10-01-sentry-staging.md)에 당시 조건이 있다.

## 삭제와 보류를 소유권 증거에 연결한 이유

삭제된 자기 여행·기록이 확인되면 뒤의 정상 요청을 전송할 수 있다. 소유권을 판별할 수 없는 404까지 같은 방식으로 끝내면 기기에만 남은 입력이 사라진다. 따라서 자식 쓰기는 부모 여행을 먼저 잠그고, 이미 삭제된 자기 기록만 명시적 결과로 반환한다. 원래 입력을 기기에 남기지 않는 구버전 온라인 요청은 서버에서 사용자별 보류본을 보존해야 새 앱에서 확인할 수 있다. ## 수정 요청의 준비와 저장 경계를 구별한 이유

일정·경비의 Local·API 수정 함수도 표식을 준비하도록 둔 구현은 Repository를 통과한 요청을 다시 준비했다. 이미 있는 표식을 재사용해 이중 발급은 없었지만, 실제 앱의 하위 수정 호출자가 Repository뿐인 조건에서 발급 책임을 여러 곳에 둘 이유가 약했다. Repository에서 제출 시점의 표식과 입력 검증을 확정하고 하위 함수가 준비된 요청을 받도록 정리했다. 저장 대기 전에 표식 발급 순서와 여행 작업 순서를 확보하는 관계, API의 전송 검증과 Local의 행·큐 원자성은 유지한다.

생성·삭제 뒤 조회 갱신도 수정과 같은 취소·갱신 유틸을 사용한다. 캐시 없는 첫 조회가 늦게 끝나면 단순 무효화만으로는 저장 전 목록이 남을 수 있어, 옛 요청을 먼저 취소하는 순서를 공통으로 적용했다. 새 목록을 받는 데 실패했다고 이미 성공한 저장을 실패로 바꾸지는 않는다.
