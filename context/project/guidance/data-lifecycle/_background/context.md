# 즉시 해제와 미전송 변경 보존을 함께 다루는 이유

[현재 본문](../INDEX.md)은 저장·서버 반영·사본 정리가 서로 다른 완료라는 관계를 설명한다. 오프라인 기록을 먼저 받아들이는 제품에서는 전송하지 못한 변경이 남는 시간이 정상적으로 생기기 때문이다. 선택에 사용한 문장과 현재 관찰은 [근거](evidence.md)에 보존한다.

## 비활성화를 동기화 대기에 묶지 않았다

2025년 비활성화 정리 결정은 서버에 전송하지 않은 경비가 있는데 기기의 원본부터 삭제하는 위험을 문제로 삼았다. 즉시 hard delete는 저장 공간을 빨리 돌려주지만 회복 경로를 없앤다. 반대로 동기화를 끝낼 때까지 비활성화를 막으면 오프라인에서 사용자가 언제 기다림을 끝낼 수 있을지 알 수 없다.

선택은 활성 상태 해제와 사본 삭제를 분리하고, 미전송 변경이 남으면 정리를 예약한 뒤 soft delete·기간 기반 물리 삭제로 이어가는 것이었다. 무기한 soft delete만 유지하는 안보다 저장 공간을 회수할 수 있지만 예약 상태·실행 계기·부분 실패를 관리하는 비용이 생긴다. 7일은 현재 삭제 유예 기간이지 그 시간이 지나면 모든 정리가 반드시 끝난다는 약속이 아니다.

당시 문서는 PENDING 검사와 soft delete만으로 동기화 완료·데이터 안전을 보장한다고 설명했다. 현재 코드 대조와 후속 보완은 그 주장을 제한한다. FAILED·IN_PROGRESS도 미전송이고, 부분 UPDATE는 payload에 여행 ID가 없을 수 있으며, 다시 활성화한 여행에 옛 정리를 실행해서도 안 된다. 필요한 보존 의미는 유지하되 과거 코드 예시를 정본으로 복제하지 않은 이유다.

## 원본을 남기는 것은 재전송 이상의 책임이다

queue는 전송할 payload를 보존하지만 계정 소유권 판별에는 원본 행도 사용한다. 오래된 행이라는 이유만으로 vacuum이 지우면 같은 계정의 변경을 식별할 근거까지 사라질 수 있다. 후속 구현은 queue 상태에 관계없이 참조하는 원본을 남기도록 했다. 실패 작업이 오래 남으면 공간도 계속 차지한다는 비용을 받아들인다.

계정 종료는 여행별 사본 정리와 달리 로컬 계정 데이터를 비우므로 이미 접수한 저장·sync·cleanup의 종료를 기다린 뒤 검사해야 한다. transaction부터 막으면 앞선 sync·cleanup의 마지막 쓰기가 마무리되지 못할 수 있어 sync → cleanup → DB 순서를 사용한다. 세 미전송 상태의 보류와 명시적 폐기를 구별해, 전송 실패가 자동 폐기 동의로 바뀌지 않게 한다. 세션 조율의 상세 Owner는 앱 실행 본문으로 유지한다.

## 문서를 나누는 기준도 실제 질문에 맞췄다

Local mutation부터 queue·push/pull·정리까지는 하나의 변경이 어디에 남는지 이해해야 하므로 같은 본문에서 연결했다. 반면 인증 상태·로그인·실패별 종료 처리는 기존 앱 실행 본문에 유지하고 필요한 전제만 재서술했다. 같은 사실을 common/current/guidance 세 문서로 나누지 않았다.

옛 Entity 구조·처리 순서는 역할과 실제 순서를 이해하는 데 유용해 설명·표·번호의 의미를 살렸다. 일반 체크리스트는 저장·전송·정리 각 조건 가까이 통합했고, 긴 과거 구현 예제·작업 통계·‘완벽한 안전’ 주장은 현재 가이드에서 제외했다. 새로운 충돌 정책이나 중단 작업의 재개 정책은 이 편입으로 채택하지 않는다. 미전송 판정, 재활성화·정리 책임, 종료 절차 또는 서버 cursor가 바뀌면 본문과 이 이유를 함께 재검토한다.

## ID와 queue를 같은 데이터 수명에서 찾게 했다

기존 Client-Side ID rule과 Guard Map은 `generateId()`·client ID 서버 수용을 별도 짧은 기준으로 유지했다. 이를 Local 저장·queue·서버 전송과 함께 설명해, ID wrapper만 교체하고 request·서버에서 다른 ID를 쓰는 누락을 막도록 구성했다. 원문의 직접 `ulid()` 호출 금지는 유지하되 wrapper 주석의 ‘충돌 없음’을 새 보장으로 승격하지 않았다. 세 생성 폼·create schema·server insert를 대조했으며, CREATE 재전송의 멱등성은 이 사실에서 따라오지 않는다. 기존 원자성·soft-delete·미전송 보호의 이유와 구현 공백은 그대로 유지했다.

## 실패 횟수 한도를 없애고 중단된 전송을 되돌렸다

2026-10-31 개발 앱에서 경비 CREATE 하나가 queue를 영구히 막았다. 서버는 첫 요청을 저장했지만 앱이 응답을 받지 못했고, 같은 ID의 재전송은 중복 키 500으로 세 번 실패했다. 이전 선택 규칙은 `retryCount < 3`인 FAILED까지만 보냈으므로 이 작업과 뒤의 모든 작업, pull이 멈췄고 출시 빌드에서는 아무도 알 수 없었다. 위 편입 때 열어 둔 "중단 작업의 재개 정책"을 이 사고로 다시 판단했다.

선택은 세 가지를 한 묶음으로 바꾼 것이다. 서버는 같은 사용자의 이미 반영된 생성·삭제를 성공으로 응답하고([API 계약의 형성 자료](../../_background/api-contracts/context.md#같은-사용자의-재전송은-서버가-처음-결과로-응답한다)), 앱은 횟수와 관계없이 FAILED를 다시 보내며, push를 시작할 때 남은 IN_PROGRESS를 PENDING으로 되돌린다. 뒤의 둘은 같은 요청을 더 자주 다시 보내게 만들므로 서버 쪽이 먼저 안전해야 한다. 앞 절에서 "CREATE 재전송의 멱등성은 client ID 수용에서 따라오지 않는다"고 한 공백을 이 서버 응답이 메운다.

재시도 방식은 다음 대안과 비교했다.

| 대안 | 일시 오류 뒤 | 우리 버그를 고친 뒤 | 기각·선택 이유 |
| --- | --- | --- | --- |
| 3번 실패하면 영구 정지 (이전) | 멈춤 | 멈춤 | 여행 중 일시 오류만 쌓여도 영구 정지가 된다 |
| 오류 종류에 따라 일부만 정지 | 풀림 | 멈춘 건 안 풀림 | 상태 코드로 영구 실패를 가를 수 없다. 이번 500은 몇 번 보내도 실패했고, 버그로 생긴 400은 서버를 고치면 성공한다 |
| 한도 + 앱 재시작 때 초기화 | 재시작까지 정지 | 재시작까지 정지 | 실패 횟수 정보도 사라진다 |
| **한도 없이 sync 때마다** | 풀림 | 풀림 | 두 경우 모두 풀리는 안 중 가장 단순하다 |
| 한도 없음 + 몇 분마다 자동 재시도 | 빨리 풀림 | 풀림 | 새 실행 계기가 필요하고 헛요청이 계속 는다 |

받아들인 비용은 끝내 실패할 요청도 sync마다 실제로 보낸다는 것이다. 실패 뒤 일정 시간이 지나야 다시 보내는 간격 재시도는 이 비용을 줄이지만 연결 회복 뒤 전송도 늦춘다. sync는 실행 조건이 새로 갖춰질 때만 시작하므로 비용이 그 횟수에 묶인다는 것은 확인했지만, 연결이 자주 끊기는 실제 사용에서 그 횟수는 측정하지 못했다. 그래서 간격 재시도는 거절하지 않고 보류했다. 실제 시작 횟수를 얻거나, 같은 작업의 실패가 자주 반복되거나, sync 계기를 늘릴 때 다시 판단한다.

IN_PROGRESS는 다음 sync에서 바로 되돌린다. 앱 시작 때 한 번만 되돌리면 다음 시작까지 막히고, 일정 시간이 지난 것만 되돌리면 그 시간만큼 막히면서 구현이 늘어난다. sync는 한 번에 하나만 실행되므로 push 시작 시점의 IN_PROGRESS는 끊긴 이전 실행의 흔적이고, 실제로 서버에 닿은 뒤 끊겼더라도 재전송 응답 덕분에 안전하다. 이 판단은 실행 잠금에 기대므로 잠금 방식이 바뀌면 다시 본다.

횟수나 시간으로 작업을 버리는 안은 기각했다. 며칠 오프라인은 정상 사용이고, 버리면 기기에만 남은 수정이 다음 pull에서 조용히 사라질 수 있다. 다시 보내도 성공할 수 없는 변경(다른 기기와의 충돌, 지운 부모)을 끝내는 규칙과 그 정지를 알리는 표시는 이 변경에 포함하지 않았다. FIFO를 여행별로 나누는 안도 pull 보호가 먼저 필요해 미뤘다.

## 원본을 잃은 요청과 새 삭제 요청

1.0.1의 기기 정리는 삭제 표시 후 7일이 지난 일정·경비를 지울 때 큐의 참조를 확인하지 않았다. 기기에 요청만 남으면 누구의 변경인지 확인하지 못해 같은 계정의 로그인도 막혔다. 원본 없는 생성·수정 요청에는 마지막 사용자 입력이 남을 수 있고, 당시 계정을 추정해 전송하면 다른 계정에서 변경을 실행할 위험이 있었다. 그래서 확인할 수 없는 요청을 기기에 보존하고, 로그인 검사와 후속 전송에서 건너뛰도록 했다. 같은 ID가 다시 나타났다는 사실만으로는 옛 요청을 다시 보낼 근거가 생기지 않는다.

사용자는 “소프트 딜리트는 유지하고 userId는 저장하자”라고 선택했다. 새 요청을 만드는 순간에는 삭제 권한을 확인한 실제 행이 있으므로 그 소유자를 함께 저장할 수 있다. 소유자를 알 수 있어도 일정을 즉시 지우면 연결 경비와 경로에 영향이 생겨 삭제 표시와 물리 정리는 나눠 두었다. 이 선택은 예전에 소유자를 기록하지 않은 삭제 요청의 최종 처분까지 결정하지 않는다.

2026-11-07 개발 코드의 격리와 새 삭제 요청 형식은 각각 `06cebd6f`, `30783ccb`에 있다. 일정 원본을 제거한 뒤에도 같은 계정의 삭제가 개발 서버에 반영된 범위와 구버전 설치·업데이트 경로의 미확인은 [007의 검증 기록](../../../../work/workspaces/007-sync-failure-recovery/current/memory/tickets/08-orphaned-queue-task-blocks-login.md)에서 찾는다.
