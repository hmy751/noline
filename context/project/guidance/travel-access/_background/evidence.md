# 여행 접근 선택을 확인할 최소 근거

[현재 본문](../INDEX.md)과 [형성 맥락](context.md)의 선택 이유를 확인하는 발췌·관찰이다. 2026-10-31 저장소의 기존 결정과 작업 기록에서 선별했다. 문서에 보존된 사용자 발화이며 원 대화 전체를 새로 확보한 것은 아니다. 과거 코드 예제·완료 표시는 현재 구현이나 검증 결과로 승격하지 않는다. 출처 식별자는 조사 판본을 구별하기 위한 것이며 현재 읽기를 옛 문서로 안내하는 링크가 아니다.

## Data와 Service의 책임

2025-11-20 Data/Service 분리 결정은 활성 여행의 온라인 지도 제한을 문제로 들고 다음을 구별했다.

> 데이터 (Trip, Schedule, Expense): 소유권이 있고, 동기화가 필요하며, 무결성이 중요함

> 서비스 (Map, Search, Directions): 소유권이 없고, 단순 조회이며, 최신성이 중요함

데이터는 Local/Remote 소유권과 queue를 지키고 서비스는 네트워크 조건에 맞춰 선택한다. 온라인마다 Router를 Server 우선으로 바꾸는 안은 당시 기록에서 sync_queue·Ghost Data 위험으로 기각했고, 사용자가 완전 온라인/오프라인 모드를 선택하는 안은 복잡도를 사용자에게 넘긴다는 이유로 기각했다. 이는 당시 위험 판단이며 이 문서에서 새로 장애를 재현했다는 뜻은 아니다.

같은 날 Policy 책임 분리 결정은 data hook 내부 검사가 Policy·Router·CRUD를 한곳에 묶는다고 판단해 화면 소비를 선택했다. Entity별 Policy hook 대신 `useAppPolicy`와 작업별 정책을 채택했다. 당시의 화면 전체 교체 예시는 이후 초안 보존 계약으로 적용이 제한됐다.

같은 Data/Service 결정의 선택적 차단 표에는 일정 생성의 이유로 “텍스트 기록이 핵심, 좌표는 부가정보”, 경비 생성의 이유로 “금액 기록이 핵심”이라고 적혀 있다. 이 우선순위는 현재도 좌표 없이 기록하고 나중에 장소를 보완하는 흐름을 설명한다. 좌표 없는 일정의 지도 표시 제한과 수정 경로는 [현재 본문](../INDEX.md#수동-기록과-좌표-보완)이 연결한 코드에서 대조했다. 당시 표에 함께 적힌 여행 생성의 메타데이터 전제나 과거 구현 예제를 이 이유와 묶어 영구적인 제품 제약으로 채택하지 않는다.

## 조회 조합과 화면 표현

## 경비 초안과 일정 연결

2026-10-02 경비 초안·일정 연결 결정의 사용자 발췌:

> 당연히 활성 여행에서는 오프라인 일정 연결 변경할 수 있어야 하고

> 일정을 연결할 수 있는건 말그대로 일정에 연결을 할거냐 안할거냐

같은 여행의 모든 날짜 일정을 제시하는 방향에 “그래 그렇게 정하자”라는 승인이 기록돼 있다. 같은 날짜 후보만 보이던 제한과 offline 때 별도 수동 폼으로 교체하던 동작을 대체한 선택이다. 후보를 날짜·시간순으로 보여 주고 초기 탐색은 경비 날짜 그룹에 접근하기 쉽게 하되, 경비 날짜를 바꿔도 기존 연결을 해제하지 않는다. 선택 일정의 제목·날짜·시간과 명시적 해제를 제공한다.

비활성 여행의 offline/unknown에서는 새 후보·저장을 막되 기존 초안·연결 설명·해제는 유지한다. 날짜를 결제일·사용일 중 무엇으로 정의할지, 다른 여행 후보나 일정 삭제·접근권 변경을 어떻게 처리할지는 이 선택으로 결정하지 않았다. 활성 여행 범위나 연결 후보 범위가 달라지면 다시 검토한다. 서버 소유권 검증 완비의 증거도 아니다.

출처: `2026-10-02-expense-draft-and-schedule-association.md`의 선택·작성 보존·재검토 조건. 후속 날짜 표현·호환의 현재 내용은 [날짜와 시각](../../../common/date-and-time.md)을 따른다.

## 새 여행과 목록 반영

2026-10-04 비활성 Trip 생성 결정은 다른 여행이 활성화됐을 때 새 여행의 CREATE는 Local 큐, 수정·삭제는 Server로 갈라져 CREATE 전송 전 삭제가 실패한 문제를 기록했다. 새 여행은 서버에서 만들고 기존 여행은 대상 활성 상태로 분기하는 원칙으로 맞췄다.

서버 mutation마다 Local 사본을 고치는 첫 안에서는 반영 실패 뒤 목록 조회가 Local만 읽어 회복되지 않았다. 목록 조회가 서버 전체 결과를 반영하면서 활성 여행·미전송 작업의 부모를 보호하는 안으로 바꿨다. 성공한 서버 mutation을 후속 조회 실패와 혼동하지 않고, remote/mixed/local 출처로 선택 정리 여부를 구별한다.

10월 5일 후속 기록에는 연결 조건별 Query key와 staleTime 0을 사용하던 중간 구현이 활성 여행 없는 단절에서 기존 목록을 undefined로 만든 재현이 있다. 단일 key·기존 5분 유효기간과 앱의 한 번 연결되는 갱신 계기로 정리했다. 최초 요청 취소·API 장애 fallback·미분류 오류 전달도 후속 검사로 보완했다. 현재 코드는 본문의 Repository·Local datasource·선택 훅으로 확인한다.

출처: `2026-10-04-inactive-trip-creation.md`의 문제·결정·후속 검토. 기록의 실기 확인은 후속 취소·fallback 수정 전 버전이므로 그 이후 구현의 실기 단절 성공을 뜻하지 않는다.

## 네트워크 관측 수명

2026-10-04 복귀 연결 기록의 사용자 정정:

> 관심사랑 기존시스템 활용해서 책임 분리 잘 고려해서 useNetwork도 있는데 거기에 달랑 추가하면안되잖아?

AppInitialization에 붙였던 AppState 구독을 기존 Network Store로 이동했다. Store가 NetInfo와 복귀 구독의 init~cleanup 수명을 함께 소유하고 기존 refresh를 공유한다. 당시 외부 라이브러리의 iOS background 관측 제한을 보완 이유로 삼았으나, 그 설명을 앱에서 실제 단절을 재현한 증거로 사용하지 않았다.

출처: 002의 `2026-10-04-02-foreground-network-refresh.md`. 기록은 시뮬레이터의 앱 복귀와 refresh 호출을 확인했으며 실제 기기 단절·background Wi-Fi 전환은 확인하지 않았다. 현재 지원과 검사 범위는 본문의 코드·테스트 연결을 따른다.
