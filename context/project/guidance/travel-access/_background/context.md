# 여행 접근·복구 설명이 형성된 이유

[본문](../INDEX.md)은 연결 변화가 데이터 위치·조회 허용·화면 표시·입력 수명에 미치는 영향을 함께 이해하게 한다. 여러 기능이 같은 네트워크 신호를 소비해도 보존할 대상과 완료의 의미가 다르기 때문이다. 아래 선택의 최소 원문과 당시 조건은 [형성 근거](evidence.md)에 보존한다.

## 데이터 준비와 온라인 서비스를 분리했다

활성화는 여행 데이터를 기기에 준비하는 선택이다. 초기에는 활성화된 여행의 지도까지 Local 방식에 묶어 온라인 검색·지도를 충분히 활용하지 못했다. 2025년 Data/Service 분리 결정은 사용자가 소유하고 sync해야 하는 Trip·Schedule·Expense와 외부 지도·검색·길찾기의 책임을 나누었다. 활성 여행의 쓰기를 온라인마다 Server 우선으로 바꾸는 대안은 미전송 변경과 소유권을 흔들 위험 때문에 기각했고, 사용자가 온라인/오프라인 모드를 고르는 대안은 전환 판단의 부담 때문에 선택하지 않았다.

분리의 비용도 있다. 두 책임과 Policy 조합을 함께 이해해야 하고, 네트워크 변화로 지도 제공자가 바뀌면 표시 전환이 생긴다. 오프라인 수동 입력은 좌표가 없을 수 있어 지도 표시·검색 결과와의 연결을 나중에 보완해야 한다. 이 비용을 없다고 보지 않고 기록 지속과 온라인 서비스 이용을 함께 얻기 위해 받아들였다.

Router는 데이터 위치와 실제 실행 조건을, Policy는 현재 쓸 수 있는 기능·화면 모드를 맡는다. Policy를 data hook 안에서 검사하는 대안은 UI 가용성·저장 위치·CRUD 책임을 한곳에 합쳐 재사용을 어렵게 했다. 따라서 화면·feature 조합부가 Policy를 소비하고 data hook은 데이터 작업을 맡는다. 과거 예시의 ‘화면 전체 차단’은 이미 열린 초안 보존이라는 후속 계약에 그대로 적용할 수 없다.

오프라인 입력에서는 일정의 텍스트 기록과 경비의 금액 기록을 먼저 남기고, 좌표를 얻는 외부 검색은 별도로 보완하도록 선택했다. 좌표가 없어도 기록은 남지만 지도 마커로 쓸 수 없다는 비용이 따른다. 이 구별은 현재 입력·지도·수정 흐름에서도 유효하므로 제품 기준과 본문에 함께 설명한다. 과거 예제의 필드명이나 ‘온라인이면 모든 기능 사용 가능’이라는 넓은 표현까지 현재 규칙으로 가져오지는 않는다.

## 조회 계약을 공유하되 화면이 표현을 맡는다

일정과 경비는 각 Entity Query를 유지하고 공통 service가 Policy·Query 상태를 조합한다. Policy 계산에 Query 실행 수명까지 합치지 않으면서 폼과 화면이 같은 접근 조건을 사용하게 하려는 선택이다. 여행은 조회 범위이며 결과의 소유자는 일정·경비이므로 모든 조회를 trip feature 아래에 모으지 않았다.

구체 조회 조합을 폼에서 재사용하는 한정 선택은 공개 index 사용, UI·입력·저장 책임 없음, entities/shared만 참조, 소비 폼으로 역참조 없음이라는 조건을 갖는다. 조합을 Entity로 내리면 data hook의 Policy 책임 경계가 바뀌고, 폼마다 조합하면 접근 계산이 반복된다. 이 절충은 당시 작업의 선택이며 Project-wide FSD 예외는 채택하지 않았다. [보존 발췌](evidence.md#조회-조합과-화면-표현)는 이 차이를 설명한다.

홈 요약도 기존 조회 결과를 다시 포장하지 않고 화면이 정상·제한·부분 실패를 표현하도록 했다. 한쪽 요약의 실패가 다른 쪽의 유효한 내용을 숨기지 않으며 최초 실패를 0건·0원으로 만들지 않는다. 복구 토스트 추가와 경비 상세의 특정 재시도·삭제 실패 이유 처리는 별도로 보류돼 있다.

## 목록·입력의 보존은 내용 공개와 다르다

계정 전체 여행 목록은 어느 여행을 보고 있었는지 이어 주는 기본 정보다. 연결이 끊겨도 이미 얻은 목록과 선택은 유지하되, 비활성 여행의 일정·경비 내용은 읽기 정책에 따라 제한한다. 조건별로 목록 캐시를 나눈 중간 구현은 활성 여행이 없는 단절 때 기존 목록을 잃었으므로 단일 캐시와 별도의 갱신 계기로 정리했다.

새 여행을 다른 활성 여행 때문에 Local CREATE로 보내면 새 여행의 수정·삭제는 Server로 가는 불일치가 생겼다. 새 비활성 여행은 서버에서 생성하고, 서버 mutation 뒤 사본을 각각 갱신하는 대신 목록 조회가 미전송 변경을 보호하며 전체 사본을 반영하도록 했다. 서버 변경의 성공과 재조회 성공도 구별한다. 이 이유와 실패 조건은 [목록 형성 근거](evidence.md#새-여행과-목록-반영)에 보존한다.

작성 초안은 이미 읽은 서버 내용과 달리 사용자의 미저장 입력이다. 연결이 바뀌면 실행할 수 없는 기능 영역을 제한하고 초안 자체는 유지한다는 기준을 세웠다. 다만 현재 일정 수정 화면은 정책 제한 때 입력 영역 전체를 대체하므로 이 기준의 구현 완료를 뜻하지 않는다. [작성 계약과 현재 구현 차이](../INDEX.md#작성과-읽기의-제한을-구별한다)를 함께 확인한다. 활성 여행의 일정은 Local 데이터이므로 경비의 일정 연결을 외부 검색처럼 막지 않는다. 경비 날짜와 일정 연결을 별개로 정한 선택은 [경비 형성 근거](evidence.md#경비-초안과-일정-연결)에 있다. 날짜를 결제일·사용일 중 무엇으로 부를지는 여전히 별개 판단이다.

## 네트워크 관측 수명과 화면 복구를 분리했다

앱 복귀 재확인은 주기적 관측을 기다리지 않고 현재 상태를 확인하는 보완이다. 인터넷 연결이나 API 성공을 만들어 주는 동작은 아니다. 처음 앱 초기화에 직접 추가했던 구독은 기존 Store의 init~cleanup 감지 수명으로 옮겼다. 수동 확인·복귀 확인의 중복 요청 공유와 늦은 결과 처리를 같은 책임 안에서 재사용하기 위해서다.

## 현재 설명과 필요한 근거를 함께 옮겼다

제품 기준은 사용자 장면·데이터 의미를, 여행 접근 본문은 관련 개발의 구체 계약과 현재 연결을 맡는다. 선택 이유를 이해하려고 옛 제품 문서나 아카이브를 다시 읽어야 하는 구성은 이 목적을 충족하지 못한다. 필요한 당시 선택·기각 이유·발췌를 가까운 형성 근거에 선별했고 현재 본문과 함께 관리한다. 옛 Policy 호환 진입은 남기지 않는다.

미전송 정리·지도 준비 전체의 성공 보장, 새 오류 UX와 전역 FSD 예외는 이관으로 채택하지 않는다. 활성 여행의 범위, 서버 목록의 보존·선택 조건, 입력 수명 또는 Policy 책임이 바뀌면 해당 코드와 여기 보존한 선택 이유를 함께 재검토한다.

## 짧은 Router·Policy 규칙을 변경 질문에 합쳤다

기존 Activation Router·Policy UI rule과 Guard Map의 Data/Service 구분은 유효하다. 별도 규칙·위험 지도에서 같은 문장을 다시 관리하는 대신 실제 분기 표와 사용 가능 여부·실행 위치·표시 책임 옆에 배치했다. 특히 ‘Hook이 DB/API를 고르지 않는다’는 말은 hook이 repository를 호출하지 못한다는 금지가 아니라, repository의 Router 선택 책임을 우회하지 말라는 뜻으로 보존했다. 새 Entity는 UI 전에 데이터 경계를 정하며, Policy 제한 안내를 바꿔도 Router를 우회하지 않는다는 조건을 유지한다. 새 분리 문서를 만들지 않아 관련 작업이 기존 설명의 예외·현재 공백까지 같은 읽기에서 확인하게 했다.
