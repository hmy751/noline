# 값의 위치보다 수명을 먼저 구분한 이유

[작성 기준](../INDEX.md)을 이해하고 변경할 때 필요한 형성 맥락이다. 일정·경비·picker의 기존 설명과 2026-10-01~06 구현 기록, 현재 호출부·검사를 대조해 구성했다. 당시 검증 수치를 현재 전체 앱의 보장으로 이어받지 않는다.

## 하나의 초안과 기능별 제한을 유지했다

일정 생성의 이전 문제는 네트워크 정책에 따라 수동/일반 폼과 전체 차단 화면이 달라지고, 장소 변경의 reset과 감시 effect가 제목·입력을 덮는 것이었다. 값 자체가 이미 화면의 hook에 있었다는 점만으로 문제를 설명할 수 없었다. 사용자 작성 단계, 초안과 채택 장소, 검색·지도·저장 가용성을 구분해 네트워크가 작성 수명을 지배하지 않게 했다.

초안·검색·제출 hook을 조건부 패널보다 위에서 유지한 것은 검색을 오갈 때 작성 상태를 보존하기 위해서다. 코드 길이를 줄이려고 hook을 폼 내부로 옮기거나 총괄 workflow hook을 추가하는 안은 필수 개선으로 채택하지 않았다. 수명을 확인하는 소비 경로가 늘어나는 비용을 받아들였고, 현재 변경도 부모 key·장착·대상값을 함께 보게 했다.

경비는 날짜와 일정 연결을 독립된 입력으로 정했다. 활성 여행의 일정은 Local에 있는데 오프라인이라는 이유로 연결을 숨기거나 경비와 같은 날짜로 후보를 제한할 이유가 없었다. 같은 여행 전체 후보와 명시적 해제를 사용하며, 비활성 여행이 제한되면 전체 후보 대신 이미 선택한 일정 설명만 보존한다. 이 선택의 제품 의미와 발췌는 [여행 접근 근거](../../travel-access/_background/evidence.md#경비-초안과-일정-연결)가 소유한다. 날짜를 결제일/사용일로 부르는 의미나 일정 삭제·접근권 변경 뒤 연결 정책까지 결정한 것은 아니다.

## Places는 결과 보장과 소비자 호환을 분리했다

생성과 수정이 공유하는 것은 검색·상세 검증·query·정책이며, 후보를 초안에 채택하는 행위는 feature가 맡는다. 생성은 상세 확인된 결과만 받으므로 한 건의 상세 실패가 전체 검색 실패가 되는 비용이 있다. 부분 성공 UX로 바꾸려면 결과와 오류 표현의 계약을 함께 판단해야 한다.

수정은 이전 상세 실패의 0/0 동작을 adapter에 격리했다. 정상 장소 타입의 보장을 낮추지 않고 기존 동작을 유지하기 위한 한정 선택이며, 그 값이 실제 장소를 가리킨다는 뜻은 아니다. 정상 0 좌표와 실패 대체값을 구분해야 한다. 지도에서 B를 보여도 초안 A를 유지하고 명시적으로 선택할 때만 바꾸는 이유도 표시와 채택의 보장이 다르기 때문이다.

## Picker의 임시 선택과 폼 연결을 나눴다

폼 날짜와 다른 달로 열리고 폼 시각과 다른 행부터 보이는 문제는 저장 시간대 변환과 별개였다. DatePicker는 현재 폼 날짜의 달·강조를 받고 재열기 때 새 Calendar를 만든다. 시간은 중앙 고정 줄에서 값을 읽는 유한 휠을 채택했다. 무한 순환·native picker·입체 효과까지 요청한 결과로 확장하지 않았다.

TimePicker는 원래도 RHF를 몰랐다. 실제 분산은 Controller의 표시·오류, 화면의 watch, 여러 위치의 열기·닫기·setValue였다. TimeField가 이를 구독·선택창 수명·확정 반영으로 묶고 trigger 모양은 호출자가 정하게 했다. 기존 setValue 검증·dirty/touched 의미는 보존했다. public API 이름을 바꾸거나 TimeWheel 파일을 추가하는 것을 자동 필수 작업으로 만들지 않았다.

## 기존 설명의 현재성은 부모까지 다시 판단했다

이관 전 폼 본문은 책임·조건·실패를 이미 구체적으로 설명해 유효한 문단·비교표·Controller 예시를 유지했다. 초안·장소·picker는 별도로 바꿀 질문이어서 상세를 나눴고, 제출과 공통 책임은 시작 본문에 두었다. 수동 입력만 별도 폼인 것처럼 보이게 하는 문서는 통합했다.

이관 당시 경비 Drawer 내부의 ID effect만 보면 같은 ID의 isOpen 토글은 reset하지 않았지만, 실제 부모는 닫을 때 선택 대상을 비웠다. 부모까지 대조해 재열기는 원본으로 reset한다고 바로잡은 이유다. 수정 장소 검색도 닫힌 채 장착된 경우와 실제 부모의 조건부 해제를 구별했다. 일정 정책 제한은 입력 표시 계약을 어기지만 RHF 상태는 유지하고 TimeField 임시 선택은 해제한다. 이 차이를 제품 계약 축소나 모든 초안 소실 주장으로 바꾸지 않았다.

이후 편집 코드 간결화에서는 입력과 진행 중인 저장의 수명을 분리했다. React의 [key에 따른 폼 초기화](https://react.dev/learn/preserving-and-resetting-state#resetting-a-form-with-a-key)와 [prop 변화의 전체 상태 초기화](https://react.dev/learn/you-might-not-need-an-effect#resetting-all-state-when-a-prop-changes)를 근거로, 두 수정 Drawer의 내부 폼을 열림·대상 ID에 맞춰 새로 만들도록 정리했다. 같은 ID의 배경 갱신을 무시할 초기값은 폼에 고정하고, 렌더와 검증에 쓰는 일정 시간대는 ref가 아닌 편집 기준 state에 포함했다. 이는 모든 초기값을 prop과 계속 동기화하라는 뜻이 아니다.

조건부 해제만으로 이미 시작한 Promise가 취소되지는 않는다. 해제된 폼의 늦은 검증·성공·실패가 새 폼에 영향을 주지 않도록 하는 확인은 유지한다. 반면 공개 Drawer의 공통 저장 잠금은 제거하고 각 폼의 `isSubmitting`으로 저장·취소·닫기를 제어한다. 앞선 잠금 검사는 두 press를 하나의 `act`에 묶거나 부모 props를 강제로 교체한 조건이었으므로, 일반 사용자 탭에서 `isSubmitting`이 부족하다는 근거로 사용할 수 없었다. 사용자가 이 구별을 짚고 기존 제출 상태로 정리하도록 요청했다. 새 폼의 저장을 이전 폼 때문에 막는 것과 이전 응답이 새 입력을 덮지 못하게 하는 것을 별개의 책임으로 판단한 이유다. [Testing Library의 사용자 이벤트 권장](https://oss.callstack.com/react-native-testing-library/13.x/docs/api/events/user-event)에 따라 탭은 순차 `userEvent`로 검사하고, 강제 대상 교체는 응답의 수명 경계 검사로 구별한다.

처음에는 성공 후에도 소비자가 창을 유지할 수 있다고 보고 비교 기준 갱신을 제출 처리에 남겼다. 이후 실제 두 Screen은 성공 시 열림 상태와 선택 항목을 비워 폼을 해제한다는 점과 아래 사용자의 성공 후 닫기 결정을 대조해, 두 폼의 `reset`과 일정 비교 기준 갱신을 제거했다. 빈 `onClose`로 열린 폼에 재저장하던 테스트도 실제 닫기·재열기 흐름으로 바꿨다. 초기 데이터·시간대를 고정하는 상태는 배경 조회에서 편집 기준을 보호하므로 유지한다. `isCurrentEdit`은 편집 내용의 변경 여부가 아닌 폼의 장착 여부를 확인하므로 `isMounted`로 이름을 맞췄다. 이 확인은 계정별 화면 재생성 등으로 폼이 해제된 뒤의 비동기 검증·알림·닫기를 제한한다. 적용 범위는 두 수정 폼이며 생성 초안의 검색 단계 보존이나 native 닫힘 애니메이션 전체를 새로 보장하지 않는다.

제출 뒤 같은 폼에서 추가 편집한 값이 성공 시 reset과 닫기로 사라지는 장면을 확인한 뒤, 입력 잠금과 추가 변경이 있을 때만 폼을 유지하는 대안을 검토했다. 사용자는 “그냥 닫는걸로 해 성공하면 그것도 충분해보여”라고 성공 후 닫기를 선택했다. 따라서 제출 당시 값을 저장하고 성공하면 편집을 끝내는 기존 흐름을 유지하며, 같은 폼의 제출 후 미저장 변경까지 자동 저장·복원하는 범위로 넓히지 않는다. 이미 확정된 큐 입력과 새로 열린 다른 폼의 보호는 별개로 유지한다.
