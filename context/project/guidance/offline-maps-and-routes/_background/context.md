# 지도와 경로를 미리 준비하는 선택

[현재 본문](../INDEX.md)의 선택 이유를 재검토하기 위한 자료다. 과거 결정의 목적과 현재 구현 관찰을 구별하며, 당시 API 가격·성능 예상이나 완료 체크를 현재 지원 선언으로 보존하지 않는다.

## 연결이 끊긴 여행에서도 지도를 남기려 했다

2025-11-07의 지도 도입 결정은 여행 중 네트워크가 끊겨도 계획한 지역의 지도를 볼 수 있어야 한다는 문제에서 시작했다. 당시 비교는 Google 지도 경로, OpenStreetMap 기반 직접 구성, React Native 지도 라이브러리와 Mapbox의 통합 비용을 살폈고, 앱에서 지역·zoom·style을 지정해 native 자원을 미리 받는 Mapbox 경로를 선택했다. 이 문장은 당시 판단의 복원이며 다른 공급자의 현재 기능·약관·가격을 판정하는 자료가 아니다. 공급자를 다시 선택하면 그 시점 조건을 별도 확인해야 한다.

지도 자원을 SQLite에 직접 넣지 않고 native 저장소에 맡긴 것은 SDK의 다운로드·렌더링을 이용하려는 선택이다. SQLite에는 앱이 조회할 도시·범위·공유 정보를 둔다. 받아들인 비용은 두 저장소를 함께 관리해야 한다는 점이다. DB 초기화 뒤 native pack만 남아 중복 등록이 발생한 과거 관찰은 이 비용을 보여 준다. metadata와 pack을 함께 확인하는 현재 기준은 이 불일치를 숨기지 않으려는 것이다.

도시별 공유는 같은 도시를 방문하는 여러 여행의 중복 다운로드를 줄이려는 선택이었다. 여행별 독립 pack은 관계가 단순하지만 용량·다운로드가 반복되고, 하나의 전역 pack만 유지하면 도시를 옮길 때 교체·재다운로드 비용이 생긴다. 도시 단위는 그 사이의 재사용 단위지만 실제 획득·해제 관계를 관리해야 한다. 지금의 count 갱신·만료 재계산이 서로 다른 집합을 센다는 관찰 때문에 단순 count를 자원 소유의 증거로 사용할 수 없다.

원래 첫 일정 생성을 다운로드 계기로 둔 이유는 여행만 만들고 사용하지 않는 경우의 선다운로드를 줄이려는 것이었다. 현재 진입은 명시적 활성화로 바뀌었다. 이를 옛 이유의 단순 연장이나 새로 합의한 제품 결정으로 꾸미지 않고 현재 호출 경로로 정정했다. zoom을 넓히면 상세 지도와 다운로드량이 함께 늘어나는 절충은 유지하지만, 예전 용량·소요 시간 예상과 토큰 초기화 문제를 zoom 자체의 검증 결과로 보존하지 않았다.

## 이동 경로는 온라인 계산 결과를 남겨 표시한다

2025-11-08의 경로 결정은 지도 타일만으로 도로를 따라가는 선·거리·시간을 얻을 수 없다는 점을 다뤘다. 온라인에서 이동수단별 geometry를 계산해 Local에 남기면 연결이 끊겨도 선택한 경로를 볼 수 있다. 반대로 매번 실시간 계산하는 방식은 연결에 의존하고, 직선만 잇는 방식은 화면을 유지하지만 실제 도로를 표현하지 못한다. 저장 결과가 없을 때 직선을 쓰는 fallback은 이 차이를 감수하고 일정의 공간 관계를 보여 주려는 선택이다.

경로 공급자도 Mapbox Directions를 택한 당시 이유는 이미 사용 중인 Mapbox 지도와의 통합 비용을 줄이고, 자체 경로 서버의 구축·운영 부담을 피하려는 것이었다. 직접 호스팅은 운영 책임과 자원 관리가 늘어나는 대안이었다. 현재 가격·호스팅 조건의 우열을 뜻하지 않으므로 공급자를 바꾸면 통합 비용과 운영 책임을 당시 조건으로 다시 비교한다.

여러 이동수단을 준비하면 오프라인 전환이 가능하지만 API 호출·저장량이 늘고 일부만 성공할 수 있다. 전체 재계산은 흐름이 단순한 대신 반복 비용이 있고, 변경 구간만 갱신하면 호출을 줄이는 대신 최신 좌표·순서·기존 결과를 비교해야 한다. 이 절충은 유지하되 현재 두 downloader의 중복 저장과 ID 쌍 재사용을 완성된 증분 전략이라고 설명하지 않았다.

시각 수정 뒤 재계산하는 이유는 일정의 인접 관계가 달라지기 때문이다. 저장 성공 뒤 500ms를 기다리는 예전 설명은 캐시 반영을 기대했지만, 현재 코드가 캡처한 목록과 새 좌표의 관계를 보장하지 않는다. 이 지연을 개발 규칙에서 제외해도 인접 관계·최신 입력을 확인해야 한다는 이유는 남긴다. polyline6는 요청과 decode의 정밀도를 맞춰야 한다는 의미를 보존하며 압축률·도로 스냅 오차를 검증 없이 단정하지 않는다.

## 준비 표시의 근거를 다시 분리했다

2026-10-31 대조에서는 지도 helper가 native 등록 후 완료 flag를 기록하는 반면 설치 SDK iOS 경로는 로딩 시작 후 반환하고 완료를 별도 이벤트로 알리는 구조를 확인했다. 경로 downloader는 전체 실패도 downloaded:0으로 반환할 수 있고 renderer는 저장된 첫 matching row를 고른다. 그래서 등록·저장 행·함수 반환을 실제 사용 가능성과 분리했다. 이는 실기기 실패를 새로 재현했다는 주장이 아니라 직접 소스에서 확인한 완료 경계다.

기존 문서의 코드 전문·구현 완료 목록보다 현재 독자는 준비 결과, 공유 파일의 수명, 일정 변경 뒤 geometry의 적합성을 함께 알아야 한다. 시작 본문은 그 관계를 묶고 지도 파일·경로 상세는 관련 변경 때만 읽게 나눴다. 비교표는 서로 다른 동작을 한 기준으로 대조하는 데 유지하고, 일반 체크리스트와 고정 코드 지시는 실제 작업 조건 가까이 재구성했다. 과거의 선택 이유를 없애거나 모든 기존 형식을 버리는 전환은 아니다.

이 배경의 근거는 지도·경로 도입 결정과 기존 가이드, 현재 activation·offline-map·directions·route·map renderer 및 SDK 소스다. 원본 판본과 문장 묶음의 처리 판단은 006의 이관 기록이 보존한다. 현재 판단에 필요한 이유는 여기에 담았으며 옛 파일이나 아카이브를 다시 읽어야만 적용할 조건은 남기지 않는다.
