# 변경할 책임에서 시작한다

**언제 쓰나:** client 계층·공용 UI·TypeScript와 공유 schema를 추가하거나 옮길 때 읽는다.

**핵심 기준:** 같은 화면에서 쓰인다는 이유보다 무엇이 바뀔 때 함께 바뀌는지를 보고 책임을 정한다. 기존 모듈의 역할과 실제 소비자를 확인하고, 공유 계약·저장 경로·사용자 흐름을 보존한다. 현재 코드의 예외는 그 범위와 비용까지 확인한 뒤 재사용한다.

| 변경할 것 | 적용할 본문 |
| --- | --- |
| 라우팅·앱 준비·화면·feature·entity·shared의 위치나 의존 | [계층과 재사용](layers.md)에서 기본 방향과 현재 한정 예외를 구별한다. |
| UI primitive·앱 공용 조합·domain 표시·폼 adapter | [UI 책임](ui.md)에서 상태·간격·부작용의 소유자를 정한다. |
| 공유 데이터 shape·타입·입출력 검증·코드 스타일 | [TypeScript와 schema](schema-and-types.md)에서 정적 타입과 실제 검증 경계를 나누어 확인한다. |

예를 들어 일정 생성 화면을 바꾼다면 route는 화면 진입, screen은 작성 단계와 화면 조립, feature는 초안·장소 선택·제출, entity는 데이터 접근을 맡는다. 시간 선택창의 임시 선택은 UI 안에 남을 수 있고, 저장 요청은 공유 schema로 수렴한다. 파일을 작은 함수마다 나누거나 모든 상태를 feature로 올리는 것으로 이 책임 분리를 대신하지 않는다.

관련 데이터 경로에서는 [여행 접근](../travel-access/INDEX.md), [저장·동기화·정리](../data-lifecycle/INDEX.md)를 함께 적용한다. Map/Search/Directions는 사용자 소유 데이터의 Router 경로가 아니라 Policy를 따르는 서비스이며 [지도·경로](../offline-maps-and-routes/INDEX.md)가 준비·표시의 현재 차이를 설명한다. API의 직렬화·접근·오류 계약은 [API 가이드](../api-contracts.md)가 소유한다.

기능 추가 전에는 같은 책임의 기존 앱 모듈과 package를 찾아 핵심 동작·인터페이스·품질과 변경 비용을 비교한다. 주요 로직이 같고 옵션 차이만 있다면 확장을 우선 검토하고, 큰 수정이나 서로 다른 규칙이 필요하면 별도 구현을 고려한다. 여러 앱에서 쓸 수 있다는 가능성만으로 미리 package를 만들지 않으며, 앱에 고유한 조합은 client에 둔다. 의존성은 사용하는 workspace에 선언하고 루트에는 공통 개발 도구처럼 실제 공통 책임만 둔다. 버전은 호환성을 보면서 맞춘다.

구조 변경 뒤에는 실제 호출 흐름과 영향받는 검사로 동작 보존을 확인한다. [리팩터링 기준](../behavior-preserving-refactoring.md)과 각 app/package guide에서 검사 범위를 고른다. 타입 검사·lint 성공은 런타임 입력 검증이나 native 동작 성공을 뜻하지 않는다.
