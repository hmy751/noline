# 경계를 남기고 현재 예외를 드러낸 이유

[개발 기준](../INDEX.md)의 책임 배치와 정정 이유를 설명한다. 2026-10-31에 기존 구조·component·TypeScript 설명, 2025-11-24 Store 결정, 조회 feature의 배치 기록과 현재 코드를 대조했다. 아래 과거 선택은 보존한 당시 기록에서 확인한 이유이며, 최신 소스가 그 효과를 모두 입증한다는 뜻은 아니다.

## 폴더 모양보다 변경 책임을 보존했다

기존 구조는 라우팅·화면 조립·사용자 작업·entity·앱 공통 기반·UI primitive를 나눠 변경 영향을 줄이려는 목적이었다. 별도 widgets 계층 대신 features에 작은 action과 조합을 함께 허용해 실용성을 택했다. 이 구분은 유효해서 책임 표로 유지했다. 다만 없는 packages/db·Prisma, 빠진 application, 모든 app 파일이 단순 screen 연결이라는 설명은 현재 소스와 달라 정정했다. Client SQLite와 server PostgreSQL/Drizzle의 실제 소유 위치를 현재 구조에 연결했다.

Shared를 비즈니스와 무관하다고 한 문장과 앱 전용 service·policy를 허용한 설명은 서로 맞지 않았다. 공통 기반의 역할은 보존하면서 domain 표시·workflow의 기본 위치와 이미 존재하는 역방향 참조를 구분했다. 현재 예외를 숨기면 새 작업자가 잘못된 순수성을 전제로 수정하고, 예외를 일반화하면 경계가 사라진다. 본문은 실제 예외와 확대 시 판단할 범위를 함께 남긴다.

## Store·service·policy는 주 책임으로 나눴다

2025-11-24 결정은 상태를 보유하는 Network 구현이 services 아래 여러 파일로 흩어진 문제를 다뤘다. Network를 store로 옮겨 관련 hook과 비React 접근을 함께 찾게 하고, 작업 수행은 services, 규칙 계산은 policy로 구별했다. Policy를 store로 합치는 안은 계산 규칙과 보유 상태가 섞이고 정책 책임이 흐려진다는 이유로, Network를 services에 그대로 두고 파일만 합치는 안은 실행·상태의 구분이 남지 않는다는 이유로 채택하지 않았다.

경로·API 변경 비용을 받아들이고 관련 소비자를 갱신한 선택이다. 당시의 4개 파일을 1개로 합친 결과는 모든 store를 영구히 한 파일로 고정할 이유가 아니다. 현재 Network에는 감지 세션·refresh·복귀 구독이, Auth Store에는 계정·기기 기록 적용이 있다. 상태 수명과 맞물린 실행을 허용하되 전체 로그인·로그아웃 절차는 service가 맡는 것으로 설명했다. 당시 Policy 5분 캐시 최적화와 렌더 성능 주장도 현재 전체 동작의 실측 보장으로 가져오지 않았다. 현재 Policy는 entity의 활성 조회와 세션·실제/표시 네트워크를 사용한다.

## 조회 조합의 재사용은 좁은 비용 비교였다

2026-09-29 조회 배치에서는 모든 조회를 trip feature로 모으기보다 일정·경비가 각 결과를 소유하게 했다. Entity query는 key·repository·캐시 설정을 유지하고 feature는 Policy와 연결한다. 공통 policy-query service는 계산된 접근과 query를 조합하며 구체 일정·경비 query를 직접 import하지 않는다.

엄격한 같은 계층 격리를 유지하려면 소비 폼마다 조합을 반복하고, entity로 내리면 Policy의 책임 기준을 바꿔야 했다. 그래서 UI·입력·저장을 갖지 않는 공개 조회 훅을 조건부로 재사용하고 역의존·폼 간 의존은 만들지 않는 한정안을 택했다. 당시 사용자는 우선 Workspace에 기록하도록 요청했으며, 이번 설명도 그 사례를 일반 feature 간 import 허용으로 승격하지 않는다. 현재 폼 적용은 코드에서 확인했고 조건·비용은 본문 가까이에 보존했다. 확대하려면 중복 비용과 계층 결합을 다시 비교해야 한다.

## UI와 타입의 잘못된 예제는 규칙과 분리했다

Component 설명의 primitive·domain·workflow 구분과 외부 margin의 부모 소유는 유효했다. 같은 질문을 반복하는 마지막 체크리스트 대신 적용 조건 가까이에 두었다. UI의 임시 선택과 form adapter 책임을 유지해 모든 상태를 feature로 옮기는 오해를 피했다. 현재 Button export가 없으므로 Pressable을 실제 사례로 썼다. 이 정정이 버튼 UX를 바꾼 것은 아니다.

Schema를 공유하는 이유는 수기 DTO와 검증 shape의 불일치를 줄이기 위해서다. 그러나 z.infer는 실행이 없고, 기존 속성 존재 guard는 값 타입을 검증하지 않았다. 타입 export가 전혀 없다는 주장도 AuthProvider와 달랐다. 유효한 schema-first 기준을 유지하며 parse와 타입 연결, 입력·출력, 물리 DB와 전송 표현을 나눴다. 존재하지 않는 묶음 import·web 예시·검증을 보장하는 듯한 예제는 제거하고 실제 Expense 경로로 설명했다.

TypeScript의 기본 type·import 순서·명명·함수·주석 기준은 코드의 불일치만으로 폐기하지 않았다. 준수하지 않는 현재 예시와 검사의 상한을 따로 밝혔다. 오류를 null로 감추는 교육 예제는 실패 전달 계약을 훼손할 수 있어 일반 기준으로 옮기지 않았고, 오류 의미를 소유한 API 본문과 연결했다. 새 설명을 위해 Zod나 FSD의 최신 외부 권고를 도입한 것은 아니다.
