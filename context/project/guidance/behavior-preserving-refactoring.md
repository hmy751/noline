# 동작을 보존하는 코드 리팩터링

기존 제품 동작을 유지하면서 이름·조건·변환·흐름·내부 책임과 여러 소비 지점의 수정 부담을 줄일 때 읽는다. 명시적인 결함 수정이나 새 기능이 주목적이면 해당 작업의 제품 기준을 먼저 정하고, 이 가이드를 버그를 그대로 고정하는 근거로 사용하지 않는다.

이 본문은 Workspace 002의 Ticket 01~05에서 반복 확인한 리팩터링 판단을 Project 기준으로 통합한다. Ticket의 진행·수락·실행 수치와 시행착오는 Workspace에 남고, 다음 관련 작업이 적용할 계약은 여기서 소유한다.

## 수정 목록보다 맡을 결과를 먼저 정한다

가독성 개선은 로그 삭제나 helper 추출 같은 활동이 아니라, 어떤 이해·수정 부담을 줄이고 어떤 동작을 보존할지로 정의한다. 바텀 요소부터 시작한다는 것은 이름·조건·기본값·변환처럼 가까운 코드에서 문제를 찾는 순서이지 개선 깊이의 상한이 아니다.

함수나 파일 하나로 범위를 자동 제한하지 않는다. 같은 의미를 고치려면 함께 맞춰야 하는 consumer, 실패·상태 연결, schema와 저장 경계를 따라 필요한 범위를 확인한다. 반대로 코드가 가깝다는 이유만으로 공개 동작 변경이나 별도 결함을 포함하지 않는다. 일부만 먼저 정리한다면 그 단계가 주는 결과와 남은 수정 부담, 후속 책임을 분명히 한다.

## 보존할 계약은 관찰 가능한 관계다

입력과 반환값뿐 아니라 오류 전달, 저장 결과, 화면 변화, 부분 실패 뒤 남는 값, 부작용의 횟수와 순서, 비동기 응답의 최신성, 인증·삭제 필터도 변경에 관련되면 보존 계약에 포함한다. 모든 내부 호출 순서를 테스트로 고정하지 않고 결과를 갈라놓는 조건을 고른다.

변경 전 버그나 제품 의미가 불명확한 동작은 자동으로 정답이 아니다. 먼저 현재 결과를 재현하고, 의도된 계약·알려진 결함·열린 제품 선택을 구별한다. 결함을 고치거나 방어 동작을 새로 넣었다면 동작 보존과 의도한 변경을 따로 설명하고 검증한다.

## 변경 전후와 개선 효과를 따로 확인한다

가능하면 제품 코드를 바꾸기 전에 현재 경계를 특성화하고, 변경 후 같은 조건으로 비교한다. 테스트가 없다면 영향과 위험에 맞는 fixture·정적 대조·수동 관찰을 선택한다. 테스트가 구현 helper의 존재나 호출 순서를 그대로 복제해 내부 정리만으로 깨지지 않게 한다.

동작 보존이 확인돼도 가독성 개선이 자동으로 입증되지는 않는다. 변경 전 무엇을 여러 위치에서 추적해야 했는지 정하고, 변경 후에는 다음을 직접 비교한다.

- 값·조건·책임의 실제 의미가 이름·타입·가까운 흐름에서 읽히는가.
- 같은 의미의 수정 위치가 줄고 필요한 차이의 이유는 남았는가.
- helper나 범용 옵션이 간접 호출과 숨은 상태를 늘려 부담을 다른 곳으로 옮기지 않았는가.
- 완료 조건을 이미 고른 수정 목록에 맞춰 낮추지 않았는가.

## 영향에 맞는 검증 경계를 고른다

- 이름·주석·저위험 표현은 diff, 사용처, 관련 lint·type 확인으로 충분할 수 있다.
- 조건·계산·변환은 결과를 나누는 입력과 경계값을 전후 비교한다.
- React hook·비동기 흐름은 실제 hook을 실행해 부분 실패, refresh, 겹친 요청과 unmount 뒤 결과를 확인한다. Native module mock은 실제 기기 연결을 대신하지 않는다.
- Client API는 request가 HTTP 전에 검증되는지, response가 반환 전에 검증되는지, network·schema 오류가 호출부에 어떻게 전달되는지 확인한다.
- Server API의 공통 serializer는 단위 검사만으로 끝내지 않고 실제 route가 사용하는지 endpoint 계약 검사로 확인한다. SQL의 ownership·soft-delete 의미는 mock chain이 아니라 격리된 DB 검사로 보완한다.

실행하지 않은 native·외부 서비스·실제 인증·배포 경계를 통과한 것으로 넓히지 않는다. 전체 lint나 typecheck가 실패하면 변경 대상에서 새로 생긴 문제와 기존 실패를 구별하고, 우회한 규칙과 그에 따른 증명 상한을 남긴다.

## 완료된 사례에서 적용할 판단

- 경비 합계에서는 `baseCurrency`와 첫 그룹을 같은 뜻으로 이름 붙이지 않고, 강조·라벨이 공유하는 실제 조건과 통화별 자릿수 위치를 정리했다. 금액 반올림 정책은 별도 선택으로 남겼다.
- 도시 검색에서는 요청과 응답 필터가 공유하는 허용 코드를 한곳에 두고, 수도 예외·인구 경계·필드 변환을 이름 있는 책임으로 만들었다. 요청 실패 시 빈 배열이라는 외부 동작은 유지했다. 기능별 현재 계약은 [도시 검색의 현재 경계](../current/city-search.md)에서 확인한다.
- 저장 용량 hook에서는 표시 helper만 뽑는 얕은 정리로 끝내지 않고 SQLite·Mapbox 집계, 부분 실패와 React 최신 요청 반영을 같은 파일의 읽을 수 있는 책임으로 나눴다. 현재의 유효하지 않은 byte 방어와 늦은 응답 차단은 이후 변경이 보존할 현재 동작이지만, 모든 hook의 공통 제품 요구로 일반화하지 않는다. 실패 위치별 결과는 [저장 용량 집계의 현재 경계](../current/storage-statistics.md)가 소유한다.
- Expense API에서는 request parse, HTTP, response parse, 반환을 직접 보이게 하고 같은 오류를 기록한 뒤 재전파하던 catch를 제거했다. 오류 객체를 바꾸는 전역 fetcher와 React Query/UI의 책임은 그대로 남겼다.
- Schedule 응답에서는 일부 route만 helper로 바꾸지 않고 같은 시간 변환의 일곱 consumer를 함께 정리했다. Serializer, response schema와 접근 query는 서로 다른 책임으로 유지했다.
