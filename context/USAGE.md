# 필요한 맥락을 읽고 적용한다

평소 읽기에서는 해석·열린 후보를 채택 기준과 구별한다. 경험 검토를 요청받으면 [경험 길잡이](personal/experience/README.md)와 [관리 계약](personal/experience/MAINTENANCE.md)에서 해당 범위를 찾는다. 이번 작업의 기존 지시·재개 본문에 이미 선택된 한정 시도가 있다면 적용 상황·행동·끝나는 범위와 마무리 책임을 함께 읽는다. 다른 작업이나 종료된 시도에 확대하지 않으며, 일반 작업에 모든 후보 열람을 요구하지 않는다.

맡은 질문에 필요한 원문을 선택해 실제 대상과 대조하고, 적용할 의미·조건·남은 판단을 원래 과업에 연결한다. Main의 재개, 구현·검토·검증 중 탐색, 별도의 읽기·설명 요청에서 사용하는 공통 방법이다. 이 문서가 목표·제품 약속·수정 권한을 새로 정하지는 않는다.

대상과 내용의 경계는 [context 진입점](README.md), 일반 재개와 한정 위임의 차이는 [Work 지침](work/AGENTS.md)에서 찾는다. Main 또는 맡은 담당자는 현재 요청·검토 의견·실제 결과가 새 질문을 만들 때 필요한 자료를 추가로 고르고, 한정 위임 결과는 Main에게 돌려준다. 이미 관련 내용을 유효하게 읽었다면 이 문서를 읽었다는 이유로 다시 인수를 시작하지 않는다.

## 이번 질문에서 본문을 선택한다

사용자가 지정한 Project·Work와 맡은 요청을 우선한다. 지정이 없으면 대상의 진입 지침에서 실제 맥락 위치를 찾는다. 스킬 설치 위치나 Git 최상위를 곧바로 작업 대상으로 가정하지 않는다. 기존 Work 재개인지, 한정 질문인지, Work 없는 작업인지에 맞춰 읽으며 Work 생성은 읽기의 선행 조건이 아니다.

이번 판단을 바꾸는 질문에서 관련 영역의 입구와 본문을 고른다. Main이 준 최초 자료는 출발점이며 추가 탐색의 허용 목록이 아니다.

| 필요한 이해 | 선택할 내용 |
| --- | --- |
| 이번 목표·이미 선택한 이유·남은 행동 | 해당 Work의 현재 의미와 필요한 Spec·Ticket·결과. 일반 재개의 순서는 Work 지침을 따른다. |
| 여러 작업에 적용할 판단 관점과 조건 | [Personal](personal/README.md)의 관련 기준. 선택 차이를 이해해야 하면 상세 사례도 읽는다. |
| 제품의 뜻·약속·현재 구조와 지원 제약 | [Project](project/README.md)의 해당 주제. 제품별 질문과 계약 대조는 [Project 읽기 기준](project/REFERENCE/reading.md)을 따른다. |
| 현재 결과가 실제로 무엇을 하는지 | 관련 코드·산출물·실행 근거. 문서의 주장 범위와 실제 사용 조건을 대조한다. |
| 현재 뜻을 더 정확히 이해하거나 의도·과거 선택을 재검토 | 해당 본문의 형성 자료에서 필요한 맥락·기록·원문 근거. 모든 이력을 기본 입력으로 붙이지 않는다. |

Work에 남은 이번 적용·선택과 Main의 설명은 원문을 찾고 판단할 단서다. 그것이 원문 전체나 담당자의 직접 이해를 대신하지 않는다. 필요한 이유·조건이 현재 본문에서 빠졌다면 그 공백을 드러내며, 과거 기록을 모두 읽어 빈 계약을 대신 조립하지 않는다.

## 유효한 이해를 재사용하고 달라진 부분을 확인한다

같은 수행자가 충분히 읽었고 관련 변화가 없다면 같은 본문을 전부 다시 읽지 않는다. 다른 담당자가 읽었다는 사실만으로 자신의 원문 확인을 생략하지는 않는다. 새 사용처·검토 의견·실패·변경된 계약이 새 질문을 만들면 그 판단에 필요한 자료를 추가한다.

과거 판단을 평가할 때는 당시 입력과 조건을, 현재 수행을 이어갈 때는 현재 적용할 계약과 실제 결과를 확인한다. 경로가 같아도 본문·요구·판본이 달라졌을 수 있다. 중요한 반환 시에는 관련 변경 근거로 유효성을 대조하고, 확인하지 못한 현재판까지 의견을 확대하지 않는다. 전체 해시·열람 장부·전면 재독을 기본 요구로 만들지 않는다.

## 약속·관찰·열린 선택을 대조한다

본문이 맡는 의미·적용 조건·예외와 실제 대상의 관계를 이해한다. 채택된 약속, 그 약속이 적용되는 조건, 현재 구현이 지원하는 범위는 구별한다. 최신 문서라는 이유로 구현 완료를 가정하거나, 현재 코드라는 이유로 제품 약속을 바꾸지 않는다.

여러 사용처를 묶은 주장이라면 필요한 경계를 직접 확인하거나 확인한 범위로 한정한다. 충돌은 원요구·유효한 결정·직접 근거에서 대조한다. 범위 안에서 해결 가능한 판단은 이어 수행하고, 실제로 필요한 결정권·누락된 근거만 해당 판단과 함께 반환한다. 접근하지 못한 원문은 읽은 것으로 보고하지 않는다.

예를 들어 새 화면이 로그인 뒤 조회 결과를 필요로 한다면, 기존 소비자의 비대기 선택만 읽고 같은 처리를 반복하지 않는다. 인증 완료의 약속과 조회 실패의 의미, 새 소비자의 요구를 함께 대조한다. 이 예시는 질문이 바뀔 때 읽기를 바꾸는 장면이며 새 제품 요구를 부여하지 않는다.

## 원래 과업으로 돌아간다

필요한 이해가 생기면 맡은 구현·검토·검증·설명으로 돌아간다. 반환에는 판단을 바꾼 의미·조건·근거·중요한 공백을 연결한다. 읽은 모든 파일 목록이나 별도 이해 보고서·영구 기록은 기본 산출물이 아니다.

‘읽고 설명해 달라’는 요청은 적용할 내용·이유·남은 확인을 답하면 끝난다. ‘이번 current에 정리해 달라’면 Main이 Work 계약에 따라 반영할 의미를 정리해 record-work로 연결한다. 목표 정의나 전제 재판단이 필요하면 [기존 작업 스킬](../.agents/skills/README.md)의 호출 조건으로 연결하며 공통 읽기를 새 인터뷰나 전체 재설계로 늘리지 않는다.

지속 본문의 오류·누락을 발견하면 바뀔 의미·범위·근거를 반영 담당에게 연결한다. 읽기 자체는 쓰기 권한을 만들지 않는다. 원래 과업이 반영까지 허용했다면 같은 수행자가 유효한 근거를 이어 사용해 [context-update](../.agents/skills/context-update/SKILL.md)와 대상 관리 계약으로 반영할 수 있다. 개발 중 제안은 Main이 기존 위임 범위와 대상의 관리 권한에 따라 검토하고 반영한다. 상태 변화가 없으면 읽었다는 기록을 남기기 위해 current를 고치지 않는다.

이 방법의 목적·공통화 이유·남은 형태의 유보는 [형성 자료](_background/usage/README.md)에서 읽는다. 본문·형성 자료를 변경할 때는 [CONTENT-POLICY](CONTENT-POLICY.md)를 적용한다.
