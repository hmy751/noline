# Ticket 작성

Ticket은 이번 실행이 맡을 결과와 그 결과를 만드는 데 필요한 맥락, 진행과 실제 결과를 함께 남긴다. 이 문서는 Ticket 본문의 내용과 보존 기준을 소유한다. 작업 분해·실행·완료 판단에는 [목표를 실행 결과로 이어가는 기준](EXECUTION-CRITERIA.md)을 적용한다.

Ticket 안의 세부 작업마다 별도 관리 계층이나 Ticket을 만들지는 않는다. 기능 작업에서는 필요한 계층을 연결해 확인할 수 있는 동작을, 구조 개선에서는 동작 보존과 개선 효과를 확인할 수 있는 범위를 잡는다. 그 결과가 충분히 성립하는지 확인한 뒤 크기를 조절한다.

## 본문의 기본 구성

제목 아래 다음 네 부분을 기본 구성으로 사용한다. 정확한 제목·순서·세부 필드, 고정 상태 이름이나 특정 tracker는 요구하지 않는다. Spec의 공통 정의를 복제하기보다 이번 실행에 필요한 의미를 구체화한다.

### 맡은 결과와 범위

이번 실행으로 무엇이 달라지고 어디까지 끝내서 넘기는지 적는다. 관련 Spec 요구와 필요한 제외·후속 범위를 연결한다.

기능 구현이면 가능해질 동작을, 코드 개선이면 바꿀 책임·구조와 보존할 동작을 설명한다. 활동이나 파일 변경 목록만으로 맡은 결과를 대신하지 않는다.

### 실행 맥락과 접근

실행자가 작업을 시작하고 필요한 판단을 이어 갈 수 있도록 다음을 연결한다.

- 필요한 Spec 부분·원자료·코드·앞선 결과
- 선행 작업과 막힘
- 현재 설계와 선택 이유, 확인할 가정과 실행하면서 정할 부분

링크만으로 의미를 이어받기 어렵다면 핵심 내용도 적는다. 시작할 수 있을 만큼 구체화하되, 미정인 구조나 파일별 변경 계획을 억지로 고정하지 않는다.

### 완료 조건과 확인 방법

무엇이 관찰되면 맡은 결과를 이뤘다고 판단할지, 어떤 자료·동작·테스트·코드 비교로 확인할지 적는다. Spec의 공통 품질 기준을 Ticket 범위에 구체화한다.

코드 개선에서는 동작 보존과 구조 개선의 효과를 각각 확인한다. 보존 조건은 변경 전부터 통과할 수 있으며, 그 사실만으로 구조 개선을 입증하지는 않는다.

테스트 목록만으로 완료 조건을 대신하거나 다른 Ticket이 맡은 결과를 이번 완료 조건으로 삼지 않는다. 일부나 기반만 맡기는 경우의 충분성과 남은 책임은 [실행 기준](EXECUTION-CRITERIA.md#수정-방법보다-맡을-결과를-먼저-정한다)에 따라 설명한다.

### 현재 상태와 실제 결과

현재 진행, 실제로 만든 것과 확인한 근거, 보고받은 내용, 막힘·남은 일·미확인을 남긴다. 실행 전에는 상태를 짧게 두고 진행하며 결과를 채운다.

앞의 확인 계획과 실제 수행 결과를 구별한다. 상세 이력이 필요하면 records에 연결하되, 매번 긴 작업 일지를 쓸 필요는 없다.

## 진행과 보존

정의와 진행을 같은 Ticket 본문에 함께 적고 필요한 때 갱신한다. 새 Ticket은 `tickets/index.md`에서 찾을 수 있게 한다. 상태가 바뀐다는 이유로 정의와 진행을 서로 다른 문서로 강제 분리하지 않는다.

완료한 Ticket도 자연스럽게 남길 수 있다. 상세 이력·변경 이유·과정을 보존할 필요가 있으면 records를 사용한다. 완료나 현재 영향 유무만으로 자동 이동·삭제하지 않으며 매번 불변 사본을 만들지 않는다.

전체 state와 기계 status의 역할은 [진입 문서](README.md), 실제 갱신 책임과 다른 실행자의 결과 전달은 [갱신 기준](MAINTENANCE.md)을 따른다.
