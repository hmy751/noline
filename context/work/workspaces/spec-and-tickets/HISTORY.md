# Spec·Ticket 기준의 선택 배경과 변경 이력

이 문서는 현재 문구와 구성이 어떤 문제·논의·검토를 거쳐 선택됐는지 보존한다. 이후 지침을 고치는 Main이 처음의 실패를 다시 만들지 않고, 새로운 근거에 따라 선택을 발전시키는 데 사용한다. 현재 적용할 운영 기준은 [README](README.md)에서 연결하는 각 문서가 소유한다.

아래 내용은 결정 당시의 근거와 확인 범위다. 과거 표현이나 파일 배치를 영구히 고정하는 규칙으로 해석하지 않는다. 변경 전 읽기와 후속 결정 기록의 기준은 [README의 유지 규칙](README.md#이-기준의-유지)을 따른다.

## 2026-09-12 — Spec의 목표가 실행 중 축소되는 문제를 보완

### 사용자가 기대했던 개선

논의는 `002-code-readability-refactoring` Workspace의 Ticket 결과가 사용자가 기대한 깊이에 미치지 못하면서 시작됐다. 사용자는 콘솔·불필요한 주석 같은 작은 문제부터 컴포넌트의 복잡한 처리 흐름, 여러 위치의 연결에서 생기는 이해·수정 부담까지 하나씩 찾아 해결하기를 기대했다.

당시 사용자는 다음과 같이 설명했다.

> 여기서 바텀부터 라고 한건 AI가 회피할까봐 였어 그냥 여러군데 몇군데 특징적인거 고치고 끝 이럴까봐 고칠수있는 부분은 웬만큼 다 고쳐보려고 했거든

따라서 ‘바텀부터’는 표면적인 수정에 머물거나 모든 Ticket을 작게 제한하라는 뜻이 아니었다. 대표 사례 몇 곳을 고치고 전체 개선을 마쳤다고 판단하는 것을 막으려는 의도였다. 큰 구조 문제만 다루고 작은 문제를 빠뜨리는 방식도 이 기대를 충족하지 못한다.

Ticket 05에 관한 사용자 설명에서는 여러 위치의 연결 부담까지 이 Spec의 결과로 해결되기를 기대했다는 점이 드러났다. 이 기대는 관련 부분을 조사하고 필요한 조정안을 제시할 이유이며, 주변 코드를 제한 없이 변경하라는 권한으로 해석하지 않았다. Ticket 05의 구체적인 구현 범위와 수락은 별도 작업 판단으로 남겼다.

### 실제로 확인한 좁은 완료

Ticket 03의 `useStorageStats.ts` 최초 적용은 원래 작업 로그의 diff에서 재확인했다. `formatBytes`를 hook 밖으로 옮기고, 표시값 조립 helper를 추가하며, `setStats` 호출을 `finally` 한 곳으로 모았다. SQLite 파일 탐색, Mapbox 팩 집계, 실패 경계, React의 effect·refresh 연결은 이 최초 diff에서 나누거나 바꾸지 않았다.

그 상태에서 실행자는 “티켓 03의 요청 범위는 모두 수정했습니다”라고 보고했다. 이후 사용자는 개선 깊이와 React 관점 등을 여러 차례 보완했고, “그냥 프로덕션 수준의 퀄리티로 개선한다 생각해봐 이 파일 안에서”라고 요구했다. 후속 구현은 책임과 상태 연결을 더 다뤘으며 사용자는 기대에 가까워졌다고 평가했다.

이는 작은 Ticket 정의는 충족했어도 넓은 Spec의 품질 기대를 실행의 완료 기준으로 충분히 연결하지 못한 사례다. 최초 diff를 확인하기 전의 추정과 이후 확인은 구별했다. 또한 여러 차례의 정정이 있었으므로 `프로덕션 수준`이라는 한 표현만으로 결과가 개선됐다고 단정하지 않았다. 자세한 사실과 최소 원문은 [최초 적용 재확인 기록](../002-code-readability-refactoring/records/2026-09-12-01-ticket-03-initial-scope-reanalysis.md)에 보존돼 있다.

### 이름이나 Ticket 크기만으로 해결하지 않은 이유

사용자는 Spec의 목표를 ‘가독성’보다 ‘응집성·일관성’으로 정했어야 하는지, Ticket을 너무 작게 나눈 것인지, Spec과 Ticket의 구별을 바꿔야 하는지 등을 질문했다. 이들은 원인을 찾기 위한 가설과 우려였으며, 그대로 채택한 요구사항은 아니다.

기존 Spec에도 읽기·수정 부담, 공통점과 필요한 차이, 함께 수정할 위치, 대표 사례만으로 전체 완료하지 않는 기준이 있었다. 따라서 Spec의 이름만을 직접 원인으로 보거나 새 품질 단어를 추가하는 것으로 해결됐다고 판단할 근거는 부족했다.

선택은 Spec·Ticket의 구별을 유지하면서, **맡긴 결과에 필요한 일을 발견하는 책임과 그 결과로 완료를 판단하는 기준을 명확히 하는 것**이었다. 모든 Ticket을 크게 만들거나, 서브에이전트가 처리할 수 있는 크기를 먼저 정하거나, 개선 작업만의 별도 종류를 만드는 방식은 채택하지 않았다. 작은 작업도 충분한 결과를 만들면 유효하며, 큰 작업도 단계별 결과와 남은 책임이 이어지면 나눌 수 있다.

### 보존하려는 판단과 그 이유

아래는 현재 실행 기준을 선택한 이유다. 실제 행동 요구는 [EXECUTION-CRITERIA.md](EXECUTION-CRITERIA.md)가 소유한다.

- **결과를 맡기면 필요한 일을 찾는 책임도 따른다.** 분석의 예시나 Ticket 초안의 수정 목록만 처리하면, 사용자가 맡긴 전반적인 개선이나 기능 완성이 누락될 수 있다. 반면 수정 내용이 정해진 오탈자 요청에 같은 조사 책임을 적용하면 불필요하게 범위를 넓히게 된다.
- **같은 패턴의 다른 위치뿐 아니라 맡은 범위의 다른 문제도 살핀다.** 중복 한 곳만 찾거나 처음 발견한 종류만 반복해서 고치면 복잡한 흐름·상태·연결 같은 다른 부담을 놓칠 수 있다. 함께 다룰 이유는 목표·실제 사용·계약에서 찾으며, 같은 파일에 있다는 이유만으로 별도 문제를 포함하지 않는다.
- **수정 방법보다 충분한 결과를 먼저 정한다.** 이미 선택한 구현 목록에 맞춰 완료 조건을 낮추지 않도록 한다. 일부를 먼저 맡기더라도 그 단계의 실제 결과와 필요한 후속 작업이 설명돼야 하며, 후속으로 넘겼다는 사실만으로 현재 결과의 부족이 해소되지는 않는다.
- **실행 중 근거에 따라 접근을 발전시킨다.** 초안이 부족하면 관련 조사와 보완 또는 범위 조정안을 제시해야 한다. ‘범위 밖’이라는 보고만으로 맡은 결과의 부족을 닫지 않는다. 동시에 조사할 필요와 변경 권한, 사용자 제약과 잠정적인 파일 범위를 구별해 무단 확대나 매번의 재승인을 피한다.
- **완료와 보고는 실제 결과에 연결한다.** 테스트 통과와 수정 목록 이행이 목표를 입증하는지 확인하고, 전반적인 검토를 맡았다면 살핀 범위와 발견한 문제의 처리·유지·후속 판단을 남긴다. 아직 살피지 않은 부분을 완료로 바꾸지 않으며, 모든 Ticket마다 전체를 다시 조사하거나 모든 조사 항목을 보고서 목차로 출력하는 절차도 만들지 않는다.
- **기능·결함·코드 개선에 같은 책임을 적용한다.** 기능 완성을 맡았다면 실제 사용에 필요한 연결을 확인하고, API 자체가 납품 결과라면 그 계약과 사용 조건으로 판단한다. 코드 개선 사례에서 출발했다는 이유로 리팩토링 전용 지침이 되거나, 모든 API 작업에 UI까지 요구하게 해서는 안 된다.

### 새 Main의 판단을 검토한 과정

사용자는 현재 대화를 아는 Main의 보완만으로는 부족하다고 지적했다.

> 이 지금 상황을 모르는 main이 해결할정도의 변경이 되어야 할것 같은데

이 요구에 따라 제3 reviewer를 통해 문구를 검토했다. 처음의 “적힌 그대로 완료해도 핵심 문제가 남는가”라는 질문은 새 Main이 ‘핵심 문제’를 작게 정의하면 얕은 수정이 통과하고, 크게 정의하면 사소한 문제를 빠뜨릴 수 있다는 지적을 받았다. 그래서 특정 핵심 문제의 추측에 의존하기보다 맡긴 결과·검토 책임·범위·완료 근거의 관계를 드러냈다.

`AI 지침의 명확성과 적용 범위` 기준으로 목적·적용 조건·행동·제약을 가까이 배치하고, 조사할 내용과 사용자에게 보여 줄 내용을 구별했다. 이미 받은 권한 안의 보완에도 새 승인이 필요하거나, 모든 가상 위험을 해소해야 완료할 수 있는 것으로 읽힐 가능성도 수정했다. `ai-system_instruction-clarity.md: 적용`

이후 사용자는 기능 구현에도 적용되도록 일반화하고 문단을 구분해 달라고 요청했다. 일반화한 문구가 같은 목표에 부합하는지 다시 물었을 때에는, 문장 일부가 남아 있는지만으로 답하지 않고 현재 후보를 새 Main들에게 제공해 다시 확인했다. 이전 후보의 검토를 수정된 후보의 검증 결과로 그대로 승계하지 않았다.

### 공통안에서 확인한 범위

원대화 없이 현재 공통안과 요청·코드를 받은 Main들의 다섯 가상 계획을 독립 리뷰했다.

- 주문 계산 전반 개선: 변수명 변경을 넘어 두 계산 사용처의 관계를 다뤘고, 저장된 금액을 표시하는 영수증은 구별했다.
- CSV 미리보기 전반 개선: 로그·주석 외에 중첩 흐름, 변수 의미, 중복과 집계 상태를 다뤘다.
- 다운로드 기능 완성: 버튼과 로그에서 멈추지 않고 실제 다운로드 연결을 계획했으며, 제공되지 않은 화면 연결은 미확인으로 남겼다.
- 오탈자 수정: 지정된 문자열 수정으로 범위를 지켰다.
- API 납품: 함수 계약과 사용 예제를 완성 범위로 삼고 제외된 UI·다운로드를 추가하지 않았다.

Reviewer는 목표 해석·필요한 작업 발견·범위 준수·완료 근거가 적절하며 추가 문구 수정을 요구할 문제를 발견하지 못했다고 판단했다. 이 결과는 작은 사례의 **계획 수립** 근거다. 실제 구현 품질·검증 수행·완료 행동이나 복잡한 사례의 신뢰성을 보장하지 않는다. 이전 문구와의 비교 실험도 아니므로 성공의 원인을 이 문구만으로 단정하지 않는다.

### 운영 문서를 나눈 이유와 실제 연결

사용자는 공통안을 반영하기 전에 기존 단일 문서도 명확성 기준과 문단 스타일에 맞춰 정리하고 폴더로 구성하자고 제안했다. 기존 문서에 섞여 있던 내용을 읽는 목적과 갱신 책임에 따라 나눴다.

- `README.md`: Spec·Ticket·state의 관계, 실제 Workspace 구성, 상황별 읽기 경로
- `EXECUTION-CRITERIA.md`: 필요한 일의 발견, 범위·품질·분해·실행·완료 판단
- `SPEC.md`: Work 전체의 목표와 공통 기준을 담는 다섯 관점
- `TICKET.md`: 실행 결과·맥락·접근·완료 근거·진행을 같은 본문에 유지하는 기준
- `MAINTENANCE.md`: Main·Maintain의 갱신 책임과 기존 판단에 영향을 주는 새 근거의 반영

이 배치는 공통 운영 문서를 나눈 것이며, 각 Workspace의 Spec 다섯 파일과 Ticket·state 구조를 바꾸지 않았다. 별도 실행자나 승인 단계도 추가하지 않았다. 문서를 나누면서 조건과 예시를 덜어 내거나 공통 기준을 리팩토링 사례로 축소하지 않았다.

새 Main이 분리된 기준을 실제로 찾도록 루트·Work 진입 링크를 연결했다. 자동 Maintain에는 링크만 주는 대신 다섯 운영 문서의 실제 본문을 grounding과 후속 판단마다 제공하고, 수동 역할도 같은 문서들을 적용하도록 연결했다. 기존 `SPEC-AND-TICKETS.md`는 과거 링크를 위한 위치 안내로 남겼으며, 현재 소비 중인 Workspace의 참조·검증 입력도 새 경로로 연결했다. 과거 record와 receipt는 당시 근거로 보존했다.

### 반영 뒤의 확인과 후속 기록

원본과 새 운영 문서의 독립 대조 리뷰에서 필수 보완 사항은 발견되지 않았다. 실행 기준의 `목적과 책임` 이하 본문은 검토한 공통안과 정확히 일치했다.

원대화와 후보 문서를 받지 않은 별도 검토자는 루트에서 새 기준을 찾아 주문 계산 개선의 가상 계획을 작성했다. 필요한 주변 계산 검토, 저장된 영수증 동작 보존, 잠정 파일 범위와 변경 권한의 구별, Main·Maintain의 갱신 책임을 복원했다. 이는 문서 발견과 계획 판단의 확인이며 실제 제품 구현 결과는 아니다.

Maintain의 최초 grounding과 후속 판단 입력에 다섯 정본 본문이 포함되는지 회귀 테스트에서 확인했다. `python3 -B -m unittest discover -s context/work/harness -t . -p 'test_*.py'`는 전체 124개 테스트를 통과한 실행이 있었다. 기존 프로세스 시간 제한 테스트 `test_timeout_covers_descendant_after_group_leader_exits`는 별도 전체 실행들에서 실패했고 단독 재실행에서는 통과해, 시간에 민감한 불안정성이 남아 있다. Spec·Ticket 문서 로딩을 확인하는 Maintain 회귀 검사와는 다른 Verify 테스트다.

`pnpm harness:check`는 실행 환경의 의존성 설치 확인에서 중단되어 같은 script인 `node scripts/check-harness.mjs`를 직접 실행해 통과했다. 당시 기본 Workspace인 001과 명시적으로 연결된 002의 Recover, id 없는 기본 Recover도 성공했다. 새 Verify receipt나 제품 acceptance를 만든 것은 아니다.

반영 후 사용자는 이 배경을 모르면 다음 주체가 문구나 구성을 쉽게 바꿀 수 있다고 우려하며 해당 폴더 안에 히스토리·결정을 남기도록 요청했다. 이에 바깥 결정 문서의 내용을 이 파일로 옮기고 논의 배경을 보강했다. 바깥 문서는 이 기록으로 연결하며, 같은 결정 본문을 두 곳에서 따로 갱신하지 않는다. 이력은 기준을 변경할 때 읽는 자료로 두고 일반 Ticket 실행이나 Maintain의 매 입력에 추가하지 않았다.

### 상세 근거의 위치와 시점

사용자 인용은 이 결정을 논의한 대화에서 선택한 최소 발췌다. 최초 적용의 확인 사실과 중간 문구·검토 결과는 다음 기록에서 다시 볼 수 있다.

- [Ticket 03 최초 적용 재확인](../002-code-readability-refactoring/records/2026-09-12-01-ticket-03-initial-scope-reanalysis.md): 최초 diff, 후속 정정, 관찰과 해석의 범위
- [첫 reviewer 검토와 후보](../002-code-readability-refactoring/records/2026-09-12-02-fresh-main-contract-review.md): ‘핵심 문제’ 질문의 한계와 검토 책임 보완
- [명확성 기준을 적용한 개정](../002-code-readability-refactoring/records/2026-09-12-03-instruction-clarity-contract-revision.md): 조건·권한·완료 근거를 구별한 이유
- [일반화한 후보](../002-code-readability-refactoring/records/2026-09-12-04-generalized-ticket-contract-candidate.md)와 [그 후보의 새 Main 계획 검토](../002-code-readability-refactoring/records/2026-09-12-05-generalized-candidate-fresh-main-review.md): 리팩토링 외 적용과 현재 후보 자체의 확인

중간 기록의 ‘검토안·미채택·미반영’은 각 기록 당시의 상태다. 최종 공통안은 위 검토 후 2026-09-12에 채택·반영했다. 기록에 있는 과거 상태를 현재 운영 기준의 적용 상태로 해석하지 않는다.
