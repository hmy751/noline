# 목표를 실행 결과로 이어가는 기준

이 문서는 Spec에서 Ticket을 나누고 실행·완료를 판단할 때 적용하는 공통 기준이다. Main과 실행자는 맡은 결과를 정하거나 수행·평가할 때 읽는다. 실제 문서 구성은 [진입 문서](README.md), 지속 문서의 갱신과 공통 전제의 재판단은 [갱신 기준](MAINTENANCE.md)을 따른다.

## 목적과 책임

작업을 나누어 실행해도 사용자가 기대한 결과와 품질이 줄어들지 않게 한다. 기능 구현, 결함 수정, 리팩토링 등 작업 성격에 맞게 필요한 일과 완료 근거를 정한다.

전체 Main은 Spec의 목표와 제약을 현재 상태에 대조해 Ticket이 맡을 결과를 정한다. 실행자는 그 결과에 필요한 조사·설계·구현·검증을 수행한다. Main이 Ticket을 직접 실행할 때도 같은 책임을 맡는다.

## 무엇을 맡겼는지에 따라 검토 범위를 정한다

Spec에서 기대 결과, 보존할 계약, 명시적 제약을 확인한다. 뜻이 불분명하거나 서로 충돌하면 해당 사용자 원자료와 현재 상태를 확인해 해석을 바로잡는다.

- **변경 내용이 지정된 요청:** 오탈자 하나처럼 수정 대상과 내용이 정해져 있으면, 그 변경을 정확히 수행하고 영향을 확인하는 데 필요한 범위로 작업한다.
- **결과를 이루도록 맡긴 요청:** 기능 완성, 문제 해결, 한 영역의 전반적인 개선을 맡겼다면, 그 결과에 필요한 일을 찾아낼 책임도 맡은 것으로 다룬다. 분석의 예시나 Ticket 초안의 수정 목록을 검토 대상의 전부로 간주하지 않는다.

현재 구현에서 결과가 만들어지고 사용되는 흐름을 읽고, 목표 달성에 필요한 조건과 관계를 확인한다.

- **기능 구현:** 맡은 결과를 실제로 제공하는 데 필요한 동작과 연결을 살핀다. API 자체가 전달 결과라면 API 계약과 사용 조건을 기준으로 확인한다.
- **결함 수정:** 문제가 발생하는 조건과 같은 원인이 영향을 주는 범위를 확인한다.
- **코드 개선:** 맡은 범위의 주요 처리를 읽으며 표현·흐름·책임에 어떤 이해와 수정 부담이 있는지 판단한다.

먼저 발견한 문제나 한 종류의 수정에만 검토를 한정하지 않는다. 해당 결과에 필요한 다른 작업도 살피되, 함께 다룰 이유는 목표·실제 사용·계약의 관계에서 찾는다. 단지 같은 파일에 있다는 이유로 별도 문제를 포함하지 않는다.

범위가 크면 우선 살펴볼 부분을 고르고 아직 확인하지 않은 부분을 남긴다. 대표 부분을 확인한 사실만으로 전체 범위를 검토했다고 판단하지 않는다.

## 수정 방법보다 맡을 결과를 먼저 정한다

Ticket을 만들 때 다음 관계가 분명해야 한다.

- **맡은 결과:** 이번 실행으로 무엇이 가능해지거나 어떤 문제가 해소되는가.
- **필요한 범위:** 그 결과를 이루려면 무엇을 함께 다뤄야 하며, 제외한 부분을 남겨도 결과가 성립하는가.
- **완료 근거:** 실제로 무엇을 확인하면 결과와 필요한 품질을 갖췄다고 판단할 수 있는가.

그다음 현재 접근과 구현 방법을 정한다. 이미 선택한 수정 목록을 끝낼 수 있도록 결과와 완료 기준을 낮추지 않는다.

작업 크기는 충분한 결과를 만들 수 있는지 확인한 뒤 조절한다. 함께 검토·검증할 수 있는 작은 작업은 묶고, 큰 작업은 각 단계의 결과와 남은 책임이 이어지도록 나눈다.

일부나 기반만 먼저 맡기면 그 단계가 실제로 제공하는 결과, 아직 제공하지 않는 것, 필요한 후속 작업을 설명한다. 후속 작업이 남아 있다는 사실을 숨기거나, 후속으로 넘겼다는 이유만으로 현재 Ticket의 부족을 정당화하지 않는다.

## 실행하며 접근을 발전시킨다

실행자는 맡은 결과를 실제 사용 조건과 Spec의 품질 기준에 맞게 구현한다. 품질을 나타내는 말은 이번 결과에서 무엇이 성립해야 하는지로 구체화한다. 모든 작업에 같은 점검 항목이나 구조를 일괄 적용하지 않는다.

초안의 수정만으로 결과가 충분하지 않다는 근거가 나오면 관련 내용을 더 확인한다. 이미 맡겨진 결과와 권한 안에서는 필요한 보완을 수행하고, 범위 조정이 필요한 경우에는 근거와 보완안을 제시한다. 범위 밖이라는 보고만으로 맡은 결과의 부족을 닫지 않는다.

사용자가 정한 제약과 보존할 계약은 지킨다. Ticket 작성자가 택한 수정 방법이나 잠정적인 파일 범위는 근거에 따라 조정할 수 있다. 사용자 목표·보존하기로 한 공개 동작·명시적 제외 범위를 바꿔야 한다면 차이와 영향을 설명하고, 기존에 받은 권한에 따라 결정하거나 필요한 판단을 요청한다.

조사할 범위와 실제 변경할 권한은 구별한다. 주변을 확인해야 한다는 이유만으로 변경 권한까지 확대하지 않는다.

## 맡은 결과를 기준으로 완료한다

실행자는 기대 결과와 실제 결과를 대조한다. 구현 목록 이행이나 테스트 통과가 맡은 결과를 입증하는지 확인하고, 필요한 품질과 보존 계약도 함께 판단한다.

결과에 필요한 일을 찾아낼 책임까지 맡았다면 초안의 항목을 처리한 것에 더해, 맡은 범위를 관련 기준으로 살폈는지 확인한다. 발견한 작업과 문제에는 수행·유지·후속 판단의 근거가 있어야 한다.

맡은 결과의 달성 여부를 판단할 근거가 없거나 그 결과를 막는 미해결이 남으면 완료로 닫지 않는다. 필요한 보완이나 범위 재판단을 남긴다.

**사용자 보고**에는 무엇이 달라졌고 왜 충분하다고 보는지, 이를 뒷받침하는 근거와 결론을 제한하는 남은 문제를 설명한다. 조사한 모든 항목을 고정 목차로 나열할 필요는 없다. 확인한 사실, 계획, 실행하지 않은 검증을 구별한다.

**전체 Main**은 Ticket 결과를 Spec에 연결해 다음 일을 정한다. 폭넓은 작업에서는 기존 후보·Ticket·state에서 수행한 결과와 미검토·미완료 범위를 찾을 수 있게 한다. 다음 작업을 고를 때와 전체 완료를 판단할 때 이를 확인하며, 매 Ticket마다 전체를 다시 조사하지는 않는다.

## 적용 예시

아래 예시는 맡은 결과에 따라 검토 범위와 완료 근거가 달라진다는 뜻이다. 모든 Ticket에 같은 구현이나 검증 구성을 요구하지 않는다.

- **기능 구현:** 사용자가 검색 결과를 찾아볼 수 있게 하는 작업이라면 입력 화면을 만든 것만으로 끝내지 않는다. 실제 검색과 결과 전달에 필요한 연결을 확인한다. 화면 시안만 요청받았다면 시안의 결과로 판단한다.
- **결함 수정:** 한 입력에서 계산이 틀렸다면 해당 값만 예외 처리하기 전에 원인을 확인한다. 같은 원인이 영향을 주는 관련 입력도 검토하며, 무관한 계산 정책까지 바꾸지는 않는다.
- **코드 개선:** 미리보기 모듈의 전반적인 정리를 맡았다면 로그 삭제 외에 주요 처리 흐름과 상태 갱신도 관련 기준으로 살핀다. 로그 문구 하나만 수정하라는 요청에는 그 변경과 영향만 확인한다.
