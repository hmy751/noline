# expo-updates 논의와 Work를 만든 경위

## 논의가 나온 맥락

1.1.3에는 흐린 버튼과 넘치는 시트의 수정이 담겼다. 둘 다 JS 번들 안의 수정인데도, 사용자에게 보내기까지 다음 과정을 모두 거쳐야 했다.
1. main 병합·push
2. EAS production 빌드(약 20분)
3. `eas submit`
4. App Store Connect에서 업데이트 안내 작성, 빌드 연결, 출시 방식 설정
5. 심사 제출

배포를 진행하던 중 사용자가 "그래 그럼 배포 다 하고 expo-updates 작업에 대해 논의하자"고 했다. 그 사이에 나온 질문도 이 논의의 동기를 보여 준다. 사용자는 "저건 바로 eas로 배포 되나?", "애플 스토어 심사제출 해야하냐고?"라고 물었다. Main은 OTA가 없어 새 빌드와 심사가 필요하다고 답했다.

## 추천과 이유

배포를 마친 뒤 Main이 처음 낸 정리(원문 2710행)와 사용자의 요청에 따른 상세 설명(2855행)의 추천은 같다.

- **fingerprint runtime:** `appVersion`은 단순하지만, 네이티브를 바꾸고 버전 올리기를 잊으면 맞지 않는 JS가 깔린다. 같은 버전 안에서 빌드 번호만 올린 재빌드도 구별하지 못한다. Mapbox·Sentry·SQLite처럼 네이티브 모듈이 많은 이 앱에서는 사람의 기억에 맡기지 않는 쪽을 골랐다.
- **`fallbackToCacheTimeout: 0`:** 앱을 열 때 업데이트를 기다리면 네트워크가 나쁜 곳에서 시작이 늦어진다. 이 앱의 제품 약속과 정면으로 부딪치기 때문에 옵션이 아니라 필수로 두었다. 업데이트가 한 번 늦게 적용된다는 대가는 받아들인다.
- **기기 DB 변경은 스토어 빌드로만:** 마이그레이션이 JS 안(`src/shared/db/migrations`)에 있어 OTA로 나갈 수 있다. 업데이트 롤백이 기기 DB를 되돌리지 못한다는 점이 결정적이다.
- **서버 계약 변경은 서버 배포 뒤에만:** `field_edits` 배포 때 DB → 서버 → 앱 순서를 지켜야 했던 경험에서 나왔다. OTA는 앱이 바뀌는 속도를 높이므로 순서를 어길 위험도 커진다.
- **환경값:** 상세 설명에서 새로 짚은 위험이다. `eas update`는 실행한 컴퓨터에서 번들을 만들기 때문에, 로컬 `.env`의 개발 서버 주소가 운영에 나갈 수 있다. 상세 설명에서는 이것을 "가장 실수하기 쉬운 지점"이라고 했다.
- **iOS 15를 함께 싣기:** 같은 날 온 ITMS-90068 메일을 보고 Main이 제안했다. 어차피 새 스토어 빌드가 필요하고 expo-updates 첫 빌드도 심사를 받아야 하니, 한 빌드로 심사를 한 번만 받는다. 사용자는 안내 상자의 문구가 영어라고 지적했을 뿐 이 제안을 따로 거절하지 않았고, 이어진 "그래 좋아"로 전체 방향에 동의했다.

넣지 않은 것도 있다. 앱 안의 "새 버전 적용" 안내는 급한 수정에 유용하지만, 처음 도입에 필요하지는 않아 나중 후보로 두었다.

## Work를 만든 이유와 범위

사용자는 구현 전에 Work로 남기라고 했다. 이어서 두 가지를 범위에 넣으라고 했다.
- 작업 뒤 Project context 반영
- hook 등으로 위험한 발행을 막는 장치

이 목표는 기존 Work와 겹치지 않는다. 008은 예외 안내 규칙이고 1.1.3 릴리스는 그 Work의 수정 결과를 내보낸 것이다. 007은 동기화 실패 복구다. 그래서 새 번호 011로 만들었다. 010은 같은 날 다른 세션이 만든 README Work다.

hook 요청은 형태가 정해지지 않았다. Main은 판단에 필요한 후보와 각 후보의 한계를 Spec 05에 정리했다. 특히 AI 도구 hook만으로는 사람이 직접 실행하는 발행을 막지 못한다는 점을 적었다. 결정은 Ticket 02로 남겼다.

Project 반영은 위치부터 열려 있다. Project에 배포를 소유하는 본문이 없기 때문이다. 확정되지 않은 "규칙 후보"를 미리 Project에 쓰지 않고, 01·02에서 확정한 것만 옮기도록 Ticket 03에 조건을 두었다.

## 이어받지 않은 것

- 1.1.3의 수정 내용과 검증: Work 008이 소유한다.
- START_GUIDE 검증: 커밋 `45363594`와 START_GUIDE의 마지막 확인 절이 소유한다.
- 릴리스 절차의 상세: 007·008 records를 접근점으로만 두었다.

## 인수 확인

Main이 새 README와 재개 안내에서 출발해 직접 대조했다. 목표, 위험 규칙, 완료 기준, 현재 결과(없음), 미확인, 첫 행동을 따라가 보았다. 대화 이력을 받지 않은 별도 읽기 주체의 인수 시험은 하지 않았다. 기본 Workspace와 `index.json`의 active id는 바꾸지 않았다.
