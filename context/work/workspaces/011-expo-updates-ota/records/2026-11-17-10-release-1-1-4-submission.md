# 1.1.4(빌드 18): main 병합, 빌드, 심사 제출

2026-11-17 오후 5시 5분경부터 5시 40분경(KST)까지의 기록이다. `feat/011-expo-updates`를 main에 병합하고 버전을 1.1.4(빌드 18)로 올려 production 빌드를 만들었다. 이어서 App Store Connect에 올려 심사에 제출했다. 지금 상태는 "1.1.4 심사 대기 중"이다. 이 과정에서 fingerprint runtime이 앱 버전과 빌드 번호까지 포함한다는 것을 새로 알았다.

원문은 [source 색인](../source/index.md)의 두 번째 세션 원문이다. 괄호 안 숫자는 그 파일의 행 번호이며, 이 기록의 범위는 5522–6148행이다. App Store Connect 화면은 Main이 브라우저에서 읽고 조작했다. 인증서·팀 식별자 같은 계정 세부는 적지 않는다.

## 시작과 병합 결정

> "1.1.4 진행하자" (5522)

Main은 먼저 이전 릴리스 절차를 확인했다(5579). 기준은 Work 007의 빌드 16과 Work 008의 1.1.3이다. 순서는 main에서 버전만 올리는 커밋을 따로 만들어 push하고, main으로 빌드하고, 제출한 뒤 App Store Connect 정보를 채우는 것이다.

그런데 expo-updates 작업은 아직 브랜치에만 있었다. 그래서 Main은 main에 병합한 뒤 빌드할지, 브랜치에서 빌드할지 물었다(5607, 한국어 설명은 5615).
- **병합 뒤 빌드(추천):** 이전 절차와 같다. 스토어 앱과 main의 코드가 같아진다. OTA 방지 장치가 빌드 커밋을 기준으로 변경을 검사하므로, 그 커밋이 main에 있어야 헷갈리지 않는다. Ticket 03은 문서 작업이라 병합 뒤에도 이어 할 수 있다. 대신 "011이 다 끝나면 병합"하기로 한 원래 계획은 바뀐다.
- **브랜치에서 빌드:** 원래 계획은 지키지만, 병합 전까지 스토어 앱과 main의 코드가 다르다.

> "로그인했어 main 병합하고 빌드 진행해" (5627)

사용자가 병합을 골랐다. 앞서 정한 "일단 011 부터 하고 다되면 병합하자"(841)가 이것으로 바뀌었다. Ticket 03은 병합 뒤에 이어 한다. 이 대화에서 사용자는 "앞으로 한글로 대답해"(5765)라고도 했다.

### 병합 전 확인(5652–5675)

- 병합은 fast-forward였다.
- main과 브랜치 사이에 `apps/server`·`packages` 변경이 없다.
- `render.yaml`은 main에서 `autoDeploy: true`이고, 빌드 명령이 `pnpm install && …`로 workspace 전체를 설치한다. pnpm patch도 그때 적용되므로 Render가 다시 배포해도 같은 서버 코드가 돈다.

main을 `92ca714d`로 fast-forward했다. 버전 커밋은 `d160c7b5` "chore(client): 1.1.4 빌드 18 배포 준비"다(`app.config.js`의 version 1.1.4, buildNumber 18). main을 origin에 push했다(`99235878..d160c7b5`). Render 자동 배포가 실제로 돌았는지는 확인하지 않았다.

## 깨끗한 재설치와 runtime

`node_modules`를 지우고 `pnpm install --frozen-lockfile`로 다시 설치했다(5696–5711). production runtime은 `0367b72f…`, preview runtime은 `92c898f2…`가 나왔다.

### 새 발견: runtime에 앱 버전과 빌드 번호가 들어간다

preview runtime이 `54a96787…`에서 바뀐 이유를 확인했다(5714–5719). 이 구성(SDK 51, expo-updates 0.25)의 fingerprint는 앱 버전과 iOS buildNumber를 포함한다.

| version / buildNumber | preview runtime |
| --- | --- |
| 1.1.3 / 17 | `54a96787…` |
| 1.1.3 / 18 (buildNumber만 바꿈) | `52e0c41b…` |
| 1.1.4 / 18 | `92c898f2…` |

이 결과에서 나오는 것은 다음과 같다.
- 스토어 빌드마다 runtime이 다르다. OTA는 버전과 빌드 번호가 정확히 같은 빌드에만 간다.
- 1.1.5가 나온 뒤 1.1.4 사용자에게 OTA를 보내려면 아직 1.1.4(18)인 코드 트리에서 발행해야 한다. 발행 스크립트의 runtime 대조가 이 실수를 잡는다.
- 기존 preview 빌드 `f610d9b5…`(1.1.3/17)는 이제 main과 runtime이 다르다. preview로 OTA를 다시 시험하려면 preview 빌드를 새로 만들어야 한다.

이 내용은 [Ticket 03](../current/memory/tickets/03-project-context-reflection.md)의 반영 후보로 연결했다.

## 1.1.3 상태 확인

Claude in Chrome 탭은 App Store Connect 로그인 화면에 머물렀다(5603–5796). Main은 비밀번호를 넣지 않고 사용자에게 로그인을 부탁했다. 사용자는 앱 안의 브라우저 패널에서 로그인했다.

> "옆 브라우저봐" (5801)

그 화면에서 1.1.3은 "배포 준비됨"이었다(5836). 심사를 통과했고, 자동 출시 설정이라 공개된 상태다. 그래서 1.1.4 제출을 막는 것은 없었다.

## 빌드와 업로드

- EAS production 빌드 `7033c2ba-0dc7-46e6-96cf-bfcc7044b881`이 FINISHED가 됐다(5738–5864). runtime은 계산값과 같은 `0367b72f…`, 커밋은 `d160c7b5`, 버전은 1.1.4(18)다. EAS는 배포 인증서와 프로필이 2026-12-30까지 유효하다고 보고했다.
- `eas submit` 제출 `012b0d56-7c0a-4f8b-a971-3e5c898b64f0`으로 App Store Connect에 올렸다(5874). TestFlight에서 빌드 18이 "제출 준비 완료"로 처리됐다(6021).
- ITMS-90068은 확인하지 못했다. Gmail 커넥터 연결이 끊겨 Main이 메일을 볼 수 없었다(6023). 사용자는 작업 중에 "매일에 ready to test 라네"(6070)라고 알렸다. 이 메일은 빌드 처리가 끝났다는 알림이다. ITMS-90068 경고 메일이 따로 왔는지는 아직 모른다.

## 업데이트 안내 문구

Main이 초안을 냈다(5836). 두 번째 줄은 "iOS 15.0 이상에서 사용할 수 있어요"였다.

> "문구 괜찮아 빌드 끝나면 제출까지 해 근데 ios 이말 좀 짜치지 않나? 꼭 넣어야 돼?" (5841)

Main은 그 줄을 빼자고 답했다(5845). App Store의 호환성 항목에 최소 iOS 버전이 자동으로 표시된다. 그리고 iOS 13–14 기기에는 1.1.4가 업데이트로 보이지 않으니 안내를 읽는 사람에게는 의미가 없다는 이유였다. 최종 문구는 이렇다.

> 앱을 더 안정적으로 쓸 수 있도록 개선했어요.
>
> • 앞으로 생기는 문제를 더 빠르게 고칠 수 있도록 업데이트 방식을 개선했어요.

사용자의 "빌드 끝나면 제출까지 해"가 심사 제출의 허락이 됐다.

## App Store Connect 입력과 제출(5893–6129)

- 1.1.4 버전을 만들었다.
- 업데이트 안내를 넣었다. 칸에 1.1.3 안내가 미리 채워져 있어 처음 입력은 그 안에 섞였다. 그래서 칸의 값을 통째로 바꾸고, 새로고침 뒤에도 남아 있는지 확인했다.
- 설명·키워드·지원 URL은 이전 값이 그대로 이어졌다.
- 빌드 18을 연결하고 저장했다.
- 출시 설정은 이전과 같다. 자동으로 버전 출시, 모든 사용자에게 즉시 출시, 기존 평가 유지다.
- "심사에 추가" → "심사를 위해 제출"을 눌러 "1개의 항목 제출됨"을 확인했다. 사이드바에 "1.1.4 심사 대기 중"이 보였다(2026-11-17 오후 5시 36분경).
