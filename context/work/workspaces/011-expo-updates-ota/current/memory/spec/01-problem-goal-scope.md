# 문제·목표·범위

## 왜 시작했나

2026-11-16, 1.1.3(빌드 17)을 Apple 심사에 냈다. 이 릴리스에는 두 가지 수정이 담겼다.
- 로그인 화면의 흐린 버튼: Pressable에서 `transition-colors`를 빼서 고쳤다.
- 긴 수정 시트가 넘치는 문제: Drawer의 구조를 바꿔 고쳤다.

둘 다 JS 번들 안의 변경인데도, 사용자에게 보내려면 EAS 빌드 → 업로드 → App Store 정보 입력 → 심사 대기를 거쳐야 했다. 이 앱에는 `expo-updates`가 없고 `app.config.js`에 `runtimeVersion`·`updates` 설정도 없어서 OTA 경로가 없다. 배포가 끝나자 사용자가 다음 주제를 꺼냈다.

> "그래 그럼 배포 다 하고 expo-updates 작업에 대해 논의하자"

같은 날 Apple에서 빌드 17에 대한 경고 메일이 왔다(ITMS-90068).
- 앱이 iOS 13.4를 대상으로 빌드돼 있다.
- 2027년 4월부터는 iOS 15.0 이상이어야 업로드·제출할 수 있다.
- 원인은 최소 iOS 버전 설정이 없어 `ios/Podfile`의 기본값 `'13.4'`가 쓰인다는 것이다.
- 고치려면 네이티브 설정이 바뀌므로 새 스토어 빌드가 필요하다.

## 목표

1. JS·화면만 바뀐 버그 수정을 `eas update`로 심사 없이 내보낼 수 있다.
2. OTA를 넣어도 Noline의 핵심 약속, 즉 네트워크가 없어도 앱이 바로 열린다는 점이 깨지지 않는다.
3. 네이티브와 맞지 않는 JS, 기기 DB 구조 변경, 서버보다 먼저 나간 계약 변경, 개발용 환경값이 OTA로 운영 사용자에게 가지 않는다. 사람의 주의에만 맡기지 않고 발행 전에 막는 장치(hook 등)를 둔다.
4. 위 기준이 이 Work가 끝난 뒤에도 남도록 Project context에 반영한다.
5. iOS 최소 버전 15.0 설정을 같은 1.1.4 빌드에 싣는다.

사용자는 구현에 앞서 이 Work를 만들며 3과 4를 직접 요청했다.

> "나중에 잊지않게 context도 작업하고나서 알맞게 반영해야할거고 참고로 hook같은걸로 뭔가 방지하게 하는 그런것도 할거라고 잘 기록해놔줘"

## 범위

포함한다.
- `expo-updates` 설치(SDK 51에 맞는 버전)
- `app.config.js`의 runtime version·updates 설정
- `eas.json` 채널
- 발행 절차: 환경값과 Sentry 소스맵 포함
- preview 빌드에서의 확인
- 1.1.4 스토어 빌드와 심사 제출
- OTA 방지 장치
- Project 반영
- `expo-build-properties`로 iOS 15.0 설정

포함하지 않는다.
- 앱 안의 "새 버전 적용" 안내 UI: 나중에 붙일 수 있는 후보로만 둔다.
- Android 배포
- 서버 배포 방식(Render 자동 배포) 변경
- 1.1.3 심사 결과 대응: 1.1.3은 Work 008의 릴리스다.
