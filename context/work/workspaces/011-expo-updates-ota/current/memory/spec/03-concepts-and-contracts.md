# 개념과 지킬 계약

## 앱의 두 층

| 층 | 내용 | 바꾸는 방법 |
| --- | --- | --- |
| 네이티브 층 | RN 엔진, Mapbox·Sentry·SQLite 같은 네이티브 모듈, 권한, 아이콘, 최소 iOS 버전 | 스토어 빌드와 Apple 심사 |
| JS 번들 | `apps/client`와 `packages/ui`의 TS 코드, SQLite 마이그레이션 코드, 빌드 때 박힌 `EXPO_PUBLIC_*` 값 | 스토어 빌드, 도입 뒤에는 OTA로도 |

## runtime version

OTA 번들은 특정 네이티브 층을 전제로 만들어진다. 빌드와 업데이트에 같은 runtime version 값을 붙이고, 값이 일치할 때만 업데이트를 받게 해서 맞지 않는 JS가 깔리는 것을 막는다.

| 방식 | 특징 |
| --- | --- |
| `appVersion` | 앱 버전을 그대로 쓴다. 네이티브를 바꾸고 버전을 올리지 않으면 막지 못한다. |
| `fingerprint` | 네이티브 의존성·설정을 해시로 계산한다. 네이티브가 바뀌면 자동으로 다른 값이 된다. |

**추천은 `fingerprint`다.** 네이티브 모듈(Mapbox·Sentry·SQLite)이 많은 앱이라 사람이 버전 올리기를 잊는 위험을 없애는 편이 낫다. 사용자가 이 방향에 동의("그래 좋아")했지만 실제 설치·빌드에서 SDK 51과의 호환은 확인하지 않았다.

## 채널

`eas.json`에는 development, preview, production 프로필이 있다. preview와 production 프로필에 같은 이름의 `channel`을 붙인다.

발행 순서는 이렇게 한다.
1. preview 채널로 먼저 발행해 내부 기기에서 확인한다.
2. 확인되면 production 채널로 낸다.
3. 문제가 생기면 `eas update:rollback`으로 되돌린다.

## 외부 조건

- **Apple 정책:** Apple은 앱의 주요 목적을 바꾸지 않는 해석형 코드(JS) 수정을 이런 방식으로 내보내는 것을 허용한다. 버그 수정과 UI 다듬기가 대상이며, 심사를 피해 큰 기능을 넣는 용도로 쓰지 않는다.
- **첫 빌드 심사:** `expo-updates` 자체가 네이티브 모듈이라 이를 넣은 첫 빌드(1.1.4)는 심사를 받아야 한다. 그 빌드를 설치한 사용자부터 OTA를 받는다.
- **Expo 요금:** Expo 무료 플랜에 월간 업데이트 사용자 한도가 있다. 현재 규모라면 무료 범위일 가능성이 높지만 확인하지 않았다.
- **Sentry:** OTA 번들마다 소스맵을 올려야, 오류가 어느 업데이트의 어느 코드에서 났는지 맞게 보인다.
