# 01. 앱 준비 실패와 조회·저장 오류 복구

## 맡은 결과와 범위

필수 초기화 실패를 정상 준비 완료로 처리하지 않고, 데이터 조회/저장 실패를 빈 목록·0 합계·성공처럼 보이지 않게 한다. 사용자는 실패 이유를 이해하고 가능한 경우 입력을 유지한 채 재시도할 수 있어야 한다.

DB/auth 준비 순서, 준비 신호와 지연 cleanup, 일정·경비 목록/상세와 생성 실패의 오류 소비를 맡는다. 인증 원인 분류는 02, 활성화 부분 실패 UI는 05, 검색 오류는 09, 수동 sync 결과는 11가 맡는다.

## 실행 맥락과 접근

[카테고리 조사](../../../records/2026-09-13-02-major-feature-category-investigation.md)에서 DB 초기화 실패 후 initAuth 0회·ready=true를 실행했다. [첫 사용 조사](../../../records/2026-09-13-01-first-use-scenario-investigation.md)의 첫 query 실패와 console 중심 생성 실패는 소스 근거이며, 입력 유실까지 확정한 것은 아니다.

[root](../../../../../../../apps/client/app/_layout.tsx), [일정 화면](../../../../../../../apps/client/src/screens/ScheduleScreen.tsx), [경비 화면](../../../../../../../apps/client/src/screens/ExpensesScreen.tsx), [상세](../../../../../../../apps/client/src/screens/ScheduleDetailScreen.tsx)에서 시작한다. 독립적으로 실패 주입·UI 설계가 가능하다. 02·13의 오류 종류, 07의 실제 query, 04의 cleanup 허용 계약을 소비한다.

공통 기준은 [기대 동작](../spec/02-behavior-and-cases.md)과 [품질·완료 판단](../spec/04-quality-and-completion.md)을 따른다.

## 완료 조건과 확인 방법

- DB·SecureStore/auth 준비 실패와 지연을 주입해 필수 준비 이전에 일반 화면·sync·cleanup이 안전하지 않게 실행되지 않음을 확인한다. 치명적 실패와 계속 가능한 실패의 구분을 명시한다.
- 고정 2초 경과를 준비 완료 대신 쓰는 정리 경로를 실제 readiness/보존 조건과 연결한다. 느린 시작·재시도·백그라운드 복귀도 확인한다.
- cache 없음의 조회 실패, cache가 남은 재조회 실패, 정상 빈 목록과 경비 합계 0을 구별해 표시한다. 재시도 뒤 실제 데이터가 복구되는지 native 화면에서 확인한다.
- 여행·일정·경비 저장 실패가 console에만 남지 않고 입력을 유지한 채 재시도할 수 있다. 중복 클릭·늦은 응답·화면 이탈 뒤 결과도 확인하며 새로운 입력 유실 주장을 증거 없이 만들지 않는다.
- 기존 PolicyErrorDisplay·네트워크 표시 패턴을 우선 사용한다. 표시 개선으로 하위 실패를 숨기거나 04/07/11의 domain 오류 처리까지 완료한 것으로 보고하지 않는다.

## 현재 상태와 실제 결과

구성됨, 실행 전. 위 확인 계획을 수행하거나 제품 코드를 수정한 상태가 아니다. 기존 조사 근거는 위에 연결했으며, 실행할 때 현재 코드·환경과 수정 전 조건을 다시 대조한다.
