# 12. Pull 누락과 미전송 수정 덮어쓰기 방지

## 맡은 결과와 범위

서버 변경을 받는 동기화에서 시간 경계 때문에 변경을 놓치거나, 아직 전송하지 않은 로컬 수정을 설명 없이 이전 값으로 덮어쓰지 않게 한다. 서버 조회 기준 시각, cursor 입력, local upsert·삭제와 pending 충돌을 함께 맡는다.

이 Ticket은 **서버 변경을 수신할 때 폰의 미전송 수정을 보호**한다. 예를 들어 서버 금액 25 USD를 받아와도 아직 보내지 않은 30 USD 입력과 화면 표시를 보존한다. 이후 요청을 보낼 때는 [007 Ticket 07](../../../../007-sync-failure-recovery/current/memory/tickets/07-conflict-rule-and-cleanup.md)이 항목별 편집 표식으로 최종 값을 결정하고, 폰에 결과를 반영한 뒤 해당 큐 작업을 끝낸다. 두 티켓은 같은 충돌 규칙을 사용한다.

## 실행 맥락과 접근

[카테고리 조사](../../../records/2026-09-13-02-major-feature-category-investigation.md)는 실패한 수정의 local 표시값이 이전 서버 값으로 바뀌고 queue payload는 남는 조건을 실행했다. 당시 미확인이었던 실제 cursor와 조회 중 쓰기는 아래 PostgreSQL 통합 검사로 보완했다.

[client engine](../../../../../../../apps/client/src/shared/services/sync/engine.ts), [DB upsert](../../../../../../../apps/client/src/shared/db/utils.ts), [server sync](../../../../../../../apps/server/src/routes/sync.ts)가 연결된다. 10의 정확한 미전송 귀속 결과가 충돌 판정의 선행 결과다. 11의 실패/재시도 계약을 소비하지만 이 티켓이 전송 엔진을 다시 소유하지 않는다.

공통 기준은 [기대 동작](../spec/02-behavior-and-cases.md)과 [품질·완료 판단](../spec/04-quality-and-completion.md)을 따른다.

## 완료 조건과 확인 방법

- 격리 PostgreSQL에서 pull 조회 도중 생성·수정·삭제를 주입하고 다음 cursor 요청까지 대조하여 빠진 변경이 없음을 확인한다.
- 같은 entity의 미전송 CREATE/UPDATE/DELETE와 서버 수정·삭제의 조합을 재현한다. 자동 처리 가능한 기존 정책과 사람 선택이 필요한 정책을 명시하고, 미확정 정책이 결과를 막으면 구현 완료로 닫지 않는다.
- 채택한 정책에서 사용자 입력 또는 복구 가능한 변경 근거가 남고, 성공적인 재전송·후속 pull 뒤 화면·SQLite·서버가 합의된 값에 도달한다.
- 정상적인 서버 변경 수신과 삭제 전파는 보존한다. mock 응답 덮어쓰기 시험만으로 server cursor 무누락을 입증하지 않는다.

### 2〜7단계의 후속 순차 검토 완료

### 2026-11-12 저장 1단계의 후속 수정·검증

사용자가 단계별 검토를 요청한 뒤 저장 경로의 동작, 기술스택 활용, 기존 유틸 재사용을 순서대로 검토하고 승인 후 수정했다. 폼 비교 기준·순수 변경 계산의 책임과 타입을 정리하고, 일정·경비의 중복 제출·외부 전환 뒤 늦은 완료를 보호했다. 저장 후 조회는 기존 취소·갱신 유틸을 쓰며 Local UPDATE는 반환 행을 같은 트랜잭션에서 검증한다. 직접 PUT의 서버 처리 후 표식 보관 실패는 일반 저장 실패와 구별하고, 관찰한 표식은 현 프로세스에서 보존해 다음 발급이 영속화되기 전 반환되지 않게 한다. 구버전 복구 입력도 이 실패 때문에 정리하지 않는다.

Main은 **저장 1단계 수정과 해당 범위 검증 완료**를 판정했다. 최종 client 74묶음 828/828, 독립 검사 92개(지속 88·시계 1·경비 회차 3)가 통과했다. 변경 26파일 lint 오류는 0개이며 기본 타입 검사의 기존 오류 7개는 남는다. 기존 FIFO·표식 순서·그룹·호환·삭제·소유권 규칙을 유지했고 서버·SQL·공유 schema 계약은 바꾸지 않았다. 전체 서버 병합·pull·네이티브/두 기기 검증을 이번에 재실행한 것으로 넓히지 않으며 배포도 미실행이다. ### 선행 구현과 전체 Ticket 검증 이력

선행판과 후속 보완의 완료 판단 뒤, 최종 high 검토에서 비활성화·정리 후 늦은 pull의 본문 재저장을 재현했다. 이 반례까지 보완해 최신 판단은 개발·검증 완료, 배포 별도다. 서버 pull은 같은 repeatable-read snapshot에서 조회하고 PostgreSQL 트랜잭션 ID 하한을 다음 cursor로 반환한다. 조회 도중 열려 있던 쓰기가 나중에 commit해도 다음 조회 범위에 포함되며, 옛 `lastSyncedAt` 요청은 호환 경로로 남긴다. 앱 cursor는 계정·활성 여행 집합별로 관리한다.

기기에서는 pull과 push 응답을 같은 `reconcileRecordInTransaction`으로 반영한다. 완료한 요청만 제외하고 같은 기록의 나머지 PENDING·FAILED·IN_PROGRESS 입력을 순서대로 다시 겹친다. 자기 소유 삭제 증거가 확인된 경우의 정리는 007-07 규칙을 사용하며, 근거 없는 404나 손상된 요청을 임의 종결하지 않는다.

Main은 격리 PostgreSQL에서 경비 테이블을 잠가 실제 pull이 조회 중 대기하는 것을 확인한 뒤 생성·수정·삭제를 주입했고, 진행 중 응답은 0건·다음 cursor 응답은 3건으로 모두 수신했다고 보고했다. 기록 담당자는 [시험 코드](../../../../../../../apps/server/tests/integration/pull-cursor.test.ts)를 직접 대조했다. 두 iOS 시뮬레이터의 실제 저장·REST·SQLite 경로에서는 미전송 금액 30과 다른 기기의 분류가 함께 남고, 앞선 응답 후 저장한 35도 큐에 보존되며 재전송 뒤 서버와 SQLite가 35.00·교통으로 일치한 실행 로그를 확인했다.

검사 근거와 한계는 [007과 공동 구현·검증 기록](../../../../007-sync-failure-recovery/records/2026-11-10-04-conflict-pull-implementation.md)에 연결한다. Main은 이어 일반 앱의 보류 입력 복구 UI에서 닫기·분류만 선택 저장·현재 값 유지를 확인했고 재시작 후 35 USD·쇼핑, 큐와 기기·서버 보류 0건의 수렴을 보고했다. 최종 독립 검사에서 PostgreSQL 4파일 44/44, 서버 단위 73/73, client 67묶음 741/741과 server 타입 검사·빌드·schema 빌드가 통과했다. checkpoint 중간 실패 때 시간·cursor 동시 rollback과 계정 전환 거절, 추가 DELETE 귀속 회귀도 확인해 Main이 두 Ticket의 개발·검증 완료를 판정했다. 전체 앱 타입 검사 등의 기존 실패는 공동 기록에서 구별한다. SQL·서버·앱 배포는 하지 않았다.

현재 후속 범위는 [추가 독립 검토와 수정 기록](../../../../007-sync-failure-recovery/records/2026-11-10-05-conflict-pull-review-fixes.md)을 따른다. 늦은 활성화 응답, 손상 입력의 삭제 수신 보존, 정상 후속 PENDING의 pull 진행을 수정했고 실제 네이티브 SQLite 실행으로 확인했다. 옛 목록 version fallback·직접 수정과 활성화의 양 순서도 확인했다. 최종 저장소 검사는 client 70묶음 778/778·서버 12묶음 73/73·PostgreSQL 5파일 49/49이며, 별도 독립 재현 8개와 최종 제품 코드의 후속 시뮬레이터 3조건도 통과했다. 위 선행 수치는 당시 근거로 유지한다. 후속 검증은 시뮬레이터 1개이고 선행 두 기기·일반 앱 UI 확인과 구별한다. client 타입 오류 7개·전체 lint 31개는 별도 기존 이슈이며 SQL → 서버 → 앱 배포는 미실행이다. 여행 재활성 뒤 옛 정리 예약 실행 순서는 003-04가 맡는다.

최신 high 검토에서는 활성 A의 pull을 지연한 동안 비활성화·사본 정리를 완료해 자식 숨김과 `serverRecords.record=null`을 확인한 뒤, 같은 판본의 옛 pull 응답이 자식 `deletedAt=null`과 본문을 다시 쓰는 조건을 재현했다. 정상 재활성 없이 발생하며 현재 활성·사본 상태를 확인하고 쓰는 이 Ticket의 책임으로 수정·재검증했다. 003-04의 재활성 뒤 옛 정리 예약 실행과 구별한다. [최신 공동 검토 기록](../../../../007-sync-failure-recovery/records/2026-11-10-05-conflict-pull-review-fixes.md#비활성화사본-정리-뒤-늦은-pull의-본문-재저장)을 따르고 위 완료·수치는 선행 이력으로 읽는다. 이번 review-only 요청에서는 제품·Project를 수정하지 않았다.

최종 보완은 사본 수명 ID 대조와 본문·cursor의 동일 SQLite 트랜잭션, 기한 지난 응답의 확정 삭제 증거 보존, 세 정리 경로 통합이다. 원재현 포함 독립 12/12, high 개선 검토 53/53, 최신 client 71묶음 797/797·서버 73/73·PostgreSQL 49/49가 통과했다. 시뮬레이터 1대의 실제 hook·네이티브 SQLite·서버 실행에서 정리 후 늦은 수신에도 hidden=true·본문 null·cursor 유지와 정상 재활성 35.00을 확인했다. [공동 기록의 최신 절](../../../../007-sync-failure-recovery/records/2026-11-10-05-conflict-pull-review-fixes.md#세-반례-수정과-최종-재검증)이 현재 완료 범위다. 선행 미수정 판단은 당시 이력으로 읽는다.
