# 11. 동기화 실패·재시도·중단 복구

## 맡은 결과와 범위

전송 실패나 앱 중단 뒤에도 미전송 작업을 다시 처리할 수 있고, 자동·수동 동기화 결과와 마지막 성공 표시가 실제 서버 반영 상태를 나타내게 한다.

FAILED/IN_PROGRESS 회수, 재시도 횟수와 종료 조건, 중복 trigger·재연결·중단 복구, 개발자 수동 동기화 표시를 포함한다. 토큰 갱신은 02, pull 충돌 정책은 12이 맡는다.

## 실행 맥락과 접근

[두 조사](../../../records/2026-09-13-01-first-use-scenario-investigation.md)와 [추가 실행](../../../records/2026-09-13-02-major-feature-category-investigation.md)에서 일반 push 실패의 정상 반환, 다음 push에서 FAILED 제외, 재시작 입력의 IN_PROGRESS 제외를 확인했다. _retry와 _retryCount의 충돌 및 실제 동시 trigger·강제 종료는 실행 범위를 구체화해야 한다.

[engine](../../../../../../../apps/client/src/shared/services/sync/engine.ts), [queue](../../../../../../../apps/client/src/shared/services/sync/queue.ts), [provider](../../../../../../../apps/client/src/shared/services/sync/provider.tsx)가 중심이다. 격리 재현은 먼저 가능하나 실제 로컬 입력 보존을 포함한 완료에는 10의 원자성·미전송 계약이 필요하다. 인증 오류 분류는 02와 계약을 맞추되 일반 전송 실패 복구를 기다리게 하지 않는다.

공통 기준은 [기대 동작](../spec/02-behavior-and-cases.md)과 [품질·완료 판단](../spec/04-quality-and-completion.md)을 따른다.

## 완료 조건과 확인 방법

- 일반 실패 후 재연결·수동 재시도로 서버 반영에 도달하며, 재시도 불가 오류는 무한 반복 대신 식별 가능한 실패와 보존된 입력으로 남는다.
- 요청 전·전송 중·서버 반영 뒤 응답 수신 전 중단을 구분해 재시작 후 누락/중복을 확인한다. 중복 생성 방지는 기존 client ID·서버 수용 계약으로 검증한다.
- 동시에 발생한 수동/자동/재연결 요청이 같은 작업을 서로 훼손하지 않는다. 실제 앱 강제 종료와 복귀는 격리 계정·DB에서 실행한다.
- 일부 실패와 전체 반영을 구별하고 활성 여행이 없어 pull을 건너뛰어도 실패를 성공으로 알리지 않는다. 마지막 동기화 시각과 debug 알림도 확인한다.
- 미전송 입력이 남은 상태에서 cleanup을 허용하지 않도록 04에 실제 결과 계약을 전달한다.

## 현재 상태와 실제 결과

구성됨, 실행 전. 위 확인 계획을 수행하거나 제품 코드를 수정한 상태가 아니다. 기존 조사 근거는 위에 연결했으며, 실행할 때 현재 코드·환경과 수정 전 조건을 다시 대조한다.
