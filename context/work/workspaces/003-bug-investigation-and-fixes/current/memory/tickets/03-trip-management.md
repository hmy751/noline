# 03. 여행 생성·선택·수정·삭제의 연결

## 맡은 결과와 범위

여행을 만든 뒤 바로 주요 작업을 이어갈 수 있고, 직접 고른 여행과 수정하지 않은 필드가 유지되며, 여행 삭제 후 목록·활성 판단·후속 조회가 일관되게 한다.

기간만 수정할 때 좌표를 null로 만드는 local 업데이트, 서버가 허용한 latitude/longitude/cityId를 무시하는 처리, 목록 변경 뒤 선택 덮어쓰기, 활성 여행 삭제 후 activation 잔존을 포함한다. A 활성 중 B 생성 직후 B 일정 추가·활성화의 부모 미전송 조건도 이 티켓에서 판별한다.

[첫 사용 조사](../../../records/2026-09-13-01-first-use-scenario-investigation.md)와 [카테고리 조사](../../../records/2026-09-13-02-major-feature-category-investigation.md)의 여행 조건을 사용한다. 좌표 null·선택 덮어쓰기·activation 잔존은 분리 실행했고, 새 부모와 원격 자식의 전송 타이밍은 소스 근거다.

[trip local](../../../../../../../apps/client/src/entities/trip/lib/trip-local.ts), [repository](../../../../../../../apps/client/src/entities/trip/repository/trip-repository.ts), [root 선택](../../../../../../../apps/client/app/_layout.tsx), [server trips](../../../../../../../apps/server/src/routes/trips.ts)가 중심이다. 저장·삭제 검증은 10, 서버 도착 연결은 11의 계약을 사용한다. 비활성 자식 자체의 local 의존은 07, 기간 밖 항목 접근은 08, 활성화 전환 자체는 04이 맡는다.

공통 기준은 [기대 동작](../spec/02-behavior-and-cases.md)과 [품질·완료 판단](../spec/04-quality-and-completion.md)을 따른다.

## 완료 조건과 확인 방법

- 여행 B를 선택한 뒤 목록 내용 수정·재조회·sync가 있어도 유효한 B 선택을 유지하고, B 삭제 시에는 유효한 대체 선택 또는 빈 상태가 된다.
- 날짜만 수정해 좌표·도시를 보존하며, 허용 필드의 생략/null/0/일반 값을 local·server 양쪽에서 구별해 저장·재조회한다.
- 마지막 활성 여행 삭제 뒤 활성 판단·목록·Router가 일치한다. soft delete와 자식·지도·queue 정리는 미전송 보존 조건을 지키고 재시작 뒤 삭제 상태도 일치한다.
- 도시 선택→여행 생성→즉시 일정/경비 추가를 활성 여행 유무에 따라 실행한다. 새 부모의 서버 도착 전 후속 작업은 정상 연결되거나 이유·재시도 경로가 명확해야 하며, 광범위한 routing 재설계가 필요하면 먼저 판단을 남긴다.
- 느린 생성 중 반복 저장·실패 후 재시도에서 중복과 잘못된 여행 귀속을 검사한다.

## 현재 상태와 실제 결과

구성됨, 실행 전. 위 확인 계획을 수행하거나 제품 코드를 수정한 상태가 아니다. 기존 조사 근거는 위에 연결했으며, 실행할 때 현재 코드·환경과 수정 전 조건을 다시 대조한다.
