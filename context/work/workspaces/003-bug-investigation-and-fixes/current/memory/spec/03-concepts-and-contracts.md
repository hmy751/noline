# 개념·데이터·오류 계약

확인 수준은 소스에서 확인한 조건, 분리 실험에서 재현한 결과, 실제 앱/API에서 확인한 결과, 기대 동작·발생 조건 확인이 필요한 후보로 구분한다. 이전 분석의 의심을 모두 확정 버그로 바꾸거나 분리 실험을 실제 데이터 손실 사고로 서술하지 않는다.

활성 여행의 데이터는 SQLite가, 비활성 여행은 서버가 기준이다. Router가 선택을 맡으며 전송 queue가 동기화 변경을 나타낸다. CREATE·UPDATE·DELETE의 payload 형태가 다를 수 있으므로 tripId의 존재를 가정하지 않는다. 미전송 여부는 PENDING만으로 대신할 수 없고 FAILED·IN_PROGRESS 및 중단 복구 조건을 확인한다.

Transaction은 관련 local mutation과 queue 기록의 원자성을 보장해야 한다. `withTransaction`이라는 이름이나 호출 형태 자체를 보장으로 보지 않는다. 설치 드라이버의 동기/비동기 계약, 실제 쿼리 실행 시점, tx 사용과 예외 전파가 구현 판단에 필요하다.

동기화 요청 시도, 일부 성공, 전체 반영, 마지막 반영 시각, cleanup 가능 상태는 별개 의미다. 재시도 횟수·인증 실패·일반 실패·앱 중단의 상태 전이를 기대 결과와 연결한다. pull cursor와 조회 snapshot의 시간 경계, 미전송 local 변경과의 충돌 정책은 구현 전에 확인할 계약이다.

경로의 재사용 가능 여부는 from/to 일정 ID와 profile만으로 충분한지 검증한다. 최신 좌표·일정 순서·삭제 상태·기존 캐시와 후속 실패가 판단 입력이다. 저장 성공 callback에서 받은 최신 결과와 이전 query 목록을 혼동하지 않는다.

서버의 request/response와 클라이언트 타입은 `@repo/schema`가 원천이다. user ownership은 인증 여부와 별도로 확인하며 부모 tripId/scheduleId의 소유권도 포함한다. 공개 오류 계약을 통일하는 경우 표시·재시도 소비자까지 확인하고 새 UX 결정을 리팩토링으로 취급하지 않는다.
