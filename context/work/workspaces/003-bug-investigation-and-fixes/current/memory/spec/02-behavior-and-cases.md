# 기대 동작과 대표 사례

- 로컬 데이터 저장 뒤 queue 추가가 실패하면 둘 중 하나만 남지 않아야 한다. 기존 helper의 분리 실험과 정상 대조군을 비교하되 실제 드라이버·호출부 전체의 동작도 수정 범위에서 확인한다.
- 아직 전송하지 않은 부분 UPDATE, FAILED·IN_PROGRESS 작업이 있는 여행은 '미전송 없음'으로 판정해 정리하지 않아야 한다. 여행 식별과 작업 상태를 모두 보며, 중단·재시도 중 사용자 입력을 보존한다.
- 전송 실행이 끝난 것과 모든 변경이 서버에 반영된 것을 구분한다. 실패 후 재시도·복구, 마지막 동기화 표시, cleanup 가능 여부는 실제 결과와 맞아야 한다.
- 동기화 pull의 조회 중 새 변경이 생기는 경우 다음 동기화에서 놓치지 않아야 한다. 로컬 미전송 수정과 내려온 데이터가 충돌하면 적용 정책을 확인하고 미확정 규칙을 임의로 만들지 않는다.
- 일정 장소 변경은 저장된 최신 좌표로 경로 준비에 반영돼야 한다. 일정 ID가 같아도 좌표나 경유 순서가 바뀌면 예전 경로를 그대로 재사용해도 되는지 구별한다. 위도·경도 0은 유효 좌표이고 누락·null과 구별한다.
- 비활성 여행을 온라인에서 수정·삭제·조회할 때 해당 데이터가 로컬에 없다는 이유만으로 정상 서버 작업을 막지 않아야 한다. 비활성 여행의 오프라인 편집을 새로 지원하는 목표는 아니다.
- 서버의 다른 사용자 여행·일정·경비 접근과 삭제된 데이터 반환을 기존 인증·소유권·soft delete 계약에 맞춰 제한한다. 요청에서 허용하고 성공으로 응답한 수정 필드는 실제 저장돼야 한다.
- 같은 경비는 CRUD·활성화·sync에서 같은 schema 의미로 전달돼야 한다. 날짜·불리언 변환과 실제 검증 여부를 응답 이름으로 대신하지 않는다.
- 필수 초기화 실패와 앱 준비 성공, 지도 준비와 경로 준비, 폼 취소·재열기·늦은 기본값 도착의 의미를 구별한다. 구체적인 실패 UI·재시도 정책은 현재 계약과 사용자 의도를 확인한 뒤 채택한다.

- 자동 갱신 가능한 인증과 실제 재로그인 필요를 구분한다. 갱신을 거친 API도 정상 요청과 같은 응답 의미를 유지하고 재로그인 안내를 따라 복귀할 수 있어야 한다. 계정 종료/전환은 미전송 입력과 사용자 경계를 보호한다.
- 유효한 사용자 여행 선택과 전달하지 않은 수정 필드는 유지한다. 생성 직후 후속 작업, 삭제 뒤 활성 판단과 조회가 일관돼야 한다.
- 재활성화한 여행에 과거 cleanup 예약을 적용하지 않는다. 지도 준비는 pack 생성이 아니라 실제 준비 상태에 근거하고, 부분 실패·삭제·재시도 뒤 표시도 그 결과와 맞아야 한다.
- 날짜 입력은 저장·표시 왕복에서 뜻이 유지되어야 한다. 기간 밖으로 이동한 항목의 접근 경로, 늦은 폼 기본값과 사용자 직접 입력을 보존하며 구체 UI/시간대 해법은 실행에서 확인한다.
- 노출된 지도 이동 버튼은 해당 일정을 보여 주고, 검색/조회 실패는 잘못된 좌표나 정상 빈 결과로 위장하지 않는다.

실제 사용자 데이터·서버 호출이나 iOS 전체 시나리오를 이번 구성에서 재현하지 않았다. 코드 조건·분리 실험과 제품 환경 증거를 각각 구분해 남긴다.
