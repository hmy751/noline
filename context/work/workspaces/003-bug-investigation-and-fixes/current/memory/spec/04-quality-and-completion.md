# 품질·완료 판단

주요 기능 조사의 충실성은 발견한 버그 수로 판단하지 않는다. 실제 화면·기능의 카테고리마다 어떤 사용·실패·연결 조건을 확인했고, 정상 근거·결함 관찰·코드만 확인한 후보·미실행 범위가 무엇인지 찾을 수 있어야 한다. 분리 실험의 정상 결과를 전체 카테고리 무결함으로 올리지 않으며, 미확인 항목을 조용히 제외하지 않는다. 현재 대응 관계는 [카테고리별 조사 기록](../../../records/2026-09-13-02-major-feature-category-investigation.md)에서 확인한다.

[Ticket 구성](../tickets/index.md)은 알려진 후보와 미확인의 담당을 빠짐없이 연결해야 한다. 개별 티켓은 자기 결과를 입증할 수정 전/후 근거를 맡고, 마지막 iOS 통합 검증은 그 결과가 연속 사용에서도 성립하는지 확인한다. 환경이 없어 필수 검증을 못 한 경우를 통과나 완료로 바꾸지 않는다.

채택한 결함은 기대 동작과 수정 전 실패 조건, 수정 후 결과가 연결돼야 한다. 기존 분석의 각 후보는 확인한 결함·변경 불필요·기대 계약 미확정·보류와 그 이유를 추적하며 조용히 없애지 않는다. 재현 가능한 결함을 후보 분류만으로 해결했다고 보고하지 않는다.

데이터 보존·권한·동기화 경계 변경은 실패·부분 성공·재시도 등 결과가 갈리는 조건의 회귀 근거가 필요하다. 정상 경로만 통과하거나 mock으로 실제 driver 계약을 바꾼 테스트만으로 원자성을 입증하지 않는다. 영향받지 않아야 할 정상 저장·조회·활성화 동작도 함께 확인한다.

기존 실험은 메모리 SQLite와 설치된 Expo Drizzle driver를 사용했다. 실제 기기 전체 저장·비활성화·cleanup이나 사용자 데이터 손실의 재현은 아니다. raw script와 output은 [실험 원자료](../../../source/index.md), 해석은 [추가 조사 기록](../../../records/2026-09-10-02-additional-findings.md)에 있다. 수정 후에는 과거 결함을 기대하는 assertion을 완료 검증으로 사용하지 않고 올바른 동작을 확인할 회귀 조건을 만든다.

타입·린트의 이전 기준선과 설치 불일치는 [구성 기록](../../../records/2026-09-10-01-workspace-setup.md)에 남겼다. 검사 도구 정비는 두 Work의 공통 지원 작업이며 버그 수정 결과와 분리한다.

초기 `verify.json`은 client noEmit 타입 검사만 담는다. 로컬 소스·설정·생성 선언 파일과 package/lockfile을 evidence로 선택했지만 외부 node_modules를 고정한 환경은 아니다. 실행 직전 파일 추가·resolution·생성물의 입력 범위를 대조하고, 실제 Ticket이 선택되면 해당 결함을 입증할 검사와 canonical basis를 구체화한다. server나 동작 결함이 해결됐다는 주장을 client 타입 검사로 대신하지 않는다.

이 Workspace에서 제품 Verify는 아직 실행하지 않았다. `ready_for_verification`은 null receipt를 가진 초기 기계 상태다. 이전 실험·검사 이력을 현재 제품 Verify 성공이나 전체 완료로 옮기지 않는다. 최종 상태에는 실제 확인 범위와 남은 미확인을 구분한다.
