이전 4b743e0f는 dbb5902e로 철회한 판본이며 해당 917개·독립 106개를 현재판 결과로 쓰지 않는다. 미커밋 008 UI와 타 작업은 보존했고 배포에서 제외했다. 현재 배포 요청은 접수 확인까지 마쳤지만 003 전체·Ticket 04/05의 모든 UX·정책 검증 완료는 아니다. 다음 출시 확인에서는 심사 결과와 실제 공개를 구별한다.

## 선행 검토·단계별 커밋 이력

아래 ‘다음 작업’, 미착수·미커밋·미배포는 당시 상태이며 위 최신 결과를 대신하지 않는다.

다른 세션의 다음 작업은 **[007 Ticket 09의 2〜7단계 후속 코드 검토·정리](../../../007-sync-failure-recovery/current/memory/tickets/09-staged-code-review-and-refinement.md)**다. 선행 high 검토·수정·검증 완료와 원래 두 Ticket 정책은 유지하며, 이후 1단계처럼 코드 설명·질문을 연결한 후속 개별 검토는 아직 미착수다. 2단계 실제 수신 경로부터 확인한다. [009 루프 개선](../../../009-development-review-improvement/current/memory/tickets/01-stage-one-review-and-judgment-loop.md)은 별도 Ticket이며 서로 착수를 기다리지 않는다. 마지막 종합에도 사용자 아쉬움이 남았고 새 스킬·판단 규칙은 아직 채택하지 않았다. 사용자는 10171행에서 미검토 코드 작업부는 커밋하지 않고 기록·티켓·재개 안내 등 문서만 선별 커밋하도록 승인했다. 마지막 제품 코드 기준은 8f94af5c(경로 부모 a527e977)이며 이후 문서 전용 커밋으로 현재 HEAD는 달라질 수 있다. 새 세션은 실제 HEAD와 diff를 재확인하되 후속 2〜7단계 제품 코드는 검토 후로 남기고 일괄 stage·commit하지 않는다.

현재는 **클라이언트 저장 1단계 분리 커밋 8f94af5c 완료** 상태다. 경로 커밋 a527e977 위에 제품/검사51·기록/색인2의 53파일을 커밋했다. [분리 범위와 검사](../../../007-sync-failure-recovery/records/2026-11-12-10-stage-one-isolated-commit.md)의 client789·독립37·기존 서버73/타입·schema build가 근거이며, 전체 workingtree892·독립36과 다른 판본이다. 후속 2〜7단계·direct-update-failure/구버전·삭제·응답/pull은 작업 폴더에 미커밋으로 보존한다. 앞선 코드 커밋은 다시 쓰지 않는다. 최신 요청은 문서만 별도 커밋하도록 허용한 것이며 후속 제품 코드는 확인 전 미커밋으로 보존한다. push·배포·기존 native 확인은 미실행이다.

**2〜7단계의 순차 검토·개선과 마지막 연결 확인을 완료했다.** 각 단계 high 검토·필요 수정·별도 검증을 거쳤으며 client 847/847·서버 73/73·격리 PostgreSQL 49/49가 통과했다. 서버 타입도 통과했고 기존 client 타입 오류 7개·과거 링크 문제 64개는 유지한다. [단계별 결과와 코드 리뷰 진입](../../../007-sync-failure-recovery/records/2026-11-12-02-staged-review-followups.md)에서 유지/수정 이유와 범위를 확인한다. 이 완료 뒤 사용자 1단계 코드 리뷰를 시작했으며 최신 UI 후속은 위 안내를 따른다. 사용자 수락·커밋·배포는 미실행이며 당시 임시 서버·검증 DB는 정리했다.

11월 12일에는 007-07과 연결된 **저장 1단계만** 추가 검토·수정해 해당 범위 검증을 마쳤다. 최종 client 74묶음 828/828과 독립 92개가 통과했고 기본 타입 오류 7개는 기존 이슈다. [후속 기록](../../../007-sync-failure-recovery/records/2026-11-12-01-save-stage-review-and-cleanup.md)에서 폼·표식·완료 안내·조회 갱신의 수정과 한계를 확인한다. pull 무누락·서버 병합 전체를 이번에 재검증한 결과로 넓히지 않는다. 이후 사용자 요청으로 2〜7단계 순차 검토를 시작했으며, 현재 단계별 진행은 위 최신 안내를 따른다. SQL → 서버 → 앱 배포는 여전히 미실행이다.

추가 조사에 따른 [14개 Ticket](../memory/tickets/index.md)의 번호를 사용자가 요청한 첫 사용 장면 순서로 재배치했다. 티켓의 범위·완료 조건·미확인 담당은 유지하고, 파일명·제목·현재 문서의 번호 참조를 함께 바꿨다. 이후 2026-11-10 [Ticket 12](../memory/tickets/12-pull-consistency.md)를 007 Ticket 07과 함께 선행판 개발·검증을 마쳤고, 추가 독립 검토의 누락 3건도 수정·검증을 마쳤으나, 최종 high 검토에서 비활성화·사본 정리 뒤 늦은 pull이 자식 본문을 다시 저장하는 조건을 재현했다. 이 조건은 사본 수명 대조·본문/cursor 원자적 반영으로 보완했다. 최신 판단은 개발·검증 완료, 배포 별도다. [후속 기록](../../../007-sync-failure-recovery/records/2026-11-10-05-conflict-pull-review-fixes.md)이 최종 보완·검증 범위를 소유한다. 나머지 장면 전체의 구현이나 iOS 통합 검증 완료를 뜻하지 않는다.

## 번호와 별개인 기술 의존 관계

번호는 실제 확인할 장면의 순서이지 모든 구현을 직렬 실행하라는 지시가 아니다. 10의 원자성과 미전송 식별은 11의 재시도·12의 pull 충돌·04의 안전한 데이터 전환을 검증하는 기반이다. 02의 인증 복구는 독립 착수가 가능하지만 계정 정리 완료에는 10의 미전송 판정과 11의 진행 요청 격리가 필요하다.

04의 실제 서버 통합은 13의 활성화 응답 계약을, 05의 전체 준비 표시는 09의 경로 결과 계약을 필요로 한다. 각 티켓은 fixture 기반 확인부터 진행할 수 있으나 필수 선행 결과가 없으면 해당 완료를 보류한다. 같은 파일·계약 변경은 먼저 맞추고, 번호가 뒤라는 이유로 필요한 기반 확인을 미루지 않는다.

14의 시험 계정·DB·iOS 절차 준비는 먼저 가능하지만 전체 통과 판정은 기능별 결과와 남은 blocker를 받은 뒤 한다. 구체적인 실행이 요청되면 선택한 장면의 현재 코드·수정 전 조건·격리 환경을 대조한다.

번호 변경의 이유와 과거 기록을 읽는 대응표는 [재배치 기록](../../records/2026-09-13-04-ticket-scene-order.md)에 있다. 기존 리팩토링 우선이라는 Work 간 선택은 유지한다.

## 유지하는 근거와 미확인

[최신 카테고리 조사](../../records/2026-09-13-02-major-feature-category-investigation.md)의 39개 관찰에는 정상 대조군 16개와 같은 원인의 변형 조건이 포함된다. 이는 신규 버그 수나 실제 기기 통과 수가 아니다. [첫 사용 조사](../../records/2026-09-13-01-first-use-scenario-investigation.md)의 인증·선택 유지·비활성 수정·로그아웃 근거, [기존 transaction·queue 실험](../../records/2026-09-10-02-additional-findings.md)도 유효하다.

실제 iOS 로그인·지도 다운로드·SQLite 저장·강제 종료·계정 전환의 전 과정은 확인하지 않았다. 소스·분리 함수·일부 React 렌더·시간대별 실행의 확인 수준을 유지한다. 사용자 데이터나 외부 서비스에서 삭제·전환을 시험하려면 격리 환경과 허용된 조작 범위를 먼저 확인한다.

다른 Workspace와 진행 중인 제품/테스트 변경은 보존한다. 이번 문서 반영은 자동 연결을 만들지 않는 Maintain 수동 경로이며 active/default index·session binding·제품 Verify status/receipt는 바꾸지 않는다. 이번 직접 검사로 기존 제품 Verify receipt나 기계 상태를 갱신하지 않았다. 초기 기계 상태를 구현 완료로 해석하지 않는다.
