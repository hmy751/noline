# 현재 상태와 다음 행동

추가 조사에 따른 [14개 Ticket](../memory/tickets/index.md)의 번호를 사용자가 요청한 첫 사용 장면 순서로 재배치했다. 티켓의 범위·완료 조건·미확인 담당은 유지하고, 파일명·제목·현재 문서의 번호 참조를 함께 바꿨다. 제품 구현과 실제 iOS 통합 검증은 시작하지 않았다.

## 장면 순서와 다음 행동

앱 시작(01)·로그인(02)·홈의 여행 관리(03), 활성화(04)·지도 준비(05), 입력 폼(06)·일정/경비 작업(07)·날짜 변경(08)·지도/경로(09), 오프라인 저장(10)·재연결 전송(11)·서버 변경 수신(12), 서버 경계(13)·전체 iOS 검증(14) 순서다.

다음에 장면별 검토를 이어갈 때는 01의 초기 화면부터 본다. 로그인과 로그아웃, 여행 생성과 삭제처럼 여러 시점에 걸친 티켓은 첫 접점에 배치하고 후반 조건을 끝에서 다시 확인한다. 이번 요청은 번호 재배치이며 실제 수정이나 앱 조작 착수는 포함하지 않는다.

## 번호와 별개인 기술 의존 관계

번호는 실제 확인할 장면의 순서이지 모든 구현을 직렬 실행하라는 지시가 아니다. 10의 원자성과 미전송 식별은 11의 재시도·12의 pull 충돌·04의 안전한 데이터 전환을 검증하는 기반이다. 02의 인증 복구는 독립 착수가 가능하지만 계정 정리 완료에는 10의 미전송 판정과 11의 진행 요청 격리가 필요하다.

04의 실제 서버 통합은 13의 활성화 응답 계약을, 05의 전체 준비 표시는 09의 경로 결과 계약을 필요로 한다. 각 티켓은 fixture 기반 확인부터 진행할 수 있으나 필수 선행 결과가 없으면 해당 완료를 보류한다. 같은 파일·계약 변경은 먼저 맞추고, 번호가 뒤라는 이유로 필요한 기반 확인을 미루지 않는다.

14의 시험 계정·DB·iOS 절차 준비는 먼저 가능하지만 전체 통과 판정은 기능별 결과와 남은 blocker를 받은 뒤 한다. 구체적인 실행이 요청되면 선택한 장면의 현재 코드·수정 전 조건·격리 환경을 대조한다.

번호 변경의 이유와 과거 기록을 읽는 대응표는 [재배치 기록](../../records/2026-09-13-04-ticket-scene-order.md)에 있다. 기존 리팩토링 우선이라는 Work 간 선택은 유지한다.

## 유지하는 근거와 미확인

[최신 카테고리 조사](../../records/2026-09-13-02-major-feature-category-investigation.md)의 39개 관찰에는 정상 대조군 16개와 같은 원인의 변형 조건이 포함된다. 이는 신규 버그 수나 실제 기기 통과 수가 아니다. [첫 사용 조사](../../records/2026-09-13-01-first-use-scenario-investigation.md)의 인증·선택 유지·비활성 수정·로그아웃 근거, [기존 transaction·queue 실험](../../records/2026-09-10-02-additional-findings.md)도 유효하다.

실제 iOS 로그인·지도 다운로드·SQLite 저장·강제 종료·계정 전환의 전 과정은 확인하지 않았다. 소스·분리 함수·일부 React 렌더·시간대별 실행의 확인 수준을 유지한다. 사용자 데이터나 외부 서비스에서 삭제·전환을 시험하려면 격리 환경과 허용된 조작 범위를 먼저 확인한다.

다른 Workspace와 진행 중인 제품/테스트 변경은 보존한다. 이번 문서 반영은 자동 연결을 만들지 않는 Maintain 수동 경로이며 active/default index·session binding·제품 Verify status/receipt는 바꾸지 않는다. 제품 Verify는 미실행이고 초기 기계 상태를 구현 완료로 해석하지 않는다.
