## 철회한 수정과 다시 고른 범위

처음 4b743e0f는 사본 보호와 같은 여행 작업 직렬화를 함께 바꿨다. 전체 917개·독립 106개·회귀 5조건은 그 판본에서 통과했지만, 제3 리뷰는 기기 해제 뒤 서버 알림에서 재로그인 요구가 발생하면 화면이 해제 실패로 돌아가는 회귀를 확인했다. 기존 공유 지도에도 A가 받지 않은 지도를 반납하면서 B의 유일한 파일을 삭제 요청하는 문제가 있었다. 사용자는 “니가 한작업 되돌려놔봐 … 리뷰 까지고려해서”와 “배포 관련은 냅두고”라고 지시했다.4b743e0f는 dbb5902e에서 revert됐고 당시 제품 tree는 ef6838f2로 돌아갔다. 이전 검증을 현재 수정의 증명으로 쓰지 않는다.

설명 과정에서는 미전송 1건 때문에 미루는 대상이 **그 여행의 로컬 일정·경비 전체**라는 사실을 분명히 했다. 전송 대기와 사본 정리 예약은 다른 일이다. 해제 상태를 유지하면 미전송·보류 입력 해결 후 정상 정리하고, 다시 활성화하면 서버 전송은 계속하되 현재 보관하기로 한 사본은 남긴다. 예약 확인 자체를 금지하는 것이 아니라 실제 삭제 전에 현재 선택과 예약 유효성을 다시 확인하는 것이다. 사용자는 이 뜻을 확인한 뒤 “일단 그 두 군데만 수정”하도록 범위를 정했다.

## 003-04 — 두 파일의 예약 취소와 삭제 직전 확인

## 003-05 — 여행별 지도 반납과 도시별 파일 순서

A가 미전송 입력 때문에 정리를 기다리고 B만 같은 도시 지도를 확보한 경우, 입력 해결 후 A의 사본 정리는 허용돼도 B의 파일은 남아야 한다. 기존 코드는 A의 실제 보유 여부 없이 저장된숫자1에서1을 빼 B의 파일 삭제를 요청했다. 새 코드는 기존 여행별 `mapDownloaded`를 사용해 A의 보유 표시만 해제하고 같은 도시의 남은 보유 여행을 다시 센다. B가 남으면 파일을 보존하고 마지막 보유 여행이 반납하면 파일을 삭제한다. 같은 여행 반복 준비도 한 건으로 센다. 새 DB 테이블은 추가하지 않았다.

같은 도시의 마지막 삭제와 새 획득은 `city-sharing.ts`의 도시별 순서로 처리한다. A 삭제 도중 B가 준비되면 삭제가 끝난 뒤 B가 실제 pack을 다시 확인한다. 공유 파일 등록·재사용은 `download.ts`, 여행별 반납과 최종 삭제는 `cleanup.ts`가 담당한다.007은 미전송·보류 입력이 해결돼 사본 정리가 허용될 때까지 계속 보호하며, 이 변경은 그 뒤 지도 파일의 여행 간 공유 책임을 맡는다.

초기안은 만료 시 여행의 보유 표시까지 끄도록 넓어졌다. 리뷰에서 활성 여행을 실제 다운로드 없이 ‘준비 중’으로 표시하고 열린 화면도 갱신되지 않을 수 있음을 확인했다. 사용자는 **“만료 처리는 원래대로 돌리고 … A를 해제해도 B 지도가 남는 데 필요한 수정만”** 남기도록 정정했다. 최종 만료 함수 두 개는 f5cb9564와 일치한다. 기존 정책은 여행 종료의 현지 날짜 기준 7일 유예 후, 미만료 여행이 있으면 그 수를 도시 등록 정보에 기록하고 모두 만료되면 **도시 DB 등록 정보만** 지운다. Mapbox 파일과 여행별 보유 표시는 건드리지 않는다. 만료와 명시적 여행 반납의 서로 다른 효과를 문서·테스트에도 유지했다.

최종 **c8004d6e**는 제품 3파일(`city-sharing.ts`, `cleanup.ts`, `download.ts`)·검사 1파일(`city-sharing.test.ts`)·Project `map-packs.md`의5파일이다. 초기안의 9개·전체 921개는 최종 범위가 아니다. 축소 후 지도 8개·전체 920개가 통과했다. 미사용 공개 숫자 감소 훅 정리나 지도 만료·재시도 화면 전반으로 확대하지 않았다. 파일 삭제 실패 테스트의 직접 재호출을 앱 자동 재시도로 부르지 않으며, 기존 불명확한 보유 표시는 오삭제보다 보존을 택했다.

## 자동 검사와 실제 native 지도 확인

최종 앱 전체 **78묶음920/920**과 별도 예약 회귀 **6개**가 통과했다. 미커밋 008 UI가 빠진 배포용 체크아웃도 920개 통과했다(`/private/tmp/noline-release-16-client-tests.log`). 변경 파일 lint는 통과했고 전체 타입에는 변경 파일 밖 6개 오류가 남았다. 앞선 타입 수치5·7개와 판본을 섞지 않는다.

iOS26 시뮬레이터에서 현재 JS·실제 SQLite·native Mapbox로 확인했다. 미전송 큐가 비는 시점은 시험 데이터로 만들었으며 실제 운영 서버 재전송은 이번 native 확인 대상이 아니다.

| 상황 | 직접 확인한 결과 |
| --- | --- |
| A에 미전송 입력 있음 | A의 정리 예약·지도 보유 표시·native pack 유지 |
| 큐가 빈 뒤 A 예약 정리 | A의 보유 표시만 꺼짐, B 표시·도시보유 수 1·native pack 유지 |

| A·B 모두 만료 | 도시 DB 등록만 없어지고 B보유표시·native pack 유지 |
| 마지막 B 직접 반납 | 도시 DB 등록 삭제·B보유표시 꺼짐·native pack 목록에서 제거 |

Mapbox의 네트워크 연결을 끄고 B 일정 지도 화면에서 **서울시청 주변 도로와 일정 마커 표시**를 확인했다. 이는 모의 삭제 요청만의 검증보다 넓지만 **물리 iPhone의 비행기 모드·배포 binary16의 실물 기기 검증**을 대신하지 않는다. native pack 자원 목록은 B 보존 시 존재했고 마지막 반납 후null이었다.
