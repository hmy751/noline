# 추가 조사 결과의 티켓 구성

사용자는 주요 기능 조사 뒤 같은 대화에서 다음을 요청했다.

> “한번 티켓을 구성해줘”

이에 Main은 [첫 사용 조사](2026-09-13-01-first-use-scenario-investigation.md), [주요 기능 카테고리 조사](2026-09-13-02-major-feature-category-investigation.md), [기존 후보](../current/memory/analysis-items.md)를 바탕으로 [14개 Ticket](../current/memory/tickets/index.md)을 구성했다. 이번 결과는 실행할 일의 정의이며 제품 수정·실제 계정/DB 조작·제품 Verify를 수행한 결과가 아니다.

## 무엇을 기준으로 나누었는가

로그인 안내는 조사 계기였지만 사용자 판단 기준은 “개발자가 이 앱을 키고 확인해보려고 하는 카테고리를 충실히 조사햇나”였다. 따라서 인증 중심 목록으로 돌아가지 않고 여행·활성화·일정/경비·지도·오프라인 복구·계정·오류의 실제 사용 결과를 기준으로 배치했다.

여러 결함이 같은 결과를 함께 깨뜨리면 묶었다. 여행의 날짜만 바꿨는데 좌표가 없어지는 문제, 선택한 여행이 바뀌는 문제, 삭제 뒤 활성 flag 잔존은 여행 관리 결과에 연결했다. 반면 활성화 데이터 저장과 지도 타일 완료는 시점·실패 복구가 다르므로 데이터 전환(06)과 지도 준비(07)로 나눴다. 경로 계산 자체는 일정 수정·지도 소비까지 연결되는 11이 맡고 07은 그 결과를 표시한다.

저장·queue(01), push 재처리(02), pull 충돌(03)은 모두 동기화와 관련 있지만 실패 원인과 입증할 결과가 다르다. 분리 후에도 01의 미전송 식별을 02·03·04·06이 소비한다는 선행 관계를 남겼다. 04의 인증 복구는 별도 착수가 가능하지만 로그아웃 안전성까지 완료하려면 미전송 판정과 진행 요청 격리가 필요하다.

비활성 CRUD(08), 폼 입력 상태(09), 날짜 의미·기간 밖 접근(10), 오류 소비(13)는 같은 화면을 읽더라도 맡은 결과를 구별했다. 서버 소유권과 응답 검증은 12가 소유하고 여행 수정 허용 필드, 갱신 응답 이중 추출, 좌표 0의 기능 경계는 각각 05·04·11에 두어 중복 변경 책임을 피했다.

## 조사 범위와 실제 담당

기존 후보 14개 영역은 [후보 본문](../current/memory/analysis-items.md)에 담당을 붙였다. 티켓 수가 14라는 사실은 원래 후보와 일대일 대응하거나 14개 독립 버그가 확정됐다는 뜻이 아니다.

추가 발견 중 인증·계정은 04, 선택·생성/삭제 연결은 05, 재활성화 cleanup은 06, 지도 ready·재시도는 07, 폼 통화 지연은 09, 날짜·기간 밖 항목은 10, 검색·지도 버튼은 11, DB 준비 실패는 13에 배치했다. 비활성 삭제/상세, 재시도/pull 등 기존 후보를 강화한 근거는 원래 담당이 함께 읽는다.

아직 실행하지 않은 중요한 조건도 담당이 있다. 새 여행 부모의 서버 도착 시점은 05, A→B 실패 정책은 06, native pack 중단/복구는 07, 일정·경비 연결 변경/삭제는 08, cold link·picker는 09, 기간 변경의 지도 날짜/활성화 만료는 10, 위치 재허용·native 지도 연결은 11, 실제 두 계정과 PostgreSQL 응답은 12, 느린 시작/저장·화면 이탈은 13이다. 프로필·개발자 도구를 포함한 전체 연속 조작의 실제 iOS 증거는 14가 종합한다.

같은 ID 재열기는 부모 null 초기화라는 반대 근거가 있으므로 무조건 수정 항목으로 만들지 않았다. 정상 일정 날짜 전달, 통화별 합계, 기간 밖 경비 노출, 로그인 취소·위치 거절 대조군도 보존 조건으로 남겼다. 숨겨진 설정 메뉴·영수증 업로드·비활성 오프라인 편집은 새 기능 범위로 올리지 않았다.

## 실행 순서와 보장 범위

첫 제안은 데이터 저장과 미전송 판정을 바로잡는 01이다. 다른 영역의 정상 동작 시험도 입력이 보존된다는 전제가 필요하기 때문이다. 사용자 경계와 응답 계약의 12는 독립적으로 높은 우선순위를 가진다. 이는 버그 Work 안의 추천이며, 리팩토링 우선이라는 기존 Work 간 선택을 뒤집거나 이번 요청을 구현 착수로 넓히지 않는다.

모든 티켓은 기대 결과·범위·조사 근거·선행 관계·완료 확인 개요를 갖췄다. 실제 시작 시 현재 코드와 환경을 대조해 재현·검증을 구체화한다. 정책 미확정을 임의 구현하거나 분리 실험을 native 성공으로 올리지 않는다. 개별 티켓의 필수 검증이 없으면 14를 후속으로 붙였다는 이유로 완료 처리하지 않는다.

최종 14는 각 티켓의 결과가 연결된다는 근거를 만드는 검증 작업이다. 알려진 결함과 미확인은 이미 담당에 배치했고, 새 실패는 담당으로 반환하며 미배정이면 Main이 새 범위를 판단한다. 기존 source·record는 덮어쓰지 않고 새 정의와 현재 단계만 기존 current Owner에 연결했다.
