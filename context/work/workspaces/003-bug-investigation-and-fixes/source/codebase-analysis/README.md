> 분석일: 2026-09-06 · 기준 코드: `b4ed41f6e4bbae26fd45827b3b9063097a2c1ea4`

현재 코드는 **기본적인 역할 분리는 갖춰져 있고, 여러 기능을 연결하는 처리 방식과 함수 내부의 표현이 충분히 일관되지 않은 상태**다. 특히 이름·주석·설정이 암시하는 의도와 실제 동작이 다른 곳이 있다. 가독성을 다듬을 부분과 기능 정확성을 확인할 부분을 함께 발견했다.

이 문서는 분석 시점의 관찰이다. 제품 코드나 현재 정책을 바꾸는 문서가 아니며, 리팩토링 순서와 범위도 아직 확정하지 않았다.

## 분석의 출발점과 범위

사용자는 핵심 기능이 안정적으로 동작하고, 코드의 흐름과 설계 이유가 자연스럽게 읽히길 원했다. 가독성, console 정리, 명확한 코드, 확장 가능성, 컴포넌트 내부 흐름을 함께 언급했다.

분석 방향을 정한 사용자 원문:

> “일단 대강 후보 정하고 하는걸 떠나서 좀 코드 베이스 분석해서 설명해주면 좋겠어”
>
> “코드적인 느낌? 지금은 큰그림으로서만 얘기한것 같아서”

이에 따라 먼저 수정 대상을 고르는 접근을 보류하고, 구조 분석과 함수 내부 표현 분석을 모두 수행했다. 앞서 제안했던 ‘일정 생성부터 시작’은 사용자가 채택한 작업 계획이 아니다.

앱 진입점, client의 화면·feature·entity·shared, server, schema, UI package의 TypeScript 소스 목록을 조사하고 핵심 실행 경로의 대표 파일을 읽었다. 선언 파일을 제외한 조사 대상은 281개 소스 파일이다. 모든 파일을 전수 정독하거나 앱의 모든 시나리오를 실행한 분석은 아니다. AI 작성 여부를 코드만으로 추정하거나 품질의 원인으로 확정하지 않았다.

관찰을 읽을 때는 다음을 구분한다.

- **코드에서 확인:** 현재 표현, 호출 관계, 조건, 검증 스키마의 차이를 소스에서 확인했다.
- **검사로 확인:** 설치된 도구를 실행해 나온 결과다.
- **실행 검증 필요:** 코드상 조건은 확인했지만, 실제 사용자 상황에서의 영향은 재현하지 않았다.

## 이후 판단에 사용할 구분

현재까지 확인한 내용을 실제 변경으로 옮길 때는 세 종류를 구분할 수 있다.

- **표현 정리:** 반복 주석·로그 주변 코드, 의미가 숨은 조건식, 불필요한 변환처럼 읽기 부담을 줄이는 일.
- **처리 방식 정리:** 입력 초기화, callback, 저장 후 이동, 공통 구현 사용처럼 여러 함수와 화면의 책임을 맞추는 일.
- **동작 수정과 검증:** 소유권 조건, 누락 필드, 좌표 값 처리, 재시도, queue와 cleanup처럼 실제 결과에 영향을 주는 일.

이 구분은 수정량이나 우선순위를 뜻하지 않는다. 다음 논의에서는 각 항목의 사용자 영향과 변경 범위를 보고 작업 단위를 정할 수 있다. 이 기록에서 제품 코드 변경이나 리팩토링 착수는 수행하지 않았다.
