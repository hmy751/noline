# 현재 상태와 다음 행동

## 작업 위치와 반영 경계

현재 제품 작업 브랜치는 `refactor/app-startup-lifecycle`이다. `b4db89d`까지 목록·상세 조회 훅의 공통화가 커밋되어 있고, 일정 상세, 경비 생성·수정 폼, 홈 요약, 일정 생성·수정 폼의 소비자 변경은 구현·테스트됐으나 아직 커밋되지 않았다.

별도 Project context 브랜치·worktree의 결과는 이 작업 브랜치에 반영된 것으로 간주하지 않는다. Workspace Maintain은 Project context를 대신 반영하지 않는다.

## 완료·수락 경계

Ticket 01~05는 각각의 테스트 한계 안에서 수락됐지만 Workspace 전체 완료나 제품 Verify를 뜻하지 않는다. Project context 반영 후보 범위도 Ticket 01~05이며 Ticket 06은 포함하지 않는다. 제품 Verify receipt는 아직 없다.

- 2-A와 2-B는 온라인 복귀 시 기존 데이터를 즉시 다시 보여 주고 갱신은 Query에 맡기는 기준으로 구현됐다. 이전의 ‘재조회 성공 후 복구’ 전제는 [온라인 복구 정책 변경 기록](../../records/2026-09-29-02-schedule-recovery-query-sync-decision.md)에서 대체됐다.
- 목록·상세 조회 훅 공통화는 `b4db89d`에 반영됐다.
- Main은 관련 자동 검증 42개 suite, 406개 test가 통과했다고 보고했다. 기존 TypeScript 오류 3건은 남아 있으며 이번 결과로 새 제품 Verify나 사용자 acceptance가 생긴 것은 아니다.

## 시뮬레이터와 폼 검증

앞선 시뮬레이터 확인에서는 비활성 여행의 offline·unknown 제한과 온라인 복구, 일정 상세 격리, 경비 폼의 일정 목록 전환, 일정 수정값 유지, API 중단·재시도·복구, 활성 여행의 오프라인 Local 표시를 살폈다. 한 차례 잘못된 offline 판정은 앱 재시작 뒤 해소됐지만 원인은 확인하지 못했다.

추가 검증에서 Main은 다음 전환의 입력값이 복귀 후 유지됐다고 보고했다.

- 경비 생성·수정
- 일정 수정
- 장소 검색 후 일정 생성

검증은 실제 통신 차단이 아니라 디버그 상태 전환으로 수행됐으며, 검증 설정은 원복됐다.

## 새로 확인한 일정 생성 결함

폼 검증 중 기존 일정 생성 화면에서 다음 문제 3건이 확인됐다.

- 수동 작성 중 온라인으로 복귀하면 폼이 사라지고 검색 화면으로 돌아간다. 이후 장소를 선택하면 작성하던 값이 덮어써진다.
- 장소를 선택한 뒤 오프라인으로 전환하면 일반 폼과 수동 폼이 동시에 장착된다.
- 일반 폼에서 취소하면 렌더 중 상태 갱신에 관한 React 경고가 발생한다.

Main은 세 항목 모두 이번 훅 변경 이전부터 존재한 코드 경로라고 보고했다. 이번 확인에서는 수정하지 않았다.

## 다음 행동

사용자는 기존 일정 생성 문제 3건을 간단히 기록하고, 현재 훅 작업에 문제가 없으면 커밋하도록 요청했다. 추가 코드 검토에서 이번 변경의 blocker를 발견하지 못했고 전체 client Jest 42개 suite·406개 test가 다시 통과했다. 전체 타입 검사는 기존 Mapbox/download 오류 3개가 남는다. 적용과 세 문제의 재현·한계는 [조회 조합과 폼 후속 기록](../../records/2026-09-30-01-read-query-consumers-and-form-followups.md)에 있다.

세 문제는 이번 훅 커밋의 수정 범위에 넣지 않았다. 다음은 2-C의 알림 의미와 시점을 결정해 구현하고 검증하는 작업이며, 기존 일정 생성 문제의 수정과 종합 UX 검토도 후속으로 남는다. 2-C를 이번 구현 구간의 끝으로 보는 방향과 Ticket 06 전체 완료는 구분한다.

스크린샷·상세 검증·HTML은 로컬 전용 `artifacts/ticket-06-simulator/`에 보관하고 Git에서 제외한다.
