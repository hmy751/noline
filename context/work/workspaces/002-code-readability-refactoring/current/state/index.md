# 현재 상태와 다음 행동

[01번 Ticket](../memory/tickets/01-expense-totals.md)은 사용자가 구현 결과와 검증 한계를 확인하고 수락해 완료됐다. 통화별 소수 자릿수 규칙과 경비 합계의 첫 항목 판단을 정리한 제품 파일은 [output](../../output/index.md)에 연결한다.

01번의 Main 보고상 변경 전후 fixture 결과는 같았고 제한된 정적 검사는 통과했다. client의 기존 타입 오류 3건은 남았으며 정규 ESLint는 기존 Prettier 호환 오류로 완료되지 않았다. 실제 React Native 화면 렌더는 실행지 않았다. 수락은 이 한계를 포함한 01번 범위에 한정된다.

[02번 Ticket](../memory/tickets/02-city-search.md)도 사용자가 구현 결과와 검증 한계를 확인하고 수락해 완료됐다. 요청과 응답 필터가 도시 코드 목록을 공유하고, 필수 필드·수도 예외·인구 기준 판단과 `City` 변환을 같은 API 파일의 이름 있는 책임으로 분리했다. 수정 전후 직접 fixture와 별도 verifier 비교에서 요청 인자, 선별 경계, 순서, 좌표 변환과 실패 반환이 같았다. 실제 GeoNames 연결과 전체 앱 화면은 확인하지 않았으며 영구 테스트 파일은 없다.

[04번 Ticket](../memory/tickets/04-expense-api.md)은 사용자가 재전파 catch와 로그 제거의 의미, 검증 한계를 확인하고 수락해 완료됐다. 다섯 remote API export에서 요청 검증·HTTP·응답 검증·반환 순서를 직접 보이게 했고, 수정 전후 동일한 8개 Jest 검사가 통과했다. fetcher를 mock한 검사이므로 실제 네트워크·Axios interceptor·React Native 화면은 확인하지 않았다. 제품 파일은 [output](../../output/index.md)에 연결한다. Main은 사용자 요청에 따라 Ticket 04 관련 파일만 `dce576f`로 커밋했다고 보고했다.

제품 Verify receipt는 제공되지 않았다. 개별 보고와 사용자 수락을 전체 Work 완료나 제품 Verify 결과로 확대하지 않는다.

## 공통 Spec·Ticket 운영 기준 반영

인터뷰에서 사용자가 밝힌 기대는 코드베이스를 폭넓게 살피고, 사소한 문제부터 컴포넌트 내부의 복잡한 흐름과 여러 위치에 걸친 연결 부담까지 발견한 문제를 충분한 깊이로 하나씩 해결하는 것이었다. 바텀부터라는 방향은 작은 표현 개선에 머무는 제한이 아니라 AI가 몇몇 특징적인 곳만 고치고 전체 개선을 끝내는 것을 막기 위한 것이었다.

최초 Ticket 03에서는 포맷 함수 이동, 표시값 조립 helper와 단일 상태 반영만으로 좁게 완료할 수 있었다. 이후 사용자가 개선 깊이와 React 관점 등을 보충하면서 현재 구현으로 이어졌다. 실제 최초 diff와 완료 주장, 정정 과정은 [재확인 기록](../../records/2026-09-12-01-ticket-03-initial-scope-reanalysis.md)에 있다.

이 사례를 다시 본 결론은 Spec에 넓은 품질 원칙이 있어도 Ticket의 결과와 실행 범위가 작은 수정으로 축소되면 실행자가 그 수정만 끝내고 멈출 수 있다는 것이었다. 사용자는 Spec·Ticket 구분 자체를 없애거나 `프로덕션 수준` 같은 표현을 추가하는 데 그치지 않고, 원대화를 모르는 새 Main도 목표를 필요한 실행 결과로 이어 가는 공통 판단 방식을 요구했다.

후보는 다음 과정을 거쳤다.

- [첫 fresh-Main 검토](../../records/2026-09-12-02-fresh-main-contract-review.md)에서 현재 맥락에 의존하는 판단 문구의 빈틈을 확인했다.
- [명확성 적용 기록](../../records/2026-09-12-03-instruction-clarity-contract-revision.md)에서 목적·적용 조건·행동·제약을 연결하고 조사 범위와 변경 권한을 구별했다.
- [일반화 후보](../../records/2026-09-12-04-generalized-ticket-contract-candidate.md)는 코드 개선에 한정하지 않고 기능 구현·결함 수정에도 적용되는 맡은 결과 완성 책임으로 넓혔다.
- [현재 후보의 계획 검토](../../records/2026-09-12-05-generalized-candidate-fresh-main-review.md)에서는 원대화를 받지 않은 새 Main들이 전반적 개선과 기능 완성에서는 필요한 관련 작업을 찾고, 오탈자와 API 납품처럼 명시적으로 작은 요청에서는 범위를 지키는 계획을 세웠다고 Main이 보고했다.

사용자는 검토된 공통 기준을 반영하면서 기존 운영 문서도 명확성 기준과 읽기 흐름에 맞게 개선하고, 단일 문서를 디렉터리 구조로 나누는 방향을 제시했다. Main은 이 지시에 따라 공통 기준을 실제 운영 정본에 반영했다고 보고했으며 로컬 파일에서도 새 구조를 확인했다.

현재 공통 운영 기준은 [산출물 지도](../../output/index.md)에 연결한 `context/work/workspaces/spec-and-tickets/`가 소유한다.

- `README.md`: Spec·Ticket·state의 관계와 상황별 읽기 경로
- `EXECUTION-CRITERIA.md`: 필요한 일의 발견, 범위·품질·분해·실행·완료 판단
- `SPEC.md`: Work 전체의 목표와 공통 기준을 구체화하는 다섯 관점
- `TICKET.md`: 실행 결과·맥락·접근·완료 근거·진행의 작성 기준
- `MAINTENANCE.md`: Main·Maintain의 갱신 책임과 새 근거에 따른 재판단
- `HISTORY.md`: 현재 기준을 선택한 배경, 막으려 한 실패, reviewer를 거친 수정 과정과 검증 한계, 이후 기준 변경 이력

실행 기준은 다음 의미를 현재 정본으로 둔다.

- 변경 내용이 명시된 요청은 그 변경과 영향을 확인하는 범위에서 수행한다.
- 기능 완성·문제 해결·전반적 개선처럼 결과를 이루도록 맡긴 요청은 필요한 일을 찾아낼 책임도 포함한다. 분석 예시와 초안 수정 목록을 검토 대상 전체나 개선 상한으로 삼지 않는다.
- Ticket은 구현 방법보다 맡은 결과, 필요한 범위, 완료 근거를 먼저 정한다. 작업 크기를 먼저 정해 목표와 완료 기준을 낮추지 않는다.
- 실행자는 맡은 결과와 권한 안에서 접근을 발전시키고, 초안만으로 부족하면 관련 내용을 확인해 보완하거나 범위 조정안을 제시한다. 조사 범위와 실제 변경 권한은 구별한다.
- 구현 목록 이행이나 테스트 통과가 맡은 결과를 입증하는지 확인한다. 결과를 막는 미해결이나 판단 근거의 부재가 남으면 완료로 닫지 않는다.
- 기능 구현·결함 수정·코드 개선은 같은 책임을 각 작업의 실제 결과와 계약에 맞게 적용한다.

사용자는 현재 문구와 구성을 나중에 바꾸는 주체가 이번 문제와 선택 배경을 알지 못하면 해결한 판단을 쉽게 훼손할 수 있다고 우려했다. 이에 따라 `HISTORY.md`는 다음 의미를 보존한다.

- 처음 기대한 폭넓은 개선과 Ticket 03의 실제 부족
- `바텀부터`와 `프로덕션 수준` 표현이 등장한 배경
- Spec 이름이나 Ticket 크기만 바꾸는 방식으로 해결하지 않은 이유
- 현재 실행 기준이 보존하려는 판단과 reviewer를 거친 수정 과정
- 문서를 책임별로 나눈 이유, 확인한 범위와 남은 한계

`README.md`는 판단에 영향을 주는 문구·구성·읽기 경로를 바꾸기 전에 `HISTORY.md`를 읽도록 한다. 변경자는 기존 문구를 둔 이유와 방지하려던 실패를 확인하고 새 안에서도 같은 판단이 유지되는지 대조해야 한다. 선택 이유가 달라지거나 더 나은 방법을 확인해 기준·책임·읽기 경로를 바꾼다면 이유, 영향과 확인 범위를 `HISTORY.md`의 새 날짜별 항목으로 남기며 앞선 근거를 현재 결론에 맞춰 덮어쓰지 않는다.

`HISTORY.md`는 일반 Ticket 실행이나 Maintain의 매 판단 입력이 아니다. 기준 자체를 변경할 때 읽는 배경 Owner다. 실행 행동은 계속 `EXECUTION-CRITERIA.md`가 소유하고, Maintain 자동 입력은 README·실행 기준·Spec·Ticket·갱신 기준의 다섯 운영 문서를 제공한다.

기존 `SPEC-AND-TICKETS.md`는 과거 링크를 이어 주는 위치 안내로 남았고 본문 정본은 새 디렉터리가 소유한다. 바깥 프로젝트 결정 문서는 중복된 결정 본문을 유지하지 않고 `HISTORY.md`로 연결한다. Main은 이 연결 뒤 링크 검사가 통과했다고 보고했다.

`HISTORY.md`에 보존된 반영 당시 확인 범위는 다음과 같다.

- 기존 단일 문서와 새 다섯 운영 문서의 독립 대조 리뷰에서 필수 의미 누락이 발견되지 않았다.
- 원대화와 후보를 받지 않은 검토자가 루트에서 새 기준을 찾아 가상 계획을 작성하고 필요한 주변 검토, 보존 동작, 파일 범위와 변경 권한, Main·Maintain 책임을 복원했다.
- Maintain 최초 grounding과 후속 판단에 다섯 정본 본문이 포함되는 회귀 검사를 수행했다.
- 전체 하네스 단위 검사 124개 중 기존 프로세스 시간 제한 검사 한 건이 간헐적으로 실패했으며 단독 재실행은 통과했다. 앞선 전체 재실행에서는 124개가 통과했다고 기록돼 있다.
- `pnpm harness:check`는 실행 환경의 의존성 설치 확인에서 중단됐으며, 그 안의 `node scripts/check-harness.mjs`를 직접 실행한 결과는 통과했다.
- 기본 Workspace 001, 명시적으로 연결된 002와 id 없는 기본 Recover가 성공했다고 기록했다.

사용자 요청에 따라 Main은 이 세션에서 반영한 공통 운영 기준, 하네스 소비 경로와 관련 Workspace 문서를 `d7223b7 feat(harness): Spec·Ticket 실행 기준 강화`로 커밋했다고 보고했다. read-only commit 조회에서 전체 해시 `d7223b7b6622f625e26f7e7457f6eb1373cf91d9`과 관련 파일 포함을 확인했다. Main은 커밋 시점의 작업 트리가 clean이었다고 보고했지만 Maintain은 작업 트리 상태를 독립 확인하지 않았다.

Main은 커밋 전 Maintain 관련 검사 9개와 하네스 링크 검사가 통과했다고 보고했다. 전체 124개 검사에서는 위 시간 제한 검사 한 건의 간헐적 실패가 남았으며 단독 실행은 통과했다. 이 검증 한계는 `HISTORY.md`에도 기록돼 있다. Maintain은 검사를 재실행하지 않았다.

현재 공통 기준의 문서 반영·배경 보존·읽기 경로와 커밋은 완료됐지만, 실제 Ticket 구현과 완료 판단에서도 같은 행동이 지속되는지는 후속 실행에서 확인해야 한다. 새 제품 Verify receipt나 이 Workspace 전체에 대한 사용자 acceptance가 생긴 것은 아니다.

## 계속 적용할 기준과 남은 범위

코드 범위별 Ticket 안에서 여러 개선 관점을 바텀부터 적용하고 변경 전후 동작 보존과 개선 효과를 각각 확인한다. 실행 접근은 [작업 단위와 진행 방식](../memory/spec/05-constraints-design-assumptions.md), 전체 후보의 확인한 범위와 남은 범위 관리는 [품질·완료 판단](../memory/spec/04-quality-and-completion.md)을 따른다. 채택 원문과 정정 경위는 [합의 기록](../../records/2026-09-11-01-ticket-boundary-agreement.md)에 있다.

03번은 이번 수락 범위가 아니다. 사용자는 현재 결과가 거의 기대한 수준이라고 평가했지만 상세 재검토 가능성을 남겼고 최종 수락을 명시하지 않았다.

[05번 Ticket](../memory/tickets/05-schedule-response.md)은 Project Context와 실제 코드를 먼저 대조한 결과 실행 범위 재판단 단계다. Main은 Schedule 날짜 직렬화가 CRUD 네 곳이 아니라 nested list·activation·sync를 포함한 일곱 소비 지점에 있고, 기존 문서의 Node 내장 module mock 계획은 프로젝트의 Node 20.18.1에서 실행할 수 없다고 보고했다. 제품 코드·제품 test·server 설정 변경과 서버 검사·사용자 수락은 없다. 공통 추출 없이 닫을지, 일곱 소비 지점의 공유 직렬화 책임으로 다시 정의할지는 아직 선택되지 않았다. 대화 맥락 없는 새 세션의 재구성안도 05의 문서·구현·상태를 그대로 두고 다른 Ticket에서 관계만 표시했다.

대화 맥락을 이어받지 않은 새 세션은 현재 다섯 Ticket만으로 Spec 목표를 달성하기 부족하다고 판단하고, 완료·수락된 01·02·04와 미결인 03·05를 구별한 채 남은 범위를 06부터 17까지의 책임 단위로 제안했다. 입력 생명주기, 저장 뒤 경로 준비, 날짜 계산, local mutation과 Router 전제, sync 계약, 미전송 데이터 보존, activation 완료 상태, 표시 책임, server route 경계와 전체 종료 검토까지 기존 다섯 Ticket 주변을 넘어 배치했다. 보고 원문과 Main의 평가 범위는 [fresh-session Ticket 재구성 검토](../../records/2026-09-12-06-fresh-session-ticket-recomposition-review.md)에 보존한다.

Main은 저장된 문서만으로 기대를 복원하고 관련 흐름을 함께 묶은 점은 상당 부분 성공했다고 평가했다. 다만 06·07·08 등은 조사할 장면에서 실제로 해소할 코드 부담과 완료 결과로 더 구체화해야 하고, 11·12·13 등에서 결함을 별도 분리할 때 선행·차단·담당 관계를 명시해야 하며, 전체 분석 항목의 Ticket 배정과 미배정 범위를 17 이전에도 보여 줘야 한다고 판단했다. 코드에 관한 개별 주장은 이번 Main이 재검증하지 않았고 실제 구현 깊이와 완료 판단도 아직 입증되지 않았다.

Main의 다음 권고는 같은 fresh session에서 이 세 간격을 먼저 보완하고, 이후 07처럼 여러 연결을 다루는 Ticket 하나를 실제 실행 가능한 수준으로 작성해 맡은 결과·필요한 범위·완료 근거의 연결을 확인하는 것이다. 이 보완안의 채택과 Ticket 문서 수정은 아직 사용자 결정 전이며, 이번 보고로 Workspace 문서나 제품 코드가 변경됐다는 근거는 없다.

[기존 후보](../memory/analysis-items.md)와 [추가 조사·후속 범위](../memory/additional-research.md)도 남아 있다. 폼 초기화·재진입, picker, 날짜 그룹, 저장 후 처리, 공통 데이터·경로·정리, 완료 상태와 설정 등의 후속 분해를 이어가되 전체 후보 배치를 실행의 일괄 선행 조건으로 두지 않는다.

합산·정렬은 01번에서 보존을 비교한 대상이며 대표 통화의 제품 기준을 확정한 결과가 아니다. sync 재시도 설명과 조건의 충돌도 실제 요청 횟수 확인이 필요한 후보로 유지한다. 직접 걸리는 버그만 기대 동작·수정 범위·선행 관계를 연결한다.

과거 타입·린트 실패와 설치 상태의 한계는 [구성 기록](../../records/2026-09-10-01-workspace-setup.md)에 있다. 제한된 검사 결과를 전체 client lint 통과나 다른 package의 검증 결과로 확대하지 않는다.

## 원자료와 운영 경계

최초 방향은 [사용자 원문](../../source/user-direction.md), 분석의 보존본·원문 사본·해시는 [source 색인](../../source/index.md)과 [분석 목차](../../source/codebase-analysis/README.md)에서 찾는다. 원래 분석 경로에 의존하지 않는 보존 검증은 [분석 보존 검증 기록](../../records/2026-09-10-04-analysis-preservation-validation.md)의 범위를 따른다.

대화의 수동 전달·문서 반영·Evidence 사후 보존과 자동 hook 처리는 서로 다른 확인 범위다. 운영 상태 보고를 제품 검증이나 완료로 사용하지 않는다. 연결과 처리 귀속은 [session binding 계약](../../../../harness/maintain/SESSION-BINDING-AND-LIFECYCLE.md)을 따른다.
