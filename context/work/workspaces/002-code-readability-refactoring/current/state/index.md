## 현재 결과와 확인 범위

- 홈 카드의 요약 영역이 로딩·제한·최초 실패·갱신 실패의 표시를 소유한다. Main은 기존 조회 결과의 성공 데이터만 집계하며, 정책·조회 상태를 별도 타입이나 훅으로 복제하지 않는다. 공동 제한은 한 안내로, 부분 실패는 정상값과 함께 표시한다.
- 구현자가 최종 client 49 suites / 550 passed / 1 skipped와 형식·lint 검사를 보고했다. 독립 검토는 기존 계약 재사용과 필요한 구조를 확인했고 Main은 코드·검사 본문·이미지를 점검했다. 기존 타입 오류 3개는 남는다. 제품 Verify receipt는 생성하지 않았다.
- 간결화 전 Debug offline/unknown으로 비활성 홈의 제한·복귀를 확인하고, 간결화 후 최신 native에서는 원래 활성 홈의 일정 2개·EUR 56 정상 표시를 확인했다. 실제 인터넷 단절 검증과 간결화 후 native 전환 전체 재실행은 하지 않았다.
- 비활성 일정·경비 목록의 선택 유지·제한·복귀와 기존 상세, 일정 picker 취소 후 초안 보존을 추가 관찰했다. 열린 폼의 네트워크 전환은 이번 수집의 근거가 아니다.

기존 일정 생성·Places 경계(`78acff5`), 경비 날짜(`4646752`), 일정 시각·입수 계약(`d823b41`), 경비 초안·일정 연결(`a8e60a7`)은 유지한다. 이전 실앱·서버 DB 관찰과 자동 검사의 범위는 [10월 2일 기록](../../records/2026-10-02-03-expense-time-decisions-and-verification.md)에 보존한다. 열린 초안 유지, 경비 날짜와 일정 연결 독립성, 활성 여행 Local 이용은 이번에도 보존하는 계약이다.

## 다음 행동과 명시적 보류

홈 안내와 foreground 재확인 연결은 저장됐다. 다음에는 Ticket 06의 목록·상세·폼 종합 UX와 날짜 기준 판단을 현재 증거에서 이어간다. 날짜 기준 검토를 우선 제안했으며 아직 착수하지 않았다. 어떤 항목부터 구현할지는 다음 작업에서 정하며, 새 작업을 시작한 상태로 기록하지 않는다.

- foreground: Network Store 세션이 복귀를 구독해 기존 refresh를 실행한다. 관련 2 suites / 43 tests 통과와 최신 시뮬레이터의 두 번 복귀에서 각각 1회 호출을 Main이 확인했다. 실제 기기 단절·복구 검증은 남는다.
- 날짜: 현재 파리의 홈 9/30~10/2와 목록 9/29~10/1은 같은 timestamp의 현지/UTC 해석 차이로 원인이 확인됐다. Trip 기간의 달력 날짜 의미를 입력·대표 여행·활성 만료와 함께 판단해야 하며 이번에 수정하지 않았다.
- UX·실행 확인: 실제 단절 Local 저장, 열린 폼의 연결 전환, 일정 전체 native 작성·picker, 새 activation 전체 등 남은 검증을 구분한다. 보고서 존재나 부분 관찰을 전체 수락으로 해석하지 않는다.

경비 삭제 실패 이유 유실·상세의 특정 재시도 불일치는 사용자 보류를 유지한다. 해결·폐기 또는 다음 작업의 필수 선행으로 바꾸지 않는다. 복구 토스트 2-C는 현재 추가하지 않는다. 남은 결과·보류·검증 한계를 종합해 06 종료를 판단하며 곧바로 07로 넘어가지 않는다.

## 후속 Ticket과 실행 환경

01~05의 기존 수락 범위는 유지한다. 날짜·폼·Local 반환·transaction·typed pull·시각 계약의 선행 결과는 08·10·11·14·15·17에서 재사용하되, 대표 여행 계산·늦은 기본 통화·전체 form 재진입·저장 후 경로 준비·cache·sync·cleanup·나머지 서버 계약은 각각의 남은 책임이다. 여행 기간 밖 일정 접근, 500ms 경로 준비, 정상 0 좌표, 검색 부분 성공과 수정 fallback 등 기존 미완료도 유지한다.

마지막 앱 관찰은 원래 활성 파리 홈·실제 online·Debug override null이다. 이번 홈 작업에서 DB·계정·활성 상태를 변경하지 않았고 임시 대표 조건은 원복했다. 이전 테스트 경비는 삭제하지 않았다. 앱·서버·Metro가 다음 실행에도 살아 있다고 가정하지 않는다.

현재 session은 자동 Maintain unbound 상태였으므로 사용자 기록 요청에 따라 수동 guarded apply로 반영했다. 자동 연결·기계 상태·receipt·active index는 변경하지 않았다.
