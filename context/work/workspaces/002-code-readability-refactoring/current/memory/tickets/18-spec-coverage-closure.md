# 18 — Spec 범위와 개선 결과의 종료 검토

## 맡은 결과와 범위

완료된 Ticket 몇 개를 전체 Work로 확대하지 않고, Spec의 목표·보존 계약·품질 기준과 기존 분석·추가 후보를 실제 결과에 대조해 이 Workspace가 어디까지 완료됐는지 판단할 수 있는 근거를 만든다. 각 후보를 완료, 근거 있는 유지·제외, 별도 버그 Work, 보류·미확인으로 연결하고 담당 없는 필요한 일이 남지 않게 한다.

이 Ticket은 01–17의 제품 구현을 대신하거나 알려진 누락을 처음 발견해 배치하는 catch-all 구현 범위가 아니다. 현재 배정은 [Ticket 색인](index.md)에 먼저 둔다. 각 Ticket의 실제 결과와 검증·사용자 수락을 대조해 연결의 충분성을 최종 확인하고, 새 중요 근거가 나오면 완료 선언 전에 Main에게 추가 Ticket 또는 별도 Workspace 배치를 요구하는 조사·판정 결과를 맡는다.

## 실행 맥락과 접근

[01번](01-expense-totals.md), [02번](02-city-search.md), [04번](04-expense-api.md)의 사용자 수락은 각 범위에 한정된다. [03번](03-storage-stats.md)은 구현 결과가 있지만 최종 수락 전이다. [05번](05-schedule-response.md)은 직렬화·response schema·ownership/soft-delete를 완료했고, [17번](17-server-data-route-boundaries.md)은 Trip·Expense 직렬화만 선행 완료했다. 이 결과들을 초기화하거나 다른 번호의 신규 성과로 집계하지 않는다.

새 [06번](06-app-startup-lifecycle.md)의 앱 진입 연결과 [13번](13-schedule-route-preparation.md)의 저장 후 처리 보완도 전체 범위에 포함한다. 06–16의 구현과 17의 남은 경계는 문서 구성만으로 완료되지 않는다. 18을 완료하기 전에 03의 실제 수락 여부, 05의 검증 한계, 후속 결과와 [003 담당 Ticket](../../../../003-bug-investigation-and-fixes/current/memory/tickets/index.md)의 직접 차단 조건을 확인한다. 개별 Ticket이 근거 있게 유지·제외한 항목은 자동 구현 대상으로 되돌리지 않지만 Spec 결과를 막는 미확인은 숨기지 않는다.

## 완료 조건과 확인 방법

- Spec 다섯 문서의 주요 요구와 `analysis-items.md`, `additional-research.md`의 모든 후보가 01–17의 결과 또는 명시적 유지·제외·별도 Work·미확인에 연결된다.
- 각 완료 주장에는 변경 전후 동작 보존과 개선 효과의 근거가 있고, 테스트 미실행·mock 한계·기존 실패와 새 회귀가 구별된다.
- 03의 구현과 수락, 05의 완료, 17의 직렬화 조각과 남은 결과를 각각 실제 이력대로 기록한다. 새 번호로 옮겼다는 이유로 이전 수락을 지우거나 새 수락을 만들지 않는다.
- 06–17에 직접 연결된 계약·버그는 담당과 실제 결과를 확인한다. 모든 003 버그의 해결을 일괄 선행 조건으로 삼지는 않지만 002의 맡은 결과를 막는 미해결이 있으면 전체 Workspace 완료를 선언하지 않는다.
- 색인의 미배정 후보·미확정 method·입력 UX에도 유지·추가 Ticket·별도 Work·미확인 중 판단과 근거가 있다. 이미 알려진 누락의 배치를 이 단계까지 미뤄 둔 경우 먼저 Main이 실행 책임을 정한다.
- 제품 Verify receipt와 사용자 acceptance가 없다면 문서·테스트 결과만으로 이를 대신하지 않는다.

## 현재 상태와 실제 결과

기존 17을 18로 옮기고 03의 구현·미수락, 05의 완료와 17의 부분 결과를 반영했다. 종료 검토 실행은 아직 없으며 제품 Verify나 전체 Workspace 사용자 수락도 없다.
