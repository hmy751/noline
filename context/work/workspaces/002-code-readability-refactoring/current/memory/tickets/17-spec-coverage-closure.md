# 17 — Spec 범위와 개선 결과의 종료 검토

## 맡은 결과와 범위

완료된 Ticket 몇 개를 전체 Work로 확대하지 않고, Spec의 목표·보존 계약·품질 기준과 기존 분석·추가 후보를 실제 결과에 대조해 이 Workspace가 어디까지 완료됐는지 판단할 수 있는 근거를 만든다. 각 후보를 완료, 근거 있는 유지·제외, 별도 버그 Work, 보류·미확인으로 연결하고 담당 없는 필요한 일이 남지 않게 한다.

이 Ticket은 01–16의 제품 구현을 대신하거나 알려진 누락을 처음 발견해 배치하는 catch-all 구현 범위가 아니다. 현재 배정은 [Ticket 색인](index.md)에 먼저 둔다. 17은 각 Ticket의 실제 결과와 검증·사용자 수락을 받은 뒤 그 연결의 충분성을 최종 확인하고, 새 중요 근거가 나오면 완료 선언 전에 Main에게 추가 Ticket 또는 별도 Workspace 배치를 요구하는 조사·판정 결과를 맡는다.

## 실행 맥락과 접근

[01번](01-expense-totals.md), [02번](02-city-search.md), [04번](04-expense-api.md)의 사용자 수락은 각 범위에 한정된다. [03번](03-storage-stats.md)은 구현 결과가 있지만 최종 수락 전이다. [05번](05-schedule-response.md)은 문서와 구현을 그대로 둔 별도 판단 트랙이며, 공통 추출 없이 닫을지 일곱 소비 지점의 직렬화 책임으로 실행할지 결정되지 않았다. 06–16도 문서 생성만으로 완료되지 않는다.

17을 시작하기 전에 03의 수락 여부, 05의 별도 처분, 06–16의 결과와 직접 차단한 결함 Work의 상태를 확인한다. 개별 Ticket이 근거 있게 제외한 항목은 다시 구현 대상으로 만들지 않지만, 근거가 없거나 Spec 결과를 막는 미확인은 전체 완료에서 숨기지 않는다.

## 완료 조건과 확인 방법

- Spec 다섯 문서의 주요 요구와 `analysis-items.md`, `additional-research.md`의 모든 후보가 01–16 결과 또는 명시적 유지·제외·별도 Work·미확인에 연결된다.
- 각 완료 주장에는 변경 전후 동작 보존과 개선 효과의 근거가 있고, 테스트 미실행·mock 한계·기존 실패와 새 회귀가 구별된다.
- 03은 사용자의 실제 수락 여부대로, 05는 별도 판단 결과대로 기록하며 둘을 다른 Ticket의 결과로 흡수하지 않는다.
- 06·11–14·16에 연결된 계약·버그 결함은 담당과 결과가 확인되며, 미해결이면 전체 Workspace 완료를 선언하지 않는다.
- Auth/Places server 경계, `RadioGroup`의 `as any`, 미호출 auth helper처럼 현재 미배정인 낮은 근거 후보도 유지·추가 Ticket·별도 Work·미확인 중 하나로 판정한다.
- 제품 Verify receipt와 사용자 acceptance가 없다면 문서·테스트 결과만으로 이를 대신하지 않는다.

## 현재 상태와 실제 결과

Ticket 문서와 사전 배정 기준만 구성했다. 03·05·06–16의 결과가 없으므로 종료 검토는 시작하지 않았고 제품 Verify나 전체 Workspace 사용자 수락도 없다.
