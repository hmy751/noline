# 문제·목표·범위

현재 제품은 일반적인 화면·feature·data·repository 역할 분리와 재사용 기반을 갖추고 있다. 한편 작은 처리 주변에 반복 주석·로그·catch가 붙고, 비슷한 처리 방식이 다르거나 이름·설정·주석과 실행 의미가 어긋나 독자가 값·조건·타입과 설계 이유를 다시 추적해야 하는 부분이 있다. 폼과 저장 후 처리에도 비슷한 책임이 서로 다른 위치에 놓여 있다.

목표는 기존 기능과 유효한 역할 분리를 유지하면서 코드를 이해하고 수정하는 부담을 줄이는 것이다. 비슷한 처리는 공통된 방식으로 이해할 수 있게 하고 필요한 차이는 이유가 드러나게 한다. 이름·주석·타입·설정은 실제 동작과 책임을 설명해야 한다.

사용자가 선택한 방향은 **리팩토링 우선, 큰 구조보다 바텀 요소부터**다. 바텀은 이름·조건식·기본값·값 변환·작은 함수·타입 등 가까운 코드 요소를 먼저 본다는 뜻이다. 작은 요소에서 반복 패턴을 확인하고 근거가 있을 때 필요한 내부 책임 정리로 이어간다. 특정 디렉터리의 전수 개편, 전면 통일이나 큰 구조 개편을 목표로 추가하지 않는다.

포함 범위는 client·server·schema·UI의 코드 표현, 함수 내부 흐름, 기존 계약을 유지하는 타입·검증 정리, 의미가 같은 중복, 폼·컴포넌트·hook의 내부 책임이다. [전체 후보](../analysis-items.md)에 기존 분석과 추가 관찰을 유지한다. 후보는 채택 시 원자료와 현재 코드를 대조하며 무조건 변경할 목록이 아니다.

README 개선, 신규 기능, 폴더·계층 재편 자체, 버그 수정, 하네스 개편은 이 Work의 목표에 포함하지 않는다. 공개 동작·오류 계약을 바꾸어야 하는 후보는 동작 확인과 수정 범위를 분리한다. 알려진 결함은 잘못된 동작을 영구 보존할 근거가 아니라 직접 관련된 범위의 선행 조건 또는 제외 경계다.

두 Workspace의 초기 구성에서 시작해 현재는 Spec을 구체화하는 단계다. 제품 코드 구현·실행 Ticket은 아직 없고 첫 대상·세부 순서도 미확정이다. 최초 방향의 원문은 [사용자 발췌](../../../source/user-direction.md), 목표 보강에 사용한 분석은 [보존본](../../../source/codebase-analysis/README.md)에 있다. 사용자는 source를 읽어 배경을 보강하되 무조건 따르지는 말라고 했고, 보강된 목표를 수용했다. 현재 목표와 변경 판단은 이 Spec을 기준으로 한다.
