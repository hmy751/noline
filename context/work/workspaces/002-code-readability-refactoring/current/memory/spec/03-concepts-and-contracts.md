# 코드 개선에서 함께 사용할 개념과 계약

리팩토링은 관찰 가능한 동작과 계약을 유지하며 표현·중복·내부 책임을 개선하는 변경이다. 버그 확인·수정은 기대 동작과 현재 결과의 차이를 판별하고 고치는 변경이다. 한 파일에도 두 종류가 함께 있을 수 있으므로 파일 이름만으로 분류하지 않는다.

보존 계약은 함수 입력·반환값뿐 아니라 오류 전달, 저장 내용, 화면 변화, 관련 부작용의 횟수와 필요한 실행 순서·완료 범위를 포함한다. 변경 범위에 관련된 계약과 관찰 조건을 선택하며 기존 구현의 모든 내부 단계를 고정하지 않는다. 변경 전 버그나 불명확한 동작은 자동으로 정답이 되지 않는다. 직접 걸리는 부분은 기대 동작을 먼저 판단하거나 별도 버그 Work와 구분한다.

타입과 입력의 원천은 `@repo/schema`다. `any`, `as never[]`, non-null assertion의 제거는 이미 검증한 데이터 형태·허용 수정 필드·조회 결과의 존재가 이후 처리까지 전달되는 방식으로 해결한다. 검사를 통과시키기 위한 새 단언이나 실패를 숨기는 기본값으로 대체하지 않는다.

저장 요청, 저장된 결과, React Query 캐시 반영, 화면 이동, 지도·경로 준비는 서로 다른 완료 시점이다. 함수의 이름·인자·반환값·callback은 실제 소유한 책임을 드러내야 한다. 단순히 모든 기능을 같은 모양으로 만들기 위해 이동이나 후속 처리를 한 곳으로 강제하지 않는다.

조회 정책·권한·오류 응답은 외부에서 관찰하는 계약이다. 내부 변환 책임을 정리할 수 있지만 공개 오류 형태나 재시도 가능 여부를 바꾸는 결정을 리팩토링 안에 숨기지 않는다. 폼 값 선택과 닫기·취소의 의미 역시 기존 UX와 함께 확인한다.

local upsert·cleanup·경로 다운로드의 공통화는 동일한 입력·출력뿐 아니라 실패·중복·최신성 조건도 같은지 확인한 뒤 결정한다. 제품 구현은 `apps/`·`packages/`의 기존 Owner에 두고 Workspace에는 계획·판단·증거 위치를 남긴다.

Ticket 06에서 함께 사용할 의미는 다음과 같다. 실제 네트워크 관측은 online/offline/unknown이며 unknown은 초기뿐 아니라 이후 미확정 관측도 포함한다. 여행 활성화와 현재 화면에서 선택한 여행은 다른 값이다. React Query의 이전 서버 응답 캐시와 활성 여행의 Local SQLite도 다른 역할이며 캐시 존재가 오프라인 접근 허용을 뜻하지 않는다.

Router의 정책 거부는 요청을 시작하지 않았다는 결과이며, 이미 전송한 HTTP 요청의 실패와 구별한다. 제한 이유는 기존 오류 흐름으로 전달하고 버튼마다 같은 검사를 복제하지 않는다. Debug override는 화면용 값으로 실제 요청을 허용하는 근거가 아니며, override 중 쓰기 차단은 별도 조건이다. 정확한 상태 변환·동작과 책임 연결은 [Ticket 06](../tickets/06-app-startup-lifecycle.md)을 따른다.

앱 준비 완료는 DB 사용 가능과 인증 복원 시도의 완료이며, 로그인·네트워크 확정·sync 완료와 다르다. 앱 준비 조율은 `application`, 인증 정보와 상태는 Auth Store, 기능별 선택·정리 규칙은 해당 Entity·서비스가 소유한다. 앱 전체 책임과 하위 기능의 책임을 함께 바꾸지 않는다. `getDatabase`는 초기화 성공 뒤 접근 계약이다. 인증의 초기 복원은 완료 결과를 Store 생애 동안 재사용하고 복원 실패의 명시적 재시도만 새 읽기를 허용하는 계약으로 연결한다. 기존 메서드 이름 자체를 후속 구현 제약으로 고정하지 않는다. Repository의 실제 조회 출처는 현재 연결 상태나 화면 override에서 추정하지 않는다.

sync 실행의 조건·현재 작업·종료 대기는 sync lifecycle 서비스가 소유하며 Provider는 상태 구독과 자동·주기 요청을 연결한다. DB 준비 상태는 DB 모듈에서 읽으며 화면의 준비 완료를 재추정하지 않는다. `skipped`는 엔진을 시작하지 않은 결과, `completed`는 엔진 Promise가 resolve한 결과, `failed`는 reject한 결과다. 엔진 내부가 오류를 잡는 현재 한계 때문에 `completed`를 모든 작업의 서버 반영 성공으로 확대하지 않는다. 엔진 결과 의미와 재시도는 Ticket 15가 계속 맡는다.

후속 인증 설계의 세션 기록은 SecureStore의 사용자 ID와 nullable access/refresh token 묶음이다. 로그인 성공으로 생성하며 SQLite의 여행 데이터와 별개다. 토큰의 만료·무효화, 기기의 토큰 삭제, 계정 기록 부재, 저장소 읽기·해석 실패와 명시적 로그아웃 명령은 서로 다른 사건이다. 로컬 접근에는 복원된 계정과 대상 데이터 소유권·활성화 조건을 적용하고, 서버 작업에는 필요한 인증과 실제 요청 조건을 적용한다.

Auth 상태는 `initializing`, `signed-out`, `signed-in`, `reauth-required`, `restore-failed`로 명시한다. `signed-in`은 서버가 방금 유효성을 보장한 상태가 아니라 인증 수단을 복원해 요청·자동 갱신을 시도할 수 있는 상태다. `signed-out`은 기록이 없다고 확인한 결과이며, `restore-failed`는 존재·정상성을 확정하지 못한 결과다. 같은 로그인 화면에 연결해도 삭제·재시도 부작용을 합치지 않는다. 요청 당시 세션의 동일성은 userId 일치와 다르므로, 이전 세션의 늦은 토큰 응답은 같은 계정 재로그인 뒤에도 버린다. 상세 전이와 구현 확인 범위는 Ticket 06이 소유한다.
