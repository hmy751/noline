# 코드 개선에서 함께 사용할 개념과 계약

리팩토링은 관찰 가능한 동작과 계약을 유지하며 표현·중복·내부 책임을 개선하는 변경이다. 버그 확인·수정은 기대 동작과 현재 결과의 차이를 판별하고 고치는 변경이다. 한 파일에도 두 종류가 함께 있을 수 있으므로 파일 이름만으로 분류하지 않는다.

타입과 입력의 원천은 `@repo/schema`다. `any`, `as never[]`, non-null assertion의 제거는 이미 검증한 데이터 형태·허용 수정 필드·조회 결과의 존재가 이후 처리까지 전달되는 방식으로 해결한다. 검사를 통과시키기 위한 새 단언이나 실패를 숨기는 기본값으로 대체하지 않는다.

저장 요청, 저장된 결과, React Query 캐시 반영, 화면 이동, 지도·경로 준비는 서로 다른 완료 시점이다. 함수의 이름·인자·반환값·callback은 실제 소유한 책임을 드러내야 한다. 단순히 모든 기능을 같은 모양으로 만들기 위해 이동이나 후속 처리를 한 곳으로 강제하지 않는다.

조회 정책·권한·오류 응답은 외부에서 관찰하는 계약이다. 내부 변환 책임을 정리할 수 있지만 공개 오류 형태나 재시도 가능 여부를 바꾸는 결정을 리팩토링 안에 숨기지 않는다. 폼 값 선택과 닫기·취소의 의미 역시 기존 UX와 함께 확인한다.

local upsert·cleanup·경로 다운로드의 공통화는 동일한 입력·출력뿐 아니라 실패·중복·최신성 조건도 같은지 확인한 뒤 결정한다. 제품 구현은 `apps/`·`packages/`의 기존 Owner에 두고 Workspace에는 계획·판단·증거 위치를 남긴다.
