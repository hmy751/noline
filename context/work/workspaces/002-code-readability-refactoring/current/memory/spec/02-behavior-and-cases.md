# 보존할 동작과 대표 사례

## Ticket 06에서 채택한 네트워크 동작

네트워크 정책을 연결하는 변경은 기존 임시 online·null의 offline 축약을 보존하지 않고 [Ticket 06의 합의](../tickets/06-app-startup-lifecycle.md)를 기준으로 확인한다. 정상 모드에서는 활성 여행이 unknown/offline에서도 Local로 읽고 쓰며, 비활성 여행은 확인된 online에서 서버를 사용한다. 탭·여행 기본 정보·활성 상태·사용자 선택은 네트워크 변화로 자동 변경하지 않는다.

예를 들어 비활성 여행의 스케줄을 보던 중 unknown이 되면 이전 서버 응답 캐시는 남겨 두고 내용 영역에 제한 안내를 보여 준다. 수정 폼에서 저장을 누르면 Router가 전송 전에 거부하고 기존 오류 흐름이 이유를 안내하며 입력은 유지한다. 같은 여행을 계속 보고 있을 때 실제 연결이 복구되어 접근이 허용되면 기존 데이터를 먼저 표시한다. 재조회 여부는 Query의 데이터 유무·유효기간·무효화 상태에 맡기며 화면 표시를 새 조회나 sync 완료까지 기다리게 하지 않는다. 조회와 sync 갱신이 겹쳐 발생하는 추가 조회는 허용하고, 실제 변경이 화면에 반영되는지는 별도로 지킨다. 저장은 자동 실행하지 않는다. 초기 unknown은 10초 후 확인 불가 안내로 바뀔 수 있지만 상태를 임의 offline으로 바꾸지 않는다.

Debug override 중에는 화면만 강제 상태를 사용하고 요청 판단은 실제 관측을 따른다. 쓰기·queue 추가·새 sync 전송은 차단한다. 이 예외를 활성 여행의 정상 Local 쓰기 정책과 혼동하지 않는다. 세부 전환·토스트·재확인 기준과 검증 사례는 Ticket 06이 소유한다.

## Ticket 06에서 채택한 앱 준비와 선택·종료 동작

DB가 준비되기 전에는 인증 복원과 앱 화면·Provider를 시작하지 않는다. DB 준비에 실패하면 실패 안내와 재시도를 제공하며, 재시도는 저장된 여행·큐·인증 정보를 삭제하지 않는다. DB 준비 성공 뒤 세션 기록 부재는 `signed-out`, 보안 저장소 읽기·해석 실패는 `restore-failed`로 복원 시도를 마치고 로그인 화면으로 간다. 복원 실패에는 안내와 명시적 재시도를 제공하고 기존 저장값·여행·큐를 보존한다. 네트워크 확정과 서버 토큰 검증은 새 진입 선행 조건이 아니다.

예를 들어 인증 정보가 저장돼 있어도 SQLite 준비에 실패하면 재시도 화면을 보여 준다. 반대로 SQLite 준비에 성공해도 인증 저장소 읽기가 실패할 수 있으며 이때는 로그인 화면을 보여 준다. 여행이 없거나 활성 여행이 없는 것과 기기 DB·스키마의 준비 여부는 별개의 조건이다.

사용자 선택은 네트워크 변화나 불완전한 Local 목록으로 바꾸지 않는다. 성공한 Remote 목록·실제 online·조회 완료에서 기존 선택의 제거를 확인하면 다른 여행을 선택하고, 목록이 비었으면 해제한다. 로그아웃/탈퇴는 새 pending cleanup을 막고 진행 중 정리의 성공·실패 종료 뒤 로컬 세션을 비운다. 이 동작을 전체 sync나 지도 정리의 취소·데이터 보존 보장으로 확대하지 않는다. 세부 계약과 자동 검사 범위는 Ticket 06이 소유한다.

새 sync는 DB 사용 가능·로그인·세션 만료가 아닌 상태·실제 online·override 해제·세션 종료 중 아님을 함께 확인한다. 로그인·인증 복구·네트워크 복구·강제 설정 해제로 조건이 충족되면 자동 요청하고, 수동 요청도 같은 경계를 사용한다. 실행 중 동시 요청은 새 작업을 예약하지 않고 보류한다. 이미 전송한 요청을 네트워크 변화만으로 취소하지 않는다.

로그아웃/탈퇴가 기존 미동기화 확인을 통과하거나 사용자가 강제 종료를 선택하면 새 sync를 막고 실행 중 sync의 성공·실패 종료를 기다린다. 그 뒤 서버 세션을 종료하고 기존 cleanup 대기 안에서 로컬 세션을 비운다. 서버 로그아웃 실패 시 로컬 종료 진행과 서버 계정 삭제 실패 시 로컬 유지의 차이를 보존한다. 강제 종료 대기 중에도 진행 표시와 종료 버튼 비활성화를 유지한다. DB reset이 실패해 준비 상태가 해제되면 인증 정보가 남아도 새 sync를 시작하지 않는다. [선택·검사 근거](../../../records/2026-09-18-03-sync-start-and-session-teardown.md)를 함께 적용한다.

## Ticket 06에서 채택한 세션·재로그인 동작

이 절은 기존 인증 구현을 보완할 현재 기준이다. SecureStore에는 서버 로그인 성공으로 얻은 계정과 토큰을 한 세션 기록으로 다룬다. 계정 기록은 유효하지만 인증 수단이 없거나 인증 사유로 자동 갱신이 거절되면 `reauth-required`로 두고 그 계정 소유의 활성 여행 Local CRUD를 유지한다. 인증 만료에 별도 이용 기간을 두지 않으며 기존 활성화·정리 정책은 해당 Owner를 따른다.

`initializing`은 앱 프로세스 시작의 초기 복원과 복원 실패 뒤 명시적 재시도에만 사용한다. 화면 이동·foreground 복귀·네트워크 변화·토큰 갱신·재로그인으로 초기 복원을 반복하거나 기존 로컬 작업을 막지 않는다. 실제 상태 정의와 저장·소비 책임은 [Ticket 06](../tickets/06-app-startup-lifecycle.md)에 있다.

접근 토큰 만료는 자동 갱신을 먼저 시도하고 통신 오류·서버 장애와 인증 사유의 갱신 불가를 구별한다. `reauth-required`에서는 보호된 Remote 작업·새 sync를 멈추며 로그인 화면을 열 수 있다. 비활성 여행 서버 이용·새 여행 생성·새 활성화에는 필요한 인증이 있어야 한다. 서비스 기능은 실제 네트워크와 기존 정책을 따르고 인증 만료를 offline으로 바꾸지 않는다. 사용자 선택·입력은 유지하며 기기 저장과 서버 동기화 완료를 구분한다.

같은 계정 재로그인은 기존 데이터·큐를 유지하고 인증 정보만 갱신한다. 다른 계정을 선택하면 기존 상태를 보존한 채 불일치를 안내하며, 계정 변경은 명시적 로그아웃 뒤 로그인으로 진행한다. 정상 로그아웃 완료는 로컬 DB·큐·인증 세션을 비우며, 서버 반영 데이터와 달리 폐기한 미전송 변경은 복구되지 않는다. 만료 후 같은 계정 재로그인의 서버 인증·기기 저장이 실패하거나 취소되면 기존 `reauth-required`와 로컬 이용을 유지하고 다시 시도하게 한다. 저장 성공 전 로그인 완료로 전환하지 않으며 별도 저장 실패 상태를 추가하지 않는다. 복원 실패 또는 세션 기록 부재에서 로그인했어도 잔존 데이터 소유 계정을 검사한다. 조회·변경·활성화·전송 모두 현재 계정의 소유 범위를 지킨다.

예를 들어 A의 토큰 갱신 요청이 진행 중일 때 로그아웃하거나 로그아웃을 거쳐 B로 로그인한 경우 늦은 A 응답은 저장소·현재 상태를 덮지 않는다. A로 다시 로그인했어도 요청 당시 세션과 다르면 같은 처리를 한다. 일반적인 세션 종료 순서와 오류 처리는 유지하며, 로그아웃 중 앱 강제 종료 후 정리를 재개하는 장치와 다중 기기 제어는 이번 범위에 넣지 않는다.

일반 API는 첫 401 뒤 자동 갱신을 공유하고 성공하면 원래 요청을 한 번 재전송한다. 갱신을 완료하지 못하면 그 호출은 오류로 끝내고, 사용자 재로그인까지 일반 요청을 보관하는 대기열은 만들지 않는다. 로그인 후 필요한 새 조회와 로컬 sync_queue의 재전송은 별개다. 통신·서버 장애·기기 저장 실패를 모두 인증 거절로 분류하지 않는다.

선택한 비용·탈락안과 설명 정정은 [추가 결정 기록](../../../records/2026-09-19-01-auth-complexity-review-and-decisions.md)에서 읽는다. 신규 시나리오는 구현 전에 검사로 고정하고 API·저장·소비 연결의 결과를 확인한다.

## 나머지 보존 사례

리팩토링 결과는 [보존 계약](03-concepts-and-contracts.md)을 유지하면서 읽기 부담을 줄여야 한다. 정상뿐 아니라 변경에 관련된 실패·취소·재진입·늦은 응답·경계값을 골라 확인한다. 모든 작업에 전체 앱 시나리오를 의무화하지 않는다. 알려진 버그를 바르게 보이도록 이름만 바꾸거나 검증 조건을 지워서는 안 된다.

- API 함수가 요청·응답 검증·반환을 수행할 때, 반복적인 로그와 재전파 catch를 정리해도 실패가 호출부로 전달되고 필요한 오류 기록 책임이 남는다. 후속 처리나 오류 종류를 바꾸는 catch는 단순 중복으로 지우지 않는다.
- 조건이 통화 강조나 금액 소수 자릿수를 정하면, 이름만으로 판단 의미가 읽히게 하되 통화별 값·표시·정렬 결과를 유지한다. Main이 확인한 경비 화면 사례에서는 첫 통화가 항상 여행 기본 통화인 것은 아니므로 `isBaseCurrency`처럼 실제보다 강한 의미를 붙이지 않는다. 후보 채택 시 현재 코드와 입력을 다시 대조한다.
- 이미 number인 값을 문자열로 바꿨다가 다시 숫자로 만드는 표현은 입력 계약을 확인해 단순화한다. `0`과 누락을 구분하도록 결과를 바꾸는 수정은 좌표 버그 범위로 따로 다룬다.
- 폼에서 새 항목 열기, 같은 항목 재열기, 취소, 다른 항목으로 전환, 늦은 조회 결과 도착을 구별한다. 초기값 보존·초기화의 의도를 먼저 확인하고, 기존 UX의 잘못 여부가 미정이면 값을 임의로 리셋하지 않는다.
- picker의 선택과 닫기, 저장 완료와 화면 이동·경로 준비는 각각 의미와 호출 주체가 드러나야 한다. 반환값이 같아도 화면이 먼저 닫히거나 경로 준비가 두 번 실행되면 동작이 달라질 수 있다. 연결된 부작용의 횟수와 필요한 실행 순서·완료 범위도 확인한다. 타이머 제거·실패 표시 변경처럼 실제 결과가 달라지는 부분은 먼저 기대 동작과 증거를 확보한다.
- 중복된 경로 다운로드·local upsert·cleanup은 기존 경로 유무, 변경 좌표, 미전송 작업 보존 조건이 서로 다를 수 있다. 중간 실패 시 남는 데이터와 작업도 비교하고, 같은 의미에 한해 공통화한다.

활성 여행은 Local SQLite, 비활성 여행은 Server API라는 기존 기준, 클라이언트 생성 ID, 공유 schema, 인증·소유권·soft delete와 데이터 보존 정책을 유지한다. 시간 표현은 필드 계약을 구별한다. Main이 보고한 현재 schema와 Ticket 05 결과에서 Schedule 날짜와 생성·수정 시각은 timezone을 포함한 ISO datetime이고, Expense `date`는 `YYYY-MM-DD`다. 이것이 의도된 domain 구분인지 과거의 일괄 ISO datetime 규칙에서 교정할 예외인지는 아직 판단하지 않았으므로, Ticket 08·11·17에서 어느 한쪽으로 통일된 계약처럼 다루지 않는다. 실기기·외부 API 확인이 없는 코드 비교를 제품 전체 동작 보존 증거로 확대하지 않는다.
