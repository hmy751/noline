# 보존할 동작과 대표 사례

리팩토링 결과는 [보존 계약](03-concepts-and-contracts.md)을 유지하면서 읽기 부담을 줄여야 한다. 정상뿐 아니라 변경에 관련된 실패·취소·재진입·늦은 응답·경계값을 골라 확인한다. 모든 작업에 전체 앱 시나리오를 의무화하지 않는다. 알려진 버그를 바르게 보이도록 이름만 바꾸거나 검증 조건을 지워서는 안 된다.

- API 함수가 요청·응답 검증·반환을 수행할 때, 반복적인 로그와 재전파 catch를 정리해도 실패가 호출부로 전달되고 필요한 오류 기록 책임이 남는다. 후속 처리나 오류 종류를 바꾸는 catch는 단순 중복으로 지우지 않는다.
- 조건이 통화 강조나 금액 소수 자릿수를 정하면, 이름만으로 판단 의미가 읽히게 하되 통화별 값·표시·정렬 결과를 유지한다. Main이 확인한 경비 화면 사례에서는 첫 통화가 항상 여행 기본 통화인 것은 아니므로 `isBaseCurrency`처럼 실제보다 강한 의미를 붙이지 않는다. 후보 채택 시 현재 코드와 입력을 다시 대조한다.
- 이미 number인 값을 문자열로 바꿨다가 다시 숫자로 만드는 표현은 입력 계약을 확인해 단순화한다. `0`과 누락을 구분하도록 결과를 바꾸는 수정은 좌표 버그 범위로 따로 다룬다.
- 폼에서 새 항목 열기, 같은 항목 재열기, 취소, 다른 항목으로 전환, 늦은 조회 결과 도착을 구별한다. 초기값 보존·초기화의 의도를 먼저 확인하고, 기존 UX의 잘못 여부가 미정이면 값을 임의로 리셋하지 않는다.
- picker의 선택과 닫기, 저장 완료와 화면 이동·경로 준비는 각각 의미와 호출 주체가 드러나야 한다. 반환값이 같아도 화면이 먼저 닫히거나 경로 준비가 두 번 실행되면 동작이 달라질 수 있다. 연결된 부작용의 횟수와 필요한 실행 순서·완료 범위도 확인한다. 타이머 제거·실패 표시 변경처럼 실제 결과가 달라지는 부분은 먼저 기대 동작과 증거를 확보한다.
- 중복된 경로 다운로드·local upsert·cleanup은 기존 경로 유무, 변경 좌표, 미전송 작업 보존 조건이 서로 다를 수 있다. 중간 실패 시 남는 데이터와 작업도 비교하고, 같은 의미에 한해 공통화한다.

활성 여행은 Local SQLite, 비활성 여행은 Server API라는 기존 기준, 클라이언트 생성 ID, 공유 schema, 인증·소유권·soft delete와 데이터 보존 정책을 유지한다. 시간 표현은 필드 계약을 구별한다. Main이 보고한 현재 schema와 Ticket 05 결과에서 Schedule 날짜와 생성·수정 시각은 timezone을 포함한 ISO datetime이고, Expense `date`는 `YYYY-MM-DD`다. 이것이 의도된 domain 구분인지 과거의 일괄 ISO datetime 규칙에서 교정할 예외인지는 아직 판단하지 않았으므로, Ticket 08·11·17에서 어느 한쪽으로 통일된 계약처럼 다루지 않는다. 실기기·외부 API 확인이 없는 코드 비교를 제품 전체 동작 보존 증거로 확대하지 않는다.
