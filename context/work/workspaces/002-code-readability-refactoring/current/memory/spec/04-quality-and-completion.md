# 품질·완료 판단

완료에는 실제 코드 개선과 동작 보존의 근거가 모두 필요하다. 타입·린트 통과, 줄 수 감소, 함수 분리 개수만으로 가독성 개선을 판정하지 않는다.

- 채택한 범위에서 값·조건·함수의 의도와 책임을 이름·타입·가까운 코드로 설명할 수 있고, 반복되는 해석과 우회가 변경 전보다 줄어든다.
- 의미가 같은 중복은 줄고, 필요한 차이는 숨겨지지 않는다. 줄 수를 줄이기 위해 간접 호출이나 범용 옵션을 늘리지 않는다.
- 관련 입력·실패·취소·재진입의 동작과 기존 데이터 계약을 보존했다는 근거를 변경 위험에 맞게 남긴다. 저위험 표현 수정에 구현을 그대로 복제하는 테스트를 만들지 않는다.
- 전체 후보를 처리·변경 불필요·다른 Work의 동작 수정·보류 중 무엇으로 판단했는지 근거를 남기며 조용히 누락하지 않는다. 중요한 가독성 문제를 그대로 둔 채 후보 분류만 끝낸 것을 완료로 보지 않는다.

실행 전 기준선은 client 타입 오류 3건, server 타입 오류 1건, ESLint/Prettier 호환 오류로 린트 미완료였다는 이전 검사다. 상세 진단과 설치 상태의 한계는 [구성 기록](../../../records/2026-09-10-01-workspace-setup.md)에 있다. 검사를 가능하게 하는 준비는 공통 지원 작업이며 제품 가독성 개선 자체와 구별한다. 기존 실패와 새 회귀를 나눠 보고하며 기존 오류를 숨겨 통과시키지 않는다.

초기 `verify.json`은 client noEmit 타입 검사만 선언한다. 현재 설치에서 TypeScript가 읽은 로컬 소스·설정·생성 선언 파일과 package/lockfile을 evidence로 선택했다. node_modules의 설치 내용, 이후 추가 파일·resolution 변화까지 고정한 재현 환경은 아니다. 실행 직전에 입력 구성을 다시 확인한다. server·schema·UI 변경에는 해당 검사와 필요한 동작 검증을 추가로 고른다. 초기 Verify 하나로 이 Work 전체를 완료 처리하지 않는다.

이번 구성에서 제품 Verify를 실행하지 않았으므로 `status.json`의 receipt·result·finished_at은 null이다. `ready_for_verification`은 현재 schema가 사용하는 미실행 값이다. 가독성 판단·다음 행동·사람의 수락은 machine status와 분리한다.
