# 품질·완료 판단

각 실행 범위의 완료에는 동작 보존 근거와 실제 코드 개선 근거가 모두 필요하다. 테스트 통과는 개선 효과의 증거를 대신하지 않는다. 줄 수·함수 분리 개수·테스트 개수·coverage 숫자만으로 가독성 개선을 판정하지 않는다.

## 동작 보존 확인

리팩토링 전 코드에서 기존 테스트를 활용하고 필요한 테스트를 추가·실행하여 기준 결과를 확인한다. 수정 후에는 같은 테스트와 관찰 조건으로 비교한다. 테스트는 확인된 계약과 결과에 기대값을 두며 구현을 복제하지 않는다. 보존 계약을 깨뜨리는 변경에는 실패하면서 내부 함수 분리나 이름 변경만으로 불필요하게 깨지지 않도록 구성한다.

실패하면 구현과 테스트 중 원인을 확인하고 통과를 위해 기대값부터 바꾸지 않는다. 변경 전 버그나 불명확한 동작을 정답으로 고정하지 않으며 [보존 계약](03-concepts-and-contracts.md)의 경계에 따라 처리한다.

검증 범위는 변경의 영향에 맞게 고른다.

- 단순 이름·주석·저위험 표현은 전후 diff·사용처·관련 타입/린트로 확인할 수 있다. 구현을 따라 쓰는 새 테스트를 만들지 않는다.
- 조건·변환·검증·계산은 결과를 갈라놓는 관련 입력과 경계값으로 확인한다.
- 폼·비동기·저장 후 처리는 관련 상태 변화와 연결된 부작용까지 확인한다.
- 저장·동기화·정리는 관련 데이터와 부작용을 확인할 통합 검증을 선택하고, 중간 실패나 미전송 데이터가 관련되면 그 조건을 포함한다.

mock이나 함수 반환값 확인만으로 실제 연결이나 데이터 보존을 증명했다고 말하지 않는다. 자동화하기 어려운 부분은 재현 조건과 관찰 결과를 남기는 수동 검증을 사용하고 미확인을 밝힌다. 구체적인 사례·도구·실행 방법은 Ticket 또는 실행 범위에서 정한다.

## 개선 효과 확인

수정 전에 무엇을 해석하거나 추적해야 했으며 무엇이 명확해져야 하는지 정하고, 수정 후 그 기준으로 코드를 비교한다. 사후 소감만으로 개선을 주장하지 않는다.

- 값·조건·함수의 실제 의미와 책임을 이름·타입·가까운 코드로 이해할 수 있다.
- 반복 해석·불필요한 우회·함께 맞춰 수정할 위치가 줄어든다.
- 유사 처리의 공통점과 필요한 차이가 읽히고 차이의 이유가 숨겨지지 않는다.
- 간접 호출이나 범용 옵션을 늘려 읽기·수정 부담을 다른 위치로 옮긴 결과를 자동으로 개선으로 보지 않는다.

예를 들어 같은 통화 강조 조건을 두 곳에서 해석해야 했다면, 변경 후 조건의 의미가 정확한 이름으로 드러나고 두 사용처가 그 판단을 함께 쓰는지 확인한다. 이름만 추가하고 더 많은 함수를 따라가게 됐다면 개선 여부를 다시 판단한다.

## 결과와 전체 완료

각 범위에는 실제 실행 조건과 결과, 동작 보존 및 개선 효과의 근거, 기존 실패와 새 회귀의 구분, 남은 문제와 미확인을 남긴다. 부족하면 보완한다.

사용자가 채택한 진행 방식에 따라 개별 Ticket의 결과와 전체 분석 관점의 검토 범위를 함께 관리한다. [기존 후보](../analysis-items.md)와 [추가 조사·후속 범위](../additional-research.md)를 [Ticket](../tickets/index.md)과 연결해 각 관점·후보에서 확인한 코드 범위와 남은 범위를 찾을 수 있게 한다. 한 Ticket의 이름·조건 개선을 해당 관점 전체의 검토 완료로 보지 않는다. 다룬 범위에는 개선 내용과 이유, 변경 없이 유지한 이유, 버그 수정으로 분리한 부분, 보류·미확인을 남긴다. 실행하며 이 연결을 보완하되 전체 후보의 Ticket 배치를 먼저 끝내야 실행할 수 있다는 일괄 선행 조건을 만들지 않는다.

전체 후보를 조용히 누락하지 않으며 채택한 개선을 실제 수행해야 한다. 작은 예시 개선이나 후보 분류만으로 전체 완료가 아니다. 중요한 가독성 문제를 그대로 둔 채 분류만 끝낸 것을 완료로 보지 않는다. 개별 Ticket·검사 통과나 서면 기준의 작성은 전체 목표 달성이나 사람의 수락을 대신하지 않는다.

## 기존 검사와 증명 범위

client 타입 오류 3건, server 타입 오류 1건, ESLint/Prettier 호환 오류로 린트 미완료였다는 것은 이전 검사 결과다. 상세 진단과 설치 상태의 한계는 [구성 기록](../../../records/2026-09-10-01-workspace-setup.md)에 있다. 실행 시 필요한 기준선을 다시 확인한다. 검사를 가능하게 하는 준비는 공통 지원 작업이며 제품 가독성 개선 자체와 구별한다. 기존 오류를 숨겨 통과시키지 않는다.

초기 `verify.json`은 client noEmit 타입 검사만 선언한다. 구성 당시 TypeScript가 읽은 로컬 소스·설정·생성 선언 파일과 package/lockfile을 evidence로 선택했다. node_modules의 설치 내용, 이후 추가 파일·resolution 변화까지 고정한 재현 환경은 아니다. 실행 직전에 입력 구성을 다시 확인한다. server·schema·UI 변경에는 해당 검사와 필요한 동작 검증을 추가로 고른다. 초기 Verify 하나로 이 Work 전체를 완료 처리하지 않는다.

이번 Spec 구체화에서 새 제품 테스트나 Verify를 실행하지 않았다는 Main 보고를 유지한다. 제공된 상태의 `status.json`은 receipt·result·finished_at이 null이고 `ready_for_verification`은 schema의 미실행 값이다. 이 문서 반영으로 Verify receipt나 machine status를 변경하지 않는다. 가독성 판단·다음 행동·사람의 수락은 machine status와 분리한다.
