# 제약·현재 접근·열린 판단

채택된 방향은 코드에 집중하고 리팩토링부터 하며 작은 요소에서 시작하는 것이다. 이름·조건·기본값·변환·로그·타입·작은 함수를 보고 반복 패턴의 근거가 있을 때 필요한 폼·컴포넌트 내부 책임으로 이어간다. 큰 구조를 먼저 설계하거나 모든 중복을 제거하는 목표를 추가하지 않는다. 특정 첫 파일이나 '일정 생성부터 시작'은 채택된 계획이 아니다.

## 작업 단위와 진행 방식

작업 단위는 파일 또는 함수 하나로 고정하지 않고 관련된 개선들을 함께 수행하며 동작 보존과 개선 효과를 확인할 수 있는 작은 코드 범위로 정한다. 이름·조건식·기본값·값 변환·타입·작은 함수·책임 분리는 그 범위를 살펴보는 개선 관점이며 각각이 별도 Ticket을 뜻하지 않는다. 한 Ticket에 관련된 여러 관점이 함께 들어갈 수 있다.

예를 들어 경비 합계 표시는 실제 작업 범위이고, 그 안에서 첫 통화의 이름, 강조·소수 자릿수 조건, 합산·표시 사이의 변환과 기본값, 반복 계산의 작은 함수와 책임을 함께 살핀다. 범위 안에서 바텀 요소부터 보고 필요할 때 함수·책임 정리로 이어가되 모든 관점에서 반드시 수정할 것을 찾지는 않는다. '한 가지 개선 목적'을 하나의 개선 관점만 허용한다는 제한으로 사용하지 않는다.

여러 범위에 걸친 중복이나 계약 문제가 드러나면 근거에 따라 관련 Ticket 경계를 조정하거나 공통 부분을 맡는 Ticket을 추가할 수 있다. 새 개선을 포함하기 전에는 영향을 받는 보존 계약·변경 전후 검사·개선 판단 기준을 보완한다. 개별 범위 수행과 전체 분석 관점의 검토 범위를 연결하는 기준은 [품질·완료 판단](04-quality-and-completion.md)을 따른다. 이 접근을 채택한 원문과 정정 경위는 [합의 기록](../../../records/2026-09-11-01-ticket-boundary-agreement.md)에 있다.

Ticket에 적힌 부분만으로 개선이 충분하지 않다는 근거가 실행 중 드러나면 그 지점에서 문서상 범위를 완료 기준으로 고정하지 않는다. 주변 메서드와 호출 관계를 살펴 남는 이해·수정 부담과 함께 고려할 변경을 분석하고, 사용자가 범위를 판단할 수 있게 제시한다. 이는 관련 변경을 모두 묻지 않고 확대하라는 뜻이 아니며, 공개 동작·오류 계약·버그 수정처럼 결과를 바꾸는 선택은 기존 경계에 따라 사용자 판단과 별도 범위를 확인한다.

1. 현재 문제, 보존할 계약, 개선 기대를 정한다.
2. 영향을 받을 동작과 검증 방법을 고른다.
3. 변경 전 코드에서 기존 테스트를 활용하고 필요한 테스트를 추가·실행하여 기준 결과를 확인한다. 저위험 표현이나 자동화하기 어려운 부분은 [품질 기준](04-quality-and-completion.md)에 따라 검증 방법을 선택한다.
4. 정한 범위를 리팩토링한다.
5. 같은 테스트와 관찰 조건으로 동작 보존을 검증하고, 별도로 사전에 정한 개선 목표에 대해 코드를 비교한다.
6. 부족하면 관련 코드와 남는 부담을 분석해 범위 보완안을 제시하고, 실제 결과와 미확인을 남긴 뒤 다음 범위를 선택한다.

사용자는 변경 전 동작을 먼저 확인하고 수정 후 같은 테스트로 비교한다는 설명에 '맞아 이건 리팩이니까 거기에 맞는 테스트를 구성하는게 맞아보여'라고 동의했다. 상세 테스트 사례와 구현 방법은 Ticket 또는 실행 범위에서 정한다. 내부 구조를 미리 전부 고정하지 않으며 특정 테스트 도구·파일 구성·coverage 수치는 아직 채택하지 않았다. 후보를 다루는 세부 순서는 실행 중 근거로 조정할 수 있다.

## 알려진 경계와 열린 판단

Ticket 06의 네트워크 연결에는 [범위 문서](01-problem-goal-scope.md)에 명시한 사용자 선택이 우선 적용된다. unknown·10초 안내·제한 화면·Router 중앙 차단·debug 표시 분리는 채택한 방향이며 다시 미정으로 되돌리지 않는다. 내부 함수 배치·상태 소비 연결·재확인 동시성은 Main이 기존 코드에 맞춰 구체화한다. 버튼별 네트워크 검사, 별도 cache 관리, 쓰기 예약, 일반 Remote 요청의 별도 결과 추적 시스템은 추가하지 않는다.

같은 연결에 필요한 대상 여행 분기·inactive child의 Local 선조회 정상화는 06에서 수행하고 14가 결과를 재사용한다. Local 원자성, sync engine 실패·재시도, cleanup 보존 조건은 각각 14·15·16의 남은 범위다. 아래 일반적인 003 분리 원칙을 이 합의 범위에 다시 적용해 구현을 나누지 않는다. 정확한 경계와 이유는 [Ticket 06](../tickets/06-app-startup-lifecycle.md)과 [합의 기록](../../../records/2026-09-16-01-network-policy-and-implementation-boundaries.md)에 있다.

앱 준비의 DB·auth 실패 정책과 선택 적용, pending cleanup 실행·세션 종료 연결은 Ticket 06에서 수행한다. 사용자가 앱 전체 준비를 `application`에 분리하도록 선택했으며, 이는 범용 초기화 프레임워크나 다른 feature의 일괄 이동을 뜻하지 않는다. 추가 필수 준비는 `AppInitialization`, 화면 이동은 `AppNavigation`, 로그인 후 작업 연결은 `AuthenticatedEffects`, 기능별 규칙은 해당 Owner에 둔다. 검증할 시나리오를 구현 전에 작성하고 실제 기대 동작과의 실패를 확인한 뒤 구현하는 접근을 이 범위에 적용했다. 자세한 이유와 한계는 [기록](../../../records/2026-09-18-02-app-initialization-and-style.md)에 있다.

트랜잭션과 여행별 미전송 작업 조회는 분리 실험에서 결함이 재현됐다고 기존 자료에 기록되어 있다. 큐 상태 보존, 오래된 좌표를 사용하는 경로 계산, 서버 소유권·응답 계약과 동기화 실패는 별도의 동작 확인·수정 범위다. Ticket 06의 비활성 Local 선조회 정상화와 아래 명시적으로 채택한 startup 실패 처리는 해당 연결 안에서 수행한다. 이 부근의 표현을 정리할 때 결함을 더 숨기거나 재현 근거를 없애지 않는다. 버그 전체 완료는 이 Work의 일괄 선행 조건이 아니며 직접 걸리는 부분만 연결한다.

기존 분석의 실행 검증 필요 항목은 장애가 실제 발생했다는 사실로 승격하지 않는다. 폼의 취소·재진입, 활성화 완료·지도 준비·경로 준비, 오류 표시의 기대 UX는 아직 선택이 필요한 부분이 있다. 변경 전 버그나 불명확한 동작을 보존 테스트의 정답으로 고정하지 않는다. 공통 기준을 정하기 위한 추가 선택은 남아 있지 않지만, 실행 범위에서 실제 결과를 바꾸는 선택이 드러나면 사용자에게 확인한다.

## 자료와 작업 경계

Workspace 구성 당시 기준은 `refactor/codebase`, commit `aa2314cd9c1400420ea8d22f5ea39f9d76ceca21`였다. 기존 분석의 코드 기준은 `b4ed41f6e4bbae26fd45827b3b9063097a2c1ea4`다. 이는 과거 기준이며 현재 HEAD를 뜻하지 않는다. Main이 읽은 보존 분석의 관찰은 2026-09-06 기준으로 전달됐으며 전 파일 정독이나 앱 전체 실행의 증거가 아니다. 후보 채택 시 현재 코드를 다시 확인한다.

원래 분석 경로는 과거 출처이며 영구 파일 보존 제약이나 실행 의존성이 아니다. [Workspace 안의 분석 보존본](../../../source/codebase-analysis/README.md)과 [출처·무결성 설명](../../../source/index.md)을 기준으로 읽는다. 원문 사본을 유지하며 읽기용 문서는 링크 위치와 사용자가 요청한 배경 표현만 다듬었다는 기존 보존 기록을 따른다. 편집 내역은 출처 정보에 남기고 기술 관찰·확인 수준을 유지한다. 원래 경로의 향후 삭제 계획은 있었으나 구성·보존 당시에는 삭제하지 않았다.

기존 미커밋 변경을 보존하고 사용자 요청 없이 stage·commit·push하지 않는다. 다른 작업의 하네스·hook 변경을 이 제품 Work의 결과로 포함하지 않는다.

초기 생성 요청은 두 Workspace 문서 구성이었으며 당시 active 기본값과 session binding을 변경하지 않았다. 이는 생성 당시 사실이며 이후 작업을 막는 고정 제약이 아니다. 현재 작업 단계는 [state](../../state/index.md)가 소유한다. 실행·유지 연결은 [Work 지침](../../../../../AGENTS.md)과 [session binding 계약](../../../../../harness/maintain/SESSION-BINDING-AND-LIFECYCLE.md)에 따라 명시적으로 선택한 Workspace에만 적용한다.
