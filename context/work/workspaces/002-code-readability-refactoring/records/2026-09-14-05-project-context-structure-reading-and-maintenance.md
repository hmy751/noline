# Project context 구성·읽기·갱신 방향 합의

날짜: 2026-09-14

이 기록은 Project context 문서를 검토하며 사용자와 Main이 합의한 구성 방향, 그 이유와 정정 과정, 아직 검증할 판단을 보존한다. 후속 작업자는 이 문서에서 합의의 의미를 복원하고 실제 관리 지침·읽기 경로·스킬의 변경안을 만들 수 있어야 한다. 이 기록 자체가 Project 관리 계약을 대체하거나, 제안한 문서·스킬이 이미 구현됐음을 뜻하지 않는다.

기록 위치는 `002-code-readability-refactoring`이지만 이번 논의의 대상은 **Project context의 구성 자체**다. 002의 완료된 Ticket 01–05는 문제를 발견한 계기이자 이후 적용을 확인할 사례다. 미완료 Ticket 06 이후의 실행이나 제품 전체 문서 개편을 이번 논의에 포함하지 않는다.

## 다시 논의한 이유와 유지할 전제

앞선 반영은 002의 작업 자료와 records를 주 근거로, 관련된 기존 non-archive `.claude` 자료를 참고해 Project로 현재 의미의 Owner를 옮기는 작업이었다. 사용자는 주제별 분리와 기록 같은 본문을 개선한 결과는 인정했지만, `current`에 세부 주제가 많이 생기고 다음 개발에서 읽을 공통 계약과 적용 설명의 관계가 약하다고 느꼈다. `schedule-api`를 독립된 구현 설명으로 접한 뒤, API에 관한 계약과 가이드 안에 Schedule의 구체적인 내용이 이어지는 모습을 예로 들었다.

이 문제를 파일 수만 줄이는 요청으로 해석하지 않는다. 원하는 것은 관련 작업에서 제품 의미와 계약·판단 이유·구체적인 적용을 이해하고 감안할 수 있는 본문이다. 조사한 Ticket의 결과를 잘 나눠 보존하는 것과, 다음 작업에서 필요한 설명을 구성하는 것은 별도로 확인해야 한다.

사용자가 지정한 초기 연구 문서 세 편을 Main이 직접 읽었다. 그 문서들은 작업 연속성뿐 아니라 제품과 구조를 다시 판단하는 연속성이 필요하며, 정보의 보존 기간·읽히는 조건·현재 권위를 구별해야 한다는 배경을 제공했다. 초기 문구를 현재 지침보다 우선하는 새 지시로 적용하지 않았다.

사용자의 다음 정정이 이번 구성의 전제다. 발췌는 현재 대화에서 직접 확인한 사용자 원문이며, 앞뒤의 반복 설명만 생략했다.

> "초기설계에서 새 디랙터리 만들필요 없단건 그냥 유연하게 하려고 했는데 아예 폴더를 안 만들어서 강제한거야"

초기 연구는 책임을 유연하게 배치하려고 세 폴더를 필수로 하지 않았지만, 실제로 폴더를 구성하지 않는 결과가 나와 이후 물리 경계를 명시적으로 요구했다는 설명이다. 따라서 `common/current/guidance` 세 폴더는 의도된 탐색·관리 경계로 유지한다. 초기 문구와 현재 폴더 구조의 차이 자체를 결함이나 되돌릴 근거로 삼지 않는다.

> "가이던스를 일종의 런북이랑 유사한 층위라고 생각하고 만들긴 한거였어"

Guidance는 처음부터 관련 작업에서 구체적으로 참고하는 가이드에 가까웠다. Main이 runbook을 수행 순서로만 설명해 guidance와 별개로 등장시킨 해석은 좁았다. 사용자가 기대한 가이드는 계약·판단·적용 방법을 포함하며, 필요하면 순서도 설명한다. 다만 모든 runbook과 guidance를 반드시 하나로 합치거나 같은 양식으로 만들기로 한 것은 아니다.

> "지금 002 보단 이 구성에 관한게 포인트라"

Main은 이후 설명과 검증 대상을 Project 구성의 일반 기준으로 잡는다. 002의 자료를 정리하는 최적화가 기준 자체를 대신하지 않는다.

## 채택한 문서 단위: 관련 작업이 읽을 온전한 주제 본문

관련 작업에서 주제를 이해하고 판단할 수 있는 본문을 먼저 구성하고, 실제 읽기·재사용·관리 필요에 따라 나눈다. Ticket, Entity, 조사 파일이나 검증 묶음마다 Project 파일을 자동 생성하지 않는다. 좁은 주제라는 이유만으로 문서의 가치가 낮은 것도 아니다. 통화의 의미처럼 다음 작업이 반복해서 물을 질문이 분명하면 독립 문서가 적합할 수 있다.

공통 계약과 이유, 기능별 구체적인 적용까지 본문에서 설명한다. 예를 들어 API 가이드는 추상적인 schema 원칙만 제공하지 않고 Schedule과 Expense에서 무엇을 지키고 어떻게 적용하는지 알 수 있어야 한다. 코드·원문·검증 링크는 상세를 확인하는 경로이며, 문서가 맡은 의미를 링크를 따라 조립하도록 맡기지 않는다.

서로 다른 책임을 구분한다는 이유로 모든 문장이나 section을 별도 파일로 나누지 않는다. 한 문서는 주된 질문을 중심으로 구성하고 이해에 필요한 다른 층의 전제를 짧게 설명할 수 있다. 의미의 기준 본문은 명확히 두되, 필요한 전제의 재서술까지 모두 중복으로 금지하지 않는다.

### 사용자가 방향을 수용한 API 문서 예시

Main은 가상의 「API 계약과 변경 가이드」를 다음 흐름으로 제시했다.

```text
API 계약과 변경 가이드

1. 요청·응답의 공통 계약
   schema, 데이터 변환, 검증, 오류 전달의 책임과 이유

2. Schedule에 적용되는 구체적인 계약
   날짜 표현, 일반 조회와 동기화의 삭제 처리 차이
   여러 응답 경로에서 함께 지킬 사항

3. Expense에 적용되는 구체적인 계약
   요청 검증과 응답 반환, 날짜 표현의 열린 판단

4. 관련 코드를 변경할 때의 판단
   함께 살펴야 할 연결과 변경 결과를 확인할 검사
```

Schedule 절은 날짜를 API에서 시간대가 포함된 ISO 문자열로 표현하고, 일정 endpoint뿐 아니라 여행 활성화·동기화 응답에서도 같은 표현을 지켜야 한다는 관계를 설명한다. 일반 조회는 삭제된 일정을 제외하지만 동기화는 다른 기기에 삭제 사실을 전달해야 하므로 같은 삭제 필터를 기계적으로 재사용할 수 없다는 이유와 적용 차이까지 본문에 둔다. 이 예시는 API 관련 작업에서 읽을 설명의 구체성을 보여 주며 새로운 제품 계약을 채택하거나 API 전체를 검증한 결과가 아니다.

사용자는 다음과 같이 방향을 수용했다.

> "맞아 뭐 이런느낌 좋은 것 같아 뭐 가이드 형태는 런북이나 가이던스에 맞춰서 한는게 좋고 뭐 아무튼 전반적으로 니 얘기 괜찮아보여"

따라서 위 목차와 제목은 고정 양식이나 확정 경로가 아니다. 실제 runbook·guidance의 목적에 맞게 구성한다. 함께 읽기 좋은 분량이면 한 문서로 두고, Schedule과 Expense를 각각 다룰 때 무관한 상세를 과도하게 읽게 되거나 독립적인 갱신 책임이 생기면 공통 본문과 하위 문서로 나눈다. 큰 API 문서 하나로 모든 설명을 통합하기로 한 것도 아니다.

## `common`과 `guidance`의 본문 소유 범위

`common`은 제품·데이터·시스템의 의미와 핵심 제약을 소유한다. Noline을 어떤 제품과 시스템으로 이해해야 하는지를 설명하며, 기술적인 내용도 그 의미나 핵심 제약이면 포함할 수 있다.

`guidance`는 관련 작업에서 적용할 구체적인 개발 계약과 판단·적용·검증 방법을 소유한다. 새 기능 개발뿐 아니라 관련 수정·리팩터링·문제 조사에서도 선택해 읽을 수 있다. 단순 조언이나 수행 순서에 한정하지 않으며, 여러 API가 함께 지킬 개발 계약도 API 가이드의 본문이 될 수 있다.

두 층 모두 상세한 설명과 지켜야 할 계약을 가질 수 있다. 추상적인 것은 `common`, 상세한 것은 `guidance`라는 구분이나, 여러 곳에 공통으로 쓰이는 규칙은 전부 `common`으로 올리는 방식은 채택하지 않는다. 제품 의미와 그 의미를 구현·변경하는 작업 기준이 각각 무엇을 소유하는지로 판단한다.

Schedule 삭제를 예로 들면, 삭제된 일정의 일반 이용과 기기 간 삭제 전파가 어떤 관계인지가 제품·데이터 의미다. API 가이드는 그 전제를 짧게 설명하면서 일반 조회와 sync에서 어떤 조건을 달리 적용하고 사용자 범위와 검증을 어떻게 다룰지 이어서 설명한다. 핵심 의미를 바꾸는 기준 본문과 그 의미를 실제 작업에 적용하는 본문의 관계를 명확히 한다.

모든 주제에 `common/current/guidance` 문서를 하나씩 만들지 않는다. 통화는 `common` 본문만으로 충분할 수 있고 API는 `guidance`를 중심으로 구성할 수 있다. 실제 문서 배치는 후속 구성에서 확인한다.

## `current`의 필요성과 관리비용: 남겨 둔 판단

사용자는 Project 공통 참고 문서가 작업한 주제마다 늘어나는 부담과, 관련 코드를 어차피 확인하는데 현재 구현 설명까지 별도로 유지해야 하는지를 반복해서 물었다. 문서 수가 이미 과도하다는 확정 판단이나 `current`를 없애라는 요청은 아니었다.

Main의 처음 설명은 현재 구현·지원·검증 상태를 제공하면 코드 탐색을 줄일 수 있다는 것이었다. 그러나 관련 가이드도 현재 구조와 적용 방법을 설명할 수 있고 코드도 직접 확인해야 하므로, 조사 비용 절약만으로 독립 `current` 본문을 정당화하기는 부족하다고 판단을 좁혔다. 저장 용량의 여러 구현 관계가 유용하다는 사실도 해당 가이드가 그 관계를 온전히 설명할 수 있다면 별도 `current` 문서의 필요성을 곧바로 증명하지 않는다.

검증할 가치가 있는 후보 정보는 다음과 같다.

- **현재 구현을 받아들일 지위와 근거:** 채택한 기준인지, 임시 상태인지, 알려진 불일치인지, 아직 선택하지 않은 결과인지. 코드에서 동작을 읽는 것과 그 지위를 확정하는 것은 다르다.
- **실제 적용·지원 범위:** 채택한 구조나 개발 방식이 어디까지 적용됐고 어떤 영역은 아직 같은 상태가 아닌지. 완성된 구조나 지원 상태도 후보이며 문제 목록으로만 제한하지 않는다.
- **다음 판단을 바꾸는 확인 범위와 제약:** 대역으로 확인한 경계를 실제 기기나 외부 서비스까지 검증한 것으로 받아들이지 않도록 필요한 현재 한계. 당시 검사 과정 전체나 매 실행 결과를 복제하는 것과 구별한다.

이 후보들이 모두 `current`에 들어가야 한다고 합의한 것은 아니다. Expense 날짜의 제품 의미가 미정이라는 논의는 도메인 본문에서 다룰 수 있고, 현재 적용 차이 몇 문단이 API 가이드에서 충분히 설명된다면 별도 파일은 불필요할 수 있다. 미정·불확실·자주 변경된다는 속성만으로 분류하지 않는다.

요청 인자, 함수의 세부 반환 흐름, 정확한 dependency 버전, 당시 테스트 케이스 수처럼 코드·설정·기록에서 쉽게 확인할 수 있는 사실은 추가 관리의 효용을 따져야 한다. 특정 버전 제약처럼 다음 판단을 실제로 바꾸는 경우까지 일괄 생략하지 않는다. 기준이 바뀌어도 이유를 잃지 않아야 하는 선택은 decision·record와의 관계로 다룬다.

Main은 별도 관리 필요가 확인된 현재 상태에 한정하는 보수적인 방향을 추천했다. 사용자는 그 성격을 짚으며 구체적인 적용으로 검증하는 방향을 받아들였다. **`current`의 적정 크기, 편입 기준과 기존 문서의 통합·축소 범위는 아직 확정되지 않았다.** `current`를 제거하거나 모든 주제에서 작은 현황 문서만 남기기로 결정하지 않았으며, 실제 효과도 아직 검증하지 않았다.

## 읽기는 관련 주제에서 시작한다

세 폴더는 책임·탐색·관리 경계로 유지하면서, 일반 진입점에서는 관련 작업이나 주제로 시작할 수 있게 한다. Project README에서 주요 주제와 시작 본문을 찾고, 각 본문은 어떤 작업에서 읽을지 밝힌다. 사용자가 먼저 작업을 세 층으로 분류해야만 내용을 찾을 수 있게 하지 않는다.

예를 들어 Schedule 응답 변경은 API 가이드에서 공통 계약과 구체적인 적용을 이해하며 시작한다. 날짜의 제품 의미까지 바꿀 필요가 있을 때 관련 `common`을, 현재 적용 차이가 판단에 영향을 줄 때 관련 `current`를 선택한다. 추가 링크에는 언제 무엇 때문에 읽어야 하는지 설명한다.

Project의 공통 참고는 모든 작업의 기본 입력과 같은 뜻이 아니다. 관련 자료 전체를 항상 읽도록 묶지 않고, 읽지 않은 자료도 진입점에서 필요한 위치를 찾을 수 있게 한다. 가이드 본문은 자기 범위를 충분히 설명해야 하며, 이 선택적 읽기가 링크만 남기는 이유가 되지는 않는다.

## 쓰기는 바뀐 의미와 실제 영향을 따른다

바뀐 의미를 소유한 기준 본문을 먼저 갱신하고, 그 변화 때문에 설명·적용·판단 또는 읽기 경로가 달라지는 문서만 함께 맞춘다. 링크로 연결됐다는 사실만으로 모든 문서를 일괄 갱신하지 않는다.

논의에서 사용한 변경 예시는 다음과 같다.

- Schedule 내부 helper만 교체했다면 실제 구현 위치나 방식을 설명한 부분을 확인한다. 제품 의미까지 변경한 것으로 다루지 않는다.
- API 응답 처리 계약을 바꿨다면 API 가이드의 공통 설명과 영향을 받는 기능별 적용을 함께 맞춘다.
- 경비 날짜의 제품 의미를 정했다면 `common`의 기준과 관련 적용 가이드를 갱신한다. 구현이 아직 따라오지 못한 차이가 있다면 필요한 현재 상태도 연결한다.

상세 기준의 Owner는 하나로 두고, 다른 본문은 이해에 필요한 전제만 짧게 재서술한다. 짧은 설명도 변경된 의미에 영향을 받으면 갱신 대상이다. 같은 내용을 길게 복제해 독립적으로 유지할 부담을 만들지 않는다. 과거 record의 당시 판단을 현재 답으로 덮어쓰지 않으며, 실제 경로·책임 변경의 live consumer 영향은 기존 관리 계약과 함께 확인한다.

## 추가 요청: 읽기용 스킬과 기준 reference

이번 기록 요청에서 사용자는 쓰기 시점의 기존 장치뿐 아니라 읽기 시점의 스킬을 구성하고, 이를 뒷받침하는 reference도 마련하고 싶다고 명시했다.

> "쓰는건 메인터넌스 파일과 update-project-context 스킬을 자연스레 수정할것 같고 읽기에 대한 스킬도 하나 구성하면 좋겠어"

> "레퍼런스도 하나 잘 만들면 좋겠어 뭐 다양하고 그렇다면 spec-and-tickets처럼 갈수도 있는거고"

쓰기 쪽은 [Project 관리 계약](../../../../project/MAINTENANCE.md)과 [update-project-context](../../../../../.claude/skills/update-project-context/SKILL.md)를 이번 방향에 맞게 수정하는 후속 작업으로 연결한다. 읽기 쪽은 관련 주제와 필요한 본문을 선택해 실제 작업에서 이해·적용하게 돕는 스킬을 구성할 방향이다. 스킬 이름, 구체적인 발동 조건, 자동·명시 호출 여부, Recover와의 접점 및 수행 범위는 아직 설계하지 않았다.

Reference는 구성·읽기·쓰기의 판단 근거를 설명하는 기준 문서로 마련할 방향이다. 내용과 책임이 다양해 별도 관리가 적합하면 [Spec과 Ticket 운영 기준](../../spec-and-tickets/README.md)처럼 진입 문서와 하위 기준 문서들로 구성할 수 있다. 이는 그 폴더의 목차·파일 수·스킬 관계를 그대로 복제하라는 결정이 아니다. Reference의 실제 위치, 단일 문서 또는 디렉터리 여부, Project README·MAINTENANCE와의 소유 관계는 후속 설계에서 정한다. 전역 reference로 만들기로 결정한 것도 아니다.

기존 foundation에서 유지한 전제는 실제 의미와 관리 기준을 문서가 소유하고, 스킬은 이를 읽어 적용하는 교체 가능한 실행 장치라는 것이다. 새 읽기 스킬이나 쓰기 스킬에만 구성 의미와 권위 규칙이 남지 않게 한다. 이번 사용자의 추가 요청으로 읽기 경로 설계는 문서 routing뿐 아니라 스킬의 실제 사용까지 확인할 대상으로 보강됐다.

## 후속 작업과 아직 반영하지 않은 것

다음 작업은 기존 지침과 이번 합의의 구체적인 변경안을 대조하는 것이다. 구성·본문 소유·파일 분리·현재 상태 편입의 기준과 reference의 책임을 잡고, 읽기 스킬 및 기존 쓰기 스킬이 이를 어떻게 선택·적용할지 연결한다. 필요한 경우 대표 주제를 구성하는 동안 이 배치를 다시 보완한다.

대표 주제에서는 최소한 다음을 확인한다.

- 관련 작업을 어디서 시작할지 바로 찾을 수 있는가.
- 선택한 본문에서 계약·이유·기능별 적용을 이해한 뒤 코드를 확인할 수 있는가.
- 가이드와 코드만으로 충분한 부분과 별도 현재 상태가 필요한 부분을 구별할 수 있는가.
- 기준 하나를 바꿀 때 함께 갱신할 본문과 이유가 납득 가능한가.
- 선택한 스킬이 필요한 맥락을 실제로 읽고 적용하면서도 전체 문서의 자동 입력이나 기준의 중복 소유를 만들지 않는가.

이는 후속 확인 방향이며 새로운 고정 검증 절차나 이미 통과한 결과가 아니다. 확인된 기준을 실제 지침과 스킬에 반영한 뒤 002의 완료 범위에도 적용할 수 있다. 002의 현재 문서 배치는 아직 이번 방향으로 재구성하지 않았다. 앞서 만든 Owner 이동 지침 커밋 `26350d6`은 이번 추가 합의의 반영 완료를 뜻하지 않는다.

사용자의 이번 실행 요청은 종합 내용을 records에 남기는 것이다. 이 기록 작성에서는 새 날짜별 record와 기록 색인만 변경한다. Project 본문·관리 지침·스킬·reference, Workspace Spec·Ticket·state와 machine 설정을 함께 수정하거나 commit하지 않는다.
