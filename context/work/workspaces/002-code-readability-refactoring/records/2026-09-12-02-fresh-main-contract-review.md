# Fresh Main 기준의 Ticket 운영 문구 검토

날짜: 2026-09-12
Workspace: `002-code-readability-refactoring`

이 기록은 Spec 목표가 Ticket 분해·실행·완료 과정에서 작은 수정으로 축소되는 문제에 대해, 현재 대화를 모르는 새 Main도 적용할 수 있어야 한다는 사용자 기준과 제3 reviewer의 지적, 수정한 공통 운영 문구 후보 및 가상 사례 검토 결과를 보존한다.

## 사용자가 요구한 독립성

사용자는 현재 Main이 대화 맥락을 알기 때문에 만든 보완안만으로는 부족하다고 지적했다. 변경된 규칙은 이 상황을 전달받지 않은 새 session의 Main도 실제 목표에 맞는 범위와 깊이를 판단할 수 있어야 한다. 사용자가 `프로덕션 수준` 같은 표현을 사용한 것은 부족한 품질과 깊이를 전달하기 위한 예시이며, 그 표현을 규칙에 추가하는 것 자체가 해결책이라는 뜻은 아니다.

사용자는 이 관점에서 제3 reviewer에게 보완안을 검토하도록 요청했다.

## reviewer 지적과 수정 방향

Main의 보고에 따르면 reviewer는 앞선 질문인 “적힌 그대로 완료해도 핵심 문제가 남는가” 역시 현재 Main의 문제 정의에 의존한다고 판단했다. 새 Main이 핵심 문제를 중복 한 곳처럼 작게 정의하면 얕은 수정이 통과하고, 큰 구조만 핵심으로 보면 사소한 문제들을 남겨도 통과할 수 있다.

Main은 이 지적을 받아들여 문구의 중심을 특정한 `핵심 문제`를 추측하는 데서 **맡은 코드 범위 자체에 Spec의 관련 품질 기준을 적용해 검토하는 책임**으로 바꿨다. 포괄적인 개선과 명시적인 국소 요청을 구별하고, 분석의 대표 위치를 전체 작업 범위로 오인하지 않으며, 확인 범위와 미확인 범위를 드러내는 것이 주요 보완점이다.

## 리뷰 반영 문구 후보

아래 문구는 임시 파일 `/private/tmp/noline-ticket-contract-20260912/candidate-reviewed.md`에서 직접 확인한 검토안이다. 확인 당시 SHA-256은 `8b70bd4dcdd1df8334077f5db0ad70e13207ff4e20271a94be76dc367a0e4758`이다. 임시 파일에 의존하지 않도록 후보 본문을 이 기록에 보존한다.

### 목표에 맞는 작업 범위를 정하기

Main은 사용자가 맡긴 결과를 실제로 이루는 데 필요한 일을 찾아 Ticket으로 구성한다. 작업 이름이나 먼저 눈에 띈 수정거리만으로 목표의 깊이와 범위를 정하지 않는다. Spec에서 기대하는 결과·보존할 계약·명시적 제외 범위를 읽고, 관련 원자료와 현재 구현을 대조해 지금 무엇이 부족한지 확인한다.

코드 개선에서는 해당 코드가 실제로 맡는 일과 사용 관계를 먼저 이해한다. 그 일을 읽거나 수정할 때 어떤 값·조건·실패·상태를 함께 추적해야 하는지, 같은 의미를 바꾸려면 어느 위치들을 함께 맞춰야 하는지 살펴 개선할 문제를 정한다. 함수명·파일 경계를 따라 임의로 끊지 말고, 확인된 부담을 만드는 관계를 따라 필요한 코드를 확인한다. 관련 책임이 이미 명확하거나 각 처리의 차이가 필요한 경우에는 그 근거로 현재 구조를 유지할 수 있다.

전반적인 개선을 맡았다면 분석의 대표 위치를 작업 대상의 전부로 간주하지 않는다. 이번에 검토하는 코드 범위의 주요 처리 흐름에 관련 품질 기준을 적용하고, 발견한 문제를 판단하는 데 필요한 사용처와 관련 구현을 확인한다. 확인한 범위와 아직 살피지 않은 범위는 구별한다. 사용자가 특정 오탈자·표현·국소 결함만 지정했다면 그 요청을 완료하는 데 필요한 범위를 따른다. 코드가 가까이 있다는 이유만으로 별도 문제를 같은 작업에 넣지 않는다.

Ticket에는 이번 실행이 해소할 문제와 그 문제를 충분히 다뤘다고 볼 결과를 먼저 적고, 수정 방법과 파일 배치는 이를 이루기 위한 현재 접근으로 둔다. 완료 조건을 이미 고른 수정 목록에 맞춰 낮추지 않는다. 여러 곳에 걸친 같은 책임을 일부 위치에서만 정리하려면 부분 개선으로도 얻을 결과, 남겨도 그 결과가 성립하는 이유, 필요한 후속 작업을 설명한다. 후속 작업이 있다는 말만으로 현재 결과의 부족을 정당화하지 않는다.

작업 크기는 관련된 결과를 확인한 뒤 조절한다. 단순한 정리는 함께 검토·검증할 수 있는 범위로 묶고, 규모가 크면 각 단계에서 실제로 얻을 결과와 남은 책임이 이어지도록 나눈다. 전체 Ticket을 먼저 확정해야만 시작할 필요는 없다.

### Ticket을 실행하기

실행자는 Ticket이 맡은 결과를 그 코드의 실제 사용 조건과 Spec의 품질 기준에 맞게 구현하고 검증한다. `가독성`, `일관성`, `프로덕션 수준` 같은 품질 표현은 그 작업의 역할·계약·사용 조건에 비춰 구체화한다. 코드 개선에서는 표현 정리와 함께 해당 목표에 필요한 처리 흐름, 책임, 실패와 상태 연결을 살피고, 기능 구현에서는 필요한 실제 사용 경로가 이어지는지 확인한다. 모든 작업에 같은 품질 항목을 일괄 적용하거나 새 요구사항을 추가하는 뜻은 아니다.

Ticket의 문제 정의와 접근은 시작할 때의 판단이며, 작업 중 확인한 근거로 발전시킨다. 조사할 관계를 수정 허용 파일에 한정하지 않는다. 허용된 범위에서 목표를 더 잘 이루는 세부 설계·구현은 실행자가 판단해 진행한다. Ticket에 적힌 수정만으로 목적을 이루기 어렵다면 관련 근거, 남는 문제와 필요한 범위 조정을 제시한다. 사용자에게 모든 기술 선택을 다시 묻거나, 범위 밖이라고 보고하는 것만으로 맡은 문제를 닫지 않는다. 공개 동작·오류 계약·명시적 제외 범위를 바꿔야 하는 선택은 그 차이를 설명하고 기존 권한 경계를 따른다.

### 완료를 판단하기

실행자는 수정 전의 실제 문제와 수정 후 결과를 비교해 무엇이 달라졌는지 판단한다. 테스트 통과나 수정 목록 이행과 함께, 맡았던 이해·수정 부담 또는 필요한 실제 동작이 해결됐는지 확인한다. 맡은 범위에 관련 품질 기준을 적용해 살폈고, 확인한 문제를 개선하거나 유지·후속으로 판단한 근거가 있을 때 완료를 판단한다. 결과를 바꿀 수 있는 미확인이 남아 있으면 완료의 한계로 밝힌다. 부족하면 허용된 범위에서 보완하고, 범위나 기대 결과를 다시 정해야 하면 근거와 제안을 반환한다. 보고에는 결론을 뒷받침하는 실제 코드·동작·검증 근거와 남은 문제를 남긴다.

전체 Main은 Ticket 결과를 Spec의 목표와 연결해 다음 일을 정한다. 폭넓은 개선 작업에서는 살펴본 범위의 결과와 유지 이유, 분리·보류한 문제와 아직 살피지 않은 범위를 기존 후보·Ticket·state에서 찾을 수 있게 한다. 대표 위치를 개선한 것, 후보를 나열한 것, Ticket 수를 소진한 것을 전체 완료로 취급하지 않는다. 매 Ticket마다 제품 전체를 다시 조사하는 절차는 요구하지 않는다.

## fresh-Main 계획 검토

Main은 원래 대화를 전달하지 않은 새 Main에게 위 문구와 가상 코드만 제공해 계획을 작성하게 했다고 보고했다.

- 주문 계산 전반 개선에서는 변수명 변경에 머무르지 않고 두 사용처의 중복 정책을 발견했다. 저장 금액을 표시하는 영수증은 다른 책임으로 구별하고 필요한 범위 조정을 제안했다.
- 오탈자 하나 수정에서는 문자열 한 곳만 고치고 주변 구조를 유지했다.
- CSV 미리보기 전반 개선에서는 최초 후보인 로그·주석 삭제에 더해 조건 흐름, 변수 의미와 결과 집계를 정리했으며 불필요한 함수 분리는 요구하지 않았다.

이 결과는 포괄적으로 맡긴 개선에서는 관련 문제를 더 찾고 명시적 국소 요청에서는 적절히 멈추는 계획을 새 Main이 만들었다는 Main의 보고다. reviewer 원문과 fresh-Main의 전체 출력은 이번 입력에 포함되지 않았으므로 독립적인 실행 결과를 직접 재검증한 것은 아니다.

## 현재 한계와 적용 상태

후보는 기존 공통 `SPEC-AND-TICKETS.md`의 분해·실행·완료 부분에 통합하기 위한 검토안이며 아직 운영 규칙에 반영되지 않았다. 사용자가 문구를 채택했다는 결정도 없다.

가상 코드로 계획을 작성한 결과는 문구가 범위 판단을 유도할 가능성을 보여 주지만, 실제 프로젝트에서 Ticket 작성·구현·완료 판단까지 반복적으로 같은 결과를 내는지 입증하지 않는다. 채택한다면 적절한 Owner에서 공통 계약을 갱신한 뒤 Ticket 03·05와 아직 실행하지 않은 후보를 대상으로 실제 분해와 실행 결과를 확인해야 한다.
