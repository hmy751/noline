# 일정 온라인 복귀 — Query 기준과 추가 조회 허용 결정

## 선택한 방향과 적용 범위

비활성 여행의 offline/unknown 제한은 유지한다. 실제 연결이 돌아와 접근 정책이 허용되면 같은 계정·여행의 기존 데이터를 먼저 표시하고, 화면을 재조회 성공이나 sync 종료까지 기다리게 하지 않는다. 기존 Query의 캐시·갱신 기준을 활용하고 sync·저장·삭제의 갱신이 겹쳐 추가 조회가 발생하는 것은 허용한다. 실제 변경이 화면에 반영되는 책임은 유지한다.

이번 결정은 우선 Ticket 06의 2-A 일정 화면을 개선할 기준이다. 제품 코드는 아직 바꾸지 않았으며 작업 트리에 이전 복구 구현이 남아 있다. 2-B 경비 연결과 2-C 토스트, 커밋·완료 수락은 별도다. 현재 유효 정책·실행 정의는 [Ticket 06](../current/memory/tickets/06-app-startup-lifecycle.md), 전체 다음 행동은 [state](../current/state/index.md)가 소유한다.

## 무엇을 다시 판단했는가

[앞선 논의 기록](2026-09-29-01-schedule-recovery-responsibilities-discussion.md)은 재조회 성공 뒤 내용을 복구한다는 기존 정책과 단순화 후보를 보존한다. 이후 사용자는 인터넷이 잠시 끊겼다고 이미 보던 데이터 자체가 갑자기 잘못되는 것은 아니라며, 예외 처리를 계속 붙이기보다 기존 정책·시스템을 함께 보고 적절한 복잡도를 결정하자고 요청했다.

Main의 앞선 설명에는 커밋된 동작, 미커밋 구현, 새 제안이 섞여 있었다. HEAD `0c1b17d`와 변경 내용을 대조한 결과, offline/unknown의 제한 안내는 `be2f5b9`부터 존재했고 HEAD는 제한이 풀리면 기존 Query 데이터를 표시했다. 미커밋 2-A가 추가한 것은 새 조회 성공까지 표시를 기다리는 절차와 복구 요청 추적이었다. 기존 제한 UI를 다시 구현하는 작업으로 이해하면 안 된다.

또 Main이 ‘sync 무효화가 있으니 자연스럽게 갱신된다’고 설명한 것만으로 전체 경로가 해결되지는 않았다. 사용자는 일부 Query 자동 갱신 옵션을 sync 때문에 꺼 두었을 가능성을 지적했고, 기존 방향을 다듬을지 다른 방법을 쓸지 개선 리뷰를 요청했다. 요청 횟수가 겹치는 것 자체보다 화면 대기·실제 변경 누락·책임 간 의존을 구별하게 된 것이 이번 결정의 핵심이다.

## 채택 근거가 된 대화

출처는 2026-09-29의 Ticket 06 논의와 기록 요청이다. 아래는 선택의 범위를 재검토할 수 있도록 보존한 최소 원문이다.

사용자는 구현 방법의 재검토를 요청했다.

> “그럼 여기서 정해야할게 sync와 자꾸 QUery 와 겹치는게 문제인데 기존 방향을 유지하면서 다듬는게 맞을지 아니면 절절한 복잡도로 또 다른 방법이 있는지 생각해보자”
>
> “별도 검증 말고 끌어올릴 개선 리뷰어 맡겨봐 어떻게 해야할지”

개선 리뷰와 Main의 추천 뒤 사용자는 다음과 같이 이해를 확인했다.

> “그럼 Query동작은 유지하고 근데 5분 지나거나 자연스러운 갱신이 마침 걸린경우는 어쩔수 없이 추가 조회를 허용하고 이해한게 맞아?”

Main은 “5분이 지났다고 즉시 자동 조회하는 것은 아닙니다”라고 설명하고, 조회를 판단하는 계기에 유효기간을 확인하며 sync가 뒤에 데이터를 변경해 다시 조회하는 것은 허용한다고 답했다. 추가 조회를 없애기 위한 별도 대기·조율은 만들지 않되 실제 변경 반영은 지키자는 설명이었다. 사용자는 이를 채택했다.

> “그래 그게 낫겟다 복잡도도 줄이고 그럼 남은게 있나?”

남은 오류 안내·토스트와 구현 과제를 확인한 뒤 기록을 먼저 요청했다.

> “그럼 정책이나 논의 통해서 기록 남겨야 할건 남기자 먼저”

이 채택은 앞선 모든 후보나 미커밋 구현을 수락한 것이 아니다. 특히 캐시가 있는 재조회 실패의 표시와 토스트의 의미는 아래 열린 판단으로 남는다.

## 기존 코드에서 확인한 관계

Main은 HEAD와 작업 트리, Git 이력 및 설치된 TanStack Query 5.90.5 소스를 읽었다. 개선 리뷰어도 관련 코드와 기록을 읽기 전용으로 대조했다.

- [QueryClient](../../../../../apps/client/src/shared/lib/queryClient.ts)의 refetchOnReconnect false에는 ‘SyncProvider가 처리’라는 주석이 있으며, 설정을 추가한 `ffcaf2c`부터 있었다. refetchOnWindowFocus도 false다. 이 주석은 의도를 보여 주지만 비활성 화면의 모든 복귀 경로가 처리된다는 증거는 아니다.
- [SyncProvider](../../../../../apps/client/src/shared/services/sync/provider.tsx)는 실제 online과 인증·DB·override 등의 실행 조건이 충족될 때 sync를 요청한다. [엔진](../../../../../apps/client/src/shared/services/sync/engine.ts)은 push 뒤 pull을 실행한다. push 호출이 항상 서버 쓰기를 뜻하지는 않으며 전송할 큐가 있어야 실제 쓰기가 발생한다.
- pull은 활성 여행만 Local에 반영하지만 HEAD의 pull 끝 무효화는 비활성 여행의 Query도 포함한다. 비활성 여행 Query의 재조회는 Router를 거쳐 Server API를 읽는 것이며 pull이 비활성 데이터를 Local에 저장하는 것은 아니다.
- 비활성화 전에 만든 미전송 큐가 남을 수 있으므로 push는 현재 비활성인 여행의 서버 데이터도 바꿀 수 있다. ‘pull이 비활성 여행을 건드리지 않는다’는 이유만으로 그 Query의 후속 갱신을 생략할 수는 없다.
- 활성 여행이 없으면 pull은 끝의 무효화 전에 반환한다. push 일부 성공 뒤 실패하거나 push 성공 뒤 pull이 실패해도 끝의 무효화에 도달하지 못한다. cleanup이 실제 처리한 항목이 있으면 별도 무효화가 있지만 이를 모든 복귀의 보장으로 삼을 수는 없다.
- [일정 조회](../../../../../apps/client/src/entities/schedule/data/useGetSchedules.ts)의 staleTime 5분은 주기 실행 타이머가 아니다. Query는 조회 허용 전환 등 계기에 stale 여부를 검사한다. 무효화는 유효기간이 남아 있어도 갱신을 요청할 수 있으므로 5분 설정만으로 sync와의 추가 조회를 없애지는 않는다.

## 책임 배치와 받아들인 비용

화면은 정책 제한·내용 배치와 선택·입력 보존을 맡는다. Query는 조회가 가능한 동안 캐시와 조회 상태를 관리한다. Router·인증 계층은 기존 실행 시점의 실제 연결·세션·소유권·Local/Remote 분기를 유지한다. sync는 push→pull과 실제 변경 뒤 갱신을 맡는다.

전역 refetchOnReconnect false를 유지하면서 해당 일정 Query의 조회 가능 여부와 기존 Query 상태를 연결하는 안을 사용한다. 제한이 풀렸을 때 유효한 캐시는 바로 사용하고, 데이터가 없거나 오래됐거나 무효화됐다면 필요한 조회를 한다. 따라서 온라인 복귀 계기에 조회가 전혀 발생하지 않는다는 뜻은 아니다. 별도의 전역 reconnect 구독·onlineManager 연결이나 복구 성공 추적을 이번 해결의 전제로 두지 않는다.

예를 들어 화면 복귀 직후 GET가 끝났어도, 뒤이어 push가 서버 데이터를 바꿨다면 다시 GET할 수 있다. 이 두 번째 조회는 변경 반영에 필요할 수 있다. 실제 변경이 없는 sync의 보수적 무효화 때문에 일부 추가 GET가 남는 비용도 받아들인다. 이를 줄이려고 화면을 sync 뒤까지 기다리게 하거나 모든 요청을 한 번으로 맞추는 조율은 추가하지 않는다.

비교한 다른 안은 다음과 같다.

- sync 종료 뒤 화면 조회를 한 번 수행하면 요청 수를 줄일 여지가 있지만, 데이터가 없는 화면도 관련 없는 큐·pull을 기다릴 수 있다. pull 생략·실패·이미 실행 중인 sync와의 합류까지 조율해야 하므로 현재 사용자 경험·복잡도 기준에 덜 맞는다.
- pull은 Local Query만, push는 변경된 Remote Query만 정밀하게 무효화하면 호출을 줄일 수 있다. 다만 일정 상세 등 일부 Query key에는 tripId가 없어 key와 관계 영향을 정리할 비용이 있다. 실제 추가 조회 비용이 문제가 될 때 재검토할 최적화로 두고 지금의 선행 조건으로 삼지 않는다.
- 앞선 조회 부분 재mount·성공 후 표시 후보는 일반 진입의 캐시 사용과 별도 완료 판정을 함께 바꿀 수 있었다. 새 표시 정책에서는 그 후보를 유지할 이유가 줄어들었다.

## 개선할 코드와 아직 열린 판단

미커밋 복구 훅의 required·previousRequest·QueryCache 성공 구독, 이전 요청 대기 뒤 refetch, 복구 완료까지 observer를 disabled로 두는 절차는 새 방향에 맞춰 정리한다. sync에서 비활성 일정 목록만 cancelRefetch false로 공유하는 예외도 개선 대상이다. 최초 실패와 빈 목록의 구별, 지도 날짜·일정 선택과 Drawer 입력 보존은 별도 가치가 있으므로 유지한다.

성공한 push의 변경 알림은 pull 성공에만 기대지 않게 해야 한다. 또한 캐시가 없는 최초 GET가 진행 중이면 설치된 Query는 일반 무효화에서도 이전 요청을 공유할 수 있다. 실제 쓰기 후 해당 Query의 진행 중 조회를 취소하고 무효화하는 방식은 작은 보완 후보다. 구체 key 범위와 다른 소비자·활성 전환까지 맞는지는 구현할 때 확인한다. Query 결과 채택을 취소하는 것과 실제 HTTP 전송 중단을 같은 보장으로 설명하지 않는다. 이 기술 문제를 ‘이전 GET를 복구 성공으로 인정할지’라는 사용자 정책으로 다시 돌리지 않는다.

기존 데이터가 있는 background 재조회 실패 때 내용을 유지하고 실패·재시도를 안내하는 것은 Main의 추천이며 별도 채택 전이다. 데이터가 없을 때는 일반 조회·로딩·오류 흐름을 사용한다. 2-C에서는 토스트가 연결 복귀를 알리는지 데이터 갱신 성공을 알리는지 정해야 한다. 초기 unknown·단순 재확인에는 복구 토스트를 붙이지 않고 같은 장애에 반복 표시하지 않는 기준은 유지한다. 토스트를 위해 강제 GET나 화면 대기를 되살리는 방향은 피한다.

이번 보완은 2-A의 변경 반영에 직접 필요한 연결을 다룬다. Ticket 14의 전체 write/cache 계약, 15의 typed pull·재시도·전체 결과 모델, 16의 cleanup 보존·집계 전체를 완료하거나 이번에 흡수하는 결정은 아니다.

## 근거의 범위와 다음 실행

이전 구현의 전체 client Jest 37개 suite·347개 test 통과는 앞선 Main의 구현 보고이며 새 설계의 검증 결과가 아니다. 같은 대화의 앞선 조사에서 Main은 실제로 `schedule-recovery`, `auth-interceptor`, `fetcher` 관련 3개 suite·47개 test 통과를 확인했다.

별도 임시 fixture에서는 이전 서버 응답을 붙잡은 복구 GET와 mock 서버 값을 바꾸는 실제 syncData 실행을 겹쳤다. 미커밋 코드에서 예상한 최신 데이터 반영이 일어나지 않는 사례를 확인했다. 같은 Query의 추가 observer 유무, 복구 observer만 disabled인 일반 무효화, 활성 여부 변경이 늦게 도착하는 제어 사례의 올바른 결과 기대 네 개가 실패했고, 활성 observer의 일반 mutation 무효화 대조 사례 하나는 통과했다. Repository·서버·DB·큐·활성 조회 입력은 mock이며 실제 서버·native DB·실기기 활성화 전체의 증거가 아니다. 이 fixture 결과를 커밋된 HEAD 전체의 결함으로 일반화하지 않는다. 임시 파일을 다음 실행의 필수 근거 경로로 두지 않고 위 재현 조건에서 필요한 검사를 제품 테스트로 구성한다.

이후 사용자가 요청한 개선 리뷰어는 새 테스트나 실험 없이 대안을 비교했다. Main은 그 추천 중 기존 구조 유지·화면의 sync 대기 제거·추가 조회 허용을 추천했고 사용자가 방향을 채택했다. 제품 코드와 테스트는 아직 새 방향으로 바꾸지 않았다. 기존 타입 오류 3개와 native·실서버·OAuth·SecureStore 미확인 범위도 남아 있다.

다음 제품 실행에서는 남은 오류 안내를 정리한 뒤 새 정책으로 2-A를 개선한다. 기존 테스트의 ‘새 조회 성공까지 숨김’과 ‘반드시 요청 한 번’ 기대를 명시적으로 바꾸고, 데이터 표시·실제 변경 반영·선택/입력·인증/활성 경계를 확인한다. 이번 요청은 그 실행 전에 정책과 논의를 기록하는 범위다.
