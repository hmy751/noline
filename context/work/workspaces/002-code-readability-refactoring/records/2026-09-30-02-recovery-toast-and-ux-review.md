# 복구 알림을 추가하지 않는 결정과 UX 검토

## 결정과 배경

2026-09-30 사용자는 Ticket 06의 2-C 복구 토스트를 현재 추가하지 않고, 다음 작업을 종합 UX 검토로 진행하는 방향을 채택했다. 2-C는 구현 완료가 아니라 현재 추가하지 않기로 한 결정이다. 실제 UX 검토에서 사용자가 복귀를 알아차리기 어렵다는 근거가 나오면 해당 상황에 필요한 짧은 알림을 재검토한다.

[처음 합의](2026-09-16-01-network-policy-and-implementation-boundaries.md)의 배경은 비활성 여행을 보다가 연결이 끊겨 내용이 제한된 뒤, 같은 여행의 내용을 다시 볼 수 있게 됐음을 알리는 것이었다. 당시에는 복구 조회 성공 뒤 토스트를 한 번 표시하기로 했다. 앱 전체의 연결 변화를 항상 알리는 기능이 목적은 아니었다.

이후 [복구 정책 변경](2026-09-29-02-schedule-recovery-query-sync-decision.md)으로 접근이 허용되면 기존 내용을 바로 표시하고 새 조회는 Query에 맡기게 됐다. 헤더의 네트워크 상태와 제한 안내가 사라지고 내용이 돌아오는 변화가 이미 복귀를 전달한다. 온라인인데 요청이 실패하는 경우는 기존 조회 오류·재시도가 맡는다. 데이터가 없으면 최초 오류를, 기존 데이터가 있으면 내용을 유지하며 갱신 실패를 안내한다. 이 위에 연결 복구 토스트를 더할 실익이 현재 크지 않다고 판단했다. 이 판단은 새 UX 검증을 완료했다는 뜻은 아니다.

## 판단 근거가 된 대화

사용자는 구현 전에 기존 정책과 시스템의 각 역할을 고려해 불필요한 복잡함을 없애자고 요청했다. 이어 다음과 같이 알림의 필요성을 물었다.

> “네트워크가 왔다갔다 오른쪽상단에도 어차피 표시되고 만약 온라인으로 돌아왔는데도 안되면 그건있나? 근데 애초에 그건 자연스러운 에러처리같고”

Main은 현재 토스트를 추가하지 않고 UX 검토에서 복귀 인지가 부족한지 확인하자고 제안했다. 사용자는 “그래 그렇게 하자 그럼 다음 작업 뭐지?”라고 채택했고, 다음 작업을 설명받은 뒤 “기능의 안정성도 중요하지만 UX적으로도 확인할 필요가 있어보여”라며 Workspace 기록을 요청했다. 인용은 이 결정을 논의한 현재 대화의 발췌다.

Network Store의 관측·재확인, Policy의 접근 판단, Query의 캐시·조회 상태, Sync의 동기화 책임은 유지한다. 알림을 위해 강제 조회, 조회·sync 완료 대기, 별도 복구 상태 추적을 추가하지 않는다. 검토 중 제안됐던 앱 전체 연결 알림과 offline만 알림 대상으로 삼는 안은 채택된 새 정책으로 올리지 않는다.

## 다음 작업과 남은 경계

다음은 홈·목록·상세·폼의 제한·오류·복구 경험을 함께 보는 UX 검토다. 기존 스크린샷과 검증 기록으로 후보를 좁히고, 전환을 직접 봐야 판단할 부분만 시뮬레이터에서 확인한다.

- 상단 상태 표시, 홈 경고, 내용 영역의 제한 안내가 같은 말을 과하게 반복하는지 본다.
- 여행 선택·내용·입력이 무엇을 유지하고 무엇을 가리는지 이해되는지, 추가 토스트 없이 복귀를 알아차릴 수 있는지 본다.
- 작성 중 제한과 복귀, 최초 조회 실패와 갱신 실패의 안내·재시도가 자연스러운지 본다.

[기존 일정 생성 결함 3건](2026-09-30-01-read-query-consumers-and-form-followups.md)은 확인된 기능 결함으로 유지하고 수정 우선순위를 함께 정한다. UX 검토나 수정은 아직 실행하지 않았다. foreground 복귀 재확인, mutation 제한 이유 전달, 최종 검증도 남아 있으며 Ticket 06 전체 완료나 UX 수락을 뜻하지 않는다. 이번 기록에서는 제품 코드를 변경하지 않았다.
