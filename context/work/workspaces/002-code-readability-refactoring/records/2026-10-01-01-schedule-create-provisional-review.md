# 일정 추가의 정책 소비·작성 상태와 품질 재검토

## 현재 남기는 결론

일정 추가만 대상으로 검색 먼저 시작하는 구현을 작업 트리에 적용했다. 경비와 일정 수정의 전면 개편은 포함하지 않았다. 사용자는 현재 코드를 유지하되 커밋하지 않고 더 검토하기로 했다. 이번 구현에서 논의한 행동·책임 기준은 잠정 유지하며 최종 설계나 사용자 수락으로 올리지 않는다. 폼 소유 위치 변경과 새 품질 리뷰의 개선안은 적용하지 않았다.

기록 기준은 2026-10-01, 브랜치 `refactor/app-startup-lifecycle`, HEAD `ee1c005`와 당시 미커밋 일정 추가 변경이다. 실제 코드의 재진입점은 [CreateScheduleScreen](../../../../../apps/client/src/screens/CreateScheduleScreen.tsx), [생성 feature](../../../../../apps/client/src/features/schedule/create-schedule/index.ts), [생성 흐름 검사](../../../../../apps/client/tests/screens/create-schedule-flow.test.tsx)다. 이 기록은 당시 코드·대화·리뷰의 근거이며 이후 작업 트리 상태를 고정하지 않는다.

## 무엇을 해결하려 했는가

기존 생성 화면은 `schedule.create.mode === 'manual-only'`로 별도 수동 폼을 표시하고, `allowed`가 false가 되면 화면 전체를 제한 안내로 대체했다. 작성 과정과 기능 가용성이 같은 분기에 묶여 온라인 복귀 때 수동 폼이 사라지거나, 선택 장소 폼과 수동 폼이 함께 나타났다. 렌더 중 날짜 초기값을 설정하는 경로도 React 경고와 연결됐다.

사용자는 단순한 파일 분할보다 필요한 만큼의 제한과 실제 책임 소유를 요구했다. 이전의 총괄 workflow 중심 시도는 거부하고 원복했으며, 그 뒤 검색·작성·제출의 근본 역할을 다시 논의했다. 최초 진입 허용 여부를 별도 상태로 기억하는 설계는 채택하지 않았다. 현재 정상 목록의 추가 행동에서 정책을 확인하고, 이미 열린 작성 화면은 기능별 제한과 실행 순간 검사를 사용한다.

## 구현에 사용했고 잠정 유지하는 기준

- 작성 단계와 입력값은 사용자 행동에 따른다. 네트워크 변화만으로 단계를 바꾸거나 폼·선택 장소를 초기화하지 않는다.
- 검색 먼저 시작하되 직접 입력으로 진행할 수 있다. 검색 선택과 수동 작성은 같은 폼 값을 사용한다. 여기서 ‘초안’은 아직 저장하지 않은 폼 값과 선택 장소이며, 화면 종료 후 복원하는 임시 저장 기능은 아니다.
- 검색 가능 여부, 지도 표현, 일정 저장 가능 여부를 각각 소비한다. `mode`를 화면 전체의 형태나 작성 단계로 해석하지 않는다. 검색 불가는 기존 선택 장소의 무효를 뜻하지 않는다.
- 제한과 오류는 해당 장소·검색·저장 영역이 보여준다. Policy는 가용성과 사유를 제공하고, 영역 컴포넌트는 필요한 속성을 받아 표시한다. 기존 지도는 내부에서 정책을 읽는 구조를 유지했으므로 모든 영역의 정책 주입 구조를 통일한 것은 아니다.
- 저장의 최종 권한과 Local/Remote 분기는 기존 Activation Router가 소유한다. 활성 여행 Local 이용과 비활성 여행의 실제 온라인·서버 인증 조건은 기존 제품 계약이다. 이번 잠정 UI 기준과 함께 그 계약까지 미정으로 바꾼 것은 아니다.
- 상태·행동을 상위에 둘 이유는 실제 수명·소비·재사용·조정 필요로 설명해야 한다. 무조건 하위 소유, 상위 조합, 훅 분리 또는 파일 통합을 정답으로 삼지 않는다. 폼뿐 아니라 검색·정책·지도·제출·저장 후 처리의 실제 연결까지 검토한다.

현재 화면은 사용자 단계와 기능 연결을, `useCreateScheduleForm`은 값·선택 장소·검증·날짜/시간 선택 상태를, `useCreateScheduleSearch`와 `useLocationSearch`는 검색 사용 조건·요청·결과를 맡는다. `useSubmitSchedule`은 요청 변환·mutation·기존 성공 후 경로 다운로드 연결을 맡고, 실제 저장은 Entity→Repository→Router에 남았다. 입력 폼과 검색 패널이 교체돼도 훅은 화면에서 유지된다.

## 구현과 후속 설명에서 바뀐 것

별도 ManualScheduleForm을 제거하고 단일 폼을 사용했다. 날짜 기본값은 form 초기값으로 설정했다. 검색 장소를 선택해도 사용자가 고친 제목은 유지하고, 장소를 직접 수정하면 텍스트는 유지한 채 이전 좌표 연결을 해제한다. 장소 검색은 public service 가용성으로 별도 판단하며, 검색 요청 중 차단도 오류로 처리한다.

첫 독립 리뷰가 발견한 세 문제는 수정했다: 정책 차단이 빈 성공 캐시로 남아 복구 후 같은 검색어를 재요청하지 않는 문제, 상세 실패의 대체 좌표 `(0, 0)`를 생성에 사용하는 문제, 이전 저장 실패가 현재 정책 제한을 가리는 문제다. 생성만 상세 조회 성공을 요구하고 캐시 키를 기존 수정 검색과 분리했다. 저장 안내는 현재 제한을 우선하고 과거 오류에는 ‘마지막 저장 실패’라는 표시를 붙였다.

사용자는 불필요한 `inputClassName` 추출을 지적했고 직접 className으로 되돌렸다. `onAddSchedule`도 처음에는 화면에서 전달했으나, 일정 전용 리스트가 여행·날짜와 상세 이동을 이미 알고 있고 사용처가 하나라는 근거로 정책 확인·안내·이동을 ScheduleListView 안으로 옮겼다. 이 실제 수정은 유지한다.

이어 폼 상태를 해당 폼 내부로 옮기는 대안을 설명했지만 적용하지 않았다. 조건부 입력 폼 안으로 훅만 옮기면 검색 전환에서 상태가 사라지므로, 옮기려면 검색을 포함한 작성 컴포넌트의 수명도 함께 바꿔야 한다. Main은 그 대안을 더 자연스럽다고 먼저 평가했으나, 새 리뷰에서 현 구조보다 낫다는 근거는 확보하지 못했다. 현재 배치와 대안 모두 검토 대상으로 남긴다.
