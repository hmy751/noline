# 홈 요약의 표시 책임·정책 재사용과 UX 후속 검토

홈 카드의 제한 안내를 요약 영역이 소유하도록 고치고, 기존 조회·정책 결과를 중복 포장하던 첫 구현을 간결화했다. 제품 코드와 테스트는 `e54fe42`에 저장했다. 이 기록은 해당 설계 선택과 검증 근거, 앞서 진행한 나머지 UX 검토를 연결한다. Ticket 06과 Workspace 전체는 진행 중이다.

## 기존 검토에서 홈 수정으로 좁힌 이유

사용자는 Ticket 06의 남은 범위를 기존 gitignore 대상 보고서와 대조하고, 시뮬레이터 하나는 수집에 집중하면서 코드·정책 조사를 병렬로 진행하도록 요청했다. 홈에 이어 foreground 재확인, 목록·상세·폼 UX, 홈·목록 날짜 차이, 보류·후속 경계의 네 보고서를 작성했다. 초기 보고서는 무엇이 되고 안 되는지와 검사 이유가 이전 보고서에 충분히 연결되지 않았고, 가능한 추가 검토도 부족하다는 사용자 지적을 받았다. 이에 기존 비활성 여행의 제한·복귀, picker 취소, 현재 날짜 원본과 설치 네트워크 라이브러리를 추가 확인했다.

이번에 구현한 문제는 비활성 홈의 숫자 두 칸에 완성된 정책 오류 UI를 각각 주입해 설명이 좁아지고 재확인 버튼이 중복되는 것이었다. 홈 대표 여행은 일정·경비 탭의 선택 여행과 별도로 날짜에 따라 계산된다. 따라서 다른 활성 여행 선택을 요구하는 일반 문구만으로 홈 대표 카드의 상태를 설명하기도 어려웠다.

사용자는 표시 책임을 먼저 정하도록 방향을 바로잡았다. 현재 대화의 최소 발췌는 다음과 같다.

> “ui의 에러를 어떻게 보여주는건 그 ui가 담당을 해야하고”
>
> “정확히 섹션인지 아니면 일정 안 카드인지 어떻게 보여줄지 부터 확실히 정해야할 것 같아”

이에 홈의 일정·경비 요약을 카드 안의 한 영역으로 정했다. 정책은 기능 사용 가능 여부와 제한 이유를 제공하고, 이 영역이 공간·문구·로딩·실패 표시를 맡는다. 다른 목록·상세·폼의 정책과도 일치시켜야 하지만 모든 화면을 같은 오류 박스로 바꾸는 요구는 아니다.

## 현재 구현과 간결화한 이유

[MainTripSection](../../../../../apps/client/src/screens/HomeScreen/MainTripSection.tsx)은 기존 일정·경비 조회 훅을 호출하고 성공한 데이터만 일정 수·통화별 금액으로 가공한다. 기존 `ReadQueryView`와 재조회·네트워크 재확인 callback을 전달한다. [TripCard](../../../../../apps/client/src/entities/trip/ui/TripCard.tsx)는 카드 배치를, 그 안의 [TripSummary](../../../../../apps/client/src/entities/trip/ui/TripSummary.tsx)는 정상·로딩·제한·최초 실패·갱신 실패의 표현을 소유한다. 새 전용 훅이나 상태 저장소는 만들지 않았다.

첫 구현에는 기존 조회 결과와 거의 같은 `TripSummaryState`, `getSummaryState`, `SummaryRestriction`이 생겼고, 공동 제한 비교를 위해 정책 사유 코드 7종을 추가했다. 기능 검사를 통과하고 첫 리뷰에서 회귀를 찾지 못했지만, 사용자가 다음과 같이 다시 지적했다.

> “기존 useAppPlicy 를 이해하지 못하고 덕지 덕지 붙여있는게 있는데 간결하게 할수 있는 것 그리고 기존 시스템을 고려해서 다시 개선 시켜봐”

재검토에서는 테스트 통과와 구조 적합성을 구분했다. 기존 조회 조합이 이미 제한·로딩·최초 실패·성공·갱신 실패를 판별하므로 새 상태 타입과 변환은 필요하지 않았다. 이를 제거하고 `ready.data`의 집계만 남겼다. 단순 Text 래퍼와 정책 사유 동등성 비교도 제거했다. `useAppPolicy`와 장소 검색의 추가 변경은 걷어내 최종 커밋에서 변경이 없다.

같은 여행의 Schedule·Expense read 정책표는 네 상태에서 같고, 인증·활성 확인·unknown의 선행 제한도 공통이다. 두 조회가 모두 blocked이면 한 안내를 표시한다. 단, 표시용 online·실제 offline인 Debug 상황에서 한쪽 캐시만 있으면 그 항목은 ready, 다른 항목은 blocked가 될 수 있다. 이 차이는 기존 조회 조합이 판별하며 요약 UI가 전체 제한으로 덮지 않는다. 향후 두 읽기 정책이 달라지면 이 공동 안내 계약과 관련 검사를 함께 재검토해야 한다.

`reasonCode: 'offline-inactive'`는 두 read 정책에만 남겼다. 기존 화면의 기본 문구는 유지하면서 홈에는 “이 여행의 일정과 경비는 인터넷에 연결하면 볼 수 있어요.”를 표시하기 위한 구별값이다. 문구 비교나 네트워크 상태 재추정으로 인증·활성 확인 제한을 오인하지 않는다. 권한·pending·복구 행동은 기존 정책 결과를 사용한다. 재확인은 기존 Store refresh, 재조회는 기존 guarded actions.refetch를 사용한다.

## 검사 결과와 보장 범위

Sol 구현자가 최종 코드에서 client Jest **49 suites, 550 passed, 1 skipped**를 실행해 보고했다. 간결화 전 551개 통과는 최종 수치가 아니다. 합성 사유 조합 검사를 실제 정책 계약에 맞춰 정리하고, 한쪽 캐시가 있는 두 방향의 통합 검사를 보강했다.

- [요약 UI 검사](../../../../../apps/client/tests/entities/trip/TripSummary.test.tsx): 정상 0·통화 표시, 로딩과 0의 구별, 공동 제한과 단일 복구 행동, 부분 실패·갱신 실패의 기존 값 유지, 진행 중 버튼 제한.
- [화면 연결 검사](../../../../../apps/client/tests/screens/read-query-consumers.test.tsx): 실제 Main·Policy·조회 조합에서 한쪽 캐시 유지와 없는 항목 제한, 실제 online 복귀 후 누락 항목 조회, 재확인 공유, 활성 여행 값 유지, 실패한 항목만 재조회, 보유 여행의 재조회 실패 시 카드 유지.
- [네트워크 정책 검사](../../../../../apps/client/tests/shared/policy/useAppPolicy-network.test.ts)와 [활성 확인 검사](../../../../../apps/client/tests/shared/policy/useAppPolicy-activation.test.tsx): 같은 여행의 두 read 정책 동등성, 인증·활성 확인·unknown의 기존 우선순위.

구현자 보고로 변경 파일 Prettier·diff 검사 통과, ESLint 오류 0·기존 TripCard inline-style 경고 1을 확인했다. 타입 검사는 기존 Mapbox/download 오류 3개로 전체 성공이 아니며 새 진단은 없었다. Astra 검토자는 원본 계약·최종 코드·테스트 본문을 독립 대조해 중복 상태 정의 제거, 남은 props·내부 함수·사유 표지의 필요성, 공동 제한의 근거와 혼합 상태 보존을 확인했다. Main은 코드·검사 본문·diff와 화면 이미지를 직접 점검했다. 리뷰어와 Main이 전체 테스트를 재실행한 것은 아니다.

재확인할 때는 Project root에서 `pnpm --filter @apps/client exec jest --config jest.config.cjs --runInBand`를 사용할 수 있다. repository·HTTP·일부 native 경계를 대체하는 자동 검사이며 실제 통신 단절 성공을 뜻하지 않는다.

## 화면 관찰과 남은 UX 근거

수집은 기존 iPhone 15 Pro 시뮬레이터와 기존 데이터를 사용했다. 실제 연결은 online이었고 offline/unknown은 Debug 표시 강제 설정이었다. 여행 활성화·DB 데이터 변경 없이 관찰했으며 마지막에는 원래 활성 여행과 override null로 복원했다.

| 확인 범위 | 관찰 결과와 한계 |
| --- | --- |
| 비활성 홈 수정 후 | 임시 대표 선택 조건으로 기존 비활성 파리 1/6~1/9를 홈에 표시했다. online은 일정 0개·EUR 7, offline은 전체 폭 안내 하나, unknown은 확인 불가 설명·재확인 버튼 하나, 복귀 후 같은 숫자가 보였다. 임시 조건은 원복했고 커밋에 없다. |

## 후속 판단을 위해 확인한 두 사항

날짜 추가 조사자는 현재 Local DB를 read-only로 조회하고 시뮬레이터 KST를 확인했다. 활성 파리의 start/end는 `2026-09-29T22:00:00.000Z`·`2026-10-01T22:00:00.000Z`였다. 현재 홈은 현지 날짜로 9/30~10/2, 일정·경비 목록의 `getUTCDateRange`는 9/29~10/1을 만든다. 따라서 현재 날짜 차이의 원인은 확인됐다. 생성 당시 의도나 과거 9/30 캡처의 원본까지 확정한 것은 아니다. 해결에는 Trip 기간의 달력 날짜 의미, 입력·대표 여행 선택·활성 만료를 함께 판단해야 하며 이번 홈 표시 수정과 분리했다.

foreground 추가 조사자는 앱과 설치된 NetInfo 11.4.1 코드에서 복귀마다 명시적으로 최신 상태를 읽는 연결을 찾지 못했다. 앱의 mount 초기화·일반 native 관측·JS 반복 도달 확인은 존재하므로 “복귀 후 갱신이 전혀 없다”는 뜻은 아니다. 화면이 온라인으로 돌아온 관찰만으로 foreground 전용 refresh를 입증하지 않는다. 최신성 보장이 필요하면 기존 network refresh에 복귀 이벤트를 연결하고 실제 기기에서 background 연결 변화까지 검증하는 후속 작업이다.

## 현재 남은 경계와 저장 요청

사용자는 홈 구현·간결화 보고 뒤 “그래 커밋 하고 workspace 기록할거 잘 남겨놓자”라고 요청했다. 이 요청을 이번 코드와 기록의 저장 승인으로 적용했다. 종합 UX 전체 수락이나 Ticket 06 완료로 확대하지 않는다.

다음은 foreground 재확인 연결과 남은 목록·상세·폼 UX, 날짜 기준 판단 및 실제 통신 단절 검증을 현재 결과에서 이어가는 것이다. 경비 삭제 실패 이유 유실·상세의 특정 재시도 불일치는 기존 사용자 보류를 유지한다. 복구 토스트 2-C도 현재 추가하지 않는 선택을 유지한다. 일정 수정·검색 fallback·저장 후 경로 준비 등 다른 미완료는 기존 Ticket 책임을 따른다.

현재 session의 자동 Maintain은 unbound임을 확인했다. 사용자 명시적 기록 요청에 따라 bounded bootstrap과 수동 guarded apply로 반영했으며, 자동 binding·제품 Verify receipt·기계 상태·active index는 변경하지 않는다.
