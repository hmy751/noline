# 앱 준비의 실패 정책·책임 정리·독립 리뷰와 코드 스타일 반영

2026-09-18, Ticket 06의 네트워크/Provider 정리 이후 앱 시작의 DB·인증·첫 화면·인증 후 작업을 개선한 기록이다. 현재 실행 계약은 [Ticket 06](../current/memory/tickets/06-app-startup-lifecycle.md), 전체 진행과 다음 후보는 [state](../current/state/index.md), 코드 읽기 경로는 [output](../output/index.md)이 소유한다. 아래 사용자 발췌는 이 Main 대화에서 직접 확인한 문구이며, 세부 실행 이력은 Main의 보고와 [구현 결정 기록](../../../../../.claude/decisions/2026-09-18-app-startup-failure-recovery.md)을 연결한다. 이전 [파일별 검토 기록](2026-09-18-01-network-provider-layout-review-and-commits.md)의 레이아웃 내부 유지 결정은 당시 선택으로 보존한다.

## 실패 정책을 정한 이유

사용자는 남은 범위를 확인한 뒤 DB·auth 준비부터 진행하도록 선택했다. DB 실패에는 “실패 안내와 재시도 화면을 보여주고, DB 준비 성공 후 진입한다”를 골랐다. 인증 정보를 읽지 못했을 때는 “보통 로그인 화면으로 보내나? 일반적으로?”라고 확인하고 “일반적으로 가자”라고 선택했다. 이 범위의 의미는 인증 정보가 없는 경우와 보안 저장소 읽기 실패 모두 비인증 상태로 복원을 마치고 로그인 화면으로 보내는 것이다. 읽기 실패를 서버 인증 거부·토큰 만료와 동일한 사건으로 정의하지 않았다.

DB와 인증 저장소를 같은 것으로 받아들이면 DB 준비 실패에도 인증 여부에 따라 진입해도 된다고 오해하기 쉽다. SQLite 연결·스키마와 보안 저장소의 토큰은 별개라 어느 한쪽만 실패할 수 있다. 사용자는 “DB준비 실패하고 인증정보 잇으면 … 그땐 재시도가 자연스럽겟다”라고 정리하고 진행을 요청했다. 여행이 없거나 활성 여행이 없는 경우에도 앱 DB·테이블은 준비한다. 로컬에 여행 내용이 얼마나 있는지와 DB가 사용 가능한지는 다른 조건이다.

재시도는 준비를 다시 시도하며 reset·데이터 삭제를 하지 않는다. 준비 완료는 DB 사용 가능과 인증 복원 시도의 완료다. 네트워크 확인·로그인·지도 다운로드·sync 결과는 이 완료에 포함되지 않는다. DB가 실패한 동안 Provider와 앱 화면을 연결하지 않는다.

## 테스트를 먼저 작성한 범위

사용자는 “진행하기전에 시나리오 짜려는 기능에 대한 테스트 먼저 작성하고 하자”라고 요청했다. Main은 DB 준비와 인증 복원, 준비 실패/재시도, 해제된 화면의 늦은 완료와 실제 Root 연결 시나리오를 먼저 작성했다. 첫 구현 전 검사에서 삭제 SQL 정규식의 외래키 ON DELETE 오탐을 수정한 뒤 33개 중 7개 실패·26개 통과를 확인했다고 보고했다. 실패는 import 시 DB 열기·열기 실패 전달, DB 실패 뒤 진입과 재시도 부재, 화면 해제 뒤 인증 실행, 중복 인증 읽기였다.

이후 getDatabase 접근 계약·여행 선택·cleanup 공유/종료 조율도 변경 전에 실패를 확인했다. Main이 보고한 새 실패는 DB 접근 3개, 사용자 선택 보존 1개, cleanup 조율 4개이며, 세션 종료 때 여행 선택을 비우는 기대도 로그아웃·탈퇴 2개에서 실패를 확인한 뒤 구현했다. 각 세부 테스트는 Entity·서비스에 두고 Root 테스트는 앱 구성의 통합 연결을 유지했다. 테스트 개수만으로 실제 기기 저장이나 전체 제품 안전성을 입증하지 않는다.

## 초기화와 인증, 화면·기능의 책임을 나눈 과정

첫 개선은 `_layout.tsx`에서 DB→인증→준비 완료를 읽도록 만들고 준비 상태를 한곳에 모으는 방식이었다. 사용자는 “preparation 과 auth init … 따로 구현된느낌”과 “우리 spec의 목표도 생각해봐”라고 지적했다. 단순히 준비 여부를 나타내는 boolean을 옮기거나 테스트를 통과하는 정도로는 이해·수정 부담이 충분히 줄지 않았다.

이어 “확장성 응집도 모듈도 고려해서 레이아웃 정리”, “이니셜라이즈 앱 초기화의 의미더 생각하고”라는 요청에 따라 앱 구성이 무엇을 연결하는지와 준비 과정 자체의 수명·실패·재시도를 분리했다. 앱 준비는 네트워크 감지 시작/정리, DB와 인증 복원의 순서, 준비 UI와 Splash, 실패 안내·재시도를 함께 가진 책임이다. 인증 Store는 보안 저장소와 인증 상태를 유지하는 책임이며 앱 화면 연결을 소유하지 않는다. `restoreSessionOnce`는 완료 Promise도 재사용해 이후 login/logout 상태를 다시 덮지 않는다.

사용자는 독립 리뷰 이후 “일단 application 분리 하고 리뷰어 리뷰 고려해서 한번 작업 진행해봐”라고 요청했다. 앱 전체 준비는 여러 기능을 조율하므로 features 아래에 넣지 않고 `src/application/AppInitialization.tsx`에 둔다. `_layout.tsx`는 Root 구성을 먼저 보여 주고, 같은 파일의 AppNavigation은 Stack·인증 리다이렉트를, AuthenticatedEffects는 로그인 수명에 연결되는 작업을 모은다. 기능별 선택·정리는 기존 Entity·서비스에 남긴다. application 파일 하나의 분리는 승인됐지만 모든 내부 컴포넌트를 파일별로 나누거나 범용 startup registry를 만들지는 않았다.

이 배치의 판단 기준은 함수나 파일 수가 아니라 함께 변경되는 조건과 책임이다. 추가 필수 준비 단계는 AppInitialization에서 순서·실패·UI와 함께 바꾸고, 화면 이동은 AppNavigation, 로그인 후 연결은 AuthenticatedEffects, 개별 규칙은 해당 Owner에서 바꾼다. 보안 저장소와 인증 상태까지 application으로 올리면 하위 기능이 앱 구성에 의존하게 되므로 현재 분리를 유지했다.

## 독립 품질 리뷰의 반영과 열린 경계

사용자는 변경한 부분만 독립 리뷰어에게 제공하고 대화 등 다른 맥락은 주지 않도록 요청했다. Main은 reviewer 제안을 그대로 규칙으로 올리지 않고 기존 FSD·Selective Local-First·데이터 보존 계약과 대조한 뒤 반영 범위를 판단했다고 보고했다. 아래는 채택 후 실제 구현한 범위이며 전체 리뷰 항목의 무조건 승인이 아니다.

- DB 연결과 준비된 ORM 객체를 구별하고 getDatabase로 준비 성공 뒤 접근만 허용한다. 초기화 전/SQL 실패/reset 실패 접근은 오류로 드러내고 reset 시작 시 준비 완료 상태를 폐기한다. 기존 DB 호출부 21개 파일을 접근 함수에 연결했다. SQL·transaction 내부는 유지했다.
- 여행 선택을 별도 hook으로 모으고 실제 조회 출처를 Repository 결과에 포함했다. 서버 목록 성공으로 기존 선택의 제거를 확인한 경우의 UX는 사용자에게 물었다. 사용자는 “다중기기까지는 개발할때 … 생각을 안하긴 햇는데 일단 다른여행으로 전환한다로 가자”라고 선택했다. 남은 목록이 비었으면 선택을 해제한다. Local 불완전 목록·실패·조회 중·offline/unknown에서는 유지하며 연결 복구만으로 선택을 바꾸지 않는다. 다중 기기 지원 전반을 추가하지 않았다.
- pending cleanup의 진행 중 Promise와 캐시 후처리를 공유하고 startup 타이머는 hook에 둔다. Sync engine의 중복 캐시 요청은 제거했다.
- 사용자는 cleanup 실행 중 세션 종료에 “실행 중인 정리가 끝난 뒤 DB를 비우고 로그아웃”을 선택했다. 새 pending cleanup을 막고 이미 시작한 작업의 성공·실패 종료를 기다린 뒤 큐·DB·인증·여행 선택·캐시를 정리한다. 같은 로컬 종료를 공유하는 회원 탈퇴에도 적용하고 실패 때 일시 중단을 해제한다.

DB migration, 실제 SQLite 원자성, cleanup 내부의 처리 수·미전송 데이터 보존, full sync와 로그아웃의 실행 조율, 지도 만료 정리 전체의 중단은 이번에 해결하지 않았다. getDatabase는 이미 반환한 객체를 취소하지 않는다. Store 복원 도중 다른 직접 login/logout 진입점이 상태를 변경하는 경쟁까지 새로 보장하지 않는다. `any`·`as never[]`·non-null을 새 단언으로 감추는 전면 타입 정리는 후속 Ticket에서 검증된 형태를 전달하는 방식으로 다룬다.

## 코드 스타일 리뷰의 기준과 적용

사용자는 “코드 개행이나 이런게 … AI가 짜준것 같고 실제 회사 프로덕션 레벨이 아닌것 같아”라고 지적하고, 변경 파일만 독립 리뷰어에게 제공해 구체적 기준을 물으라고 요청했다. Main이 받은 리뷰는 개행뿐 아니라 실제보다 강한 주석·로그, 의미가 흐린 이름, 비동기 완료 표현, 테스트의 불분명한 대기와 경우별 분기를 함께 문제로 봤다. 사용자는 “한 번 개선해봐 기준가지고”라고 적용을 요청했다.

적용한 기준은 다음과 같다.

1. 들여쓰기·따옴표·줄바꿈은 기존 formatter 설정에 맡기고 빈 줄은 준비·guard·외부 작업·결과의 의미가 바뀌는 곳에 둔다.
2. 짧은 guard에도 중괄호를 사용해 주변 코드와 일관되게 읽는다.
3. 주석은 계약·이유·예외를 설명한다. 반복 단계 번호·단순 사용 예시·코드를 다시 말하는 설명을 줄이고, 실제보다 강한 최신성·반환 타입·활성 정보 포함 주장을 바로잡는다.
4. 이름은 실제 범위를 드러낸다. 도시 참조 감소처럼 보이는 함수는 재계산이라는 이름으로, 좌표 입력은 ScheduleCoordinates로, 사용 중인 결과 인자는 result로 정리한다.
5. 선행 조건은 await하고 완료를 기다리지 않는 작업은 그 이유와 실제 완료 범위를 드러낸다. 스타일 정리 때문에 await를 추가하지 않으며 캐시 재조회 요청을 완료로 기록하지 않는다. 모듈 scope와 이벤트를 표시하고 선행 이모지를 제거한다.
6. 테스트는 준비·실행·기대 결과가 읽히도록 나누고 경우별 입력 객체를 사용한다. cleanup 조율의 반복 microtask 대기를 실제 일시 중단 진입을 관찰하는 Promise로 교체한다. React 업데이트 반영 helper는 준비 완료를 보장하는 듯한 이름을 피한다.

void는 오류 처리 자체가 아니며, 비동기 호출 전체에 새로 붙이는 방식은 기존 no-void 규칙과 충돌했다. Main은 이 추가를 철회하고 기존 호출 시점과 오류 처리·규칙을 유지했다. 기존 초기화/cleanup의 void 경고를 모두 없애기 위해 lint 정책을 바꾸지는 않았다. 이 기준을 formatter의 수동 덮어쓰기나 모든 파일의 일괄 분리 규칙으로 해석하지 않는다.

## 최종 검사와 현재 남은 일

Main이 코드 스타일 정리 전후 직접 실행한 전체 client Jest는 14개 suite·154개 test 통과다. 최종 검사도 같은 결과다. 포함된 새/확장 검사 범위는 Layout 26개, Tabs 2개, 인증 Store 7개, DB 준비 8개, 여행 선택 9개, 목록 출처 2개, cleanup 수명 7개다.

실행 명령은 Project root에서 `node_modules/.bin/jest --config apps/client/jest.config.cjs --runInBand`와 `node_modules/.bin/tsc --project apps/client/tsconfig.json --noEmit`이다. 변경된 TypeScript 39개 파일은 client ESLint 설정에서 `prettier/prettier` 연동 규칙만 제외해 검사했고 오류 0개·경고 26개다. 직전 27개에서 미사용 import 경고 1개를 제거했다. 동일 파일의 별도 Prettier 검사와 git diff --check가 통과했다. pnpm을 통한 검사 시도는 package-manager 자동 설치 경로에서 실패해 설치된 실행 파일로 검사했다. 이 실행 실패를 제품 typecheck 결과로 기록하지 않는다.

타입 검사에는 기존 mapbox.ts 좌표 배열의 tuple 타입 오류 1개, offline-map/download.ts의 OfflinePack size·tileCount 필드 오류 2개가 남는다. Jest는 SQLite·SecureStore·native·외부 서버를 대체하므로 실제 Expo UI, 기기 DB 데이터 보존·migration, 실제 토큰 저장/서버 전송을 확인한 증거가 아니다. 테스트 통과는 production 품질 전체나 사용자 acceptance를 뜻하지 않는다.

현재 startup·스타일 결과는 미커밋 작업 트리에 있다. 새 stage·commit·push는 요청받지 않았으며 기존 다른 변경과 .pnpm-store를 보존했다. 기존 Network·Provider·Layout 저장 경계는 앞선 기록에 남긴다.

다음 startup 후보는 DB 준비·인증 상태·실제 online·override 해제의 SyncProvider 시작/해제와 Debug engine 직접 호출의 우회 연결이다. Root가 준비 뒤 Provider를 mount하는 것과 인증 상태의 변화에 Provider가 반응하는 것은 다른 결과다. 인증 route guard 전체, 대상 여행별 Router·inactive child 선조회, 제한/복구 화면 전체, foreground 재확인도 Ticket 06에 남는다. 08의 대표 여행 계산, 14의 실제 SQLite 원자성, 15의 엔진 결과·재시도, 16의 미전송 보존·파괴적 정리 계약을 이번 완료로 흡수하지 않는다.

## 기록 반영의 경계

사용자는 “여태 대화 기반으로 워크스페이스에 필요한 기록들 잘 남겨줘”라고 요청했다. 이 요청으로 선택된 002 Workspace에 현재 계약·결과와 선택 과정 기록을 수동 반영한다. 당시 Main session은 status 조회에서 unbound였고, 명시적 bounded bootstrap과 guarded apply 경로를 사용한다. 자동 Maintain binding·freshness, machine status·Verify receipt, 다른 Workspace와 Project 본문은 이 요청으로 변경하지 않는다. Ticket 06과 Workspace 전체의 최종 수락은 열린 상태다.
