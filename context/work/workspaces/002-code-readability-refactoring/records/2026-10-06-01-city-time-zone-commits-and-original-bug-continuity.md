# 도시 시간대 작업의 결정·커밋·검증과 원래 버그 검토의 다음 순서

도시 시간대 작업을 일곱 단위로 나눠 커밋했다. UTC 저장을 유지하면서 여행 도시의 달력 날짜·시각으로 입력하고 표시하도록 연결한 결과다. 다음은 기존 UX 보고서에서 발견한 날짜·시간 선택창의 초기 표시 문제다. Ticket 06과 Workspace 전체의 완료·사용자 수락을 선언한 기록은 아니다.

## 이 대화가 이어 온 문제

이번 대화는 Workspace 002의 Ticket 06을 기존 Git 제외 버그 보고서와 대조하는 작업에서 시작했다. 사용자는 003 대신 해당 보고서를 보라고 정정했고, 시뮬레이터 하나는 빠른 수집을 맡기고 코드·정책 검토를 병렬로 하도록 요청했다. 홈 및 나머지 네 보고서를 만들었지만 검사 이유·결과·다음 행동이 기존 보고서와 이어지지 않고 추가 검토가 부족하다는 지적을 받아 자료를 보완했다.

원래 9월 30일 보고서는 수동 일정 작성 중 연결 복귀로 화면이 사라짐, 일반·수동 폼 동시 장착, 취소 경고, 홈 제한 안내 중복, 홈과 목록의 날짜 차이를 남겼다. 일정 작성은 단일 초안·단일 폼으로, 경비는 초안 보존·일정 연결·저장 오류 안내로 개선됐다. 홈은 정책 판단과 요약 영역의 표현 책임을 나눴다. 앱 복귀 재확인은 기존 Network Store의 감지 세션에 연결했다. 날짜 비교를 새 데이터로 재현하다가 드러난 여행 생성·목록 갱신 결함도 별도로 고쳤다.

## 날짜 설명에서 확정한 기준

처음 파리 사례는 홈이 9/30~10/2, 목록이 9/29~10/1이었다. 원본 기간은 `2026-09-29T22:00:00.000Z`~`2026-10-01T22:00:00.000Z`로 같았지만 날짜를 읽는 기준이 달랐다. 앞선 ISO 직렬화·입력 검사 개선이나 생성·목록 수정은 이 제품 의미의 차이까지 해결한 작업이 아니었다.

사용자는 UTC 저장을 유지한다는 설명과 기간·경비를 날짜로 다룬다는 설명의 관계를 여러 번 물었다. 일정 예약은 시점이고 경비는 날짜라는 이유만으로 Trip 기간까지 date-only로 바꾸는 안은 채택하지 않았다. 여행 생성 때부터 도시 기준으로 생각하고 같은 기준으로 표시하자는 방향으로 정리했다. 대화의 핵심 발췌는 다음과 같다.

> “그럼 여행기간 즉 여행 생성할 때 기준도 해당 도시를 기준으로 하면 되는거잖아?”
>
> “기존에 데이터 utc 저장이나 이런건 일관성을 유지하고 … 여행, 일정, 경비 등 해당 도시의 타임존을 고려해서 해당 로컬의 시간을 기준으로 … 저장하고 표시하면 되는거잖아?”

Trip이 IANA `timeZone`을 소유하고 shared datetime 함수가 변환을 맡는다. 예를 들어 파리 9/30 10:00 일정은 해당 도시의 offset을 반영해 08:00Z로 저장하고, 한국 기기에서도 여행 일정에는 파리 10:00을 보여 준다. Trip 시작·종료는 도시 자정의 UTC 시점으로 유지하며 종료일은 마지막 포함 날짜다. Expense의 기존 `YYYY-MM-DD`는 시각으로 변환하지 않고 그대로 보존한다. 경비 기본 날짜와 연결 일정에서 얻는 날짜만 Trip 도시 기준으로 만든다.

책임은 도시 서비스의 시간대 확인 → Trip 계약·저장 → shared 변환 → 폼·화면의 소비로 이어진다. Repository·Activation Router·transaction·sync의 기존 저장 흐름은 유지한다. [제품 날짜 기준](../../../../project/common/date-and-time.md)과 [설계 결정](../../../../../.claude/decisions/2026-10-06-trip-city-time-zone.md)이 현재 상세 의미를 소유한다.

기존 Trip의 시간대는 nullable로 받아 데이터·큐를 보존한다. 미확정 조회는 UTC fallback임을 알리고, 도시 좌표로 확인해 시간대만 기존 수정 경로로 저장한다. 그때 과거 timestamp를 자동 이동시키지 않는다. 새 생성과 시간대가 필요한 쓰기·활성화는 확인된 시간대가 필요하다. 과거 날짜 의도의 복원은 명시적인 기간 편집과 구별한다.

DST에 없는 현지 시각은 거부하고 새 입력의 중복 시각은 앞선 시점을 택한다. 수정하지 않은 기존 일정은 offset·초·밀리초를 보존한다. 종료일 전체와 이후 도시 달력 7일을 보장한 다음 자정에 활성 유예가 끝나며, cleanup도 같은 계산을 사용한다. 시간대 미확정 여행은 추정해 만료시키지 않는다.

## 기존 정책 시스템과 맞추며 교정한 부분

사용자는 `isOnline`이 네트워크 상태처럼 읽힌다고 지적했고, `useAppPolicy`에 조건을 덧붙이는 방식인지 재검토를 요청했다. 새 여행의 서버 생성도 기존 시스템을 면밀히 확인하는 독립 검토에 맡겼다.

> “useappplicy 에 떡칠한거 아냐? 다시 고민해봐 맞는건지 일관성 및 등”
>
> “기존 시스템 면밀히 파악하고 지금 상황에 제안하라고 해봐 시스템을 일관성을 지키면서 불필요한 추가 말고 근본적인 해결하려면 어덯게 해야하는지”

시간대 조회 가능성은 `canResolveTimeZone`, 저장 가능성은 기존 `policy.trip.create/update`로 표현한다. 공개 도시 조회 성공은 인증된 쓰기 허가가 아니다. 새 여행은 아직 활성화된 대상이 없으므로 Router의 기존 Server 생성 정책을 사용하고, 다른 여행이 활성화돼 있어도 이 분기는 달라지지 않는다. 기존 활성 여행 수정은 Local, 비활성 여행 수정은 Remote다.

독립 검토의 보고를 반영해 별도 capability 체계나 전용 전역 상태를 늘리지 않고 공통 인증·unknown 제한과 대상 활성 상태를 재사용했다. 폼은 표시용 정책과 시간대 준비 상태를 사용하고, 실제 조회는 실제 관측을 사용하며, 최종 mutation의 최신 조건·Debug 차단은 Router가 확인한다. pending·재확인은 기존 인라인 정책 안내로 연결했다. Query의 미시작·조회 중·실패를 구분하고, 저장 실패 후 입력을 유지하며 사용되지 않는 생성 훅을 제거했다.

이 검토는 여행 삭제 버튼의 기존 정책 연결이나 수정 실패 Alert의 상세 이유 유실까지 해결한 결과가 아니다. 당시 보고된 기존 경계로 남으며, 시간대 조회·생성/수정 연결의 완료와 분리한다.

## 검증에서 실제 확인한 범위

Main은 커밋할 단위까지 포함하고 후속 변경을 제외한 임시 snapshot으로 검증했다. 3번은 client 55 suites / 622 passed / 1 skipped, 4번은 55 / 622 passed, 5번은 56 / 624 passed, 6번은 56 / 629 passed, 7번은 **57 suites / 632 passed**였다. 해당 단계의 schema build도 통과했다. 3번의 server Trip 시간대 계약 13개 통과는 앞선 Main 실행 보고다. 이번 기록 시에는 남아 있는 client 로그의 최종 수치를 직접 대조했으며 제품 검사를 새로 실행하지 않았다.

6번에는 실제 메모리 SQLite를 사용하는 만료 갱신 검사가 포함됐다. 만료 갱신 SQL이 실패하도록 했을 때 Trip 수정·sync_queue·활성 만료가 함께 rollback되는 사례를 검사했다. 7번의 세 접근성 검사 중 이전 구현은 드롭다운/일정 카드 두 개가 실패했고, Drawer 입력·저장 검사는 기존에도 통과했다. 따라서 세 사례 모두 새로 실패를 고친 것으로 설명하지 않는다.

최종 client 타입 검사는 Mapbox 좌표 tuple, OfflinePack의 size/tileCount, UI package rootDir·파일 목록 설정의 기존 7개 진단으로 전체 통과하지 않았다. 신규 진단이 없다는 당시 비교 결과와 전체 성공은 구별한다. 앞선 server Places Language 타입 문제도 전체 해소했다고 주장하지 않는다.

별도 앱 검증 담당의 보고에서는 기존 iPhone 15 Pro 개발 앱·계정과 파리 여행을 유지했다. 로컬 개발 서버의 nullable 시간대 컬럼을 반영하고 원래 데이터 값의 보존을 확인했다. 시간대를 Europe/Paris로 확인한 뒤 홈·목록은 9/30~10/2, 일정 A/B는 10:00/14:00으로 보였다. A를 10:01로 고쳐 Local/queue의 08:01Z를 확인한 뒤 10:00으로 복원했고 서버 08:00Z, 큐 0·실패 0을 보고했다. 경비의 9/30·10/2 날짜는 유지됐다. 앱 삭제나 계정 초기화는 하지 않았다.

이 native 관찰은 마지막 커밋마다 다시 실행한 결과가 아니다. Debug offline 관찰을 실제 통신 단절 성공으로 확대하지 않는다. 실제 단절 Local 저장·연결 복구 전체, 새 여행 생성부터 새 activation까지의 native 전체 흐름은 미확인이다. 임시 로그와 이미지는 보조 자료이며 이 문단에 핵심 조건·값·한계를 보존해 해당 경로가 없어도 검증 범위를 알 수 있게 했다.

## 원래 버그 보고서로 돌아온 정정

커밋 뒤 사용자가 남은 일을 물었을 때 Main은 실제 단절 저장·폼 전환·새 생성/활성화 전체 검증을 다음으로 제안했다. 사용자는 다음과 같이 원래 맥락을 되짚었다.

> “원래 버그도 보고 있었잖아?”

Main은 Git 제외의 9월 30일 보고서와 10월 4일 추가 보고서, 현재 코드를 다시 대조했다. 원래 목적은 발견한 버그를 해결하고 대표 흐름을 확인하는 것이었으며, 미확인인 모든 실환경 시나리오를 06 종료의 필수 선행으로 자동 추가할 근거는 없었다. 따라서 다음 순서를 **날짜·시간 선택창 초기 표시 문제**로 정정했다.

| 원래 관찰 | 현재 연결 |
| --- | --- |
| 일정 작성 화면 숨김·폼 중복·취소 경고 | 단일 초안·폼 개선 결과를 재사용한다. 옛 캡처만으로 현재 결함으로 다시 올리지 않는다. |
| 비활성 홈 안내 중복·본문 읽기 어려움 | 홈 요약 영역 개선 `e54fe42`. |
| foreground 명시적 재확인 부재 | 기존 Network Store에 연결한 `d588a19`. |
| 홈과 목록의 날짜 차이 | 이번 도시 시간대 일곱 커밋의 해당 부분. |
| 선택창 초기 날짜·시간 불일치 | 현재 코드에도 남아 있으며 다음 수정 대상으로 정리했다. |

선택창의 기존 관찰은 폼 날짜 2026-09-30인데 달력은 10월을 보여 주고, 폼 시간 09:00인데 시간 목록은 00부터 보이는 것이었다. 닫은 뒤 폼 값은 보존됐다. 최신 코드에서 CreateScheduleScreen은 DatePicker에 현재 날짜를 전달하지 않는다. TimePicker는 initialTime을 내부 선택 상태로 받지만 해당 행으로 스크롤하는 연결이 없다. 이 두 관찰은 도시 시간대 저장 기준과 다른 UI 문제이며, 이 기록 시점에는 수정하지 않았다.

다음 실행에서는 폼이 소유한 현재 값을 선택창에 전달하고 선택창이 그 값을 보이게 하는 책임을 확인한다. 열기·변경·확인·단순 닫기·다시 열기를 실제 소비자와 함께 대조한다. 확인·취소의 상세 동작은 현행 callback과 재현을 보고 정하며, 이번 기록이 새 reset 규칙을 확정한 것은 아니다. Ticket 10이 picker 책임을 소유하고 Ticket 06의 기존 보고서에서 발견한 후속으로 연결한다.

사용자는 이 정정 뒤 “그래 그럼 대화 전체 기록 이후 워크스페이스 남길거 잘 남겨놔줘”라고 요청했다. 현재 대화의 주요 결정·정정과 앞선 기록을 연결해 보존했으며 전체 채팅의 원문 전사본을 생성한 것은 아니다. 제공되지 않은 과거 assistant 응답이나 외부 검색 근거를 새로 만들어 채우지 않았다.
