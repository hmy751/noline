# 조회 조합 적용과 일정 생성 후속 문제

일정 상세, 경비 생성·수정의 연결 일정 조회, 홈 요약, 일정 생성·수정의 경로 계산용 조회에 공통 정책·Query 조합을 연결했다. 단건 일정·일정별 경비·여행별 목록의 원래 조회 범위와 Query key를 유지한다. 조회 제한·최초 오류·빈 결과·기존 데이터 갱신 실패를 구별하며, 수정 폼의 보조 조회는 열렸을 때만 실행한다. 일정 생성·수정은 조합의 query를 기존 경로 계산에 사용하고 저장 정책은 유지한다.

## 검증과 남은 문제

client Jest 42개 suite·406개 test가 통과했다. 전체 타입 검사는 기존 `shared/lib/mapbox.ts`와 `shared/services/offline-map/download.ts`의 오류 3개 때문에 성공하지 않았다. 시뮬레이터에서 확인한 경비 생성·수정, 일정 수정, 검색 후 일정 생성은 연결 상태 전환 뒤 미저장 값을 유지했다. 기존 디버그 override를 사용했으며 실제 통신 단절·모든 폼 입력 조합의 검증은 아니다.

활성 여행 일정 생성에서 다음 기존 문제를 재현했고, 이번에는 수정하지 않았다.

1. **수동 작성 중 온라인 복귀:** 입력 폼이 사라지고 검색 화면으로 돌아간다. 다시 제한 상태가 되면 값은 복원되지만, 이후 장소 선택 시 수동 제목·장소·주소가 검색 결과로 덮어써진다.
2. **장소 선택 후 오프라인 전환:** 일반 폼과 수동 폼의 렌더 조건이 동시에 성립한다. 접근성 트리에 두 폼의 필드·저장 버튼이 함께 남으며 캡처에서는 수동 폼이 주로 보인다.
3. **일반 폼 취소:** `Controller`를 `CreateScheduleScreen` 렌더 중 갱신한다는 React 경고가 발생한다. 취소의 `form.reset()` 이후 렌더 본문에서 날짜를 `setValue`하는 경로가 경고와 부합한다. 수정 검증은 남아 있다.

관련 코드는 `apps/client/src/screens/CreateScheduleScreen.tsx`의 검색·폼 렌더 조건, 취소와 초기 날짜 처리, `features/schedule/create-schedule/useCreateScheduleForm.ts`의 장소 선택 값 적용이다. 화면 파일은 비교 기준 HEAD `ffe022c`와 동일하고 해당 훅의 값 적용도 기존 코드다. 이번 공통 조회 조합이 새로 만든 회귀로 분류하지 않는다. 기존 자동 테스트가 생성 화면 전체를 장착하지 않아 이 전환 경계를 입증하지 못한다는 한계도 확인했다.
