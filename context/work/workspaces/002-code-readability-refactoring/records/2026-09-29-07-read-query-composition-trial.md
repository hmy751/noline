# 세 화면의 접근 조건·표시 판단 공통화 비교

사용자는 “이정도 양의 로직이면 훅이든 뭔가 빼는게 맞지 않나 … 단순히 나누는게 아니라 시스템을 보고 … 종합적으로 리뷰어를 불러서 판단시켜보자”라고 요청했다. 프론트 아키텍처 독립 리뷰 결과를 설명한 뒤 “일단 커밋 부터 해주고 하나만 적용해봐 구현 결과를 보고 판단하게”라고 실행 범위를 정했다. Main은 기존 경비 복구 작업을 `ed50ce1`로 저장하고, 제안 중 접근 조건·표시 판단 공통화 하나를 미커밋으로 적용했다. 구조에 대한 최종 수락은 아직 아니다.

## 이전 판단을 다시 본 이유

앞선 [일정 화면 직접 조합 결정](2026-09-29-04-schedule-policy-query-composition.md)은 소비자가 하나였고 훅 안에서 Policy 판단을 다시 구현하던 부담을 다뤘다. 이후 일정·경비 목록·경비 상세가 같은 캐시 노출, 조회 허용, 최초 오류와 갱신 오류 우선순위를 공유하게 됐다. 리뷰어는 코드·Spec·Ticket·기록·기존 테스트를 읽고 동일한 규칙을 세 화면에서 맞춰야 하는 변경 부담을 공통화 근거로 제시했다. Main도 세 화면과 이전 선택 기록을 직접 대조했다.

Policy는 계정·활성 여부·관측 조건의 기능 허용을, Query는 데이터·진행·실패·캐시를 소유한다. 화면에 무엇을 표시할지는 둘을 결합한 판단이다. 같은 접근 허용에서도 데이터 없음, 정상 빈 목록, 기존 데이터의 재조회 실패는 다른 표시가 필요하다. Policy에 모든 Query 결과를 넣거나 데이터 훅에 표시 계약을 넣으면 홈·폼의 조회까지 영향을 받으므로 기존 책임은 유지했다.

## 적용한 범위와 비용

[read-query.ts](../../../../../apps/client/src/screens/read-query.ts) 한 모듈에 조회 전 `useTripReadAccess`와 조회 후 순수 함수 `getReadQueryView`를 둔다. 전자는 기존 Policy를 표시용·실제용으로 두 번 호출하고 일정·경비 접근 결과를 함께 반환한다. 상세 화면이 경비와 연결 일정에 같은 관측 쌍을 쓰기 위해서다. 후자는 미선택·제한·로딩·오류·표시 가능 결과를 계산한다. 반환 타입은 매번 계산한 표시 결과이며 별도 데이터 복사·저장 상태·effect·복구 이력이 없다.

화면은 접근 조건 → 기존 데이터 훅 → 표시 계산 순서로 연결한다. 새 모듈과 반환 타입을 이해해야 하는 비용을 받아들이고, 표시 우선순위를 한곳에서 수정하도록 했다. Query key·staleTime·sync 무효화·Router는 바꾸지 않았다. 상세 ID 검색과 부재, 일정 지도 선택, 날짜·통화 가공, 폼 mount, 사용자 새로고침 표시는 원래 화면에 둔다. 안내 UI 통합과 Drawer 조회 조건 개선은 적용하지 않았다.

리뷰어는 상세의 대상 없는 목록 캐시·이전 조회 오류·Debug 강제 online·실제 offline 조합에서 무동작 재시도 버튼이 나올 수 있음을 소스로 보고했고 Main도 해당 분기를 확인했다. 이번 공통화는 이 기존 경계를 고치는 범위까지 포함하지 않았다. Drawer도 열린 동안 별도 Query observer가 활성이라는 현재 의미를 유지한다. 두 사항을 추출 성공으로 해결된 것으로 간주하지 않는다.

## 확인한 결과와 다음 판단

Main은 변경 전 일정·경비 화면 2개 suite의 42개 test와 변경 후 전체 client 40개 suite의 386개 test 통과를 직접 확인했다. 사용한 전체 명령은 client에서 `node ../../node_modules/jest/bin/jest.js --config jest.config.cjs --runInBand`다. 기존 화면·정책·sync·활성 전환 검사를 재사용했고 추출 내부 구현을 따라가는 새 테스트는 만들지 않았다. 변경 네 파일의 Prettier, ESLint(기존 Prettier plugin 충돌 규칙 제외), `git diff --check`가 통과했다. 타입 검사는 기존 Mapbox 좌표 tuple과 OfflinePack 필드 오류 3개 때문에 전체 성공이 아니다.

native 표시와 repository 등 기존 mock 범위는 유지되며 실기기·실서버 검증은 아니다. 다음은 사용자가 이 구현의 읽기·변경 부담을 보고 채택 또는 조정하는 일이다. 이번 적용은 미커밋이며 남은 개선 후보와 2-C를 자동으로 계속 진행하지 않는다.
