# Ticket 06 네트워크 정책과 구현 범위 합의

2026-09-15~16의 Ticket 06 조사·정책 인터뷰에서 선택한 내용과 이유를 보존한다. 현재 실행 기준은 [Ticket 06](../current/memory/tickets/06-app-startup-lifecycle.md), 공통 범위는 [Spec](../current/memory/spec/01-problem-goal-scope.md), 다음 행동은 [state](../current/state/index.md)가 소유한다. 이 기록은 제품 구현 완료나 테스트 결과 보고서가 아니다.

## 작업의 출발점과 범위 선택

사용자는 앱 초기화 문제 중 네트워크 관측·소비 정책부터 다루기로 했다. 기존 구조는 Selective Local-First이며, 활성 여행의 Local SQLite와 비활성 여행의 Server API를 대상별로 선택한다. 따라서 모든 데이터를 Local에서 읽게 만들거나 네트워크 하나로 전체 앱을 막는 방향은 맞지 않는다.

사용자는 “이 전체 아키텍쳐는 선택적 라우팅이야”, “003 애매하게 따로 분리보다는 여기서 그냥 할 수 있는 범위는 하면 좋겠어”라고 범위를 명확히 했다. Network Store 내부 동작과 Router·Policy·화면·sync 시작까지 연결하는 데 필요한 수정은 002-06에서 함께 수행한다. 기존 003은 관련 결함의 재현 근거로 사용한다. 트랜잭션 원자성, sync engine의 실패·재시도, 파괴적 cleanup은 각각 14·15·16의 후속 책임으로 남는다.

## 비활성 여행을 볼 수 없을 때의 경험

네트워크가 끊겨도 여행이 사라진 것처럼 보이거나 탭이 닫히면 사용자는 데이터가 없어졌다고 이해할 수 있다. 활성 여행은 이미 준비된 Local 데이터를 계속 사용할 수 있으므로, 네트워크 변화로 활성 여행 자체를 바꿀 이유도 없다.

그에 따라 여행 기본 정보·탭·사용자 선택을 유지하고, 비활성 여행의 일정·경비 내용에 제한 안내를 표시하기로 했다. 이미 offline일 때 새 비활성 여행을 선택하려 하면 기존 선택을 유지하고 연결 뒤 선택하도록 안내한다. 보던 비활성 여행에서 연결이 끊긴 경우에는 그 여행 선택을 유지하며 오프라인 준비된 활성 여행으로 돌아갈 행동을 제공한다. 활성 여행이 없으면 이 기기에서 쓸 수 있는 여행이 없다고 설명한다.

복구 시 같은 비활성 여행을 보고 있을 때만 다시 조회한다. 사용자가 이동한 뒤 원래 여행으로 강제 복귀하지 않는다. 복구 조회가 성공하면 한 번의 토스트면 충분하다는 사용자 판단을 채택했다. 실패는 일반 조회 오류로 처리한다. 초기 연결 확인과 단순 재확인 완료는 장애 복구 토스트의 대상이 아니다.

React Query 캐시는 앞서 서버에서 받은 응답이 앱 메모리에 남아 있는 것이고, 활성 여행의 Local SQLite와는 다르다. 새 요청을 막아도 이전 data가 남을 수 있다는 설명 뒤 사용자는 “복잡도가 너무 높아질것 같아 … 그냥 자연스레 제한을보여주는걸로 하자”라고 선택했다. 캐시를 삭제하거나 별도 관리하지 않고 화면에서 접근 정책에 따라 제한 안내를 선택한다. 캐시 존재를 오프라인 이용 권한으로 취급하지 않는다.

## unknown을 초기 이후에도 쓰기로 한 이유

처음에는 초기 네트워크 판정 전을 unknown으로 표현하는 것부터 논의했다. 이후 isConnected와 isInternetReachable에 null이 올 수 있다는 소스를 확인하면서, 이미 사용 중이더라도 연결 가능 여부가 다시 미확정이면 unknown이 될 수 있도록 확장했다.

사용자가 우려한 점은 정상적인 인터넷 환경에서 확인할 때마다 unknown이 되어 화면이 자주 바뀌는지였다. Main은 설치 NetInfo 11.4.1의 reachability 코드를 읽고 fetch·timer를 대체한 임시 특성화로 확인했다. 정상 true 상태에서 주기 probe를 시작해도 기존 true를 유지하며, 같은 값은 중복 통지하지 않았다. false 이후 연결을 다시 확인하는 일부 흐름은 null을 거쳤다. 이 설명 뒤 사용자는 “이정도면 unknown에 반영해도 엄청 불안하고 그렇지는 않겠어”라고 판단했다.

채택한 변환은 두 신호 중 명시적 false가 있으면 offline, 둘 다 true이면 online, 나머지 미확정 조합은 unknown이다. unknown의 적용은 초기로 제한하지 않는다. 다만 재확인 버튼을 누른 사실만으로 기존 확정 상태를 unknown으로 강제 변경하지 않는다.

별도 weak/degraded 상태와 선제적인 debounce·전환 지연은 도입하지 않는다. 약한 신호의 정도를 별도 관리하기보다 실제 관측과 개별 요청 오류를 처리하고, 자동 여행 전환·중복 sync·반복 토스트·불필요한 화면 재생성을 막기로 했다. 실기기에서 실제 반복 부작용이 관찰되면 debounce나 NetInfo 설정을 재검토한다. 실기기 확인을 이번 정책 선택의 선행 조건으로 두지는 않았다.

### NetInfo 조사 근거와 한계

앞선 Main이 확인한 설치 버전은 11.4.1이며 [reachability 구현](https://github.com/react-native-netinfo/react-native-netinfo/blob/v11.4.1/src/internal/internetReachability.ts)과 [기본 설정](https://github.com/react-native-netinfo/react-native-netinfo/blob/v11.4.1/src/internal/defaultConfiguration.ts)을 대조했다. iOS RNCNetInfo.m은 이 버전에서 native isInternetReachable을 제공하지 않아 JS probe를 사용하며, Android는 native 연결 검증값을 사용할 수 있다. 이전 Ticket의 “iOS 기본 Native Reachability”라는 설명은 이 조사로 교정한다.

JS 기본 설정에서 성공 후 다음 검사 대기는 60초, 실패 후 대기는 5초, 요청 timeout은 15초다. 이는 iOS를 포함해 JS probe가 사용되는 조건의 설정이며 모든 기기에서 동일한 이벤트 주기를 보장하지 않는다. probe 대상의 응답은 Noline API 자체의 정상 여부를 뜻하지 않는다.

임시 mock에서 관찰한 흐름은 초기 null→204 응답 뒤 true, online 주기 검사 중 true 유지, 실패 응답 뒤 false, false 후 연결 재확인에서 null→성공 뒤 true였다. 실제 기기의 연결 변동 빈도나 오판율을 측정한 결과는 없다. 라이브러리 listener 등록 자체에도 최초 상태 조회가 있으므로 앱의 명시적 fetch를 줄여도 native 호출이 반드시 한 번이 되는 것은 아니다.

refresh는 최신 연결 정보를 돌려주지만 후속 인터넷 probe 완료까지 보장하지 않는다. 내부 초기 조회·refresh의 실패나 지연을 앱에서 모두 복구한다고도 보장하지 않는다. 이 제약 때문에 listener의 늦은 결과와 제한 영역의 안내를 함께 사용한다.

## 10초 안내와 재확인

초기 확인 실패·장시간 미응답은 offline으로 추정하지 않고 unknown을 유지한다. 네트워크 때문에 앱 전체 Splash를 연장하지 않으며 활성 여행 Local 이용은 계속한다. 비활성 여행 Remote 조회·Network-First Service·sync는 실제 online까지 기다린다.

사용자의 “그래 10초 하자”에 따라, unknown에서 연결 확인 중 안내가 10초 지나도 확정되지 않으면 확인 불가와 재확인 행동으로 바뀐다. 이 시간은 UI 안내 기준이며 요청 timeout이나 전역 offline 전환 기준이 아니다. 같은 null 관측이 올 때마다 시간을 초기화해 무한 확인 중으로 남게 하지 않는다.

재확인은 기존 listener와 NetInfo.refresh를 이용하는 설계다. 늦은 확정값은 재확인 버튼을 누르지 않아도 반영한다. background→active에서 한 번 관측을 갱신하는 배선, 재확인 연타·안내 시간 재시작·늦은 응답 억제는 구현에서 구체화한다. 초기 제안의 “unknown일 때만 foreground 재확인”은 확정된 상태도 stale할 수 있다는 조사 때문에 고정 제약으로 채택하지 않는다.

## 쓰기는 Router와 기존 오류 흐름에서 처리

온라인 비활성 여행의 수정·삭제는 새로 허용할 정책이 아니라 기존 정상 지원 계약이다. 사용자는 “온라인 비활성 여행은 당연히 수정삭제 정식지원해야하는거 아니야?”라고 분명히 했다. 다른 활성 여행이 있다는 이유로 Local로 잘못 분기하거나 Local에 child가 없어서 실패하는 문제는 이 계약을 정상화할 구현 문제다.

unknown/offline의 비활성 여행은 서버 전송을 시작하지 않는다. 활성 여행은 기존 Local 저장·queue 경로를 유지한다. 입력 유지는 폼을 자유롭게 작성하되 저장 차단 때 초기화하거나 닫지 않는다는 뜻이다. 별도 draft 저장이나 지연 실행 관리자가 아니다.

처음에는 버튼에서 공통 정책을 확인하는 안도 나왔지만 사용자는 “버튼 말고 라우터에서 일괄 처리하게 할수는 없을까?”라고 제안했다. Router가 실행 순간 서버 접근을 거부하고 제한 이유를 오류로 전달하며 기존 화면 오류 처리에서 안내하는 방향을 채택했다. 버튼마다 unknown 분기를 복제하지 않고 Router 안에서 Alert·toast를 실행하지 않는다. 일반 저장 실패 문구가 제한 이유를 덮는 기존 연결만 정리한다. 복구 후 저장을 자동 실행하지 않고 사용자가 재시도한다.

### 전송 후 응답 유실은 일반 요청 처리 범위

Main은 이미 전송한 요청의 결과를 모를 때 별도 복구 대조를 제안했지만, 사용자는 “비활성 여행의 온라인이면 … 일반 앱 동작과 같은 상황”이므로 거기에 맞게 처리하자고 정정했다. 이 정정을 따라 별도 결과 추적·자동 대조 시스템을 이번 필수 정책에서 제외했다.

이미 보낸 요청은 일반 성공·실패 처리를 사용한다. 네트워크 상태 변화만으로 취소하거나 자동 재전송하지 않으며 실패 안내·입력 유지·사용자 재시도를 연결한다. 서버가 반영했으나 응답만 잃은 가능성 자체가 사라지는 것은 아니다. 관련 재시도 결함은 코드 계약에서 확인하며, client ID를 유지한다는 사실만으로 서버 중복 처리가 보장됐다고 주장하지 않는다.

## Debug는 화면 확인, 실제 쓰기는 보류

기존 기능은 개발 메뉴와 online/offline 강제 설정이다. [Network Store](../../../../../apps/client/src/shared/store/network.ts)는 realStatus와 overrideStatus를 따로 저장하지만 getStatus가 override를 우선해 Router 요청 판단까지 바꾼다. __DEV__는 메뉴 표시 조건으로, 서버 데이터 격리 장치가 아니다.

앞선 설정 조사에서는 development가 LAN 주소의 API와 로컬 PostgreSQL noline_dev, production이 Render API와 Neon PostgreSQL을 가리켰다. 확인한 파일은 client의 babel.config.js·eas.json·환경 파일, server의 config·DB 연결·환경 파일이다. 환경 파일은 자격증명을 출력하지 않고 연결 대상만 선별해 읽었다. 실제 실행 앱의 APP_VARIANT, 배포 서버 환경변수와 데이터 내용·격리는 확인하지 않았고 서버 조회도 하지 않았다.

사용자는 “화면만 일단 debug로 덮을까? 쓰기는 안되고 추후 분리 설정 확인하고 하게”라고 선택했다. Main은 Local 변경과 queue도 나중에 서버 쓰기가 되므로 차단 범위에 포함한다고 설명했고, 기존 override 존재 여부를 사용하는 기능 분리 설명 뒤 사용자가 “그래 그렇게 하자”라고 동의했다.

따라서 강제 상태는 화면 표시·제한 이유에 사용하고 실제 요청 가능 여부는 실제 관측을 사용한다. override 중 Trip·Schedule·Expense 쓰기, Local 변경·queue 추가와 새 sync 전송은 막는다. 해제 후 실제 상태의 정상 동작으로 돌아간다. 이미 전송된 요청의 원복은 보장하지 않는다. 새 앱 전체 debug 모드 시스템은 만들지 않는다. 실제 쓰기를 포함하는 실험은 환경 격리를 확인한 뒤 재검토한다.

## 문서 반영과 아직 하지 않은 일

이 기록은 현재 대화에 보이는 사용자 발화와 앞선 Main의 조사·임시 검사 보고를 바탕으로 작성했다. 짧은 인용은 범위·선택을 바꾼 사용자 발화이며 대화 전체의 전사가 아니다. 2026-09-16 문서 작업의 코드 기준 HEAD는 30deac5였고, Network Store·Router 소비 연결은 앞선 turn에서 직접 재확인했다. NetInfo mock과 client baseline 18개 test는 앞선 실행 보고로 보존하며 이번 문서 작업에서 재실행하지 않았다.

기존 Maintain generation 2의 실패 뒤 자동 반영되지 않은 논의가 누적돼 Ticket과 state에 버튼 중심 안·미정 10초·추가 응답 유실 정책 논의가 남아 있었다. 사용자가 Main에게 Work 문서 갱신을 명시적으로 요청해 현재 문서로 복원했다. 자동 처리의 실패·pending 이력은 변경하지 않았으며, 이번 수동 갱신을 과거 자동 event의 성공이나 재처리 완료로 간주하지 않는다. 민감한 Maintain runtime 원문은 문서 근거로 열거나 복제하지 않았다.

남은 것은 실행 코드에서 상태·요청·화면·sync 연결을 구체화하고 구현·검증하는 일이다. 문서 반영만으로 제품 동작, 실제 기기 관측, 환경 격리, Ticket 06 전체 수락을 주장하지 않는다.

작성 뒤 변경한 문서 14개의 로컬 링크 155개에서 누락된 대상을 찾지 않았고 git diff --check가 통과했다. 명시적 Workspace Recover도 성공해 Spec 다섯 파일과 갱신한 state가 재진입 packet에 포함되는 것을 확인했다. 이 검사는 문서의 경로·구성 확인이며 제품 테스트나 자동 Maintain 복구 검증이 아니다.
