# sync 시작 조건과 세션 종료 대기 연결

앱 준비 경계를 저장한 `8a1a3ea` 다음 실행으로, 인증·실제 연결·Debug 강제 설정에 따른 sync 시작과 수동 요청의 우회를 정리했다. 추가 선택은 진행 중 sync와 로그아웃의 순서였고 사용자가 이번 범위에 포함하도록 승인했다. Ticket 06 전체 완료나 최종 수락은 아니다.

## 종료 순서를 선택한 이유

사용자는 구현 전에 “그래 하기전에 구체적으로 논의하거나 물어볼거 있어?”라고 물었다. Main은 현재 Provider가 실제 네트워크만 구독하고, Debug 화면이 engine의 `triggerSync`를 직접 호출하는 것을 확인했다. 로그아웃은 cleanup만 기다린 뒤 DB를 reset하고 인증을 비우므로, 진행 중 sync가 뒤늦게 DB에 쓰는 문제는 로그인 여부 확인만으로 해결되지 않았다.

Main은 “로그아웃이 확정되면 새 sync를 막고, 실행 중인 sync가 성공하거나 실패해서 끝난 뒤 세션과 DB를 정리하는 방식”을 추천하면서, 앞서 후속 범위로 남겨둔 동작을 이번에 포함할지 물었다. 사용자는 “그래 그렇게 하자”라고 답했다. 기다리는 동안 로그아웃 완료가 늦어지는 비용을 받아들이며, 진행 중 요청 취소나 새 timeout을 추가하는 선택은 하지 않았다. 서버 로그아웃으로 sync의 인증을 먼저 무효화하지 않도록 서버 요청도 대기 뒤로 옮겼다.

종료 확정은 기존 큐 확인에서 종료 가능한 결과를 얻거나 강제 종료를 선택한 시점이다. 미동기화 안내로 보류할 때는 세션과 sync 실행을 유지한다. 서버 로그아웃 실패 시 로컬 종료를 계속하고, 서버 계정 삭제 실패 시 로컬 세션을 유지하는 기존 차이를 보존한다.

## 테스트 우선과 실제 구현

앞선 “진행하기전에 시나리오 짜려는 기능에 대한 테스트 먼저 작성하고 하자” 지시를 이어 적용했다. 기존 Provider에 로그인 전 차단·강제 설정 해제 자동 요청·로그아웃 후 새 실행 차단·세션 만료 복구 테스트를 먼저 추가해 네 개 실패를 직접 확인했다. 실제 Provider와 로그아웃 서비스의 지연 sync 테스트도 구현 전에 작성했고, 로그아웃·회원 탈퇴가 종료 대기 전에 서버/DB 처리를 진행하는 세 개 실패를 확인했다. 기존 동작 보존 사례는 통과했다.

sync lifecycle 모듈에 실행 순간의 조건·공유 Promise·상태·중첩 일시 중단을 모았다. Provider는 인증·세션 만료·실제 네트워크·override·종료 중단을 구독하고 실행 불가→가능 변화에서 요청한다. 일반 rerender와 작업 완료는 새 자동 요청을 만들지 않는다. 공통 Promise는 엔진 시작과 구독자 반응보다 먼저 등록해 React 밖 재진입과 Provider 재mount에서도 잠금을 공유한다. 동시 요청은 보류하며 뒤 실행을 예약하지 않는다.

로그아웃/탈퇴는 새 sync 중단→진행 중 sync 종료→서버 세션 종료→pending cleanup 중단/종료→큐·DB·인증·여행 선택·캐시 정리 순서로 연결했다. 중단은 `finally`에서 해제하며 진행 중 sync 실패도 로그아웃을 막지 않는다. Debug는 Context를 사용하고 보류 결과를 성공으로 표시하지 않는다. 새 의존이 auth barrel을 통해 돌아오는 순환을 피하도록 engine과 sync API의 인증 import를 실제 모듈로 좁혔다.

추가 점검에서 DB reset 실패 때 인증 상태가 남을 수 있어, DB의 사용 가능 상태도 실행 직전에 확인했다. 준비 상태가 해제됐을 때 로그인·online만으로 새 실행을 열지 않는 테스트를 먼저 실패시킨 뒤 보완했다. DB 상태 조회 자체는 파일을 열거나 초기화를 수행하지 않는다. 초기 startup 재시도 UI를 reset 실패 뒤의 별도 복구 화면으로 확대하지 않았다.

Profile의 미동기화 확인 창에서 강제 종료를 선택하면 기존 진행 표시가 빠지는 문제도 테스트로 먼저 재현했다. sync 종료 대기가 추가됐으므로 이 경로도 진행 표시와 두 종료 버튼의 비활성화를 유지하도록 보완했다. 화면 전체 스타일이나 메뉴 구조는 바꾸지 않았다.

## 최종 검사와 보장 한계

Main이 직접 실행한 전체 client Jest는 18개 suite·185개 test 통과다. Provider 15개·공통 실행 10개·sync/종료 9개·Debug 4개·강제 종료 대기 표시 2개와 기존 검사들을 포함한다. 변경한 TypeScript 16개 파일의 scoped ESLint는 기존 Prettier 플러그인 연동 문제 때문에 그 규칙만 제외했고 오류 0개·기존 경고 3개다. Prettier는 별도 검사하고 diff whitespace 검사도 통과했다. client 타입 검사는 기존 Mapbox 좌표 1개·OfflinePack 필드 2개 오류만 남는다.

DB·네이티브·토큰 저장·서버를 대체한 fixture 검사이며 실제 Expo 실행, 기기 DB 보존, 서버 전송 성공 증거는 아니다. 엔진이 내부 오류를 잡고 resolve하는 한계는 이번에 고치지 않아 `completed`는 엔진 호출 완료이며 모든 전송 성공을 뜻하지 않는다. 개별 전송의 오류 집계·FAILED 재시도·pull 타입은 Ticket 15, 실제 원자성은 14, cleanup 보존 조건은 16에 남는다. 인증 route guard 전체와 대상별 Router·제한/복구 화면·foreground 재확인도 남는다.

기록 시점의 이번 변경은 미커밋이다. 현재 계약은 [Ticket 06](../current/memory/tickets/06-app-startup-lifecycle.md), 읽을 코드·테스트는 [output](../output/index.md), 다음 후보는 [state](../current/state/index.md)가 소유한다. Main이 기존 unbound session에서 해당 Workspace의 bounded bootstrap과 guarded apply로 기록했으며 activation이나 제품 Verify receipt를 생성하지 않았다.
