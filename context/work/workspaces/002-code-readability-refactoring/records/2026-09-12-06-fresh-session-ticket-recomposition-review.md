# 대화 맥락 없는 새 세션의 Ticket 재구성 검토

## 검토 목적과 근거

사용자는 Ticket 05를 구현 전 상태로 그대로 두고, 현재 Spec을 기준으로 남은 Ticket 구성을 다시 검토하되 기존 대화를 모르는 새 세션이 저장된 지침과 Workspace 문서만으로 기대를 복원하는지 확인하려 했다. 첫 요청은 재구성안과 이유만 요구했고 Ticket 문서와 제품 구현의 변경은 금지했다.

사용자가 전달한 fresh-session 보고 원문은 SHA-256 `e6e9ddf942b0ff7053c4604ea78c8d326c2fd2a6b8d5bd6ff008cc5d7b19f2ed`인 임시 attachment였다. 임시 경로에 지속적으로 의존하지 않도록 이 기록에 판단에 필요한 내용을 보존한다. 보고자는 Workspace를 generation 1로 연결하고 explicit Recover가 성공했다고 밝혔으며, 연결 전에 시작된 응답은 사후 귀속하지 않고 다음 요청부터 연결된 Workspace로 처리된다고 구별했다. Main과 Maintain은 이번 판단에서 그 운영 상태나 보고서의 코드별 관찰을 독립 재검증하지 않았다.

## fresh session이 제안한 구성

보고서는 현재 다섯 Ticket만으로 Spec 목표를 달성하기 부족하다고 판단했다. 01·02·04의 완료와 사용자 수락은 각 범위에 한정해 유지하고, 03은 구현 완료·수락 대기, 05는 별도 판단 상태로 보존했다. 05의 Schedule server 직렬화 책임은 다른 Ticket이 흡수하지 않고 관계만 표시하도록 했다.

남은 범위는 분석 항목명을 그대로 옮기기보다 함께 이해·수정·검증할 책임으로 다음처럼 묶었다.

- 06: Trip·Schedule client API 경계
- 07: 일정 생성·수정 입력 생명주기
- 08: 경비 생성·수정 입력 생명주기
- 09: 일정 저장 이후 경로 준비 책임
- 10: 날짜 기반 선택·그룹 계산
- 11: Data Entity local mutation과 Router 선행조건
- 12: Sync 실행 결과·재시도·pull 타입
- 13: 미전송 데이터 보존과 파괴적 정리
- 14: 활성화와 offline-prep 완료 상태
- 15: 경비 카테고리 표시와 실제 컴포넌트 소유권
- 16: Schedule을 제외한 server route 경계
- 17: 기존 분석 관점과 추가 후보를 완료·유지·별도 버그·보류·미확인으로 연결하는 종료 검토

제안은 03 수락 판단과 비교적 국소적인 06·10·15를 먼저 처리하고, 07→08→09의 입력·저장 흐름, 11→12→13→14→16의 데이터 보존 위험 범위, 마지막 17의 전체 충분성 판단 순서를 제시했다. 모든 Ticket 문서를 먼저 만드는 것을 실행의 일괄 선행 조건으로 두지 않고 승인 뒤 다음 실행에 필요한 Ticket부터 작성하도록 했다. 알려진 계약 충돌은 리팩토링의 보존 대상으로 고정하지 말고 별도 결함 판단에 연결했다.

보고자는 이번 단계에서 Workspace 문서와 제품 코드를 수정하지 않았고 기존 미커밋 `current/state/index.md`와 `output/index.md`도 그대로 보존했다고 밝혔다.

## Main이 평가한 성과

Main은 이번 구성이 기대한 방향에 상당히 가까워졌다고 평가했다.

- 기존 다섯 Ticket을 전체 작업의 상한으로 삼지 않고 Spec과 분석에서 남은 책임을 찾아냈다.
- 07은 화면·form hook·수정 Drawer·picker를 입력 생명주기로, 09는 저장 이후 경로 준비를, 12는 sync 실행부터 완료 표시까지를 함께 보아 한 파일의 표현 수정에 머물지 않았다.
- 완료·수락된 범위와 03·05의 미결 상태를 구별하고 대표 수정 몇 개로 전체 완료를 선언하지 않도록 종료 검토를 제안했다.

따라서 저장된 운영 지침과 Workspace 문서만으로 사용자의 폭넓은 개선 기대를 복원하는 단계는 상당 부분 성공했다. 이 결론은 Ticket 구성 계획에 한정되며 실제 구현의 깊이나 완료 판단을 입증하지 않는다.

## 보완이 필요한 간격

Main은 현재 제안을 바로 실행 가능한 Ticket으로 확정하기 전에 세 간격을 보완해야 한다고 판단했다.

1. 06·07·08 등은 확인할 상황과 관찰된 문제를 잘 제시하지만, 조사 뒤 어떤 코드상의 부담이 해소돼야 완료인지가 약하다. 특히 06은 Ticket 04의 접근, catch와 로그를 중심으로 다시 작은 수정으로 축소될 여지가 있다. 관찰된 문제는 출발점이지 맡은 결과의 상한이 아니라는 의미를 Ticket 결과·범위·완료 근거에 연결해야 한다.
2. 11·12·13처럼 계약과 데이터 보존이 얽힌 범위에서 결함을 별도로 분리한다면, 그 결함을 남겨도 현재 개선이 가능한지, 선행 해결이 필요한지, 판단 전에는 무엇을 완료할 수 없는지와 담당을 밝혀야 한다. 분리로 필요한 일이 담당 없이 남아서는 안 된다.
3. 17의 종료 검토는 유효하지만, 기존 분석의 어느 부분을 각 Ticket이 맡고 어디가 미배정인지 현재 구성 단계에서도 대략 보여 줘야 한다. 전체 누락을 마지막에 처음 발견하는 구조만으로는 지금 제안의 충분성을 판단하기 어렵다.

코드 위치와 동작에 관한 fresh-session의 개별 주장은 이번 Main이 재검증하지 않았다. 보고서는 Ticket 문서와 제품 구현을 변경하지 않았으므로 새로운 제품 결과, 검증 또는 사용자 수락도 없다.

## 다음 판단

Main은 구성 방향을 유지한 채 같은 fresh session에서 위 세 간격을 보완하고, 그다음 07처럼 여러 연결을 다루는 Ticket 하나를 실제 실행 가능한 수준으로 작성해 맡은 결과·필요한 범위·완료 근거의 연결을 확인하자고 권고했다. 이 단계에서도 실제 제품 구현의 깊이와 완료 판단은 별도 후속 검증으로 남는다.

이 권고의 채택, Ticket 문서 반영과 실행 시작은 아직 사용자가 결정하지 않았다.
