# 외부 자료를 참고한 Project context 반영 기준과 재구성 검증 방향

날짜: 2026-09-14

이 기록은 Matt Pocock의 `skills`와 Peter Steinberger의 `agent-scripts`를 조사한 뒤, 기존 Project context 합의에 무엇을 보강할지 정리한 내용과 `current`의 역할을 후속 테스트에서 다시 판단하기로 한 방향을 보존한다. 사용자는 직전 정리를 앞선 기록과 별개 문서로 남기도록 요청했다.

[앞선 구성·읽기·갱신 합의](2026-09-14-05-project-context-structure-reading-and-maintenance.md)는 최초 문제 제기, 세 폴더를 유지한 경위, guidance에 기대한 역할과 초기 연구를 바탕으로 한 논의를 보존한다. 이 문서는 그 기록을 덮어쓰지 않고 외부 조사로 구체화한 반영 기준과 이후 검증 방향을 이어 남긴다. 두 기록 모두 후속 지침 작업의 근거이며, 현재 Project 관리 계약이나 제품 본문을 이미 수정했다는 뜻은 아니다.

논의 대상은 Project context 구성 자체다. Workspace 002의 완료된 Ticket 01–05는 이후 구성을 확인할 사례이며, 미완료 Ticket의 실행이나 제품 전체 문서 개편으로 범위를 넓히지 않는다.

## 이번에 분명히 한 결정: current는 유지하고 재구성 결과로 판단한다

외부 조사 결과를 들은 사용자는 다음과 같이 말했다. 발췌는 현재 Main 대화의 사용자 원문이며 줄바꿈으로 두 구간을 나눴다.

> "current를 일단 폐기는 안하고 이따 나중에 지침 수정 작업하면 테스트를 해볼생각이야"

> "지금 있는 문서들 다시 원복시키고 그때 다시 판단해보자 current의 존재 이유를"

따라서 `common/current/guidance` 물리 경계는 유지한다. `current`를 없애거나 반드시 축소한다는 결론을 지침에 먼저 넣지 않는다. 후속 지침 수정과 기존 문서 원복·재구성을 통한 테스트에서, 가이드와 코드를 함께 읽어도 별도로 유지할 현재 맥락이 무엇인지 다시 판단한다.

여기서 원복은 후속 검증을 위한 방향이다. 정확히 어떤 문서를 어느 시점으로 되돌릴지는 아직 정하지 않았다. 이 발화를 제품 코드, Ticket, 기존 records나 관련 없는 변경의 포괄 원복 승인으로 해석하지 않는다. 실제 원복 전에는 대상·기준 상태·사용자 변경과 연결된 소비 경로를 확인해야 한다. 이번 기록 작성에서는 원복을 실행하지 않는다.

## 외부 조사에서 참고한 것과 비교의 한계

Main은 두 자료를 별도 조사 담당에게 나눠 맡기고, 문서 작성 기준·domain 문서 역할·문서 목록 코드·주제 가이드 등 핵심 원문을 직접 대조했다. 확인한 것은 로컬 문서·코드·설정의 내용과 연결이다. 조사 대상 스크립트를 실행하거나 실제 작업에서 읽기·갱신 효과를 측정한 결과는 아니다.

### Matt 자료: 남길 가치와 함께 읽을 범위

[문서 작성 기준](/Users/hammyeong-yeon/Desktop/skills/skills/productivity/writing-for-agents/SKILL.md)은 환경도 사실의 원천으로 본다. 설정이나 코드 한 곳에서 바로 확인할 내용을 문서에 다시 쓰면 별도로 유지할 복사본이 생긴다. 반면 쉽게 드러나지 않는 관례·선택 이유·주의점과, 찾아 이해하는 비용이 큰 내용은 문서로 남길 가치가 있다. 이것은 코드에 있는 사실을 모두 제외하라는 규칙이 아니다.

같은 기준은 한 개념의 정의·규칙·주의점을 함께 배치하고, 해당 문서를 읽는 작업에 공통으로 필요한 내용은 본문에, 일부 작업에서만 필요한 내용은 읽을 조건을 밝힌 별도 자료에 두도록 한다. 내용의 종류가 다르다는 이유만으로 의미를 흩뜨리지 않으면서 선택적 읽기를 가능하게 하는 기준으로 참고했다.

다만 [domain-modeling](/Users/hammyeong-yeon/Desktop/skills/skills/engineering/domain-modeling/SKILL.md)의 `CONTEXT.md`는 구현 현황을 포함하는 Project 맥락 전체가 아니라 용어집에 한정된다. 단순히 용어집을 읽는 일은 별도 skill이 아닌 다른 작업에서도 수행하는 기본 습관으로 다룬다. 이 작은 용어집을 Noline의 세 층 전체와 직접 대응시키거나, 이 사례만으로 새 읽기 스킬의 필요 여부를 확정하지 않는다.

### Peter 자료: 읽을 조건과 주제별 가이드

[문서 목록 도구](/Users/hammyeong-yeon/Desktop/agent-scripts/scripts/docs-list.ts)는 문서의 짧은 설명인 `summary`와 읽을 상황인 `read_when`을 목록으로 보여 준다. 작업과 맞는 조건을 발견하면 AI가 해당 본문을 읽는 방식이다. 참고할 핵심은 YAML 형식 자체가 아니라, 언제 읽어야 하는지도 문서와 함께 관리한다는 점이다.

[macOS 배포 가이드](/Users/hammyeong-yeon/Desktop/agent-scripts/docs/RELEASING-MAC.md)는 적용 전제, 버전 계약, 실행 방법, 검증과 실패 복구를 한 주제 안에서 설명한다. 앱별 설정값과 실행 명령은 실제 설정·스크립트가 소유하게 한다. 자기 범위의 판단과 수행에 필요한 내용을 충분히 설명하는 것과 모든 현재 값을 본문에 복제하는 것은 다르다는 사례다. 배포 절차 자체를 Noline에 도입하는 제안은 아니다.

발견과 실제 적용의 보장은 구분해야 한다. README는 메타데이터를 강제한다고 설명하지만, 확인한 목록 도구는 `read_when` 누락을 오류로 처리하지 않고 메타데이터 문제로 실패 종료하지도 않는다. 필요한 본문을 실제로 읽었는지는 확인하지 않는다. 이 자료를 완성된 자동 문서 관리 체계로 간주하지 않았다.

두 자료 모두 일부 판단 기준이나 작업 절차를 skill 본문이 소유한다. 따라서 Noline의 '기준 본문은 문서가 소유하고 skill은 이를 적용한다'는 배치를 입증하는 사례는 아니다. 유용한 기준을 참고하되 그 포장이나 책임 배치까지 복제하지 않는다. 두 저장소에서 Noline과 같은 `common/current/guidance`의 적정 경계·파일 수나 관리 효과를 입증하는 근거도 확인하지 못했다.

## 후속 지침에 반영할 기준

아래는 외부 방식으로 기존 합의를 대체하는 것이 아니라, 기존 합의에 조사 결과를 더해 Main이 사용자에게 정리한 반영 방향이다. 사용자는 이 정리를 별도 기록으로 남기도록 요청했다. 실제 지침 문구·파일 배치와 테스트 결과는 아직 없다.

### 지속되는 주제와 관련 작업을 중심으로 구성한다

Ticket이나 조사 결과마다 Project 문서를 만들지 않는다. 다음 관련 작업에서 반복해서 이해하고 판단해야 하는 주제를 중심으로 본문을 구성한다.

`common`은 제품·데이터·시스템의 의미와 핵심 제약을, `guidance`는 관련 작업에서 그 의미를 적용하고 변경하는 기준을 맡는다. 둘은 추상적인 내용과 상세한 내용으로 나뉘는 것이 아니다. Guidance는 단순 조언이나 수행 순서가 아니라 계약·이유·구체적인 적용·판단·검증을 제공하는 작업 가이드다. API 가이드라면 공통 원칙과 Schedule 같은 기능에 적용되는 내용을 함께 설명한다.

### 함께 이해할 내용은 모으고, 따로 읽을 이유가 있을 때 나눈다

한 개념의 정의·규칙·예외·주의점을 여러 파일에 흩뜨리지 않는다. 그 주제를 읽는 작업에 공통으로 필요한 내용은 본문에 두고, 일부 작업에만 필요한 상세는 읽을 조건을 밝혀 분리한다. 책임 종류나 문서 길이만으로 기계적으로 나누지 않는다.

기준 본문은 하나로 유지하되, 다른 문서를 이해하는 데 필요한 전제를 짧게 다시 설명하는 것은 허용한다. 링크는 구현 상세나 근거를 다시 확인하는 경로이며, 본문이 맡은 의미를 독자가 여러 링크에서 조립하도록 맡기는 수단은 아니다. 자기완결적인 주제 본문을 만든다는 이유로 모든 현재 값과 구현 세부를 복제하지도 않는다.

### 남길 가치와 독립 문서의 필요성을 따로 판단한다

설정이나 코드 한 곳에서 바로 확인할 사실을 계속 복제하는 것은 관리비용에 비해 가치가 작은 경우가 많다. 선택 이유, 드러나지 않는 관례, 오해하기 쉬운 조건·예외, 여러 구현 경로를 연결해야 이해되는 관계, 다음 판단을 바꾸는 적용 범위·현재 차이는 남길 가치가 있다.

Main의 판단에서 보완된 점은 코드에 있다는 이유만으로 문서에서 제외하면 안 된다는 것이다. Schedule serializer가 날짜를 문자열로 바꾼다는 사실만 적는 것과, 여러 응답 경로가 같은 표현을 지켜야 하는 관계 및 일반 조회와 sync에서 삭제 처리를 달리하는 이유를 설명하는 것은 가치가 다르다. 이 예시는 앞선 논의에서 확인한 내용을 문서 구성에 적용한 것이며 새로운 제품 계약을 정한 결과가 아니다.

남길 가치가 있더라도 가이드 안에서 충분히 설명할 수 있다면 별도 파일이 불필요할 수 있다. 어떤 내용이 독립적인 `current` 문서를 요구하는지는 후속 재구성에서 확인한다. 정보의 가치와 파일 수를 같은 판단으로 묶지 않는다.

### 언제 읽는지도 문서와 함께 관리한다

물리적으로 세 층을 유지하면서 일반 진입점에서는 작업·주제로 시작할 수 있게 한다. 독자가 먼저 자기 작업을 세 층으로 분류해야만 필요한 본문에 도달하는 구조를 만들지 않는다.

각 문서는 무엇을 설명하며 어떤 작업에서 읽어야 하는지 밝히고, 추가 링크에도 필요한 이유를 제공한다. 모든 작업에서 모든 층을 읽도록 하지 않는다. 새 읽기 스킬은 필요한 본문을 선택하고 이해·적용하는 역할을 맡되, 문서별 읽기 조건이나 제품 계약을 다시 소유하지 않는다.

`summary/read_when` 형식이나 자동 목록 도구는 아직 채택하지 않는다. 우선 읽기 조건과 실제 사용이 연결되는지 확인한다. 스킬 설치나 링크의 존재만으로 필요한 문서를 읽고 계약을 적용했다고 판단하지 않는다.

### 바뀐 의미와 실제 영향을 따라 갱신한다

변경된 의미를 소유한 본문부터 갱신하고, 그 변화 때문에 설명·적용·판단·읽기 경로가 달라지는 문서만 함께 맞춘다. 다른 문서가 짧게 재서술한 전제도 영향을 받으면 갱신 대상이다. 링크로 연결됐다는 사실만으로 모든 문서를 일괄 갱신하지 않는다.

작업이 끝났다는 이유만으로 Project 문서를 새로 만들지 않는다. 반대로 여러 작업에 지속해서 유효할 변화가 명확해졌다면 Workspace 종료까지 기다리지 않는다. 과거 records는 당시 근거를 보존하며 현재 답으로 덮어쓰지 않는다. 실제 path·책임·권위 이동에는 기존 live consumer reconciliation 계약을 함께 적용한다.

## 실제 수정 대상으로 연결할 것

후속 작업은 다음 책임을 맞추는 방향이다. 새 문서의 정확한 위치와 기존 문서에서 어느 내용을 옮길지는 아직 설계하지 않았다.

- **기준 reference:** 내용 선별, 주제 구성, 분리, 읽기와 갱신의 판단 기준을 이유·대비 사례와 함께 설명한다. 필수 항목을 채우는 고정 양식 모음으로 만들지 않는다.
- **[Project README](../../../../project/README.md)와 관련 진입점:** 구조·권위 관계를 유지하면서 주제별 읽기 경로를 제공한다.
- **[MAINTENANCE.md](../../../../project/MAINTENANCE.md)와 [update-project-context](../../../../../.claude/skills/update-project-context/SKILL.md):** 위 기준에 맞춰 작성·갱신 책임과 수행 방식을 조정한다. Reference와 같은 상세 기준을 중복 소유하지 않게 관계를 정한다.
- **새 읽기 스킬:** 관련 본문을 선택하고 이해·적용하는 역할을 구성한다. 단순히 README를 읽으라는 문장을 반복하는 것 이상의 역할과 실제 사용 효과를 확인한다.

Reference의 위치, 단일 파일 또는 디렉터리 여부, 스킬 이름·발동 조건, 기존 Recover와의 접점은 후속 설계에서 정한다. 전역 reference 생성이나 특정 형식의 자동화 도입을 이미 선택한 것으로 다루지 않는다. 기준 본문은 문서가 소유하고 스킬은 이를 적용하는 교체 가능한 실행 장치라는 기존 전제는 유지한다.

## 후속 재구성에서 확인할 것과 실행 경계

지침을 보완하고 원복 대상·기준 상태를 확인한 뒤, 새 지침으로 문서를 다시 구성해 본다. 앞선 논의의 API 주제는 대표 사례로 제안된 것이며 모든 API를 통합하는 고정 템플릿이나 제품 전체 개편 범위를 정한 것은 아니다.

이때 관련 작업에서 시작 본문을 찾을 수 있는지, 선택한 본문이 계약·이유·적용을 충분히 설명하는지, 불필요한 읽기를 줄이면서 필요한 의미를 놓치지 않는지, 한 기준을 바꿀 때 갱신할 문서와 이유가 납득 가능한지 확인한다. 가이드와 코드만으로 충분한 부분과 별도 현재 맥락이 필요한 부분을 비교해 `current`의 독립적인 역할과 유지비용을 다시 판단한다. 이 항목들은 후속 확인 방향이며 검증을 통과한 결과나 새로운 고정 검사 절차가 아니다.
