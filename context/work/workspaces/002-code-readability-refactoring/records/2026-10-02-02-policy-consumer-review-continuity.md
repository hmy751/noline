## 원래 논의와 기록에서 끊긴 연결

원래 출발점은 정책 변화가 화면을 통째로 바꾸거나 작성 폼을 교체하는 문제였다. 기능을 어떤 상황에 얼마나 제한할지, 그 정책을 소비하는 훅·컴포넌트·영역이 무엇을 소유할지 논의했고, 추상 설명만으로 판단하기 어려워 일정 추가에 먼저 적용했다. 그 뒤 경비 등 원래 문제로 돌아갈 때 이 기준과 실제 흐름의 차이를 확인해야 했다.

앞선 Main 기록에는 잠정 기준과 개별 finding을 보존했지만, 일정이 첫 적용이라는 의미와 원래 소비부 검토로 돌아갈 연결이 약했다. 다음 행동은 일정 실기기 확인과 개별 결함 목록을 중심으로 읽힐 수 있었다. 이는 모든 핵심 내용이 문서에 등장했다는 사실만으로 재진입에 충분하다고 확인한 Main의 한계다.

사용자가 제공한 후속 세션 발췌에서 다음 AI는 일정 실환경 확인→종합 UX→남은 구현을 먼저 제안했다. 사용자가 “아니 일단 ㅇ리정 말고 원래 에러문제 잇엇잖아? 경비랑 등”이라고 정정한 뒤, 경비 생성의 안내 누락·수정/삭제의 일반 실패 문구·상세 재시도 불일치를 보고하고 오류 해석 공통화와 기능별 표시를 제안했다. 이 지적들은 검토 입력으로 유효할 수 있지만, 정책 소비·화면 제한·작성 수명이라는 원래 문제 전체를 대신하지 않는다. 해당 발췌의 코드 진단을 이번 기록 작업에서 새로 실행·검증한 것은 아니다.

사용자는 이 세션에 다음과 같이 추가 조건을 줬다.

> “참고로 이미 작업을 좀 진행했어 지금은 기록이나 커밋 보면 알겠지만”
>
> “근데 그냥 남기면 안될거 아냐 이미 작업한게 있어서 어떻게 남길건데 자연스럽게 이어지려면”

출처는 2026-10-02 이 대화와 사용자가 붙여 넣은 후속 세션 발췌다. 기록은 이전 계획을 별도로 덧붙이는 대신 현재 커밋 성과와 실제 다음 작업의 관계를 갱신해야 한다.

## 현재에서 이어갈 검토

다음 검토는 경비의 원래 문제 장면을 현재 코드와 연결하는 것이다. 생성·수정·목록·상세의 진입, 입력/조회, 연결 변화, 실패, 복구·명시적 재시도를 따라간다. 삭제에는 입력 수명이 아니라 실행·실패 안내·재시도 책임을 적용한다.

이미 있는 공통 조회 조합, Policy, Router의 책임을 먼저 식별하고 경비 소비부에서 남은 문제를 구분한다. 일정에서 얻은 상태 수명·최소 제한·영역별 표현 기준을 비교에 사용하되, Places나 일정 컴포넌트 구성을 경비에도 그대로 옮길 필요가 있다고 전제하지 않는다. 읽기 제한과 작성 보존, 표시와 실행을 실제 소비 관계로 구분한다.

결과로 남겨야 할 것은 대표 장면의 현재 동작, 보존할 사용자 행동, 책임 Owner, 필요한 최소 변경과 검증 방법이다. 이를 통해 메시지 해석·표시·재시도·수명 중 어느 연결을 고쳐야 하는지 결정한다. 오류 공통 함수나 여행·일정 CRUD 확대는 대조 전 확정하지 않는다. 일정의 전체 구조를 처음부터 다시 설계하는 작업으로도 되돌리지 않는다.

일정 실기기 검증은 여전히 남고 날짜·경로·0 좌표 등 기존 부채도 유지한다. 하지만 그것들이 경비 흐름을 이해하는 데 반드시 선행해야 한다고 합의한 것은 아니다. 현재 앱 화면은 실행 때 다시 확인하며, 당시 시뮬레이터가 준비돼 있었다는 기록을 현재 live 상태로 취급하지 않는다.
