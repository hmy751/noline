# Ticket 03 최초 적용 범위 재확인

날짜: 2026-09-12
Workspace: `002-code-readability-refactoring`

이 기록은 [Ticket 03](../current/memory/tickets/03-storage-stats.md)의 최초 적용 범위를 원래 작업 로그에서 다시 확인하고, 이후 사용자 정정과 현재 구현 사이의 관계를 재분석한 근거를 보존한다. 최종 구현과 검증은 앞선 [리팩터링 실행 기록](2026-09-11-04-storage-stats-refactor.md)이 소유한다.

## 확인한 최초 적용

Main이 원래 Codex 작업 session의 `useStorageStats.ts` diff를 다시 찾았다. 로그에서 확인된 최초 적용은 다음과 같다.

- 기존 `formatBytes` 구현을 hook 내부에서 파일 수준 함수로 옮겼다.
- DB·지도·합계 표시값을 만드는 `createStorageStats`를 추가하고 초기 상태에도 사용했다.
- 성공 경로와 바깥 catch에서 각각 호출하던 `setStats`를 제거하고 `finally`에서 한 번 호출했다.
- SQLite 파일 탐색, Mapbox 팩 집계, 각 실패 경계, `useEffect`와 공개 `refresh`의 React 연결은 이 diff에서 나누거나 바꾸지 않았다.

이 적용 뒤 AI는 “티켓 03의 요청 범위는 모두 수정했습니다”라고 보고하며 중복 조립 제거와 부분 실패 동작 보존을 완료 항목으로 제시했다. 따라서 최초안이 실제로 적용됐는지 알 수 없다는 앞선 미확인은 해소됐다.

## 이어진 사용자 정정

같은 작업 session에서 사용자는 최초 완료 보고 직후 “그리고 티켓 범위 안에서 더 개선 해봐 코드 개찔끔이네”라고 요구했다. Main이 이번 재조사에서 전달한 원문 순서에 따르면 사용자는 이후에도 개선된 느낌이 부족하다는 점과 React 관점을 고려해야 한다는 점을 보완했고, 마지막에는 “그냥 프로덕션 수준의 퀄리티로 개선한다 생각해봐 이 파일 안에서”라고 요구했다.

최종 구현은 이 보완 뒤 SQLite 집계, Mapbox 집계, 표시 변환과 React 상태 연결을 나누고 부분 실패 정책과 최신 요청 반영을 명시하는 수준으로 확대됐다. 사용자는 후속 인터뷰에서 현재 결과가 거의 기대한 수준이라고 평가했지만 Ticket의 최종 수락은 명시하지 않았다.

## 재분석에서 보장하는 범위

최초 diff는 좁은 Ticket 결과인 stats 조립 중복 제거가 실제로 구현됐고, 그 상태에서 실행자가 Ticket 범위를 완료했다고 판단했다는 근거다. 반면 사용자가 기대한 내부 처리 흐름과 React 연결의 개선 깊이는 후속 정정 전까지 다뤄지지 않았다.

이 사례는 Ticket의 맡은 결과가 작은 수정으로도 충족될 수 있으면 넓은 Spec 품질 기준이 실행의 정지 조건으로 작동하지 않을 수 있다는 Main의 분석을 뒷받침한다. `프로덕션 수준`이라는 한 단어가 결과를 바꿨다고 단정하지 않는다. 실제 원문에서는 사용자가 개선 깊이와 빠진 관점을 여러 차례 보완했다.

기존 Spec에는 읽기·수정 부담, 공통점과 필요한 차이, 함께 수정할 위치와 작은 예시만으로 전체 완료하지 않는 기준이 이미 있었다. 그러므로 이 사례만으로 Spec 이름이 직접 원인이었다거나, 모든 초기 Ticket과 전체 계획이 실패했다고 확정하지 않는다. Spec·Ticket 구분을 유지하고 Ticket 결과·조사 범위를 고치자는 것은 현재 Main의 추천이며 사용자 채택은 아직 없다.

원래 session JSONL은 재확인 경로였지만 제거될 수 있는 runtime 파일이므로 현재 기준이 그 경로에 의존하지 않게 이 기록에 필요한 사실과 최소 원문을 보존했다.
