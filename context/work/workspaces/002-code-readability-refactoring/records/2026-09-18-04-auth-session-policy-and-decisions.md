# 인증 만료 후 로컬 이용과 세션 모델을 정한 과정

2026-09-18 Ticket 06의 sync 시작·세션 종료 연결을 마친 뒤, 인증 route guard를 다음 후보로 검토하면서 이어진 논의다. 이 기록은 최종 정책을 선택한 이유, 중간에 철회한 안과 사용자 정정을 보존한다. 다음 구현의 현재 기준은 [Ticket 06](../current/memory/tickets/06-app-startup-lifecycle.md), 전체 상황과 재진입 순서는 [state](../current/state/index.md)가 소유한다. 여기서 정한 후속 인증 설계는 기록 시점에 아직 구현하지 않았다.

## 출발점: 로그인 화면 충돌보다 먼저 정해야 했던 것

기존 코드에는 로그인된 상태에서 세션 만료 배너가 로그인 화면으로 이동시키려 하지만, root guard가 로그인된 사용자를 다시 홈으로 보내는 충돌이 있었다. 단순히 그 guard를 열기 전에, 인증이 만료된 사용자에게 어떤 이용을 허용할지 정해야 했다.

사용자는 “로그인 세션이 만료돼도 로컬 여행을 계속 사용할 수 있다는거야? 로그인 상태를 유지해서?”라고 물었고, 이어 “지금 이 티켓에서 합의한 흐름으로보면 맞나 이게? 정책이?”라고 확인했다. 기존 06 합의는 서버 확인 없이 저장된 인증 정보를 복원해 오프라인으로 진입하는 것과 활성 여행의 Local 이용이었다. 갱신 토큰까지 사용할 수 없을 때 로컬 CRUD를 계속 허용할지는 그 합의에 자동 포함된 확정 사항이 아니었다.

앱의 목적은 네트워크가 불안정해도 준비한 여행의 계획·경비 기록을 이어가는 것이다. 인증은 최초 로그인에서 계정을 확인하고 서버 요청 때 현재 인증과 소유권을 확인한다. 이후의 기기 내 이용을 서버 토큰 수명과 어디까지 함께 끝낼지가 이번 제품 선택이었다.

## 검토한 대안과 추천이 바뀐 이유

Main은 처음 로컬 CRUD 지속을 추천했다가, 사용자의 부작용 우려를 듣고 재로그인 전 읽기만 허용하는 안을 제시했다. 그러나 사용자가 든 network unknown 사례를 핵심 문제로 확대했다. 사용자는 “아니 언노운은 중요하게 보란건 아니고 예시이고 … 인증은 다르다”라고 정정하고 `ai-self-check`를 요청했다.

독립 자기 점검은 인증의 역할과 종료 기준을 먼저 정하지 않은 채 허용·차단부터 고른 점을 지적했다. 읽기 전용은 타인의 열람을 막지 못하고, 미전송 데이터의 소유 계정·보존·전환 문제도 해결하지 못한다. Main은 성급했던 읽기 전용 추천을 철회했다. 이후 세 상태를 설명하는 과정에서 사용자가 reauth와 sign-out의 차이를 다시 묻자 Main은 인증 갱신 거절 후 로컬 전체 차단안도 추천했다. 이것도 최종 채택안은 아니다.

사용자는 자신의 원문과 기존 정책만 제3 reviewer에게 주고, 앱 흐름과 규칙·예외·복구 절차의 부담을 함께 고려해 달라고 요청했다. 이때 판단하려던 것은 단순한 상태 개수나 코드 길이가 아니라, 앱 목적에 비해 이용 제한과 복구 절차가 과하지 않고 사용자가 전체 흐름을 납득할 수 있는가였다.

독립 정책 reviewer는 다음 이유로 활성 여행의 로컬 CRUD 지속을 추천했다.

- 잠깐 연결돼 인증 만료를 확인했다는 이유로 여행 중 조회·기록이 끊기는 비용이 크다.
- 전체 이용을 차단해도 미전송 데이터 보존, 같은 계정 재로그인, 다른 계정 전환 처리는 필요하다. 상태 이름을 줄이는 것이 그 책임을 없애지는 않는다.
- 허용 범위는 기존 계정의 활성 여행이며, 비활성 여행의 서버 이용이나 새 여행의 오프라인 생성까지 열리지 않는다.
- 재로그인이 오래 지연되면 기기에만 남은 기록이 쌓이므로 로컬 저장과 서버 동기화 완료를 구별해 안내해야 한다.

Reviewer는 대화와 정책 두 입력으로 판단했으며 제품 코드를 독립 검증하지 않았다. 기존 06의 DB 준비·서버 검증 없는 진입·활성 여행 분기·종료 순서는 유지하고, 갱신 거절 후 로컬 지속은 새로 결정해야 한다고 구분했다. 사용자는 이 추천을 전제로 구체화를 이어갔다.

## 계정 경계는 채택하고 다중 기기 제어는 제외

Reviewer가 제기한 계정 혼합 방지는 한 기기에서도 필요한 문제였다. 같은 계정이면 기존 데이터와 큐를 이어 사용하고, 다른 계정이면 이전 데이터가 보이거나 전송되지 않도록 해야 한다. 큐의 소유 계정 검사는 필요하지만 별도 `userId` 컬럼 등 구현 방식은 코드 조사 후 정할 사항으로 남았다.

반면 원격 로그아웃·기기별 접근 회수까지 제품을 넓히는 것은 사용자가 제외했다. 당시 발화는 “다른기기에서 이기기.. 이건 지금 고려할건 아니라고봐”였다. 일반적인 토큰 무효 응답을 계정 삭제나 원격 회수의 증거로 해석하는 정책도 만들지 않았다.

## 정책 문장에서 실제 저장과 상태 전환으로 다시 구성

Main은 `signed-in`에 `needsReauthentication`을 붙이는 안과 세 상태 안을 오갔다. 사용자는 정책을 줄이자는 것이 아니라 표현과 프로그램의 판정이 단순하고 명확하길 원했다. 특히 같은 토큰 부재를 한 상태에서는 로그인 화면으로 보내고 다른 상태에서는 로컬 허용하는 설명, 계정 일치를 전환 예시에만 엄격하게 적용하는 설명을 지적했다.

사용자의 핵심 정정은 다음과 같다.

> “프로그래밍적으로 좀 명확하게 생각하면 좋겟어 일관성이나 정책의 일관성만 생각하니까 빈틈이 보이고 헤깔려 … 로그아웃은 명시적 로그아웃행동과 사용할 계정을 복원하지 못한다면 프로그래밍적으로 정확히 어떻게 정의할지”

두 번째 독립 자기 점검은 상태 이름을 먼저 정하고 반례마다 허용 조건을 고친 접근을 지적했다. 이후에는 무엇을 저장하고 읽으며, 어떤 결과를 확인했고, 실패·재시작 후 무엇이 남는지에서 모델을 다시 설명했다.

구체화한 저장 단위는 SecureStore의 세션 기록이다. SQLite의 여행 데이터와 다른 저장소다. 현재 낱개 키로 저장하는 사용자 ID·access token·refresh token을 하나의 기록으로 다루며, 서버 로그인 성공으로 생성한다. 별도 성공 이력 파일을 만드는 것이 아니고 SQLite의 사용자 ID를 찾아 세션을 만들어내는 것도 아니다. 유효한 계정 기록이 있고 인증 수단만 없으면 로컬 계정을 유지하는 reauth가 가능하다. 읽기 실패·해석 불가·계정 정보 모순은 기록 부재와 다르다.

접근 토큰 하나가 없지만 갱신 수단이 남은 경우는 자동 복구를 시도할 수 있다. 접근 토큰만 있고 refresh token이 없더라도 사용할 수 있는 동안의 서버 요청과 이후 재로그인 필요 판정을 구별한다. 통신 오류와 인증 갱신 거절을 같은 실패로 묶지 않는다. 구체 저장 포맷·기존 낱개 키 이관·부분 정보 판독은 후속 구현에서 시나리오로 검증할 사항이다.

## 복원 실패를 숨기지 않고 초기화의 실행 수명을 좁힘

Main이 복원 실패를 세 인증 상태 밖의 결과로만 설명하자 사용자는 “그럼 마지막에 복원실패는 어떤상태로 두게? 저 세상태로 안두게? 애매한데?”라고 물었다. 이에 복원 실패를 명시적인 `restore-failed`로 두고, 초기 복원 중 상태까지 포함하는 다섯 상태로 정리했다.

`signed-out`은 저장소 읽기에 성공해 기록이 없음을 확인한 상태다. 명시적 로그아웃은 정리를 수행해 그 상태로 끝내는 동작이다. `restore-failed`는 세션의 존재·정상성을 확정하지 못한 상태이며, 로그인 화면에 안내하더라도 자동으로 기존 데이터를 지우지 않는다. 같은 화면으로 간다는 이유로 상태와 부작용을 합치지 않는다.

사용자는 초기 복원 상태가 화면 이동이나 앱 복귀마다 반복돼 작업을 막을 가능성도 지적했다. 초기 복원은 앱 프로세스 시작과 복원 실패 뒤 명시적 재시도에만 사용한다. 탭 이동·foreground 복귀·재렌더링·네트워크 변화·토큰 갱신·재로그인은 현재 세션을 유지하며 작업 결과로 상태를 직접 바꾼다. 완료된 복원을 반복하지 않는 것은 Auth Store의 실행 수명으로 보장한다.

이름은 `restoring`에서 길어진 `restoring-session-at-startup`을 거쳐, 사용자의 짧은 이름 제안 뒤 `initializing`으로 확정됐다. 사용자는 그 제안에 “그래 그걸로 하고”라고 답했다. `idle`은 대기 의미의 후보였고 최종 이름이 아니다. 전체 상태는 `initializing`, `signed-out`, `signed-in`, `reauth-required`, `restore-failed`다. 메서드명까지 길게 고정한 중간 제안은 구현 제약으로 남기지 않는다.

## 마지막에 확정한 범위와 제외한 장치

사용자는 최종 정리 뒤 다음을 명시했다.

> “로컬 이용기간은 그냥 제한하지 말자 … 다른계정 전환은 그냥 폐기하자 이정도는”

따라서 인증 만료 후 로컬 이용에 별도 기한을 두지 않는다. 다른 계정 전환은 이전 계정의 로컬 데이터와 미전송 큐를 폐기하는 정책으로 확정됐다. 새 로그인 실패·취소로 기존 데이터를 지우는 것은 아니며, 전환 정리를 마친 뒤 새 세션을 적용한다. 여러 계정 보관함·이전 계정 복구함·기록 이전 기능은 추가하지 않는다.

사용자는 활성 여행의 기존 기간별 정리가 있을 것이라고 추정했다. Main이 확인한 일부 활성 여부 조회는 `isActivated`를 사용하고 `expiresAt`을 접근 제한으로 검사하지 않았다. 그러므로 기간 제한 없음의 결정은 유효하지만, 그 이유를 “여행 전체가 정해진 날 반드시 삭제됨”이라는 검증된 구현 사실로 바꾸지 않는다. 기존 활성화·정리 정책과 미전송 데이터 보존 문제는 각 Owner의 책임으로 유지한다.

Main은 SecureStore와 SQLite를 정리하는 도중 앱이 종료되면 로그아웃 진행 표시로 다음 실행에서 정리를 이어가는 장치를 제안했다. 사용자는 설명을 들은 뒤 이를 명시적으로 제외했다.

> “로그아웃중 앱종료 냅둬”

이번 구현에는 로그아웃 중 앱 강제 종료에 대비한 durable marker·journal·다음 실행의 정리 재개 기능을 넣지 않는다. 기존의 실행 중 sync·pending cleanup 종료 대기와 일반 오류 처리를 없애는 결정은 아니다. 앱 종료 중간 복구를 완료 조건이나 필수 선행 작업으로 되살리지 않는다.

반대로 늦은 토큰 갱신 응답 방어는 사용자가 “마지막꺼는 그렇게 해”라고 채택했다. A의 갱신 요청 후 로그아웃하거나 B로 전환했는데 A 응답이 늦게 도착하면 적용하지 않는다. 같은 A로 다시 로그인했어도 요청 당시 세션과 다르면 버린다. 사용자 ID 일치만으로 판정하지 않고 요청을 시작한 세션의 동일성을 검사해야 한다. 어떤 세션 식별·generation 구현을 쓸지는 후속 설계 사항이다.

## 기존 06과 이어지는 것, 아직 구현할 것

DB 준비 성공 후 인증 복원 시도를 하고 서버 확인 없이 진입하는 순서, DB 실패 재시도, 사용자 선택과 입력 유지, 기존 sync 시작 조건과 명시적 종료 대기는 유지한다. 이전 Spec의 “보안 저장소 읽기 실패는 비인증으로 완료”는 로그인 화면을 보여 주는 UX는 이어가되, 후속 설계에서는 `restore-failed`라는 내부 결과로 구체화한다. 계정 복원 실패를 데이터 삭제나 정상적인 로그아웃으로 취급하지 않는다.

현재 구현과 새 기준의 차이는 기록 시점의 파일 읽기로 확인했다. 실제 데이터 혼입이나 native 실패를 재현한 결과는 아니다.

- Auth Store는 아직 `isAuthenticated`와 `isSessionExpired`를 사용하며, 실패한 초기 복원도 완료된 Promise로 유지한다. 다섯 상태·실패 재시도와 세션 기록 방식은 후속 구현이다.
- 일반 API의 refresh catch는 모든 실패를 묶고, sync 일부 경로는 첫 401에서 만료로 판정한다. 통신 실패·갱신 가능·재로그인 필요를 일관되게 구별해야 한다.
- root guard는 인증된 사용자를 로그인 화면에서 돌려보내고, LoginScreen의 다른 계정 정리는 기존 만료 상태에 의존한다. 새 로그인 진입 경로 전체에서 데이터 소유 계정을 확인해야 한다.
- 일부 활성화 조회는 tripId만 확인하며 큐에는 별도 userId 컬럼이 없다. 조회·변경·큐 전송에 동일한 계정 경계를 연결하는 방식은 구현 시 확인한다.

사용자가 요청한 순서는 시나리오 테스트 작성 후 구현이다. 이번 기록으로 기존 18개 suite·185개 test 결과가 새 인증 설계까지 검증한 것으로 바뀌지 않는다. 해당 수치는 [앞선 sync 구현 기록](2026-09-18-03-sync-start-and-session-teardown.md)의 당시 결과다.
