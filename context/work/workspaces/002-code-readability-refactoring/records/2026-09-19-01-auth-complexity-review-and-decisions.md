# 인증 구현의 관리 복잡도 재검토와 재로그인 범위 결정

검토 기준: HEAD `10960e9`와 그 이후 현재 작업 트리, Workspace 002의 Spec·Ticket 06·인증 결정/구현 기록, 이번 대화에서 추가로 채택한 방향. 제품 코드를 수정하기 전 Main이 조사·검증하고 사용자와 방향을 정한 기록이다. 이 기록과 함께 Workspace current에 최신 기준을 반영하며, 제품 구현·검증 완료나 Ticket 06 수락을 뜻하지 않는다.

## 논의를 시작한 이유와 선택 과정

사용자는 “막상 합의된대로 구현한걸 보니 관리 복잡도가 너무 높아 보여서 이게 이해가 되고 관리가 될까”라고 우려했고, `useAppPolicy`뿐 아니라 전체 연결을 자세히 검토해 달라고 했다. 검토 목표는 인증 조건 몇 개를 줄이는 일이 아니라, 활성 여행의 이용 경험을 지키면서 다음 변경의 책임과 영향을 예상할 수 있는지 판단하는 것이었다.

Main은 인증 만료 뒤 로컬 기록을 이어가고 같은 계정 재로그인 뒤 동기화하는 흐름, 그리고 재로그인 저장 실패 뒤 일관된 상태로 남는 흐름을 대표 검사로 제안했다. 사용자는 첫 흐름이 기존 정책과 같다는 점을 짚고, 핵심 경험을 유지하면서 정책을 조금 조정하는 tradeoff도 요구했다. 대표 흐름을 골랐다는 사실은 그 정책 자체를 복잡도의 원인으로 판정한 것이 아니다. 동작 성공뿐 아니라 몇 곳의 판단을 함께 바꿔야 하는지 확인하려던 제안으로 범위를 바로잡았다.

로컬 수정을 읽기 전용으로 줄이는 안은 기록 중단의 비용이 큰데 기존 미전송 데이터·계정 귀속·동기화 책임은 남으므로 추천하지 않았다. 대신 재로그인에서 다른 계정까지 바로 전환하는 편의를 줄이는 안을 선택했다. 정상 재로그인이 인증 복구만 담당하므로 DB 폐기·캐시 정리·새 계정 공개를 함께 처리할 부담이 줄어든다. 다만 로그아웃 뒤 새 계정 로그인이 실패하면 이전 로컬 여행으로 바로 돌아갈 수 없는 비용을 설명했다.

사용자는 “로그아웃시 로컬 db 삭제가 부자연스럽다고 생각은 안해”라고 했고, 인증 만료 후 재로그인과 명시적 로그아웃 후 로그인을 구별한 뒤 “그래 그걸로 가자 그게 자연스럽고 덜 복잡하고 좋은것 같아”라고 채택했다. 여기서 복구하는 것은 서버 인증이다. 만료만 된 경우 DB는 계속 존재하며, 명시적 로그아웃으로 지운 뒤에는 서버에 반영된 데이터만 다시 받을 수 있다.

두 번째 흐름에서는 Main이 서버 인증 성공 후 기기 저장 실패를 별도 정책처럼 길게 설명했다. 사용자는 “이걸 또 따로 상태를 만들려고 물어본건가?”라고 우려했다. 새 실패 상태를 추가하지 않고 기존 `reauth-required`와 요청 차단을 유지하며, 저장 실패 후 일부 내부 값만 바뀌는 구현 결함을 고칠 일로 정리했다. 실제 서버 인증 거절, 기기 저장 실패, 초기 세션 복원 실패의 원인까지 같은 상태로 합친다는 뜻은 아니다.

사용자는 이어 “아니 apiclient가 제대로 되어 있냐고”라고 질문 대상을 정정했다. 앞선 답이 인증 상태·배너에 치우쳤음을 바로잡고, 자동 갱신 동안 원래 요청을 기다리는 처리, 갱신 성공 뒤 재전송, 사용자 재로그인까지는 일반 요청을 보관하지 않는 경계와 로컬 sync_queue를 대조했다. 실제 apiClient 연결 검사에서 재시도 응답 가공과 오류 전달 결함을 추가 확인했다.

일반 앱에서도 필요한 인증 동시성 처리인지 공식 자료를 확인했다. Microsoft 인증 라이브러리 MSAL의 [토큰 요청 설명](https://github.com/AzureAD/microsoft-authentication-library-for-js/blob/dev/lib/msal-browser/docs/acquire-token.md)은 동일 조건의 동시 silent 요청 공유와 interactive 요청 중복 제한을 설명한다. Google Firebase Authentication의 [구현](https://github.com/firebase/firebase-js-sdk/blob/main/packages/auth/src/core/auth/auth_impl.ts#L642-L652)은 현재 로그인 객체인지 확인해 저장·알림을 적용한다. 2026-09-19 접근 당시 내용이며 라이브러리 도입을 결정한 것은 아니다. 종료된 갱신 요청이 나중에 다시 응답하는 것처럼 설명한 예시는 바로잡았고, 진행 중 요청과 세션 변경이 겹치는 조건으로 한정했다.

마지막으로 사용자는 기존 구현을 되돌릴지 개선할지 물었다. Main은 단일 세션 저장·상태 구분·로컬 지속·갱신 공유·늦은 응답 방어는 유지하고, 문제 있는 함수나 책임은 부분적으로 교체하는 방향을 추천했다. 사용자는 “좋아 그럼 구현전에 우리 대화 전체 고려해서 워크스페이스 문서에 필요한곳에 잘 남겨놔”라고 요청했다. 전체 원복 대신 기존 코드에서 개선하는 방향과 문서 선반영을 채택한 것으로 남긴다. 현재 내부 변수·함수 배치·처리 순서까지 고정한 것은 아니다.

## 결론과 채택 범위

핵심 사용자 정책은 결정됐다. 활성 여행의 로컬 이용을 유지하면서 재로그인을 같은 계정의 인증 복구로 좁히고, 다른 계정 전환은 명시적 로그아웃 뒤 로그인으로 분리한다. 이 조정은 정상적인 재로그인에서 DB 삭제와 새 계정 적용을 함께 처리하던 부담을 줄인다. 인증 저장 실패를 위한 새 전역 상태나 재로그인까지 일반 HTTP 요청을 보관하는 대기열은 추가하지 않는다.

이것으로 전체 관리 복잡도가 해결됐다고 판단하지 않는다. API 응답 처리, Policy와 실제 요청의 불일치, Local/Remote 분기, DB 원자성, sync 결과·미전송 데이터 정리 문제는 별도로 남는다. 관리 가능성은 이 책임들을 실제 코드에서 구분하고 연결 검증을 통과시켜야 입증된다.

## 결정한 사용자 흐름

1. 서버 토큰이 만료되어도 그것만으로 명시적 로그아웃이 되지 않는다. 자동 갱신까지 거절되면 기존 계정을 유지하는 `reauth-required`가 되고 같은 계정의 활성 여행 Local CRUD를 계속 허용한다. 인증 만료에 별도의 로컬 이용 기한을 추가하지 않는다.
2. 같은 계정으로 재로그인하면 기존 DB·미전송 기록을 유지한다. 새 인증 정보 저장과 적용이 성공하면 다른 실행 조건도 충족될 때 동기화를 재개한다. DB를 복원하거나 갈아끼우는 과정이 아니다.
3. 재로그인에서 다른 계정을 선택하면 기존 데이터를 지우거나 새 계정을 적용하지 않는다. 계정 변경은 명시적 로그아웃을 거친다.
4. 정상 로그아웃 완료 시 로컬 DB·큐·인증 세션을 비운다. 서버에 이미 반영된 데이터는 남지만 미전송 변경은 복구되지 않는다. 같은 계정으로 다시 로그인해도 예전 오프라인 준비가 자동 보존되는 것은 아니다.
5. 만료 후 같은 계정 재로그인에서 서버 인증 또는 기기 저장이 실패하면 기존 `reauth-required` 상태와 로컬 이용을 유지하고 다시 시도하게 한다. 전용 `login-storage-failed` 같은 상태를 추가하지 않는다. 오류 안내는 작업 결과로 처리한다.
6. 초기 로그인 실패, 자동 갱신 실패, 초기 세션 복원 실패까지 모두 `reauth-required`로 합치지 않는다. 기존의 다섯 상태와 사건별 의미는 유지한다. `signed-in`은 서버가 방금 유효성을 보장했다는 뜻이 아니다.

## API 요청 처리의 의미

- 일반 API의 첫 401은 토큰 자동 갱신으로 이어진다. 같은 세션의 동시 갱신은 하나의 작업을 공유한다. 갱신에 성공하면 각 원래 요청을 새 토큰으로 한 번 재전송한다.
- 자동 갱신을 완료하지 못하면 해당 호출은 오류로 끝난다. 통신 장애·서버 5xx·기기 저장 실패를 서버의 인증 거절로 단정하지 않는다.
- 갱신 거절 등으로 사용자 재로그인이 필요하면 일반 HTTP 호출을 재로그인까지 붙잡아 두지 않는다. 로그인 뒤 필요한 조회를 새로 실행하는 것과 과거 HTTP 요청·수정 명령을 일괄 재전송하는 것은 다르다.
- React Query에는 현재 조회 재시도 1회, mutation 재시도 0회가 별도로 설정돼 있다. 따라서 "원래 호출 종료"를 "이후 어떤 계층에서도 요청이 다시 발생하지 않음"으로 설명하면 부정확하다. 인증 필요로 확정된 조회의 불필요한 재시도는 오류 의미를 보존한 뒤 해당 계층에서 제외할 수 있다.
- `sync_queue`는 로컬에 이미 저장한 변경의 미전송 기록이다. 일반 HTTP 대기열과 다르다. 인증 오류로 보류한 작업은 PENDING으로 남겨 이후 새 HTTP 요청을 만들어 전송한다.
- 기존 FAILED 큐까지 재로그인만으로 모두 자동 재전송된다는 보장은 현재 없다. PENDING만 읽는 엔진과 FAILED 복구 정책은 Ticket 15에서 맞춰야 한다.
- 세션이 바뀐 뒤 도착한 예전 응답은 적용하지 않는다. 재로그인 뒤 새로 만드는 조회·동기화 요청은 새 세션에 속하므로 이 규칙과 충돌하지 않는다.

## 앞선 설명에서 보정할 부분

- 재로그인 저장 실패는 일반적인 인증 구현 실패다. 별도의 제품 정책처럼 길게 논의할 필요는 없었다. 현재 코드의 실패 후 내부 상태 불일치를 수정할 근거로 남긴다.
- 로컬 DB는 인증 동시성 처리의 원리를 바꾸지 않는다. 인증을 회복하지 못한 동안에도 어떤 사용자 작업을 유지할지에 영향을 준다.
- 종료된 자동 갱신 요청이 나중에 다시 응답하는 것은 아니다. 늦은 응답 방어는 아직 진행 중인 요청과 세션 변경이 겹칠 때 필요하다. 그 사용자 경로를 실제 기기에서 재현했다고 주장하지 않는다.
- "로그아웃하면 DB가 비어 있으므로 소유권 검사는 불필요하다"고 확대하지 않는다. 정상 종료 전제 밖의 잔여 데이터·기존 기록·읽기 실패를 다룰 검사까지 없애는 결정은 아니다.
- 로그인 완료를 알린 뒤 조회 캐시 갱신이 실패하는 경우도 인증 저장 실패와 구분해야 한다. 현재 `completeLogin`은 세션 저장 뒤 `invalidateQueries`까지 같은 await 흐름에 둔다. 이 후속 실패를 모든 인증이 실패한 것으로 설명하지 않도록 완료 범위를 정한다.

## 모순과 연결 점검

### 추가 합의와 기존 문서·코드의 차이

현재 [로그인 서비스](../../../../../apps/client/src/shared/services/auth/login-service.ts)는 다른 계정 로그인 성공 뒤 DB·큐를 지우고 새 세션을 적용한다. [로그인 화면](../../../../../apps/client/src/screens/LoginScreen.tsx)도 그 자동 삭제를 안내한다. 추가 합의에 맞춰 이 분기와 안내를 바꿔야 한다.

검토 시작 당시 Workspace Spec·Ticket 06과 [기존 결정 문서](../../../../../.claude/decisions/2026-09-18-device-session-and-local-access.md)에 예전 전환 기준이 남아 있었다. 이번 반영에서 Workspace current는 새 방향으로 맞추고, 과거 records는 당시 근거로 보존했다. 기존 구현 범위와 후속 보완도 구분했다. Workspace 밖의 결정 문서는 제품 구현 때 후속 결정과 연결해야 한다.

### 계정 정보를 복원하지 못한 경우

새 정책은 복원된 기존 계정과 비교할 수 있는 정상 재로그인을 단순화한다. `restore-failed`나 세션 기록 부재인데 로컬 데이터가 남은 경우까지 비교 검사를 제거하지 않는다. 서버 인증으로 얻은 userId와 남은 데이터의 귀속을 확인할 수 있으면 기존 경계에 따라 판단하고, 귀속이 불명확하면 보존·복원 실패 처리를 유지한다. DB만 보고 로그인 세션을 임의로 만들어내지 않는다.

계정 확인이 불가능한 화면에서도 기존 데이터 정리를 사용자가 명시적으로 선택할 수 있는 진입을 어떻게 연결할지는 구현에 포함해야 한다. 정상 화면의 프로필 로그아웃만 전제로 두고 접근할 수 없는 계정에 영구적으로 묶이게 해서는 안 된다. 자동 삭제·새 인증 상태·계정별 보관함을 추가하는 제안은 아니다.

### 로그아웃과 미전송 기록

[로그아웃 서비스](../../../../../apps/client/src/shared/services/auth/logout-service.ts)는 PENDING·IN_PROGRESS만 종료 보류에 포함하고 FAILED는 반환하되 보류 판정에 포함하지 않는다. 계정 변경을 로그아웃으로 옮길 때 미전송 실패 기록도 손실 안내와 명시적 폐기 판단에 포함해야 한다. 저장소 정리 실패를 로그아웃 완료로 간주하지 않는 것과, 이미 제외한 앱 강제 종료 후 복구 journal을 새로 만드는 것은 별개다.

### 정책 UI와 실제 API 권한

`useAppPolicy`는 재인증 필요·온라인·활성 여행에서도 장소 검색을 허용하지만, 장소 검색은 모든 요청에 인증을 요구하는 일반 apiClient를 사용한다. 서버의 Places 경로에는 현재 사용자 인증 middleware가 없다. 현재 정책과 요청 경로가 충돌한다. 인증이 필요한 요청과 그렇지 않은 서비스를 실제 서버 요구에 맞게 연결해야 한다. 이를 해결하기 위해 재인증 상태를 임의로 오프라인 취급하는 제품 변경을 넣지 않는다.

| 계정 전환 | 재로그인이 DB 폐기·캐시 정리·다른 계정 공개까지 담당 | 같은 계정 복구와 명시적 로그아웃 분리. 복원 실패·소유권 검사 유지 |

## 이번 검증과 한계

기존 client 전체 테스트를 재실행했다: 23 suite, 235 test 통과.

임시 검토 테스트는 기존 SQLite fixture의 8개 검사와 신규 8개 검사로 총 16개를 실행했다. 11개 통과, 5개는 기대 동작과 다른 결과를 재현하며 실패했다.

신규 검사에서 확인한 정상 동작:

1. 두 요청의 동시 401은 한 번의 refresh를 공유하고 각 원래 요청을 한 번씩 재전송한다. 응답 body 검증은 별도 실패 검사다.
2. refresh 인증 거절로 종료된 apiClient 호출은 이후 Store 로그인만으로 자동 재전송되지 않는다. Provider와 React Query에 의한 새 요청까지 없다는 증명은 아니다.
3. `reauth-required`에서 재로그인 저장 실패 후 기존 계정과 상태를 유지하고, 다음 로그인 저장이 성공하면 `signed-in`으로 전환된다. 이 검사는 Store 단위이며 실제 기기 DB·화면·sync 전체 검증은 아니다.

실패로 확인한 결함:

1. apiClient의 401·refresh·재전송 뒤 정상 `{ trips: [...] }` 응답이 `undefined`로 전달된다.
2. 인증 필요 오류가 "알 수 없는 에러"로 변환된다.
3. signed-in Store에서 새 로그인 저장이 실패하면 기존 공개 sessionId는 남지만 그 세션의 refresh 적용이 false로 거절된다. UI에서 항상 도달하는 경로라고 주장하지 않는다. 만료 후 재로그인 실패가 로컬 DB를 잃게 한다는 증거도 아니다.
4. 다른 소유자 row와 귀속 불명 큐가 함께 있을 때 `inspectLocalAccount`가 unresolved 대신 different를 반환한다. 현재 자동 폐기 분기와 결합하면 보존 기준을 어긴다. 새 정책으로 자동 폐기를 없애면 해당 경로의 직접 위험은 줄지만 판정 의미는 정리해야 한다.
5. 실패할 transaction이 대기하는 동안 별도 upsert가 성공 반환한 후, 첫 transaction의 rollback으로 그 upsert도 사라진다.

테스트는 Axios adapter mock, SecureStore mock, Node 메모리 SQLite+실제 Drizzle을 사용했다. 실기기 저장 장애·실제 OAuth·서버 token rotation·전체 화면 복귀·운영 장애 빈도는 검증하지 않았다. TypeScript와 lint는 이번 종합 점검에서 재실행하지 않았다.

재현 코드·fixture·실행 방법과 결과는 [검사 근거](2026-09-19-02-auth-review-checks.md)에 보존했다. 임시 디렉터리 없이 이 record와 저장소 파일에서 다시 구성할 수 있다.

## 다음 실행의 완료 판단

정책 확인을 반복하기보다 API 재시도·오류 전달과 세션 실패 정합성을 먼저 수정한다. 다음으로 같은 계정 재로그인과 명시적 계정 종료를 연결하고, Policy의 실제 소비 및 Router 경계를 정리한다. DB·큐·sync의 기존 별도 문제는 해당 Ticket에서 이어가되 데이터 보존을 입증하지 못한 상태를 전체 완료라고 하지 않는다.

개선 효과는 코드 줄 수나 통과 테스트 수만으로 판단하지 않는다. 서버 인증 처리 변경이 로컬 SQL과 여러 화면의 인증 분기를 함께 바꾸게 하는지, 하나의 실패가 여러 모듈에서 서로 다른 상태로 해석되는지, 재로그인에서 DB 폐기와 복구까지 생각해야 하는지가 실제로 줄어들어야 한다.
