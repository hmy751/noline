# 날짜·시간 선택창 수정, 중앙 휠과 TimeField 적용

이번 대화는 앞선 도시 시간대 작업 뒤 남은 선택창 초기 표시 문제에서 시작했다. 기존 보고서의 문제를 확인해 수정하고, 사용자가 요청한 중앙 고정 시간 휠과 폼 연결 책임 정리를 적용했다. 제품 결과는 `09b07f8`과 `3ab8f55`에 저장됐다. 이 두 커밋 범위의 구현·검증은 마쳤으며 Ticket 06과 Workspace 전체의 종료 판정은 별도로 남는다.

## 문제 출처와 사용자가 선택한 흐름

사용자는 “방금 그 두 문제는 이전의 기록에 있던거야?”, “확인해봐 그리고 어떻게 할지 설명해봐”라고 요청했다. 10월 4일 관찰 기록에는 폼 날짜가 2026-09-30인데 달력이 10월로 열리고, 폼 시간은 09:00인데 시간 목록이 00부터 보이는 장면이 있었다. 두 선택창을 배경 클릭으로 닫은 뒤 폼 값은 유지됐다. 따라서 이번 문제는 저장된 시간대 변환과 별도로, 현재 폼 값과 선택창 초기 표시의 연결이었다. 앞선 범위 정정은 [이전 기록](2026-10-06-01-city-time-zone-commits-and-original-bug-continuity.md)에 보존돼 있다.

사용자는 구현과 리뷰를 함께 맡기도록 지시했고, 이후 “워커 리뷰 검증 이런거 6 sol 미디엄으로 시켜 앞으로”라고 작업 배치를 지정했다. 진행 중 시뮬레이터 검증도 해당 설정으로 전환했으며, 이후 휠 구현·리뷰와 TimeField 구현·리뷰·native 검증에 적용했다. 이는 이번 작업을 이어가는 위임 선호이며 제품 설계 규칙은 아니다.

첫 수정 이후 사용자는 iPhone 알람과 현재 앱 스크린샷을 제시하며 “선택된 라인이 계속 가운데 유지하면서 도는 그런느낌”, “지금 앱은 초록색으로 마킹되는데 따라가기 어려워 보이네”라고 요청했다. 선택된 숫자만 색칠하는 상태에서 고정된 중앙 선택 줄로 시·분을 읽는 UI로 변경했다.

## 현재 값 연결과 선택 수명

DatePicker는 현재 폼의 `selectedDate`를 받아 해당 달과 선택 표시를 함께 설정한다. 일정·여행·경비 생성/수정 소비자에 연결했고, 닫히면 Calendar를 해제해 다음 열기에서 탐색하던 달 대신 현재 폼 날짜로 시작한다. 빈 경비 날짜는 안내 문구를 날짜로 넘기지 않고 undefined를 사용한다. 리뷰에서 발견한 안내 문구 전달 위험을 수정하고 회귀 검사를 보강했다.

날짜를 누르면 기존처럼 즉시 폼에 적용한다. 날짜 하단 확인 버튼은 기존 닫기 역할을 유지한다. 일정 생성의 단순 닫기는 같은 값을 다시 setValue하며 검증하던 연결을 제거하고 닫기만 수행한다.

시간은 선택창이 열린 동안 임시 시·분을 보유하고 확인할 때만 폼에 반영한다. 단순 닫기는 그 선택 세션을 폐기하며 다시 열 때 현재 폼 값을 읽는다. 수정 폼은 최초 scheduleData.time 대신 현재 폼의 확정된 값을 사용한다. 저장된 일정과 폼의 미저장 값, picker 내부의 미확정 값은 서로 다른 수명이다. 예를 들어 저장값 10:00에서 picker로 11:00을 확인하면 폼과 다음 picker 열기는 11:00이지만, 수정 폼 자체를 취소하면 저장값은 10:00이다.

## 중앙 고정 시간 휠

TimePicker의 열은 행 높이 44, 다섯 행 높이 220, 위아래 여백 88을 사용한다. 고정 중앙 선택 줄 아래로 목록이 움직이며 스크롤 위치를 행 높이로 나눈 가까운 인덱스가 현재 선택이다. 스크롤 정지 시 행 경계에 맞추고, 숫자를 누를 때도 해당 행을 중앙으로 옮긴다. 시와 분은 독립적으로 움직인다.

첫값과 마지막 값도 여백을 통해 중앙에 놓인다. 범위는 시 00–23, 분 00–59인 유한 목록이다. 무한 순환, iOS native picker, 입체 회전·햅틱까지 구현한 결과는 아니다. 사용자 요청에서 채택한 것은 고정된 중앙 선택 줄과 그 줄에서 값을 읽는 동작이다.

리뷰 후 중복 offset ref를 없애고 최초 contentOffset을 안정적으로 유지했다. 확인은 최신 선택 ref를 읽어 React 상태 반영 시점에 이전 값이 전달되지 않도록 한다.

## RHF 설명을 반영한 책임 정리

사용자는 [React Hook Form watch 설명](https://chatgpt.com/c/6ac4edd2-4aac-83ee-af80-625d860be13b)을 제공하며 “이 구조 설명 고려해서 가보는건 어떨까? 일단 파악해봐”라고 요청했고, 조사 뒤 구현을 지시했다. 참고 대화의 핵심은 picker가 RHF를 알지 않고, 외부 상태와의 연결은 adapter가 맡는다는 것이었다.

기존 TimePicker도 RHF에는 의존하지 않았다. 실제 분산은 시간 필드의 표시·오류는 Controller, 선택창 값은 화면의 watch, 열기·닫기·setValue는 화면과 훅에 나뉜 부분이었다. 이번에는 `TimeField`가 useController로 값·오류를 구독하고 선택창 수명과 확인 시 반영을 함께 소유하도록 했다. 일정 생성 ScheduleForm과 UpdateScheduleDrawer가 이를 사용하며 화면·훅의 중복 시간 연결을 제거했다. UI 트리거는 renderTrigger로 기존 모양을 유지한다.

`getValues`는 읽는 순간의 값만 반환하며 스스로 구독·렌더를 발생시키지 않는다. 그렇다고 매 소비자에 watch가 반드시 필요한 것은 아니다. 현재 TimeField는 useController가 구독한다. picker의 외부 상태 독립성과 RHF adapter의 구독 책임을 구별한다.

확인 시 기존 `setValue(..., { shouldValidate: true })`를 사용해 검증 시점과 dirty/touched 동작을 보존했다. field.onChange로 기계적으로 바꿔 기존 폼 의미를 변경하지 않았다. 같은 폼의 외부 reset은 이미 열린 임시 선택을 덮지 않고, 닫고 재열면 최신 폼 값을 사용한다. 다른 일정 ID로 전환하거나 수정 Drawer를 닫으면 `TimeField` key를 바꿔 열린 선택 세션을 폐기한다. 리뷰에서 A의 미확정 선택이 B에 적용될 가능성을 지적해 이 경계를 보완했다.

사용자의 “아 필드만 만든거야?”에는 이번 단계가 TimeField adapter와 실제 소비자 이전까지라고 설명했다. TimePicker 공개 API를 value/onConfirm으로 개명하거나 별도 TimeWheel 컴포넌트로 분리하지 않았다. 이들은 자동으로 남은 필수 작업이 되지 않는다. 현재 picker의 RHF 독립성과 adapter의 연결 책임은 이미 성립한다.

## 커밋과 검증 근거

| 커밋 | 저장한 범위 |
| --- | --- |
| `09b07f8 feat(ui): 시간 선택을 중앙 고정 휠로 변경` | TimePicker와 휠 검사. 내부 선택 세션 수명·확인 연결도 동작에 필요한 범위로 포함했다. |
| `3ab8f55 fix(form): 날짜·시간 선택을 현재 폼 값과 연결` | 날짜 소비자 연결, DatePicker 재열기, TimeField와 일정 생성/수정 이전, 회귀 검사. |

사용자는 먼저 “직전 구현만 따로 커밋하자”라고 요청해 휠 두 파일만 분리했다. 그 커밋을 나머지 미커밋 폼 변경 없이 별도 디렉터리에서 검사해 5개 휠 테스트 통과를 확인했다. 이후 “이번작업 커밋하자” 요청으로 나머지 21개 파일을 저장했다. 커밋 직후 남은 미추적 항목은 기존 `.pnpm-store/`뿐이었다.

최종 구현 worker가 전체 client Jest 60 suites / 650 tests 통과를 보고했고 Main이 실행 로그를 확인했다. TimeField의 실제 useForm·picker 연결, 확인 시 오류 표시/해제, dirty/touched 보존, reset·닫기·재열기와 일정 전환 등을 포함한다. 독립 리뷰의 마지막 결과에 미해결 actionable finding은 없었다. 초기 picker 회귀 검사에서는 당시 HEAD의 별도 복사본에 새 검사를 적용했을 때 12개 실패, 수정본 관련 검사에서는 76개 통과를 확인했다. 최종 650개 전체를 변경 전후 동일 조건으로 대조한 결과라는 뜻은 아니다.

변경 파일 형식·lint와 diff check를 확인했다. ESLint의 기존 prettier 연동 충돌은 해당 규칙을 제외하고 실제 formatter로 별도 확인했다. client 타입 검사는 기존 Mapbox tuple, OfflinePack size/tileCount, UI workspace rootDir/파일 목록의 7개 진단이 남는다. 전체 타입 검사 통과는 아니다.

Native는 iPhone 15 Pro / iOS 26에서 단계별로 검증했다. 아래 관찰은 담당 검증 agent의 기록이며 Main은 해당 기록과 휠 스크린샷을 대조했다.

- 초기 picker 수정: 9/30의 9월 달력·선택 표시, 다른 달 탐색 후 재열기, 09:00의 임시 10시 취소 후 유지, 23:59 확인·재열기, 수정의 10:00→11:00 확인·재열기를 관찰했다.
- 중앙 휠: 실제 drag/fling, 정지 후 중앙 정렬, 분을 05→07로 바꿀 때 시 10 유지, 10:07 확인·재열기, 00 끝값 중앙 표시를 관찰했다. 11:05 스크린샷은 관성 이동 중 중간 프레임이며 정지 결과는 00:05였다. 새 휠의 23:59 native 끝값은 확인하지 못했고 자동 검사로만 확인했다.
- TimeField 적용 후: 생성 09:00→11:00과 수정 10:00→11:00의 확인·재열기를 관찰했다. 이번 마지막 smoke에서 미확정 선택의 취소를 다시 실행하지는 않았으며 이전 native와 자동 검사 근거를 구별한다.

각 검증 후 폼 초안을 취소하고 홈으로 돌아갔으며 저장된 일정 A 10:00과 일정 수 2개, 기존 계정을 유지했다. 마지막 Reload 직후 sync·fetchAllTrips 네트워크 오류 redbox 5개가 나타났고 닫은 뒤 picker 확인을 진행했다. 해당 관찰을 TimeField 렌더 결함으로 판단하지 않았지만, 원인을 이번 작업에서 규명·해결했다고도 하지 않는다. Android native는 실행하지 않았다.

로컬 상세 증거는 `artifacts/ticket-06-simulator/picker-20261006/observations.md`, `time-wheel-20261006/observations.md`, `time-field-20261006/observations.md`에 있다. 이들은 Git 제외 자료이므로 재진입에 필요한 관찰과 한계는 위 본문에 보존했다. 자동 로그는 `/tmp/noline-time-field-jest.log`·`/tmp/noline-time-field-tsc.log`를 확인했으며 임시 파일의 영구 보존에 의존하지 않는다.

## 다음 판단과 남은 책임

이번 선택창 수정·중앙 휠·TimeField 범위는 커밋과 검증을 마쳤다. 사용자가 전체 작업의 문제 유무를 물었을 때 Main은 이 범위에서 확인된 미해결 결함이 없다고 보고했으며, 이를 Ticket 06 전체나 앱 전체의 무결함으로 확대하지 않는다.

바로 다음은 Ticket 06의 기존 UX 보고서와 누적 수정 결과를 대조하는 종료 검토다. 원래 지적이 해결됐는지, 보류·후속 범위가 현재 결과를 막는지 확인해 종료 가능 여부를 제시한다. 단지 아직 실행하지 않은 native 시나리오라는 이유로 모두 추가 구현이나 필수 검증으로 올리지 않는다. 실제 통신 단절 Local 저장·복구, 열린 폼의 실제 연결 전환, 새 생성부터 activation까지의 전체 native는 미확인으로 유지한다.

경비 삭제 실패 이유 유실과 특정 상세 재시도 불일치는 사용자 보류다. 복구 토스트도 현재 추가하지 않는 결정을 유지한다. 기간 밖 일정 접근은 08, 나머지 입력 수명은 10·11, 경로 준비·좌표·검색 후속은 13과 연결해 판단하고 원자성·sync·cleanup·서버의 나머지는 14–17이 맡는다. 07–18의 전체 작업을 이번 두 커밋으로 완료하지 않는다. 06 종료 뒤 기본 순서의 다음 후보는 07의 client API 경계이며, 앞서 해결된 Trip PUT 연결 등은 현재 코드에서 재사용해야 한다.

이번 기록 요청은 Workspace 문서 갱신이며 자동 session activation, 제품 Verify receipt·machine status 변경이나 새로운 제품 작업 착수를 뜻하지 않는다.
