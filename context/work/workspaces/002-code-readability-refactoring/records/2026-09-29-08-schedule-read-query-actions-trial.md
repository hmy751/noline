# 일정 목록의 Query 상태·접근 조건·실행 분리 시험

일정 목록 한 곳에 `useSchedulesRead`를 적용했다. 화면은 한 번 호출해 `query`, `access`, `actions`, `view`를 받는다. 기존 Entity Query와 `useAppPolicy`를 조합하며 별도 데이터·복구 상태나 정책표를 만들지 않는다. Router의 Local/Remote 선택, sync 갱신, 5분 freshness와 전역 reconnect 설정은 유지한다.

## 선택 이유와 적용 범위

사용자는 “query 를 할당할때 그대로 할당이 아니라 refetch처럼 뭔가 정책적으로 고려되어야 하는 메서드는 query에 담지말고 다른 곳에 담아서 반환하면 안되나?”라고 제안했다. Query의 상태와 실행을 구분하되 타입 관계를 유지하는 방향을 구현했다. `query`는 원본 상태를 유지하면서 `refetch`만 타입과 실제 객체에서 제외한다. 상태 union별로 필드를 제외해 성공·재조회 실패에 따른 data/error 타입 좁히기를 보존하고, 나머지 속성은 getter로 전달해 객체 구성 시 모든 Query 속성을 읽지 않는다. `view` 계산에 필요한 상태 속성은 여전히 구독한다.

`actions.refetch`는 현재 commit의 접근 조건을 확인하고, 여행 미선택·호출자 disabled·정책 제한이면 `blocked`와 이유를 반환한다. 실제 재조회가 끝나면 `finished`와 Query 결과를 반환하며 그 결과에서도 raw refetch는 제외한다. `finished`는 요청 성공을 뜻하지 않는다. 일반 오류는 결과에 남고 `throwOnError: true`는 기존 Query처럼 reject한다. 기존에 받은 action도 후속 정책 변경을 반영하도록 callback이 최근 입력을 참조한다.

Main은 처음에 access를 내부에 두고 `actions.canRefetch`만 반환했지만, 사용자의 “근데 access 는 어디간거야?”를 즉시 복원 명령으로 받아들였다. 사용자는 “아니 무조건 하란게 아니라 판단하라고”라고 정정했다. 다시 비교한 결론은 일반 화면은 `view`를 쓰되, 폼·직접 데이터 소비자가 화면 표시 분기를 해석하지 않고 접근 조건을 사용할 수 있도록 `access`를 별도로 제공하는 것이다. 접근 여부와 실행의 중복을 줄이기 위해 `actions.canRefetch`는 제거했다. Main이 이 판단과 비용을 설명한 뒤 사용자가 “그래”라고 답했다. 이는 구현 방향 동의이며 전체 적용 수락이 아니다.

사용자는 “잠깐 일단 다 적용하진말고 한군데 적용하고 마쳐봐”라고 범위를 정했다. 일정 목록만 새 API를 사용한다. 경비 목록·상세는 앞선 `screens/read-query.ts` 조합을 유지하고 폼은 이번에 전환하지 않았다. 비교 단계라 기존·신규 조합이 함께 남아 있으며, 확대 여부를 정하면 공통화와 기존 모듈 정리도 함께 판단한다. 수정·삭제 Policy는 기존 화면의 별도 용도를 유지한다.

## 확인한 범위

Main이 실제 Query와 정책 입력 fixture로 새 계약 7개 검사를 추가했고, 일정·경비 복구와 인증 정책을 포함한 4개 suite·69개 test가 통과했다. 실행 메서드 제외, 이전 callback의 정책 변경 반영, 표시용/실제용 접근 차이, disabled·미선택, 재조회 오류와 throwOnError, 성공한 undefined를 검사했다. Query 상태 타입 관계와 refetch 제외도 TypeScript 검사 대상에 포함했다. 기존 Mapbox/download 타입 오류 3개 때문에 전체 타입 검사는 성공이 아니다. 실제 기기·서버 검증은 하지 않았다.

상세의 무동작 재시도, ScheduleDetail의 정책 연결 및 다른 폼·화면으로의 확대는 이번 수정에 포함하지 않는다. 기존 전체 386개 검사 결과는 이전 공통화 단계의 증거이며 이번 단계의 전체 재검사로 해석하지 않는다. 커밋하지 않았고 사용자가 한 곳의 구현 결과를 검토하는 단계다.
