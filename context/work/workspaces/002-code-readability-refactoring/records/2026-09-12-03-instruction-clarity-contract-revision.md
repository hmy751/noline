### 맡은 결과와 검토할 범위

이 기준의 목적은 작업을 나누어 실행해도 사용자가 기대한 결과와 품질이 줄어들지 않게 하는 것이다. 작업을 총괄하는 Main은 Spec과 사용자 원자료에서 기대 결과, 보존할 계약, 명시적 제약을 확인하고, 현재 구현을 대조해 Ticket이 맡을 결과와 범위를 정한다. 각 Ticket을 맡은 실행자는 그 결과에 필요한 설계·구현·검증을 수행한다. Main이 직접 Ticket을 실행할 때에도 같은 기준을 적용한다.

사용자가 특정 오탈자나 동작 하나의 수정만 요청했다면 그 결과를 이루고 영향을 확인하는 데 필요한 범위로 작업한다. 한 영역의 전반적인 개선을 맡겼다면 그 영역을 검토할 책임도 함께 맡은 것으로 다룬다. 이때 분석에 나온 예시나 Ticket 초안의 수정 목록은 출발점이며, 검토할 대상의 전부나 개선의 상한이 아니다.

코드 개선의 범위를 정할 때에는 해당 코드가 맡는 일과 실제 사용 관계를 읽는다. 이름과 조건에서 의미를 다시 추측해야 하는지, 처리 흐름에서 값·실패·상태를 함께 추적해야 하는지, 같은 의미를 바꾸려고 여러 위치를 맞춰야 하는지 등 이번 목표에 관련된 기준으로 주요 처리를 살핀다. 먼저 발견한 문제와 같은 패턴만 찾는 데 그치지 않고, 살펴보는 범위 안의 다른 개선 가능성도 판단한다. 불필요한 표현 정리와 필요한 책임 정리를 함께 고려하되, 각각의 차이가 실제로 필요한 코드라면 그 이유로 유지한다.

한 번에 전체를 조사할 수 없으면 우선 검토할 범위를 고르고 나머지는 미검토로 남긴다. 선택한 범위에서 문제를 이해하는 데 필요한 호출부·다른 구현·계약을 따라 확인한다. 코드가 가까이 있다는 이유만으로 별도 문제를 같은 Ticket에 넣지는 않는다.

### Ticket 구성과 실행

Ticket에는 무엇을 개선하거나 가능하게 할 것인지, 어느 범위에서 무엇이 달라져야 충분한지를 먼저 적는다. 그다음 이를 이룰 현재 접근과 확인 방법을 정한다. 완료 기준을 이미 골라 둔 수정 목록에 맞춰 낮추지 않는다. 작업 크기는 결과를 충분히 다룰 수 있는지 확인한 뒤 조절한다. 작은 정리들은 함께 검토·검증할 수 있으면 묶고, 큰 작업은 각 단계의 결과와 남은 책임이 이어지도록 나눈다.

일부만 먼저 처리할 때에는 그 부분만으로 얻을 결과와 남은 문제를 설명한다. 전체 목표에 필요한 후속 작업은 어디에서 이어갈지 남긴다. 나머지를 후속으로 넘겨도 이번 Ticket의 결과가 성립해야 하며, 부분 완료를 전체 목표의 달성으로 보고하지 않는다.

실행자는 맡은 결과를 코드의 실제 사용 조건과 Spec의 품질 기준에 맞게 구현한다. 품질을 뜻하는 말은 해당 코드에서 무엇이 달라져야 하는지로 구체화한다. 예를 들어 비동기 흐름을 이해하기 쉽게 만드는 작업이라면 함수 이름뿐 아니라, 언제 시작하고 실패 후 어디까지 진행하며 어떤 결과가 상태에 반영되는지 읽을 수 있어야 하는지 판단한다. 이 예시는 관련 흐름을 고르는 기준이며 모든 작업에 비동기 점검이나 함수 분리를 요구하지 않는다.

사용자가 정한 제약과 보존할 계약은 지킨다. Ticket을 작성할 때 선택한 수정 방법이나 잠정적인 파일 범위는 실제 근거에 따라 발전시킬 수 있다. 이미 맡겨진 결과와 권한 안의 세부 설계·구현은 실행자가 판단해 진행한다. 적힌 수정만으로 결과가 충분하지 않으면 관련 코드를 더 확인하고, 필요한 보완을 수행하거나 범위 조정안을 제시한다. 사용자 목표·보존하기로 한 공개 동작·명시적 제외 범위를 바꾸어야 한다면 차이와 영향을 설명하고, 기존에 받은 권한에 따라 결정하거나 필요한 판단을 요청한다. 조사할 범위와 실제 변경할 권한을 구별한다.

### 완료 판단과 보고

실행자는 수정 전의 문제와 수정 후 결과를 비교한다. 동작 보존 확인과 함께, 맡은 개선 효과나 실제 사용 결과가 이루어졌는지 확인한다. 전반적인 개선을 맡았다면 초안의 수정 목록 이행에 더해, 맡은 범위의 주요 처리를 관련 품질 기준으로 살폈는지 확인한다. 발견한 문제에는 개선·유지·후속 판단의 근거가 있어야 한다. 맡은 결과의 달성 여부를 판단하는 데 필요한 근거가 없거나 그 결과를 막는 미해결이 남으면 완료로 닫지 않고, 필요한 보완이나 범위 재판단을 남긴다.

사용자에게는 무엇이 달라졌고 왜 충분하다고 보는지, 이를 뒷받침하는 근거와 결론을 제한하는 남은 문제를 설명한다. 조사한 모든 항목을 보고서의 고정 목차로 나열할 필요는 없다. 확인한 사실, 계획, 실행하지 않은 검증을 구별한다.

전체 Main은 Ticket 결과를 Spec에 연결해 다음 일을 정한다. 폭넓은 개선에서는 기존 후보·Ticket·state에서 살펴본 범위의 결과와 남은 범위를 찾을 수 있게 한다. 아직 살피지 않은 영역을 개선 불필요나 완료로 처리하지 않는다. 다음 작업을 고를 때와 전체 완료를 판단할 때 이 범위를 확인하며, 매 Ticket마다 제품 전체를 다시 조사하지는 않는다.
