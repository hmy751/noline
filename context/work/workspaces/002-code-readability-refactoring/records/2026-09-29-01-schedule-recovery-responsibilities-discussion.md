# Ticket 06 온라인 복구 — 현재 구현과 책임 분리 논의

## 현재 결론과 사용자 요청

2-A 일정 화면의 구현은 작업 트리에 남아 있고 커밋하지 않았다. 기존 네트워크·화면 정책은 유지한다. 복구 훅을 단순화하는 방법, sync의 무효화 범위 조정, 조회 부분의 mount를 활용하는 구조는 모두 논의 중인 후보다. 이 기록 요청은 해당 후보의 채택이나 추가 제품 수정 승인이 아니다.

2026-09-29 현재 대화의 사용자 발화에서 판단에 필요한 부분을 보존한다.

> “수정은 하지말고”
>
> “일단 2번 정책을 기존 기록들 관련 부분 확인해봐 티켓이랑 확실한지”
>
> “예를 들어 라우터도 있고 뭐 있잖아 한번 시스템도 점검해서 각자 맡은걸 하면서 최대한 간단하게 할 수 잇는걸 생각해봐”
>
> “어떻게 하게 구체적으로? 어떻게 해결된다는건지 이해가 아직 잘 안돼”
>
> “일단 이건 확정은 아니야 하지만 계속 논의가 필요한 상황이고 일단 work 쪽에 기록 남길거 다 남겨놔봐”

사용자가 원하는 개선은 복구 훅의 조건문 개수만 줄이는 것이 아니다. 기존 시스템의 각 역할을 활용해 사람이 읽고 변경하기 쉬운 구현을 찾는 것이다. Main의 앞선 역할 분리 설명에는 구체적으로 어떤 코드가 사라지고 복구 완료를 어떻게 판단하는지 연결이 빠져 있었다. 마지막 제안은 이를 설명하기 위한 후보이며 사용자 수락을 받지 않았다.

## 정책 기록을 대조한 결과

[9월 16일 네트워크 합의](2026-09-16-01-network-policy-and-implementation-boundaries.md), [Ticket 06](../current/memory/tickets/06-app-startup-lifecycle.md), Spec과 Git 이력을 Main이 읽기 전용으로 대조했다.

- 비활성 여행은 offline/unknown에서 캐시가 있어도 일정·경비 내용을 제한 안내로 가린다. 캐시는 삭제하거나 별도 복제하지 않는다.
- 여행 선택·기본 정보·탭과 작성 중인 입력을 유지하고 활성 여행의 Local 이용은 계속한다.
- 실제 online 복귀 때 같은 비활성 여행을 계속 보고 있다면 재조회하고 성공 뒤 내용을 복구한다. 실패는 일반 조회 오류·재시도로 안내한다.
- 실제 offline 제한에서 회복한 성공에는 같은 장애당 토스트 한 번, 초기 unknown이나 단순 재확인에는 복구 토스트 없음이라는 정책도 유지한다. 토스트 구현은 2-C에 남아 있다.

위 핵심은 기존 정책 커밋 `7cfa7db`에서도 확인했다. 반면 **연결 전에 시작한 요청은 성공해도 복구로 인정하지 않고 기다린 뒤 새 요청을 보내야 한다**는 구체 조건은 현재 미커밋 2-A 구현 설명에 들어 있다. 확인한 보존 기록에서는 그 조건에 대한 별도 사용자 합의를 찾지 못했다. 전체 원대화 로그를 모두 조사한 결과는 아니다.

[9월 17일 구현 기록](2026-09-17-02-network-consumer-quality-improvements.md)에는 여러 Query 소비자의 요청을 cancelRefetch false로 공유한 이력이 있지만, 해당 구현은 이후 원복됐다. 이 이력은 연결 전에 시작한 GET의 성공을 복구로 인정하기로 했다는 합의 근거가 아니다. 쓰기 요청을 네트워크 변화만으로 취소·자동 재전송하지 않는다는 문장도 GET의 모든 처리 방법을 확정한 것으로 확대하지 않는다.

## 현재 작업 트리에 구현된 것

복구 기능은 `features/schedule/schedule-recovery/`에 있고, 화면은 정책 제한·조회 안내·목록/지도를 배치한다. `useScheduleRecovery`는 여행·인증 세션·차단 여부·복구 필요 여부·제한 이전 Query Promise를 보존한다. 렌더 중 조건부 상태 보정과 effect, QueryCache 성공 이벤트 구독으로 연결 변화와 다른 소비자의 성공을 처리한다.

현재 구현은 연결 전 요청을 기다린 뒤 refetch하며, 수동 setQueryData를 서버 성공으로 인정하지 않는다. 여행 변경·재단절·세션 변경·unmount 뒤 이전 실행이 새 복구를 완료하지 못하도록 처리한다. 이 구체 구현을 제품 정책 전체와 동일시하지 않는다.

사용자 승인 아래 앞서 반영한 개선도 남아 있다.

- 훅 반환은 idle/restricted/loading/recovering/error/ready로 좁혔다. 최초 조회 실패를 정상 빈 목록과 구분한다.
- 조회 안내 컴포넌트의 현재 이름은 `ScheduleQueryFeedback`이다. 일반 로딩·복구 로딩·조회 실패와 재시도를 표시한다.
- 지도 날짜·일정 선택은 ScheduleScreen에 두고 지도 컴포넌트에는 값과 변경 콜백을 전달한다. 제한·실패·재시도·목록/지도 전환 중 선택을 유지하고, 새 결과에서 삭제된 날짜·일정은 유효한 선택으로 보정한다. 여행이 바뀌면 선택을 초기화한다.
- sync의 pull 후 무효화에는 비활성 일정 목록의 진행 중 요청을 공유하는 예외가 현재 들어 있다. 이를 없애는 제안은 아직 적용하지 않았다.

앞선 React 검토에서는 이전 요청 대기용 refetch 때문에 추가 요청이 생기는 경우와, 별도 오류 상태 때문에 다른 소비자의 성공 후에도 오류 화면이 남는 경우를 재현·수정했다. 이 수정 이후에도 현재 구현의 복잡성이 적정한지 논의를 계속하고 있다.

## 시스템을 따라 확인한 책임과 충돌

Main이 실제 파일을 읽어 다음을 확인했다. 아래 경로는 프로젝트 root 기준이다.

1. `shared/store/network.ts`는 실제 관측과 Debug 표시용 override를 구분한다. `shared/policy/useAppPolicy.ts`는 표시용 상태·인증·활성 여부로 허용과 제한 이유를 선택한다. Debug 강제 online을 실제 요청 허용으로 사용하면 안 된다.
2. `entities/schedule/data/useGetSchedules.ts`는 Query key·캐시·Repository 호출을 소유한다. 현재 선택적 enabled 인자는 복구 화면이 사용하며 홈·폼·Drawer 등의 다른 소비자는 기본 설정을 사용한다. 한 observer를 disabled로 만들어도 같은 Query의 다른 소비자까지 중단시키는 것은 아니다.
3. `shared/services/offline-prep/router.ts`는 실행 순간 Local/Remote를 선택하고 비활성 여행의 실제 네트워크·인증을 확인한다. 캐시의 화면 표시와 연결 복구 감지는 맡지 않는다.
4. `shared/services/auth/auth-interceptor.ts`는 요청과 성공 응답의 인증 세션을 검사한다. 이 보장은 서버 응답의 유효성 경계이며, 화면의 이전 비동기 작업이 현재 복구 상태를 바꾸는 문제까지 자동으로 해결하지 않는다.
5. `shared/services/sync/provider.tsx`는 실행 조건 변화에서 sync를 시작한다. `engine.ts`의 pull은 활성 여행만 저장하고 활성 여행이 없으면 일찍 종료한다. 그런데 저장 뒤에는 비활성 여행 Query도 무효화해 화면의 서버 복구 조회와 겹칠 수 있다.
6. `shared/lib/queryClient.ts`는 refetchOnReconnect false이며 앱 코드에는 onlineManager 연결이 없다. 주석의 “SyncProvider가 처리”만으로 비활성 여행의 복구가 보장된다고 볼 수 없다.

sync가 바꾼 Local 데이터에 해당하는 Query만 갱신하도록 좁히자는 것은 Main의 개선 제안이다. 아직 적용·검증하지 않았다. 일정 상세 등 일부 Query key에는 tripId가 없으므로 key와 소비자별 영향을 조사해야 한다. 이 조정만으로 복구 훅의 이전 요청 추적까지 없어지는 것은 아니다.

## 검토한 단순화 방법과 남은 비용

### 현재 훅을 유지하며 상태와 책임을 줄이는 방법

현재 네트워크·활성 여부에서 계산할 수 있는 값과 과거 제한 이력을 구분하고, 조회 상태는 React Query에 맡기는 방향이다. 앞선 독립 리뷰어들은 상태 필드 축소, 공개 Query 결과로 완료 판단, 캐시 이벤트 구독 제거 가능성을 제안했다. 이들은 개선 후보이며 같은 동작을 보장하는 구현 실험 결과는 아니다. 조건부 render setState를 effect로 옮기는 것만으로 단순화가 보장되지 않으며 상태 반영 지연·추가 effect가 생길 수 있다.

Main이 처음에는 현재의 “이전 요청 대기 후 새 요청”도 전부 고정한 채 단순화하자고 했지만, 이후 그 구현 선택과 제품 요구를 구분해야 한다고 보정했다. 반대로 기존 요청을 공유해도 된다고 이미 합의된 것처럼 설명한 부분 역시 근거가 부족했다. 현재는 어느 쪽도 새 확정 정책으로 채택하지 않았다.

### 조회 부분이 다시 나타나는 시점을 활용하는 방법

마지막 설명에서 Main이 제시한 구체 후보는 다음이다.

- 여행·지도 선택·Drawer 입력은 일정 화면에 유지한다.
- 비활성 여행 접근이 제한되면 내용 조회 부분 대신 기존 PolicyErrorDisplay를 표시한다.
- 조회 부분이 다시 mount될 때 refetchOnMount always로 조회한다.
- isFetchedAfterMount가 false이면 대기, 이후 오류면 재시도, 성공이면 내용을 표시한다.
- Repository·Router와 기존 인증 검사는 그대로 사용한다. 활성 여행의 Local 조회에는 복구용 대기를 일괄 적용하지 않는다.

이렇게 하면 별도 Recovery 객체와 Query Promise·캐시 성공 이벤트 추적을 줄일 가능성이 있다. 하지만 마지막에 제시한 코드는 개념 예시이며 실제 구현·검증된 대체안이 아니다. 현재 useGetSchedules에는 refetchOnMount 입력도 없다.

현재 구현과의 차이는 반드시 함께 판단해야 한다.

1. 연결 전에 시작한 요청이 연결 복구 뒤 성공하면 새 observer가 그 결과를 받을 수 있다. 현재 구현의 “이전 요청 제외 후 새 요청”과 다르다.
2. 복구 외의 일반 화면 진입에서도 재조회하고 기다릴 수 있다. 유효한 캐시를 즉시 보여 주는 기존 진입과 차이가 있다.
3. isFetchedAfterMount는 서버 요청의 출처를 증명하는 값이 아니다. 설치된 Query에서는 데이터·오류 갱신 횟수로 계산하며 수동 캐시 변경도 영향을 줄 수 있다. 현재 앱 src 검색에서는 setQueryData/setQueriesData 실제 호출이 발견되지 않았지만, 기존 복구 테스트에는 이 경우가 들어 있다.
4. 화면 전체를 재생성하면 안 된다. 입력과 지도 선택 보존, 실제/Debug 상태 차이, 인증 세션 교체·재단절·다른 소비자의 조회가 겹치는 경우를 검증해야 한다. 기존 테스트의 기대를 후보에 맞춰 조용히 삭제하거나 변경하지 않는다.

전역 onlineManager를 연결하고 자동 reconnect를 켜는 대안도 즉시 채택하지 않는다. Local DB Query까지 offline에서 pause되지 않도록 networkMode와 적용 범위를 먼저 설계해야 한다. 새 NetInfo listener나 별도 네트워크 상태 시스템을 덧붙이는 것이 기본안은 아니다.

## 검증 근거와 한계

앞선 구현 턴에서 Main은 전체 client Jest **37개 suite·347개 test 통과**를 보고했다. 복구 화면 22개와 정책 화면 20개, 합계 42개의 관련 테스트를 확인했고 형식·diff 검사도 통과했다. ESLint는 기존 Prettier plugin 충돌 규칙을 제외해 오류 0개, 기존 지도 코드 경고 4개였다. 전체 TypeScript 검사는 기존 Mapbox 좌표 타입 1개와 offline-map download 속성 2개 오류로 통과하지 않았다.

347개 결과는 341개 결과 뒤 최초 실패/빈 목록 구별과 지도 선택 보존 등의 여섯 검사를 추가한 현재 구현에 대한 보고다. 이번 정책·구조 논의 및 기록 턴에서 제품 테스트를 재실행하지 않았고, 미구현 후보가 통과했다는 근거로 사용할 수 없다. 실제 화면·Query·조회 훅과 일부 실제 목록/지도 컨테이너를 연결했지만 Repository·활성 조회·네트워크·native 지도 등의 mock 경계가 있다. 실제 서버·기기 네트워크·native 지도 카메라/스크롤·OAuth·SecureStore 검증을 추가한 것은 아니다.

기술 확인에는 설치된 React Query 5.90.5의 Query/QueryObserver 소스와 2026-09-29 접근한 [React Native 안내](https://tanstack.com/query/v5/docs/framework/react/react-native), [useQuery 안내](https://tanstack.com/query/v5/docs/framework/react/reference/useQuery)를 사용했다. enabled 재활성화만으로 fresh cache의 재조회가 보장되지 않는 점, 진행 중 요청 공유, mount 이후 결과 판정과 네트워크 연결 필요성을 구분했다.

## 논의를 이어갈 지점

현재 [Ticket 06](../current/memory/tickets/06-app-startup-lifecycle.md)의 기존 정책을 출발점으로 삼고, 현재 구현과 후보의 사용자 관찰 차이를 먼저 설명한다. 연결 전 요청 성공을 복구로 인정할지, 일반 진입의 캐시·로딩 동작을 어떻게 보존할지, sync 무효화와 여러 Query 소비자의 재조회 책임을 어디까지 조정할지가 열린 판단이다.

아직 구현 방법을 선택하지 않았으므로 다음 행동은 논의 재개다. 2-A를 확정·커밋하거나 2-B 경비 복구, 2-C 토스트로 자동 진행하지 않는다. 기록 저장은 정책 변경·후보 검증·사용자 acceptance를 의미하지 않는다.
