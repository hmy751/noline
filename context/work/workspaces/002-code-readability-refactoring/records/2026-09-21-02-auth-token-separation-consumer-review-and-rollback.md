# 토큰 비공개 분리, 인증 소비 기준 재검토와 직전 구현 원복

이 기록은 [분할 검토·커밋 기록](2026-09-21-01-auth-policy-split-review-and-commits.md) 뒤, 2026-09-21에 이어진 인증 논의를 보존한다. 토큰을 공개 상태에서 빼는 승인된 작업과, 이후 인증 소비 구조를 재편했다가 되돌린 작업을 구별한다. 최신 구현의 테스트 통과나 Main 완료 보고를 사용자 수락으로 해석하지 않는다.

## 토큰을 공개 상태에서 빼려던 이유

사용자는 “클라이언트 상태에서 가지고 있는게 맞을까? … 직접 가지고 있는게 보안상 좋은가”라고 물었다. 당시 AuthState는 세션 객체 안에 access/refresh token을 포함했다. Main은 저장 시 SecureStore를 사용한다는 사실과 실행 중 공개 상태가 토큰 원문까지 노출한다는 사실을 나눠 설명했다. 당시 Store에는 persist/devtools middleware가 없었으며, 해당 경로의 실제 유출을 확인한 것은 아니었다. 변경 목적은 일반 화면 코드나 상태 로그·수집에서 토큰이 우발적으로 노출되는 범위를 줄이는 것이었다.

사용자는 기존 정책과 기능을 유지할 수 있는지, 어떻게 유지되는지 재차 확인하고 전체 코드와 합의 정책을 다시 점검하도록 요청했다. Main이 제시한 방향은 다음과 같았다.

- 하나의 인증 책임이 토큰과 공개 상태를 함께 갱신한다. 별도의 토큰 관리자와 UI store를 이벤트·구독으로 맞추는 구조를 만들지 않는다.
- 실제 세션과 토큰은 createAuthStore 내부의 currentSession에 두고, Zustand의 데이터에는 status·userId·userInfo·sessionId를 공개한다.
- SecureStore의 단일 세션 저장 형식, 다섯 인증 상태, 저장 성공 뒤 로그인 적용, 계정·활성 여행 Local 이용 정책을 유지한다.
- 일반 API·sync뿐 아니라 내 정보 조회와 회원 탈퇴도 현재 실행의 세션 검사와 토큰 조회를 사용한다. SecureStore에서 직접 읽어 현재 실행의 인증 차단을 우회하는 소비 경로를 줄인다.
- 실패한 재로그인에서 폐기하는 대상은 현재 세션 토큰이 아니라 방금 발급됐지만 적용하지 못한 토큰이다. 이 경로를 무조건 현재 토큰 조회로 통일하지 않는다.

이는 토큰을 JavaScript 메모리에서 없애거나 OS 보안 경계를 새로 만든다는 뜻이 아니다. 요청에 필요한 토큰은 메모리와 SecureStore에 남는다. signed-in은 서버가 방금 검증했다는 뜻이 아니라 인증 요청·갱신을 시도할 수 있다는 뜻이다. 로컬 접근은 계정·상태·소유권·활성화 조건을 사용하므로 토큰 원문 없이도 기존 정책을 유지할 수 있다.

Main의 “동시성 처리 자체까지 없어지는 것은 아니다”라는 표현에 사용자는 버그를 남기는 것인지 물었다. Main은 동시 401의 갱신 공유와 이전 세션의 늦은 응답 차단은 계속 필요한 장치라는 뜻이며, 알려진 버그를 남겨도 된다는 결론이 아니라고 정정했다. 사용자는 이어서 “좋아 그럼 진행해봐”라고 승인했다.

## 승인된 토큰 분리와 종료 실패 보완

첫 구현에서는 [Auth Store](../../../../../apps/client/src/shared/store/auth.ts) 내부에 토큰을 두고 요청 당시 sessionId와 현재 상태가 일치할 때만 조회하게 했다. [인증 인터셉터](../../../../../apps/client/src/shared/services/auth/auth-interceptor.ts)가 일반 API와 sync에 같은 검사를 적용한다. [auth-transport](../../../../../apps/client/src/shared/services/auth/auth-transport.ts)는 갱신 HTTP 전송을 인터셉터와 분리해 순환 참조와 재귀 갱신을 피하는 역할을 맡는다.

내 정보 조회·회원 탈퇴에 자동 갱신·현재 세션 검사를 적용한 것은 단순한 토큰 위치 이동을 넘는 동작 변경이다. Main은 후속 검토에서 이 차이를 명시했다. 기존 서버 인증 정책에 맞추려는 변경이지만, 위치만 바뀌었다고 설명하지 않는다. 당시 Main 보고는 전체 client 28개 suite·262개 test 통과였다.

사용자가 “정책이나 동작 위반도 안하면서 원래 변화 의도만 잘 고려”됐는지 다시 점검하라고 하자, Main은 SecureStore 삭제 실패 사례를 임시 검사로 재현했다. 내부 토큰을 비워 요청을 막은 뒤 삭제가 실패하면 공개 상태만 signed-in으로 남는 결함이었다. 기존 262개 테스트에는 이 사례가 없었다. Main은 앞선 완료 평가가 넓었다고 정정했다.

사용자는 이 부분의 수정과 인증 작업 전체의 재설명을 지시했다. 보완 결과는 다음과 같다.

- 로그아웃의 인증 종료를 시작하면 이전 요청을 막고, 로컬 계정이 있던 공개 상태는 reauth-required로 맞춘다.
- SecureStore 삭제 성공 뒤 signed-out으로 전환한다. 실패는 호출자에게 전달하고 종료를 다시 시도할 수 있게 한다.
- [logout-service](../../../../../apps/client/src/shared/services/auth/logout-service.ts)에서 DB가 이미 비워졌다면 이후 인증 삭제 실패에도 여행 선택과 조회 캐시를 정리한다. 지워진 DB를 복구했다는 뜻은 아니다.

이 보완 뒤 전체 client 28개 suite·266개 test 통과를 Main이 보고했다. 이 두 차례의 변경은 아래 직전 소비 구조 원복 이후에도 유지하는 작업이다. 아직 인증 묶음으로 커밋·최종 수락하지 않았다.

## 복원 질문이 소비 기준 재검토로 이어진 과정

사용자가 처음 “왜 앱시작시 restore 에서 로컬 어카운트만 확인해?”라고 묻자 Main은 저장된 세션·계정 검증 순서를 설명했다. 그러나 사용자의 핵심은 데이터 항목이 아니라, 언제 공개 상태를 보고 언제 내부 계정을 검사해야 하는지 일관되게 이해할 수 없다는 점이었다.

> “내말은 singine-in 이런 상태로 왜 검사를 안하냐고 뭔가 파편화되어 있는것 같다 이거지”
>
> “토큰을 시큐어에 저장하고 이런건 좋은데 그렇다고 각 소비하는데서 이렇게 애매하면 안되잖아 그럼 언제 authstore를 보고 등 지금 벌써 깨지잖아 다시 전체 auth 관련 코드 바탕으로 점검해보자”

복원은 initializing에서 저장된 세션을 읽고 계정 소유권을 확인한 뒤 상태를 만드는 과정이다. 따라서 시작에 signed-in guard를 붙이는 방식은 해법이 아니다. 하지만 restoreDeviceSession에서 Store로 들어갔다가 선택적 검증 callback을 통해 다시 local-account로 나가는 구조는 판단 책임을 따라 읽게 만들었다. Main은 “판단이 한곳으로 통일됐다”는 앞선 평가가 소비 코드의 가독성까지 보장한 것은 아니라고 정정했다.

전체 인증 소비 경로를 읽은 감사에서는 다음 차이를 확인했다.

1. `authStore.userId`는 로컬 이용 가능 상태까지 검사하지만 `useAuthStore.getState().userId`는 원래 값을 읽는다. 같은 계정 조회처럼 보여도 의미가 다르고, React hook에는 토큰·세션 검사 메서드까지 붙어 있다.
2. 로그인 화면이 쓰는 completeLogin은 소유권·sync·cleanup 절차를 포함하지만 공개 Store.login은 일부만 처리한다. performLogout, Store.logout, 서버 요청만 하는 logout도 함께 노출돼 있다. 앱 시작 경로 자체는 검증을 연결하지만 restoreSessionOnce의 validate가 선택 사항이라 다른 소비자가 이를 생략할 수 있다.
3. API는 AuthRequiredError, Router의 requireRemoteSession은 일반 Error를 반환한다. Query retry가 전자만 제외하므로 같은 재인증 필요 상태에서 Router 조회는 다시 실행된다. Main은 임시 테스트 두 개로 오류 클래스 불일치와 조회 두 번 실행을 재현했다. 임시 검사는 이후 제거했다.
4. useAppPolicy의 Schedule·Expense read.allowed와 실제 목록 표시가 연결되지 않아 비활성 여행의 기존 Query 캐시가 계속 표시될 수 있다. 이 항목은 코드 연결 확인이며 실기기 재현은 아니다.
5. restore-failed 또는 signed-out이면서 잔존 데이터가 있는 경우, 프로필에 들어가지 못해 명시적 데이터 정리·로그아웃을 실행할 진입이 빠져 있다.

모든 소비자를 signed-in 검사로 바꾸면 만료 후 로컬 이용 정책을 깨뜨린다. signed-in과 reauth-required에서 로컬 계정을 유지하는 판단, signed-in에서 보호 요청을 시도하는 판단은 구별해야 한다. 문제는 소비자가 그 구분을 내부 저장 구조에서 매번 재구성해야 한다는 것이었다. 이 감사 결과와 특정 구현 구조의 채택은 별개다.

## medium 서브에이전트 구현 시도와 철회

사용자는 “그래 그럼 진행 시켜봐 미디엄으로”라고 했고, 이어 “서브 미디엄 추론으로 시키라고”라고 실행 주체와 추론 수준을 구체화했다. 이후 인증 핵심 구현, 화면 연결, 독립 리뷰를 medium 추론 서브에이전트에 나누고 Main이 앱 연결 검사를 맡았다.

이 시도는 공개 Store를 읽기 전용 facade로 바꾸고 별도 내부 session-store에 상태 변경을 모았다. 로그인 제공자 교환부터 소유권 검사·저장까지 공개 명령에 포함하고, 필수 복원 검증을 내부에 고정했다. access/errors 모듈로 인증 거부를 맞추고, 로그인 화면의 기기 데이터 정리 진입과 일정·경비 목록 read 제한도 연결했다. 해당 구조와 테스트들은 원복된 시도의 설명이며 현재 제품 API가 아니다.

작업 중 겹친 로그인에서 뒤 요청이 앞 요청을 취소하는 방식의 문제도 확인했다. A 저장 성공 뒤 B 저장 실패 시 A의 저장 토큰을 폐기하면서 디스크·공개 상태가 어긋날 수 있어, 시도 안에서는 연속 로그인 저장을 순서대로 적용하고 로그아웃만 이전 구간을 무효화하도록 바꿨다. 이 회귀 검사·SessionSupersededError·추가 내부 구조도 직전 작업의 일부로 함께 되돌렸다. 앞선 토큰 분리의 이미 채택된 계약으로 승격하지 않는다.

Main은 이 작업 트리에서 전체 31개 suite·290개 test 통과, 기존 지도 타입 오류 3개만 잔존, 인증 관련 정적 import cycle 없음, 별도 포맷 검사 통과를 확인했다. lint는 Prettier plugin을 제외하고 검사했으며 새 테스트 경고를 정리했다. 실제 OAuth·기기 검증은 하지 않았다. 이 수치는 철회된 구현의 당시 검사이지 현재 원복 상태의 증거가 아니다.

사용자는 이 보고에 “뭐야 이게”라고 했고, 이어 다음과 같이 정정했다. Main의 중간 응답은 “제가 방금 설명에서 무엇을 바꿨는지와 별도로 발견한 문제를 한꺼번에 섞었습니다”라며 설명 방식으로 접근했지만, 사용자의 요구는 구현 판단과 기록·원복이었다.

> “그게 아니라 이게 맞는거야? 됐다 기록 워크스페이스에 제일 최근 기록 남긴 이후 대화 다시 다 보고 기록 부터 남기자”
>
> “그리고 지금 직전 코드 작업 이전으로 되돌려놔줘 뭔가 이상한것 같아”

사용자는 직전 구현의 적절성을 문제 삼고 원복을 요청했다. 어떤 파일·장치가 이상함의 결정적 원인인지까지 확정한 발화는 없으므로 이를 기록자가 추정하지 않는다. 또한 전체 인증 정책이나 앞선 토큰 비공개 분리까지 철회한 것으로 확대하지 않는다. 테스트 통과로 구현 방향이 수락됐다고 볼 수 없다.

## 원복 범위와 확인

Main은 medium 서브 작업 시작 이전을 복원 경계로 삼았다. HEAD로 전체 복원하지 않고, 당시 최초 파일 읽기 원문과 실제 편집 명령을 역으로 대조해 해당 작업만 되돌렸다. 직전 변경 내용은 로컬 임시 백업에 보존했지만 그 경로를 현재 설계의 근거로 사용하지 않는다.

인증 핵심·소비 코드의 기존 파일 36개, 화면 3개와 Main의 앱 테스트 2개를 복원했다. 이 중 인증 핵심 16개·화면 3개·앱 테스트 2개는 작업 전 전체 읽기 출력과 일치시켰고, 나머지 20개는 기록된 치환·추가를 역적용했다. 이번 시도에서 추가한 session-store/access/errors, 테스트 상태 helper, 화면 테스트 2개와 consumer-boundary 테스트를 제거했다. 앞서부터 있던 auth-transport·local-account 등 미추적 파일과 다른 미커밋 작업은 유지했다.

복원 후 Main이 전체 client Jest를 다시 실행해 **28개 suite·266개 test 통과**를 직접 확인했다. `git diff --check`도 통과했다. Core 작업자는 타입 검사에서 기존 Mapbox/download 오류 3개만 남았다고 보고했다. 이 결과는 철회된 구현의 31개 suite·290개 test와 별개의 현재 근거다. f0f680e·9936662의 커밋과 Policy CRUD, 이전 토큰 분리·로그아웃 저장소 삭제 실패 보완은 원복 범위가 아니다. 원복으로 소비 감사의 문제들이 해결된 것은 아니며 다음 설계 검토의 입력으로 남는다.

## 별도로 남은 데이터 보존 문제

medium 독립 리뷰는 기존 cleanup·세션 종료 코드에서도 다음 위험을 보고했고 Main이 관련 경로를 읽었다. 새 실행 재현이나 수정은 하지 않았다.

- [cleanup-job](../../../../../apps/client/src/shared/services/sync/cleanup-job.ts)의 오래된 soft-delete row 정리는 sync_queue 참조를 제외하지 않는다. pending cleanup 처리는 보류돼도 이후 vacuum이 실행되면 미전송 DELETE의 원본 row가 사라질 수 있다. local-account는 큐 소유자를 원본 row로 확인하므로 unresolved가 되어 같은 계정 복원·재로그인을 막을 수 있다. 실제 SQLite로 이 연결을 재현하고 보존 조건을 확인할 책임은 Ticket 16에 남긴다.
- [logout-service](../../../../../apps/client/src/shared/services/auth/logout-service.ts)는 미전송 수량 확인 뒤 sync 대기·서버 요청을 수행하고 DB를 비운다. 그 사이 새 Local mutation은 별도로 차단되지 않으므로 force 없는 종료도 최초 확인 이후의 변경을 삭제할 가능성이 있다. 단순 재조회만으로 충분한지, 확인과 삭제 사이 Local write까지 어떻게 조율할지는 검증·설계가 남았다. 계정 삭제에도 같은 순서를 확인해야 한다.

이 두 문제를 새 구현 때문에 생긴 결함이나 이미 수정된 결과로 기록하지 않는다. 사용자에게 언급한 것만으로 확대 구현을 승인받은 것은 아니다. cleanup·미전송 보존은 Ticket 16, Local 실행 경계는 14, 인증 종료 연결은 06과 함께 확인한다.
