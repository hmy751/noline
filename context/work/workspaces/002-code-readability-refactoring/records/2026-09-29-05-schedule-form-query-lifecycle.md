# 일정 수정 폼과 Query의 수명 분리

사용자는 “프론트 아키텍쳐 전문가 리뷰어 에게 개선 하기 위해서 어떻게 해야될지 물어봐”라고 요청했다. Main은 독립 리뷰어의 원자료 검토 뒤 현재 Policy·Query 직접 조합은 유지하고 폼 조회 수명과 변경 후 갱신 연산을 정리하자고 제안했다. 사용자는 “일단 커밋하고 그거 진행해봐”라고 실행을 요청했다. Main은 앞선 2-A 코드·검사·기록 22개 파일을 `57d878f fix(client): 일정 복구를 Policy와 Query 수명에 맞게 정리`로 먼저 저장한 뒤 아래 후속 변경을 구현했다.

## 유지한 구조와 개선 이유

리뷰어는 실제 코드와 사용처·테스트를 읽기 전용으로 확인했다. Policy가 허용 여부를, Query가 데이터와 조회 상태를, Screen이 표시 조합과 선택을 맡는 구조는 유지하도록 권고했다. 날짜별 그룹화는 기존 화면 가공이고 지도 선택 상태는 제한 화면 동안 사용자 선택을 보존한다. 현재 규칙 규모에서는 별도 훅으로 추출하는 비용이 커 즉시 분리하지 않았다. 향후 필터·오늘 날짜 선택·상세 복귀 등 선택 보정 규칙이 커질 때 상태와 보정을 함께 분리할 수 있다.

Main은 수정 폼이 `isOpen`과 무관하게 일정 Query를 구독하고, 화면 테스트는 해당 폼을 null로 대체한다는 사실을 직접 확인했다. 입력을 보존하기 위한 폼 mount와 저장 후 경로 재계산용 조회가 함께 살아 있는 관계를 끊는 것이 이번 개선의 목적이다. 폼 자체는 유지하고 `useGetSchedules`에 `enabled: isOpen`을 전달했다. 닫힌 폼은 무효화 뒤 조회를 시작하지 않고, 다시 열면 기존 Query의 유효성 기준으로 조회한다. 이 옵션이 다른 소비자의 조회나 이미 진행 중인 요청을 전역 차단하는 것은 아니다. 편집 대상 여행과 접근 허가는 기존 폼·Router 책임을 유지한다.

sync와 활성화·비활성화에 반복된 취소 후 무효화는 `cancelAndInvalidateQueries(client, filters)`로 모았다. 입력은 QueryClient와 대상 filter이고 내부 상태는 없다. 기존 조회 결과의 채택을 취소한 뒤 무효화를 시작하며 새 GET 완료는 기다리지 않는다. 갱신 Promise의 오류는 공통 로그로 처리한다. 대상과 호출 시점은 각 호출자가 소유하므로 sync의 광범위 갱신과 활성 전환의 일정 갱신 범위는 유지한다. 요청 횟수 조정이나 변경 추적 체계는 추가하지 않았다.

## 검사와 입증 범위

Main은 관련 5개 suite·42개 test에 이어 전체 client Jest **39개 suite·366개 test 통과**를 확인했다. 전체 명령은 client 디렉터리의 `node ../../node_modules/jest/bin/jest.js --config jest.config.cjs --runInBand`다. 기존 sync·활성 전환 검사는 새 공통 함수의 실제 연결을 통해 이전 조회 결과 배제와 새 GET를 기다리지 않는 동작을 계속 확인한다.

추가된 두 검사는 다음 결과를 확인한다.

- 실제 수정 폼을 닫은 상태에서 무효화해도 조회하지 않고, 열 때 갱신하며 다시 닫으면 무효화로 추가 조회하지 않는다.
- 실제 Screen·ScheduleMenu·UpdateScheduleDrawer·react-hook-form에서 제목과 날짜를 바꾼 뒤 연결 제한·복귀, 조회 실패·재시도 성공을 거쳐도 초안을 보존한다. 서버의 새 제목은 목록에 반영되고 폼의 작성 중 제목은 유지된다. 사용자가 저장하기 전에는 mutation이 없으며 저장 요청에 작성한 제목·날짜가 포함된다.

이전 364개 검사의 일정 화면은 수정 폼을 null mock으로 대체했으므로 그 결과를 실제 일정 폼의 입력 보존 증거로 확대하지 않는다. 이번 검사는 폼과 상태 관리를 실제로 연결하지만 Drawer·메뉴의 native 표시, 날짜 선택기, 지도, repository와 활성 입력은 mock이다. 실기기 애니메이션·실서버·native DB 전환까지 입증하지 않는다.

변경 파일 Prettier와 `git diff --check`가 통과했다. 기존 Prettier plugin 충돌 규칙을 제외한 ESLint는 오류·경고 없이 통과했다. pnpm 실행은 자동 의존성 확인 단계에서 실패하여 설치를 진행하지 않고 설치된 도구의 Node 진입점을 직접 실행했다. client 타입 검사는 기존 Mapbox 좌표 tuple과 OfflinePack의 size·tileCount 오류 3개가 유지됐으며 새 오류는 없었다.

앞선 구현은 커밋됐고 이 후속 개선·기록은 미커밋이다. 실패 안내의 최종 UX 확인, 경비 2-B·토스트 2-C와 Ticket 전체 완료는 남는다. 현재 단계는 [Ticket 06](../current/memory/tickets/06-app-startup-lifecycle.md)이 소유한다.
