# 개념과 계약

## 함께 쓸 말

| 말 | 뜻 |
| --- | --- |
| 상황 | 사용자에게 알릴지 판단할 앱의 상태나 사건. 예: 비활성 여행 오프라인, 미전송 있음 |
| 안내 형태 | 헤더 표시, 전역 배너, 제자리 안내, 화면 블록, 모달, 토스트(도입 시), 상태 줄(도입 시) |
| 사건과 상태 | 사건은 한 번 일어나고 끝난다. 상태는 해결될 때까지 계속된다 |
| 복구 행동 | 안내에서 사용자가 바로 할 수 있는 일. 예: 재로그인, 다시 확인 |

## 안내 규칙의 내용

Ticket 02의 결과는 상황마다 아래를 정한 표다. 양식은 바뀔 수 있어도 이 판단은 빠지면 안 된다.

| 항목 | 답할 질문 |
| --- | --- |
| 대상 | 사용자가 알아야 하는가, 개발자만 알면 되는가 |
| 형태 | 어떤 안내 형태인가. 안내하지 않는 것도 답이다 |
| 위치 | 전역인가, 해당 영역인가 |
| 동시 발생 | 다른 안내와 겹치면 무엇을 먼저, 무엇을 숨기는가 |
| 문구 | 무슨 일인지, 데이터는 어떤지, 무엇을 할 수 있는지. 내부 용어 없이 |
| 복구 행동 | 있다면 무엇이고, 진행 중·실패 때 어떻게 보이는가 |
| 위험한 행동 | 데이터를 지우는 행동을 언제 어디서 어떤 모양으로 보이는가 |

## 코드의 책임 경계

아래는 현재 Project 기준에서 확인한 경계다. 규칙을 정하다 바꿀 필요가 생기면 그 이유를 기록하고 사용자에게 묻는다.

- 사용 제한은 Policy가 판단하고 UI가 표시한다. 화면에서 연결 조건을 다시 계산하지 않는다. 동기화 실행 가능 여부는 `getSyncBlockReason`이 맡는다.
- 안내를 고쳐도 실제 실행 조건과 데이터 실행 위치를 바꾸지 않는다.
- 제한 문구를 비교해 행동을 추정하지 않는다. 복구 행동은 `recoveryAction` 같은 값으로 고른다.
- 사용자 문구에 토큰·SQL·stack trace를 노출하지 않는다.
