# 제약·현재 설계·가정

## 제약

- 규칙을 사용자와 정하기 전에 화면을 고치지 않는다. 사용자는 "해당 상황을 보고 판단해야할것 같은데"라고 했다.
- Project를 고치는 일을 이 Work의 결과나 완료 조건에 넣지 않는다.
- 설명이나 판단 요청을 구현으로 넓히지 않는다. 커밋·푸시·배포·제출은 사용자가 요청할 때만 한다.
- 구현·검토·검증과 시뮬레이터 수행은 Sonnet medium 담당자에게 맡긴다. Main은 조율, 채택 판단, Work 문서 반영을 맡는다.
- 사용자에게 보이는 글과 다음 단계 제안은 한글로 쓴다.
- 운영 서버와 운영 DB에는 접근하지 않는다. 재현은 로컬 서버와 시뮬레이터에서 DB를 백업한 뒤 하고, 삭제 확인은 누르지 않는다.
- 데이터를 조용히 잃게 하는 안내나 행동을 만들지 않는다.
- 스크린샷은 git에 넣지 않는다. 저장소 root의 `artifacts/` 아래에 두고 `.gitignore`에 추가한 뒤 records에서 링크로 잇는다(2026-11-04 사용자 지시).

## 현재 설계

아직 정한 안내 규칙은 없다. 논의된 후보와 사용자 반응은 다음과 같다.

| 후보 | 내용 | 상태 |
| --- | --- | --- |
| 헤더 네트워크 표시 유지 | 오른쪽 표시 | 사용자가 괜찮다고 봄 |
| 오프라인 일정 추가의 노란 배너 | 안내할 말이 있으니 유지 | 사용자가 괜찮다고 봄. 함께 나오는 빈 상태와 반복 문장은 미판단 |
| 멈춤 표시로 헤더 표시 옆 | 사용 제한이 아닌데 네트워크로 읽힐 수 있음 | Main이 철회 |
| 멈춤 표시로 세션 만료 같은 배너 | 기존 선례. 전역 배너 둘이 겹치고 눈에 띔 | 사용자가 UI가 꼬일 것을 우려 |
| 토스트 | 사건에 맞고 부담이 작지만, 상태에는 맞지 않음. 장치를 새로 들여야 함. Project에 연결 복구 토스트를 추가하지 않은 기존 선택이 있음([Project 선택](../project-context.md#토스트-판단-전에-읽을-것)) | 사용자가 물음. 미판단 |
| 프로필 등의 상태 줄 | 부담이 작지만 찾아가야 보임 | 미판단 |
| 토스트 + 상태 줄 | 사건과 상태를 나눔 | Main 추천이었으나 화면을 보고 정하기로 함 |
| 멈춤은 마지막 동기화 실패 때 표시, 변경 버리기는 미제공 | 같은 세션에 재시도 계기가 없음 | Main 추천. 사용자 결정 아님 |

## 가정 (확인 필요)

- 표의 현재 동작은 2026-11-03~04 판본 기준이다. 개별 버그 수정과 007의 변경으로 달라질 수 있어 실행 전 다시 대조한다.
- 흐리지만 눌리는 버튼은 첫 렌더의 `disabled` 모양이 남는 것으로 추정하며 확인하지 않았다. 사용자는 실제 기기에서도 같다고 확인했다.
- 11-03 시뮬레이터가 네트워크를 오프라인으로 읽던 원인은 모른다. 이때 본 "온라인 강제 설정인데 비활성 여행이 오프라인 블록"은 테스트 환경 탓일 수 있다.
- 1.1.0 (13)은 2026-11-03 심사에 제출돼 있다. 이 Work의 화면 변경은 그 뒤 빌드에 들어간다. 빌드와 제출 시점은 사용자가 정한다.
- 사용자 수와 상황별 빈도를 모른다. 어느 안내가 얼마나 자주 나오는지로 우선순위를 정할 근거가 없다.
- 시간대 없는 여행이 앞으로 얼마나 남을지 모른다. 새 여행은 시간대가 필수이므로 줄어드는 상황일 수 있다. 안내의 비중을 정할 때 확인한다.
