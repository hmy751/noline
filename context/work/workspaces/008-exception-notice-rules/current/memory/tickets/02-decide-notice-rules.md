# 02. 상황별 안내 규칙 정하기

## 맡은 결과와 범위

상황마다 대상·형태·위치·동시 발생·문구·복구 행동을 사용자와 정한다. [Spec 03](../spec/03-concepts-and-contracts.md#안내-규칙의-내용)의 표가 결과다. 화면 구현은 맡지 않는다.

## 실행 맥락과 접근

- Ticket 01의 화면을 나란히 놓고 정한다. 사용자가 화면을 보고 판단하기로 했다.
- 기준을 먼저 합의하면 상황마다 다시 논의하지 않아도 된다. 다음 질문이 먼저다.
  - 상태와 사건을 다른 형태로 보여 줄 것인가.
  - 전역 안내를 몇 개까지, 어떤 우선순위로 허용할 것인가.
  - 헤더가 이미 말한 것을 화면 안에서 다시 말할 것인가.
  - 성공도 알릴 것인가, 실패만 알릴 것인가.
  - 토스트를 들일 것인가.
  - 말투를 어떻게 통일할 것인가.
  - 세션 만료 배너를 계속 띄울 것인가. 사용자가 "일단 저 배너 꼭 계속 떠있어야 하나"라고 물었다. 지금은 `reauth-required`인 동안 닫을 수 없이 계속 보인다. Project의 앱 실행 기준은 재로그인 안내까지만 정한다고 검색 범위에서 봤다. 변경이 기기에만 남는 상태이므로 안내를 다시 찾을 방법은 남겨야 한다. Main 초안은 로그인 화면에서 숨기고, 다른 화면에서는 닫을 수 있게 한 뒤 작은 표시를 남기는 것이다. 결정은 아니다.
- 현재 Project 기준 "오류와 제한은 발생한 영역에서 표현한다", "기존 패턴을 우선한다"와 시간대 안내의 제품 의미를 출발점으로 삼는다. 달라지는 판단은 이유를 적는다.
- 시작 전에 [007 안내 현황 기록의 표시 방식 비교](../../../../007-sync-failure-recovery/records/2026-11-04-01-notice-inventory.md#표시-방식-비교-채택-없음-008의-입력)를 읽는다. 토스트를 판단할 때는 [Project 선택](../project-context.md#토스트-판단-전에-읽을-것)도 읽는다.
- 추천은 대안과 함께 제시하되 제품 선택은 사용자가 한다.

## 완료 조건과 확인 방법

- 상황 전부에 규칙이 있고 사용자가 수락했다.
- 기각한 대안과 이유, 받아들인 비용을 records에 남겼다.
- 03~06의 범위를 규칙에 맞춰 다시 정했다.

## 현재 상태와 실제 결과

실행 전. Ticket 01을 기다린다.
