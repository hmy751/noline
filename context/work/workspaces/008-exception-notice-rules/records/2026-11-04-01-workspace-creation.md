# 2026-11-04 — 008 생성

007에서 멈춤 표시를 정하다가, 앱 전체의 예외 안내를 먼저 정리해야 한다는 판단이 나와 만든 Workspace다.

## 왜 007에서 나눴나

007은 동기화 실패가 큐를 막지 않게 하는 Work다. 안내 현황을 모아 보니 문제가 동기화보다 넓었다. 오프라인 제한, 시간대, 로그인 화면이 모두 같은 질문에 걸렸다. "이 상황을 누구에게, 어떤 형태로, 다른 안내와 겹치면 무엇을 먼저 알릴 것인가."

사용자는 "정책 별로 예외 상황을 알리는걸 좀 뭔 가 정리가 필요해보이네"라고 했고, 일을 나누는 구성에 "그래"로 답한 뒤 "008도 만들어 구성해 다"라고 지시했다.

나눈 기준은 다음과 같다.

| 어디에 | 무엇을 | 이유 |
| --- | --- | --- |
| 007 | 원본 없는 큐 작업, 운영 기록과 횟수, 충돌 규칙 | 동기화 큐와 데이터의 문제다 |
| 008 | 사용자에게 보이는 안내 전체 | 앱 전체의 규칙이다 |
| Workspace 없음 | 개별 버그 다섯 가지 | 규칙 없이도 잘못이 분명하다 |

복원 실패는 양쪽에 걸친다. 막히는 원인은 007이, 화면의 문구와 버튼은 008이 맡는다.

## Project를 고칠 대상에서 뺀 경위

Main은 처음에 규칙의 결과를 Project UI 기준에 남기고, 007 Ticket 08의 완료 조건에 앱 실행 기준 수정을 넣으려 했다. 사용자가 정정했다.

> "008도 만들어 구성해 다 project는 확실한게 아닌데 왜 넣으려고 하지?"

아직 정해진 규칙이 없고, 복원 실패의 처리와 1.0.1 경로도 확정되지 않았으니 Project에 적을 내용이 없다는 뜻으로 이해했다. 그래서 다음과 같이 했다.

- 008의 Spec과 Ticket에서 Project 반영을 결과와 완료 조건에서 뺐다. 확정 뒤 사용자 요청이 있을 때 별도로 판단한다.
- 007의 Ticket 06·08에서도 같은 항목을 뺐다.
- Project 본문은 읽는 근거로만 선택했다. 앱 실행 기준의 `restore-failed` 설명이 재현 결과와 다르다는 사실은 [Project 선택](../current/memory/project-context.md)에 적되 고치지 않았다.

## Project 선택

`recover.json`은 이 Work의 판단을 실제로 바꾸는 본문만 골랐다.

- **여행 접근, UI 기준:** 기존 제한 안내의 경계. 멈춘 동기화가 사용 제한이 아니라는 구별의 근거다.
- **오류 처리:** 토스트 같은 공통 장치를 검토할 때의 기준.
- **앱 실행:** 로그인 화면 상태의 현재 설명.
- **날짜와 시각:** 사용자가 뜬금없다고 본 시간대 안내에 제품 의미가 있다. 시간대 없는 여행의 UTC 호환 표시는 확인 필요 안내와 함께 쓴다고 정해져 있어, 그냥 지우면 안 된다. 생성 중 Main이 읽어 새로 확인한 점이다.
- **제품 의미, 데이터 수명:** 미전송 표시의 근거.

Decision 문서는 고르지 않았다. 세 Decision 모두 이 Work의 판단을 바꾸지 않는다고 봤다.

## 이어받지 않은 것

- 007의 동기화 설계와 재시도 판단. 안내 문구를 정하는 데 필요한 사실만 Ticket 05에 직접 적었다.
- 007 current 전체. 현재 의미는 이 Workspace의 Spec에 직접 적고, 상세 근거만 007 기록을 가리킨다.
- 표시 방식 후보를 결정으로 이어받지 않았다. Main의 추천은 [Spec 05](../current/memory/spec/05-constraints-design-assumptions.md#현재-설계)에 상태와 함께 적었다.

## 스크린샷

사용자 지시로 스크린샷은 git에 넣지 않는다.

> "참고로 스크린샷은 git 에 안들어가게 하자 artifact 쪽 폴더를 gitignore 로 지정하고 그리고 records에 스크린샷을 거기에 넣어서 링크로 연결해놓자"

저장소에 이미 있던 방식대로 root의 `artifacts/` 아래 폴더를 만들고 `.gitignore`에 그 폴더를 추가했다. 전체를 무시하지 않고 폴더별로 추가하는 기존 방식을 따랐다. 받아들인 비용은 다른 체크아웃에서 링크가 열리지 않고 `pnpm harness:check`가 깨진 링크로 보고할 수 있다는 점이다.

## 초안인 것

목표·완료 기준과 Ticket 구성은 사용자의 말을 바탕으로 Main이 쓴 초안이다. 사용자 확인이 남아 있다.

## 재진입 확인

구성을 모르는 Sonnet medium 담당자에게 Recover 결과만 줬다. 답변은 Recover 범위로 하고, 링크 존재만 따로 확인하게 했다.

**복원한 것:** 목표, 제약, 완료 기준이 초안이라는 점, 현재 상태와 첫 행동, 대기 결정, 이어받지 않은 범위. 시간대 안내를 그냥 지우면 안 되는 이유, 토스트가 앱에 없다는 점, 복원 실패의 원인을 여기서 고치지 않는다는 점, 스크린샷 위치도 답했다. 깨진 링크는 없었다.

**판정은 "보완 필요 (경미)"였고 Main은 다음과 같이 처리했다.**

| 지적 | 처리 |
| --- | --- |
| Ticket 01의 재현 방법과 사용자 개입 지점이 없음 | 반영. 사용한 방법과 시도하지 않은 방법을 나눠 적음 |
| 초안 확인 전에 어디까지 진행하는지 불분명 | 반영. Ticket 01은 진행 가능, 02 시작 때 확인 |

| 007 Ticket 07·08의 상태를 볼 경로가 없음 | 반영 |
| 개별 수정의 담당과 Ticket 03과의 경계가 없음 | 반영. 담당과 시점은 사용자 결정으로 올림 |
