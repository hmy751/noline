# 제약·현재 설계·가정

## 제약

- 독자는 다른 개발자다. 매끄럽게 읽히는 것이 가장 중요하다.
- 2026-10-31판의 제목과 문단을 뼈대로 둔다. 통째로 새 틀로 갈아엎지 않는다. 지금의 절 순서는 10-31판과 같지 않다. Architecture를 Quick Start 뒤에서 Preview & Features 뒤로 올린 것은 이번 작업에서 Main이 바꾸고 사용자가 미리보기로 본 순서다.
- 목차를 둔다. Preview로 앱이 무엇을 하는지 먼저 보여 준다.
- 코드로 확인되지 않는 주장, 근거 없는 수치를 넣지 않는다.
- 공개 문서이므로 Personal·Work의 내용과 경로를 문안에 쓰지 않는다.

## 현재 설계

README는 다음 순서다(2026-11-15, 커밋 `b418d5cb`, 383줄).

1. 헤더와 소개 한 문단, 목차
2. Motivation
3. Preview & Features — 3열 2행 이미지 그리드, 기능 네 줄, 상태별 동작 표
4. Architecture: 선택과 책임 — 세로 방향 다이어그램과 네 절
5. UI State: 불안정한 연결에서 화면이 지키는 것 — 지키는 세 가지, 훅 조합, 늦은 응답 처리
6. Tech Stack & Structure, Quick Start, 현재 한계

선택 이유는 다음과 같다. 누가 정했는지와 이유를 말한 주체를 구별해 적는다.

- **Architecture를 4개 절로 둔 이유:** 데이터가 가는 길을 한 방향으로 따라가게 하려는 Main의 선택이다. 사용자는 개수를 정하지 않았고 구성이 "얼추 된것 같아"라고 받았다. 주제를 더 넣으면 다시 무거워진다는 것이 지킬 조건이고, 4라는 수 자체는 조건이 아니다.
- **UI State를 Architecture 밖 별도 절로 둔 이유:** Main의 첫 추천과 독립 리뷰어의 추천은 모두 Architecture의 5번 절이었다. 사용자가 별도 절의 초안을 요청했고 별도 절로 확정했다. 사용자는 이유를 말하지 않았다. 목차 최상위에 보인다는 이점은 Main이 든 것이고, 덧붙인 인상을 줄 수 있다는 비용은 리뷰어가 든 것이다.
- **UI State를 Architecture 뒤에 둔 이유:** Main은 Preview & Features 바로 뒤를 제안했고 사용자가 Architecture 뒤로 정했다. 그 결과 Policy와 활성 여행 개념이 1번 절에서 먼저 설명된다.
- **인증·더 읽을 곳 절을 뺀 이유:** 사용자가 없어도 되지 않겠느냐고 했고 Main이 동의했다. 인증은 Tech Stack 표 한 행과 Architecture 4번 절로, 서버 안내 링크는 Quick Start 끝으로 옮겼다.

각 선택의 과정은 [뼈대와 문장 기록](../../../records/2026-11-15-02-structure-and-readability.md)과 [UI State 절 기록](../../../records/2026-11-15-04-ui-state-section.md)에 있다.

## 가정과 열린 판단

- 버전 배지 1.1.2는 `app.config.js`의 값이다. Main은 이 판이 빌드 16으로 심사에 접수된 것이라 App Store에 공개된 버전과 다를 수 있다고 알렸고, 사용자는 어느 기준으로 할지 답하지 않았다.
- Preview 자산은 이전 버전에서 녹화한 것이다. README에 그 사실을 적어 두었다. UI State 절이 말하는 실패·제한 화면을 보여 주는 자산은 없다.
- README가 383줄로 늘었다. 2번 절 트레이드오프(끝냄·보류·격리)를 한 문장과 링크로 줄이는 안이 제안됐지만 결정하지 않았다.
- "여행 정보 수정에는 항목 단위 병합을 아직 적용하지 않는다"는 문장은 서버 여행 수정 route를 읽어 쓴 것이다. 앞으로 여행에도 적용되면 README 3번 절을 고쳐야 한다.
- 1번 절의 과거 서술 두 문장은 당시 코드로 확인한 것이 아니다. "처음에는 활성 여행이면 … 지도와 장소 검색까지 오프라인 방식으로 동작했습니다"는 결정 문서와 배경 문서의 서술을 근거로 썼고, Main이 기억과 다르면 알려 달라고 했으나 사용자는 답하지 않았다. "처음에는 모든 여행을 기기에 자동으로 저장했습니다"는 근거를 대조한 흔적을 대화 원문에서 찾지 못했다.
- UI State 절의 "조회 실패와 0원이 같은 화면이 될 수 없는 이유입니다"는 독립 리뷰어가 피한 표현("타입이 강제한다")에 가깝게 읽힐 수 있다. 훅이 원본 조회 상태도 함께 돌려주기 때문이다. 낮출지는 정하지 않았다.
- 구성과 UI State 절에 대한 사용자의 수락은 "얼추 된것 같아", "이정도 방향으로 하자"다. README 전체를 최종 수락한다는 발화는 없다.
