# 문제·목표·범위

2026-10-31판 README는 그 뒤 바뀐 구현을 따라가지 못하고 있었다. 버전 배지는 1.0.1이었고, 기기 사본 정리는 "PENDING 중심이라 … 모든 미전송 상태의 보호를 충족하지 못합니다"라고 설명했으며, 여러 기기 편집 병합과 동기화 실패 복구는 빠져 있었다. Main은 이 판이 제품과 구조를 평면적으로 서술한다고도 보았다. 이 평가는 사용자의 말이 아니다. 사용자는 이 판을 "엄청 맘에 안들어서 갈아 엎고 싶던건 아닌데"라고 했다. 더 이전 판(2026-03)은 고민 → 대안 → 해결 형식이었지만 지금 근거를 확인할 수 없는 수치("85% 압축", "데이터 손실 제로" 등)가 섞여 있었다.

목표는 README를 처음 보는 개발자가 끝까지 읽고 다음 세 가지를 알게 하는 것이다.

- 이 앱이 무엇을 하는지 (Preview와 기능으로)
- 어떤 문제를 놓고 무엇을 선택하고 무엇을 포기했는지 (설계 절로)
- 저장소 주인이 화면 상태와 사용자 경험을 어떻게 다루는 프론트엔드 엔지니어인지 (UI State 절로)

처음 요청은 "프로젝트 컨텍스트와 코드를 통해서 리드미를 좀 개선"하는 것뿐이었고, 기준은 초안에 대한 정정에서 하나씩 나왔다. 다른 개발자에게 매력 있게 보일 것, 개발자가 보기에 매끄럽게 읽히고 이해하기 쉬울 것, 논리와 고민이 느껴지되 너무 많지 않을 것, 목차가 있고 Preview로 앱이 하는 일을 보여 줄 것이다. 10-31판을 고려하지 않고 갈아엎지 않는다는 조건도 있다. 세 번째 목표는 작업 후반에 사용자가 "내가 프론트이기도 하고"라며 더한 것이다. 이 기준들은 서로 당기므로, 내용을 더할 때마다 분량과 읽기 흐름을 함께 판단한다. 발화 원문은 [사용자 방향 원문](../../../source/user-direction.md)에 있다.

범위는 루트 `README.md` 한 파일이다. `START_GUIDE.md`, 서버 README, Project 본문, 제품 코드, Preview 자산의 재촬영은 포함하지 않는다. README를 쓰다 Project 본문과 코드의 불일치를 발견하면 README는 코드에 맞추고, Project 본문 갱신은 별도 판단으로 넘긴다.
