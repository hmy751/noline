# 구별해야 할 사례

README를 고칠 때 비슷해 보이지만 결과가 달라야 하는 경우다. 모두 이번 작업에서 실제로 반려되거나 정정된 장면에서 나왔다. 각 사례 끝에 선택 과정이 있는 기록을 적었고, 사용자 발화는 [사용자 방향 원문](../../../source/user-direction.md)에 있다.

**고민이 느껴지는 글과 내용이 많은 글.** 설계 결정 8개를 문제 표와 함께 나열한 판에 대해 사용자는 고민이 느껴지는 것 자체는 좋다고 하면서 "너무 뭐가 많아서 그런가 싶기도 하고"라고 했고, 이어진 질문에서 "내용이 너무 많다"를 골랐다. 주제를 "어디에 저장하나 → 어떻게 보내나 → 겹치면 무엇이 남나 → 지울 때 무엇을 지키나"의 4개 절로 묶고, 데이터/서비스 분리는 1번 절에, ID 생성은 2번 절의 규칙 목록에 흡수했다. 고민을 보여 주는 것은 항목 수가 아니라 대안과 트레이드오프다. 4라는 수는 사용자가 정한 제약이 아니다. 사용자는 "3~4개를 제한해야한다는 아니지만" Project context를 면밀히 보고 무엇이 적절한지 고민하라고 했다. ([뼈대와 문장](../../../records/2026-11-15-02-structure-and-readability.md))

**새로 짠 틀과 원래 글을 살린 틀.** 같은 판에서 사용자는 10-31판을 고려하지 않고 갈아엎은 것을 아쉬워했다. 형식이 더 나아 보여도 원래 제목과 문단을 뼈대로 두고 필요한 곳만 바꾼다. 이번에 바꾼 곳은 Architecture 안쪽의 서술 방식과 Preview의 3열 그리드였다. ([뼈대와 문장](../../../records/2026-11-15-02-structure-and-readability.md))

**결론만 압축한 문단과 따라 읽을 수 있는 문단.** Router와 Policy를 나눈 이유를 네 문장으로 압축한 문단은 "이렇게 넣으면 이해가 안되니까"라는 지적을 받았다. Main이 본 원인은 왜 문제가 생겼는지를 건너뛴 것이다. 지금은 문제 → 원인 → 역할 표 → 결과 순으로 쓴다. ([코드·배경 문서 대조](../../../records/2026-11-15-03-code-and-background-check.md))

**코드보다 강한 문장과 코드에 맞춘 문장.** "실패하면 뒤 작업을 멈춘다"는 일반 실패에는 맞지만 예외(삭제 확인, 구버전 충돌 보류, 원본 잃은 요청 격리)를 빼면 과하다. "7일 뒤 지운다"는 실제로는 유예 기간이고 정리 예약이 있을 때만 실행된다. "같은 기록을 고쳐도 항목이 함께 남는다"는 일정과 경비에만 맞다. 요약하면서 조건을 떨어뜨리지 않는다. ([코드·배경 문서 대조](../../../records/2026-11-15-03-code-and-background-check.md))

**원칙을 나열한 절과 엔지니어링이 드러나는 절, 그리고 한쪽으로 덮은 절.** UI 쪽 내용을 원칙 세 가지로 정리한 초안은 "아까 니가 말한것들의 매력이 덜 초안에 나온 느낌"이라는 평가를 받았다. 반대로 사용자가 짚은 훅 조합을 절의 뼈대로 삼아 전부 바꾼 초안은 "그렇다고 그걸로 다 바꾸면 어떻게 해"라는 답을 받았다. 지적을 반영할 때 앞서 좋다고 한 것을 밀어내지 않는다. 지금 구성은 도입 문단이 사용자 경험(무엇을 지키나)과 훅 조합(어떻게 지키나)을 함께 말하고, 아래를 그 순서로 둔다. ([UI State 절](../../../records/2026-11-15-04-ui-state-section.md))

**절 제목.** 사용자는 `Frontend`를 대놓고 쓴 제목을 반려했다. Main이 `UI State`로 바꿨고 사용자는 그 초안의 방향을 받았다. 역할을 내세우는 제목보다 다루는 대상을 쓰는 제목이 낫다는 것은 이 정정에서 Main이 읽은 뜻이며, 사용자가 일반 규칙으로 말한 것은 아니다. ([UI State 절](../../../records/2026-11-15-04-ui-state-section.md))
