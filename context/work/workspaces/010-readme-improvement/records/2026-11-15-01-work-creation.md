# README 작업을 돌아보며 Work를 만든 경위

README 반영과 push를 마친 뒤 사용자가 물었다.

> "그럼 이제 우리 대화 전체 보면 리드미 반영하면서 생각한 맥락들있잖아? 결정이나 이런걸 남기고 싶은데 어디에 남기면 좋을까? work에?"

Main은 세 영역을 비교했다. README는 Project 본문의 요약이지 제품 계약이 아니므로 Project의 결정 문서 자리가 아니다. "README를 쓸 때 무엇을 중요하게 보는가"는 Personal 후보지만 `context/personal/`에 사용자의 미커밋 수정이 있어 이번 기록과 섞지 않기로 했다. 한 작업의 선택·과정·결과는 Work가 맡는다. 기존 001~009에는 README를 목표로 삼은 Work가 없었고, 007(동기화 실패 복구)이나 006(Project context 재구성)에 넣으면 그 목표와 섞인다. 그래서 새 Work를 제안했고 사용자가 수락했다.

> "그래 잘 남겨줘 그래야 저걸 어떻게 햇는지 알것 같아"

이 Work는 실행 전에 만든 것이 아니라 실행을 마친 뒤 돌아보며 만든 것이다. 그래서 Ticket 01은 처음부터 "반영 완료" 상태이고, current의 Spec은 작업 중 사용자가 준 기준과 정정에서 뽑아 정리했다. 실행 중의 선택 과정은 대화 원문을 읽는 기록 담당자가 별도 record로 남긴다.

이어받지 않은 것도 있다. 다른 Work의 목표·결과·완료 상태는 가져오지 않았다. README가 근거로 삼은 여러 기기 편집과 동기화 실패 복구의 구현 과정은 007이 소유하며, 여기에는 README 문장의 근거가 된 Project 본문의 접근점만 두었다.

구성은 목표·사례·계약·완료 판단·제약의 Spec 다섯 관점, Ticket 두 개(반영 완료한 재구성, 남은 게시 뒤 확인), 선택한 Project 맥락, source·output 색인, 재개 안내다. 기본 Workspace와 `index.json`의 active id는 바꾸지 않았다. 제품 코드와 Personal·Project 본문은 이 생성으로 수정하지 않았다.

인수 확인은 Main이 새 README와 재개 안내에서 출발해 목표·조건·현재 결과·남은 일·첫 행동을 따라가 보는 직접 대조로 했다. 대화 이력을 받지 않은 별도 읽기 주체의 인수 시험은 하지 않았다.
