# UI State 절이 만들어진 과정

README의 `UI State: 불안정한 연결에서 화면이 지키는 것` 절은 사용자의 한 질문에서 시작해 독립 리뷰어의 검토와 초안 네 판을 거쳐 들어갔다(커밋 `b418d5cb`). 리뷰어의 추천과 다른 위치에 놓였고, 초안마다 사용자의 정정으로 중심이 바뀌었다. 이 기록은 각 판이 왜 반려됐는지와 최종판이 무엇을 얻고 무엇을 내려놓았는지를 남긴다.

기록 담당자가 대화 원문 JSONL의 1016〜1283행을 직접 읽었다. 리뷰어의 보고 전문은 1116행에, Main이 리뷰어에게 준 과업은 1101행에 있다. 사용자 발화는 [사용자 방향 원문](../source/user-direction.md)에 있다.

## 시작한 질문과 재료

사용자의 말이다. "내가 프론트이기도 하고 그래서 뭔가 더 어필할 문단이나 이런게 있을까? 사용자 경험 제공 측면도 그렇고 프론트엔드 엔지니어로서 한번 context랑 쭉 둘러보고 생각해봐"

Main은 Project의 여행 접근·작성 입력 본문과 클라이언트 코드를 읽고, Architecture 네 절이 모두 데이터를 어디에 저장하고 어떻게 보내는지에 관한 것이며 그 상태를 화면이 어떻게 보여 주는지는 빠져 있다고 보았다. 사용자에게 먼저 제시한 주제는 앞의 넷이었고, 리뷰어에게는 아래 여섯 가지를 재료로 넘겼다.

| 재료 | 내용 | 최종 README |
| --- | --- | --- |
| 조회 표시 상태 (`ReadQueryView`) | 조회 결과를 여섯 상태로 구별한다. 처음 실패를 빈 목록·0원으로 그리지 않고, 갱신 실패 때 보던 내용을 유지하고, 홈 카드는 일정과 경비를 따로 판정한다 | 중심 재료. 타입 코드와 "모르는 것을 없다고 보여 주지 않는다" |
| 연결 상태 셋 | online·offline·unknown. 모르는 상태를 오프라인으로 단정하지 않고 10초 뒤 "확인 불가"로 바꾼다 | 목록 한 줄 |
| 작성 중 입력 보존 | 연결이 바뀌어도 입력을 유지하고 실행할 수 없는 영역만 막는다. 복구돼도 자동 제출하지 않는다 | "쓰던 입력을 지우지 않는다" |
| 늦은 응답 처리 | 활성화 전환 때 진행 중인 조회를 취소한 뒤 무효화한다 | 하위 절 하나 |
| 기능 제한 안내 (`PolicyErrorDisplay`) | 막힌 이유와 복구 행동을 그 영역에 표시한다 | "막힌 이유를 그 자리에서 알린다" |
| 공유 UI, 계층 구조, 폼 라이브러리 | — | 넣지 않음 |

Main의 첫 추천은 Architecture에 5번 절 하나를 더하는 것이었다. 세 주제를 각각 절로 만들면 README가 다시 길어진다는 이유였다. 사용자는 이 추천을 받는 대신 이렇게 말했다. "아님 지금 이사항을 지금 리드미에 어떻게 반영하면 좋을지 제3리뷰어한테 잘 물어봐"

## 독립 리뷰어에게 물은 방식과 답

Main은 리뷰어에게 README를 처음 보는 프론트엔드 개발자의 입장에서 읽으라고 했다. 사용자가 그동안 말한 기준의 원문, 현재 README, 재료 여섯 가지(사실만)와 근거 코드 위치를 주었고, 자신의 추천안은 일부러 주지 않았다. 결론을 미리 주면 그대로 확인해 올 가능성이 크다는 이유였다. 재료 선정 자체가 틀렸다고 봐도 된다고 열어 두었다. 리뷰어는 읽기 전용이었고 `context/personal/`과 `context/work/`는 읽지 않았다.

리뷰어의 답은 다음과 같다. 이 문단의 내용은 리뷰어의 보고이며, 리뷰어는 테스트를 실행하지 않았고 앱 화면을 보지 않았다.

- **인상.** 지금 README는 "동기화를 잘 아는 클라이언트 엔지니어"로 읽힌다. Architecture 네 절이 모두 다이어그램의 Router 아래쪽이고 맨 위 상자 `화면 · hook`은 한 번도 설명되지 않는다. "현재 한계" 셋째 줄은 입력을 남기는 것이 목표라고 하지만 그 원칙이 앞에 나오지 않아 한계만 있고 기준이 없다.
- **반영 방식.** 세 가지를 비교했다. Architecture 5번 절 추가(추천), 기존 절에 몇 줄씩 분산, Architecture 밖 별도 섹션. 5번 절을 고른 이유는 사용자의 기준이 "통째로 갈아엎지 않는다"와 "매끄럽게 읽힌다"이고, 절 형식과 트레이드오프를 그대로 쓸 수 있다는 것이다. 별도 섹션은 가장 눈에 띄지만 형식이 달라져 덧붙인 인상을 주고, 데이터 설계와 같은 수준의 고민이라는 점이 약해진다고 보았다. 분산은 가볍지만 목차에 안 보이고 코드가 없다.
- **재료.** 조회 표시 상태를 중심에 두고 연결 미확인과 작성 중 입력을 짧은 문단으로 붙인다. 늦은 응답 처리는 9줄짜리 helper인데 이유를 설명하려면 문단 하나가 든다며 뺐다. 계층 구조는 Project 문서 스스로 엄격한 FSD 인증이 아니라고 적고 있어 강조하면 과장이 된다고 했다. 접근성은 테스트가 3건뿐이라 넣지 않았다. 클라이언트 테스트 파일 수(78개)는 금방 낡으니 적지 않고 절 끝 링크로만 쓴다.
- **일부러 약하게 쓴 곳.** 비활성·오프라인 안내는 버튼이 없어 "이유"까지만 썼다. "타입이 강제한다"고 쓰지 않았다. 훅이 원본 조회 값도 함께 돌려주므로 화면이 그것을 직접 쓰면 우회할 수 있기 때문이다. 이 저장소가 과거에 실패를 0원으로 보여 줬다는 이력은 확인하지 못해 "처음에는 …" 서사를 쓰지 않았다.
- **범위 밖 제안.** 홈 카드에서 "경비를 불러오지 못했어요"와 "0원"을 나란히 찍은 스크린샷이 있으면 설득력이 크게 오른다. 순증을 줄이려면 2번 절 트레이드오프(끝냄·보류·격리)를 한 문장과 링크로 줄일 수 있다.

Main은 리뷰어가 근거로 든 파일이 있는지와 화면 문구("불러오지 못했어요", "갱신하지 못했어요. 이전 내용을 표시하고 있어요", "확인 중", "확인 불가"), 관측 번호 처리, 문서 앵커를 검색으로 다시 확인했다. 그리고 리뷰어 안을 채택하되 연결 문단과 트레이드오프를 줄이고 Features 아래의 안내 한 줄은 넣지 말자고 사용자에게 권했다.

## 별도 절과 그 위치

사용자는 5번 절 안을 받지 않고 물었다. "만약 별도 절로 만든다면? 초안 보여줘봐"

Main은 별도 절이라면 Preview & Features 바로 뒤, Architecture 앞이 맞다고 했다. 상태별 표에서 "조회·저장 제한"을 본 직후라 자연스럽게 이어지고 프론트엔드 쪽 내용이 데이터 설계보다 먼저 나온다는 이유였다. 그리고 프론트엔드 엔지니어로 보이는 것이 목적이라면 5번 절보다 별도 절이 낫다고 판단을 바꿨다. 5번 절은 300줄 가까이 읽은 뒤에야 나온다는 것이다.

사용자의 답은 "별도 절이고 아키텍쳐 뒤에 오면 되는거 아닌가?"였다. 그래서 절은 Architecture 뒤, Tech Stack 앞에 들어갔다.

| 결정 | 누가 | 얻은 것 | 내려놓은 것 |
| --- | --- | --- | --- |
| 5번 절이 아닌 별도 절 | 사용자가 초안을 요청하고 별도 절로 확정. 이유는 말하지 않았다 | 목차 최상위에 보인다. Architecture의 "결론 → 배경 → 트레이드오프" 형식에 묶이지 않는다 | 리뷰어가 본 장점인 형식의 일관성. 트레이드오프 블록이 없다 |
| Architecture 뒤 | 사용자 | Policy와 활성 여행 개념이 1번 절에서 먼저 설명된다(리뷰어가 5번 자리를 고른 이유와 같다) | Main이 "앞"에서 기대한 첫인상. 이 절도 설계 절을 다 지난 뒤에 나온다 |

별도 절이 된 뒤에도 Architecture 도입 문장은 "아래 네 가지는 …"으로 남았고, 리뷰어가 제안한 "앞의 넷은 데이터가 지나는 길을, 마지막은 그 결과를 받는 화면을" 문장은 쓰이지 않았다.

## 초안 네 판

| 판 | 제목과 구성 | 사용자의 반응 | Main이 본 원인 |
| --- | --- | --- | --- |
| A | `UX: 끊겨도 화면이 지키는 것`. 기준 세 가지(빈 결과로 보여 주지 않는다, 오프라인으로 단정하지 않는다, 입력을 지우지 않는다)를 나란히 놓았다 | "근데 그것보다 아까 니가 말한것들의 매력이 덜 초안에 나온 느낌이야" | 원칙 세 가지로 정리하면서 왜 어려운 문제인지와 코드가 실제로 무엇을 막는지를 덜어냈다 |
| B | `Frontend: 불안정한 연결에서 화면이 지키는 것`. 화면 쪽에서 풀어야 했던 문제 네 가지. 늦은 응답 처리를 독립 항목으로 올리고, 캐시를 지우지 않고 가리는 선택과 달라진 항목만 보내는 폼을 되살렸다. 약 60줄 | "일단 대놓고 frontend라는 문단 제목이 짜쳐 다르게 바꾸고 음 훅으로 조합한 점도 프론트 엔드로서 좋은 관점인데 복잡한 훅으로 관리한거 그것도 안나온것 같아" | — |
| C | `UI State: 불안정한 연결을 화면이 다루는 방식`. 훅 조합을 절의 뼈대로 맨 앞에 올리고, 사용자에게 보이는 차이는 훅이 만들어 내는 결과로 옮겼다. 약 75줄 | "아니 그렇다고 그걸로 다 바꾸면 어떻게 해 아까 사용자 경험제공과 방금 지적한 부분을 아우르는 문단으로 하고 아래 구성해야지" | 훅 이야기로 절 전체를 덮어서 사용자에게 무엇을 지켜 주는지가 훅 설명의 부속물이 됐다 |
| D | `UI State: 불안정한 연결에서 화면이 지키는 것`. 도입 문단이 사용자 경험(무엇을 지키나)과 훅 조합(어떻게 지키나)을 함께 말하고, 아래를 지키는 세 가지 → 훅 조합 → 늦은 응답 처리 순으로 둔다. 약 70줄 | "그래 이정도 방향으로 하자" | — |

여기서 두 가지를 구별해 둔다.

훅 조합이라는 관점은 사용자가 가져왔다. Main의 재료 조사와 리뷰어의 보고는 조회 결과를 화면 상태로 바꾸는 곳이 한 군데에 모여 있다는 점까지만 말했다. 사용자의 지적 뒤에 Main이 조회 훅을 다시 읽고, 화면이 부르는 훅이 세 줄이며 그 세 줄이 각각 한 가지만 아는 훅 세 개를 잇는다는 것을 찾았다. "아는 것 / 모르는 것" 표는 여기서 나왔다.

C가 반려된 것은 훅 조합이 틀려서가 아니다. 사용자가 원한 것은 사용자 경험과 훅 조합 가운데 하나를 고르는 것이 아니라, 둘을 아우르는 도입 문단을 두고 그 아래를 구성하는 것이었다. 지금 도입부 두 문단이 그 요구에 대한 답이다. 첫 문단이 화면을 믿을 수 없는 순간과 세 가지 약속을, 둘째 문단이 그 판단을 훅에 모은 이유를 말한다.

제목에서는 `Frontend`만 반려됐다. Main은 `Architecture: 선택과 책임`과 같은 형식이라며 `UI State`를 골랐고, 영어를 빼고 싶으면 `화면 상태: …`도 된다고 했다. 사용자는 제목에 대해 더 말하지 않았다.

## 최종판에서 다시 빠진 것

D는 B와 C에서 되살린 내용 일부를 다시 덜어냈다. 사용자는 D를 "이정도 방향으로"라고 받았고, 아래 항목을 하나씩 확인한 것은 아니다.

- **달라진 항목만 보내는 폼.** 수정 폼이 처음 열었을 때와 달라진 항목만 보내고, 이것이 3번 절의 항목 단위 병합을 떠받친다는 내용이다. B와 C에 있었다. Main은 3번 절에 속하는 내용이라 사용자 경험과 직접 닿지 않는다며 D에서 빼고, 원하면 "쓰던 입력" 아래 한 줄로 되살리겠다고 했다. 사용자는 되살리라고 하지 않았다. 리뷰어도 같은 이유로 뺐던 재료다.
- **연결을 모르는 상태의 설명.** B와 C에서는 독립 하위 절이었고, 오프라인이나 온라인으로 처리하면 각각 무엇이 잘못되는지와 앱 복귀 때의 자동 재확인을 적었다. D에서는 목록 한 줄이 됐다.
- **`useAppPolicy`가 조건을 고르는 순서, 이전 렌더의 재조회 함수도 최신 조건으로 판단한다는 문장, 연결 확인의 관측 번호 설명.** C에 있었고 D에서 빠지거나 한 문장으로 줄었다.
- **"지하철 터널", "오프라인 안내가 깜빡인다".** B에서 문제를 설명하려고 Main이 쓴 장면이다. 실제로 겪은 일로 읽힐 수 있어 C에서 뺐다.

D에서 새로 들어간 것은 "막힌 이유를 그 자리에서 알린다"다. 리뷰어에게 넘긴 재료에는 있었지만(기능 제한 안내) A〜C에서 빠져 있던 항목이다.

## README에 반영하며 함께 바꾼 것

목차에 새 절과 하위 세 항목을 넣었다. "현재 한계" 셋째 줄은 "입력은 남기고 못 쓰는 부분만 막는 것이 목표"라는 설명을 빼고 새 절의 기준을 가리키는 링크로 바꿨다. 리뷰어가 짚은 "한계만 있고 기준이 없다"는 문제가 이것으로 풀렸다. README는 약 300줄에서 383줄이 됐다.

`cancelAndInvalidateQueries` 인용은 실제 소스에서 `.catch` 오류 처리와 원래 주석 두 줄을 빼고 README의 설명 주석을 단 형태다. 블록 첫 줄에 "(오류 처리 생략)"이라고 밝혔다. 기록 담당자가 현재 소스와 비교해 이 차이와, 나머지 두 블록(`useTripExpensesReadQuery`, `ReadQueryView`)이 주석을 빼면 소스와 같다는 것을 확인했다.

## 확인되지 않았거나 열린 것

- **렌더링.** 새 목차 앵커가 GitHub에서 제목으로 이동하는지 확인하지 않았다. 제목에 콜론과 영문이 섞여 있어 가장 어긋나기 쉬운 곳이라고 Main이 짚었다. push 뒤 Main이 브라우저 확인을 제안했지만 사용자는 답하지 않고 기록 이야기로 넘어갔다.
- **테스트와 화면.** 링크한 테스트 세 개는 실행되지 않았다. 실제 앱 화면도 보지 않았다. 문구와 분기는 소스 기준이다.
- **문장의 강도 하나.** 리뷰어는 훅이 원본 조회 값도 돌려주므로 타입이 강제한다고 쓰면 과하다고 했다. 최종 README의 "조회 실패와 0원이 같은 화면이 될 수 없는 이유입니다"는 그보다 강하게 읽힐 수 있다. 기록 담당자가 현재 훅을 읽었을 때도 `refetch`만 빠진 원본 조회 상태가 `query`로 함께 반환된다. 이 문장을 낮출지는 정해지지 않았다.
- **스크린샷과 분량.** 리뷰어의 범위 밖 제안 두 가지는 Main이 사용자에게 전했고, 사용자는 답하지 않았다. 남은 판단은 [Ticket 02](../current/memory/tickets/02-post-publish-checks.md)에 있다.
