# README의 문장을 코드와 배경 문서에 대조한 과정

구성과 가독성을 정리한 뒤(커밋 `542b3c54`) 사용자가 README의 한 문장을 의심했다. 그 의심에서 시작해 README 전체의 주장을 코드와 대조했고, 이어서 Project context의 `_background`를 읽어 두 곳을 더 고쳤다. 결과는 커밋 `bd2be723`이다. 이 기록은 무엇이 틀렸고 무엇이 맞았는지, 어떤 문장이 여전히 확인되지 않은 채 남았는지를 남긴다.

기록 담당자가 대화 원문 JSONL의 629〜1006행을 직접 읽고, 고친 문장은 `git show bd2be723 -- README.md`로 확인했다. 아래의 코드 동작은 Main이 소스를 읽어 보고한 내용이다. Main은 테스트와 앱을 실행하지 않았다. 기록 담당자는 그 대조를 되풀이하지 않았고, Architecture의 인용 블록 세 곳(Router, Outbox, `EXPENSE_EDIT_GROUPS`)이 현재 소스와 맞는지와 `cleanup-job.ts`가 정리 후보가 없으면 먼저 반환하는지만 직접 확인했다.

## 의심과 실제 결과

사용자의 말은 이렇다. "근데 내용중에 미전송 있으면 sync queue가 막힌다 했는데 실제 다중기기 작업에서 그게 해제 된걸로 알아 그래서 그러는데 이제 지금 리드미 기준으로 디테일하게 검증해봐 맞는지 코드랑 대조해서"

대조 결과는 사용자의 기억과 README 문장이 둘 다 부분적으로 맞았다는 것이다. README의 "실패하면 뒤 작업을 멈춘다"는 일반 실패(통신 오류, 5xx, 원인을 구별할 수 없는 404 등)에는 지금도 맞다. 그 경우 작업을 FAILED로 남기고 뒤 작업을 보내지 않으며 pull도 하지 않는다. 다만 멈추지 않고 넘어가는 경우가 넷 있었고 README에는 그 예외가 없었다.

| 경우 | 지금 동작 (Main 보고) |
| --- | --- |
| 구버전 앱의 요청이 서버 값과 충돌 (409) | 원문을 보류로 옮기고 큐에서 빼서 다음 작업을 계속 보낸다 |
| 이미 삭제된 기록·여행에 대한 요청 (410) | 삭제를 확인하고 그 요청을 끝낸 뒤 계속 보낸다 |
| 기기 원본을 잃은 요청 | 격리하고 뒤의 정상 작업을 보낸다. 여러 기기 작업 이전 커밋에서 들어온 동작이다 |
| 전송 도중 새로 저장한 변경 | 막힌 것으로 세지 않고 pull까지 진행한다 |

Main은 마지막 줄이 사용자가 기억한 변경일 가능성이 크다고 보았다. 이전에는 FAILED·IN_PROGRESS 개수로 중단을 판단했고 커밋 `e994171c`에서 남은 정상 PENDING을 다음 실행의 입력으로 보게 바뀌었다는 설명이다. 이것은 Main의 추정이며 사용자가 확인해 주지는 않았다.

README에는 앞의 셋만 예외로 적었다. 네 번째를 넣지 않은 이유는 원문에 설명이 없다. 실패한 요청을 넘기는 예외가 아니라 막힘을 세는 방식의 변화라서 트레이드오프 문장과 결이 다르다는 것은 기록 담당자의 해석이다.

7일에 관한 코드 동작은 Main이 처음 대조할 때 이미 찾았다. 그때는 "README 문장은 틀리지 않았지만 코드가 더 좁게 동작하는 곳"으로만 보고하고 고치지 않았다가, 배경 문서를 읽은 뒤에 문장을 낮췄다. 같은 동작은 Project의 데이터 수명 본문에도 적혀 있다(자동 경로는 정리 후보가 없으면 vacuum 전에 반환한다는 문단). 이 동작이 의도인지는 이 Work에서 판단하지 않았다.

코드와 일치한다고 Main이 보고한 것은 다음과 같다. 인용 코드 세 곳, ULID 생성과 서버의 ID 수용, 횟수 제한 없는 재시도, 생성·삭제의 멱등 재전송, 편집 표식과 서버의 묶음별 비교, 응답 대기 중 재수정을 겹쳐 보여 주는 동작, 구버전 충돌 보류, 여행 해제 시 사본 유지와 정리 예약, 로그아웃·탈퇴 보류와 명시적 폐기, 재인증 중 동기화 중단, 상태별 표, 버전·JWT 만료 시간·Quick Start 명령, 현재 한계 세 줄, 링크한 테스트 두 개의 내용.

## 배경 문서를 뒤늦게 읽은 경위

네 곳을 고치는 도중 사용자가 물었다. "너 project/context 에서 _background 들도 확인해서 반영한거지? 이전에?"

Main의 답은 "아니요"였다. 그때까지는 각 주제의 본문(INDEX, 결정 문서, 제품 기준, 현재 구조)과 코드만 보았다. Main은 그 자리에서 README와 관련된 다섯 개(데이터 수명의 맥락·근거, 여행 접근, 지도·경로, 앱 실행)를 읽고 위 표의 마지막 두 줄을 고쳤다. 통화, 날짜, API 계약, 작성·입력, 개발 경계의 형성 자료는 README가 다루지 않는 주제라며 읽지 않았다.

배경 문서가 README에 준 것은 "과거 문서가 지금 구현보다 강하게 말했던 부분"이다. 본문만 읽으면 현재 기준은 알 수 있지만, 예전에 쓰던 표현 중 어느 것이 과장이었는지는 알기 어렵다. 이번에 더 고친 두 곳이 모두 그런 표현이었다. 배경 문서와 일치해 그대로 둔 것도 있다. 횟수 제한 없는 재시도의 이유, 큐가 하나인 이유, 재인증 중 기기 이용 유지, 명시적 로그아웃 때만 폐기, 사용자가 온라인/오프라인 모드를 고르지 않는 선택이다.

## Router와 Policy 문단

1번 절에서 Router와 Policy를 나눈 이유는 네 문장짜리 한 문단이었다. 사용자는 그 문단을 그대로 붙여 넣고 말했다. "이렇게 넣으면 이해가 안되니까 잘 적어봐 문단 형식으로나 뭔가 좀 정리해서"

Main이 본 원인은 왜 활성 여행이 온라인 지도를 못 썼는지를 건너뛰고 바로 결론으로 간 것이다. 고친 글은 문제(활성 여행이면 지도와 검색까지 오프라인 방식으로 동작했다) → 원인(성격이 다른 데이터와 서비스를 같은 기준으로 묶었다) → 역할 표(Router와 Policy가 각각 무엇을 무엇으로 정하는지) → 결과(활성 여행도 온라인에서는 검색과 Google 지도를 쓴다) 순이다.

확인되지 않은 문장이 하나 남았다. "처음에는 활성 여행이면 … 지도와 장소 검색까지 오프라인 방식으로 동작했습니다"는 결정 문서와 배경 문서의 서술을 근거로 쓴 것이고, 당시 코드를 확인한 것이 아니다. Main은 이 점을 밝히고 기억과 다르면 알려 달라고 했다. 사용자는 이에 답하지 않고 "커밋해"라고 했다. 1번 절 첫머리의 "처음에는 모든 여행을 기기에 자동으로 저장했습니다"도 같은 종류의 과거 서술이며, 이 문장의 근거를 대조한 흔적은 원문에서 찾지 못했다.

## 커밋과 push

커밋은 `bd2be723`이고 README만 포함한다. Main은 이 커밋을 push하지 않았다. 다음 커밋(`b418d5cb`)을 push할 때 원격에 없는 커밋은 그것 하나뿐이었으므로 `bd2be723`은 그 사이 다른 경로로 원격에 올라가 있었다. Main은 사용자가 직접 올린 것으로 보았지만 원문에서 확인되지는 않는다.

Router·Policy 역할 표와 세로 다이어그램이 GitHub에서 어떻게 보이는지는 이때도 확인하지 않았다.

## 이 Work 밖으로 넘긴 것

README는 코드에 맞췄고 다른 문서는 고치지 않았다. 대조에서 드러난 것 가운데 README 밖의 문서와 관련될 수 있는 사실은 다음과 같다. 반영 여부는 이 Work에서 정하지 않았다.

- 서버의 `GOOGLE_GEO_DIRECTIONS_API_KEY`는 설정에만 있고 쓰이지 않는다는 Main의 보고. 기록 담당자가 서버 소스를 검색했을 때도 이 값을 읽는 곳은 설정 파일뿐이었다. 서버 README는 이 키를 Google 경로 서비스용으로 설명하고, 개발 시작 안내는 환경 변수 예시에 이 키를 두고 있다.
- 여행 정보 수정이 요청 단위로 덮어쓴다는 사실. Project의 여러 기기 편집 기준은 제목부터 일정·경비로 범위를 정하고 있으나, 여행 수정의 동작을 따로 적은 문장이 있는지는 기록 담당자가 확인하지 못했다.
