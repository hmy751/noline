# README의 뼈대와 문장을 정한 과정

README의 지금 구성은 처음 요청에서 바로 나온 것이 아니다. 요청은 "지금 프로젝트 컨텍스트와 코드를 통해서 리드미를 좀 개선할 수 있을까?" 한 문장이었고, 독자·분량·구성에 관한 기준은 초안이 두 번 반려되는 동안 사용자 발화에서 하나씩 드러났다. 이 기록은 세 판을 거치며 무엇이 반려됐고 왜 지금 뼈대가 됐는지를 남긴다.

기록 담당자가 대화 원문 JSONL의 1〜591행(컨텍스트 요약 이전 구간)을 직접 읽고 썼다. 사용자 발화의 원문과 행 번호는 [사용자 방향 원문](../source/user-direction.md)에, 커밋되지 않은 초안을 꺼내는 방법은 [source 색인](../source/index.md)에 있다. 세션은 한국 시각 2026-11-14 23:17에 시작해 자정을 넘겼고, 커밋 네 개는 모두 2026-11-15에 만들어졌다.

### 2판 뒤의 질문과 답

사용자는 두 번(1판 뒤, 2판 뒤) "모르겠으면 물어봐", "질문을해서 이끌어봐"라고 했다. Main은 2판 뒤에 가설을 세워 네 가지를 물었다. 가설은 "원래 뼈대를 버리고 새 틀을 얹은 것이 문제이고, 8개 결정을 같은 무게로 나열해 초점이 없다"였다.

| 질문 | 사용자의 답 | 반영 |
| --- | --- | --- |
| 아쉬운 점 (복수 선택) | 네 보기를 모두 골랐다: 내용이 너무 많다, 첫 화면이 무겁다, 제품 소개가 약해졌다, 원래 글의 흔적이 없다 | 첫 화면의 표를 없애고 Motivation과 기능 설명을 되살렸다. |

뼈대 질문에서 Main이 보여 준 추천안의 순서는 Motivation → Preview & Features → Architecture → Authentication → Tech Stack → Quick Start였다. 2026-10-31판의 실제 순서는 Architecture가 Quick Start 뒤에 있었다(`git show bebf1232:README.md`). Architecture를 앞으로 올린 것은 1판에서 Main이 바꾼 순서이고 이 추천안이 그대로 이어받았다. 그러므로 "원래 구성을 살렸다"는 것은 제목과 문단을 살렸다는 뜻이지 10-31판의 절 순서를 되돌렸다는 뜻이 아니다. 사용자는 이 순서가 담긴 미리보기를 보고 답했다.

## 설계 절을 4개로 정한 이유

Main은 Project context에서 지금 가장 비중이 큰 흐름을 "어디에 저장하나 → 어떻게 보내나 → 겹치면 무엇이 남나 → 지울 때 무엇을 지키나"로 읽고, 2판의 8개를 이 순서의 4개로 묶었다.

| 절 | 담은 것 | 흡수한 것 |
| --- | --- | --- |
| 1. 활성 여행에 준비를 집중 | 대안 비교 표, Router 코드 | 데이터/서비스 분리, 상태별 표(이후 Features로 이동) |
| 2. 저장한 변경을 서버까지 전달 | Outbox 코드, 전송 규칙 | 클라이언트 ID 생성 |
| 3. 여러 기기 편집 | 휴대폰·태블릿 예시, 묶음 코드 | 구버전 요청 복구 |
| 4. 보내지 못한 변경 보호 | 해제·삭제·로그아웃·로그인 만료 | 삭제 7일, 인증 절의 로그아웃 보류와 재인증 |

데이터/서비스 분리를 1번 절 안에 넣은 이유는 두 가지다. 사용자가 고민된다고 했고, Router를 넣은 뒤 생긴 문제라 이야기가 이어진다는 것이 Main의 판단이었다. 격리, pull 조회 경계, Hybrid Logical Clock 설명은 본문에서 빼고 문서 링크로 넘겼다. 화면이 입력과 맥락을 보존한다는 원칙은 이때 Features 한 줄과 "현재 한계"로만 남았고, 나중에 [UI State 절](2026-11-15-04-ui-state-section.md)이 됐다.

4라는 숫자는 사용자가 정한 제약이 아니다. 사용자가 준 것은 "무엇이 적절한지 Project context를 면밀히 보고 고민하라"는 기준이다. Main은 3판을 내면서 "아직 많다고 느껴지면 가장 먼저 덜어낼 후보는 1번의 대안 비교 표와 4번 절"이라고 했고, 사용자는 이 후보를 택하지 않았다.

2번 절 제목은 처음에 "빠짐없이 서버에 전달한다"였다. Main이 과한 표현으로 보고 "서버까지 전달한다"로 고쳤다. 사용자의 지적이 아니라 Main의 자체 수정이다.

## Authentication과 더 읽을 곳을 없앤 과정

3판을 본 사용자가 "Authentication 이랑 더 읽을곳은 좀 안해도 되지 않을까 싶어"라고 했고, 수정하지 말고 구조 변경을 제안하라고 했다. Main은 두 절을 없애는 데 동의하면서, 통째로 지우면 사라지는 내용만 다른 곳으로 옮기자고 했다.

| 제안 | 이유 | 결과 |
| --- | --- | --- |
| Authentication 절 삭제. OAuth·JWT는 Tech Stack 표 한 줄로, 로그아웃 보류와 재인증 중 이용은 4번 절로 | OAuth·JWT는 흔한 구성이다. 4번 절은 목록만 있어 가장 약했는데 해제·삭제·로그아웃이 모이면 주제가 또렷해진다. | 반영. 4번 절 제목도 "아직 보내지 못한 변경은 지우지 않는다"로 바꿨다. |
| 더 읽을 곳 삭제. 서버 안내와 DB 스크립트 링크만 Quick Start 끝으로 | 나머지 링크는 이미 본문에 있다. | 반영 |
| 소개 둘째 문단(이 README가 무엇이고 정본이 어디인지)을 맨 아래로 | 문서에 대한 설명이라 첫 화면에서 힘이 없다. | 반영. 지금 README의 마지막 문장이다. |
| (선택) 상태별 표를 1번 절에서 Preview & Features로 | 1번 절이 가장 길다. 표는 설계보다 앱 동작 설명에 가깝다. | 이때는 보류. 두 절의 균형이 함께 바뀐다는 이유였다. 아래 가독성 정리에서 반영됐다. |
| (선택) Features 목록 다섯 줄을 네 줄로 | 마지막 두 줄이 그리드 캡션과도, 서로도 겹친다. | 반영 |

사용자의 답은 "그래 그렇게 해봐"였다. 선택 사항 둘 중 하나만 반영한 것은 Main의 판단이다. "현재 한계" 절은 Main이 남기기를 권했다. 세 줄뿐이고 한계를 스스로 밝힌 문서가 개발자에게 더 믿음을 준다는 이유였다.

함께 빠진 것이 있다. 관리자에게 하는 말인 "제품 동작이나 구조를 바꾸면 README를 함께 갱신합니다"와, 4번 절 주제에서 벗어난 공유 지도 파일 이야기다.

## 가독성 정리

`707468c4`를 push한 뒤 사용자가 "가독성을 위해서 더 개선할 수 잇는 부분 잇을까? 쭉쭊잃히고 이해되게 대상은 개발자"라고 물었다. Main은 GitHub 페이지를 브라우저로 열어 목차 링크, 3열 그리드, mermaid 다이어그램이 그려지는 것을 확인했고, 다이어그램은 노드 일곱 개가 가로로 늘어서 글자가 작게 나온다는 것을 보았다. 그 뒤 여섯 가지를 제안했다. 구성이 아니라 문장과 절 안의 흐름에 관한 것이었다.

1. **첫 문단을 쉬운 말로.** 첫 문장에 "Selective Local-First"가 설명 없이 나오고 추상 명사가 이어졌다. 무엇을 하는 앱인지 먼저 말하고 마지막 문장에서 이름을 붙이게 했다.
2. **Architecture 절마다 굵은 결론 한 줄.** 절마다 순서가 달라 훑어보기 어려웠다. 제목 아래 결론을 두고 본문은 왜 → 어떻게 → 트레이드오프로 맞췄다.
3. **다이어그램을 세로 방향으로.** 부수 노드(Policy, PostgreSQL)를 빼고, 앞에 무엇을 볼지 알려 주는 두 문장을 두었다.
4. **같은 것을 한 가지 말로.** "미전송 변경"은 "보내지 못한 변경"으로, "필드"는 "항목"으로 맞추고 "Local SQLite"는 한 번만 밝혔다. 3번 절을 읽어야 뜻을 아는 "사용자의 선택을 기다리는 입력"은 4번 절에서 뺐다.
5. **1번·2번 절의 곁가지 정리.** 상태별 표를 Features로 옮겼다. 앞서 보류한 안인데 렌더링된 화면을 보니 옮기는 쪽이 낫다고 Main이 판단을 바꿨다. 2번 절은 Outbox를 먼저 두고 ID 생성을 규칙 목록의 한 줄로 내렸다.
6. **긴 문단 쪼개기.** Quick Start 마지막 문단을 세 줄 목록으로, Motivation 둘째 문단을 두 문장으로 줄이고, 현재 한계 셋째 줄은 현재 동작을 먼저 말하게 뒤집었다.

Main은 1〜3번의 효과가 가장 크고 4〜6번은 다듬기에 가깝다고 했다. 사용자가 "일단 반영해봐"라고 해 여섯 가지를 모두 반영했다(커밋 `542b3c54`). 이때 첫 문단의 "지도와 경로는 준비된 범위에서 사용할 수 있다"는 문장이 빠졌다. 같은 내용이 현재 한계에 있다는 이유였다.

`542b3c54`를 push한 직후 Main이 다시 브라우저를 열려 했을 때 사용자가 그 호출을 중단했다. 그래서 세로로 바꾼 다이어그램은 GitHub에서 확인되지 않았다.

## 되살리지 않은 것

- **2026-03판의 수치.** "85% 압축", "엣지케이스 21개 → 9개", "도시당 60~200MB"는 지금 근거를 확인할 수 없어 넣지 않았다. Main은 실측값이 있으면 넣을 자리가 있다고 했다.
- **이모지 제목.** 2판에서 넣지 않았고 이후 논의되지 않았다. 목차도 2판에서는 뺐지만 사용자가 원해 3판에서 넣었다.
- **README 독자가 알 수 없는 맥락에 기대는 문장.** 10-31판의 "과거 README의 압축률은 제시하지 않습니다", "7일 복구 기능으로 소개하지 않습니다" 같은 문장은 사실 서술로 바꿨다.

## 확인한 범위와 열린 것

- **수락의 강도.** 구성에 대한 사용자의 말은 "얼추 된것 같아", "일단 커밋 해보자"다. 가독성 정리는 "일단 반영해봐" 뒤 결과에 대한 평가 없이 "커밋하고 push"로 이어졌다. README 전체를 최종 수락한다는 발화는 원문에 없다.
- **버전 배지.** `app.config.js`의 1.1.2에 맞췄다. Main은 이 판이 빌드 16으로 심사에 접수된 것이라 App Store에 올라간 버전과 다를 수 있다고 알리고 스토어 기준이 낫다면 말해 달라고 했다. 사용자는 이 점에 답하지 않았다.
- **Preview 자산.** 새로 찍지 않았고 README에 이전 버전에서 녹화한 데모라고 적었다. 저장소에 있었지만 쓰이지 않던 `manual-input1.png`를 그리드에 넣었다.
- **링크.** 판마다 Main이 파일 링크와 목차 앵커를 대조했다. `pnpm harness:check`는 과거 Workspace 기록의 끊긴 링크 64건으로 실패했고 README에서 나온 항목은 없었다는 것이 Main의 보고다. 기록 담당자가 다시 실행하지는 않았다.

문장의 사실 여부를 코드와 대조한 것은 이 뒤의 일이며 [코드·배경 문서 대조 기록](2026-11-15-03-code-and-background-check.md)에 있다.
