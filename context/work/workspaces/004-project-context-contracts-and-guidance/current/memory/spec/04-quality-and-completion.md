# 품질과 완료 판단

제품 계약 작업은 확인된 경계별 사실, 사용자와 비교한 선택 및 채택 이유, 반영된 기준 본문과 남은 구현 차이를 함께 확인한다. 사실 오류나 기존 의미 누락을 모두 사용자에게 새 선택으로 돌리지 않는다. 아직 선택되지 않은 항목을 “열린 문제로 적었다”는 이유만으로 해결 완료 처리하지 않는다. 일부를 의도적으로 후속 범위로 남기려면 사용자와 그 범위를 합의한다.

지침 개선은 실제 실패와 당시 기준의 관계를 대조해 바꿀 책임과 이유를 설명하고, 수정된 지침을 다른 실행 주체가 적용한 산출물로 확인한다. 기존 의미 보존, 사실 대조, 주제별 충분성, current의 효용·관리비용, 기존 진입점과 변경 영향의 연결이 확인 대상이다. 작성자가 결과를 직접 고친 것과 새 지침으로 다시 구성한 것은 구별한다. 재실행하지 못했다면 개선안 작성까지의 결과로 남긴다.

제품 합의와 지침 변경을 같은 시험에서 함께 바꾸면 무엇이 개선을 만들었는지 불명확할 수 있다. 당시 입력·지침·산출물과 개입 범위를 보존하고 변화의 영향을 구별한다. 기존 결과와 동일한 파일 수나 문구를 재현하는 것이 목적은 아니다.

기계 검사는 의미 판정을 보조한다. `node scripts/check-harness.mjs`, `git diff --check`, 004의 explicit Recover로 경로·형식·재진입을 확인한다. Project Owner나 경로를 바꾼 실행에서는 관리 계약에 따라 영향받는 live consumer도 확인한다. 제품 코드를 바꾸지 않은 문서 시험에서 테스트 개수를 늘리는 것으로 문서 품질을 증명하지 않는다.

초기 `verify.json`은 Python 표준 JSON 파서로 004의 `recover.json`이 읽히는지만 검사한다. 선언한 evidence는 그 파일 하나이며 Python runtime은 외부 실행 환경이다. 이 작은 claim은 schema·내용·지침 효과를 보장하지 않는다. 생성 때 durable Verify는 실행하지 않으며, 이후 검증 계약을 넓힐 때에는 실제 명령의 입력 범위와 claim을 함께 구체화한다.

Workspace 완료는 두 Ticket의 맡은 결과와 사용자 수락을 대조해 판단한다. 다른 세션의 보고, Main의 직접 대조, 실제 제품 실행을 구분하고 기존 테스트 pass나 002의 완료를 004의 완료로 이어받지 않는다.
