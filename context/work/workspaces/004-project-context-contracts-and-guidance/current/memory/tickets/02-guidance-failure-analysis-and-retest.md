# Project 작성 지침의 실패 분석과 재시험

## 맡은 결과

기존 지침이 실제 갱신 결과의 문제를 걸러내지 못한 이유를 판단하고, 필요한 지침 수정을 수행한 뒤 다른 세션·실행 주체의 결과로 효과를 확인한다. 현재 본문을 Main이 직접 완성하는 것은 이 Ticket의 완료를 대신하지 않는다.

## 실행 맥락

`3baa7b7`은 Project 구조·읽기·REFERENCE를 정비했고 `2937c25`는 원자료 순서의 본문화, 사례 선별, current의 추가 효용·중복, 대표 작업의 읽기 검증을 보강했다. 그 지침으로 다른 세션이 당시 미커밋 초안을 만들었다. 받은 결과는 완료를 보고했지만 Main의 직접 검토에서 다음 문제가 남았다.

- `current/architecture.md`에 테스트 개수, 이번 환경의 EPERM, Docker 미실행 등 실행 이력이 누적됐다. 검사 기반과 증명 범위를 설명하는 의미와 구별해야 한다.
- 이전 currency 정책의 Expense별 통화 선택과 금액·통화 코드/기호 동시 표시가 새 Owner 본문에 명시적으로 이어지지 않았다.
- 날짜 문서는 client local 입력도 date-only를 강제한다고 설명하지만 form·request·local 경계가 서로 다르다.
- 기존 server guide의 API runbook 진입에는 새 API 본문이 연결되지 않았다. 날짜 runbook도 기존 일괄 datetime 문구에서 시작한다.

API 공통 계약과 기능별 적용을 한 흐름으로 구성한 점, 리팩터링을 원칙 중심으로 재구성한 점은 개선됐다. 이 개선은 유지할 후보지만 파일 수가 줄었다는 사실만으로 전체 성공을 판정하지 않는다. [원문 발췌](../../../source/trial-excerpts.txt)는 수정 전 문구를, [생성 기록](../../../records/2026-09-14-01-workspace-setup-and-review-basis.md)은 확인한 근거와 Main의 해석을 구분한다.

이후 관리·구성·읽기 기준과 읽기·갱신 skill을 보강하고 기준 commit의 격리 재시험에서 앞선 네 실패가 개선된 것을 확인했다. 그러나 원복 뒤 별도 세션이 다시 만든 문서에서는 본문 자체의 품질과 사실성은 좋아졌어도 기존 Owner 의미 보존, 실제 개발 진입점, Workspace Recover·state·output reconciliation이 다시 빠졌다. 그때 Main 검토에서는 `current`의 실행 기록화와 날짜 사실 오류가 해결됐고, 통화 의미 보존은 부분 해결됐으며 실제 진입점 연결은 미해결로 남았다.

## 접근과 열린 판단

앞선 Main은 이 반복을 완료 장치 부족으로 진단해 초안과 전환 완료의 분리, 네 가지 필수 결과 보고, 별도 검증 단계와 자동 검사 보강을 제안했다. 그러나 다른 세션이 기존 지침을 실제로 어떻게 적용했는지 확인하지 않았으므로 절차 부족을 원인으로 확정할 근거가 없고, 이 제안은 이미 있는 의미 보존·사실 확인·진입점 점검·Workspace 연결 기준과도 겹친다. 따라서 큰 완료 장치는 현재 개선안에서 제외한다.

선택한 최소 수정은 `update-project-context`의 기존 마지막 확인에서 검토의 출발점을 분명히 하는 것이다.

> 변경 후에는 기존 문서와 기존 작업 진입점에서 시작해, 보존해야 할 의미가 새 본문에 남아 있는지, 이전 경로로 들어온 독자도 변경된 기준과 열린 판단에 도달하는지 확인한다.

이 문구는 통화 기준 누락과 runbook 미연결을 함께 겨냥한다. 새 단계·필수 보고 양식·자동 검사를 추가하지 않고 기존 확인 절차 안에 통합한다. `current` 구성과 날짜 사실성에 관한 기존 지침은 후속 결과에서 개선이 확인됐으므로 유지한다.

제품 계약의 정답은 Ticket 01이 맡으며 이 지침 변경이 대신 결정하지 않는다. 다른 세션의 적용 과정이 확인되지 않은 상태이므로 이번 실패가 문구 하나로 해소된다고 단정하지 않는다. 최소 수정은 현재 문서 보완에 적용했고, 다음 실제 독립 갱신에서도 재발 여부를 확인한다.

## 완료 확인

최소 문구가 기존 갱신 절차에 중복 없이 통합되고, 다음 실제 Project context 갱신에서 기존 Owner와 실제 작업 진입점부터 대조했는지 확인한다. 그 결과에서 기존 의미 보존과 변경된 기준·열린 판단으로의 도달성이 개선됐는지 판단한다.

정적 검사 통과나 작성자의 자체 설명만으로 완료하지 않는다. 반대로 별도 단계·고정 보고 양식·자동 검사를 두지 않았다는 이유만으로 불충분하다고 판정하지 않는다. 작은 수정의 실제 효과와 남은 실패 원인을 근거로 추가 장치의 필요성을 다시 판단한다.

## 현재 상태

재검토에서 선택한 최소 수정을 `update-project-context`의 기존 완료 확인에 통합했다. 변경 뒤 기존 Owner와 영향받은 기존 작업 진입점에서 각각 시작해 의미 보존과 변경된 기준·열린 판단으로의 도달성을 확인하도록 문장을 명확히 했다. 별도 단계·필수 보고 양식·자동 검사는 추가하지 않았다.

Main이 현재 Project 문서를 직접 보완하면서 이 기준을 적용해 통화 의미, API·날짜·통화 routing과 004 live consumer를 맞췄다. 이는 현재 누락을 해소한 근거지만 다른 실행 주체에서도 최소 문구가 재발을 줄이는지는 아직 확인하지 않았다. 다음 실제 독립 갱신에서 같은 누락이 반복되는지 확인한 뒤 Ticket 완료와 추가 장치의 필요성을 판단한다. 앞선 원인·실행·검증 한계는 [작업 기록](../../../records/2026-09-14-02-guidance-failure-analysis-and-retest.md), 당시 기준 선택은 [결정 기록](../../../../../../../.claude/decisions/2026-09-14-project-context-semantic-and-routing-verification.md)에 남아 있다.
