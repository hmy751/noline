# 실제 설계 선택과 결과를 기준으로 Ticket 재구성

## 요청과 판단 변화

사용자는 후보 16개를 보고 “왜이렇게 많지? 작업한게 많은거야? 아님 기록을 바탕으로 판단한거야? 뭐지?”라고 물었고, 이어 “다시 구성한다 생각해봐”라고 요청했다. Main은 16개가 실제 개선 필요를 확인한 결과가 아니라 기록의 주제를 세분화하고 미완료·검증·마무리를 함께 나열한 후보라고 정정했다.

원래 목표는 새 Context를 기준으로 02의 기록과 코드를 대조해 개선하는 것이다. 따라서 당시의 설계 선택과 실제 결과를 검토 단위로 삼고, 기록·코드·대안 판단·채택한 개선·검증을 같은 Ticket에 묶는 안을 제시했다. 첫 대상이던 일정 저장 후 처리는 미완료 범위가 중심이어서 기존 남은 개발을 이어 하는 쪽으로 흐르기 쉽다고 판단해 후속 후보로 내렸다.

대신 저장 용량 Hook, 일정·경비 조회 공통화, 인증·세션 책임 재배치의 세 단위를 제안했다. 사용자는 “그래 그 방향으로 스펙이랑 티켓 다시 구성해줘”라고 승인했다. 이 발췌는 현재 Codex 대화의 2026-10-30 발화이며 전체 02 대화 전사본은 아니다.

## 적용 범위와 이유

Spec의 첫 대상·대표 사례·실행 단위·완료 기준, Ticket과 색인, Context 선택·범위 지도·state·source/output 진입을 함께 맞춘다. 기존 01 경로는 저장 용량 Ticket 경로로 바꾸며 현재 내용은 채택한 방향으로 대체한다. 초기 선택·생성 검사 근거는 앞선 record를 보존한다.

저장 용량에는 초기의 얕은 정리, 사용자 정정, 최종 책임 분리와 검사 한계가 연결된다. Main은 기존 Ticket·실행 기록과 현재 hook을 일부 직접 읽었다. 조회 조합은 당시 명명·배치 기록과 공통 훅 일부를 확인했다. 인증은 기존 기록 색인·결과 설명으로 초기 범위를 잡았고 실제 전체 대조는 착수 시 수행한다. 이를 세 영역의 개선 필요가 이미 입증됐다는 뜻으로 쓰지 않는다.

각 Ticket은 유지가 적절하면 그 근거로 끝낼 수 있고, 개선을 채택하면 구현·검증까지 맡는다. 독립된 결과·제품 선택 때문에 나눌 수 있지만 조사·구현·검증을 기본적으로 별도 Ticket으로 늘리지 않는다. 초기 세 Ticket은 시작 범위이며 전체 02 검토를 대신하지 않는다.

제품 코드·기계 JSON·Verify receipt·active index·session binding·과거 02·03 자료는 수정하지 않는다. 제품 검사·activation·commit은 수행하지 않는다. 이 문서 반영은 Main이 explicit 005의 수동 Maintain bootstrap·guarded apply로 수행하며 자동 session 연결을 만들지 않는다. README와 Ticket 파일명 정렬은 사용자가 요청한 재구성의 Main 작업이다.
