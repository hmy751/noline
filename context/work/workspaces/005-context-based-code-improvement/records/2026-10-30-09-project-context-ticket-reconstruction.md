# Project Context 우선 범위와 Ticket 재구성

2026-10-30 사용자 요청:

> 그럼 컨텍스트 기준으로 다시 구성하고 먼저 작업하자 니가 한건 개인 판단 그거 같은데 그건 나중에 하게 티켓 구성 다시 생각해보자

Main은 이번 단계의 산출물을 제품·구조·계약의 Project Context로 정리하고 개인 판단·협업·스킬 개선을 후순위로 분리했다. [전체 대응](2026-10-30-08-context-coverage-reassessment.md)의 각 항목을 독립 Ticket으로 만들지 않고, 다음 개발자가 함께 이해할 관계를 기준으로 세 실행에 묶었다.

- 04는 앱 준비·인증·DB 작업과 세션 종료의 보존 관계를 맡는다. 인증 하나를 전체 개선의 대표로 고르는 방식과 달리 앱이 준비됐다는 뜻과 실행 중 작업의 종료까지 연결한다.
- 05는 실제 네트워크·화면 표시·Query 실행·내용 공개와 복구를 맡는다. 여행 목록과 일정·경비 조회의 차이를 보존한다.
- 06은 작성 초안·선택창·Places·일정 연결·날짜 입력을 맡는다. 이미 반영된 시간·API·통화 계약을 중복 작성하지 않고 실제 입력 관계와 대조한다.

세 Ticket 모두 기록·코드 대조, 본문 보완, 읽기 경로와 확인까지 포함한다. 조사·검증·마무리를 별도 실행 Ticket으로 늘리지 않았다. 새 파일 배치는 본문의 질문·Owner·중복을 보고 정하며 Ticket 수와 파일 수를 일치시키지 않는다. 기존 충분한 의미는 범위 지도에 유지·관련 대조로 배치했다.

완료한 01은 보존하고 기존 02/03 코드 구조 재검토는 대체 상태로 남겼다. 원래 번호와 역사적 의미를 바꾸지 않기 위해 새 실행은 04–06을 사용한다. 현재 Spec 다섯 본문, memory·Ticket·state·source/output 진입을 맞추고 Workspace README 및 Recover 선택을 현재 목적에 맞춘다. 002의 역사 자료, 제품 코드·Project 본문·개인 기준·기계 검증 상태는 이 재구성에서 변경하지 않는다.

이번 결과는 실행 가능한 작업 재구성이며 Context 본문 보완 완료가 아니다. 첫 실행은 04에서 현재 앱 준비·인증·종료 구현과 기존 Owner를 대조해 유효한 계약을 복원하는 일이다. 사용자 보류와 새 제품 선택이 필요한 충돌을 구별한다.
