# 재작업 장면과 현재 Context를 대조한 개선 후보

2026-10-30. 사용자는 앞선 목적 재판단에 이어 “그래 다시 파악해봐 그리고 context 보완 관련도”라고 요청했다. Main은 코드 영역별 순회를 이어가는 대신 002의 큰 정정·원복·판단 전환과 잘된 대조 사례를 살피고, 현재 제품 코드와 Personal·Project 및 기존 상세 Owner를 대조했다. 이번 요청으로 재조사 방향은 선택됐으며 아래 개별 개선안의 구현·기준 채택까지 결정된 것은 아니다.

## 무엇을 개선해야 하는가

005에서 저장 용량의 작은 보완을 완료한 것과, 원래 루프에 중요한 대상을 골랐다는 것은 다른 판단이다. 002에서도 문제는 한 방향으로만 생기지 않았다. 좁게 끝내는 일뿐 아니라 품질 개선을 기능 확장으로 넓히거나, 동작 검사를 구조 적절성의 근거로 확대하는 일이 있었다. 따라서 모든 사례를 ‘더 깊게 검토한다’나 ‘더 많이 테스트한다’ 하나로 묶는 것은 부정확하다.

- [네트워크 소비자 품질 개선과 원복](../../002-code-readability-refactoring/records/2026-09-17-02-network-consumer-quality-improvements.md): 사용자 요청은 “동작의 개선보다 가독성 응집도 뭐 파악쉬운 등의 spec 목표정도의 코드 퀄리티”였다. 기능 확장과 검사가 진행됐지만 목표를 벗어난 변경을 원복했다. 허용 범위와 개선 이득을 먼저 정해야 했던 사례다. 원복된 구현을 현재 결함으로 취급하지 않는다.
- [인증 복잡도와 선택](../../002-code-readability-refactoring/records/2026-09-19-01-auth-complexity-review-and-decisions.md): 사용자는 “관리 복잡도가 너무 높아 보여서”라고 문제를 제기했다. 같은 계정 재인증과 명시적 로그아웃 뒤 계정 변경을 택하면서 복잡한 자동 전환을 줄였다. 테스트 통과 뒤 실제 연동 검사를 추가하자 놓친 경계도 드러났다. 제품 선택의 단순화와 검증 범위 보완은 서로 다른 개선이다.
- [인증 소비자 검토와 원복](../../002-code-readability-refactoring/records/2026-09-21-02-auth-token-separation-consumer-review-and-rollback.md): 사용자는 “그렇다고 각 소비하는데서 이렇게 애매하면 안되잖아”라며 전체 소비 관계를 문제 삼았다. 이후 재구성 결과에 대한 이의를 Main이 설명 문제로 답했고 사용자는 “그게 아니라 이게 맞는거야?”라고 정정했다. 테스트 성공과 변경 이유 설명만으로 실제 구조의 적절성을 확인했다고 할 수 없다. 원복 원인을 단순히 파일 수나 추상화 수로 확정할 근거는 부족하다.
- [일정 생성의 잠정 검토](../../002-code-readability-refactoring/records/2026-10-01-01-schedule-create-provisional-review.md)와 [책임 경계 재확인](../../002-code-readability-refactoring/records/2026-10-02-01-schedule-create-boundaries-and-verification.md): 작성 상태의 수명과 화면 전환, 서비스 결과와 호환 처리를 구별해야 했다. 동작상 문제를 확인한 검토를 구조 검토까지 마친 것으로 보고한 차이가 있었고, 사용자는 “문제 해결에 대해서는 꽤 접근한건 맞아 근데 관심사 분리 아키텍쳐 코드 관점에서 뭔가 확신이 안들어서”라고 범위를 밝혀 주었다.

좋은 대조 사례도 있다. [복구 토스트 재검토](../../002-code-readability-refactoring/records/2026-09-30-02-recovery-toast-and-ux-review.md)에서는 기존 내용의 재표시와 제한 해제로 복구가 드러나는 현재 화면을 보고 계획했던 토스트·추적 상태를 추가하지 않기로 했다. 예정된 구현을 접는 것도 실제 이득에 근거한 개선 결과다.

현재 [리팩터링 기준](../../../../project/guidance/behavior-preserving-refactoring.md)은 이미 이해·수정 부담, 동작 보존과 개선 효과의 구별, 고른 수정 목록에 완료 기준을 맞추지 않는 판단을 담고 있다. development·reconsider-work도 목적·대안·검토 범위를 다룬다. 이번 근거는 일반 지침 문장을 더 늘리기보다 005에서 실제 문제와 기대 결과를 먼저 선택하고 그 결과를 검토하는 데 기존 기준을 사용해야 함을 지지한다. 과거 사건 당시에도 현재 스킬이 설치·사용됐다고 주장하지 않는다.

## Context에서 실제로 보완할 것과 유지할 것

**인증의 현재 계약과 소비 관계 복원이 우선 후보다.** Project의 주제별 입구와 기존 상세 Context 색인에서는 현재 인증 관계를 한 주제로 읽는 경로가 확인되지 않았다. [기존 결정](../../../../../.claude/decisions/2026-09-18-device-session-and-local-access.md)은 최초 선택과 후속 변경을 함께 보존하며 002 Spec·기록으로 연결한다. 현재 계약을 이해하려면 중간안·원복 기록·여러 코드 파일을 다시 조립해야 한다.

현재 [인증 상태와 접근 판단](../../../../../apps/client/src/shared/store/auth.ts), [로그인 완료](../../../../../apps/client/src/shared/services/auth/login-service.ts), [세션 변경 조율](../../../../../apps/client/src/shared/services/auth/session-lifecycle.ts), [요청 인증](../../../../../apps/client/src/shared/services/auth/auth-interceptor.ts), [로그아웃](../../../../../apps/client/src/shared/services/auth/logout-service.ts), [로컬 접근](../../../../../apps/client/src/shared/services/auth/local-access.ts)을 대조했다. 로컬 접근은 재인증 필요 상태에서도 가능하고 원격 접근과 구별되며, 로그인 전체 절차와 Store의 저장은 다른 책임이다. 토큰 갱신·세션 교체·미동기화 데이터 확인·명시적 데이터 정리의 관계도 함께 설명해야 한다. LoginScreen의 completeLogin 호출, entity와 Router의 접근 helper 사용처도 검색으로 확인했다.

추천 내용은 함수 목록이나 인증 파일 재분할이 아니라, 왜 로컬 작업과 원격 인증을 구별하는지, 소비자는 무엇을 확인하고 어느 전체 작업을 호출하는지, 실패 때 어떤 데이터와 상태를 유지하는지에 관한 하나의 주제다. 현재 구현·채택한 제품 의미·검증 한계를 구별해 Project 본문에 복원하고 기존 입구를 연결하는 안이다. 상세 Owner와 기록의 유효한 의미를 확인해 구성해야 하며 문서 작성 자체를 인증 코드 전체의 적절성 입증으로 취급하지 않는다. 새 제품 정책이나 상태를 정하는 제안은 아니다.

효용은 예를 들어 ‘재로그인 필요 상태에서 활성 여행을 수정할 수 있는가’, ‘로그인 화면은 저장 함수와 로그인 전체 절차 중 무엇을 호출하는가’, ‘다른 계정으로 바꿀 때 로컬 자료를 언제 정리하는가’를 현재 본문에서 설명하고 실제 코드와 대조할 수 있는지로 확인한다. 추가 문서의 유지 부담은 인증 계약이 바뀔 때 이 관계도 함께 맞추는 것이며, 과거 사건 전체나 테스트 수를 복제하지 않는다.

**입력 보존은 이미 기준이 있다.** [현재 정책 설명](../../../../../.claude/context/policy-architecture.md)의 ‘작성과 읽기의 제한을 구별한다’는 네트워크 변화 때 작성 중인 form과 입력을 유지하고 제한을 필요한 동작에 적용하는 뜻을 담는다. 새 규칙을 같은 뜻으로 추가하기보다 관련 작업이 이 본문을 선택하고 화면·상태 수명에 적용하는지 확인할 대상이다. 모든 일정 생성 구조의 정당성을 이 한 규칙으로 판정할 수는 없다. [여행 활성화 설명](../../../../../.claude/context/selective-activation-architecture.md)에도 여행 목록의 조회·보존·갱신 관계가 이미 통합돼 있어, 002의 후반 내용을 전부 미반영으로 분류하지 않는다.

**조회 공통화는 보완 여부를 별도로 선택해야 한다.** [당시 소유권 결정](../../002-code-readability-refactoring/records/2026-09-29-09-policy-query-ownership-and-migration.md)에서 사용자는 “우선 워크스페이스 쪽에 문서 잘남기는거 어때? project-context보다”라고 했다. 현재 useTripReadAccess·usePolicyReadQuery에서 표시 허용, 실제 요청 허용, Query 상태·실행·표시 조합을 확인했으나 이 구현만으로 좁은 feature 재사용 예외를 Project-wide 원칙으로 올릴 수 없다. 현재 소비 관계의 복원과 일반 개발 규칙 채택을 구별해 판단할 후보로 남긴다.

## 다음 선택과 확인 범위

추천은 인증의 흩어진 현재 의미를 복원하는 일을 다음 구체 후보로 삼고, 그 대조에서 실제 계약 불일치나 소비 부담이 남을 때 코드 개선 범위를 정하는 것이다. 005에서 코드 순회와 문서 증가 자체를 성과로 잡지 않는다. 범위·완료 판단의 문제는 현재 Work 수행에 적용하며, 이번 근거만으로 새 Personal 일반 기준이나 스킬 절차를 추가하지 않는다. 기존 저장 용량 결과는 유지하고 기존 Ticket 02·03은 자동 실행하지 않는다.

이번 재조사는 002 records 색인·현재 상태와 위 관련 기록 본문, 현재 Context 본문·지침, 연결된 인증·조회 코드를 확인한 결과다. 정확한 사용자 발췌는 해당 당시 기록에 보존된 것을 사용했으며, 002 전체 runtime 대화나 모든 코드·실기기 동작을 새로 검증하지 않았다. 이번 세션 원문 확인 범위는 [앞선 재판단](2026-10-30-06-improvement-loop-reconsideration.md)과 연결한다. 과거 실패의 빈도나 현재 인증 전체의 결함 유무는 이번 근거로 확정하지 않는다.

이번에는 조사 결과와 다음 판단을 Work 및 관련 Personal 경험에 반영했다. Project 본문·제품 코드·Spec·Ticket 재구성은 아직 수행하지 않았다. 상세 후보의 선택과 반영은 다음 논의에서 이어갈 수 있다.
