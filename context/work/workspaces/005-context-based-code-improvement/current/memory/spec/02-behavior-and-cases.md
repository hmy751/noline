# 요구 동작과 대표 사례

한 Ticket은 당시 설계 선택과 그 결과를 맡는다. 기록에서 원래 문제·제약·선택 이유와 정정을 확인하고, 현재 코드·소비자·검사에서 실제 결과를 대조한다. 관련 Context로 현행과 의미 있는 대안을 비교하고, 채택한 수정과 필요한 검증·기록까지 같은 Ticket에서 마친다. 조사·구현·검증을 기본적으로 별도 Ticket으로 늘리지 않는다.

- 저장 용량에서는 표시값 중복만 정리한 초기안과 집계·부분 실패·React 수명을 나눈 최종안을 구별한다. helper 수가 늘었다는 사실보다 실패 정책과 최신 결과 반영을 얼마나 직접 읽고 고칠 수 있는지 본다.
- 조회 조합에서는 여러 화면이 공유하는 접근·재시도 계약과 화면마다 달라야 하는 표시·조회 수명을 구별한다. 옵션을 추가하거나 우회해야만 필요한 차이를 표현하는지 실제 사용처와 대조한다.
- 인증에서는 초기 모델, 복잡도 재검토와 원복, 이후 책임 재배치의 순서를 확인한다. 철회된 안을 현재 결함이나 현재 채택 구조로 취급하지 않는다. Local 이용·세션 종료의 약속을 유지하면서 지금 구조의 부담을 비교한다.

현행 유지가 적절하면 판단 근거를 남겨 완료할 수 있다. 개선을 채택했다면 제안만으로 끝내지 않고 구현과 확인까지 책임진다. 독립적인 새 제품 요구나 별도 실행 규모 때문에 분리할 때에는 현재 완료에 미치는 영향과 다음 담당을 밝힌다.

활성 여행의 Local 저장·queue 원자성, 비활성 여행의 Remote 경계, 인증·소유권과 날짜·통화 의미는 제품 Owner를 따른다. 과거 오류 보고는 이후 수정·현재 상태와 대조하며, 현재 재현하지 않은 가능성은 결함 확정과 구별한다.
