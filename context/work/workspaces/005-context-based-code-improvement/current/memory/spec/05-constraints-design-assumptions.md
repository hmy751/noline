# 제약·현재 설계·가정

## 제약

02의 당시 선택·검증·원자료는 역사 근거로 보존한다. 제품 계약과 사용자 보류를 유지하고, Context의 예시를 Noline의 새 요구로 만들지 않는다. Personal·Project의 지속 기준 변경은 해당 Owner의 관리 계약으로 연결한다. 제품의 의미를 단지 이름만 좁혀 없애지 않는다.

02에는 01–05 결과와 06의 합의된 종료가 기록돼 있다. 07–18에는 반영된 조각과 미완료가 섞여 있다. 06 종료는 실제 단절·복구 전체와 Android 검증을 포함하지 않는다. 경비 삭제 실패 이유 유실과 특정 경비 상세 재시도 불일치는 기존 사용자 보류다.

## 현재 설계

저장 용량 Hook부터 시작한다. 작은 범위 안에 초기의 얕은 정리, 사용자 정정, 최종 책임 분리와 검사 한계가 연결돼 있어 당시 개선 깊이와 현재 결과를 비교하기 좋다. 이후 조회 공통화와 인증 책임을 검토한다. 각 Ticket 안에서 기록·코드 대조, 대안 판단, 채택한 개선과 검증까지 잇는다.

첫 판단 전에 [기존 저장 용량 Ticket](../../../../002-code-readability-refactoring/current/memory/tickets/03-storage-stats.md), [최종 구현 기록](../../../../002-code-readability-refactoring/records/2026-09-11-04-storage-stats-refactor.md), [초기 범위 재확인 기록](../../../../002-code-readability-refactoring/records/2026-09-12-01-ticket-03-initial-scope-reanalysis.md)을 읽는다. 이들은 보존 조건, 현재 선택의 이유, 사용자 정정의 근거다. 실제 코드·검사 및 적용할 Personal·Project 본문은 새 Ticket 01에서 찾는다.

인증은 범위가 크므로 선택·실제 변경의 경계를 확인한 뒤 독립적인 결과로 나눌 수 있다. 파일 수만으로 분할하거나 분석·구현·검증을 별도 관리 단계로 만들지 않는다. 다음 주제와 실행 배치는 현재 결과·사용자 지시·development 기준으로 정한다.
