# 품질과 완료 판단

Context 본문에서 해당 주제의 목적·책임 관계·계약·이유·중요 조건·현재 지원 범위를 이해할 수 있어야 한다. 링크 모음이나 함수 목록, 작업 기록 요약만으로 완료하지 않는다. 기록에서 얻은 관계를 현재 코드와 대조하며 한 문장이 여러 구현 경계를 설명하면 그 경계를 각각 확인하거나 문장 범위를 좁힌다.

각 Ticket은 기존 본문에 있던 유효한 의미의 보존과 확인된 공백의 보완을 함께 확인한다. Project README와 해당 작업의 실제 진입점에서 대표 질문으로 읽어 같은 Owner와 답에 도달하는지 확인하고, 링크·형식 검사를 수행한다. 작성자의 기억으로 본문의 빈칸을 메우지 않는다. 본문 저장·읽기 확인·실제 후속 개발 효과는 구별한다.

제품 동작을 바꾸지 않는 문서 작업에는 일괄 제품 테스트를 추가하지 않는다. 실제 지원 주장을 확정하려면 필요한 코드·기존 테스트 본문을 대조하며, 실행이 필요한 주장에는 해당 검사를 선택한다. 기존 pass와 이번 재실행을 구별하고 native·서버·DB 대역의 한계를 보존한다.

Work 완료에는 review-scope의 각 실제 결과가 보완·충분하여 유지·명시적 보류 중 어디에 놓였는지 근거가 있어야 한다. 세 Ticket의 필요한 본문과 읽기 경로가 남으면 완료하지 않는다. 개인 판단 개선은 후순위로 분리했으므로 이번 단계 완료 조건에 포함하지 않는다.

현재 verify.json은 recover.json의 JSON 구문만 확인하는 초기 계약이다. 문서 의미나 제품 검증을 입증하지 않으므로 이번 재구성에서 durable Verify를 실행하지 않는다. 문서 대조와 명시적 Recover의 결과를 구별해 보고한다.
