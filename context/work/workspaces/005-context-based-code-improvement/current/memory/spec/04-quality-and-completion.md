# 품질과 완료 판단

각 Ticket의 결과는 당시 목적·현재 계약·실제 소비자를 연결해 선택을 설명할 수 있어야 한다. 이름·흐름·책임·오류·수명의 필요한 범위를 살피고, 첫 발견 한 건만으로 전체를 검토했다고 하지 않는다.

수정 시 기존 정상 동작과 의도한 변화의 검증을 나눈다. 값·오류·부분 실패·반환 시점·부작용 순서 중 결과를 가르는 조건을 확인한다. 가독성 개선은 테스트 통과와 별도로 실제 읽기·수정 위치·간접 연결의 부담이 어떻게 달라졌는지 비교한다. 의미 있는 동작·계약·통합 변경은 development 기준의 별도 검증으로 확인한다.

Work 전체 완료에는 review-scope의 결과 범주별로 검토 결과 또는 근거 있는 제외·보류와 후속 책임이 있어야 한다. 채택한 개선의 구현·필요한 검증이 남거나, 결과를 막는 문제가 미배정이면 완료하지 않는다. 초기 세 Ticket이나 첫 검토의 종료를 전체 완료로 확대하지 않는다. 사용자가 범위를 조정하면 이유와 미검토 영향을 보존한다.

각 Ticket은 당시 선택과 실제 결과의 대조, 적용한 기준과 대안, 유지·수정·보류의 이유를 연결한다. 채택한 수정의 구현·필요한 검증이 남으면 해당 Ticket을 완료로 닫지 않는다. 보류가 맡은 결과를 막는지 판단하고 독립적인 후속에만 넘긴다.

현재 초기 verify.json의 claim은 recover.json을 Python 표준 JSON 파서로 읽을 수 있다는 한정 사실이다. 이는 제품 코드·Workspace schema·내용 충분성·개선 효과를 증명하지 않는다. 제품 검증을 남길 때는 해당 Ticket의 실제 기준과 명령이 읽는 입력을 확인해 계약을 교체한다. 이번 문서 재구성에서는 durable Verify를 실행하지 않는다.
