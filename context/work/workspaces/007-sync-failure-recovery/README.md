# 007 — 동기화 실패가 큐를 영구히 막지 않게 하기

동기화에 실패한 변경이 영구 정지로 남지 않게 하는 Workspace다. 실패한 변경은 **서버에 도착하거나, 합의한 규칙으로 정리되거나, 사람이 결정하는** 세 결말 중 하나로 끝나야 한다. 끝나기 전까지는 변경을 보존하고, 순서를 지키고, 누군가 그 상태를 알 수 있어야 한다.

2026-11-02 1.1.0 출시 확인 중 iOS 시뮬레이터의 개발 앱에서 경비 CREATE 하나가 동기화 큐를 영구히 막고 있는 것을 발견했다. 그 원인 추적과 이후 논의(고칠 위치, 기존 정책과의 관계, 폐기 기준, 주제별 선택지 비교)를 이 Workspace의 Spec과 Ticket으로 구성했다.

## 이 작업을 이어받을 때

[재개 안내](recover.md)에서 현재 요청에 필요한 자료와 읽을 이유를 고른다.

## 003과의 관계

[003 발견한 버그 확인·수정](../003-bug-investigation-and-fixes/README.md)의 Ticket 11(동기화 실패·재시도·중단 복구)이 같은 영역을 "실행 전"으로 맡고 있었다. 그 Ticket은 "중복 생성 방지는 기존 client ID·서버 수용 계약으로 검증한다"를 전제로 두었는데, 이번 사고로 서버가 재전송을 견디지 못한다는 사실이 드러나 전제가 바뀌었다. 007은 이 영역을 새 goal로 분리한 후속 Workspace다. 필요한 의미는 007의 current에 직접 적었으므로 003의 current를 읽어야 이해되는 관계가 아니다.

003의 Ticket 12(pull 충돌)와 13(서버 소유권)은 각자의 범위를 유지하고, 007은 필요한 결과만 연결한다. 생성 중에 003 문서는 수정하지 않았다. 003에 "007로 옮김"을 표시할지는 사용자 결정으로 남겼다.

## 다음 작업에도 보존할 판단

- 실패 횟수나 경과 시간으로 변경을 버리지 않는다. 자동으로 버릴 수 있는 것은 서버가 이 변경보다 나중 상태를 갖고 있고 pull로 기기도 같은 결과가 되는 경우뿐이며, 그 규칙도 충돌 정책을 정한 뒤에만 쓴다.
- 큐는 하나의 FIFO로 두고 실패하면 그 자리에서 멈춘다. 막힌 작업을 건너뛰거나 '완료'로 바꾸지 않는다.
- "이미 반영됐는가"는 서버가, "언제 다시 보내는가"는 앱의 큐가, "다시 보내도 안 되는 변경을 어떻게 끝내는가"는 충돌 규칙과 사람이 판단한다.
- 설명이나 판단을 요청받았을 때 구현으로 넓히지 않는다. 구현·커밋·배포·심사 제출은 사용자가 요청하거나 직접 한다.

상세 계약을 이 README에 복제하지 않는다. 진행은 state, 실행 범위는 Ticket, 기준은 Spec, 선택 과정은 records가 소유한다.
