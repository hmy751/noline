# 저장 중 닫기 안내와 같은 폼의 추가 입력 경계

앞선 [RHF 제출 상태 정리](2026-11-12-05-rhf-submitting-and-user-events.md)는 완료 범위를 유지한다. 이번 후속은 **저장 중 닫기 시도의 안내 반영·검증 완료**이며, 새로 확인한 **같은 폼에서 저장 중 추가한 입력의 손실은 미해결 검토 사항**이다. 두 범위를 섞어 1단계 전체 문제가 해결됐다고 선언하지 않는다.

사용자는 취소 버튼이 disabled인 상태와 안내 없이 닫기를 무시하는 UX를 질문했다. Main은 닫기 허용을 검토하면서 실패한 초안 보존까지 함께 제안했으나, 사용자가 “또 초안 보존까지 추가해야 하는 거야? 실제 사용자 흐름 기준으로 어디까지 필요한지 먼저 검토해봐”라고 요청했다. read-only 검토와 high 범위 재검토는 **별도 초안 저장소가 원래 합의에 없었다**는 점을 확인했다. 활성 여행의 저장값은 SQLite·큐에 이미 남고, 열린 폼에서 실패한 입력 유지와 닫은 폼의 자동 복원은 다른 선택이다. 003-12의 미전송 보호·007-07의 구버전 원문 보존을 모든 닫힌 폼의 초안 복구 약속으로 확대하지 않는다.

검토 중 더 직접적인 결함을 재현했다. 같은 경비 폼에서 30을 제출한 뒤 저장 Promise가 대기하는 동안 35를 입력하면, 앞선 성공 처리가 `reset(30)`과 닫기를 실행해 35가 사라졌다. `isCurrentEdit`는 폼 교체·해제를 구별하므로 **살아 있는 같은 폼의 후속 입력**은 보호하지 않는다. 앞선 전체 853개 통과도 이 장면의 보장이 아니었다. 최소 격리 검사 1개 통과는 이 결함을 재현했다는 뜻이며 제품 요구 충족 판정이 아니다. 실제 제품 폼·순차 userEvent를 사용했지만 네이티브 금액 prompt의 확인 콜백은 주입했다.

사용자는 “초안 보존은 추가하지 말고 닫기 시도에는 저장 중이라고 안내”하라고 요청하면서, 입력을 무조건 막지 말고 실제 사용자 시나리오로 판단하라고 했다. 이어 “보통 저장하고 닫히지 않나?”라고 확인했다. Main은 성공 후 닫기는 기존 동작이며, 남은 틈은 **제출부터 성공까지 폼이 열려 있는 짧은 구간**이라고 구별했다. 입력 잠금·추가 입력의 성공 처리 변경은 아직 선택·구현하지 않고 합의한 닫기 안내만 반영했다.

두 수정 Drawer는 저장 중 `handleClose`에서 “저장 중입니다 / 저장이 끝난 뒤 닫을 수 있어요.”를 안내하고 폼을 유지한다. 저장 요청을 취소하거나 창을 닫겠다는 확인은 아니다. 취소 버튼은 누를 수 있게 하여 같은 안내로 연결한다. 공유 `ExpenseSubmitActions`의 선택 인자 `isCancelDisabled`는 기본값을 기존 `isPending`으로 유지하고 수정 화면에서만 false로 넘겨, 생성 화면의 기존 비활성화 조건은 바꾸지 않았다.

Main의 관련 두 테스트 파일 39/39와 제품 lint 오류 0·기존 색 경고 16개는 로그에서 확인했다. 별도 검증자는 코드·검사 적절성을 확인하고 새 결함이 없다고 반환했다. 관련 39개는 Main의 유효한 실행 근거를 재사용했고, 공유 경비 생성 화면 회귀 9개를 독립 실행해 통과했다. 추가 생성 화면 pending 취소 비활성화 probe 1개도 통과해 수정 화면만 취소 버튼 안내를 허용한다는 경계를 확인했다. 전체 client 853개를 이번에 다시 실행한 결과는 아니다. 기록 담당자는 두 Drawer와 공유 action의 실제 분기·기본값을 대조했다. 별도 draft store·입력 잠금·같은 폼 후속 입력 보존은 이번에 구현하지 않았다. Project의 현재 입력 계약과 미해결 범위는 Main이 갱신했고 기록 담당자는 수정하지 않았다.

닫기 안내는 이번 범위의 수정·검증 완료다. 다음에는 저장 중 같은 폼의 추가 입력을 실제 UX에 맞게 어떻게 다룰지 검토를 이어간다. 검토자의 “보통 성공은 닫되 추가 입력이 실제로 있으면 현재 폼을 유지해 명시적으로 다시 저장” 안은 후보일 뿐 사용자 채택·구현은 아직 없다. 기존 네이티브 수정창 열기·닫기·재열기도 미확인이다. 사용자 수락·커밋·배포는 미실행이다.

원문은 같은 Main 대화 `01a1c4a4-3065-7b32-8404-2c5066fcbaf9`의 `/Users/hammyeong-yeon/.codex/sessions/2026/11/10/rollout-2026-11-10T17-47-37-01a1c4a4-3065-7b32-8404-2c5066fcbaf9.jsonl`에서 직전 이후 **7100〜7368행**을 읽었다. 7184행은 초안 보존 전제의 재검토, 7291행은 초안 추가 금지·닫기 안내 승인과 입력 제한 검토, 7314행은 성공 후 닫기 UX 확인이다. 판정과 사용자 선택의 범위를 유지했다.

직접 확인한 재현은 `/tmp/noline-save-close-review/same-form.test.tsx` 마지막 probe와 `result.log`, 구현 관련 검사 근거는 `/tmp/noline-save-close-notice-tests.log`·`/tmp/noline-save-close-notice-lint.log`다. 기록 담당자가 제품 검사를 재실행한 것은 아니다. 후속 독립 결과는 Main이 연결한 `/tmp/noline-close-notice-verify-create.log`·`/tmp/noline-close-notice-verify-cancel.log`와 probe 소스 `/tmp/noline-close-notice-verify-cancel-probe.tsx`를 직접 대조했다. 최종 `/tmp/noline-save-close-notice-types.log`는 이전 corrected 타입 로그와 완전히 같아 기존 오류 7개만 남는다. 이 최종 반환은 위 고정 원문 구간 이후 추가로 연결받은 결과다.
