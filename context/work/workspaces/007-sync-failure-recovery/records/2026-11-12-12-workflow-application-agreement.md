# 1단계 대화 재판단과 앞으로의 작업에 적용할 실행 합의

사용자는 1단계 대화를 Main이 직접 다시 판단한 뒤, 최근의 공식 문서 문제만이 아니라 앞선 정정 전체를 앞으로의 개발 작업에 연결하도록 요청했다. 마지막 종합의 **실제 작업 적용과 필요한 기록·커밋을 승인했고, 스킬 직접 수정은 하지 말라고 했다.** 이번 결과는 실행 방식에 대한 합의다. 제품 코드 변경·제품 테스트·독립 코드 검토·검증을 수행한 결과나 개선 효과를 확인한 결과는 아니다.

## 이번에 무엇을 다시 판단했는가

처음에는 Ticket 09의 2단계 수신 코드를 읽기 시작했다. “니가 직접 검토”를 Main의 직접 코드 리뷰로 해석해 읽기를 이어갔으나, 사용자는 **2단계 전에 1단계 관련 대화 원문을 직접 보고 판단하라는 뜻**이라고 바로잡았다. 그 뒤 2단계 검토를 보류하고 선행 대화의 판단·정정 과정을 다시 읽었다. 따라서 이번 후속 검토를 전혀 미착수라고 하거나 2단계 검토가 끝났다고 하지 않는다.

선행 [판단 과정 기록](2026-11-12-11-stage-one-judgment-and-next-tickets.md)은 당시의 열린 종합으로 보존한다. 이번 Main은 그 요약을 결론으로 물려받지 않고 이전 대화의 해당 발화와 대조했다. 재판단에서 중요했던 차이는 다음과 같다.

- 초기 검토가 모두 무효였던 것은 아니다. 늦은 저장 결과의 다른 편집 침범, 서버 저장 뒤 기기 준비 실패의 오분류 같은 유효한 문제를 찾았다. 다만 흐름 오류를 찾은 사실이 기술 선택·책임·이름·타입·표현의 품질까지 검토했다는 뜻은 아니었다. 사용자는 앞서 Context에 있는 코드 스타일과 세부 기준을 적용하지 않은 점을 이미 지적했다.
- 범위를 작게 나눈 이유는 판단을 깊게 하고 사용자가 이해할 수 있게 하기 위해서였다. 사용자가 `openingValueRef` 의문을 검토자에게 정답처럼 주지 말라고 했던 요청도 함께 본다. 특정 제거 결론을 미리 정하거나 필요한 소비자 연결을 잘라 내는 분할은 이 취지와 다르다.
- 초기화 질문의 첫 답에도 폼을 새로 마운트하는 대안은 언급돼 있었다. “대안을 전혀 생각하지 않았다”로 평면화하면 부정확하다. 문제는 현재 구조의 필요성을 설명한 뒤, 실제 부모·편집 수명·공식 동작을 충분히 비교하기 전에 그 구조를 유지하도록 권한 데 있었다.
- 공통 잠금·성공 후 reset에서는 현재 구현과 테스트 조건을 요구의 근거로 삼았다. 같은 `act` 안의 두 `fireEvent`, 강제 B 전환, 아무 일도 하지 않는 `onClose`는 실제 순차 사용자 입력·현재 소비자의 닫힘과 같지 않았다. 선행 답변에는 “테스트가 구조를 고정하면 안 된다”는 취지도 있었지만 같은 답변에서 렌더 전 잠금을 유지했다. 원칙을 알고 말한 것과 같은 선택에 적용한 것은 달랐다.
- 공식 문서와 기존 유틸, 실제 호출자, Personal·Project 기준을 뒤늦게 대조하면서 불필요한 상태·reset·중복 준비를 줄였다. 사용자 질문마다 해당 줄만 고치고 그 전제에 의존한 검사·설명까지 잇지 못하면 사용자가 다시 찾아야 했다. 마지막 결과만 요약하면 처음부터 충족한 품질과 사용자 정정 뒤에 확보한 품질이 섞였다.

이미 수락한 Local 변경·queue 보호와 새 미제출 입력의 draft 보존은 다른 요구다. 선행 과정에서 draft 복구·입력 전면 잠금까지 확대하려던 제안을 재검토했고, 사용자는 제출값 저장 성공 후 닫기를 선택했다. 늦은 응답 보호를 이유로 추가 보존·잠금 요구를 임의로 만들지 않는다는 경계를 다음 작업에도 적용한다.

이 분석은 기술스택 지식 부족 하나로 원인을 축소하거나, 모든 보호 코드를 없애자는 결론이 아니다. 사라진 편집의 늦은 응답 보호, HTTP 검증과 Local 변환·트랜잭션처럼 서로 다른 이유의 책임은 보존한 채 각 선택의 필요와 표현을 판단해야 한다.

## 채택한 적용 방식

2단계에만 쓸 별도 점검표를 만드는 대신, 앞으로의 작업에서 기존 Main·구현·독립 검토·검증의 책임과 판단 시점에 적용한다. 실제 과업의 위험과 적용 계약에 따라 필요한 배정을 유지하며, 새 상설 리뷰 담당이나 모든 API의 전수조사를 추가하지 않는다.

### 작업을 나누고 설계를 고를 때

Main은 목표·지켜야 할 동작·실제 대상·열린 질문을 먼저 분명히 한다. 파일 수나 단계 수가 아니라 **한 선택의 이유와 결과를 판단할 수 있는 크기**로 나누고, 그 선택에 필요한 호출자·소비자는 함께 확인한다. 현재 구현이 처리하는 상황과 사용자가 요구한 상황을 구별하며, 검토자에게 특정 수정 결론을 미리 정답으로 넘기지 않는다.

구현 담당자는 아래 입력을 따로 읽었다고 보고하는 데서 멈추지 않고 같은 코드 선택에 연결한다.

| 입력 | 그 선택에서 확인할 의미 |
| --- | --- |
| 사용자 요구·Project·Ticket | 제공해야 할 결과, 보존할 계약과 제한 |
| 공식 문서·설치 버전 | 기술이 이미 보장하는 동작과 제공하는 기능, 그 보장이 성립하는 조건 |
| 실제 소비자·호출 관계·기존 유틸 | 지원해야 할 실제 사용 범위와 이미 해결한 책임 |
| Personal | 이해·수정하기 쉬운 책임, 이름·타입·표현의 선택 |
| 실행·테스트 | 위 판단이 실제 조건에서 성립하는지와 확인의 한계 |

특히 기술 동작에 의존하는 중요한 구조를 고르기 **전에** 공식 문서와 설치 버전을 설계 입력으로 쓴다. 이미 만든 구조를 정당화하는 사후 인용으로 붙이지 않는다. 문서만으로 모호한 부분은 타입·구현 또는 실제 사용 조건의 작은 재현으로 좁혀 확인한다. 모든 API를 조사하거나 문서가 제품 요구를 대신 정하게 하지는 않는다.

첫 구현부터 동작과 세부 품질을 함께 맡는다. 수명·호출·실패·완료가 실제로 어떻게 이어지는지 보고 불필요한 상태·wrapper·조회·변환을 줄이며, 이름·타입·조건·인자·콜백·함수 배치까지 해당 책임에 맞춘다. 버그가 있어야만 개선할 수 있는 것은 아니며, 이를 리뷰 단계나 사용자 질문까지 미루지 않는다.

### 독립 검토와 검증을 받을 때

독립 검토자는 구현자의 결론을 확인하는 데 그치지 않고 선택과 전제를 다시 판단한다. Main은 관찰한 문제와 제안한 해결책을 구별해 근거·영향·비용을 확인하고 채택·조정·미채택을 결정한다. **Main이 직접 판단한다는 요청은 독립 검토를 없애라는 뜻이 아니다.** 독립 결과를 받았다는 사실만으로 Main의 채택 책임이 끝나지도 않는다.

검증의 기대값은 요구·실제 소비자·공식 동작에서 도출한다. 실제 사용자 경로와 강제로 주입한 경계, mock·adapter의 한계, 현재 구현 가정을 굳힌 테스트를 구별한다. 테스트가 실패하면 현재 코드에 기대값을 맞추는 것이 아니라 어느 전제가 유효한지부터 판단한다. 최종 전달·커밋할 판본과 검증한 판본도 맞춘다. 전체 dirty 판의 통과를 분리 커밋 판의 통과로 대신하지 않는다.

### 설명과 정정 뒤에 이어갈 때

설명도 같은 작업 단위에 포함한다. 실제 사용자 동작에서 시작해 코드와 기술의 관계, 선택 이유, 검사와 남은 한계를 연결하면 사용자가 전제를 확인할 수 있다. 이미 선택한 구현을 납득시키는 것만을 설명의 목표로 삼지 않는다.

사용자 정정이나 새 근거가 전제를 바꾸면 그 전제에 의존한 코드·타입·검사·설명까지 영향 범위를 추적한다. 언급된 한 줄만 바꾸거나 매번 전체 검토를 다시 하는 양극단 대신, 실제 영향을 받는 범위를 다시 확인한다. 변경 이유와 남긴 보장·미확인은 기록해 다음 세션이 최종 코드만 보고 필요성을 추측하지 않게 한다.

## 기록 확인과 커밋 미완료

Main은 007 문서 7개의 전체 diff와 새 기록의 의미를 확인했고, `git diff --check -- context/work/workspaces/007-sync-failure-recovery`는 exit 0이었다. `pnpm` 실행 파일이 없어 `package.json`의 `harness:check`에 해당하는 `node scripts/check-harness.mjs`를 직접 실행했다. 문서 수정 전후 모두 기존 링크 오류 64개로 exit 1이었으며 출력도 완전히 같았다. 작업 전부터 있던 dirty 102파일의 SHA256도 전후 동일했다. 이는 Main이 실행해 반환한 문서 확인 결과이며 제품 검증 결과가 아니다.

새 기록을 포함한 007 문서 7개만 `git add`하려 했으나 `.git/index.lock: Operation not permitted`로 exit 128이 발생했다. 환경에서 `.git`은 읽기만 허용되어 **stage와 커밋을 완료하지 못했다.** 권한 상승 승인도 자동 거절하도록 설정돼 있어 우회·재시도하지 않았고, 사용자에게 커밋 미완료와 권한 제한을 알렸다. 문서 수정은 남아 있으며 Git 쓰기가 가능한 환경에서 이 7개만 선별 커밋해야 한다. 새 커밋 hash는 없다.
