# 저장 1단계의 한정 검토와 코드 정리

007 Ticket 07·003 Ticket 12의 선행 구현과 [후속 보완](2026-11-10-05-conflict-pull-review-fixes.md)을 단계별로 설명하던 중, 사용자가 저장 순간의 구현을 따로 검토하도록 요청했다. 이번 범위는 **폼에서 실제 변경을 추리고 편집 표식을 준비한 뒤 Local 또는 Remote에 저장하고 완료를 화면에 전달하는 1단계**다. 서버 병합·pull 전체를 다시 검증하는 작업으로 넓히지 않는다. 이전 두 Ticket의 완료 근거는 당시 확인으로 유지하고, 이번 수정의 검증과 구별한다. SQL → 서버 → 앱 배포는 계속 미실행이다.

## 검토 범위를 정한 과정

사용자는 작업량이 커 보이므로 “좀 더 자세히 볼 필요가 잇어보여 단계마다”라고 요청했다. Main은 저장·수신·조회 범위·서버 판정·응답 반영·호환/삭제·검증의 설명 순서를 나누고 먼저 저장 1단계를 설명했다. 이 순서는 설명을 위한 구분이며 실제 push와 pull의 고정 실행 순서가 아니다.

처음에는 경비의 `openingValuesRef` 필요성을 물었지만 곧 “아 방금 openingValueRef 는 전달하지말고 그냥 지금 단계 작업에 대해 검토 맡겨봐 우선”이라고 정정했다. 따라서 특정 변수에 대한 사용자 의문을 독립 검토의 결론 유도로 전달하지 않았다. 처음에는 수정 없이 검토했고, 이어 사용자는 “코드 관점이나 기술스택 적절한 관점”과 “우리 시스템 유틸 이나 뭔가 코드를 잘 활용했나”도 따로 점검하도록 요청했다. 기능 흐름의 오류만 보는 데 그치지 않고 상태·타입·책임과 기존 구현 재사용을 비교한 이유다.

사용자의 실제 수정 승인은 “지금 1단계에서 검토한 내용들 종합해서 필요한 수정이랑 코드 정리 진행해줘. 기존 합의는 유지하고 수정한 부분 검증도 해줘 그리고 1단계 작업자체에 대해서 다시 설명해줘”였다. 이 승인 이전의 검토·제안과 이후 실제 수정을 구별한다.

## 발견한 문제와 선택한 수정

### 편집 입력·제출의 수명을 폼과 연결한다

일정 A를 저장한 뒤 완료 전에 닫고 B를 열면, A의 늦은 성공 처리가 B의 초안을 `reset`하고 창을 닫는 조건을 격리 React 렌더와 실제 저장 훅에서 확인했다. 같은 순간의 연속 제출도 두 번 접수될 수 있었다. 일정 제출을 `mutateAsync`의 Promise를 기다리는 흐름으로 바꾸고, 렌더 전 연속 탭·닫기는 ref로 차단하며 표시 상태는 React Hook Form의 `isSubmitting`으로 관리한다. 외부 전환까지 차단할 수는 없으므로 편집 회차를 구별해 옛 성공·실패가 새 초안·안내·닫기에 영향을 주지 않게 한다.

첫 수정의 독립 검증은 경비에서도 같은 수명 문제가 남았음을 밝혔다. 경비 A 저장 중 외부에서 B를 연 뒤 A를 성공·일반 실패·서버 처리 후 기기 준비 실패로 끝내는 세 조건 모두 새 초안에 영향을 주었다. 성공은 B 창을 닫았고 실패 둘은 B에 A의 오류를 표시했다. 이 추가 발견을 일정과 같은 회차 보호로 보완했다. 이는 최초 검사가 통과했어도 화면마다 조건을 대조해야 했던 실제 후속 수정이다.

경비의 비교 기준은 별도 `openingValuesRef` 대신 React Hook Form이 `reset`으로 관리하는 `formState.defaultValues`를 사용한다. 설치본의 실험에서 초기값 재설정이 반영되는 것을 확인했다. 일정은 장소 원본과 편집 시간대 등 폼 입력 외의 기준도 필요하므로 모든 ref를 일괄 제거하지 않는다.

다만 변경 계산을 폼의 `dirtyFields`로 대체하지 않았다. 실험에서 금액 문자열 `'25.00'` → `'25'`는 폼상 변경이지만 같은 금액이므로 UPDATE를 만들 필요가 없었다. 금액이 달라지면 금액·통화를 함께, 장소가 달라지면 장소명·주소·좌표를 함께 보내야 한다. 입력과 초기값은 폼, 값의 동등성과 편집 그룹은 순수 계산, 실제 요청 유효성은 공유 Zod schema가 맡도록 했다. 거대한 공통 편집 훅으로 두 화면의 서로 다른 변환·후처리를 합치지는 않았다.

### 순수 계산·조회 갱신·Local 결과 읽기를 기존 책임에 맞춘다

`changedFields`·`editedMarks`는 기기 저장소가 필요 없는 계산이므로 `shared/lib/edit-fields.ts`로 분리했다. 화면이 비교 함수를 쓰기 위해 SecureStore 모듈에 의존할 필요를 없앴고, 경비·일정 입력과 반환 타입을 공유 schema의 추론 타입에 연결했다. 모든 편집 그룹 조합을 복잡한 타입으로 재구현하지 않으며 런타임 검증은 유지한다.

일정·경비 저장 훅은 직접 `invalidateQueries`를 호출하던 대신 기존 `cancelAndInvalidateQueries`를 재사용한다. 실제 QueryClient 격리 비교에서 캐시가 없는 첫 조회가 진행 중일 때 직접 무효화는 그 조회를 계속 사용해 저장 전 값이 남았다. 공통 유틸은 옛 조회를 취소하고 새 조회를 시작해 저장 후 값을 받았으며, 옛 응답을 나중에 풀어도 새 값을 유지했다. 성공뿐 아니라 삭제·보류로 Local 상태가 바뀌는 실패도 있으므로 `onSettled`에서 갱신한다. 새 조회의 완료 자체를 저장 성공의 필수 대기로 만들지는 않는다.

Local UPDATE 후 결과를 다시 SELECT하던 부분은 설치된 Drizzle/SQLite에서 지원을 확인한 `.returning().get()`으로 정리했다. 앞선 항목 표식을 읽는 최초 조회는 유지한다. 변경 행이 없거나 반환값 변환이 실패하면 예외를 내고, 행 변경·큐 추가·결과 변환은 기존 `withTransaction` 안에서 함께 성공하거나 되돌아간다. Expo용 Drizzle의 transaction callback이 비동기 Promise를 기다리는 방식과 달라 기존 비동기 트랜잭션 실행기를 단순 교체하지 않았다.

기존 `ownedActiveRow`, `withTransaction`, `addToSyncQueue`, `generateId`, 시간대 변환과 폼 공통 부품은 계속 재사용한다. 여행별 실행 순서는 Repository 직접 호출·활성화도 함께 조율하므로 React Query의 mutation 순서만으로 대체하지 않는다. 표식은 관찰한 시각까지 고려하므로 단순 현재 시각 유틸로, 금액 비교는 표시용 포맷 함수로 바꾸지 않았다. 일정 경로 downloader는 같은 조합의 기존 경로를 재사용할 수 있어 장소 변경 후 재계산과 의미가 다르므로 이번 범위에서 합치지 않았다.

### 서버 처리와 기기 준비 실패를 구별한다

비활성 여행의 직접 PUT에서 유효한 성공 응답까지 받은 뒤 응답의 편집 표식을 SecureStore에 보관하지 못하면, 앞선 구현은 전체를 일반 저장 실패처럼 전달했다. 격리 API 검사는 정상 HTTP 응답 뒤 기기 보관만 실패시켜 일정·경비 양쪽을 재현했다. 실제 서버와 기기의 동시 장애를 재현한 결과는 아니다.

이제 성공 응답 검증 뒤의 표식 보관 실패만 `ConfirmedUpdateError`로 구별해 “서버가 수정 요청을 처리했지만 이 기기의 동기화 준비를 마치지 못했어요. 현재 값을 다시 확인해주세요.”라고 안내한다. **서버가 요청을 처리했다는 확인은 제출값이 최종 채택됐다는 보장이 아니다.** 항목 표식에 따라 서버가 기존 값을 유지할 수 있으므로 무조건 저장 성공 안내로 바꾸지 않는다. HTTP 거절·잘못된 응답도 이 오류로 취급하지 않는다.

표식 보관 실패를 무시하고 다음 입력을 내보내지 않는다. 이미 관찰한 표식의 최댓값을 현재 프로세스 메모리에 유지하고, 다음 발급은 그 관찰값을 반영한 표식을 영속화한 뒤에만 반환한다. 여러 실패 관찰 중 가장 큰 시각·순번이 남는지도 별도 검사한다. **아직 영속화하지 못한 메모리 값이 앱 종료·재시작을 넘어 남는다고 보장하지 않는다.** 이미 표식이 있는 요청은 재사용하고, 재전송마다 새 표식을 만드는 정책으로 바꾸지 않았다.

구버전 보류 입력의 복구 화면처럼 저장을 직접 호출하는 곳도 이 상태를 구별한다. 서버 처리 후 기기 준비가 실패하면 옛 보류 입력을 정리하지 않고 조회를 갱신해 현재 값을 다시 확인하게 한다. 명시적 현재 값 유지 또는 안전하게 끝난 새 저장 뒤에만 정리하는 기존 조건을 유지한다.
