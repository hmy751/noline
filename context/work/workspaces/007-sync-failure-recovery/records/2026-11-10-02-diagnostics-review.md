# Ticket 06 진단 기준 재점검

사용자가 “중괄호만 보지 말고 development 기준에서 빠진 게 더 있는지 전체적으로 점검하고 보완해줘”라고 요청했다. 이전 시험에서는 실제 Sentry 수신과 시험 예외의 소스 위치 복원을 확인했다. 그 시험만으로 오류 원인 분류, 릴리스 비교, 개인정보 처리, 관련 Project 기준이 모두 충족됐다고 볼 수 없어 코드·검사·문서를 함께 대조했다.

| 발견한 문제 | 보완하는 이유와 확인 기준 |
| --- | --- |
| 앱에서 여행 변경을 보내려고 호출했지만, 먼저 수행한 인증 토큰 갱신이 500·연결 실패로 끝날 수 있다. | 이때 여행 변경 요청은 서버에 도착하지 않았다. 여행 자체의 거절이나 응답 유실로 표시하면 운영자가 원인을 잘못 조사한다. 실제로 어느 요청이 전송됐는지와 진단 단계를 함께 확인한다. |
| 서버 거절 로그의 정보 제한 필터가 SDK의 환경·릴리스 필드까지 지운다. | SDK가 필터 전에 넣은 `sentry.environment`와 `sentry.release`를 보존해야 운영 환경과 빌드별 거절을 구별할 수 있다. 새로 허용한 값이 살아 있고 나머지 요청 정보는 빠지는지 실제 수신 내용으로 확인한다. |

개선 검토에서는 Sentry를 유지하는 판단을 지지했다. 기기에서만 일어난 일까지 이미 실제 앱에서 관측했고, 별도 진단 API·DB를 운영할 필요가 추가로 확인되지 않았다. 개발 기준을 코드 표현에 적용하고, [오류·진단 기준](../../../../project/guidance/error-handling.md)과 [데이터 수명](../../../../project/guidance/data-lifecycle/INDEX.md)에 이어지는 동작·확인 범위도 대조한다. 이 검토는 운영 환경 배포나 지역 정보 제거 성공을 입증하지 않는다.

## 수정 내용과 현재까지의 재검증

- **앱 인증과 재시도.** 갱신 오류를 원래 오류로 유지하되 여행 요청의 5xx 재전송 대상으로 잡지 않고 `auth-refresh-failed`로 기록한다. 실제 HTTP 어댑터에서 선제 갱신이 실패한 경우 여행 요청 0회·갱신 1회, 여행 요청이 401을 받고 갱신이 실패한 경우 여행 요청 1회·갱신 1회였다. 두 경우 모두 갱신 실패로 판별했다. 서버 응답 뒤 기기 후처리에서 생긴 실패도 해당 단계에서 기록하도록 보완했다.
- **앱 진단 내용과 소스 위치.** 전송 직전 단계에서 태그·fingerprint의 값과 코드 프레임의 파일명 범위를 제한했다. 임의의 파일 경로나 함수명은 버리고 허용된 번들의 위치 좌표를 보존한다. 양 플랫폼의 실제 Hermes 번들과 소스맵을 내보내 debugId와 소스 위치 역매핑을 확인했다. 기존 iOS 프로젝트 복사본에 Expo 설정을 적용해 업로드 빌드 단계가 생성되는 것도 확인했다. 이 결과는 수정판을 운영 환경에 배포하거나 소스맵을 새로 업로드한 근거가 아니다.
- **서버 진단과 시작 실패.** SDK가 필터 뒤에 덧붙인 로그 속성도 최종 전송 내용에서 제한하고 설정된 환경·릴리스는 남겼다. 요청 식별자가 섞일 수 있는 임의 경로를 오류 프레임에서도 제거했다. 환경 설정 검증·모듈 로드·DB 연결·포트 수신까지 시작 실패 처리를 묶고, 진단 실패가 원래 종료 코드를 덮지 않도록 했다. 서버 테스트 73개·타입 검사·배포 빌드·포맷 검사 통과. 배포 번들의 두 시작 실패와 DSN 미설정·staging·production 세 조건을 조합한 6건도 로컬 수신기로 확인했다.
- **재사용할 기준.** Project의 [개발자 진단](../../../../project/guidance/error-handling.md)과 [동기화·저장 수명](../../../../project/guidance/data-lifecycle/INDEX.md)에 신호의 의미, 진단과 여행 데이터의 수명, 확인 범위를 반영했다. [개발 시작 안내](../../../../../START_GUIDE.md)는 환경 설정과 소스맵 확인 경로를 연결한다.

## 최신 통합판의 확인 결과

- 앱은 63개 테스트 묶음 702개와 변경 코드 lint가 통과했다. 앱 전체 타입 검사의 기존 오류 7개는 남았다. 서버는 12개 묶음 73개, 타입 검사와 빌드가 통과했다.
- 별도 검증자는 갱신 응답 유실·500, 여행 요청이 401을 받은 뒤 갱신 실패, 여행 요청 자체의 500을 재현했다. 실제 HTTP 어댑터 호출 횟수·남은 큐·호출자에게 돌아간 원래 오류를 대조해, 인증 요청의 실패가 여행 요청의 서버 거절로 집계되지 않음을 확인했다. 서버의 부팅 실패 및 거절 로그는 수신 데이터까지 대조했다.
- 독립 검증에서 실제 iOS·Android Hermes `.hbc.map` 파일명과 debugId를 최종 필터에 넣어 허용한 프레임·trace가 남고 시험용 개인정보와 오염된 trace가 제거되는지 확인했다. Main은 두 플랫폼에서 내보낸 소스맵으로 원본 코드 줄을 복원했고 업로드 토큰 실제 값이 산출물에 포함되지 않은 것을 확인했다.
- Main이 변경된 JS·TS 파일 29개의 신규 코드를 구문 트리로 검사해 중괄호 누락 0건을 확인했다. `harness:check`의 문제 79건은 보완 전과 같은 목록이었다.

개발 기준 재점검 때에는 수정판의 로컬 검증까지 마쳤다. 앞선 staging 수신 결과, 도시 정보 및 Warning 전용 알림의 남은 판단, EAS 설정은 [실제 프로젝트 시험 기록](2026-11-10-01-sentry-staging.md)에서 구별한다.

## 최종 수정판의 staging 대시보드 확인

사용자가 “최종 수정판으로 실제 Sentry 대시보드에 들어오는 것까지 확인하고 작업한 것만 커밋하자”라고 요청했다. Main은 로컬 시험 수신기를 사용한 앞선 검증에 이어 실제 Sentry 프로젝트에서 이번 시험 이벤트와 릴리스를 대조했다.

- 서버 오류 상세에서 일정(schedules) PUT 요청의 500, 환경 `staging`, 릴리스가 이번 시험 판본과 일치했다.
- 동일 서버 시험의 404 거절은 Logs에서 `api.request.rejected`와 사유 `target_unavailable`로 확인했다. 실제 요청의 거절이 남았다는 근거이며 404만으로 해당 일정이 서버에서 삭제됐다고 단정할 수 없다.

- 최종 iOS 시뮬레이터 Release 빌드에서 임시 시험 진입점으로 제품의 시작·진단·종료 함수를 호출했다. staging 시험 릴리스의 앱 경고 이벤트에 `schedules` UPDATE, `auth-refresh-failed`, HTTP 503, 이전 실패 횟수 1이 표시됐다. 앱 실행 trace에서 `sync.started`·`sync.push.blocked`·`sync.finished` 세 항목이 연결됐다.

앱 시험에서는 인증 갱신 실패 신호를 지정해 SDK 송신부터 대시보드 표시까지 대조했다. 실제 토큰 갱신이 실패하는 흐름은 앞선 HTTP 어댑터 독립 재현에서 확인했다. 이번 staging 수신은 운영 배포·EAS 비밀 설정의 확인 범위를 넓히지 않는다.
