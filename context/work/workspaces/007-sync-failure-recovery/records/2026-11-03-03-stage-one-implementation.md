# 2026-11-03 — 1단계 구현(Ticket 01·02)과 독립 검증

생성 재전송 수정을 유지하기로 정하고 Ticket 01·02를 구현해 별도 검증자에게 확인받은 기록이다. 모두 commit `d048c9f1` 위의 미커밋 변경이며, 커밋·배포는 하지 않았다.

## 유지 결정

Main이 작업 트리의 생성 재전송 수정을 구현·수정 없이 다시 검토하고 "유지"를 추천했다. 근거는 다음과 같다.
- 앱은 CREATE 응답 body를 읽지 않고 2xx로만 성공을 판단한다. 그래서 201→200 변화가 앱에 영향을 주지 않는다.
- 큐는 CREATE·UPDATE를 합치지 않으므로, 기존 행을 돌려줘도 뒤의 UPDATE가 사라지지 않는다.
- 조회는 `id + userId`로 제한돼 다른 사용자 행을 읽거나 바꾸지 않는다.
- 당시 서버 단위 65·통합 11이 다시 통과했다.

이어 사용자가 다음과 같이 답했다(2026-11-03, 이 세션).

> "유지하고 진행"

이 답을 생성 재전송 수정의 유지와 1단계 진행 승인으로 받았다. Spec 03의 "바뀌는 약속" 세 가지(재시도 3회 한도 제거, 003 Ticket 11 완료 조건 대체, API 응답 세 가지 변경)도 이 승인에 포함된 것으로 본다. 각각 1단계 범위로 제시돼 있었기 때문이다. 같은 세션에서 사용자는 "서브는 소넷 미디엄으로 해"라고 지시했고, 검증자는 그대로 배정했다.

## 구현하며 정한 것

- **삭제 재전송:** Ticket 01의 초안대로 했다. 쓰기 조건 `id + userId + deletedAt IS NULL`은 그대로 두고, 0행일 때만 `id + userId`로 조회한다. 이미 삭제됐으면 200과 처음 삭제 시각을 돌려주고, 아니면 기존 404를 유지한다.
- **여행 삭제 재전송:** 코드는 바꾸지 않았고, 다시 보내도 200인 것만 통합 테스트로 고정했다. 다시 보낼 때 삭제 시각을 새로 찍고 version을 올리는 차이는 남겼다. 일정·경비처럼 처음 시각을 유지하려면 Trip mutation의 조건을 바꿔야 한다. 그런데 "선행 조회 뒤 ID만으로 변경"하는 공백은 003 Ticket 13의 범위이고, 같은 줄을 두 이유로 고치게 된다. 앱은 DELETE 응답 body를 읽지 않으며, pull이 삭제된 여행을 한 번 더 내려도 결과는 같다. 이 차이는 [API 계약](../../../../project/guidance/api-contracts.md#큐-작업-재전송에는-이미-반영된-결과로-응답한다)에 현재 차이로 적었다.
- **IN_PROGRESS 되돌림 위치:** `getSyncableTasks`에 넣으면 조회 함수가 상태를 바꾸게 된다. 그래서 큐에 `recoverInterruptedTasks()`를 따로 만들고, `pushChanges` 맨 앞에서 호출했다. 이 지점은 계정 검사보다 앞이라 다른 계정 작업의 IN_PROGRESS도 PENDING으로 바뀐다. 상태만 되돌리고 삭제·전송은 하지 않으므로 계정 보존 계약은 그대로다.
- **3회 한도 테스트:** 지우지 않고 새 계약을 고정하도록 바꿨다. 새 계약은 "FAILED는 횟수와 관계없이 FIFO로 선택, IN_PROGRESS는 되돌리기 전까지 막음"이다.

## 독립 검증 (Sonnet, medium, 구현에 참여하지 않은 새 컨텍스트)

검증자는 제품 파일을 수정하지 않았다. 직접 실행한 검사는 다음과 같다.
- 서버 typecheck·build, 단위 69, 통합 21
- client Jest 655
- typecheck 8건이 이번 변경과 무관한지 대조

판정은 다음과 같다.
- **충족 근거 있음:** Ticket 01·02의 완료 조건과 Spec 03의 "그대로 지키는 기존 계약" 표 전부. 단, 아래 하나는 제외한다.
  - 실행 잠금 주장도 직접 확인했다. `pushChanges` → `syncData`의 유일한 비테스트 호출처는 `lifecycle.ts`의 `runSync`이고, 이것은 `executeSync`의 `activeSync`로 직렬화된다.
- **미확인:** "라우트를 되돌리면 같은 증상으로 실패"는 검증자가 다시 해 보지 않았다. 위 Main의 자기 확인만 근거다.
- **낮은 심각도의 발견**
  1. 실제 SQLite 큐에서 "남은 IN_PROGRESS가 다음 `pushChanges`로 전송되고 큐에서 지워진다"는 한 흐름을 이어서 보는 테스트가 없다. 선택은 실제 SQLite 테스트가, 순서는 mock 테스트가 나눠 확인한다. Ticket 03의 실제 앱 확인에서 본다.
  2. 다른 사용자가 쓰는 ID로 생성하면 409라서, 그 ID가 쓰인다는 사실은 드러난다. Spec 03이 받아들인 범위다.
  3. 부모 여행이 지워진 뒤의 일정 생성 재전송은 404로 계속 막힐 수 있다. 문서가 "규칙 없음"으로 밝혔고, Ticket 06·07의 범위다.
  4. `data-lifecycle`의 대조 날짜 문장이 10-31과 11-03을 이어 붙여 읽기 흐름이 어색하다. 의미 충돌은 없다.
