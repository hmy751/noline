# React 공식 문서를 근거로 저장 UI의 초기화 책임을 정리

사용자가 1단계 코드를 다시 리뷰하면서 폼 초기값 설정을 질문했고, React 공식 문서를 근거로 더 간결하게 구성하도록 승인했다. **경비·일정 저장 UI의 제품 수정과 자동·독립 검증은 완료했다. 실제 시뮬레이터의 수정창 열기·닫기·재열기는 확인하지 못했으므로 남은 실행 확인이다.** 앞선 [2〜7단계 검토](2026-11-12-02-staged-review-followups.md)와 별개의 이번 한정 결과이며 사용자 수락·커밋·배포는 미실행이다.

## 질문·정정과 실제 승인

사용자는 먼저 “defaultValues에 expenseData가 할당되니까 reset(openingValue)를 할필요가 있나?”라고 물었다. Main은 부모가 빈 데이터로 수정창을 계속 마운트하므로 기존 구조에서는 `defaultValues` 변경만으로 새 폼이 되지 않아 reset이 필요하다고 설명했다. 이 설명은 당시 구조의 동작을 설명했지만, 그 구조 자체를 더 단순하게 바꿀 수 있는지까지 판단한 답은 아니었다.

이어 사용자는 `isOpen`일 때 렌더링하는 안을 제시했지만 “아니 isOpen뿐만 아니라”라고 범위를 바로잡았다. 특정 렌더 조건 하나가 아니라 편집·저장 UI 전체의 effect·ref·상태·컴포넌트 수명을 검토하라는 의미다. “그냥 React 관점말고”와 “React 공식문서를 근거로 전문적 관점으로 더 간결하게 할수 있는지 코드를”이라는 재정정도 있었다. Main이 관련 라이브러리 공식 문서 전반으로 넓히려던 해석을 거두고 **React 공식 문서를 근거로 한 구조 간결화**에 맞췄다.

처음에는 high 검토만 요청했고 수정은 하지 않았다. 검토자가 중단된 상태를 확인해 재개한 일과, 완료된 검토 결과를 Main이 제때 회수하지 못한 일은 실제 진행 경위로 구별한다. 검토 결과 이후 사용자가 “좋아 그럼 검토한 내용대로 1단계 코드 간결하게 정리해줘. 기존 합의랑 입력 보호는 유지하고, 수정한 코드 검증하고 다시 설명해줘”라고 승인한 뒤 구현했다. 검토 요청을 곧바로 수정 승인으로 취급하지 않았다.

## 공식 문서에서 적용한 판단과 실제 구조

검토자는 React의 [prop 변경 시 전체 상태 재설정](https://react.dev/learn/you-might-not-need-an-effect#resetting-all-state-when-a-prop-changes), [useRef 주의점](https://react.dev/reference/react/useRef#caveats), [시간에 따른 상태 snapshot](https://react.dev/learn/state-as-a-snapshot#state-over-time)을 실제 코드와 대조했다. 아래는 그 문서를 Noline의 입력 보호에 적용해 선택한 구조이며, 공식 문서가 이 앱의 저장·잠금 설계를 그대로 규정한다는 뜻은 아니다.

### 새 편집은 새 폼, 진행 중 저장은 바깥 수명

두 공개 `UpdateExpenseDrawer`·`UpdateScheduleDrawer`는 유지하면서 `isOpen && data`일 때만 내부 편집 폼을 렌더링하고 기록 ID를 `key`로 사용한다. 닫았다 열면 같은 ID라도 내부 폼이 새로 생기고 A→B→A도 새 편집 회차가 된다. 폼의 입력·오류·장소/날짜 선택창 상태는 내부 폼 수명으로 초기화한다. 별도 초기화 effect와 의존성 검사 억제, 일정 기준값 ref 세 개 및 `TimeField` 초기화 key를 제거했다.

내부 폼은 처음 받은 기록을 state snapshot으로 고정한다. 일정은 기록과 시간대를 함께 보관해 같은 편집 도중 배경 조회가 입력·비교 기준·시간 해석을 바꾸지 않게 한다. 렌더에 필요한 시간대를 변경해도 렌더를 일으키지 않는 ref에 의존하던 연결을 없앴다. 성공 후에도 창을 계속 열어 두는 소비자에는 `reset`과 필요한 일정 비교 기준 갱신을 남긴다. 초기화 effect를 없애는 일과 모든 reset을 제거하는 일은 다르다.

새 `shared/lib/use-update-drawer-save.ts`는 공개 wrapper에서 저장 잠금 ref·표시 state를 관리한다. 내부 폼이 교체돼도 진행 중 저장의 중복 제출·닫기 잠금은 유지되고 완료 후 해제된다. 단순히 외부 wrapper까지 조건부 마운트해 잠금이 사라지게 만들지 않았다. 내부 폼에는 mount ref와 cleanup이 남아, 사라진 폼의 검증·성공·실패가 새 폼의 저장·입력·오류·알림·닫기를 실행하지 못하게 한다. 이는 새 입력의 수명과 이미 시작된 저장 Promise의 수명을 나누는 책임이다.

### 일정 후처리는 500ms 대신 저장 결과를 명시적으로 사용

기존 500ms timer는 기다려도 캡처한 목록이 최신 조회 결과로 바뀌지 않았다. timer를 제거하고 저장 응답의 `savedSchedule` 시각·좌표를 기존 목록에 반영해 정렬한 뒤 경로 후처리를 바로 호출한다. 이 방식도 최신 목록을 새로 조회한 보장은 아니다. 이미 저장된 일정의 후처리는 기존 폼이 사라져도 실행하지만, 그 결과로 새 폼을 닫거나 초기화하지 않는다.

실제 제품 변경은 두 Drawer와 새 저장 수명 훅의 **3파일**이다. 새 훅까지 포함한 행 수는 804→801로 큰 감소가 아니며, 주된 이득은 초기화 effect 안에서 여러 상태·ref를 함께 맞추던 책임을 컴포넌트 수명으로 표현한 데 있다. FIFO·표식·편집 그룹·Repository·Local DB·서버 계약은 바꾸지 않았다.

## 자동 검증과 독립 판단

구현자의 관련 자기 확인은 3묶음 **42/42**(기존 관련 33·신규 수명 5·장소 검색 4)였다. 독립 high 구조 검토는 새 책임 배치가 적절하고 필수 수정이 없다고 판단했다. 별도 high 검증자는 최종 client 전체 **74묶음 852/852**, 독립 추가 수명 검사 **12/12**를 확인했다. 전체 저장소와 추가 독립 검사 수는 합산하지 않는다.

추가 검사는 두 폼 각각에서 A→B→A와 동일 ID 닫기·재열기, 성공·일반 실패·서버 처리 후 기기 준비 실패를 조합했다. 새 A 초안·날짜·시간대가 남고, 앞 저장 중에는 wrapper 잠금 때문에 중복 제출·닫기가 막히며, 이전 결과가 새 안내·닫기를 만들지 않았다. 앞 저장 종료 후 새 폼에서 다시 저장하면 바뀐 항목만 제출되고 일정은 새 편집 시간대로 시각을 해석했다. 기록 담당자는 제품 3파일과 독립 assertion·로그를 직접 대조했다.

관련 lint는 오류 0·기존 테마색 경고 16개, client 타입 검사는 기존 오류 7개다. harness는 기존 과거 링크 문제 64개가 남고 신규 링크 오류는 없다는 Main 확인이며, Main의 제품 차이 검사도 통과했다. 기록 담당자의 문서 변경 뒤 차이·신규 링크 확인은 별도로 수행한다.

Main은 Project의 입력·draft·picker·형성 이유와 경로 문서를 실물에 맞춰 수정했다. 초기화와 wrapper 잠금/내부 선택창의 소유, timer 제거를 반영하고, 이미 낡아 있던 활성화 Local 조회의 삭제 필터 설명도 실제 필터 존재에 맞게 정정했다. 검증자가 지적한 두 문장도 실제 소스와 대조해 반영했다는 보고다. 이번 Work 기록 권한으로 Project를 직접 수정하지 않았다.

## 시뮬레이터에서 확인한 범위와 남은 일

Main은 부팅된 iPhone 15 Pro 시뮬레이터의 `com.noline.dev`를 현재 일반 `index.js`·Metro 8081에 연결했다. 처음 No Bundle 화면은 Reload 뒤 정상으로 바뀌었다. API가 꺼져 발생한 sync network error 개발 경고를 Dismiss하고 기존 테스트 데이터의 일반 홈·경비 목록과 경비 상세 한 번까지 확인했다.

수정 메뉴가 접근성 대상에 노출되지 않았고, 좌표 클릭 도구도 세 차례 `noWindowsAvailable` 오류를 반환해 **수정창 열기·닫기·동일 기록 재열기는 확인하지 못했다.** 사용자 권한 거부가 아니라 조작 도구 오류이며 새 권한 결정을 요구하는 문제로 기록하지 않는다. React Native 테스트 렌더러의 입력 수명 검사를 네이티브 Drawer 애니메이션·키보드·터치 완료 확인으로 확대하지 않는다.

따라서 이번 남은 일은 실제 시뮬레이터 또는 기기에서 두 수정창의 열기·닫기·재열기와 새 초기값을 확인하는 것이다. 제품 수정·자동 검증 완료와 이 실행 확인 미완료를 함께 유지한다. 임시 Metro 세션은 Main이 Ctrl-C 후 종료 코드 0으로 정리했다고 반환했다. 커밋·배포·새 제품 합의는 없다.
