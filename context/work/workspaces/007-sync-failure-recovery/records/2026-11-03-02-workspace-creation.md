# 2026-11-03 — 007 생성과 재진입 확인

## 생성 범위

사용자 요청은 "종합 논의한걸 새로운 워크스페이스에 티켓으로 잘 구성해봐 지금 논의들 다 훑어보고 이슈관한거"였다. 쓰기 전에 만질 위치를 물어 승인을 받았다("그래 워크스페이스 채워봐"). 승인 범위는 새 폴더 `007-sync-failure-recovery/`만 만드는 것이다. 제품 코드, 003 문서, Project 문서, `workspaces/index.json`, 세션 연결은 바꾸지 않았다. 커밋하지 않았다.

자료는 세 곳에서 확인했다.
- 이 세션의 로컬 대화 기록: 요약 이전 부분의 관찰 보고, 층별 판단, 넓은 수정안, 줄인 수정안을 원문으로 다시 읽었다.
- 003 Ticket 11·12·13 본문
- 인용한 코드와 Project 문서의 현재 행

## 선택과 이유

- **후속 관계:** 003 Ticket 11의 영역을 이어받되, 전제("기존 client ID·서버 수용 계약으로 중복 방지")가 이번 사고로 무너졌다. 그래서 새 goal로 분리했다. 003 문서는 자동으로 고치지 않고, "007로 옮김" 표시 여부를 사용자 결정으로 남겼다.
- **Ticket 7개:** 1단계(01·02·03), 출시(04·05), 2단계(06), 3단계(07)로 나눴다.
  - 각 Ticket은 자기 변경의 Project 문서 반영까지 맡는다. 문서 반영을 마지막 검증으로 미루지 않는다.
  - 여행별 큐, 동기화 계기 확대, 버전 사이 payload 호환은 조건이나 결정이 먼저라 Ticket으로 만들지 않았다. 각각 Spec과 state에 남겼다.
  - 경비 부모 확인과 여행 생성 중복은 003 Ticket 13·03의 범위로 두고 의존만 적었다.
- **Recover 선택:** Project 7개 문서를 골랐다. data-lifecycle, api-contracts, error-handling, app-runtime, product, Decision 0001과 routing anchor다. 각 문서가 이 Work에서 지키거나 고칠 계약을 직접 담고 있다.
- **Verify:** 제품 테스트가 아직 다 갖춰지지 않았다. 그래서 006과 같이 recover.json의 JSON 파싱만 claim으로 두었다. 1단계 제품 Verify는 Ticket 03에서 구성한다.

## 확인 결과

- **JSON:** `workspace.json`, `recover.json`, `verify.json`, `status.json`이 모두 파싱된다.
- **Recover:** `python3 -B -m context.work.harness recover 007-sync-failure-recovery`가 exit 0으로 끝났다. packet에 memory 색인·Spec 5개·project-context·Ticket 색인·state·status·output 색인과 Project 7개 문서가 실렸다.
- **재진입 검토:** 별도 검토자를 쓰지 않고 Main이 자체 점검했다. 생성자의 이해를 공유하므로 독립 검토보다 약한 근거다. packet만으로 다음을 찾을 수 있는지 확인했다.
  - 목표와 세 결말, 단계별 Ticket
  - 사용자 결정 대기 항목과 첫 행동 (1단계 진행 승인 뒤 01·02)
  - 작업 트리의 미커밋 변경과 무관한 변경의 구별
  - 003과의 관계와 의도적으로 이어받지 않은 범위
- **링크 검사:** `pnpm harness:check`는 exit 1, 실패 64건이다.
  - 64건은 모두 001–006 Workspace의 옛 `.claude` 경로 링크다. 006이 기록한 기존 64건과 같은 수다.
  - 007 안의 실패는 0건이다.
  - 이 검사는 경로 존재만 확인한다. 링크가 설명한 실제 Owner를 가리키는지는 위 자체 점검의 범위다.

## 커밋 전 독립 재진입 검토

사용자 요청("커밋 전에 다른세션이 봐도 흐름을 잘 이어갈수 있는지만 한번더 점검해보고 커밋해")으로 별도 검토자를 한 번 썼다. 검토자에게는 Recover packet만 주고, 생성자의 결론은 주지 않았다. 검토자는 먼저 packet만으로 goal·제약·상태·첫 행동을 복원했다. 그다음 실제 파일과 대조했다.

- **판정:** 인수 가능, 소폭 보완 권장. 확인한 것은 다음과 같다.
  - 목표·제약·다음 행동이 packet만으로 복원됐다.
  - 인용한 코드·Project 문서의 행 번호가 모두 맞았다.
  - 미커밋 파일과 DB 백업의 해시가 일치했다.
  - 007 안의 링크가 실제 대상으로 해석됐다.
  - 빠진 Project 문서는 없었다.
- **반영한 보완:**
  - 미커밋 생성 재전송 수정의 유지 여부를 1단계 승인 질문에 넣었다. Ticket 01의 "이어서 쓴다"라는 단정은 사용자가 답하지 않은 상태와 맞지 않았다.
  - Ticket 01·02가 데이터 수명 문서의 push 상태표를 함께 고친다는 점을 Ticket 색인과 state에 적었다.
  - Ticket 02의 문서 대상에 데이터 수명 129행을 추가했다.
  - Ticket 03에서 정의되지 않은 "3a"를 지웠다.
  - "수정 1~3"과 Ticket의 대응을 state와 설계 기록에 적었다.
  - 관찰 사례에서 1분 안에 실패 3번이 쌓인 것과 헛요청 추정이 맞지 않는 점을 Spec 02와 Ticket 03에 남겼다.
  - Project의 "재전송"(401 뒤 다시 보냄)과 이 Work의 큐 작업 재전송을 Spec 03에서 구별했다.
  - `status.json`의 초기값 뜻을 state에 적었다.
- **반영하지 않은 것:** packet에 Ticket 본문이 실리지 않는 점은 그대로 두었다. Ticket 색인이 본문 위치를 가리키므로 읽을 목록만 바뀐다.

- 활성화는 하지 않았다. 이 세션은 Claude Code라 `.codex/hooks/maintain.py activate`의 대상이 아니다. 이후 문서 반영은 Maintain 수동 경로로 한다.
