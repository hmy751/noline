# 충돌 종결과 pull 보호의 공동 구현·검증

2026-11-10, 007 Ticket 07과 003 Ticket 12의 로컬 구현을 함께 검증했다. 최신 main `25d9d359` 위의 미커밋 변경이며 이번 서버·앱 배포는 하지 않았다. 기존 규칙의 선택 이유와 사용자 원문은 [항목별 편집](2026-11-10-01-update-conflict-policy.md), [구버전 호환](2026-11-10-02-legacy-update-compatibility.md), [여행 삭제](2026-11-10-03-deleted-trip-pending-expenses.md)에 보존한다. 이 기록은 그 결정을 새로 승인하거나 다른 Ticket 전체를 완료시키지 않는다.

## 구현과 연관 Ticket의 대조

서버 `entity-mutations.ts`는 여행을 먼저 잠가 자식 생성·수정·삭제와 여행 삭제를 직렬화하고, 항목별 표식 비교와 쓰기를 같은 트랜잭션에서 처리한다. 구버전 요청은 표식 있는 서버 값과 충돌하면 요청 전체를 보류한다. 자기 소유 삭제는 410의 구별된 코드로 응답하며, 다른 사용자·부모 불일치는 404를 유지한다. 일정 soft delete와 연결 경비의 `scheduleId` 해제는 함께 확정한다. Ticket 01에서 합의한 삭제된 생성 재전송은 유지한다.

앱은 변경 항목과 표식을 저장하고, pull과 push 응답을 같은 reconcile 함수로 반영한다. 해당 응답이 완료한 큐 요청만 제외하고 후속 pending 입력을 다시 겹친다. 구버전 보류 입력은 별도 SQLite 표에 원형을 보존하며, 목록에서 확인·닫기·선택 항목 재저장·현재 값 유지의 경로를 제공한다. 여행 삭제는 확인 가능한 귀속과 유효한 요청 범위만 정리한다.

003의 10·11·13은 이번 두 Ticket의 선행 경계를 실제 코드와 대조했다. 10의 DB 실행 경계와 local mutation·queue 저장, 11의 응답 확인 뒤 종결과 실패 보존, 13의 부모 여행·소유권 확인을 공동 구현에서 사용한다. 이는 이 세 Ticket의 모든 완료 조건을 검사한 결과가 아니므로 각 본문과 전체 완료 상태는 바꾸지 않는다.

## PostgreSQL과 자동 검사

Main은 격리 PostgreSQL 통합 35개, 서버 단위 73개 통과를 보고했다. 기록 담당자는 검사 실행을 반복하지 않고 실제 테스트·제품 코드를 대조했다.

`pull-cursor.test.ts`는 열린 쓰기 트랜잭션이 경비 테이블의 읽기를 잠그고 실제 pull이 해당 조회에서 대기하는 것을 확인한 뒤 생성·수정·삭제를 주입한다. 진행 중 응답에는 0건, 다음 cursor 응답에는 3건 모두 존재함을 확인했다. 서버는 같은 repeatable-read snapshot과 트랜잭션 ID 경계를 사용하고, 기기는 계정·활성 여행 집합별 cursor를 저장한다. mock 응답만으로 무누락을 주장하지 않는다.

## 실제 앱 실행

Main은 두 iOS 시뮬레이터를 localhost 전용 DB·임시 JS 진입점에 연결해 앱의 실제 저장·REST·SQLite·화면 경로를 실행했다. 기록 담당자는 저장소 `artifacts/ticket-07-12/native.jsonl`을 직접 읽었다. 이 파일은 로컬 재접근 근거이며 영구 산출물이나 운영 환경으로 간주하지 않는다. 최종 성공 실행의 핵심 결과는 다음과 같다.

- 미전송 금액 30과 다른 기기에서 저장한 분류 교통이 함께 남았다.
- 앞선 응답을 반영한 뒤 새 금액 35의 pending 1건이 남았고, 응답 유실 뒤 재전송으로 35.00·pending 0건이 됐다.
- 옛 입력 39 USD·쇼핑은 보류 원문으로 남고, 다음 제목 요청은 전송돼 pending 0건이 됐다.
- 경비 저장과 일정 삭제를 두 순서로 실행해 경비는 8.00·2026-11-10을 유지하고 `scheduleId`만 null이 됐다.
- 여행 삭제 뒤 다른 여행의 전송이 진행돼 queue 0건이 됐다.
- 마지막 SQLite·서버 값은 35.00·교통으로 일치했다.

최초 시험 fixture의 필수 주소 누락 400은 fixture 수정 후 성공 실행으로 대체했다. 실행 로그에는 실제 engine에 시험용 `captureEvent` 수신기를 붙여 `response-unconfirmed`, `legacy-held`, `entity-deleted`, `trip-deleted` 신호도 확인했다. 이는 Sentry 서비스가 이벤트를 수신한 검증과 다르다.

## 일반 앱 화면과 다른 기기의 구버전 요청 후속 검증

Main은 임시 시험 진입점 검증 이후 Expo의 기본 진입점으로 일반 앱을 실행해 실제 경비 목록과 복구 화면을 조작했다. 목록의 버튼 문구가 화면을 깨는 문제를 발견해 수정한 뒤 최종 UI를 다시 확인했다. ‘수정 확인’을 열었다 닫아도 보류 안내가 유지됐다. 다시 열어 분류만 선택해 저장하자 SQLite는 35 USD·쇼핑, 큐는 `category`와 `edit`만 담은 1건, 보류 입력은 0건이 됐으며 재시작 뒤 서버도 같은 값으로 수렴했다. 화면 근거는 로컬 `artifacts/ticket-07-12/legacy-category-selection.png`와 `final-expense-list.png`다. 이 UI 결과는 Main의 실제 조작 보고이며 기록 담당자가 다시 조작한 결과가 아니다.

이어 B에서 표식 없는 구버전 형식 PUT으로 제목·42 USD·음식을 전송했다. 서버는 409로 응답하고 원문 전체를 계정 소유의 보류 입력으로 보존했다. B를 종료한 뒤에도 A의 일반 앱은 서버 원문을 수신해 현재 제목·금액·분류와 비교 표시했다. A에서 ‘현재 값 유지’를 선택하고 재확인한 뒤 재시작하자 화면·SQLite·서버는 35 USD·쇼핑, 큐와 기기·서버 보류 입력은 모두 0건이었다. 기록 담당자는 이 409·보류 원문 및 최종 0건 결과를 `native.jsonl`의 후속 실행 행에서도 확인했다.

서버 보존이 추가되면서 직접 요청도 앱의 큐 사본 없이 입력을 복구할 수 있게 됐다. 현재 코드는 계정별 보류 입력 조회·해제와 기기 해제 ACK 재전송을 사용한다. 완료된 ACK는 로그아웃의 미전송 손실 수에서 제외한다. Main은 초기 독립 검증과 서버 복구 독립 검증, 계정 전환 수정 확인을 보고했으며 추가 삭제 귀속 회귀를 보완하고 있다.

## 확인 한계와 남은 수행

두 기기는 같은 네이티브 빌드를 사용했다. 구버전 호환은 옛 wire 형식의 실제 PUT으로 시험했으며 실제 구버전 설치 binary·업데이트는 실행하지 않았다. 응답 유실도 OS 인터넷 차단이 아니라 서버 반영 뒤 engine이 응답을 처리하기 전 JS 경계에서 주입했다. 위 진단은 시험 captureEvent 수신 결과이며 Sentry Cloud로 다시 전송한 결과가 아니다. 물리 기기와 운영 환경도 이번 확인에 포함하지 않는다.

이후 최종 독립 검증과 삭제 귀속 회귀를 마쳐 Main이 두 Ticket의 개발·검증 완료를 판정했다. 배포는 SQL 적용 → 서버 → 앱 순서로 남아 있다. Project·Workspace 008의 지속 기준 반영은 Main의 별도 책임이며 이 기록 담당자가 수정하지 않는다.


## 최종 독립 검증과 완료 판정

Main이 최신 통합 변경판의 독립 검증 결과를 회수해 003-12·007-07의 개발·검증 완료를 판정했다. 기록 담당자가 같은 검사를 다시 실행한 결과가 아니라 독립 담당자의 결과를 Main에게서 전달받아 반영한 것이다.

| 검사 | 최종 결과와 범위 |
| --- | --- |
| 격리 PostgreSQL `noline_verify` | 4파일 44/44. 일정·경비·삭제 등 43개와 실제 조회 중 쓰기 pull 1개를 합친 수치 |
| 서버 단위 검사 | 73/73 |
| 서버·공유 schema | server 타입 검사·빌드, schema 빌드 통과 |
| 클라이언트 | 67묶음 741/741 |
| checkpoint 독립 주입 검사 | 중간 저장 실패 때 마지막 시간과 cursor가 함께 rollback되고, 계정 전환 뒤 이전 결과 반영을 거절함 |

추가 DELETE 귀속 회귀는 원본 없이 검증된 소유자와 여행 귀속을 가진 DELETE, 원본이 남은 옛 null 소유자 DELETE를 확인했다. 확인 가능한 요청은 삭제된 여행의 정리와 다음 여행 전송으로 이어지고, 증거 없는 요청은 유지했다.

최신판 실제 앱에서 구버전 요청의 표식 없음·같은 값·혼합 충돌 세 조건을 직접 전송과 큐 전송 양쪽으로 실행했다. `native.jsonl` 마지막 네 행에 두 경로의 서버 금액 30.00·분류 기타·canonical 보류 1건·큐 0건, 삭제 증거 없는 404에서 FAILED/PENDING 보존, 원인 해소 후 큐 0건 결과가 남았다. 이 후속 fixture의 값은 앞서 일반 앱 UI에서 확인한 35 USD·쇼핑의 성공 결과와 다른 시험 조건이다.

진단에서는 정상 보류 `legacy-held`와 삭제 종결 `entity-deleted`·`trip-deleted`를 info로, 응답 확인 불가 `response-unconfirmed`와 삭제 증거 없는 404의 `server-rejected`를 warning으로 확인했다. 404에는 뒤 작업이 기다리는 `hasWaiting`도 남았다. 서버 행을 복원하자 다음 작업까지 처리됐다. 일반 2xx는 정상 trace로 남고 새 개별 경고를 만들지 않았다. 실서비스 Cloud 재수집 검증은 이번 범위 밖이다.

전체 앱 타입 검사에는 기존 오류 7개, 저장소 문서 검사에는 과거 링크 오류 64개가 남아 있다. `pnpm lint` 실행을 마쳤고 이번 변경 파일의 lint 오류는 0개였다. 전체 lint에는 이번 작업 밖 client 오류 6개(`MyLocationButton`, `offline-map/download`)와 UI 오류 25개(`Pressable`·`RadioGroup`·`Select`)가 남았다. 이 완료 판정은 저장소의 모든 검사가 통과했다는 뜻이 아니다. 두 Ticket의 완료는 003 전체, 007의 운영 헬스체크·출시·Sentry 정책, 003의 10·11·13 전체 완료나 운영 배포를 포함하지 않는다. 기존 한국어 사용자 결정 원문과 그 강도는 각 결정 기록·Ticket에 유지한다.


이 완료 판정 뒤 추가 독립 검토에서 발견한 누락과 수정·재검증은 [후속 기록](2026-11-10-05-conflict-pull-review-fixes.md)으로 이어진다. 위 수치는 선행판의 결과로 보존한다.
