# 여섯 관점 전수 검토와 코드 표현 정리

2026-11-13. 3단계 설명 뒤 4단계로 이어가기 전에, 사용자는 **1·2단계에서 정리한 코드 판단을 다시 찾고 사람이 읽고 판단하기 쉬운 관점으로 묶은 뒤, 이번 1〜7단계 코드 전체를 여섯 검토자가 각각 조사**하도록 요청했다. 기능·정책·기존 합의는 유지하면서 코드 디테일을 다듬는 범위다. 4단계 상세 설명은 아직 미착수이며 이번 정리 뒤 재개할 수 있다. 이번 요청에 새 커밋 지시는 없다.

여섯 관점 전수 검토, 전체 발견의 채택·조정·유지 판단, 코드 정리, 자기·통합 검사와 독립 검증을 마쳤고 Main이 **이번 코드 디테일 정리 요청을 완료**로 판정했다. 실제 제품·검사 변경은85파일이며 제품48·기존 검사/설정36·추가 연결한 기존 서버 fixture1이다. 기능·정책의 새 채택, 사용자 최종 수락, 전체 Work 완료·커밋·배포를 뜻하지 않는다.

## 찾을 판단의 범위를 잘못 잡은 정정

사용자는 처음 “개발 판단에서 코드 가독성? 그거랑 코드 스타일 관련해서 판단 얘기했던거”를 찾아 달라고 했다. Main은 개인 개발 기준과 일부 2단계 사례부터 제시했다. 사용자가 찾으려던 것은 단어와 맞는 일반 배경보다 **실제 1·2단계 작업에서 정리했던 코드 판단 전체**였다.

> 사용자: “아니 백그라운드 보단 1,2 단계 작업하면서 판단 정리했잖아? 거기서 코드 관련은 다 찾아보라고”

Main은 범위 오독을 인정하고 1단계 판단·실행 합의, 2단계 판단, 원문 재대조 보완과 구현 기록으로 돌아갔다. 정리에는 개행뿐 아니라 상태·ref·wrapper·타입·소비자·책임·공식 동작·기존 유틸·테스트가 만든 불필요한 요구까지 포함됐다. 예를 들어 기존 구조에서 reset이 필요하다는 설명과 폼 수명 구조가 적절한지는 별개였고, 함수 분리 뒤에도 reconcile의 흐름과 범위가 읽히지 않아 다시 정리한 과정이 있었다.

> 사용자: “여기서 가독성 즉 사람이 읽고 판단하기 쉬운 관점으로 또 판단을 정리해봐 … 개행 스타일도... 에어비앤비 지적했던게 사례이고 또다른 가독성 관점으로 잘 정리해봐”

이에 Main은 여섯 관점으로 재구성했다. 개행·Airbnb는 시각적 구간 판단의 사례이며 새 preset 도입이나 모든 코드를 같은 모양으로 만드는 요청으로 바꾸지 않았다.

| 관점 | 읽는 사람이 줄일 수 있어야 할 부담 |
| --- | --- |
| 시각적 구간 | 같이 읽을 선언·검사·실행과 다음 처리의 경계를 직접 추측하는 부담 |
| 전체 흐름 | helper를 계속 따라가며 주된 순서와 책임을 재조립하는 부담 |
| 이름·타입·결과 | 이름을 믿었다가 구현을 끝까지 읽고 의미를 뒤집는 부담 |
| 판단과 효과 | 정상 보존과 실패, 계산과 저장, 현재 요청 완료와 관련 입력 정리를 혼동하는 부담 |
| 불필요한 해석 | 실질 역할 없는 콜백·별칭·반환·조건에서 특별한 이유를 찾는 부담 |
| 변경 영향 | 같은 이유로 바뀔 곳과 다른 책임을 함께 추적하는 부담 |

이 분류는 이번 실제 코드에 적용할 판단 관점이다. 줄 수 감소·함수 추출·테스트 통과가 가독성 개선을 자동 증명하지 않으며, 새 전역 규칙이나 고정 점검 절차를 채택한 것은 아니다.

## 대표 사례를 고르는 대신 같은 전체 범위를 읽게 한 요청

> 사용자: “저 6개 관점의 검토자로 지금 작업한 코드들 다 확인하라고 해봐 여기서 몇개 뽑는게 아니라 전부 잘 조사해라고 해서 작업 부분 보고 받으면 니가 판단해서 작업하자”
>
> 사용자: “기존 기능이나 합의 등을 바꾸려는건 아니고 코드 디테일을 좀 다시 다듬고 싶어”

Main은 커밋된 1·2단계와 미커밋 3〜7단계를 합친 시작 판본을 고정했다. 범위는 제품75·검사/설정51·연결된 공용UI2, 총128파일·24,287행이다. 여섯 검토자는 각각 같은 범위 전체를 읽고, 수정 없이 발견·유지 이유와 파일별 확인 범위를 보고했다. 실행 가능한 동시 수에 맞춰 차례로 배치했으며 뒤 관점에는 앞선 결론을 넘기지 않고 코드와 계약에서 판단하도록 했다.

[검토 자료 모음](../output/2026-11-13-readability-review/README.md)에 여섯 보고, 여섯 coverage, 시작 manifest와 Main 판단을 보존했다. 각 coverage는128개의 서로 다른 경로를 `full`로 기록했고 manifest와 누락·추가 없이 맞는다. 기록 담당자가 이 목록을 대조한 사실과 각 검토자가 전체 코드를 읽었다고 보고한 사실은 구별한다. 보고 자체는 읽기 검토이며 동작 검사 실행이나 사용자의 가독성 평가가 아니다.

발견은 중복 포함53개다. Main은 겹친 제안을 한 번의 변경으로 합치고 각 제안을 채택·조정·유지했다. 모든 파일을 검토한다는 요구를 모든 파일을 수정하거나 정해진 개수의 결함을 찾으라는 뜻으로 바꾸지 않았다.

## Main이 선택한 정리와 유지 이유

전체 발견 ID의 처분과 보존 조건은 [Main 판단 원문](../output/2026-11-13-readability-review/main-decisions.md)에 있다. 아래는 실제로 무엇을 덜 추적하게 하려는지와 늘어나는 비용을 함께 남긴 사람용 요약이다. 선택 당시의 이유와 최종 구현·검증 결과는 아래에서 구별한다.

| 대상 | 채택·조정한 방향 | 유지한 경계와 비용 판단 |
| --- | --- | --- |
| 처리 구간 | 생략된46블록의 중괄호, 의미 경계의 빈 줄, migration·schema·검사 사건 구간을 드러냄. 복합 조건6곳은 formatter 충돌 뒤 원래 표현으로 복구 | 모든 await·return 앞을 띄우는 규칙은 만들지 않음. 조건·else 귀속·실행 순서와 SQL 내용 유지 |
| 긴 조율 본문 | 활성화 반영, 확정 삭제의 관련 큐 정리, 보류 수신/ACK를 같은 파일 helper로 구별. 410은 엄격 해석 뒤 처리만 추출 | 거대한 context·범용 정책 기계·새 공개 DTO를 만들지 않음. 삭제 null commit 뒤 throw, 세션·큐·ACK·진단 순서 보존 |
| 선언 위치 | 서버 공개 mutation을 상세 helper 앞에, 지도 스타일을 컴포넌트 뒤에, 일정 event handler를 파생 표시 데이터 뒤에 배치 | hook 순서·render 중 선택 보정·잠금/조회 순서 유지. 검사 describe 전면 재편은 등록 구조·이름 변경 비용 대비 실익 작아 유지 |
| 이름의 실제 의미 | 준비 Promise, 그룹 전체 patch, 표식만 바뀌어도 필요한 쓰기, 보호 Local, 저장 캐시 수, 차단 수, 조회 중 정리·시계 보존 효과를 명명에 반영 | wire·DB·정책 상태를 바꾸는 개명이 아님. cleanup 숫자는 실제 삭제 완료 수로 바꾸지 않고 기존 계산과 맞는 이름·주석 사용 |
| 소비하지 않는 결과 | 보류 보존·큐 추가 반환, 지도 미사용 계산, 비활성화 내부 상세, 단건 미사용 predicate와 부모 잠금 성공 payload 정리 | ID 발급·실제 부모 잠금·DB cleanupPending·후처리 순서 유지. 비활성화 외부에는 실제 소비하는 결과만 전달 |
| 보호 표현과 입력 | 합성 HELD 큐 배열 대신 실제 소비자의 미해결 여부 boolean, 보류 출처 boolean은 명명한 옵션으로, 폼 submit의 수명 검사는 실제 처리 입구로 | 새 공통 pending 정책을 만들지 않음. 기본 ID 생성 시점·resolver 이후/저장 이후 검사·RHF Promise 수명 유지 |
| 타입·검사 기반 | 같은 화면 표시 타입은 파일 안 하나로, 세 SQLite 검사와 서버 fixture는 기존 기반 재사용, 활성화 검사 helper의 없는 목록 반환 약속 제거 | null·optional 차이와 suite별 초기화·실패 주입·기대값 보존. 새 범용 factory나 serializer로 기대값 생성은 하지 않음 |
| 조건과 실제 거절 | 소유권 검사의 누락 mock을 채우고 정확한 오류·소유자 판정 도달을 확인. schema가 이미 거절한 날짜 조건·사용되지 않는 값을 줄임 | 기존 제품 거절 원인을 바꾸는 것이 아님. parse·날짜 범위·시간대 검증 유지 |

직접 수정 실패와 sync 거절, 일정·경비 폼/CRUD, 서로 다른 경계의 검증·시계·직렬화·cleanup은 닮았다는 이유만으로 합치지 않았다. 필요한 snapshot·ref·Promise·원문·트랜잭션 보호도 역할을 보존한다. 예전에 유지했던 표현을 이번에 바꾸는 경우는 과거 선택을 숨기지 않고 현재 소비자·새 대안의 비용으로 판단했다. 특히 부모 잠금은 성공 데이터 반환을 줄여도 잠금 자체를 제거하지 않는다.

소유권 검사에서는 의도한 소유권 판정 전에 다른 초기 오류로 끝나도 검사 통과가 가능하다는 보고가 있었다. 이는 제품 기능 결함 발견과 구별되는 **검사 근거 보완**이며, Main은 실제 도달을 확인하도록 채택했다.

## 최종 구현·검증과 확인 한계

최초 시각적 표현은66파일에 적용했다. Main과 별도 검증자의 AST 대조에서 제어문 단일 블록과 migration SQL 공백만 정규화한 뒤 차이0이었다. 이는 그 표현 변경의 구조 보존 근거이며 모든 논리 변경이나 가독성 효과의 증명은 아니다. 이후 논리 변경은 별도로 대조했다.

V4에서 처음 채택한 여섯 복합 조건의 내부 개행은 기존 Prettier와 충돌했다. ignore·가짜 별칭·새 설정의 비용보다 읽기 이득이 작다고 판단해 원래 조건 표현으로 복구했다. 의미 경계의 빈 줄·블록 보완은 유지했다. 마지막3파일의 국소 formatter 수정도 AST 차이0을 확인하고 직전 검사 근거를 재사용했다.

세 구현 담당의 [sync](../output/2026-11-13-readability-review/implementation-sync.md)·[client](../output/2026-11-13-readability-review/implementation-client.md)·[server/검사](../output/2026-11-13-readability-review/implementation-server-tests.md) 보고와 [Main 확인](../output/2026-11-13-readability-review/main-checks.md)을 보존했다. 담당별 보고의 당시 타입 오류·도구 실패·통합 검사 대기는 아래 최종 결과로 해소됐다. 보고 원문을 후속 결과로 덮어쓰지는 않는다.

| 최종 확인 | 결과와 범위 |
| --- | --- |
| 통합 client | 수정 전·후 같은37묶음505개 통과 |
| 통합 server | 수정 전·후12묶음73개 통과. mock HTTP 경계이며 실제 PostgreSQL integration 제외 |
| 타입 | server 통과. client 오류7개는 시작판과 전체 출력이 같음: Mapbox tuple1·OfflinePack2·UI rootDir/include4 |

영역별 검사와 이전 단계 결과는 통합 수와 합산하지 않는다. 서버의 첫 포트 권한 실패는 허용된 동일 검사로 해결했고, lint 도구 호환 문제는 기존 plugin 경로를 지정한 최종 검사로 해결했다. 설정이나 ignore로 검사를 우회하지 않았다.

[독립 검증](../output/2026-11-13-readability-review/verification.md)은 실질 delta 전체와 호출자·검사 assertion, 최종 manifest를 대조해 **충족 근거 있음·필수 수정0건**으로 반환했다. Main이 보고 전체와 한계를 읽고 이번 완료 판정에 채택했다. 독립 검증자는 Main의505·73 실행 원본을 재사용하고 같은 전수 명령은 반복하지 않았다. 별도 실행한 대조는 다음과 같다.

- 이전 합성 큐 배열의 존재 판정과 새 boolean을240조합으로 비교해 결과와4개 조회 순서가 같음을 확인했다. 표·귀속·정상/손상 payload·Local 자식·hold의 조합이다.
- 공유 fixture 전후15개 값을 VM에서 비교해 Date와 `timeZone: null` 차이까지 같음을 확인했다.
- 활성화 transaction callback, 서버 선언·잠금, 최초 시각적 정리의 AST를 독립 추출·정규화해 대조했다. 확정 삭제·410·보류 수신/알림/ACK·폼 수명·날짜 schema·반환 소비는 실제 코드·assertion으로 연결했다.
