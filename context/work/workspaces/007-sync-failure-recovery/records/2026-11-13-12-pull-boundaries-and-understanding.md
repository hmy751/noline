# pull의 조회·반영 경계를 질문으로 연결한 과정

2026-11-13. [reconcile 이해 과정](2026-11-13-11-reconcile-understanding-and-explanation-gaps.md) 이후, 사용자는 cursor 등 reconcile 바깥의 조회 보호를 이어서 설명해 달라고 요청했다. 이번에는 **이미 있던 증분 조회의 누락을 고치는 이유, DB가 조회 경계를 정하는 근거와 반복 수신 비용, 기기의 반영 조건**을 문답으로 풀었다. 사용자는 cursor·준비 ID·세션·응답 검증·화면 갱신·삭제 정보·snapshot에 대해 각각 이해됐다고 밝혔다.

Main은 3단계의 목적과 핵심 동작 설명을 마쳤다고 정리했다. 이는 모든 코드·세부 분기를 검토했다거나 제품을 최종 수락했다는 뜻이 아니다. 4단계는 전송 순서·재전송 표식·서버 판정의 세 묶음을 예고했으며 상세 설명은 시작하지 않았다. 사용자는 그 전에 이번 대화와 앞선 미커밋 기록을 남기고 커밋하도록 요청했다.

## 설명의 출발점을 바로잡은 질문

사용자가 처음에 “reconcile 말고 4단계에 필요한것들”, “cursor”라고 지칭한 것은 실제 코드 검토 구획의 **3단계 조회 범위**였다. Main은 번호를 짚고 사용자가 가리킨 조회 보호를 설명했다. cursor·snapshot·준비 ID·세션·checkpoint를 한 번에 제시했지만 사용자는 “이해가 뭔가 잘 안되네 reconcile 처럼 이해를 도와줘봐”라고 했다.

Main은 cursor부터 다시 설명하면서 전체 데이터를 매번 받는 비용을 출발점으로 삼았다. 이때 사용자가 기존 구현을 지적했다.

> 사용자: “근데 모든 경비를 받아오지 말아야 한다 하는데 지금도 그게 구현되어 있긴하지 않아? pull 동작에서?”
>
> Main: “기존 pull에도 ‘지난번 이후 바뀐 경비만 받아오기’가 이미 구현되어 있었어요. 이전 코드를 확인했고, 제가 새로 도입하는 기능처럼 설명한 건 잘못 짚었습니다.”

Main이 `44d2a5ef`의 서버·client 코드를 확인해 설명한 기존 흐름은 `lastSyncedAt`을 보내고 서버가 `updatedAt` 이후의 행을 반환한 뒤 응답 서버 시각을 다음 기준으로 저장하는 방식이었다. **새 증분 조회 도입이 아니라 이미 있는 증분 조회에서 늦게 확정된 변경을 놓치는 문제**로 출발점을 고쳤다.

설명용 예에서는 수정 시각이 10:01인 저장이 아직 확정되기 전에 pull이 실행되고, 폰은 10:03을 다음 기준으로 저장한다. 그 수정이 10:04에 확정돼도 행에는 여전히 10:01이 적혀 있어 다음 조회에서도 빠진다. 서버 시간이 틀려서가 아니라, 응답 시각까지의 모든 변경을 전달했다고 볼 수 없기 때문이다. reconcile은 받은 값을 반영하지만, 이 누락은 값을 받기 전의 문제다.

이 정정은 사용자가 기존 동작을 몰랐던 사례로 기록하지 않는다. Main이 사용자가 알고 있는 출발점을 실제 변경 이유와 맞추지 못했던 부분이다. [설명 참고](2026-11-13-10-code-explanation-as-shared-review.md)를 다시 볼 때, 필요성을 설명하는 일반론이 이번 변경의 실제 이유를 대체하지 않았는지 대조할 자료다.

## 105라는 경계의 근거와 받아들인 비용

Main은 설명용 DB 작업 번호 105·106·107을 사용했다. 번호가 먼저 붙은 105는 미완료이고 106·107은 확정된 상황이다. 지금 볼 수 있는 106·107은 보내되 다음 기준을 108로 넘기면 나중에 확정될 105를 놓치므로, 다음에도 105부터 조회하도록 남긴다는 설명이었다. 이 번호는 경비 ID나 편집 승자를 고르는 표식이 아니다.

> 사용자: “근데 105인건 뭘 보고 결정하는거야 여기서?”
>
> Main: “앞선 예시에는 ‘105보다 작은 번호의 작업은 모두 끝났고, 105는 아직 진행 중이다’라는 전제가 있었습니다. 제가 그 전제를 더 명확히 말했어야 했어요.”

수신한 경비 목록에서 105를 계산하는 것이 아니라 DB가 관리하는 트랜잭션 상태에서 경계를 받는다. 서버의 `pg_snapshot_xmin(pg_current_snapshot())` 결과를 `oldest`로 받고 `nextCursor`로 반환한다. 이 예에서 104 이하는 확정 또는 취소로 종료됐고 105가 미완료라는 전제가 있다. 103도 미완료라면 105가 아니라 더 이른 경계를 써야 한다. “미완료를 건너뛰지 않는다”는 의도만 말해서는 **그 미완료를 누가 어떻게 아는지**가 연결되지 않았다.

사용자는 이어 범위와 비용을 물었다.

> 사용자: “그럼 105가 계속 안 끝나면 106, 107은 pull 할 때마다 계속 받아오는 거야? 다른 사용자의 작업이어도?”

Main은 현재 방식이 그 반복을 허용한다고 답했다. 설명용 105가 다른 사용자의 오래 걸리는 작업이고 106·107이 내 활성 여행 경비라면, 타사용자의 데이터는 계정·여행 필터 때문에 받지 않는다. 하지만 그 미완료 작업은 DB 조회 경계에 영향을 주므로 내 106·107 결과를 다시 받을 수 있다. 새로 확정된 108·109까지 막는 것이 아니라, 새 변경을 받으면서 기존 일부도 반복해서 받는다.

이때 **DB의 조회 하한과 사용자별 전달 대상은 별개**다. “변경분만 받는다”는 말은 아직 한 번도 받지 않은 행만 받는다는 보장이 아니다. reconcile이 같은 경비를 중복 생성하지 않더라도 네트워크와 Local 반영 비용은 남는다. 이 대화에서 새 최적화 정책을 채택한 것은 아니며, 기존 설계의 비용을 명시했다. 105가 확정되거나 취소되면 뒤늦게 나타날 가능성이 사라지므로 다음 snapshot의 상태에 따라 기준도 전진할 수 있다.

## cursor를 저장해도 되는 시점과 기기 사본의 수명

Main은 서버가 40달러와 새 cursor108을 줬지만 Local 저장은 실패한 경우를 질문했다.

> 사용자: “로컬까지 성공ㅇㄹ 확인해야겠네”

Main은 응답 수신만으로 완료 기준을 전진시키지 않으며, Local 반영과 cursor 저장을 한 트랜잭션으로 묶어 둘 다 확정하거나 둘 다 되돌린다고 연결했다. 여기서 반영 성공은 서버 값 40이 화면에 그대로 보여야 한다는 뜻도 아니다. 미처리 35가 있다면 서버 확인본40과 Local35를 함께 저장하는 reconcile 결과도 정상 반영이다. 사용자는 이어 “그래 cursor는 이해됐어”라고 했다.

다음은 pull 대기 중 준비 해제·기기 사본 정리·재활성화가 일어나는 경우였다. 현재 활성 여부와 여행 ID만 보면 같은 여행을 다시 준비한 사본에 예전 응답을 넣을 수 있다. 요청 당시와 현재의 준비 ID를 비교해 그 수명을 구별한다.

> 사용자: “준비 ID가 무슨 기준으로 정해지는거지 그럼?”

Main은 활성화 시 `generateId()`로 새 식별자를 만들고 성공한 준비 정보에 저장한다고 설명했다. pull마다 만드는 값이나 경비 내용·cursor에서 계산하는 값이 아니다. 이미 활성인 준비는 유지하고, 해제 후 재활성화는 새 ID를 갖는다. 시간·크기의 우열이 아니라 동일성을 비교한다. 사용자는 곧바로 이 조건을 cursor와 연결했다.

> 사용자: “그럼 준비 ID가 달라서 예전 응답을 반영 안 하면 cursor도 그대로 두는 거야?”

현재 구현에서는 요청한 준비 범위를 온전히 반영하지 못했다면 그 응답의 새 cursor도 저장하지 않는다. 요청 당시와 현재의 활성 여행 집합·준비 ID가 모두 맞는지를 확인한다. 계정·활성 여행 집합이 같으면 저장된 cursor로 다시 조회할 수 있고, 조회 집합이 달라졌으면 저장 기준을 재사용하지 않고 전체 조회한다. 준비 ID가 바뀐 것과 cursor의 계정·여행 집합 범위가 바뀐 것을 구별했다. 사용자는 “그래 준비 ID도 이해됐어”라고 했다.

## 같은 응답을 받을 조건, 저장한 결과를 볼 조건

이후 설명은 앞에서 이해한 경계에 하나씩 연결했다. 다음은 실제 제품을 새로 바꾼 결과가 아니라 대화에서 풀어 설명한 현재 동작이다.

| 이어서 설명한 관계 | 상황과 구별 | 사용자 발화 |
| --- | --- | --- |
| 세션과 요청 수명 | A로 요청한 뒤 B로 로그인하거나 같은 A로 다시 로그인한 경우도 이전 세션 응답을 쓰지 않는다. 사용자 ID와 세션 ID를 확인하며 반영 트랜잭션 안에서도 검사한다. | “그래 세션 검사도 이해됐어” |
| 정상 지연과 잘못된 응답 | 준비 ID 변경은 정상 응답이 늦게 온 경우다. 형식·소유자·요청 여행 검증은 응답 자체가 계약을 어긴 경우를 막는다. 요청 여행 제한은 일정·경비에 적용하고 여행 기본 정보는 계정 전체 계약이다. | “그래 응답 검증도 이해됐어” |
| Local 저장과 화면 조회 | DB가40이어도 이전 조회 캐시가30일 수 있다. 기존 조회를 취소한 뒤 다시 읽도록 갱신하되, 새 화면 조회 완료가 Local·cursor 저장 성공의 조건은 아니다. | “그래 화면 갱신도 이해됐어” |

화면 예에서는 늦게 도착한 것이 서버 pull 응답이 아니라 **화면이 Local에서 읽던 이전 조회의 완료**였다. 서로 다른 비동기 작업을 같은 “늦은 응답”으로 뭉개지 않고 취소·갱신의 대상을 연결했다. 조회 실패가 이미 확정한 DB 저장을 되돌리는 것도 아니다.

사용자가 이제 다 설명했는지 묻자 Main은 기록·코드와 대조하고, 준비가 끝나도 받아들일 정보와 snapshot의 필요성이 충분히 설명되지 않았다고 밝혔다. 항목 이름을 앞에서 언급한 것만으로 설명 완료로 세지 않았다.

## 준비가 끝나도 삭제 사실을 받는 이유와 snapshot의 연결

삭제 설명에서는 기기 사본 정리와 서버의 Entity 삭제를 나눴다. 준비 해제는 기기 보관을 끝내는 것이고, 서버에서 삭제된 경비가 재준비로 되살아나는 것은 아니다. 이전 준비의 일반 본문은 새 사본에 넣지 않지만 검증된 삭제 정보는 별도로 반영한다. Local 행이 없다는 사실만으로 사본 정리와 서버 삭제를 구별할 수 없으므로 삭제 확인을 보존하고, 뒤늦은 살아 있는 본문이 되살리지 못하게 한다.

세션·응답 소유자·요청 여행 검사와 Local 귀속 모순 검사도 여전히 적용된다. 이 설명은 임의의 늦은 삭제 응답을 모두 신뢰하자는 새 정책이 아니다. 사용자는 “그래 삭제 정보는 이해됐어”라고 하고 snapshot을 같은 방식으로 설명해 달라고 했다.

snapshot에서는 동일한 105 예를 이어 썼다. 조회 경계를 잡을 때105는 미완료였지만 여행·일정을 읽은 뒤 경비를 읽기 직전에 확정되는 상황이다. 이번 pull은 `repeatable read`의 같은 snapshot을 유지하므로 그 새40은 이번 응답에 포함하지 않는다. 서버 저장이 실패한 것이 아니라 **이번 조회가 보는 상태에 포함되지 않는 것**이다. 다음 snapshot에서는 확정된40을 볼 수 있고, cursor105부터 조회하므로 놓치지 않는다.

| 구별 | 이 대화에서 연결한 역할 |
| --- | --- |
| snapshot | 이번 여행·일정·경비·조회 경계를 같은 DB 상태로 읽는다. |
| cursor | 이번에 못 본 변경을 다음 조회 범위에 남긴다. |

일정 삭제와 연결 경비의 `scheduleId` 해제를 서로 다른 시점에서 읽는 예도 사용했다. 트랜잭션으로 묶기만 하는 것이 아니라 읽기 기준을 유지하는 설정이 필요하며, “최신”은 응답 전송 직전까지의 변경을 모두 끌어모은다는 뜻이 아니라고 설명했다.

> 사용자: “그래 snapshot도 이해됐어 그럼 이제 3단계는 다 설명한 거지?”
>
> Main: “3단계의 목적과 핵심 동작은 이제 모두 설명했습니다.”

마지막으로 여행 삭제 반영이 활성 준비를 없앨 수 있어 cursor 저장 직전에 준비를 다시 읽는 연결을 덧붙였다. 구버전 호환·비정상 cursor 등 세부 분기는 남아 있다고 구별했다. 사용자별 이해 발화는 보존하되, 특정 질문이나 표만으로 이해를 만들어 냈다는 효과 입증이나 모든 분기의 이해 확인으로 확대하지 않는다.

## 다음 설명과 기록 범위

사용자의 “4단계도 많이 남았어?”에 Main은 전송 순서, 같은 요청 재전송에서 표식 유지, 서버의 항목별·동시 요청 판정이라는 세 묶음을 제시했다. 새 편집이 전송 도중 추가되는 상황도 첫 묶음에 속하며, 응답 뒤 완료 처리의 상세는5단계에서 잇는다고 예고했다. “3단계보다 새 개념이 적을 것”은 Main의 예상이지 확인된 설명 효과가 아니다. **4단계 상세 설명은 아직 미착수**다.
