# reconcile의 필요성과 실제 처리를 이해해 간 대화

2026-11-13. 사용자는 3단계 코드 설명에 이어 `reconcile`을 질문했고, 마지막에 “아 이해 됐다”면서 헷갈린 지점과 이해한 과정을 나중에 볼 재료로 기록해 달라고 요청했다. 여기서 사용자가 말한 **“3, 4”는 앞선 설명의 구획**인 pull 수신과 push 응답의 Local 보존 문제다. Ticket09의 3·4단계를 다시 구현하라는 뜻이 아니다.

## 이후 설명에서 다시 볼 요지

이 대화는 원하는 정책 결과를 아는 것과 그 결과를 만드는 기술적 연결을 아는 것이 다름을 드러냈다. 사용자는 항목별 최신 편집 정책을 이해했지만, 이미 Repository에서 저장한 Local 값에 왜 `reconcile`이 다시 관여하는지, 온라인 push 뒤에도 왜 큐가 남는지를 물었다. Main이 과거 합의 여부나 원하는 결과부터 답했을 때는 그 연결이 채워지지 않았다. 이후 같은 편집 이력을 놓고 **어느 요청의 처리가 확인됐는지, 어느 저장소를 언제 바꾸는지, 이번 push가 선택한 요청에 무엇이 포함되는지**를 나눠 설명했다.

이를 다시 참고할 때는 다음 관계를 당시 코드와 대조한다. 고정 문답이나 모든 설명에 적용할 절차는 아니다.

- “더 나중의 편집을 보존한다”는 정책 직관만으로 Local 보존 이유를 설명하면, 서버에서 더 최신인 값을 받아도 이전 Local 값이 잠시 남는 경우가 모순처럼 보인다. 이 구현에서 미처리 입력을 겹치는 것과 서버가 표식으로 최종 채택값을 정하는 것은 다른 판단이다.
- 같은 응답 값도 특정 요청의 완료를 확인하는 push 응답인지, 그 요청의 완료를 뜻하지 않는 pull인지에 따라 Local과 큐의 결과가 다르다. 값만 나열하지 말고 그 응답이 확인해 주는 사건을 연결할 필요가 있었다.
- “중간 조정”, “화면에서 사라짐”은 실제 저장 연산을 대신하기에 모호했다. 이미 저장된 Local을 다시 구성하는 이유와, 서버 응답을 무시하거나 그대로 덮는 대안을 비교하면서 무엇이 없어지는지를 구체화했다.
- 설명용 상황도 실제 실행 순서를 만족해야 한다. B가 push 목록을 얻은 뒤 추가됐다는 조건을 빠뜨려 사용자의 반례가 생겼다. 이때 예시를 방어하지 않고 실제 코드를 확인해 조건을 고쳤다.

사용자가 마지막에 이해됐다고 말한 사실은 보존한다. 다만 표 하나나 질문 하나의 효과가 입증됐다고 단정하지 않는다. 표를 본 뒤에도 필요성·실제 처리·전송 시점에 대한 질문이 계속됐고, 여러 정정을 거쳐 사용자가 자신의 말로 다시 설명했다. 이번에는 사용자가 질문도 해 달라고 요청했지만, 이를 일반적인 퀴즈나 반복 질문 방식으로 올리지 않는다. [앞선 설명 참고](2026-11-13-10-code-explanation-as-shared-review.md)와 함께, 실제 질문의 공백을 어떻게 찾았는지 재검토할 자료다.

## 정책 결과와 미처리 입력 보존을 섞어 답한 부분

앞서 Main은 사용자가 설명 구획 3·4를 당시 논의했는지 묻자 과거 승인 여부를 조사해 답했다. 그러나 사용자는 기술적 연결을 다시 이해하려는 뜻으로 바로잡았다.

> 사용자: “아니 2번에 편집 표시나 이런거 ㄴ 이해 되는데 3,4 번에 보면 push pull에서 어떻게 해야지 저 기능과 목표가 되는건지는 잘 기억이 안나 그래서 다시 좀 설명해주고 이해를 이끌어봐 질문도 하고”

Main은 A의 30달러 요청을 기다리는 중 B로 35달러를 저장한 상황을 제시했다. 사용자는 “B가 직전 편집 그러니까 제일 최신 편집이니까 이걸 따라야 한다”고 답했다. Main도 처음에는 “B가 사용자가 더 나중에 저장한 편집이므로” 35달러가 유지된다고 설명했다. 이는 사용자의 정책 직관과 클라이언트의 미처리 입력 보존 이유를 충분히 구별하지 않은 답이었다.

태블릿 C가 그보다 나중에 40달러를 편집했다는 상황이 더해지자 사용자는 결과는 40일 것 같지만 “정확히 설명이 안되네”라고 했다. Main은 다음과 같이 정정했다.

> Main: “제가 앞서 ‘B가 더 최신이니까 35달러를 보존한다’고 말한 것은 사용자 의도에 대한 설명이었고, 구현에서 더 직접적인 이유는 B가 아직 처리되지 않은 요청이라는 점입니다.”

사용자가 같은 표식 사례를 나란히 비교해 달라고 요청해, 다음 설명용 이력을 유지했다. A=폰 30달러·9시, B=폰 35달러·10시, C=태블릿 40달러·11시다. 이는 실제 실행 측정값이 아니라 관계를 비교하기 위한 예다. 실제 표식은 시각 외 정보도 포함한다.

| 받는 응답 | 확인된 완료 요청 | 저장한 서버 확인본 | Local 표시값 | 남은 큐 |
| --- | --- | --- | --- | --- |
| A의 결과 30 | A | 30 | 미처리 B를 겹친 35 | B |
| C가 반영된 pull 40 | 없음 | 40 | 미처리 B를 겹친 35 | B |
| B의 결과 40 — 서버가 C를 유지 | B | 40 | 40 | 없음 |

B 요청이 완료됐다는 것과 B의 35가 서버에서 채택됐다는 것은 다르다. 두 번째 줄의 35는 최종 승자를 뒤집은 결과가 아니라 B 처리 확인 전의 Local 상태다. 이 표의 **pull 때 B가 남는 조건은 뒤에서 수정됐다**. 처음 설명에는 B의 추가 시점이 없었다.

사용자는 “reconcile이 최종승자를 결정하는 건 아니고 서버가 할거지만 중간 조정을 해주는거네?”라고 정리하면서도 “왜 필요하지”, “무슨 처리를 해주는건지”를 다시 물었다. 이 시점은 개념 전체를 이해했다고 처리할 수 없었다.

## 이미 Local에 저장한 B를 왜 다시 다루는가

> 사용자: “그럼 애초에 리포지터리에서 로컬 쪽에서 데이터를 저장하지 않아? B에 대한 헤깔리네”
>
> Main: “B의 35달러는 저장 버튼을 눌렀을 때 이미 Local에 저장돼 있습니다. reconcile이 B를 처음 저장하는 것이 아닙니다.”

Main은 서버 확인본, 화면 조회에 쓰이는 Local 경비 행, 미처리 요청 큐를 나눴다. B를 저장할 때 Local 금액을 35로 바꾸고 금액 변경 요청도 큐에 넣는다. 이후 서버의 40달러·교통을 받으면 서버 확인본에는 그 응답을 저장하고, Local에는 미처리 B의 금액 35를 겹쳐 35달러·교통을 만든다. 이미 저장한 B를 새 입력으로 다시 추가하거나 UI를 직접 그리는 처리가 아니다. Local 행만으로는 어떤 항목이 미처리 사용자 입력인지 알 수 없어 큐에 기록된 변경 항목을 사용한다.

현재 [expense-local.ts](../../../../../apps/client/src/entities/expense/lib/expense-local.ts)의 `updateExpenseLocal`은 Local 갱신과 큐 추가를 같은 트랜잭션에서 수행한다. [reconcile.ts](../../../../../apps/client/src/shared/services/sync/reconcile.ts)의 `projectPendingChanges`는 완료 요청을 제외하고 남은 입력을 겹치며, `acknowledgeCompletedTask`는 해당 완료 요청을 삭제한다. 이 사실은 설명과 관련된 부분만 직접 읽어 대조했다.

## push 뒤에도 B가 남는 조건을 빠뜨린 정정

> 사용자: “서버에서 40달러 교통 수신후 라고 한다면 온라인이 되었다는거고 B 큐가 저렇게 남아있나? 이미 나가고 없는거 아닌가?”

Main은 실제 코드를 읽은 뒤 앞선 예의 누락을 인정했다.

> Main: “B가 동기화 시작 전에 이미 큐에 있었고 정상 처리됐다면, 그다음 pull 시점에는 B가 없어야 합니다. 제가 앞선 예에서 B가 언제 추가됐는지를 빠뜨려”

[engine.ts](../../../../../apps/client/src/shared/services/sync/engine.ts)의 `pushChanges`는 전송할 목록을 한 번 얻은 뒤 그 배열을 순회한다. `syncData`는 push를 기다린 다음 pull을 호출한다. 따라서 앞의 예가 성립하는 순서는 다음과 같다.

1. 이번 push가 얻은 목록에는 A만 있다.
2. A 응답을 기다리는 동안 사용자가 B를 저장해 Local과 큐에 반영한다.
3. A를 완료해도 B는 이미 얻은 배열에 없으므로 이번 push에서 보내지 않는다.
4. 뒤이은 pull이 40달러·교통을 받는 동안 B는 남아 있고, 다음 동기화의 전송 대상이 된다.

B가 시작 목록에 있었고 정상 처리된 경우까지 B가 남는다고 설명하면 틀린다. 실제 전송 실패로 push가 throw한 경우도 위 예와 다르다. 그 실행은 이어서 pull하지 않는다. 온라인이라는 사실만으로 활성 여행의 저장이 Local·큐를 건너뛰는 것도 아니다. 이는 설명용 예시의 조건 정정이며 새 동작을 구현하거나 재현 시험한 결과가 아니다.

## “화면에서 사라짐”과 실제 덮어쓰기의 구별

> 사용자: “필요성은 일단 이해했고 역할 면에서 다시 궁금한게 reconcile이 없었다면 화면에 왜 금액이 안나온다는건지 알려줘”
>
> Main: “reconcile이 없어서 금액이 화면에 안 나오는 것은 아닙니다.”

Main이 앞서 B가 판단받기 전에 “사용자 화면에서 사라지는 것”이라고 말한 것은 금액 칸이 비는 것처럼 읽힐 여지가 있었다. 의도한 문제는 **서버 응답을 그대로 Local에 저장하면 이미 표시하던 B의 35가 40으로 바뀐다는 것**이었다. 단지 reconcile을 제거하고 아무 저장도 하지 않는다면 기존 35는 그대로 보인다.

35달러·식비 Local에 서버 40달러·교통을 받는 예를 세 대안으로 비교했다. 응답을 그대로 덮으면 40달러·교통이 되어 미처리 B의 표시가 사라지고, 반영을 아예 하지 않으면 35달러·식비로 남아 서버 분류 변경을 놓친다. 서버 값을 기반으로 남은 B의 금액을 겹치면 35달러·교통이 된다. 이 대비는 선택의 필요성을 설명한 것이며 다른 UX 정책이 불가능하다는 증명은 아니다.

사용자는 다른 항목인 교통은 Local에 반영하고, 서버 판단을 받아야 할 B는 큐에 남겨 자연스럽게 전송하게 하는 것으로 재진술했다. Main은 그 설명을 **pull의 일반 수정 상황**으로 한정해 확인했다. 클라이언트가 표식을 비교해 승자를 정하는 것이 아니라 큐의 변경 필드를 겹치며, 서버에서 받은 교통을 반영한다고 새 큐를 만들지 않는다. push 응답은 완료한 요청을 겹치기에서 제외하고 큐에서도 삭제한다. “큐를 안 건드린다”를 삭제 확인을 포함한 모든 reconcile 경로로 넓히지 않았다.

> 사용자: “아 이해 됐다 그 3,4 이해 안간다면서 reconcile에 대해서 논의 지금까지 한것들 잘 기록해두자 내가 헤깔리고 어떻게 이해 됐는지 여러 사항들 좋은 재료일것 같아 나중에”

이 발화를 이해의 명시와 기록 요청으로 남긴다. 새 정책 승인, 사용자 능력에 대한 평가, 제품 전체의 최종 수락으로 확대하지 않는다. 4〜7단계의 추가 상세 설명 요청은 없었다.
