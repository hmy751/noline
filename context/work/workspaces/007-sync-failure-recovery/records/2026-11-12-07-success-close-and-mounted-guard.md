# 제출한 값의 저장 성공 후 닫기로 확정하고 성공 처리를 간결화

[닫기 안내와 추가 입력 검토](2026-11-12-06-pending-close-notice-and-input-gap.md)의 미정은 사용자 선택으로 정리됐다. 사용자는 “아냐 그냥 닫는걸로 해 성공하면 그것도 충분해보여 그래도 동작 자체 는 문제 없잖아”라고 결정했다. **저장 버튼을 누른 때의 값이 저장되면 닫고, 대기 중 추가로 고친 값은 저장하거나 보존하지 않는다.** 이는 후속 입력 손실을 새 보존 기능으로 해결한 것이 아니라, 사용자에게 결과를 설명하고 성공 후 닫기를 선택한 것이다. 별도 초안 저장소·입력 잠금·추가 입력 감지·자동 재저장은 추가하지 않았다.

사용자는 이어 “이 결정으로 인해 간결화 될부분도 보고 isCurrentEidt 도 필요한지” 점검하도록 요청했다. Main은 실제 ScheduleScreen·ExpensesScreen의 `onClose`가 열림 상태를 false로 만들고 선택 항목도 null로 지우는 것을 확인했다. 따라서 성공 후 같은 폼이 계속 열릴 수 있다는 가정으로 남긴 두 폼의 `reset(data)`와 일정의 `setEditingBaseline`을 제거했다. 성공하면 폼은 사라지고 다시 열 때 저장된 값으로 새 폼을 만든다. 경비 원본·일정 원본과 시간대를 처음 값으로 고정하는 snapshot state는 배경 조회에 따른 입력 기준 변경을 막는 실제 역할이 있어 유지한다.

`isCurrentEdit`는 **`isMounted`로 이름을 바꾸고 검사를 유지**했다. 같은 폼에서 제출 뒤 값이 달라졌는지를 판별하는 장치가 아니라 비동기 검증·응답이 끝났을 때 그 폼이 아직 존재하는지 보는 값이다. 해제 뒤에는 새 입력의 저장·알림·닫기·오류 표시를 실행하지 않는다. 읽기 전용 후속 검토도 reset 제거가 실제 소비자와 맞고 post-await/global Alert 제한은 남을 역할이라고 판단했다.

실제 root Stack의 userId key·계정 변경/세션 소실 뒤 이동처럼 화면 자체가 바뀌는 경계는 Drawer의 닫기 차단과 별개다. **토큰 재인증이 언제나 곧 폼 unmount라는 뜻은 아니다.** 이미 시작한 데이터 저장·일정 경로 후처리와 사라진 폼의 UI 접근도 구별한다. 저장 중 닫기 시도의 안내, RHF isSubmitting, FIFO·표식·그룹·DB·서버 계약은 유지한다.

기존 빈 onClose 대역을 둔 채 같은 폼을 재저장하던 검사 두 개는 실제 부모가 성공 후 닫고 저장된 값으로 재열기하는 흐름으로 바꿨다. 양쪽 폼에 저장 대기 중 추가 입력이 있어도 제출값을 한 번 저장하고 성공 후 닫는 검사 두 개를 추가했다. 같은 폼 추가 입력 보존을 기대하는 검사로 해석하지 않는다.

Main 자기 확인과 별도 검증자는 각각 관련 **2묶음 41/41**을 통과했다. 같은 사례의 재실행이므로 합산하지 않는다. 독립 검증은 불충족을 발견하지 않았다. lint는 오류 0·기존 색 경고 16개이며 타입 로그는 직전 닫기 안내 판과 완전히 같아 기존 오류 7개만 남는다. Main은 차이 검사를 통과했고 관련 Project 설명과 낡은 날짜 설명도 실제 소스에 맞췄다고 연결했다. 기록 담당자는 두 Drawer·실제 두 Screen 소비자·현재 검사 이름과 실행 로그·타입 로그 동일성을 직접 대조했으며 제품·Project를 수정하거나 검사를 재실행하지 않았다.

이번 **사용자 선택에 따른 UI 간결화 수정·관련 자동/독립 검증은 완료**다. 앞선 전체 853개·서버·PostgreSQL을 이번에 재실행하지 않았다. 네이티브 수정창 열기·닫기·재열기와 기기 제스처·애니메이션 확인은 계속 남는다. 사용자 제품 수락·커밋·push·배포는 미실행이다. 이전 기록의 미정·재현은 당시 근거로 보존하고 현재 입력 처리 선택은 이 기록을 따른다.
