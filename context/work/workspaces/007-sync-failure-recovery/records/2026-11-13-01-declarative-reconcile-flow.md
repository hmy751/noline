# reconcile 본문에서 판단·반영·완료 범위를 드러내기

[첫 책임 분리](2026-11-12-14-reconcile-refinement-and-preserved-behavior.md) 뒤에도 사용자는 실제 코드의 예외 조건이 많아 핵심 흐름과 범위를 읽기 어렵다고 했다. Main은 처음에는 실제 파일을 바꾸지 않고 핵심 뼈대를 설명했다. 그 과정에서 pull에도 마지막 ACK가 공통으로 실행되는 것처럼 보이는 설명을 바로잡았다. **pull은 특정 push 요청을 완료하지 않으며, 값이 같다는 사실만으로 큐를 제거하지 않는다.** push 응답에서 전달한 완료 ID가 있어야 해당 요청을 ACK한다.

## 요청과 채택 범위

사용자의 직접 요청은 다음과 같다.

> reconcile 코드를 어느정도 선언적으로 해줄수 없어? 너무 많으니까 뭔지 헤깔려 범위 구분도 안되고

> 그리고 개행 좀 신경쓰고 코드 스타일

Main은 상태 읽기 → 서버 수락 판단·저장 → Local 반영 판단·실행 → 완료 요청 ACK가 본문에 보이는 구조안을 제시했다. 당시에는 설명용 보조 함수와 타입이며 실제 파일은 수정하지 않았다고 구별했다. 사용자는 이어 “그래 수정해봐”라고 승인했다. 이후 사용자는 “마지막으로 코드스타일 에어비앤비 가이드 따라서 잘 읽히기 쉽게 해주고”라고 추가했다.

이번 변경의 목표는 전체 파일의 줄 수 감소가 아니라 **수신 본문에서 어떤 판단과 DB 변경이 끝났고 무엇을 완료하는지 읽히게 하는 것**이다. 세부 정책은 관련 helper로 내려가 확인하되, 함수 이름만 늘리거나 정상 보존과 예외 rollback을 같은 결과로 숨기지 않는다. 선언·검사·실행 경계의 빈 줄도 실제 코드에 적용한다. 스킬·Personal의 지속 기준이나 009의 루프 개선을 갱신하는 요청으로 확대하지 않는다.

## 구현에서 유지할 대응

| 기존 조건·효과 | 선언적 흐름에서 유지할 의미 |
| --- | --- |
| 수락한 서버 판본보다 오래된 응답 | 기존 서버 확인본을 재사용하고 새 원본 저장은 생략한다. |
| 자기 기록·부모 여행의 서버 삭제 증거 | Local을 되살리지 않으며 완료 ID가 있으면 그 요청만 종결한다. |
| 최신 본문이 없고 재입수에 필요한 원본도 없음 | 필요한 오류를 전달한다. 정상 보존으로 삼지 않는다. |
| 부모 여행의 Local 숨김·미전송 삭제 | 새 서버 원본은 수락할 수 있지만 자식 표시와 다른 미완료 입력을 보존한다. |
| 손상 JSON·투영할 내용 없는 UPDATE | Local 표시 쓰기만 생략한다. 수락한 서버 원본과 이번 완료 요청 처리는 확정한다. |
| 서버에서 삭제 확정 | 삭제 본문을 저장한 뒤 기존 확정 삭제 정책을 실행한다. 큐 정리 조건은 바꾸지 않는다. |
| 저장이나 ACK 실패 | 같은 트랜잭션의 서버 확인본·Local·큐 변경을 되돌리고 예외를 전달한다. |
| pull에 완료 요청 ID가 없음 | ACK는 아무 큐 행도 제거하지 않는다. 서버값과 큐값의 동일 여부로 완료를 추정하지 않는다. |

수신 함수가 끝에서 ACK를 한 번 호출하도록 바뀌더라도 `finally`에서 실행하지 않는다. 정상 보존은 끝까지 이어지고 예외는 ACK를 건너뛰어 호출자의 rollback으로 전달되어야 한다. 편집 시계 관찰 등 DB 밖 효과까지 rollback된다는 보장은 추가하지 않는다.

## 실제 수정·검토·검증

Main이 [reconcile.ts](../../../../../apps/client/src/shared/services/sync/reconcile.ts) 한 파일을 수정했고 이번 2단계 후속의 구현·개선 검토·독립 검증을 완료로 판단했다. 소비자·공개 API·DB schema는 바꾸지 않았다. 이전 원본은 `/tmp/noline-reconcile-declarative-before/reconcile.ts`, 이번 차이는 `/tmp/noline-declarative.patch`다. 전체 파일은 257→344행으로 늘었다. 중간 결과 타입과 helper가 늘어나는 비용을 받아들여, 상단의 여섯 호출만으로 준비 → 서버 판단·저장 → Local 판단·반영 → ACK가 보이게 했다. 전체 줄 수 감소나 예외 정책 제거를 개선 근거로 삼지 않는다.

`ServerAcceptance`는 수락·재사용·보존을, `LocalDecision`은 보존·쓰기·확정 삭제를 표현한다. ACK는 본문 끝의 한 정상 경로에서 호출하며, 완료 ID가 없는 pull과 예외 경로에서는 큐를 제거하지 않는다. 새 함수들은 같은 파일에 두고 기존 트랜잭션과 실제 처리 순서를 유지했다.

개선 검토자 `/root/review_declarative_reconcile`는 책임 구분의 이득과 중간 타입의 비용을 대조해 필수 수정 문제는 없다고 반환했다. `readReconciliationState`에는 편집 시계 관찰의 외부 효과도 포함되므로 `prepareReconciliationState`가 더 정확하다는 제안을 Main이 채택했다. 명칭만 바꾸고 관찰·계정 재확인·조회 순서는 유지했다.

사용자의 추가 스타일 요청에 따라 Main은 [Airbnb JavaScript 가이드](https://github.com/airbnb/javascript)의 블록 규칙, 7.15 여러 줄 인자, 19.7 블록 뒤 빈 줄, 19.8 블록 안 padding 금지, 19.9 연속 빈 줄 금지를 직접 확인했다. 기존 formatter의 120열 설정을 유지하고 관련 선언·검사·실행 경계를 정리했다. 전역 설정이나 Airbnb ESLint preset을 새로 도입하지 않았다. 변경 파일 lint와 추가 CLI 규칙 `padding-line-between-statements`·`padded-blocks`·`no-multiple-empty-lines`는 **오류 0·경고 0**이다(`/tmp/noline-declarative-style.log`).

Main은 기존 관련 검사 8묶음을 최신판에서 다시 실행해 **158/158 통과**를 확인했다(`/tmp/noline-declarative-tests.log`). 이번에는 지속 테스트를 추가하지 않았다. 타입 검사는 기존 오류 7개이며 `/tmp/noline-declarative-types-before.log`와 `-after.log`가 완전히 같다. 이번 기록 갱신 시 harness는 다시 실행하지 않았으므로 이전 64개 링크 문제를 이번 실행 결과로 세지 않는다.

독립 검증자 `/root/verify_declarative_reconcile`는 별도 probe **9개를 직접 실행해 모두 통과**했다. 근거는 `/tmp/noline-independent-central-ack-probe.ts`와 `.log`이며 repository의 임시 검사 파일은 제거했다.

- 자기 삭제 증거·부모 삭제 증거·최신 본문 없음·Local 부모 숨김·손상 pending의 다섯 정상 보존 상황에서 pull은 모든 큐를 보존하고 push 응답은 완료 ID만 제거했다.
- 서버 원본 수락 뒤 부모 귀속 모순으로 예외가 발생하면 서버 확인본과 완료 요청 등 DB 상태가 rollback됐다.
- FIFO의 미완료 상태와 원시 표시값 보존, 필요한 최신 본문이 없을 때 오류와 보존, 정상 keep-local과 ACK 실패 시 rollback의 차이를 확인했다.

검사는 Node 메모리 SQLite와 대체된 외부 경계에서 수행했다. **native·실제 HTTP·UI 렌더링·앱 종료/재시작은 이번에 확인하지 않았다.** 이전 158개·독립 3개와 이번 158개·독립 9개를 합산하지 않는다. 이번 결과 설명 뒤 다음은 3단계이며 아직 착수하지 않았다. 스킬·Personal·009·제품 커밋·push·배포는 변경하거나 완료하지 않았다.

## 입력 범위

기록 담당은 상속된 Main 대화의 첫 책임 분리 결과, 코드 설명·뼈대 요청, pull과 ACK 설명 정정, 선언적 구성·개행 요청과 “그래 수정해봐” 승인까지 직접 읽고 기존 14번 기록·Ticket09·current를 대조했다. 추가 Airbnb 요청 원문과 검토 결과는 Main이 후속 메시지로 전달했다. 현재 코드·158개 실행 로그·독립 9개 로그·스타일 로그를 직접 대조하고 타입 전후 로그 동일함을 확인했다. 이 열람을 기록 담당의 제품 검사 재실행으로 세지 않는다. 별도 rollout 전체를 복원한 것으로 기록하지 않는다. 제품 구현·검사 실행·완료 판정은 Main과 배정된 검토·검증 담당자의 책임이다.
