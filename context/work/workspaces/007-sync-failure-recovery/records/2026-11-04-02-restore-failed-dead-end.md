# 2026-11-04 — 복원 실패 화면과 데이터 삭제만 남는 막힘 재현

사용자가 "로그인할 때 버튼이 이상하다"고 한 화면을 찾다가, 원인에 따라 데이터 삭제 말고는 빠져나갈 수 없는 경로를 확인한 기록이다. 1.1.0 (13)은 심사 대기 중이고 자동 출시라, 통과하면 이 동작이 그대로 공개된다.

## 결론

- 사용자가 기억한 화면은 세션 만료가 아니라 **복원 실패(`restore-failed`)** 화면이다.
- 큐 작업의 원본 행이 없으면 복원도 로그인도 거절되고, 남는 길은 "기기 데이터 정리하고 로그아웃"뿐이다. 시뮬레이터에서 사용자가 직접 로그인해 거절을 확인했다.
- 1.0.1 기기에 이 상태가 생길 수 있는 경로가 코드에 있다. 다만 조건 세 개가 겹쳐야 하고, 실제 사용자 중 몇 명이 해당하는지는 모른다.
- 수정은 시작하지 않았다. [Ticket 08](../current/memory/tickets/08-orphaned-queue-task-blocks-login.md)이 맡는다.

## 화면을 찾은 과정

**1차: 세션 만료로 재현했으나 다른 화면이었다.** 사용자는 "기존 계정에 데이터가 있고 앱을 다시 업데이트하든 뭔가 로그인을 다시 하는 상황을 만들어봐"라고 요청했다. 로컬 DB에서 테스트 계정의 refresh token 행을 백업 뒤 지우고 앱을 다시 켰다. 동기화가 인증 실패로 끝나고 주황 배너가 떴다. 서버 로그에는 상태 코드가 없어 401은 route 코드를 읽어 판단한 것이다.

배너의 "재로그인"을 누르면 로그인 화면 위에 배너가 그대로 남는다. 위에서부터 "여행으로 돌아가기"(진한 초록), 안내문, "기기 데이터 정리하고 로그아웃"(흐린 초록), "Google로 계속하기"(흐린 테두리), "Apple로 로그인"(검정)이 나온다.

스크린샷: [세션 만료 뒤 로그인 화면](../../../../../artifacts/2026-11-04-login-screens/session-expired-login.png), [세션 만료 홈](../../../../../artifacts/2026-11-04-login-screens/session-expired-home.png), [데이터 삭제 확인 창](../../../../../artifacts/2026-11-04-login-screens/cleanup-dialog.png)

**사용자 정정.**

> "나는 저 주황색 배너는 없었고 첫번재 처럼 두개가 나왔어 근데 다 눌렸던 기억이야 버튼들이 상단도 눌리고 구글로 계속하기도 눌리고 루그아웃 등"

**2차: 복원 실패 화면이 맞았다.** 코드에서 배너 없이 버튼 두 개가 나오는 상태를 찾아, 시뮬레이터 DB를 백업하고 비활성 여행 한 건의 소유자 값만 바꿔 앱을 켰다.

스크린샷: [복원 실패 화면](../../../../../artifacts/2026-11-04-login-screens/restore-failed-login.png)

| 버튼 | 모양 | 눌렀을 때 (담당자 확인) |
| --- | --- | --- |
| 복원 다시 시도 | 진한 초록 | 진행 표시나 안내 없이 같은 화면 |
| 기기 데이터 정리하고 로그아웃 | 흐린 초록 | 삭제 확인 창 (취소함) |
| Google로 계속하기 | 흐린 테두리 | 시스템 로그인 창 (취소함) |
| Apple로 로그인 | 검정 | 누르지 않음 |

사용자는 "실제 기기에서도 흐리지만 눌렸어"라고 확인했다. 흐린 버튼이 꺼져 있다던 Main의 앞선 설명은 틀렸다.

그때 실제 기기에서 왜 이 화면이 떴는지는 **모른다**. 아래 재현은 같은 화면을 인위적으로 만든 것이다.

## 원인별로 빠져나갈 길이 다르다

[auth.ts](../../../../../apps/client/src/shared/store/auth.ts)의 `readSession`은 세션을 읽고 [local-account.ts](../../../../../apps/client/src/shared/services/auth/local-account.ts)의 `inspectLocalAccount`로 기기 데이터의 소유자를 검사한다. 로그인(`saveAndApplySession`)도 같은 검사를 다시 한다.

| 원인 | 복원 다시 시도 | 로그인 | 남는 길 | 근거 |
| --- | --- | --- | --- | --- |
| 저장된 로그인 정보를 읽지 못함 | 실패 | 같은 계정이면 가능 | 다시 로그인 | 코드 읽기 |
| 기기에 다른 계정 데이터가 섞임 (`different`) | 실패 | 어느 계정이든 거절 | 데이터 삭제 | 복원 실패는 재현, 로그인 거절은 코드 읽기 |
| 큐 작업의 소유자 확인 불가 (`unresolved`) | 실패 | 거절 | 데이터 삭제 | 재현과 사용자 로그인으로 확인 |

삭제하면 미전송 변경도 사라진다. 서버에 있는 내용은 다시 받을 수 있다. [앱 실행 기준](../../../../project/current/app-runtime/INDEX.md)은 `restore-failed`를 "복원 재시도 또는 계정 검사를 거치는 로그인으로 해결한다"고 설명하는데, 아래 두 경우에는 맞지 않는다. Project 문서는 고치지 않았다. Main이 처음에 Ticket 08의 완료 조건으로 넣었다가, 사용자의 "project는 확실한게 아닌데 왜 넣으려고 하지?"로 뺐다. 처리 방법과 1.0.1 경로의 실제 여부가 확정된 뒤 사용자 요청이 있을 때 별도로 판단한다.

## 1.0.1 기기에서 생길 수 있는 경로

1.0.1은 2026-02의 `496f8b45`이고, 소유자 검사는 2026-09-22의 `62ce2267`에 들어왔다. 그래서 1.0.1 사용자가 1.1.0으로 업데이트하면 이 검사를 처음 거친다. 1.0.1 코드를 Main이 읽어 판단했고 실행하지는 않았다.

1.0.1의 정리 작업(vacuum)은 지운 지 7일이 넘은 일정·경비를 큐가 가리키는지 보지 않고 완전히 삭제한다.

```ts
// 1.0.1 cleanup-job.ts
await db.delete(schedules).where(and(isNotNull(schedules.deletedAt), lt(schedules.deletedAt, thresholdISO)));
```

현재 코드는 큐가 가리키는 행을 지우지 않으므로 새로 생기는 문제는 아니다. 1.0.1 때 이미 어긋난 기기가 대상이다. 겹쳐야 하는 조건은 다음과 같다.

1. 일정이나 경비를 지웠는데 삭제 작업이 서버로 가지 못했다. 1.0.1은 FAILED 작업을 다시 보내지 않고 큐에 남긴다.
2. 그로부터 7일 넘게 지났다.
3. 그 뒤 다른 여행을 미전송 변경이 있는 채로 비활성화했다. 1.0.1의 vacuum은 정리 대기 여행(`cleanupPending`)이 있을 때만 돈다.

다른 두 원인은 1.0.1 업데이트로 생길 가능성이 낮다고 봤다. 세션 만료 때 토큰을 지우지 않고 지울 때는 한 번에 지우며, 로그아웃과 계정 전환 때 DB를 지우기 때문이다. 다만 저장된 사용자 ID 없이 DB만 남은 기기에서는 정리 없이 로그인하므로 데이터가 섞일 수 있다.

## 재현과 사용자 확인

담당자가 앱을 끄고 DB를 백업한 뒤, 미전송 작업이 가리키는 일정 한 행만 지웠다. 큐 작업은 그대로 뒀다. 앱은 복원 실패 화면으로 시작했고 "복원 다시 시도"를 눌러도 같은 화면이었다. 이어 사용자가 같은 계정으로 Google 로그인을 시도했다("지ㅁ 로그인 했어 에러뜨네").

스크린샷: [로그인 거절](../../../../../artifacts/2026-11-04-login-screens/restore-failed-login-refused.png)

- 오류는 "저장된 변경의 소유자를 확인하지 못했습니다. 데이터는 보존됩니다."이고, 다음에 무엇을 할지는 알려 주지 않는다.
- 서버 로그에는 Google 로그인 성공 뒤 `POST /api/auth/logout`이 남았다. 앱이 기기 검사에서 거절한 뒤의 요청으로 보이며, 호출 지점은 확인하지 않았다.

**재현의 한계**
- 1.0.1에서 실제로 업데이트한 것이 아니라 그 결과로 생기는 DB 상태만 만들었다.
- 삭제 작업이 아니라 생성 작업으로 재현했다. 코드는 원본 행이 없으면 작업 종류를 보기 전에 판단을 끝내므로 같은 경로로 봤지만, 삭제 작업으로 실행하지는 않았다.
- 실제 사용자 중 해당 기기 수와, 사용자가 예전에 겪은 화면의 원인은 모른다.

## 1.1.0 (13)에 대한 판단

Main은 철회할 정도는 아니라고 추천했다. 조건이 좁고 삭제라는 출구가 있기 때문이다. 1.0.1 실사용자 수를 Main은 모르므로 사용자 판단이 남아 있다. 사용자 결정은 아직 없다.

## 재현 뒤 상태

- **시뮬레이터 DB:** 백업으로 되돌렸고 `cmp`로 같음을 확인했다. 일정 6개, 큐 작업 1개다.
- **앱:** 세션 만료 배너가 뜬 홈이다. 다시 로그인하면 시험용 일정 "표시 확인용"이 로컬 서버로 전송된다.
- **로컬 서버 DB:** 테스트 계정의 refresh token 행을 지웠다. 되돌리지 않았다. 앱이 기기의 토큰도 지우므로 다시 로그인하면 새 행이 생긴다.
- **임시 자료:** DB·토큰 백업은 세션 임시 폴더에 있어 재시작하면 사라진다. 스크린샷 5장은 사용자 지시로 git 밖의 [artifacts 폴더](../../../../../artifacts/2026-11-04-login-screens/)에 두고 링크만 잇는다. 다른 체크아웃에서는 열리지 않는다. 아래쪽 어두운 막대는 개발 빌드의 로그 알림이다.
- **로컬 스택:** Mac 재시작으로 꺼져 Main이 Postgres, API 서버, Metro를 다시 켰다. 운영 서버와 운영 DB에는 접근하지 않았다.
