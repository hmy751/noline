# Ticket 06의 Release 빌드와 로컬 진단 수신 확인

2026-11-09 Main이 `feat/007-sentry-diagnostics`에서 앱·서버의 Sentry SDK가 보낸 진단을 로컬 수신기로 받았다. 앱에서 선택한 신호가 언제 남고 동기화 큐는 어떻게 변했는지를 함께 대조했다. Sentry Cloud 계정의 수집 주소(DSN), 관리 화면, 소스맵 업로드와 알림은 이 검사에 사용하지 않았다.

## 빌드와 검사 범위

Expo 51용으로 먼저 시도한 React Native SDK 5.24.3은 iOS 의존성 Sentry Cocoa 8.36의 `vector<const …>` 컴파일 오류로 Xcode 26.5에서 Release 빌드가 중단됐다. 이 Expo·React Native 0.74 앱에서 React Native SDK 6.22.0과 Cocoa 8.56.2로 바꾼 뒤 iOS 시뮬레이터 Release 빌드가 통과했다. 소스맵에서 `debugId`를 확인하고 앱을 띄워 화면을 확인했다. 운영 Sentry에 소스맵을 올려 오류 위치를 복원하는 절차는 미확인이다.

- 앱 테스트 694개와 변경 코드 lint가 통과했다. 전체 타입 검사에는 기존 지도·공유 UI 오류 7개가 남았다.
- 서버 테스트 72개, 타입 검사와 빌드가 통과했다. 실제 Node SDK를 로컬 수신기에 연결해 500 오류와 404 거절이 구별되는지 확인했다. 시험용 토큰·레코드 ID·SQL 오류 문구는 받은 기록에서 발견되지 않았다.
- JS 예외, 서버 오류와 동기화 신호를 수집한다. 필터를 거치기 전에 원문이 포함될 수 있는 네이티브 크래시·멈춤 등의 자동 수집과 화면 녹화는 껐다.

## 시뮬레이터에서 관찰한 경계

별도 iPhone 15 Pro 시뮬레이터에 Release 네이티브 앱의 복사본을 설치하고, 임시 JS 시험 진입점에서 제품의 계정 검사·로그아웃·동기화 함수를 호출했다. OS 무선 연결을 전환하는 대신 루프백 수신기를 껐다 켜서 전달 경계를 만들었다. 재시작 대상은 앱이었다.

| 조건 | 로컬 수신 결과와 큐 상태 |
| --- | --- |
| 수신기를 끈 채 새 요청을 격리하고 앱을 완전히 종료한 뒤 수신기를 켜고 앱을 재실행 | 새 격리 사건 1건, 정상 PUT 1건. 정상 작업은 큐에서 빠지고 격리 작업만 남았다. |
| 수신기를 끈 채 새 격리가 생긴 뒤 실제 강제 로그아웃으로 DB를 비우고 계정 B로 로그인 | 앱 재시작 후 이전 진단 1건이 도착했다. 이 경로에서는 DB가 비워져도 SDK 측 캐시는 남았다. 수신 기록에 `user`·`request`가 없었고, 심어 둔 시험 ID·토큰을 찾은 건수는 0이었다. |
| 실제 동기화 실행 중 서버 응답 전에 앱 종료. 재실행 후 첫 작업이 404 두 번, 이어 응답 유실 | 실행 시작 4건·종료 3건. 중단된 실행은 시작만 남았다. 첫 작업의 실패 누계는 1·2·3으로 증가했고 뒤 작업은 PENDING이었다. 404 두 사건은 `server-rejected`, 이전 실패 0·1회, 반복 여부 false·true였다. 응답 유실은 `response-unconfirmed`, 이전 실패 2회였다. |
| 첫 작업의 action을 손상시켜 서버 요청 전에 동기화가 실패하게 함 | PUT 증가 0건. `sync.push.blocked` 1건에 `local-before-send`, `action=unknown`, 이전 실패 3회, 뒤 작업 대기 true가 남았다. 첫 작업은 FAILED·실패 누계 4, 뒤 작업은 PENDING·실패 누계 0이었다. |

격리 1건이 남아도 정상 작업까지 보낼 수 있는 경우와 첫 전송 실패가 뒤 작업을 막는 경우가 구별됐다. 시작만 있고 끝이 없으면 결과 미확인으로 해석한다. 이 시험의 수신 건수와 지정 문자열 검사로 모든 환경에서의 전달·무손실·개인정보 배제를 보장할 수는 없다. 실제 Sentry 프로젝트에서 오류와 실행 기록이 구별되는지, 소스맵으로 위치를 찾고 알림을 받을 수 있는지는 프로젝트 설정 뒤 확인한다.
