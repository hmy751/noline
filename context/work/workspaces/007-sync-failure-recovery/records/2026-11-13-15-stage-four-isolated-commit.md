## 설명에서 이번 커밋으로 이어진 책임

사용자는 “그럼 4단계 코드 설명해줘”라고 요청했다. Main은 기기에 A=30달러와 B=35달러의 편집을 차례로 저장한 예를 따라, 현재 Local35에서 A를 다시 만드는 것이 아니라 **각 편집 당시의 요청과 표식을 큐에 보관해 저장 순서대로 전송한다**고 설명했다. 큐 작업 ID와 payload의 편집 ID, 서버 도착 순서와 편집 표식 순서를 구별했다.

전송 대상은 rowid 순서로 읽고, 보낼 수 없는 상태가 있으면 그 뒤를 건너뛰지 않는다. 일반 실패는 FAILED로 남기고 이번 반복을 멈추며, 실패 횟수 상한 때문에 영구 제외하지 않는다. 전송 목록은 시작에 한 번 읽으므로 대기 중 새 편집은 다음 실행에 남는다. 설명은 현재 작업 트리 기준이며 모든 세부 처리가 이번4단계 커밋에 처음 들어간다는 뜻은 아니다.

서버에서는 부모 여행을 찾기 위한 tripId 조회와 잠금 후 판정할 자식 전체 행 조회가 서로 다른 역할임을 연결했다. 여행→자식 잠금으로 동시 수정·삭제를 조율하고, 항목 묶음별 표식을 비교해 받아들일 patch를 만든다. 금액·통화처럼 함께 판정할 항목과 분류처럼 독립된 항목을 구별했다. 같은 값의 새 표식도 저장해야 뒤늦은 중간 편집이 값을 되돌리지 못하므로 `requiresWrite`는 화면 값의 변화보다 넓은 의미다.

재전송은 원래 본문·표식을 유지하며, 서버는 같은/오래된 편집을 다시 적용하지 않고 현재 결과를 성공 응답으로 돌려준다. 생성은 같은 ID의 소유자·여행을 확인해 기존 행을 반환하고, 삭제는 기존 삭제 시각을 유지한다. **성공 응답이 요청 값을 채택했다는 뜻은 아니다.** 응답의 Local 반영과 현재 A만 완료하고 남은 B를 보호하는 상세는5단계로 이어진다고 설명했다. 사용자의 다음 발화는 커밋 요청이며 모든 분기 이해나 제품 최종 수락의 명시로 확대하지 않는다.

## 구버전 보류 저장이 이번에 필요한 이유

4단계 서버 판정에는 표식 없는 구버전 요청이 이미 표식이 있는 항목과 충돌했을 때 **수정 전체를 적용하지 않고 요청 원문을 보존하는 선행 처리**가 필요하다. 이 서버 저장과 DB DDL·schema를 빼면 항목별 판정의 거절 분기가 독립적으로 연결되지 않거나 복구할 원문을 잃는다. 따라서 단계 이름만으로 보류 관련 코드를 모두6단계로 미루지 않는다.

> Main: “이 부분과 DB 적용 파일은 함께 담고, 보류 목록 조회·확인 API와 클라이언트 복구 화면은 6단계로 남기겠습니다.”

이번 커밋은 FIFO의 새 PENDING·알 수 없는 상태 구별과 큐 표현, 서버 항목별 승패·부모 잠금·CREATE 재전송·삭제 동시성을 포함한다. 서버 보류 GET/ACK와 client 보류 동기화·410 후속·복구 UI는6단계에 남긴다. 독립 후보 감사에서 필수 소비 연결과 분리 범위를 확인했고 필수 수정은0건이었다. 기존 기능·정책을 새로 선택하는 요청이나 DB DDL의 실제 운영 적용 요청이 아니다.
