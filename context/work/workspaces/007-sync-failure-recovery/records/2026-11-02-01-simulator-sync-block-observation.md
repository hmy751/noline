# 2026-11-02 — 시뮬레이터에서 발견한 동기화 큐 영구 정지

1.1.0 출시 전 기능을 직접 확인하라는 요청("좋아 일단 직접 확인해봐")을 받아, iOS 시뮬레이터에서 개발 앱을 띄워 확인하던 중 발견했다. Main(Claude)이 직접 관찰하고 보고한 내용을 정리했다.

## 환경

- iOS 시뮬레이터 iPhone 15 Pro (iOS 26.0), 개발 앱 `Noline (Dev)` (`com.noline.dev`)
- 로컬 개발 서버와 Docker PostgreSQL을 함께 썼다. 운영 서버·운영 DB·TestFlight 빌드가 아니다.
- 코드는 당시 `main`의 현재 판본이다.

## 관찰한 사실

개발 앱에 남아 있던 경비 한 건이 동기화를 막고 있었다. 시각은 앱 로컬 DB의 큐 행과 로컬 서버 DB에서 읽은 값이다.

| 시각 (UTC) | 일어난 일 | 확인한 곳 |
| --- | --- | --- |
| 10-31 08:22:03 | 앱이 경비 생성(CREATE)을 큐에 넣음 | 앱 로컬 DB의 큐 행 |
| 10-31 08:22:04 | 서버 DB에 같은 ID의 경비가 만들어짐 | 서버 DB의 `created_at` |
| 10-31 08:23:00 | 앱이 이 작업을 "FAILED, 재시도 3회"로 기록 | 큐 행의 `updated_at` |
| 11-02 | 앱을 켜도 아무것도 보내지 않음 | 로그의 `SyncIncompleteError` (failedCount 1) |
| 11-02 | 다시 보내도록 되돌린 뒤, 서버가 `duplicate key … expenses_pkey`로 500 응답 | 서버 로그 |

큐에는 이 작업 뒤로 경비 수정과 확인용 테스트 일정이 PENDING으로 쌓여 있었다.

첫 요청은 서버에서 성공했는데 앱이 성공 응답을 받지 못했다. 그래서 같은 ID로 다시 보냈고, 서버는 같은 ID를 또 저장하려다 실패했다. 3회가 차자 `getSyncableTasks`의 `retryCount < 3` 조건에 걸려 그 뒤 작업이 모두 대기 상태가 됐다.

## 원인에 대해 확인한 것과 못 한 것

- **배제한 가설:** 서버가 저장한 뒤 응답 검사에서 실패해 500을 냈을 가능성. 서버에 남은 그 행을 현재 코드의 응답 검증에 통과시켜 보니 통과했다. 다만 10-31의 서버 코드는 지금과 다를 수 있어 완전히 배제한 것은 아니다.
- **남은 가설:** 응답이 중간에 끊긴 경우다. 앱 종료, 네트워크 전환, 시간 초과가 해당한다. 로그가 없어 확인하지 못했다.
- **이 사례는 로컬 서버에서 생겼다.** 서버 행이 큐 등록 1초 뒤에 만들어졌으므로 Render 기동 지연 경로가 아니다.
  - Render 기동 지연은 운영에서 같은 일이 일어날 수 있다는 별개의 가설이다.
  - 2026-11-03 답변 중 "이번 사고의 응답 유실도 잠든 서버 경로였을 수 있다"고 한 문장은 이 관찰과 맞지 않아 정정한다.

## 함께 확인한 동작

- 동기화는 앱 시작, 연결 조건 변화, 수동 실행(개발용 디버그 화면) 때만 시작한다. 주기 동기화는 꺼져 있다.
- 연결된 상태에서 일정을 저장해도 바로 서버로 가지 않았다. 3분 넘게 지켜본 결과다.
- 막힌 작업을 사용자가 되살릴 수 있는 화면은 없다. 개발용 디버그 화면에만 있다.

## 정리한 것

- 시뮬레이터 앱의 로컬 DB에서는 확인용으로 만든 테스트 일정과 큐 행을 지웠다. 건드렸던 실패 작업은 원래대로(FAILED, 재시도 3) 되돌렸다.
- 그 사이 전송은 한 번도 성공하지 않아 서버 DB는 바뀌지 않았다.
- 변경 전 백업은 [source](../source/index.md#막힌-시뮬레이터-db-백업)에 위치와 해시를 남겼다.

## 릴리스 노트에 준 영향

릴리스 노트 초안의 "동기화가 중단돼도 아직 전송하지 못한 내용을 보존해요"는 사실이다(큐에 남는다). 하지만 "저장 즉시 동기화된다"로 읽히지 않게 조심해야 한다. 이 줄을 빼거나 "작성 중인 내용이 사라지지 않도록 개선"으로 줄이는 편이 안전하다고 보고했다. 1.0.1에도 있던 동작으로 보여 1.1.0의 회귀는 아니라고 판단했다.
