# 실제 코드를 함께 검토하기 위한 설명 참고

코드나 개발 결과를 설명하면서 상대가 실제 호출·조건·값을 짚어 질문하고 다음 판단을 할 수 있게 하려는 때 참고한다. 변경 목록이나 보호 장치의 필요성을 알리는 것만으로 충분한지, 현재 동작을 따라갈 연결이 빠졌는지 살피는 자료다. 3단계 전용 목차가 아니라 다른 코드 설명에서도 당시 요구와 비교해 재사용할 판단 참고이며, 이 문서를 읽었다는 사실이 설명의 충분성이나 효과를 입증하지는 않는다.

사용자는 설명에 반영할 방법을 고민하되 explain 스킬을 직접 수정하지 말라고 했고, 이어 특정 단계에 한정하지 않고 앞으로 활용·참조할 수 있게 기록해 달라고 요청했다. 아래의 구성·충분성에 관한 종합은 원문을 대조한 Main의 해석과 적용 방향이다. 고정 순서·전수 체크리스트·새 전역 규칙을 채택한 것이 아니며, 다른 작업에서 자동으로 발견·적용됨을 보장하지 않는다. 현재 질문·코드·소비자에 맞춰 유지하거나 수정할 수 있다.

## 무엇을 설명할 때 이 참고가 필요한가

함수와 파일의 역할은 들었지만 값이 어디에서 만들어져 언제 사용되는지 연결되지 않거나, 예외와 변경 사항은 자세한데 현재 동작을 따라가기 어려울 때 본다. 반대로 특정 오류나 한 줄의 의미가 질문의 중심이라면 그 지점에서 시작할 수 있다. 항상 정상 경로부터 설명하거나 전체 시스템을 다시 설명할 필요는 없다.

설명의 범위는 사용자가 함께 판단하려는 일에 맞춘다. 대표 상황이나 핵심 흐름이 있으면 같은 입력을 따라가며 현재 코드가 무엇을 결정하고 어느 호출·저장으로 이어지는지 연결하기 쉽다. 이때 서로 다른 진입이나 조건부 분기를 연속 실행처럼 합치지 않는다. 별도 경로는 무엇을 공유하고 어디서 갈라지는지를 설명에 필요한 만큼 연결한다.

이미 함께 읽은 내부 구현은 다시 전부 펼치기보다 이번 코드가 무엇을 전달하고 어떤 결과를 맡기는지 연결한다. 다만 상대가 이해했다는 근거 없이 생략하거나, 익숙한 함수명만 붙여 필요한 연결을 대신하지 않는다. 설명 길이보다 지금 질문에 필요한 관계가 남았는지가 기준이다.

## 코드 조각 사이의 실행 관계를 남긴다

코드 블록은 역할 이름의 예시나 긴 파일 복사본이 아니라, 입력을 받아 판단하고 다음 처리로 넘기는 관계를 볼 수 있는 단위로 고른다. 필요한 인자·반환값과 호출 시점이 함께 보이면 같은 이름이라도 객체·Promise·callback의 역할을 구별할 수 있다. 파일이 바뀌는 지점에서도 앞에서 만든 값이 다음 어디에 쓰이는지 이어져야 한다. 여러 위치를 발췌했다면 생략과 별도 위치를 드러내 연속 코드처럼 오해하지 않게 한다.

예컨대 “Repository가 요청을 준비하고 Router가 Local/API를 고른다”는 역할 요약만으로는 callback을 만드는 때 두 저장이 모두 실행되는지 알 수 없다. 실제 코드에서는 준비 Promise를 만들고 작업 순서를 등록한 뒤 Router가 기다려 하나의 callback을 호출한다. 이 관계가 질문의 대상이라면 입력값과 Promise, 함수를 넘기는 시점과 실행하는 시점을 연결해야 한다. Promise를 먼저 기다리지 않는 이유도 그 실행 순서와 함께 설명해야 의미가 생긴다.

반대로 조회 경계를 만드는 코드와 다음 경계를 반환하는 코드만 보이면, 받은 경계가 실제 조회 조건에 어떻게 들어갔는지는 독자가 채워야 한다. 이는 코드 블록을 더 길게 만들라는 요구가 아니다. 설명하려는 결과에 필요한 값의 사용 지점이 빠졌는지 판단할 대비 사례다.

## 조건과 변경 이유를 해당 처리에 붙인다

예외·보호 조건은 그 조건이 바꾸는 호출·저장·반환 가까이에서 풀면 어떤 일의 일부인지 알 수 있다. 먼저 모든 예외를 같은 비중으로 열거하거나, 본문 뒤에서 같은 이유를 반복할 필요는 없다. 다만 뼈대를 줄인다는 이유로 실행 조건과 영향 범위를 지워서는 안 된다. 특정 진입에서만 하는 처리, 조건이 맞지 않을 때 생략하는 범위, 실패 시 함께 되돌리는 변경은 핵심 동작의 의미일 수 있다.

변경·유지 이유도 관련 코드에 붙인다. “이 처리가 어떤 결과를 위해 필요한가”와 “그 결과를 만드는 현재 표현·배치가 적합한가”는 구별한다. 현 구조에서 한 줄을 지우면 깨진다는 설명만으로 현 구조 전체를 정당화하지 않는다. 표현·배치를 판단했다면 실제 소비자와 비교한 대안·비용을 연결하고, 아직 판단하지 않은 부분은 필요한 결과를 확인한 것과 구별한다. 모든 줄에 설계 변론을 붙일 필요는 없다.

설명 중 질문이 전제를 바꾸면 말만 다듬어 끝낼지, 실제 코드·검사를 다시 대조해야 할지 판단한다. 설명 요청 자체를 구현 변경 승인으로 넓히지 않되, 설명용 축약에서 생긴 오해와 제품 코드에 실제 남은 중복·책임 문제를 섞지 않는다. 설명이 현재 구현을 납득시키는 데서 끝나지 않고 검토와 정정의 근거가 될 수 있게 하는 취지다.

## 이 참고가 만들어진 원문과 대비 사례

### 사용자가 요청한 것은 실제 코드의 관계와 필요성을 함께 보는 설명이었다

1단계 원문에서 사용자는 다음과 같이 말했다.

> 좋아 그럼 1단계부터 다시 코드 보면서 자세히 설명해줘. 각 부분이 왜 필요한지도 같이

> 좋아 그럼 지금 정리한 저장 흐름을 Repository부터 Local, API까지 실제 코드 보면서 자세히 설명해줘. 각 부분이 왜 필요한지도 같이

중간에는 경로 처리의 재사용·갱신 기준도 코드와 함께 설명해 달라는 요청이 있었다. 후속 답변은 25달러를 30달러로 수정하는 입력을 유지하며 Repository·Router·Local/API를 따라갔다. `local`·`remote` 함수의 등록과 실행, 준비 Promise와 그 결과, 한쪽 저장 경로만 선택하는 분기를 구별했다. 이는 질문에 필요한 관계를 연결한 관찰 근거이지 그 답변 전체가 충분하거나 당시 구현 판단이 모두 옳았다는 증거는 아니다. 초기 reset·잠금의 필요성을 설명했던 일부 판단은 뒤에 실제 사용과 대조하며 바뀌었다. 그 정정은 [07 기록](2026-11-13-07-review-depth-and-completion-correction.md)에 남아 있다.

### 뼈대가 필요했지만 뼈대만으로 실행 조건을 바꿔 보이면 안 됐다

2단계에서 사용자는 다음과 같이 요청했다.

> 너무 예외처리 조건도 많고 해서 그러는데 핵심 뼈대를 위주로 코드를 다시 구성해서 보여줘봐 실제 코드는 수정하지말고

이 설명용 요청 뒤 별도로 “범위 구분도 안되고”라며 실제 선언적 구성과 코드 스타일 개선을 요청했고 이후 수정을 승인했다. 설명용 뼈대 요청과 제품 수정 요청은 구별한다. 두 과정에서 현재 조건이 어느 책임에 속하는지 찾기 어렵다는 문제가 드러났다고 Main이 해석했다.

설명용 뼈대 끝에 ACK를 공통으로 두자 pull도 남은 push 요청을 완료하는 것으로 보일 수 있었다. 당시 Main은 다음과 같이 정정했다.

> pull을 받았다는 사실만으로 남아 있는 push 요청을 완료하지는 않습니다.

이 사례는 핵심 흐름을 줄이더라도 호출별 실행 조건을 남겨야 한다는 근거다. 이어 기존 sync와 reconcile의 역할이 겹치는지 묻는 질문에서는 실제 호출을 대조해 일반 경로의 ACK 이동과 실제 남은 중복을 구별했고, 별도 승인 뒤 중복 부분만 정리했다. [2단계 판단 기록](2026-11-13-04-stage-two-judgment-and-handoff.md)의 당시 해석·실행과 구별해 참고한다.

### 이번 설명에 적용하려던 방향을 범용 참고로 남겼다

이번 사용자는 우선 3단계만 설명하도록 범위를 좁혔다. Main의 답은 보호 상황·변경 이유와 코드 조각을 제공했지만, cursor를 생성·반환하는 사이의 실제 조회 조건 사용과 checkpoint가 다음 요청으로 이어지는 연결은 충분히 보여주지 못했다. Main은 이를 원문 대조 후 인정하고, 현재 실행을 따라 판단할 수 있도록 설명을 구성하겠다고 제안했다. 이는 3단계에 드러난 적용 사례이며 위 판단 참고를 3단계 파일 순서나 고정 목차로 만드는 근거가 아니다.

사용자는 다음과 같이 지시했다.

기록 요청에 따라 이 참고와 기존 진입 경로만 보완했다. 실제 다음 설명이 이 방향을 충분히 구현했는지, 사용자가 이해·수락했는지는 별도다. 제품 재검토 완료를 취소하지 않으며 이번에는 제품 코드·검사·스킬·Personal·Project·009·커밋을 변경하지 않았다.
