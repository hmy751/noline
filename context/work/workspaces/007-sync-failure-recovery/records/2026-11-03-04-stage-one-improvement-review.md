# 2026-11-03 — 1단계 개선 검토와 반영

[1단계 구현](2026-11-03-03-stage-one-implementation.md)이 끝난 뒤, 빠뜨렸던 개선 검토를 돌리고 채택한 보완을 반영한 기록이다. 모두 미커밋이다.

## 왜 뒤늦게 검토했나

사용자가 이번 작업의 워크플로를 물었다. Main은 다음 두 가지를 밝혔다.
- 개선 검토를 두지 않았다. `development`의 [검토 상세](../../../../../.agents/skills/development/references/review.md)는 중요한 선택이 있는 첫 결과에 개선 검토를 기본으로 고려하라고 한다. Main은 11-03의 설계 단계 비교로 충분하다고 보고 건너뛰었다.
- 구현도 Main이 직접 했다. [실행 배치](../../../../../.agents/skills/development/references/execution.md)는 내부 담당자를 기본으로 하는데, 구현 전에 이 문서를 읽지 않았다.

사용자 발화 원문은 다음과 같다.

> "근데 왜 개선 검토를 안뒀어? 그리고 구현도 왜 니가하고 스킬에 안되어 있나? 구현도 소넷 미디엄이 하길 바랬고 개선검토도 그럼 개선 검토만 한번 돌려봐"

앞서 사용자가 말한 "서브는 소넷 미디엄으로 해"를 Main은 앞으로 띄울 검증자에게만 적용했다. 사용자의 뜻은 구현자와 검토자에도 같은 배치를 쓰는 것이었다. 실행 배치 문서의 시작값(`GPT-6.1-sol, medium`)은 이 Claude Code 세션에서 쓸 수 없으므로, 이후 배치는 다음과 같다.
- 구현·검토·검증 담당자는 모두 Sonnet medium이다.
- 조율, 채택 판단, Project·Work 반영은 Main이 맡는다.

## 검토 (Sonnet medium, 구현에 참여하지 않은 새 컨텍스트)

검토자는 저장소를 수정하지 않았고, 테스트도 다시 실행하지 않았다. 코드·diff·테스트를 읽어 판단했다.

**현행 유지로 판정한 것과 이유**

| 선택 | 판정 이유 |
| --- | --- |
| 되돌림 위치 | 조회 함수에 쓰기를 섞지 않는다. 계정 검사 뒤로 옮기면 다른 계정의 IN_PROGRESS가 남아 같은 일을 반복해야 한다. |
| 여행 삭제를 그대로 둠 | 큐를 막지 않는다. 같은 route를 바꾸는 003 Ticket 13에 정리를 모은다. |
| 생성 재전송의 body를 비교하지 않음 | 같은 payload의 재전송에서 body가 다른 경우는 버그뿐이다. 그런 요청을 거절하면 새로운 막힘이 생긴다. |
| 삭제 0행일 때만 조회 | 정상 경로에는 비용이 없다. 단일 SQL로 합쳐도 얻는 이득이 적다. |
| Project 반영 위치 | 문서별 소유 구분과 맞는다. |

**발견 세 가지와 Main의 처리**

1. **한도 제거의 비용**
   - 발견: 예전에는 한도에 걸린 작업에 요청을 보내지 않았다. 지금은 영구히 실패하는 작업도 sync마다 실제 요청을 보낸다. 5xx면 HTTP 재시도 대기(2·4·8초)까지 붙는다.
   - 대안: `updatedAt` 기준의 간격 재시도. 검토자도 지금은 도입하지 않기를 권했다.
   - Main의 처리: 비용이 문서에 없다는 지적은 채택했다. 간격 재시도는 연결 회복 뒤의 전송도 늦추므로 보류했다. Ticket 03에서 실제 sync 빈도를 잰 뒤 판단한다.
   - 확인: Main이 코드로 확인한 결과, pull을 건너뛰는 것은 예전에도 같았다. 새로 생긴 비용은 요청뿐이다.
2. **엔진의 빈 작업 분기가 거의 도달하지 않는다**
   - Main의 처리: 분기는 지우지 않고 방어 코드로 남기고, 주석으로 밝혔다.
   - 확인: Main이 확인한 결과, 이 분기를 지나는 기존 테스트(`query-refresh`의 빈 큐)는 미전송이 0인 경로라 영향이 없다.
3. **테스트 파일 이름이 내용과 어긋난다**
   - 문제: `create.idempotency.test.ts`가 삭제와 여행 삭제 재전송도 담고 있다.
   - Main의 처리: `replay.idempotency.test.ts`로 바꿨다.
   - 남긴 것: 생성 시점의 해시표(source)와 11-02 기록은 당시 판단으로 보존했다. 대신 링크만 새 경로로 바꾸고, 이름이 바뀌었다는 표시를 붙였다.

## 반영과 확인

- **구현자 (Sonnet medium)**
  - 두 테스트 파일의 이름을 바꿨다.
  - 엔진 분기에 주석을 넣었다.
  - 옛 이름을 참조하는 코드·설정은 없었다. vitest는 디렉터리 glob으로 테스트를 고른다.
  - 서버 typecheck, 단위 69, 통합 21, client 655, prettier가 통과했다.
- **Main**
  - [데이터 수명](../../../../project/guidance/data-lifecycle/INDEX.md)의 "실패 횟수로 막거나 버리지 않는다" 문단에 비용과 열린 선택을 넣었다.
  - Project 2개, Ticket 01, output의 테스트 링크를 바꿨다.
  - `pnpm harness:check`에 001~006 외의 새 항목은 없다.
- **재검증 (기존 검증자에게 이어서 맡김)**
  - 이름 변경 뒤 같은 테스트가 선택되는지, 새 문서 문장, 깨진 링크를 확인했고 모두 충족 근거가 있다고 판정했다.
  - 엔진 주석의 "그 경우에도 완료로 알리지 않는다"는 사실이 아니라고 지적했다. `getSyncQueueStats`는 알 수 없는 status를 세지 않으므로, 그런 작업만 남으면 정상 반환한다.
  - 이 문구는 Main의 의뢰문에서 온 것이다. 원래 구현자가 다음과 같이 고쳤다: "알 수 없는 status가 맨 앞을 막고 그 뒤에 미전송이 남은 경우를 위한 방어용". 자기 확인은 sync 테스트 63개와 prettier였다.
  - 고친 주석에 대한 검증자의 재확인 결과는 [Ticket 02](../current/memory/tickets/02-client-queue-recovery.md#현재-상태와-실제-결과)에 남긴다.

## 이 과정에서 드러난 것

- 의뢰문의 사실 주장이 그대로 코드 주석이 됐다. 구현자에게 문구를 예시로 줄 때도 Main의 주장은 검증 대상이다.
- 개선 검토를 검증 뒤에 돌렸다. 그래서 검토에서 채택한 수정마다 재검증을 한 번 더 했다. 원래 순서인 "검토 → 수정 → 검증"이었다면 이 왕복이 없었다.
