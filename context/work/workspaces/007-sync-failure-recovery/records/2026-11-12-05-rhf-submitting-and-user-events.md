# RHF 제출 상태로 정리하고 사용자 이벤트와 강제 전환 검사를 구별

사용자는 공통 저장 잠금이 `isSubmitting`보다 무엇을 더 해결하는지 물었다. Main은 별도 잠금의 필수성을 실제 사용자 동작으로 입증하지 못했음을 정정했고, 사용자 승인에 따라 두 폼의 React Hook Form `isSubmitting`으로 저장·닫기 상태를 통일했다. 공통 `useUpdateDrawerSave` 훅은 삭제했다. **이번 수정과 자동·독립 검증을 마쳤다. 네이티브 수정창 실행 확인은 선행 미완료 범위로 유지한다.** 이전 응답의 새 초안 침범 방지는 별도로 유지한다.

## 추가 제한의 필요성과 테스트가 만든 조건을 다시 구별

Main은 처음에 렌더 전 두 호출과 A 저장 중 B 전환을 근거로 바깥 저장 잠금이 필요하다고 설명했다. 사용자가 “기존에 isSubmitting으로는 안됐냐”와 실제 어떤 상황인지 반복해 묻자, 일반적인 저장 버튼 비활성화와 검사에서 강제한 조건을 대조했다.

첫 검사는 `@testing-library/react-native`의 두 `fireEvent.press`를 하나의 `act`에 넣었다. 첫 이벤트에 따른 버튼 비활성화가 반영되기 전에 두 번째 호출을 함께 처리하는 조건이었다. 닫기도 실제 탭·제스처가 아니라 Drawer 대역의 `onClose`를 직접 호출했다. 설치 환경의 ref 없는 최소 RHF 폼으로 직접 비교한 결과는 다음과 같았다.

| 저장 이벤트 발생 방식 | 저장 호출 |
| --- | --- |
| 하나의 act로 묶은 fireEvent 두 번 | 2회 |
| 바깥 act 없이 별개의 fireEvent 두 번 | 1회 |
| await userEvent.press를 순서대로 두 번 | 1회 |

세 비교 모두 기대대로 통과했다. 이 결과는 공통 잠금이 없으면 실제 사용자의 탭이 중복 저장된다는 근거가 아니었다. Main이 React의 별개 사용자 이벤트 처리 설명과 실제 관찰을 대조해 앞선 설명을 정정했다. React Native에서 별도 실사용 문제가 있다는 측정도 확보하지 않았다.

두 번째 검사는 저장 중 부모 props를 `rerender`로 닫힘·다른 기록으로 강제 교체했다. Drawer는 View 대역이므로 실제 사용자가 저장 중 창을 닫고 다른 항목을 선택할 수 있는 경로를 증명한 것이 아니다. 강제 전환 뒤 **A의 늦은 응답이 B 입력을 지우지 않는 보호**와 **A 때문에 새 B의 저장까지 금지하는 제한**은 다른 요구다. 앞의 보호 필요성이 뒤의 제한 필요성을 입증하지 않는다. 이전 검사에서 B까지 잠겨야 한다는 기대값을 제품 계약처럼 취급한 점을 바로잡는다.

사용자의 실제 수정 승인은 “isSubmitting으로 정리하고 불필요한 공통 잠금은 제거해줘. 테스트도 실제 사용자 동작 기준으로 고치고, 이전 응답이 새 입력을 지우지 않는 보호는 유지해서 검증해줘. 그리고 1단계 다시 설명”이었다.

## 실제 반영과 유지하는 경계

두 내부 폼은 `formState.isSubmitting`을 읽고 `handleSubmit`의 Promise에서 저장 완료까지 기다린다. 저장·취소 버튼과 Drawer 닫기를 이 상태로 제어한다. 바깥 wrapper는 데이터·key에 따른 내부 폼 생성만 맡고, 이전 폼의 제출 상태를 새 폼에 강제로 이어붙이지 않는다. 공통 잠금 훅과 표시 state/ref는 제거했다.

내부 폼의 mount ref·cleanup과 검증/성공/실패의 유효성 검사는 유지한다. 대상이 강제로 바뀌더라도 이전 저장의 검증이 새 저장을 만들거나 이전 결과가 새 입력·안내·닫기에 영향을 주지 않게 한다. 초기 snapshot, 성공 후 열린 소비자의 비교 기준 reset, `unknown` 오류를 값으로 저장하는 wrapper도 유지한다. FIFO·편집 표식·그룹·DB·서버의 계약은 바꾸지 않는다.

독립 코드 재검토는 필수 수정 사항 없음으로 반환됐다. 테스트도 일반적인 순차 탭·저장 중 비활성화·실패 후 재시도와, props 강제 전환 뒤 늦은 결과 보호를 구별하도록 수정했다. 최종 별도 high 검증자는 현재 제품 결함이 없고 검사 범위가 적절하다고 반환했다. **앞선 852개·독립 12개 통과를 이번 제출 방식의 검증이나 cross-form 잠금의 필요성 근거로 재사용하지 않는다.**

## 최종 검사와 완료 범위

별도 high 검증자가 최종 전체 client **74묶음 853/853** 통과를 확인했다. 구현 담당자의 수정 테스트 두 파일은 **2묶음 39/39**로 재확인했다. 39개는 전체 853개에 포함되므로 더하지 않으며, 앞선 최소 RHF 비교 실험 3개도 제품 전체 통과 수에 합산하지 않는다.

사용자 동작은 순차 `userEvent.press`로 저장·취소·실패 후 재시도를 확인했다. 강제 props 교체 검사는 별도로 A의 늦은 성공·일반 실패·서버 처리 후 기기 준비 실패가 B 입력·안내·닫기와 **B 자신의 진행 중 제출 상태**를 바꾸지 않는지 양쪽 폼에서 대조했다. 실제 resolver를 지연한 뒤 외부에서 다음 폼을 장착하는 조건도 이전 검증 결과가 새 저장·안내를 만들지 않게 확인했다. 이들은 새 폼을 앞 저장 때문에 잠그는 요구가 아니라 이전 결과와 새 입력의 독립성을 확인하는 검사다.

수명 테스트에는 실제 Drawer를 연결했으나 `requestClose`·backdrop은 `fireEvent`로 콜백 계약을 주입했다. 순차 사용자 탭 검사와 역할을 구별하며 네이티브 기기의 실제 제스처·애니메이션을 직접 검증했다고 확대하지 않는다.

제품 두 파일 lint는 오류 0·기존 색 경고 16개, 수정 테스트 두 파일 lint는 오류 0개다. 실제 Drawer 구현의 타입 소스를 직접 참조하며 생긴 추가 오류 두 개는 공개 export의 `Pick<typeof import('@repo/ui'), 'Drawer'>`를 통해 타입을 잡도록 고쳤고 런타임 의미는 같다. 최종 client 타입 로그는 이전 표현 정리 판과 완전히 같아 **기존 7개 오류만 유지**됐다. 기록 담당자는 현재 테스트의 타입·이벤트·assertion과 최종 로그, 두 타입 로그의 동일성을 직접 대조했다. 제품 차이 검사는 Main이 통과했고 문서 변경 뒤 차이 검사도 통과했다.

삭제 공통 훅을 가리키던 두 Work output의 링크는 실제 두 Drawer로 교체했다. 정리 뒤 harness는 기존 과거 문제 64개만 남는다. 과거 records의 당시 설계·검증 문장은 보존하고 현재 정정을 이 기록으로 연결한다. Main은 Project 입력 문서의 현재 제출 상태 설명도 갱신했으며 기록 담당자는 Project·제품을 수정하지 않았다.

**이번 RHF 제출 상태 전환·공통 잠금 제거와 자동 검증은 완료**다. 네이티브 수정창 열기·닫기·재열기 미확인은 여전히 남는다. 앞선 일반 앱 홈·경비 목록/상세 확인이나 이번 Drawer 콜백 검사를 네이티브 제출 동작 확인으로 확대하지 않는다. 사용자 수락·커밋·배포는 미실행이다.
