# 실제 Sentry 프로젝트에서 앱과 서버 진단 확인

2026-11-10 사용자의 승인으로 앱·서버 프로젝트와 소스맵 업로드를 설정하고 시험 이벤트 수신을 확인했다.

앱과 서버의 수신 프로젝트를 분리했다. DSN과 소스맵 업로드용 인증 정보는 Git에서 제외한 로컬 설정에 저장했다.

| 시험·설정 | 확인한 결과 |
| --- | --- |
| 서버 SDK에서 시험 오류 전송 | 실제 서버 이슈가 표시됐다. |
| iOS Release 앱 복사본의 시험 JS 진입점에서 제품의 동기화 진단 함수 호출 | 실제 앱 이슈가 staging의 Warning으로 표시됐다. 같은 trace 화면에서 `sync.started`, `sync.finished`, `sync.push.blocked` 세 기록을 연결해 확인했다. |
| 앱의 iOS Hermes 소스맵 업로드 | 소스맵 묶음 업로드가 완료됐다. JS 예외 프레임을 소스 파일·행으로 실제 복원하는 확인은 후속이다. |
| 기본 오류 알림 규칙 | 두 Noline 프로젝트, 모든 환경의 Error 이상 새 이슈·재발·급증에 적용했다. 1시간 발송 제한, Suggested Assignees에서 Recently Active로 이어지는 수신자 설정을 확인했다. 시험 알림은 보내지 않았다. 반복 동기화 Warning은 이 규칙의 수준 아래에 있다. |

초기 시험 이벤트에서는 Sentry 수집 서버가 IP·지역 정보를 자동으로 붙였다. 로컬 수신기에서 시험용 토큰·ID가 나오지 않았던 결과만으로는 이 동작을 알 수 없었다. 두 프로젝트에서 **Prevent Storing IP Addresses**를 켰다. 변경은 이후 이벤트에 적용되며 기존 시험 이벤트에는 당시 IP가 남아 있다. 기존 이벤트를 삭제하지 않았다.

이 확인은 실제 클라우드 프로젝트에 시험 진단이 도착한 범위다. 운영 앱·서버 배포와 EAS 비밀 설정은 수행하지 않았다. 소스맵으로 실제 JS 프레임을 복원하는지, 반복 Warning을 식별하고 알릴 수 있는지는 별도로 확인한다.

## 같은 날 후속 시험에서 확인한 결과

- 실제 앱 Hermes 소스맵에 이어 시험 번들과 대응하는 소스맵도 승인 범위에서 업로드했다. 앱의 TypeError 시험 이슈에 원래 JS 파일 `/.expo/ticket06/sentry-cloud.js:9:31`, 함수 `React.useEffect$argument_0`과 해당 줄의 소스가 표시됐다. 이 시험 프레임에 대해 소스 위치 복원을 확인했다.
- 동기화 막힘 경고에는 시작·종료와 같은 trace 연결 외에 이전 실패 1회, `has_waiting=true`, `local-before-send`가 표시됐다. 두 프로젝트의 기본 Error 규칙은 저장됐고 반복 동기화 Warning 전용 규칙은 설정하지 않았다.
- IP 저장 방지를 켠 뒤 신규 이벤트 화면에 IP가 표시되지 않는 것을 확인했다. 도시 정보는 남아 두 프로젝트에 `Remove Anything from user`, 이어 `$user` 삭제 규칙을 적용했다. 그 뒤의 시험 이벤트에도 **Geography에 도시가 표시됐다**. 지역 정보 제거에 성공했다는 근거는 없고, 초기 시험 이벤트는 당시 IP와 함께 남아 있다.
- 토큰을 취급한 임시 파일은 제거하고 Git에서 제외한 로컬 비밀 설정만 유지했다. 브라우저에는 세 시험 이슈를 확인할 수 있는 대시보드를 열어 두었다. 대시보드에서 프로젝트와 staging 환경을 선택해 시험 이슈를 찾을 수 있다.

이 시점까지 유료 업그레이드·운영 서버 배포·EAS 비밀 설정·커밋은 하지 않았다. 남은 판단은 도시 정보가 계속 표시되는 원인과 운영 수집 기준, 반복 경고에 별도 알림을 적용할지다.
