## 설명을 시작하고 비교할 때

**이번 처리의 필요성은 기존 동작에서 남은 문제와 연결한다.** cursor를 설명할 때 Main은 전체 데이터를 받는 비용을 출발점으로 삼았다. 사용자는 “지금도 그게 구현되어 있긴하지 않아? pull 동작에서?”라고 지적했다. 이미 timestamp 증분 조회가 있었고, 이번 문제는 수정 시각이 이르지만 commit이 늦은 변경을 놓치는 것이었다. 새 기능의 일반적인 필요성을 말하는 것과 이번 변경 이유를 설명하는 것은 다르다. 다음 설명을 준비할 때는 기존 기능·사용자가 이미 아는 부분과 실제 보완점을 먼저 대조한다. 언제나 역사부터 길게 설명하라는 뜻은 아니다. [당시 정정과 누락 예](2026-11-13-12-pull-boundaries-and-understanding.md#설명의-출발점을-바로잡은-질문)에 근거가 있다.

**비교할 때 같은 이력을 유지하고 결과를 바꾸는 조건을 드러낸다.** 사용자는 “저 표식 비교 사례를 아까와 같이 놓고 비교해봐 reconcile이 어떻게 반응하는지”라고 했다. A=30·B=35·C=40이라는 이력을 유지하고 A 응답·pull·B 응답을 바꾸니, 수신 값뿐 아니라 어떤 요청의 처리가 확인됐는지가 Local·큐를 바꾼다는 차이를 볼 수 있었다. 그러나 그 표 뒤에도 필요성과 실제 처리를 다시 물었으므로 표 하나가 이해를 완성했다고 볼 수 없다.

같은 예에서도 B가 언제 추가됐는지 빠뜨리면 실제 실행 순서와 모순된다. “온라인이면 B도 이미 전송된 것 아닌가?”라는 질문 뒤 Main은 push가 시작할 때 목록을 한 번 읽고, 그 뒤 A 대기 중 저장한 B가 다음 실행에 남는다는 조건을 보완했다. 사례를 만드는 구현자·설명자와 이를 검토하는 사람은 발생 시점·남은 요청·응답 출처를 실제 호출에 대조한다. 모든 예에 변수를 늘리기보다 결과에 영향을 주는 전제를 남긴다. [원래 혼동과 시점 정정](2026-11-13-11-reconcile-understanding-and-explanation-gaps.md#push-뒤에도-b가-남는-조건을-빠뜨린-정정)을 다시 볼 수 있다.

## 역할과 효과를 연결하고 이해한 지점에서 이어갈 때

**역할 이름 뒤에 실제 읽기·쓰기를 연결한다.** “중간 조정”, “화면에 적용”만으로는 이미 Repository가 저장한 B와 reconcile의 관계가 분명하지 않았다. 사용자는 “애초에 리포지터리에서 로컬 쪽에서 데이터를 저장하지 않아?”라고 물었다. 서버 확인본·Local 행·큐 각각의 변화와 화면이 그 뒤 읽는 값을 나누자, B를 처음 저장하는 것과 서버 응답 뒤 Local을 다시 구성하는 것을 구별할 수 있었다.

“없으면 어떻게 되나”라는 비교도 제거 조건을 정확히 해야 한다. reconcile을 호출하지 않고 아무것도 쓰지 않으면 기존35는 남는다. 서버40으로 단순 덮어쓰면 금액 칸이 비는 것이 아니라 B의35가 바뀐다. Main의 “화면에서 사라짐”은 그 차이를 흐렸다. 설계·검토에서 대안을 비교하거나 설명을 보완할 때 호출 제거와 다른 처리로 대체를 섞지 않는다. [세 대안과 표현 정정](2026-11-13-11-reconcile-understanding-and-explanation-gaps.md#화면에서-사라짐과-실제-덮어쓰기의-구별)을 참고한다.

**이미 이해한 지점에 이어 설명하고 질문은 필요한 연결에 사용한다.** 사용자는 표식 정책은 이해했지만 push/pull이 목표를 어떻게 구현하는지 설명하고 질문도 해 달라고 했다. “Local 저장이 실패했는데 cursor만 전진해도 되는가?”에 사용자가 “로컬까지 성공ㅇㄹ 확인해야겠네”라고 답한 뒤, Main은 두 저장을 같은 transaction으로 묶는 코드에 연결했다. 이후 cursor→준비 ID→세션→응답 검증→화면 갱신→삭제 정보→snapshot을 이어 설명했고 사용자는 항목별로 이해됐다고 말했다.

이는 매 답변마다 퀴즈를 내거나 확인받기 전에는 진행하지 말라는 규칙이 아니다. 다음 설명은 이미 확인된3단계 핵심을 처음부터 반복하기보다 새로 이해해야 할 관계를 잡아야 한다. 이해가 불분명하거나 질문이 나왔을 때 관련 사례·코드로 돌아간다.3단계의 항목별 이해 명시와4단계의 설명 뒤 커밋 요청은 서로 다른 사실이다. 후자를 모든 세부 분기의 이해 확인이나 제품 최종 수락으로 올리지 않는다.

## 가독성을 판단하고 수정할 때

**줄 수나 함수 개수보다 독자가 덜 추적·추측·재구성하게 되는 것을 비교한다.** 1·2단계 판단을 찾으라는 요청을 Main이 일반 개인 배경으로 좁혔다가 정정받은 뒤, 사용자는 사람이 읽고 판단하기 쉬운 관점으로 다시 묶도록 했다. 여기서 시각적 구간, 전체 흐름, 이름·타입·결과, 판단과 효과, 불필요한 해석, 변경 영향의 여섯 관점이 나왔다.

실제 정리에서는 조율 본문에서 DB 상세를 내려 읽게 하는 같은 파일 helper, 사용하지 않는 반환 제거, 실제 쓰기 필요를 드러내는 `requiresWrite` 등을 선택했다. 반대로 기존 formatter와 충돌하는 여섯 조건 개행은 ignore·가짜 별칭을 늘리는 비용보다 이득이 작아 원래 표현을 유지했다. 테스트 통과는 동작 보존의 근거이며 이 읽기 이득을 대신하지 않는다. 구현·독립 검토·최종 설명에서는 어떤 연결이 줄고 어떤 비용이 남는지 현재 소비자와 대조한다.

[전수 검토와 선택 과정](2026-11-13-13-full-readability-review-and-refinement.md), [전체 보고·반영·검증 자료](../output/2026-11-13-readability-review/README.md)를 보존한다. 여섯 검토자가 각각128파일을 읽은 것은 이번 사용자의 명시 요청이었다. 다음 작업마다 여섯 검토자·전수 조사를 자동 실행하는 규칙은 아니다. 과거 기록13의 미커밋·4단계 설명 미착수는 당시 상태이며 현재 상태는 아래와 재개 안내를 따른다.

## 분리 커밋의 검증 범위를 정할 때

사용자의 “무슨 검사를 이렇게 오래하는거야?”라는 지적에 Main은 다음과 같이 인정했다.

> Main: “분리하면서 빠진 의존성이 없는지 확인하려고 기본 테스트에 실제 DB 검사까지 붙였는데, 커밋 요청에 비해 확인을 넓게 잡았습니다.”

섞인 변경에서4단계만 분리하는 일 자체에도 시간이 들었지만, Main은 추가 실제 DB 검사로 확인을 넓힌 판단도 과했다고 정정했다. 후보 client72·server73은 통과했고, 별도 PG 검사는 pnpm 문제로 테스트 전 준비에서 실패했다. 임시 자원을 정리하고 이를 복구하느라 추가 재시도하지 않은 채 분리 범위 감사와 확보한 근거로 커밋했다. 미실행 PG를 통과로 처리하지 않았다.

이후 커밋을 준비할 때는 **분리판에서 바뀐 의존성·실행 조건 때문에 새로 확인해야 하는 부분과, 같은 판본·동작의 기존 근거를 재사용할 부분을 먼저 구별**한다. 후보가 단독으로 연결되는지 확인은 필요하지만 커밋 요청만으로 실환경 전체 검증을 자동 확장하지 않는다. 반대로 사용자 지적을 테스트 금지나 필요한 검사 생략 승인으로 일반화하지 않는다. 실제 남은 불확실성이 추가 실행을 요구한다면 그 이유와 범위를 판단한다. [4단계 분리 기록](2026-11-13-15-stage-four-isolated-commit.md)에 실행한 검사와 한계가 있다.
