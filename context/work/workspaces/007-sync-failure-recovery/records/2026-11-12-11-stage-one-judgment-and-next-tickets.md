# 1단계 판단 과정의 남은 아쉬움과 두 후속 Ticket

1단계는 8f94af5c로 분리 커밋했고 부모 a527e977는 경로 처리다. 이후 사용자는 작업 과정의 종합 분석을 요청했지만, 변경 이력·관점 목록과 기술스택 항목 보강에 머문 답을 여러 번 정정했다. Main의 마지막 종합 뒤에도 사용자는 **“아직도 뭔가 아쉬워”**라고 말하고, 다른 세션에서 코드 후속과 검토·판단 개선을 두 Ticket으로 진행하도록 요청했다. 아래 분석을 사용자 최종 만족·정본 규칙 채택으로 올리지 않는다.

요청·정정·Main 종합·별도 self-check 보고의 핵심 원문은 [중앙 대화 발췌](../source/2026-11-12-stage-one-review-dialogue.md)에 한 번 보존했다. 이 기록은 왜 판단을 바꿨는지와 다음 작업의 열린 지점을 소유한다. 원문에 접근해도 Main이 골라 놓은 해석을 그대로 이어받지 않도록 사례별 근거를 연결한다.

## 목록을 더하는 대신 같은 선택의 전제를 검증한다

사용자가 기술스택의 공식 동작·코드 세부를 강조한 것은 전체 검토에 따로 추가할 항목 하나가 부족하다는 뜻으로 확정되지 않았다. 원문 9833행은 그것이 **전반적인 디테일 부족의 사례**라고 바로잡았다. 각 선택에서 처음 전제, 실제 소비자·호출·수명, 공식 동작·기존 코드·Context, 반례가 어떤 관계였는지 확인해야 했다. 다음은 재개자가 다시 판단할 근거이며 보편 규칙 목록으로 승격한 결론이 아니다.

### 공통 잠금: 보호가 필요한 상황부터 잘못 묶었다

처음 전제는 RHF 제출 상태만으로 렌더 전 두 호출이나 A 저장 중 B 전환을 막지 못하므로 공통 ref/state 잠금이 필요하다는 것이었다. 첫 검사는 두 fireEvent를 같은 act로 묶었고, 두 번째는 부모 props를 강제 교체했다. 실제 사용자 순차 탭·현재 버튼 상태·일반 탐색 경로와 같은 장면이 아니었다.

사용자가 isSubmitting과 테스트 방식을 거슬러 질문하자 ref 없는 최소 폼의 grouped fireEvent는 2회, 별개 fireEvent·순차 userEvent는 각각 1회였다. React/RHF의 동작을 설치 환경의 재현·화면 조건과 함께 대조하면서 추가 잠금의 근거가 무너졌다. 공통 잠금은 제거했다. 반면 사라진 A의 늦은 결과가 B의 입력·안내·닫기와 B 자체 제출 상태를 건드리지 않는 보장은 별도 수명 검사로 유지했다.

라이브러리 활용이라는 항목보다 **근거가 다른 두 문제에 같은 제한을 붙였던 판단을 철회한 과정**이다. 처음부터 테스트 모델과 사용자 경로를 구별하지 않아 사용자가 반복 질문해야 했던 부담도 남는다. [실험·검사 수정·853 판본의 범위](2026-11-12-05-rhf-submitting-and-user-events.md)를 읽는다.

### 초기화: 현재 구조의 필요성을 설명한 뒤 구조 자체를 다시 보았다

defaultValues가 있는데 reset이 필요한가라는 질문에 Main은 계속 마운트된 폼이라는 현재 구조만 설명했다. 부모가 언제 새 편집을 만들고, 배경 조회가 무엇을 갱신하며, 일정 시간대와 장소 기준을 어디에 둘지가 함께 검토돼야 했다.

사용자가 isOpen 하나에 한정하지 말고 React 공식 문서를 근거로 더 간결하게 보라고 정정한 뒤, 내부 폼의 조건부 마운트·ID key·초기 snapshot으로 편집 수명을 표현했다. 초기화 effect와 기준 ref는 제거했지만 같은 편집의 배경 조회 보호·해제 뒤 응답 보호는 유지했다. 단순 초기값 콜백은 state 수명의 보장과 무관하므로 다시 제거했다.

성공 후 reset도 계속 열린 소비자를 이유로 남겼으나, 실제 두 Screen의 onClose가 폼을 해제한다는 점과 사용자 성공 닫기 선택을 대조한 뒤 제거했다. isCurrentEdit는 입력 동일성 검사가 아니라 mount 상태라는 역할에 맞게 isMounted로 바꿔 유지했다. **공식 동작·실제 소비자·사용자 선택이 같은 코드의 제거 근거로 이어진 사례**다. [구조 선택](2026-11-12-03-react-official-save-ui.md), [단순 initializer 정리](2026-11-12-04-stage-one-expression-cleanup.md), [성공 닫기 소비자](2026-11-12-07-success-close-and-mounted-guard.md)를 필요한 범위로 읽는다.

### 입력 보존: 구현을 다루며 새 요구까지 더하려 했다

Main은 닫기를 논의하며 초안 복구까지 필요하다고 연결했다. 그러나 활성 여행의 이미 저장된 행·큐, 열린 폼의 실패 입력, 닫힌 폼의 미제출 입력은 다른 수명이다. pending 보호·구버전 원문 보존을 모든 초안의 영속 복구로 확대할 합의는 없었다.

같은 폼에서 30 제출 뒤 대기 중 35를 입력하면 성공 닫기로 사라지는 조건을 재현했지만, 사용자는 제출한 값이 저장되면 그냥 닫도록 선택했다. 새 초안 저장소·추가 입력 감지·자동 재저장·일괄 입력 잠금은 추가하지 않았다. 닫기 시도에는 안내하고, 이미 Local·큐로 확정한 다른 요청의 보호는 유지한다. 모든 입력 손실을 해결한 기능이 아니라 **어떤 입력을 제공 범위에 둘지 사용자가 선택한 결과**다. [당시 미정](2026-11-12-06-pending-close-notice-and-input-gap.md)과 [후속 확정](2026-11-12-07-success-close-and-mounted-guard.md)을 구별한다.

### 저장 계층·경로: 반복되는 모양보다 실제 책임을 대조했다

prepareEdit를 여러 번 부르는 모습만으로 중복 발급 버그라고 단정하지 않았다. 하위 호출자는 Repository뿐이고 재전송은 큐 원문을 별도 전송한다는 경로를 확인해 준비 책임을 모았다. 하위 PreparedEdit 계약은 좁혔지만 HTTP 검증, SQLite 변환, 행+큐 트랜잭션, 여행 작업 등록 순서는 이유가 달라 유지했다. 하위 직접 발급 검사를 prepared fixture로 바꾼 것도 실제 내부 계약에 맞춘 결과다.

경로는 폼 계산을 다른 훅으로 옮기는 것만으로 제목 변경 요청·좌표가 바뀐 같은 ID 캐시·늦은 응답·중복 행이 해결되지 않았다. 현재 Local 일정과 날짜별 구간, 좌표/profile 재사용, 네트워크 전후 DB 확인·짧은 트랜잭션을 함께 확인해 책임과 실행 범위를 바꿨다. 기존 날짜·query-refresh·matcher·DB 유틸의 실제 의미도 대조했다.

줄 수보다 **한 변경을 이해할 때 어느 경계를 봐야 하는가, 제거하면 무엇이 깨지는가**가 근거였다. [경로 범위와 검사](2026-11-12-08-route-preparation-scope-and-cache.md), [저장 계층 전체 판](2026-11-12-09-route-commit-and-save-boundaries.md)을 읽되 현재 분리 커밋은 [자체 완결 기록](2026-11-12-10-stage-one-isolated-commit.md)으로 구별한다.

### 설명·검토 운영: 근거를 드러냈고 불필요한 재작업도 만들었다

특정 ref 의문을 검토자의 정답처럼 주지 않은 것, 범위를 좁히되 호출 관계는 함께 본 것, Personal·공식 문서·기존 코드를 대조한 것, 검토와 검증·분리판 검사를 구별한 것은 개별 선택을 판단하는 조건이었다. 그렇다고 여러 번 검토한 사실 자체를 좋은 과정으로 포장하지 않는다. 소비자·대안을 처음에 충분히 보지 못하고 강제 테스트를 실사용으로 확대해 사용자가 다시 지시한 재작업도 있었다.

오버로드는 설명만 정정하고 코드는 유지한 사례다. 순서는 준비를 기다리기 전 작업 등록이, overload는 인자 관계의 타입이 맡는다. 순서가 필요하므로 세 선언이 기능상 필수라는 연결을 철회했다. 설명에서 이유를 구체화한 뒤 무엇이 틀렸는지에 따라 **설명만 고칠지 코드까지 바꿀지** 판단해야 했다.

## 감사 해석과 여전히 열린 종합

사용자는 9833행에서 ai-self-check를 직접 요청했다. 별도 담당자는 9888행에서 필요하다고 판정하고, Main이 실제 판단의 종합을 미래 관점 목록으로 옮겼으며 검토 깊이의 문제를 기술스택 설명 부족으로 좁혔다고 보고했다. 이는 원문을 읽은 **담당자의 잠정 감사 해석**이며 새 스킬 규칙이나 사용자 채택으로 취급하지 않는다.

Main은 9892·9904행에서 사례 중심 분석·재구성을 내놓았지만 사용자는 9911행에서도 아쉬움을 남겼다. 이 종합을 최종 해석으로 전달하지 않는다. 향후 개선에서는 원문·실물을 다시 대조해 어떤 적용·위임·판단·설명 경로를 바꿀지 판단해야 하며 지금 스킬 수정안을 확정하지 않았다.

## 두 작업은 독립적으로 시작한다

[007 Ticket 09](../current/memory/tickets/09-staged-code-review-and-refinement.md)는 이미 한 차례 high 검토·수정·검증한 2〜7단계 결과를 취소하지 않고, 그 뒤 아직 하지 않은 단계별 코드 설명·질문과 연결한 후속 검토를 맡는다. 실제 코드 확인→필요 수정/정리→독립 리뷰·검증→사용자 설명을 2단계부터 순차 수행한다.

[009 Ticket 01](../../009-development-review-improvement/current/memory/tickets/01-stage-one-review-and-judgment-loop.md)은 원문·사례·감사 해석으로 스킬·판단 운영의 개선 필요와 방법을 정한다. 코드 Ticket을 시작하기 전에 이 작업이 끝나야 한다는 의존은 없다.

원래 007-07·003-12의 정책·선행 검증은 유지한다. 단계는 설명 구획이며 push/pull 고정 실행 순서가 아니다. 8f94af5c와 부모 a527e977 위에 2〜7단계 제품·문서가 미커밋으로 남아 있으므로 전체 reset·복사본 덮어쓰기·일괄 stage를 하지 않는다. 남은 native 실행·배포도 별도다.

이번 직접 읽기는 같은 Main 원문 **9624〜9941행**, stop anchor는 9911행 요청과 9936행 분리 안내다. 앞선 사례의 대조는 기존 기록 담당의 확인을 재사용했으며 제품 검사를 이번에 다시 실행하지 않았다. 원문 user/assistant/agent 지위를 구별했다.

## 후속 문서 커밋 권한

원문 10171행에서 사용자는 “코드 작업부는 확인해야되니까 커밋하지말고 기록이나 이런 부분들은 잘 커밋하자”라고 요청했다. 문서만 선별해 보존하는 승인이고 미검토 2〜7단계 제품 코드 커밋 승인은 아니다. 마지막 제품 코드 기준 8f94af5c와 경로 a527e977는 유지하며, 이후 문서 커밋으로 실제 HEAD가 달라질 수 있다. 이번 추가는 같은 원문의 9942〜10189행을 읽고 반영했으며 문서 커밋 수행 완료를 뜻하지 않는다. 앞선 분석·검사·사용자 선택은 바꾸지 않는다.
