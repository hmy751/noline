# 현재 상태와 다음 행동

동기화 실패 복구 1단계와 [Ticket 08](../memory/tickets/08-orphaned-queue-task-blocks-login.md)을 마쳤다. 원본과 검증된 소유자 기록이 모두 없는 구버전 삭제 요청은 격리하며, 여행을 비활성화해도 보존하고 기기 DB 전체를 비울 때 함께 지운다. 현재는 [Ticket 06](../memory/tickets/06-stalled-sync-visibility.md)에서 앱·서버의 Sentry 연결과 Release 시뮬레이터의 로컬 수신을 확인했다. 실제 Sentry에 시험 이슈와 실행 기록이 도착했다.

## 현재 결과

### Ticket 06

앱·서버 SDK를 연결했다. Release 시뮬레이터와 로컬 수신기에서 격리 후 정상 작업 전송, 로그아웃 이후 이전 진단 수신, 시작만 남은 앱 중단, 전송 전 중단·404 반복·응답 유실을 대조했다. 11월 10일 실제 프로젝트에서 서버 시험 이슈와 앱 staging 경고의 trace를 확인하고 iOS Hermes 소스맵을 올렸다. 실제 앱 TypeError의 원래 JS 파일·행과 코드를 복원했다. 두 프로젝트에 기본 Error 알림을 설정했고, 신규 이벤트에서 IP가 보이지 않는 것을 확인했다. 사용자 정보 삭제 규칙 뒤에도 도시 정보는 보였다. 운영 앱·서버 배포와 EAS 비밀 설정은 별도다. [로컬 수신 검증](../../records/2026-11-09-01-sentry-local-receiver.md) · [실제 Sentry 시험·설정](../../records/2026-11-10-01-sentry-staging.md)

추가 검토에서 실제 여행 요청 전의 인증 갱신 실패와 서버 거절 로그의 환경·릴리스 누락을 발견했다. 앱에서 갱신 실패를 분리한 뒤 여행 요청 0회·1회 경로를, 서버에서 거절 로그의 환경·릴리스와 시작 실패 6개 조합을 다시 확인했다. 앱·서버 진단에서 허용할 값과 코드 위치도 좁혔다. 최신 통합판에서 앱 702개와 변경 lint, 서버 73개와 타입 검사·빌드가 통과했다. 독립 검증은 갱신 오류의 구분, Hermes 프레임·trace 필터, 서버 부팅과 로그 수신까지 확인했다. 앱 전체 타입 검사에는 기존 오류 7개가 남았다. 최종 staging 대시보드에서 서버의 일정 PUT 500·404 거절 로그와 앱의 인증 갱신 실패 시험 신호(503, 이전 실패 1회)를 확인했다. 앱에서는 한 실행의 시작·중단·종료가 같은 trace에 표시됐다. ### Ticket 08

- 원본 행이 없는 CREATE·UPDATE와 검증된 소유자 기록이 없는 구버전 DELETE는 작업 종류·payload·retryCount를 보존한 `QUARANTINED` 상태로 격리하고 자동 전송에서 제외한다. 로그인 검사에서는 이런 작업을 격리한 뒤 다음 작업으로 계속하지만, 원본과 요청 정보가 모순된 `invalid` 작업을 만나면 즉시 `unresolved`를 반환하므로 그 뒤 작업은 이번 호출에서 검사·격리하지 않는다. 동기화의 전송 목록 구성은 별도로 확인할 수 없는 작업을 격리한다.
- 확인할 수 없는 작업만 전송 FIFO에서 분리한다. 원본이나 검증된 요청 소유자로 확인되는 정상 작업의 실제 전송이 실패하면 기존처럼 뒤 작업은 기다린다.
- 한 번 격리한 작업은 앱을 다시 시작하거나 같은 record ID의 원본이 후속 pull로 돌아와도 자동 전송 상태로 복귀하지 않는다.
- 격리 요청만 남은 경우 같은 ID의 soft-delete 원본이 생겨도 기기 정리를 막지 않는다. 격리 요청 자체는 보존하며 로그아웃 때 손실 가능한 데이터 수에 포함한다.
- 같은 계정 로그인은 허용하지만, 원본이 있는 다른 계정 작업에 대한 보호는 유지한다.
- 새 여행·일정·경비 DELETE 요청에는 삭제 권한을 확인한 `userId`를 저장한다. soft-delete 표시와 요청 저장은 같은 트랜잭션에서 확정하므로 요청 저장이 실패하면 삭제 표시도 되돌아간다. 원본이 없어도 저장된 소유자와 로그인 계정이 같으면 삭제를 전송할 수 있고, 다른 계정이거나 원본과 요청의 소유자가 모순되면 차단한다. 기존 요청에는 현재 로그인 계정의 ID를 사후 부여하지 않으며, 원본도 검증된 소유자 기록도 없으면 기존처럼 격리한다. 서버의 인증·소유권 검사, soft-delete와 7일 정리 기준은 그대로다.
- Main은 최초 검토에서 Personal 코드 표현 기준과 Project 공유 타입 기준을 변경 코드에 충분히 대조하지 못했다고 정정했다. 재확인 뒤 코드 표현을 맞추고, 격리 요청을 삭제한 것처럼 기록하던 로그 세 곳을 제거했으며, 공유 queue 상태 정의와 회귀 검사에 `QUARANTINED`를 추가했다고 보고했다.
- Main은 `development` 스킬을 적용해 구현·개선 검토·최종 검증을 서로 다른 담당자에게 맡겼다고 보고했다. 계획된 Sonnet 담당은 Claude CLI 로그아웃 때문에 Codex 담당자로 대체했으며, 최종 검증자는 구현과 검토에 참여하지 않았다.
- iPhone 15 Pro 시뮬레이터에서 같은 계정 로그인, 정상 일정 CREATE 1건의 push, 일정·경비 pull, 앱 완전 종료 뒤 격리 작업 3건의 보존을 확인했다고 Main이 보고했다. 확인 뒤 시험 작업 세 건만 제거했으며 시뮬레이터는 로그인 상태다.
- 격리 보완 후 독립 검증에서 client 테스트 677개 통과, iOS 개발 번들 생성과 변경 파일 포맷 검사 통과를 확인했다고 Main이 보고했다. 후속 소유자 저장 구현에서는 실제 SQLite로 소유자 기록·다른 계정 차단·요청 저장 실패 때 rollback을 확인했고, client 테스트 691개와 iOS 개발 번들 생성이 통과했다고 보고했다. 전체 타입 검사에는 기존 오류 8개가 남아 있다.
- 이어 iPhone 15 Pro 시뮬레이터에서 앱의 실제 일정 삭제·동기화 함수를 호출해, 서버에 먼저 저장한 시험 일정을 앱에서 삭제하고 기기 원본만 제거한 뒤에도 요청의 `userId`로 로컬 개발 서버에 삭제를 반영했다고 Main이 보고했다. 서버 PostgreSQL에 삭제 시각이 기록되고 처리된 요청은 큐에서 제거됐으며 최종 미전송 요청은 0건이었다. 화면의 삭제 버튼 조작과 다른 계정으로 실제 로그인하는 전환은 하지 않았다. 다른 계정 차단과 여행·경비 삭제는 다시 통과한 자동 테스트 691개가 근거다.
- 2026-11-09 사용자가 여행 단위 정리와 기기 DB 전체 초기화의 경계를 확정했다. 여행을 오프라인 해제하거나 오래된 사본을 정리해도 격리 요청은 남는다. 기기 DB 전체를 비워 큐가 지워지면 격리 요청도 함께 지워진다. 이 정책은 기존 구현과 일치해 마무리 시 제품 코드 변경은 없었다.
- 2026-11-07 Project 가이드에 격리와 새 DELETE 소유자 기록을 반영했다(`89bf4fd8`). 실제 1.0.1 업데이트 설치 과정은 확인하지 않았다. 격리 구현의 로컬 커밋은 `06cebd6f`이며 아직 배포하지 않았다. 새 DELETE 소유자 저장은 로컬 커밋 `30783ccb`에 있다. 구현 위치는 [output](../../output/index.md)에서 찾는다.

## 다음 행동

1. **Ticket 06:** 최신 수정판의 로컬 검증과 staging 대시보드 수신 확인을 마쳤다. 신규 이벤트에 도시 정보가 계속 표시되는 원인과 운영 수집 기준도 확인한다. 반복 동기화 Warning 전용 규칙은 아직 없으므로 기본 Error 규칙과 별도로 적용할지 판단한다.
2. **[Ticket 07](../memory/tickets/07-conflict-rule-and-cleanup.md):** 일정·경비 UPDATE, 구버전 요청의 보류·안내·선택적 재저장, 자기 여행 삭제 시 미전송 일정·경비 정리, 일정 삭제 시 경비 연결 해제와 삭제된 기록의 UPDATE 종결을 확정했다. 003 Ticket 12는 수신 중 미전송 수정을 보호하고, 07은 전송 시 최종 값과 큐 종결을 맡는다. 구현 전이며 003 Ticket 13의 부모 확인과 008의 안내 세부를 맞춘다.
3. **Ticket 04:** 사용자가 확인할 수 있을 때 외부 주기 헬스체크의 주기·대상·Render 무료 사용 시간 한도와 실제 효과를 확인한다. 확인 전에는 잠든 서버 문제가 해결됐다고 말하지 않는다.
4. **출시 상태:** App Store 심사·출시 결과가 확인되면 Ticket 05와 이 state를 갱신한다.

사용자에게 보이는 멈춤 표시와 복원 실패 안내 규칙은 [Workspace 008](../../../008-exception-notice-rules/README.md)이 소유한다. 이 Workspace는 자동으로 그 current를 갱신하지 않는다.

## 확인 범위와 한계

- 2026-11-09 Main이 재개 시 격리 회귀 검사 30개를, 마무리 시 격리·로그아웃 동기화·정리 수명 관련 Jest 검사 3개 묶음 48개를 실행해 모두 통과했다. 마무리 때 홈 화면의 비활성화 버튼은 코드 경로로 대조했다. 시뮬레이터에서 다시 조작한 결과는 아니다.
- 1단계 제품 Verify receipt는 2026-11-03 서버 재전송 route 단위 claim에 대한 통과다. Ticket 08 변경과 실제 PostgreSQL·앱 업데이트 경로를 입증하지 않는다.
- Ticket 08의 시뮬레이터 확인은 1.0.1에서 남을 수 있는 DB 상태를 현재 개발 앱에 만든 검사다. 실제 1.0.1 설치 후 업데이트는 재현하지 않았다.

- 외부 헬스체크 효과, 연결이 자주 끊기는 실제 사용의 sync 시작 빈도, 10-31 응답 유실 원인은 여전히 확인되지 않았다.
