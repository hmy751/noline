## 확인 상태

- **01·02의 확인 근거:**
  - Main이 서버 typecheck·build, 서버 단위 69·통합 21, 앱 Jest 655, 라우트를 되돌렸을 때의 실패 재현을 실행했다.
  - 구현에 참여하지 않은 별도 검증자(Sonnet, medium)가 같은 검사를 다시 실행하고 코드와 문서를 대조했다. 완료 조건 전부에 충족 근거가 있다고 판정했다. 되돌림 재현만 미확인으로 남겼다.
- **개선 검토 (뒤늦게 실행):** 구현 뒤 별도 개선 검토자(Sonnet, medium)가 선택들을 다시 봤다. 채택한 보완 세 가지는 Sonnet 구현자와 Main이 반영했고, 기존 검증자가 재확인했다. 셋은 비용 문장, 방어 분기 주석, 테스트 파일 이름이다.
- **Ticket 03의 확인 근거:**
  - Main이 11-02의 막힌 DB에 IN_PROGRESS 일정을 더해 시뮬레이터 앱을 실행했다. 첫 동기화에서 세 작업이 200으로 끝나고 pull이 돌았으며 큐가 비었다. 서버 일정 행은 1개를 유지했다.
  - 별도 검증자(Sonnet, medium)가 같은 준비로 다시 실행했고, HEAD에서 서버 typecheck·단위 69·통합 21과 client 655를 다시 돌렸다. 01·02·03의 완료 조건을 요구별로 충족 근거 있음으로 판정했다. "서버 수정을 되돌리면 실패"만 미확인이다.
  - 동기화는 약 4분 동안 1번 시작했다. 실행 조건이 새로 갖춰질 때와 수동 실행에서만 돈다. 숨은 반복이 없다는 것만 확인했고, 실제 사용의 빈도는 모른다. 간격 재시도는 보류했다.
- **아직 확인하지 않은 것:**
  - 수정 전 서버와의 실제 앱 대조, 실제 앱의 실패·인증 오류 경로, 실제 응답 유실은 재현하지 않았다.
  - 10-31의 "1분 안에 실패 3번"이 왜 생겼는지는 로그가 없어 모른다.
  - 연결이 자주 끊기는 실제 사용에서 sync가 얼마나 자주 시작되는지 모른다. 한도 제거로 생긴 헛요청의 실제 크기가 여기에 달려 있다.
  - 최종 판본에서 서버 단위 테스트가 연달아 두 번 실패한 뒤로는 재현되지 않았다. 순차 38번, 동시 4개 프로세스, 순서 섞기 8번 모두 통과였다. 원인은 미확인이고, 이번 변경 때문일 가능성은 낮다고 판단했다. 근거는 [Ticket 01](../memory/tickets/01-server-replay-responses.md#현재-상태와-실제-결과)에 있다.
