# 현재 상태와 다음 행동

동기화 실패 복구의 1단계와 실제 앱 확인은 끝났다. 2026-11-06에는 원본 없는 큐 작업이 복원과 로그인을 막는 [Ticket 08](../memory/tickets/08-orphaned-queue-task-blocks-login.md)에서 CREATE·UPDATE·DELETE를 모두 격리하는 구현과 검증을 마쳤다고 Main이 보고했다. 이후 Context 적용을 다시 대조해 코드 표현, 실제 상태와 다른 성공 로그, 공유 schema의 `QUARANTINED` 누락을 고치고 재검증했다고 보고했다. 격리 구현은 로컬 커밋 `06cebd6f`에 있으며 배포 전이다. 2026-11-07에는 새 여행·일정·경비 DELETE 요청에 삭제 시점의 검증된 `userId`를 원자적으로 저장하고 그 근거로 계정을 검사하는 후속 구현과 회귀 검사를 로컬 커밋 `30783ccb`에 저장했다. 원본 없는 구버전 DELETE를 계속 보존할지는 여전히 열려 있으므로 Ticket 08은 아직 최종 처리 규칙을 확정하지 않았다. 이 판단을 마친 뒤 반복 실패의 운영 기록을 맡는 Ticket 06과 충돌 처리를 맡는 Ticket 07을 이어간다.

## 현재 결과

### 1단계와 출시

- 서버의 생성·삭제 재전송 처리와 테스트는 `ba91d1a3`, 앱 큐의 IN_PROGRESS 복구와 재시도 한도 제거는 `437cc5c7`, Project 계약 반영은 `7f8cb819`에 있다. 선택 이유를 보완한 Project 형성 자료는 `74a402a4`다.
- 실제 앱과 독립 검증에서 기존 FAILED·retryCount 3 작업과 IN_PROGRESS 작업이 풀리고 push 뒤 pull까지 진행되는 것을 확인했다. 상세 근거는 [실제 앱 확인 기록](../../records/2026-11-03-05-stage-one-real-app-verification.md)에 있다.
- 서버는 2026-11-03 배포됐고 TestFlight 1.1.0 build 13을 App Store 심사에 제출했다. supplied current에서 확인되는 마지막 상태는 심사 대기 중이며 이후 심사·출시 결과는 아직 이 Workspace에 반영되지 않았다. 배포 경과는 [배포 기록](../../records/2026-11-03-08-release-deploy-and-build-13.md)에 있다.

### Ticket 08

- 원본 행이 없는 CREATE·UPDATE와 검증된 소유자 기록이 없는 구버전 DELETE는 작업 종류·payload·retryCount를 보존한 `QUARANTINED` 상태로 격리하고 자동 전송에서 제외한다. 로그인 검사에서는 이런 작업을 격리한 뒤 다음 작업으로 계속하지만, 원본과 요청 정보가 모순된 `invalid` 작업을 만나면 즉시 `unresolved`를 반환하므로 그 뒤 작업은 이번 호출에서 검사·격리하지 않는다. 동기화의 전송 목록 구성은 별도로 확인할 수 없는 작업을 격리한다.
- 확인할 수 없는 작업만 전송 FIFO에서 분리한다. 원본이나 검증된 요청 소유자로 확인되는 정상 작업의 실제 전송이 실패하면 기존처럼 뒤 작업은 기다린다.
- 한 번 격리한 작업은 앱을 다시 시작하거나 같은 record ID의 원본이 후속 pull로 돌아와도 자동 전송 상태로 복귀하지 않는다.
- 격리 요청만 남은 경우 같은 ID의 soft-delete 원본이 생겨도 기기 정리를 막지 않는다. 격리 요청 자체는 보존하며 로그아웃 때 손실 가능한 데이터 수에 포함한다.
- 같은 계정 로그인은 허용하지만, 원본이 있는 다른 계정 작업에 대한 보호는 유지한다.
- 새 여행·일정·경비 DELETE 요청에는 삭제 권한을 확인한 `userId`를 저장한다. soft-delete 표시와 요청 저장은 같은 트랜잭션에서 확정하므로 요청 저장이 실패하면 삭제 표시도 되돌아간다. 원본이 없어도 저장된 소유자와 로그인 계정이 같으면 삭제를 전송할 수 있고, 다른 계정이거나 원본과 요청의 소유자가 모순되면 차단한다. 기존 요청에는 현재 로그인 계정의 ID를 사후 부여하지 않으며, 원본도 검증된 소유자 기록도 없으면 기존처럼 격리한다. 서버의 인증·소유권 검사, soft-delete와 7일 정리 기준은 그대로다.
- Main은 최초 검토에서 Personal 코드 표현 기준과 Project 공유 타입 기준을 변경 코드에 충분히 대조하지 못했다고 정정했다. 재확인 뒤 코드 표현을 맞추고, 격리 요청을 삭제한 것처럼 기록하던 로그 세 곳을 제거했으며, 공유 queue 상태 정의와 회귀 검사에 `QUARANTINED`를 추가했다고 보고했다.
- Main은 `development` 스킬을 적용해 구현·개선 검토·최종 검증을 서로 다른 담당자에게 맡겼다고 보고했다. 계획된 Sonnet 담당은 Claude CLI 로그아웃 때문에 Codex 담당자로 대체했으며, 최종 검증자는 구현과 검토에 참여하지 않았다.
- iPhone 15 Pro 시뮬레이터에서 같은 계정 로그인, 정상 일정 CREATE 1건의 push, 일정·경비 pull, 앱 완전 종료 뒤 격리 작업 3건의 보존을 확인했다고 Main이 보고했다. 확인 뒤 시험 작업 세 건만 제거했으며 시뮬레이터는 로그인 상태다.
- 격리 보완 후 독립 검증에서 client 테스트 677개 통과, iOS 개발 번들 생성과 변경 파일 포맷 검사 통과를 확인했다고 Main이 보고했다. 후속 소유자 저장 구현에서는 실제 SQLite로 소유자 기록·다른 계정 차단·요청 저장 실패 때 rollback을 확인했고, client 테스트 691개와 iOS 개발 번들 생성이 통과했다고 보고했다. 전체 타입 검사에는 기존 오류 8개가 남아 있다.
- 이어 iPhone 15 Pro 시뮬레이터에서 앱의 실제 일정 삭제·동기화 함수를 호출해, 서버에 먼저 저장한 시험 일정을 앱에서 삭제하고 기기 원본만 제거한 뒤에도 요청의 `userId`로 로컬 개발 서버에 삭제를 반영했다고 Main이 보고했다. 서버 PostgreSQL에 삭제 시각이 기록되고 처리된 요청은 큐에서 제거됐으며 최종 미전송 요청은 0건이었다. 화면의 삭제 버튼 조작과 다른 계정으로 실제 로그인하는 전환은 하지 않았다. 다른 계정 차단과 여행·경비 삭제는 다시 통과한 자동 테스트 691개가 근거다.
- 검증된 소유자 기록이 없는 구버전 DELETE도 계속 격리할지, 자동 삭제하고 CREATE·UPDATE만 보존할지는 아직 열린 판단이다. 사용자는 이 논의를 Ticket 08에서 계속하는 것으로 확인했다.
- Project 전체 정책 문서에는 Ticket 08의 예외를 아직 반영하지 않았고, 실제 1.0.1 업데이트 설치 과정도 실행하지 않았다. 격리 구현의 로컬 커밋은 `06cebd6f`이며 아직 배포하지 않았다. 새 DELETE 소유자 저장은 로컬 커밋 `30783ccb`에 있다. 구현 위치는 [output](../../output/index.md)에서 찾는다.

## 다음 행동

1. **Ticket 08 처리 규칙:** 원본도 검증된 소유자 기록도 없는 구버전 DELETE를 자동 삭제할지 계속 격리할지 결정한다. 새 DELETE는 저장된 `userId`가 로그인 계정과 맞으면 원본 없이도 전송하며, 일정의 시뮬레이터·로컬 개발 서버 경로는 확인했다.
2. **Ticket 08 마무리와 전달:** 선택이 현재 구현과 다르면 코드와 회귀 검사를 맞춘다. 배포는 별도로 진행하며, 실제 1.0.1 업데이트 설치 경로, 물리 기기 UI 조작과 다른 계정 실제 로그인 전환은 미확인으로 유지한다.
3. **Ticket 06:** 반복 실패 횟수와 서버 거절 이유를 어디에 어떤 식별자로 남길지 정하고, 출시 빌드에서 개발자가 막힘을 확인할 수 있게 한다.
4. **Ticket 07:** Ticket 06의 관측 결과와 003 Ticket 13의 부모 소유권 결과를 바탕으로 서버·기기 충돌을 끝내는 규칙을 정한다.
5. **Ticket 04:** 사용자가 확인할 수 있을 때 외부 주기 헬스체크의 주기·대상·Render 무료 사용 시간 한도와 실제 효과를 확인한다. 확인 전에는 잠든 서버 문제가 해결됐다고 말하지 않는다.
6. **출시 상태:** App Store 심사·출시 결과가 확인되면 Ticket 05와 이 state를 갱신한다.

사용자에게 보이는 멈춤 표시와 복원 실패 안내 규칙은 [Workspace 008](../../../008-exception-notice-rules/README.md)이 소유한다. 이 Workspace는 자동으로 그 current를 갱신하지 않는다.

## 확인 범위와 한계

- 1단계 제품 Verify receipt는 2026-11-03 서버 재전송 route 단위 claim에 대한 통과다. Ticket 08 변경과 실제 PostgreSQL·앱 업데이트 경로를 입증하지 않는다.
- Ticket 08의 시뮬레이터 확인은 1.0.1에서 남을 수 있는 DB 상태를 현재 개발 앱에 만든 검사다. 실제 1.0.1 설치 후 업데이트는 재현하지 않았다.
- 새 DELETE 소유자 저장은 실제 SQLite 검사, 자동 테스트, iOS 개발 번들과 iPhone 15 Pro 시뮬레이터의 실제 삭제·동기화 함수에서 확인했다. 시뮬레이터는 로컬 개발 서버 PostgreSQL까지 삭제를 반영했지만 화면의 삭제 버튼, 물리 기기와 다른 계정 실제 로그인 전환은 확인하지 않았다.
- Ticket 08의 역할 배치, 모델 대체, 수정 내용, 테스트 수와 결과, 번들 생성, SQLite·시뮬레이터·로컬 서버 검사, 제외한 화면·계정 전환, 타입 검사와 lint의 기존 실패 여부는 Main의 보고다. 이번 Maintain 판단은 해당 코드나 실행을 독립적으로 다시 대조하지 않았다.
- 외부 헬스체크 효과, 연결이 자주 끊기는 실제 사용의 sync 시작 빈도, 10-31 응답 유실 원인은 여전히 확인되지 않았다.
