# 품질과 완료

## 1단계를 완료로 판단할 근거

1단계의 결과는 흔한 세 길이 '도착'으로 끝나는 것이다. 테스트 통과만으로 판단하지 않고, 실제 앱에서 막힌 큐가 풀리는 것까지 확인한다.

| 영역 | 확인할 것 | 방법 |
| --- | --- | --- |
| 서버 (Ticket 01) | 생성 재전송 201→200과 행 1개, 동시 요청 [200, 201], 다른 사용자 409와 원래 행 불변, 다른 여행 409, 삭제 재전송 200과 처음 삭제 시각 유지, 다른 사용자 삭제 404, 여행 삭제 재전송 200 | PostgreSQL 통합 테스트와 route 단위 테스트. 수정을 잠시 되돌리면 같은 테스트가 이번 증상(중복 키 500, 삭제 404)으로 실패해야 한다 |
| 앱 (Ticket 02) | 남은 IN_PROGRESS 되돌림, 3회를 넘은 FAILED 재전송, 이전 앱의 FAILED·retryCount 3 회복, 실패 시 FIFO 멈춤 유지, 인증 오류 처리 유지 | Jest. 3회 한도를 고정한 기존 테스트는 새 계약으로 바꾼다 |
| 실제 앱 (Ticket 03) | 큐 맨 앞에 FAILED·retryCount 3인 CREATE가 있고 서버에 같은 행이 있는 개발 앱이, 새 서버와 새 앱에서 다음 동기화 때 풀린다. 뒤 작업과 pull까지 진행된다 | iOS 시뮬레이터와 로컬 서버. 서버 로그와 큐 상태 |
| 문서 (Ticket 01·02) | data-lifecycle의 "재전송은 별도 확인 대상"(42행)과 push 상태표(48–55행), api-contracts의 재전송 응답이 실제 동작과 맞는다 | 문서와 코드·테스트 대조 |
| 독립 검증 (Ticket 03) | 구현에 참여하지 않은 검증자가 최신 판본에서 위 근거를 확인한다 | 별도 검증자. 사용할 수 없으면 더 약한 근거임을 밝힌다 |

## 출시를 완료로 판단할 근거

- 서버 기동 지연을 측정하고, 대응을 정했다 (Ticket 04).
- 서버 배포 뒤 health와 재전송 응답을 확인했다. 배포는 사용자 승인 뒤에 한다.
- 앱 수정이 들어간 build 13을 TestFlight에서 확인했다. 1.1.0 심사 제출은 사용자가 한다.

## 2·3단계를 완료로 판단할 근거 (개요)

- **2단계 (Ticket 06):** 계속 실패하는 작업이 있을 때 출시 빌드에서 사용자나 개발자가 알 수 있음을 실제 화면이나 로그로 확인한다.
- **3단계 (Ticket 07):** 같은 기록의 미전송 생성·수정·삭제와 서버 수정·삭제의 조합을 재현한다. 채택한 규칙에서 화면·SQLite·서버가 같은 값에 도달함을 확인한다. 미확정 정책이 결과를 막으면 구현 완료로 닫지 않는다.

## 완료로 보지 않는 것

- 1단계 완료를 Work 전체 완료로 보지 않는다. 충돌과 우리 버그 경로의 정지가 남고, 여전히 보이지 않는다.
- 작업 트리에 CREATE 수정과 테스트가 있다는 사실만으로 Ticket 01 완료로 보지 않는다.
- Verify의 `verification_passed`는 기계 사실이며 사용자 수락이 아니다.
- 코드를 읽어 확인한 사실, 실제로 실행해 확인한 사실, 다른 주체의 보고, 추정을 구별해 기록한다.
