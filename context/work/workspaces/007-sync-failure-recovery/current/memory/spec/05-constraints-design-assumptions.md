# 제약·현재 설계·가정

## 제약

- 구현은 사용자의 진행 승인 뒤에 한다. 판단·설명 요청에서 코드나 문서를 바꾸지 않는다. 이 제약이 생긴 사용자 발화는 [source](../../../source/user-direction.md)에 있다.
- 커밋·푸시·배포는 사용자가 요청할 때만 한다. App Store 제출과 Render 플랜 변경은 사용자가 직접 한다.
- 운영 DB를 읽지 않는다. 비밀값과 환경변수 값을 출력하지 않는다.
- FIFO를 유지한다. 실패를 '완료'로 바꾸거나 큐를 비우지 않는다.
- 다른 사용자에게 자원 존재 여부를 드러내지 않는다.
- Project 문서는 context-update와 Project 관리 계약으로 반영한다.
- 003의 문서는 007에서 자동으로 고치지 않는다.

## 현재 설계: 주제별 선택

각 주제의 선택지를 같은 기준으로 비교한 표와 기각 이유는 [설계 판단 기록](../../../records/2026-11-03-01-sync-failure-design-decisions.md#주제별-선택지-비교)에 있다. 아래는 고른 것과 다시 볼 조건이다. 이는 현재 설계이며 고정 제약이 아니다. 새 근거가 선택 이유를 흔들면 다시 판단한다.

| 주제 | 고른 것 | 고른 이유 | 다시 볼 조건 |
| --- | --- | --- | --- |
| 재전송 처리 | 서버가 같은 사용자의 재전송이면 200 | 이미 반영됐는지와 누구의 행인지를 아는 쪽이 서버다. 앱이 409·404를 성공으로 보면 진짜 실패까지 지운다 | — |
| 끊긴 전송 | 전송을 시작할 때 IN_PROGRESS를 되돌림 | 가장 빨리 풀리고 한 곳에서 처리된다. 실행 잠금 때문에 안전하고, 실제로 보내진 뒤 끊겼어도 재전송 처리 덕분에 안전하다 | 동기화 실행 잠금이 바뀔 때 |
| 재시도 | 한도 없이 동기화 때마다 | "일시 오류 뒤"와 "버그를 고친 뒤"가 모두 풀리는 선택지 중 가장 단순하다. 상태 코드로 영구 실패를 가를 수 없다 | 동기화 계기를 늘릴 때, 실제 사용의 sync 시작 횟수를 얻거나 같은 작업의 실패가 자주 반복될 때 (헛요청의 크기는 아직 모르며 간격 재시도는 보류, Ticket 03) |
| 큐 구조 | 전체를 하나의 FIFO로 유지 | 모든 종속이 지켜지고, push 실패 시 pull 생략이 미전송 변경을 보호한다 | pull 보호가 생기거나, 예전 여행이 지금 여행을 막는 일이 실제로 보일 때 → 여행별 FIFO |
| 폐기 | 버리지 않음 | 조용한 손실이 없다. 횟수·시간 기준은 제품 약속과 충돌한다. 서버 기준 폐기는 충돌 규칙이, 사용자 선택 폐기는 표시 화면이 먼저 필요하다 | Ticket 06의 운영 기록이나 Workspace 008의 표시로 막힘이 실제로 보일 때 |
| 알림 | 다음 단계 (Ticket 06) | 사용자에게 무엇을 보일지 제품 결정이 필요하다 | 1단계 뒤 |
| 잠든 서버 | 외부 주기 헬스체크로 깨워 둠 (Ticket 04, 2026-11-03 사용자 결정) | 앱 변경 없이 동기화와 다른 화면 API를 함께 막는다. 비용이 없다 | 헬스체크 효과가 확인되지 않거나 멈출 때, 무료 사용 시간 한도를 넘길 때 → timeout 연장이나 유료 플랜 |

수정 1~3(Ticket 01·02)이 한 묶음인 이유도 이 표에서 나온다. "끊긴 전송"과 "재시도"의 선택은 같은 요청을 더 자주 다시 보내게 만든다. 다시 보내도 안전하려면 "재전송 처리"가 먼저 있어야 한다.

## 책임을 이렇게 나눈 이유

[개인 개발 기준](../../../../../../personal/development/INDEX.md)의 "누가 무엇을 알아야 하나"로 나누면 다음과 같다.

| 판단 | 그걸 아는 쪽 | 맡는 곳 |
| --- | --- | --- |
| 이 변경이 이미 서버에 반영됐나 | 서버 (DB에 같은 ID의 행이 있는지) | 서버 route의 응답 (Ticket 01) |
| 언제, 어떤 순서로 다시 보내나 | 앱의 큐 | sync engine (Ticket 02) |
| 다시 보내도 안 되는 변경을 어떻게 끝내나 | 사용자, 그리고 다른 기기와의 충돌 규칙 | 표시 (Ticket 06)와 충돌 규칙 (Ticket 07) |

앱이 500의 오류 문구를 읽고 "중복이면 성공"으로 처리하는 방법도 있었다. 하지만 이는 [계약·수명 기준](../../../../../../personal/development/contracts-and-lifetime/INDEX.md)이 구별하라고 하는 증상 대응이다. 서버 내부 문구에 기대게 되고, 오류 처리 문서가 공백으로 적어 둔 상세 노출에 의존하게 된다.

IN_PROGRESS는 같은 기준의 "상태의 수명" 문제다. "지금 보내는 중"이라는 뜻은 그 실행 동안에만 맞는데, DB에 저장되므로 실행이 끝난 뒤에도 남는다. 새 실행을 시작할 때 되돌리면 상태의 수명이 실제 실행과 맞춰진다.

## 가정 (확인 필요)

- 위 문서들의 빈도는 모두 측정하지 않은 추정이다.
- Render 무료 플랜은 15분 동안 요청이 없으면 잠들고, 깨어나는 데 약 50초가 걸린다. 50초는 2026-11-02에 한 번 관찰한 값이다. 이 지연이 15초 timeout을 넘겨 앱 시작 동기화를 실패시킨다는 것은 추정이다. 외부 주기 헬스체크가 서버를 깨워 둔다는 것도 아직 확인하지 않았다 (Ticket 04).
- 사례의 첫 응답 유실 원인은 모른다. 로그가 없다.
- 여행 삭제 재전송이 200이라는 것은 코드를 읽은 결과이며 테스트하지 않았다.
- 막힌 시뮬레이터 DB 백업은 임시 폴더에 있어 지워질 수 있다. 지워지면 Ticket 03은 재현 절차로 대신한다.
