# 요구 동작과 대표 사례

## 계속 지킬 의미

- **순서:** 큐는 생성 순서로 보내고, 실패하면 그 자리에서 멈춘다. 막힌 작업을 건너뛰거나 '완료'로 바꾸지 않는다. 같은 기록의 생성→수정→삭제, 경비→연결한 일정, 일정·경비 생성→여행 삭제의 순서가 이 규칙에 기대고 있다.
- **미전송 보존:** PENDING·IN_PROGRESS·FAILED는 모두 아직 서버에 없는 변경이다. 로그아웃 경고는 이 셋을 계속 센다.
- **존재 비노출:** 다른 사용자에게 자원이 있는지조차 드러내지 않는다.
- **완료 표시:** 실패한 동기화를 성공으로 표시하지 않는다.

## 1단계의 요구 동작

1. 같은 사용자가 이미 반영된 일정·경비 생성을 다시 보내면 처음과 같은 행을 성공으로 받는다.
2. 같은 사용자가 이미 지운 일정·경비의 삭제를 다시 보내면 성공한다.
3. 동기화 중 끊긴 작업은 다음 동기화에서 다시 보내진다.
4. 일시 오류는 몇 번이 쌓이든, 원인이 사라진 뒤의 동기화에서 도착한다.
5. 우리 서버 버그로 거절되던 작업은 서버를 고친 뒤의 동기화에서 저절로 통과한다.
6. 이전 앱에서 이미 3번 실패해 막힌 작업(FAILED, retryCount 3)도 새 앱에서 다시 보내진다.

## 비슷하지만 결과가 달라야 하는 사례

| 사례 | 결과 | 구별하는 이유 |
| --- | --- | --- |
| 같은 사용자·같은 여행의 생성 재전송 | 200, 기존 행 | 이미 반영된 같은 변경 |
| 같은 ID인데 다른 여행으로 생성 | 409 | 다른 변경이므로 성공으로 볼 수 없음 |
| 다른 사용자가 같은 ID로 생성 | 409, 원래 행은 바뀌지 않음 | 재전송이 아니며 행 내용을 드러내지 않음 |
| 이미 지운 자기 일정의 삭제 재전송 | 200, 처음 삭제 시각 | 이미 반영된 같은 변경 |
| 다른 사용자의 일정 삭제 | 404 (지금과 같음) | 존재 비노출 |
| 수정 재전송 | 200 (지금도 그렇다) | 같은 값을 다시 쓰고 version만 1 더 오름 |
| 이번 사고의 중복 키 500 (수정 전) | 몇 번을 보내도 실패 | 5xx이지만 영원히 실패하는 오류 |
| 우리 버그로 생긴 400 | 서버를 고치면 성공 | 4xx이지만 풀리는 오류. 상태 코드만으로 '영구 실패'를 가를 수 없다는 근거 |
| 전송을 시작하는 순간 남아 있는 IN_PROGRESS | PENDING으로 되돌려 다시 보냄 | 동기화는 잠금 때문에 한 번에 하나만 실행되므로 지난 실행이 남긴 흔적임 |

## 1단계 뒤에도 남는 동작 (받아들인 범위)

| 상황 | 1단계 뒤 | 끝내는 곳 |
| --- | --- | --- |
| 서버에서 이미 지운 기록을 고친 작업, 지운 여행에 일정을 만든 작업 | 계속 404로 실패하고 큐 전체와 pull이 멈춤 | Ticket 07 |
| 우리 버그로 거절되는 동안 | 고칠 때까지 멈춤 (고치면 풀린다는 점만 달라짐) | 개발자, Ticket 06의 표시 |
| 멈춰도 아무도 모름 | 출시 빌드에서는 로그아웃 경고뿐 | Ticket 06 |
| 변경이 서버로 가는 시점 | 지금처럼 앱 시작과 연결·로그인 회복 때만 | 열린 판단 |
| 오랜만에 연 앱이 잠든 서버에 걸림 | 영구 정지는 아니지만 다음 동기화까지 늦어짐 (추정) | Ticket 04 |

## 조금 나빠질 수 있는 것

- 예전에는 3번 실패하면 영영 가지 않던 수정이 이제는 늦게라도 도착한다. 그 사이 다른 곳에서 같은 기록을 고쳤다면 늦게 온 수정이 새 수정을 덮어쓴다. 다른 기기나 비활성 여행 직접 수정이 있어야 생기는 드문 경우이고, 막는 방법은 version 비교(Ticket 07)다.
- 끝내 실패할 요청도 동기화 때마다 다시 보낸다. 동기화는 앱 시작·연결 회복 때만 돌기 때문에 하루 몇 건 수준으로 추정한다. 다만 관찰 사례에서는 1분 안에 실패 3번이 쌓였고 그 원인을 확인하지 않았다. Ticket 03에서 실제 시작 횟수를 센다. 5xx면 HTTP client 재시도까지 한 번에 최대 4건이다.
