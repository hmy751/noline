# 요구 동작과 대표 사례

## 계속 지킬 의미

- **순서:** 큐는 생성 순서로 보내고, 실패하면 그 자리에서 멈춘다. 막힌 작업을 건너뛰거나 '완료'로 바꾸지 않는다. 같은 기록의 생성→수정→삭제, 경비→연결한 일정, 일정·경비 생성→여행 삭제의 순서가 이 규칙에 기대고 있다. 원본도 검증된 요청 소유자 근거도 없어 QUARANTINED로 분리한 작업은 전송 FIFO에 넣지 않는다.
- **미전송 보존:** PENDING·IN_PROGRESS·FAILED는 아직 서버에 없는 변경이고, QUARANTINED는 원본도 검증된 요청 소유자 근거도 없어 자동 전송할 수 없지만 버리지 않은 변경이다. 로그아웃 경고는 네 상태를 모두 손실 가능한 데이터로 센다.
- **존재 비노출:** 다른 사용자에게 자원이 있는지조차 드러내지 않는다.
- **완료 표시:** 실패한 동기화를 성공으로 표시하지 않는다.

## 1단계의 요구 동작

1. 같은 사용자가 이미 반영된 일정·경비 생성을 다시 보내면 처음과 같은 행을 성공으로 받는다.
2. 같은 사용자가 이미 지운 일정·경비의 삭제를 다시 보내면 성공한다.
3. 동기화 중 끊긴 작업은 다음 동기화에서 다시 보내진다.
4. 일시 오류는 몇 번이 쌓이든, 원인이 사라진 뒤의 동기화에서 도착한다.
5. 우리 서버 버그로 거절되던 작업은 서버를 고친 뒤의 동기화에서 저절로 통과한다.
6. 이전 앱에서 이미 3번 실패해 막힌 작업(FAILED, retryCount 3)도 새 앱에서 다시 보내진다.

## 비슷하지만 결과가 달라야 하는 사례

| 사례 | 결과 | 구별하는 이유 |
| --- | --- | --- |
| 같은 사용자·같은 여행의 생성 재전송 | 200, 기존 행 | 이미 반영된 같은 변경 |
| 같은 ID인데 다른 여행으로 생성 | 409 | 다른 변경이므로 성공으로 볼 수 없음 |
| 다른 사용자가 같은 ID로 생성 | 409, 원래 행은 바뀌지 않음 | 재전송이 아니며 행 내용을 드러내지 않음 |
| 이미 지운 자기 일정의 삭제 재전송 | 200, 처음 삭제 시각 | 이미 반영된 같은 변경 |
| 다른 사용자의 일정 삭제 | 404 (지금과 같음) | 존재 비노출 |
| 수정 재전송 | 200 (지금도 그렇다) | 같은 값을 다시 쓰고 version만 1 더 오름 |
| 이번 사고의 중복 키 500 (수정 전) | 몇 번을 보내도 실패 | 5xx이지만 영원히 실패하는 오류 |
| 우리 버그로 생긴 400 | 서버를 고치면 성공 | 4xx이지만 풀리는 오류. 상태 코드만으로 '영구 실패'를 가를 수 없다는 근거 |
| 전송을 시작하는 순간 남아 있는 IN_PROGRESS | PENDING으로 되돌려 다시 보냄 | 동기화는 잠금 때문에 한 번에 하나만 실행되므로 지난 실행이 남긴 흔적임 |
| 원본 행이 없는 CREATE·UPDATE 또는 검증된 소유자 기록이 없는 구버전 DELETE | QUARANTINED로 보존하고 자동 전송에서 제외 | 소유자를 추정해 실행하거나 입력을 버리지 않으면서 같은 계정 로그인을 복구함 |
| 원본 행은 없지만 삭제 시점에 확인한 `userId`가 저장된 새 DELETE | 로그인 계정이 저장된 소유자와 같을 때만 삭제를 전송하고, 다른 계정이거나 원본과 요청의 소유자가 모순되면 차단 | 소유권 근거와 원본 보존을 분리하되 다른 계정의 요청은 실행하지 않음 |
| 원본 없는 DELETE가 격리됐지만 서버 행은 남음 | 후속 pull에서 서버 행이 다시 나타날 수 있음 | 삭제 의도를 서버에 전달하지 않은 비용이며 실제 재등장은 아직 확인하지 않음 |

## 조금 나빠질 수 있는 것

- 원본도 검증된 요청 소유자 근거도 없는 작업을 격리하면 로그인과 정상 동기화는 계속되지만, 그 작업이 의도한 서버 변경은 실행되지 않는다. 특히 구버전 DELETE가 격리된 동안 서버 행이 남아 있으면 pull로 다시 보일 수 있다. 확인할 수 없는 요청을 임의로 실행하거나 버리지 않기 위해 받아들인 현재 구현의 비용이며, 실제 재등장은 아직 관찰하지 않았다.
- 예전에는 3번 실패하면 영영 가지 않던 수정이 이제는 늦게라도 도착한다. 그 사이 다른 곳에서 같은 기록을 고쳤다면 늦게 온 수정이 새 수정을 덮어쓴다. 다른 기기나 비활성 여행 직접 수정이 있어야 생기는 드문 경우이고, 막는 방법은 version 비교(Ticket 07)다.
- 끝내 실패할 요청도 동기화 때마다 다시 보낸다. 헛요청의 실제 크기는 아직 모르며, 이를 줄이는 간격 재시도는 보류했다.
  - **얼마나 가나:** 동기화는 실행 조건이 새로 갖춰질 때(앱 시작, 인증·세션, 실제 연결, override, 일시 중단 해제)와 디버그 화면의 수동 실행에서만 시작한다. 시작 1번에 헛요청 1건이고, 5xx면 HTTP client 재시도까지 최대 4건이다.
  - **아는 것과 모르는 것:** 연결이 안정적인 시뮬레이터에서는 숨은 반복 실행이 없었다([Ticket 03](../tickets/03-stage-one-real-app-verification.md#현재-상태와-실제-결과)). 연결이 자주 끊기는 실제 여행에서 조건이 얼마나 자주 새로 갖춰지는지는 모른다. 10-31 사례의 '1분 안에 실패 3번'도 조건 전환이 세 번 있었다는 뜻이지만 원인은 확인하지 못했다.
  - **보류 이유:** 간격 재시도는 헛요청을 줄이지만 연결 회복 뒤 전송도 늦춘다. 늦어지는 손해는 확실하고 헛요청의 크기는 모르며, 헛요청이 늘어도 데이터는 망가지지 않는다(배터리·데이터·서버 부하).
  - **다시 판단할 때:** 실제 sync 시작 횟수를 얻었을 때(예: Ticket 06에서 표시와 함께 시작 이유·횟수를 남길 때), TestFlight나 실제 사용에서 같은 작업의 실패가 자주 반복될 때, sync 계기를 늘리거나 주기 sync를 켤 때.
