# 문제·목표·범위

## 해결할 문제

Noline은 활성 여행의 변경을 기기 SQLite에 먼저 저장하고 `sync_queue`에 쌓아 두었다가, 동기화 때 들어온 순서대로 서버에 보낸다. 지금은 실패 이유와 상관없이 한 작업이 3번 실패하면 그 작업이 큐 맨 앞에서 영구히 멈춘다. 전송 중 앱이 종료돼 `IN_PROGRESS`로 남은 작업도 다시 보내지지 않는다.

영구 정지가 생기면 다음 일이 함께 일어난다.

- 뒤에 쌓인 모든 변경이 서버로 가지 않는다. 다른 여행이 남긴 변경도 포함된다.
- push가 실패하면 pull을 하지 않으므로 서버 쪽 변경도 받지 못한다.
- 비활성화한 여행의 미뤄 둔 기기 데이터 정리도 실행되지 않는다.
- 출시 빌드에서 이 상태가 드러나는 곳은 로그아웃할 때 뜨는 "동기화되지 않은 데이터" 경고뿐이다. 큐를 보여 주는 디버그 화면은 개발 빌드에서만 메뉴에 나온다.

사용자는 기기에 변경이 보이므로 저장됐다고 믿는다. 하지만 앱을 다시 설치하거나 휴대폰을 바꾸거나 로그아웃하면 그 변경은 사라진다.

영구 정지로 들어가는 길은 네 가지다. 빈도는 측정하지 않은 추정이다.

| 길 | 빈도 (추정) |
| --- | --- |
| 서버는 반영했는데 앱이 응답을 못 받은 생성·삭제를 다시 보냄. 생성은 중복 키 500, 삭제는 이미 지운 행이라 404 | 실제로 일어남 (아래 사례) |
| 동기화 중 앱이 종료돼 작업이 `IN_PROGRESS`로 남음 | 가끔 |
| 시간 초과·5xx 같은 일시 오류가 3번 쌓임 | 흔할 수 있음. Render 무료 플랜의 기동 지연과 15초 timeout의 관계가 측정 대상 (Ticket 04) |
| 우리 코드 문제, 다른 기기와의 충돌, 손상된 payload | 드묾 |

### 발견한 사례

2026-11-02 iOS 시뮬레이터의 개발 앱(로컬 개발 서버와 로컬 PostgreSQL)에서 경비 CREATE 하나가 큐를 막고 있었다.

- 앱이 큐에 등록한 시각은 10-31 08:22:03 UTC다.
- 서버 행은 1초 뒤인 08:22:04에 만들어졌다.
- 앱은 08:23:00에 그 작업을 "실패, 재시도 3회"로 기록했다.
- 다시 보내도록 되돌리자 서버가 `duplicate key … expenses_pkey`로 500을 반환했다.

첫 응답을 왜 못 받았는지는 로그가 없어 확정하지 못했다. 로컬 서버였으므로 Render 기동 지연 경로는 아니다. 상세 근거는 [관찰 기록](../../../records/2026-11-02-01-simulator-sync-block-observation.md)에 있다.

## 이루려는 결과

실패한 변경은 다음 세 결말 중 하나로 끝난다.

- **서버에 도착한다.**
- **합의한 규칙에 따라 정리된다.** 서버가 이 변경보다 나중 상태를 갖고 있고, pull이 그 상태를 내려 줘서 기기도 같은 결과가 되는 경우에만 해당한다.
- **사람이 결정한다.**

끝나기 전까지는 변경이 보존되고, 종속 순서가 지켜지고, 누군가 그 상태를 알 수 있어야 한다.

| 단계 | 결과 | Ticket |
| --- | --- | --- |
| 1단계 | 흔한 세 길(재전송, 전송 중 종료, 일시 오류 누적)이 '도착'으로 끝난다. 이미 막힌 기기도 새 앱에서 풀린다. | 01·02·03 |
| 출시 | 1단계 결과를 운영 서버와 1.1.0 build 13에 싣는다. 서버 기동 지연을 먼저 재고 대응을 정한다. | 04·05 |
| 2단계 | 남는 정지를 출시 빌드에서 사용자나 개발자가 알 수 있다. | 06 |
| 3단계 | 서버에서 이미 지운 기록에 대한 변경 같은 충돌이 합의한 규칙으로 끝난다. | 07 |

1단계가 끝나면 흔한 경로의 영구 정지는 사라진다. 하지만 충돌과 우리 버그 경로의 정지는 남고, 여전히 보이지 않는다. 그래서 1단계 완료를 이 Work 전체의 완료로 보지 않는다.

## 범위

포함한다.

- 서버의 일정·경비 생성·삭제 재전송 응답과 여행 삭제 재전송 확인
- 앱 큐의 중단 복구와 재시도 한도
- 위 변경에 맞춘 Project 문서 (data-lifecycle, api-contracts)
- 서버 기동 지연 측정과 대응 결정, 서버 배포와 1.1.0 build 13 준비
- 멈춘 동기화의 표시 (제품 결정 포함)
- 충돌 규칙에 따른 정리 (003 Ticket 12와 범위 조정 필요)

포함하지 않는다.

| 항목 | 이유 | 담당 |
| --- | --- | --- |
| 경비 생성의 부모 Trip·Schedule 소유권 검사 | 보안 계약의 문제이고, 같은 파일이지만 바뀌는 이유가 다르다. 단 3단계의 '삭제된 여행' 규칙은 이 결과가 필요하다. | 003 Ticket 13, 별도 커밋 |
| 여행 생성 중복 (제출마다 새 ID, 일반 API 10초 timeout) | 큐를 거치지 않는 경로이고 실제 발생은 확인하지 않았다. | 003 Ticket 03·13의 후보 |
| 저장 직후·앱 복귀 시 동기화 같은 계기 확대 | 정확성이 아니라 반영 속도의 문제이며 제품 결정이다. | [state](../../state/index.md)의 열린 판단 |
| 여행별 큐 분리 | pull 보호가 먼저 있어야 안전하다. | [Spec 05](05-constraints-design-assumptions.md)의 재검토 조건 |
| 실패 횟수·경과 시간 기준 폐기 | 정상적인 오프라인 데이터와 우리 버그로 막힌 데이터를 버린다. | 채택하지 않음 |
| 인증 오류 처리 | 지금 동작(PENDING으로 되돌림)을 유지한다. | 003 Ticket 02 |

## 선행 조건과 권한

- 1단계 구현은 사용자의 진행 승인을 받은 뒤 시작한다. 생성 시점에는 "수정 1~3을 이 범위로 진행할까요?"라는 질문에 대한 답을 기다리고 있다.
- 서버 CREATE 재전송 처리와 테스트는 판단만 요청받은 상황에서 범위를 넘어 먼저 구현됐다. 2026-11-03에 유지가 결정돼 Ticket 01 결과와 함께 커밋 `ba91d1a3`에 들어갔다. 경위는 [기록](../../../records/2026-11-02-02-create-replay-fix-beyond-scope.md)에 있다.
- 커밋·푸시·배포는 사용자가 요청할 때만 한다. App Store 제출과 Render 플랜 변경은 사용자가 직접 한다.
