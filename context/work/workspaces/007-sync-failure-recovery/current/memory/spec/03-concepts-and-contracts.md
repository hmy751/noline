# 개념과 계약

## 같은 뜻으로 쓸 개념

- **큐 작업 상태:** PENDING은 보낼 작업이다. IN_PROGRESS는 지금 보내는 중이라는 뜻인데, DB에 저장되므로 실행이 끝난 뒤에도 남을 수 있다. FAILED는 최종 실패이고 retryCount가 횟수를 센다.
- **재전송:** 같은 큐 작업을 같은 client ID와 같은 payload로 다시 보내는 것. Project의 app-runtime(64–65행)과 api-contracts(79행)에서 "재전송"은 401 뒤 token을 갱신하고 같은 요청을 다시 보내는 것을 뜻한다. Project 문서에 반영할 때는 "큐 작업 재전송"처럼 구별해 쓴다.
- **이미 반영됨:** 서버 DB에 같은 사용자의 같은 변경 결과가 있다는 것. 이를 아는 쪽은 서버뿐이다.
- **영구 정지:** 끝나는 조건이 없는 막힘. 지금은 retryCount 3의 FAILED와 남은 IN_PROGRESS가 여기에 해당한다.
- **두 재시도:** HTTP client의 5xx 재시도(한 요청 안에서 2·4·8초 뒤 최대 3번, [api.ts:39](../../../../../../../apps/client/src/shared/services/sync/api.ts))와 큐 재시도(다음 동기화)는 별개다. 시간 초과와 네트워크 오류는 HTTP 재시도 대상이 아니다.
- **동기화 계기:** 앱 시작, 그리고 연결·로그인 조건이 다시 갖춰질 때다. 주기 동기화는 꺼져 있고([_layout.tsx:34](../../../../../../../apps/client/app/_layout.tsx)), 수동 동기화는 개발 빌드 디버그 화면에만 있다([ProfileScreen.tsx:146](../../../../../../../apps/client/src/screens/ProfileScreen.tsx)). 변경 직후에 동기화를 부르는 코드는 없다.
- **실행 잠금:** `executeSync`는 한 번에 하나만 실행한다([lifecycle.ts:43](../../../../../../../apps/client/src/shared/services/sync/lifecycle.ts)). 로그인·로그아웃·탈퇴는 진행 중인 동기화가 끝나기를 기다린다([session-lifecycle.ts:13](../../../../../../../apps/client/src/shared/services/auth/session-lifecycle.ts)).

위 사실은 2026-11-03 코드를 읽어 확인했다.

## 서버 재전송 계약 (1단계에서 정함)

| 요청 | 지금 | 1단계 뒤 |
| --- | --- | --- |
| 일정·경비 생성: 같은 사용자·같은 여행의 기존 ID | 500 (중복 키) | 200, 기존 행 |
| 일정·경비 생성: 다른 사용자 또는 다른 여행의 기존 ID | 500 | 409 `ID is already in use` |
| 일정·경비 삭제: 이미 지운 자기 행 | 404 | 200, 처음 삭제 시각 |
| 일정·경비 삭제: 다른 사용자의 행 또는 없는 행 | 404 | 404 (그대로) |
| 수정 재전송 | 200 | 200 (그대로) |
| 여행 삭제 재전송 | 200 (코드 읽기 기준. 삭제 시각을 새로 찍음) | 200을 테스트로 고정. 삭제 시각을 새로 찍는 차이는 유지하고 003 Ticket 13과 함께 정리한다(2026-11-03 Ticket 01) |

- 실제 쓰기 조건 `id + userId + deletedAt IS NULL`은 바꾸지 않는다. 바뀐 행이 0개일 때만 자기 행이 이미 삭제됐는지 확인한다.
- 일정 생성은 지금처럼 부모 여행을 먼저 확인한다. "기존 행부터 확인"하는 안은 API 계약의 부모 우선 문장과 부딪혀 채택하지 않았다.
- 지금의 500은 `details`에 DB 제약 이름까지 내보낸다. 409는 그 ID가 이미 쓰인다는 사실만 알리므로 드러나는 정보가 더 적다.
- 오류 처리 문서는 status를 조용히 바꾸지 말라고 한다. 그래서 이 변경은 API 계약 문서와 테스트로 고정한다. 앱 코드에서 404·409를 따로 분기하는 곳은 찾지 못했다(2026-11-03 코드 검색).

## 앱 큐 계약 (1단계에서 정함)

- 동기화를 시작할 때 남아 있는 IN_PROGRESS를 PENDING으로 되돌린다.
- 실패 횟수로 작업을 영구히 막지 않는다. FAILED는 다음 동기화에서 다시 보낸다. retryCount는 계속 세며, 2단계에서 알림 기준으로 쓸 후보다.
- FIFO와 첫 실패에서 멈추기(`engine.ts`의 `break`)는 그대로 둔다.
- 새 상태값, 새 DB 열, 새 화면, 새 전송 계기는 만들지 않는다.

## 그대로 지키는 기존 계약

| 기존 계약 | 1단계에서 |
| --- | --- |
| 막힌 작업을 건너뛰거나 큐를 비우지 않고, 실패를 '완료'로 바꾸지 않는다 (data-lifecycle 57행) | 실패한 자리에서 멈췄다가 같은 작업부터 다시 시작한다 |
| PENDING·IN_PROGRESS·FAILED는 모두 미전송이고 로그아웃 때 손실을 경고한다 | 상태를 되돌릴 뿐 지우지 않는다 |
| 앱이 만든 ID를 서버가 그대로 받는다 (Decision 0001) | 재전송 응답도 같은 ID의 행이다 |
| 일정 생성은 부모 여행부터 확인한다 (api-contracts 37행) | 순서를 유지한다 |
| 수정·삭제의 쓰기 조건은 `id + userId + deletedAt IS NULL` (api-contracts 39행) | 쓰기 조건은 그대로다 |
| 다른 사용자에게 존재 여부를 드러내지 않는다 (api-contracts 42행) | 조회는 항상 userId로 제한하고, 다른 사용자의 삭제는 계속 404다 |
| HTTP 5xx 재시도와 큐 재시도는 별개다 (data-lifecycle 59행) | HTTP 재시도는 건드리지 않는다 |
| 주기 동기화는 기본으로 켜지 않는다 | 동기화 계기를 늘리지 않는다 |

## 바뀌는 약속 (2026-11-03 사용자 동의)

아래 세 가지는 1단계 진행 승인("유지하고 진행")에 포함해 받아들였다. 근거는 [구현 기록](../../../records/2026-11-03-03-stage-one-implementation.md#유지-결정)에 있다.

- **재시도 3회 한도:** [local-access.test.ts:195](../../../../../../../apps/client/tests/shared/services/auth/local-access.test.ts)의 테스트가 "FAILED 작업은 3회 미만까지만 다음 sync 대상으로 복구한다"를 고정하고 있다. 숫자 3을 고른 이유는 기록에서 찾지 못했다.
- **003 Ticket 11의 완료 조건:** 원래 문구는 "재시도 불가 오류는 무한 반복 대신 식별 가능한 실패와 보존된 입력으로 남는다"이다. 007에서는 "빠르게 반복하지 않고 다음 동기화 때 다시 시도하며, 입력은 보존하고, 반복 실패는 표시로 식별할 수 있다"로 대신한다. '식별'은 Ticket 06이 맡는다. 앱은 어떤 실패가 영원한지 확실히 알 수 없고, 출시 빌드에는 멈춘 작업을 풀 화면이 없기 때문이다.
- **API 응답 세 가지:** 같은 사용자의 생성 재전송은 500에서 200으로, 이미 지운 자기 행의 삭제는 404에서 200으로, 다른 사용자가 쓰는 ID의 생성은 500에서 409로 바뀐다.

## 버전 사이 payload 호환 (Project 반영 후보)

큐에 쌓인 payload는 앱 업데이트와 서버 배포를 지나서도 남는다. 서버 request schema를 바꿀 때 이전 앱이 쌓아 둔 payload를 거절하면, 그 기기의 큐는 서버를 다시 고칠 때까지 막힌다. 그래서 "서버 request schema를 바꿀 때 이전 앱이 쌓아 둔 payload도 계속 받는다"는 규칙이 필요하다.

여러 작업에 적용되는 개발 계약이므로, api-contracts나 data-lifecycle에 반영할지는 Project 관리 계약에 따라 따로 판단한다. 아직 채택하지 않았다.
