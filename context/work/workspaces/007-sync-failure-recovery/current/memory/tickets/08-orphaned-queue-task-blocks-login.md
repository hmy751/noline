# 08. 원본 없는 큐 작업이 복원과 로그인을 막지 않게 하기

## 맡은 결과와 범위

큐 작업이 가리키는 원본 행이 기기에 없어도 사용자가 데이터를 지우지 않고 같은 계정으로 다시 로그인해 앱을 쓸 수 있게 한다. 원본 없는 작업은 입력과 재시도 이력을 보존하되 자동 전송에서 제외하고, 다른 계정의 데이터가 확인되면 기존처럼 로그인을 차단한다.

복원 실패 화면의 문구와 버튼 구성은 맡지 않는다. 그것은 예외 안내 정리([Workspace 008](../../../../008-exception-notice-rules/README.md))가 소유한다. 이 Ticket은 원본 없는 큐 작업 때문에 복원과 같은 계정 로그인이 함께 막히는 원인을 다룬다.

## 실행 맥락과 접근

1.0.1의 vacuum은 큐 참조를 확인하지 않고 원본 행을 지울 수 있었다. 여기서 7일은 여행이 끝난 뒤의 시간이 아니라 사용자가 일정·경비를 삭제한 뒤 지난 시간이다. 구버전은 이 soft-delete 보존 기간이 지나면 아직 서버에 보낼 작업이 있는지 확인하지 않고 Local 원본을 물리적으로 정리할 수 있었다.

원본 행이 없는 큐 작업을 `inspectLocalAccount`가 `unresolved`로 판정하면 복원 재시도와 같은 계정 로그인도 실패해 데이터 삭제만 남는다. 2026-11-04 시뮬레이터에서 CREATE 작업으로 이 막힘을 재현했다. 실제 1.0.1 업데이트 설치 과정과 영향받은 사용자 수는 확인하지 않았다.

2026-11-06 Main은 원본 없는 CREATE·UPDATE·DELETE 작업을 영속 상태 `QUARANTINED`로 격리하는 방식을 구현했다고 보고했다.

- 작업 종류·payload·retryCount를 큐에 그대로 남기고 계정을 추정하거나 작업을 완료·삭제하지 않는다.
- 원본 없음으로 판정된 작업은 payload 내용이 손상돼도 원문을 그대로 격리하고 다음 작업의 검사를 계속한다. 다만 이후 원본과 요청의 소유자 정보가 모순된 `invalid` 작업을 만나면 로그인 보류가 확정되므로 즉시 `unresolved`를 반환한다. 그 뒤 작업은 이번 로그인 호출에서 검사·격리하지 않으며, `invalid` 작업 자체도 격리하지 않는다.
- 격리 작업은 자동 push와 수동 재시도·동기화 성공 삭제에서 제외한다.
- 같은 계정 검사는 격리 작업 때문에 막히지 않는다. 원본 행이 있는 다른 계정 작업에 대한 보호는 유지한다.
- 정상 전송 작업이 실패하면 기존 FIFO 계약대로 뒤 작업은 기다린다. 원본 없는 작업만 전송 목록에서 분리하는 예외다.
- 한 번 격리한 작업은 앱을 다시 시작하거나 같은 record ID의 원본이 후속 pull로 다시 생겨도 자동 전송 상태로 되돌리지 않는다.
- 격리 요청만 남은 경우 같은 ID의 soft-delete 원본이 나중에 생겨도 기기 정리를 막지 않는다. 격리 요청 자체는 보존한다.
- 로그아웃의 미전송 데이터 검사는 격리 작업도 손실 가능한 데이터로 센다.

앱이 저장하는 `QUARANTINED`는 client DB만의 임의 값이 아니라 공유 sync queue 상태 정의에도 포함한다. 저장 값과 공통 runtime schema가 같은 상태 집합을 받아들이는지 회귀 검사로 확인한다.

현재 분기 기준은 작업이 얼마나 오래됐는지가 아니라 원본과 소유자를 확인할 수 있는지다. 오래됐어도 소유자를 확인할 수 있는 작업은 정상 FIFO에서 보낸다. 로그인 검사에서는 원본 없는 작업을 격리한 뒤 다음 작업으로 가지만, `invalid`를 만나면 그 자리에서 로그인을 보류하고 뒤 작업은 이번 호출에서 확인하지 않는다. 동기화의 전송 목록 구성은 로그인 검사와 별도로 원본 없는 작업을 격리한다.

이 선택은 로그인을 복구하고 확인할 수 없는 요청의 임의 실행·폐기를 피하는 대신, 격리된 작업이 의도한 서버 변경을 수행하지 않는다. 원본 없는 DELETE를 버리거나 계속 격리하면 서버 행이 후속 pull에서 다시 나타날 수 있다. 반면 원본 없는 CREATE·UPDATE payload에는 사용자가 입력한 내용의 마지막 사본이 남아 있을 수 있으므로, 작업 종류를 구별하지 않고 나이만으로 폐기하면 실제 입력을 잃을 수 있다.

현재 구현은 세 작업 종류를 모두 격리한다. 사용자는 2026-11-06 원본 없는 DELETE를 자동 폐기하고 CREATE·UPDATE만 보존할지에 관한 판단을 이 Ticket에서 더 논의하는 것으로 이해한다고 확인했다. 따라서 DELETE의 최종 처리 규칙은 아직 선택하지 않았으며 별도 후속 Ticket으로 넘기지 않는다.

2026-11-07 논의에서 새 DELETE 요청의 소유권 근거를 원본 행에만 의존할 필요는 없다는 대안이 드러났다. 현재 일정 DELETE payload에는 `tripId`만 있어 전송 전에 원본 행에서 `userId`를 다시 읽지만, 삭제 권한을 확인한 시점의 `userId`를 요청에 함께 저장하고 검사·전송도 그 값을 사용하면 소유자 확인만을 위해 일정 원본을 보존할 필요는 없다. 서버가 인증된 계정과 서버 행의 소유권을 직접 확인하는 계약은 그대로 유지한다. 기존 기기에 이미 남은 요청에는 이 근거가 없으므로 현재 로그인 계정의 ID를 사후에 붙여 전송하지 않는다. 일정 원본의 soft-delete와 7일 보존은 연결된 경비·경로를 언제 정리할지의 문제로 분리해 판단해야 한다. 사용자는 소프트 딜리트를 유지하고 새 삭제 요청에 확인한 사용자 ID를 저장하기로 했다. 격리 변경을 먼저 커밋하며, 새 요청의 소유자 저장과 검사는 후속 구현이다.

사용자는 2026-11-07 로그아웃 화면에서 정상 미전송과 격리를 상태명이나 별도 건수로 설명하지 않고, 다시 로그인해도 복구할 수 없는 실제 입력 손실 가능성이 있을 때 한 번 알리는 방향을 채택했다. 원본 없는 DELETE 기록만 남은 경우의 경고 여부는 이 Ticket의 보존·폐기 결정에 따른다. 이 선택은 DELETE 처리 규칙을 확정한 것이 아니며, 실제 사용자 문구와 화면 반영은 Workspace 008이 소유한다.

주요 구현 위치는 [local-account.ts](../../../../../../../apps/client/src/shared/services/auth/local-account.ts), [queue.ts](../../../../../../../apps/client/src/shared/services/sync/queue.ts), [client DB schema](../../../../../../../apps/client/src/shared/db/schema.ts), [공유 queue 상태 정의](../../../../../../../packages/schema/src/sync/sync-queue.ts), [logout-service.ts](../../../../../../../apps/client/src/shared/services/auth/logout-service.ts), [cleanup-job.ts](../../../../../../../apps/client/src/shared/services/sync/cleanup-job.ts)다.

Project 문서 반영은 이 Ticket의 완료 조건에 포함하지 않는다. 동작이 실제 출시 계약으로 채택돼 Project-wide 기준을 바꿀 때에는 사용자의 별도 요청과 Project 관리 계약으로 판단한다.

## 완료 조건과 확인 방법

- 원본 없는 CREATE·UPDATE·DELETE가 현재 선택된 처리 규칙에 따라 내용과 재시도 횟수를 잃지 않고 격리되거나 안전하게 정리된다.
- 원본 없음으로 판정된 작업의 payload가 손상돼도 입력을 임의로 버리거나 전송하지 않고 그 작업을 격리한 뒤 다음 작업 검사를 계속한다. 단, 별도의 `invalid` 작업을 만나 로그인 판정이 `unresolved`로 확정되면 그 뒤 작업까지 이번 로그인 호출에서 검사·격리하는 것은 보장하지 않는다.
- 같은 계정 로그인이 성공하고 정상 큐 작업과 pull은 계속 진행된다.
- 정상 작업의 실제 전송 실패에서는 기존 FIFO 중단 계약을 유지한다.
- 앱을 완전히 종료했다 다시 실행해도 격리 대상으로 정한 작업의 상태와 입력이 유지된다.
- 다른 계정의 변경은 현재 계정으로 전송되지 않는다.
- client가 저장한 `QUARANTINED` 값을 공유 schema도 받아들인다.
- 격리 요청을 완료·삭제한 것처럼 기록하지 않고, 실제 상태와 로그가 일치한다.
- 원본 없는 DELETE의 보존·폐기 규칙을 결정하고 선택한 동작을 자동 검사와 실제 시뮬레이터에서 확인한다.

## 현재 상태와 실제 결과

2026-11-06 Main은 세 작업 종류를 모두 격리하는 현재 구현과 검증을 마쳤다고 보고했다. 2026-11-07 이 격리 구현과 회귀 검사를 로컬 커밋 `06cebd6f`로 저장했다. 배포 전이다. 원본 없는 DELETE의 최종 처리 규칙이 열려 있으므로 Ticket 전체를 완료로 닫지는 않는다.

- Main은 `development` 스킬을 사용했지만 처음 검토에서는 Ticket 08과 Project 인증·동기화 기준만 확인했고, Personal의 코드 표현 기준과 Project의 공유 타입 기준을 변경 코드에 충분히 대조하지 못했다고 정정했다.
- 재확인 뒤 새 조건문의 중괄호, 함수 선언과 import 순서를 팀 기준에 맞췄다고 보고했다.
- 격리 요청을 실제로 삭제하지 않았는데도 동기화 성공으로 삭제했다고 기록하던 로그 세 곳을 제거했다고 보고했다.
- client가 저장하는 `QUARANTINED`가 공유 queue 상태 정의에서 누락된 것을 고치고, 실제 저장 값을 공통 schema가 받아들이는 회귀 검사를 추가했다고 보고했다.
- Main은 구현, 개선 검토, 최종 검증을 서로 다른 담당자에게 맡겼다고 보고했다. 기존 작업 기록은 Sonnet 담당을 예정했지만 Claude CLI가 로그아웃 상태여서 그 차이를 알리고 Codex 담당자로 진행했다. 최종 검증자는 구현과 개선 검토에 참여하지 않은 별도 담당자였다.
- iPhone 15 Pro 시뮬레이터의 기존 개발 DB에 원본 없는 CREATE·UPDATE·DELETE를 각각 FAILED·retryCount 3으로 만들었다. DELETE payload는 1.0.1과 같은 문자열 `null`을 사용했다.
- 사용자가 같은 계정으로 로그인한 뒤 원본 없는 세 작업은 QUARANTINED로 남았고, 기존 정상 일정 CREATE 1건만 개발 서버에 전송됐다. 이어 일정 1건과 경비 1건의 pull이 완료됐다.
- 앱을 완전히 종료하고 다시 실행한 뒤에도 세 작업의 종류·payload·retryCount가 유지됐으며 자동 전송 대상은 0건이었다.
- 확인 뒤 Main이 추가한 시험 작업 세 건만 제거했다. 시뮬레이터는 로그인 상태이고 실제 동기화 결과는 유지됐다. 이 정리 뒤 Main이 다시 조회한 미전송 작업 수는 0건이었다.
- 수정 후 독립 검증에서 client 테스트 677개가 통과했고 iOS 개발 번들이 생성됐다고 Main이 보고했다. 변경 파일 포맷 검사도 통과했다. 전체 타입 검사와 기본 lint에는 변경 전부터 있던 오류가 남아 있다고 보고했다.
- 이번 보완 뒤 같은 계정 로그인 조작과 정상 일정 전송을 시뮬레이터에서 다시 실행하지는 않았다. 해당 실제 동작 근거는 앞선 시뮬레이터 확인이다.

실제 1.0.1 빌드를 설치해 업데이트 경로 전체를 재현하지는 않았다. 예전에 사용자가 본 복원 실패 화면이 이 원인이었는지도 확인하지 못했다. 서버에 남은 행이 후속 pull로 다시 나타나는 사례도 직접 관찰하지 않았으며, 이는 구현 계약에서 예상되는 결과다.
