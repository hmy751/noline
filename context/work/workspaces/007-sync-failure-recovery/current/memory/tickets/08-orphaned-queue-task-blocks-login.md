# 08. 원본 없는 큐 작업이 복원과 로그인을 막지 않게 하기

## 맡은 결과와 범위

큐 작업이 가리키는 원본 행이 기기에 없어도, 사용자가 데이터를 지우지 않고 앱을 다시 쓸 수 있게 한다. 다른 계정으로 변경이 전송되는 일은 계속 막는다.

복원 실패 화면의 문구와 버튼 구성은 맡지 않는다. 그것은 예외 안내 정리([Workspace 008](../../../../008-exception-notice-rules/README.md))에서 정한다. 이 Ticket은 막히는 원인을 없앤다.

## 실행 맥락과 접근

**확인한 사실** (근거는 [재현 기록](../../../records/2026-11-04-02-restore-failed-dead-end.md))
- 원본 행이 없는 큐 작업이 하나라도 있으면 `inspectLocalAccount`가 `unresolved`를 돌려준다. 앱은 복원 실패 화면으로 시작하고, "복원 다시 시도"와 같은 계정의 로그인이 모두 실패한다. 시뮬레이터에서 사용자가 직접 확인했다.
- 남는 길은 데이터 삭제뿐이고, 삭제하면 미전송 변경도 사라진다.
- 1.0.1의 vacuum은 큐를 보지 않고 행을 지웠으므로 이런 상태를 남길 수 있다. 현재 vacuum은 큐가 가리키는 행을 지우지 않는다.

**모르는 것**
- 1.0.1에서 실제 업데이트했을 때의 동작. DB 상태만 만들어 재현했다.
- 삭제 작업으로 직접 돌린 결과. 생성 작업으로 재현했고, 코드상 같은 경로로 봤다.
- 실제 사용자 중 해당 기기 수.

**지켜야 할 것**
- 소유자 검사의 목적은 다른 계정의 변경을 현재 계정으로 보내지 않는 것이다. [local-account.ts](../../../../../../../apps/client/src/shared/services/auth/local-account.ts)의 "소유자를 알 수 없으면 전송하지 않는다"를 그냥 없애면 안 된다.
- 사용자 입력을 조용히 버리지 않는다([데이터 수명](../../../../../../project/guidance/data-lifecycle/INDEX.md)의 재시도 절).
- [engine.ts](../../../../../../../apps/client/src/shared/services/sync/engine.ts)의 push도 `getQueueOwner`가 현재 계정과 다르면 `AuthRequiredError`를 던진다. 로그인만 통과시키면 이번에는 push에서 막힐 수 있으니 함께 봐야 한다.

**선택지 (결정 전)**

| 선택지 | 로그인 | 원본 없는 작업 | 부담 |
| --- | --- | --- | --- |
| 그대로 | ✕ 막힘 | 그대로 | 데이터 삭제뿐이다 |
| 원본 없는 삭제 작업은 현재 계정으로 전송 | ○ | 서버 소유권 검사가 다른 사용자의 행을 404로 거절해 다른 계정의 행은 지워지지 않지만, 그 404가 큐를 막을 수 있다 | 재전송 처리와 충돌 규칙([Ticket 07](07-conflict-rule-and-cleanup.md))과 맞춰야 한다 |
| 원본 없는 작업을 격리해 전송에서 빼고 보존 | ○ | 그 변경은 서버에 가지 않는다 | 격리 상태가 새로 생기고, 사용자에게 보일지 정해야 한다 |
| 원본 없는 작업만 지우고 시작 | ○ | 조용히 사라진다 | 삭제 작업이면 이미 지운 행이지만, 수정·생성 작업이면 입력 손실이다 |

작업 종류마다 답이 다를 수 있다. 1.0.1 경로의 행은 이미 사용자가 지운 것이어서 삭제 작업이 주된 대상으로 보이지만, 같은 행의 수정·생성 작업이 함께 남았을 수도 있다.

**진행 순서 제안**
1. 실제 1.0.1 빌드나 그에 맞는 DB로 삭제 작업 경우를 재현한다.
2. 작업 종류별 처리를 사용자와 정한다.
3. 구현, 개선 검토, 별도 검증은 Sonnet medium 담당자에게 맡긴다.

**Project 문서:** 이 Ticket의 결과나 완료 조건에 넣지 않는다. [앱 실행 기준](../../../../../../project/current/app-runtime/INDEX.md)은 `restore-failed`를 "복원 재시도 또는 계정 검사를 거치는 로그인으로 해결한다"고 설명하는데, `unresolved`에서는 재현으로, `different`에서는 코드 읽기로 맞지 않음을 봤다. 다만 처리 방법도 1.0.1 경로의 실제 여부도 정해지지 않았으므로 지금 반영하지 않는다. 사용자가 "project는 확실한게 아닌데 왜 넣으려고 하지?"라고 정정했다. 동작이 확정된 뒤 사용자 요청이 있을 때 별도로 판단한다.

## 완료 조건과 확인 방법

- 작업 종류별 처리와 그 이유를 사용자가 정하고 기록한다.
- 원본 없는 큐 작업이 있는 DB에서 같은 계정의 로그인이 성공하고, 앱을 계속 쓸 수 있다. 시뮬레이터와 테스트로 확인한다.
- 다른 계정의 변경이 현재 계정으로 전송되지 않는다.
- 사용자 입력이 조용히 사라지지 않는다. 지우기로 정한 경우는 그 이유가 기록돼 있다.

## 현재 상태와 실제 결과

재현까지 마쳤고 수정은 시작하지 않았다. 1.1.0 (13)은 이 동작을 포함한 채 심사 대기 중이고 자동 출시다. 수정은 다음 빌드 대상이다. 철회 여부는 사용자 판단으로 남아 있으며, Main의 추천은 철회하지 않는 것이다.
