# 05. 서버 배포와 1.1.0 build 13 출시

## 맡은 결과와 범위

1단계 결과를 운영에 싣는다. 서버 수정(Ticket 01)을 Render에 배포하고, 앱 수정(Ticket 02)을 넣은 1.1.0 build 13을 TestFlight에서 확인한다. 그 뒤 사용자가 1.1.0을 build 13으로 심사에 제출할 수 있게 준비한다.

배포·빌드 업로드·심사 제출은 모두 사용자 승인이나 사용자 본인의 실행이 필요하다. 이 Ticket은 준비와 확인을 맡고 공개 결정을 대신하지 않는다.

## 실행 맥락과 접근

생성 시점의 출시 상태:
- TestFlight에 1.1.0 (12)가 있고 기본 동작이 확인됐다.
- App Store Connect에 1.1.0 초안이 있고 build 12가 연결돼 있다. 심사에는 제출하지 않았다.
- `main`을 푸시하면 Render가 자동 배포한다.

**왜 서버 먼저, 그리고 왜 build 13인가**
- 서버 수정만 배포해도 build 12를 포함한 모든 앱에서 재전송 실패가 사라진다.
- 하지만 build 12에는 "전송 중 종료"와 "일시 오류 3번" 길이 남아 영구 정지가 여전히 생길 수 있다. 이미 막힌 작업도 build 13이어야 다시 보내진다.
- 1.1.0을 아직 제출하지 않았으므로 build 13으로 내는 것이 맞다고 판단했다. 대신 빌드와 TestFlight 처리 시간이 더 든다.

**순서:** 서버 배포는 build 13이 사용자에게 가기 전에 끝나야 한다. 새 앱이 다시 보내는 생성·삭제를 서버가 성공으로 받아야 하기 때문이다.

**릴리스 노트 주의:** 초안의 "동기화가 중단돼도 아직 전송하지 못한 내용을 보존해요"는 "저장 즉시 동기화된다"로 읽히지 않게 고친다. 변경은 앱 시작과 연결 회복 때만 전송된다. 출처는 [관찰 기록](../../../records/2026-11-02-01-simulator-sync-block-observation.md#릴리스-노트에-준-영향)이다.

**확인하지 않은 사실:** 1.0.1에도 같은 동작이 있었던 것으로 보여 이번 1.1.0의 회귀는 아니라고 판단했다. 이는 코드 이력으로 본 판단이며 1.0.1 앱에서 재현하지는 않았다.

## 완료 조건과 확인 방법

- 서버 배포 뒤 운영 `/api/health` 200을 확인한다.
- 생성 재전송 응답 200을 확인한다. 운영 데이터를 바꾸지 않는 방법을 쓰거나, 사용자가 허용한 테스트 계정에서만 확인한다.
- build 13이 App Store Connect에서 처리를 통과한다.
- TestFlight에서 로그인, 여행 목록, 일정 저장 뒤 동기화를 확인한다.
- 1.1.0 초안의 빌드를 13으로 바꿀 준비가 됐다. 교체와 심사 제출은 사용자가 정한다.

## 현재 상태와 실제 결과

실행 전. 01·02·03은 끝났다. Ticket 04의 대응이 앱 변경 없는 외부 헬스체크로 정해져(2026-11-03) build 13에 더할 앱 쪽 대응은 없다. 04의 효과 확인은 이 Ticket을 막지 않는다.
