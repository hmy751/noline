# 06. 멈춘 동기화를 알 수 있게 하기

## 맡은 결과와 범위

계속 실패하는 작업이 있을 때 출시 빌드에서 사용자나 개발자가 그 사실을 알 수 있게 한다. 1단계 뒤에도 우리 버그와 충돌 경로의 정지는 남는데, 지금은 로그아웃 경고 말고는 드러나지 않는다. 이 Ticket은 그 정지를 사람에게 보이게 한다.

003 Ticket 11은 "재연결·수동 재시도로 서버 반영에 도달"을 완료 조건으로 두었다. 하지만 출시 빌드에는 수동 재시도가 없다. 이 Ticket이 그 원래 뜻을 맡는다.

## 실행 맥락과 접근

확인한 사실:
- 동기화 실패는 `lifecycle.ts`의 콘솔 로그로만 남는다.
- 디버그 화면은 개발 빌드에서만 메뉴에 나온다([ProfileScreen.tsx](../../../../../../../apps/client/src/screens/ProfileScreen.tsx) 146행). 이 화면이 큐 항목마다 상태와 재시도 횟수를 보여 주고 수동 동기화를 실행한다.
- 서버 로그에는 모든 요청의 경로와 500 오류만 남는다([app.ts](../../../../../../../apps/server/src/app.ts) 26행). route는 400·404·409로 거절한 이유를 남기지 않는다.
- 수동 동기화 기능(`triggerManualSync`)은 이미 있다.

| 선택지 | 사용자 | 개발자 | 먼저 필요한 것 | 구현 |
| --- | --- | --- | --- | --- |
| 없음 (지금) | ✕ 로그아웃 경고에서만 | ✕ 디버그 메뉴는 개발 빌드에만 | 없음 | 없음 |
| 서버 로그 보강 (4xx로 거절한 이유) | ✕ | △ 서버가 거절한 것만 보이고, 시간 초과처럼 서버에 안 닿은 실패는 안 보임 | 없음 | 작음 |
| 상태 표시 + "지금 보내기" | ○ 예: "아직 못 보낸 변경 N개" | △ | 문구·위치 (제품 결정) | 중간 |
| 위 + 하나씩 버리기 | ○ 직접 해결 | △ | Ticket 07의 정리 규칙 또는 사용자 선택 정책 | 큼 |

현재 판단: 서버 로그 보강은 결정 없이 할 수 있다. 상태 표시는 제품 결정이 필요하다. 이전 논의의 기본 추천은 다음과 같았다. 사용자 결정은 아직 없다.
- 표시는 기존 `NetworkStatusIndicator` 패턴을 따르는 최소 표시로 한다.
- 버리기는 제공하지 않는다.
- 마지막 시도가 실패했으면 실패 종류와 상관없이 보여 준다.

retryCount는 Ticket 02 뒤에도 계속 세므로 표시 기준으로 쓸 수 있다.

## 완료 조건과 확인 방법

- 사용자가 표시 여부, 문구·위치, 표시 기준, 버리기 제공 여부를 정하고 그 이유를 남긴다.
- 정한 표시가 출시 빌드 구성에서 실제로 보이는지 확인한다.
- 서버 로그를 보강했다면, 거절 이유가 기록되면서 토큰이나 개인정보가 노출되지 않는지 확인한다.
