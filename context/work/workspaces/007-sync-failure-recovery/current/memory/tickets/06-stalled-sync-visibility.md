# 06. 멈춘 동기화를 알 수 있게 하기

## 맡은 결과와 범위

계속 실패하는 작업이 있을 때 출시 빌드에서 개발자가 그 사실을 알 수 있게 하고, 동기화 시작·실패 횟수를 남긴다. 1단계 뒤에도 우리 버그와 충돌 경로의 정지는 남는데, 지금은 로그아웃 경고 말고는 드러나지 않는다.

사용자에게 보이는 표시는 이 Ticket에서 정하지 않는다. 앱의 안내가 이미 여러 겹이라 표시만 따로 더하면 겹침이 심해진다. 사용자도 "예와처리가 너무 많아서 막 제공한다고 좋을것 같진 않아"라고 했다. 표시는 예외 안내 규칙을 정하는 [Workspace 008](../../../../008-exception-notice-rules/README.md)에서 다룬다. 경위와 비교는 [안내 현황 기록](../../../records/2026-11-04-01-notice-inventory.md)에 있다.

003 Ticket 11의 범위는 "개발자 수동 동기화 표시"이고, 완료 조건은 "재시도 불가 오류는 무한 반복 대신 식별 가능한 실패와 보존된 입력으로 남는다"이다. 사용자용 수동 재시도를 약속한 것은 아니다. 식별 가능한 실패 중 개발자 쪽은 이 Ticket이, 사용자 쪽은 008과 Ticket 07이 맡는다.

## 실행 맥락과 접근

확인한 사실:
- 동기화 실패는 `lifecycle.ts`의 콘솔 로그로만 남는다.
- 디버그 화면은 개발 빌드에서만 메뉴에 나온다([ProfileScreen.tsx](../../../../../../../apps/client/src/screens/ProfileScreen.tsx) 146행). 이 화면이 큐 항목마다 상태와 재시도 횟수를 보여 주고 수동 동기화를 실행한다.
- 운영 서버에는 요청 기록이 없다. 경로 기록은 개발 환경에서만 켜진다([app.ts](../../../../../../../apps/server/src/app.ts)). route는 400·404·409로 거절한 이유도 남기지 않는다. 이전에 이 문장을 "모든 요청의 경로가 남는다"로 잘못 적었다.
- 동기화 시작 이유(`app-startup`·`conditions-ready`·`manual`·`periodic`)는 코드에 있지만 콘솔에만 찍힌다. 앱에 분석 도구도 없다.
- 수동 동기화 기능(`triggerManualSync`)은 이미 있다.
- 실제 사용에서 sync가 얼마나 자주 시작되는지는 모른다(Ticket 03). 표시를 설계할 때 시작 이유·횟수도 함께 남길지 정한다. 그 값이 보류한 간격 재시도를 다시 판단할 근거가 된다.

알고 싶은 것은 둘이다. 실제 사용에서 동기화가 얼마나 자주 시작되는가, 계속 실패하는 작업이 몇 번이나 다시 보내지는가. [데이터 수명](../../../../../../project/guidance/data-lifecycle/INDEX.md)이 간격 재시도를 다시 볼 조건으로 적은 값이 이것이다.

| 어디에 남기나 | 볼 수 있는 범위 | 비용 |
| --- | --- | --- |
| 기기 안에 이유별 누적 | 직접 들여다보는 기기만. 출시 빌드에서는 볼 화면도 따로 필요 | 작음. 앱 빌드 |
| 운영 서버 로그 | 모든 사용자 | 앱에 헤더 2개, 서버에 로그 1줄. 앱 빌드와 서버 배포 |
| 외부 분석 도구 | 모든 사용자, 대시보드 | 새 의존성과 App Store 개인정보 표시 변경. 지금은 과함 |

현재 추천 (사용자 결정 없음): 운영 서버 로그로 남긴다.
- 앱은 동기화 요청에 시작 이유와 그 작업의 `retryCount`를 헤더로 붙인다. `retryCount`가 있으면 기록 ID 없이도 몇 번째 재전송인지 보인다.
- 서버는 동기화 요청의 메서드·경로·응답 코드와 두 헤더 값, 4xx로 거절한 이유만 남긴다. 사용자 ID·본문·토큰은 남기지 않는다.
- 무엇을 남기고 무엇을 남기지 않는지는 [오류 처리 기준](../../../../../../project/guidance/error-handling.md)의 진단 로그와 공개 문구 구분을 따라 이 Ticket에 적는다. Project 반영은 동작이 확정된 뒤 사용자 요청이 있을 때 별도로 판단한다.

받아들일 한계: 사용자를 구분하지 않아 "한 기기에서 하루 몇 번"은 대략만 안다. Render 무료 플랜의 로그 보존 기간은 확인하지 않았다. 헤더 없이 서버 로그만 먼저 배포해도 응답 코드별 요청 수는 볼 수 있다.

앞선 논의의 사용자 표시 추천(최소 표시, 버리기 미제공, 마지막 시도 실패 때 표시)은 008의 입력으로 [안내 현황 기록](../../../records/2026-11-04-01-notice-inventory.md)에 옮겼다.

## 완료 조건과 확인 방법

- 사용자가 횟수·거절 이유를 어디에 어떤 범위로 남길지 정하고 그 이유를 남긴다.
- 운영 구성에서 동기화 요청의 시작 이유·재시도 횟수·응답 코드를 실제로 볼 수 있음을 확인한다.
- 거절 이유가 기록되면서 토큰이나 개인정보가 노출되지 않는지 확인한다.
- 사용자에게 보이는 표시는 이 Ticket의 완료 조건이 아니다. 008에서 정한다.

## 현재 상태와 실제 결과

기록 범위의 사용자 결정 대기. 표시를 008로 넘긴 것은 2026-11-04 사용자가 일을 나누는 구성에 동의한 결과다("그래 일단 워크스페이스 기록 잘 남겨봐").
