# 06. 멈춘 동기화를 알 수 있게 하기

## 맡은 결과와 범위

계속 실패하는 작업이 있을 때 출시 빌드에서 개발자가 그 사실을 알 수 있게 하고, 동기화 시작·실패 횟수를 남긴다. 1단계 뒤에도 우리 버그와 충돌 경로의 정지는 남는데, 지금은 로그아웃 경고 말고는 드러나지 않는다.

사용자에게 보이는 표시는 이 Ticket에서 정하지 않는다. 앱의 안내가 이미 여러 겹이라 표시만 따로 더하면 겹침이 심해진다. 사용자도 "예와처리가 너무 많아서 막 제공한다고 좋을것 같진 않아"라고 했다. 표시는 예외 안내 규칙을 정하는 [Workspace 008](../../../../008-exception-notice-rules/README.md)에서 다룬다. 경위와 비교는 [안내 현황 기록](../../../records/2026-11-04-01-notice-inventory.md)에 있다.

003 Ticket 11의 범위는 "개발자 수동 동기화 표시"이고, 완료 조건은 "재시도 불가 오류는 무한 반복 대신 식별 가능한 실패와 보존된 입력으로 남는다"이다. 사용자용 수동 재시도를 약속한 것은 아니다. 식별 가능한 실패 중 개발자 쪽은 이 Ticket이, 사용자 쪽은 008과 Ticket 07이 맡는다.

## 왜 앱에서도 기록하는가

서버 요청 헤더에 동기화 시작 이유와 재시도 횟수를 붙이는 안은 서버에 도착한 요청만 설명한다. 로그인 중 삭제 요청이 격리되거나, 앱이 전송 전에 멈추면 요청 자체가 없다. 한 번의 동기화에서 여러 요청을 보내므로 서버 요청 수로는 동기화 시작 횟수도 알 수 없다. 사용자는 “로컬에서 전송하려다 격리되는것처럼 끊기는 작업”을 어떻게 측정할지 물었다.

운영 도구는 Sentry로 정했다. 사용자가 “관리 영역이 아예 생기는게 낫지 않아? 다른 에러도 모으면 좋고?”라고 짚었듯이, 앱과 서버의 일반 오류까지 릴리스별로 모아 조사할 곳이 필요하다. 앱은 로컬에서 실제로 일어난 일을, 서버는 실제로 받은 요청의 거절과 예외를 기록한다. 전용 진단 API와 PostgreSQL 저장소를 구축하는 안은 보류했다.

## 무엇을 세는가

| 앱·서버가 확인한 사실 | 운영에서 해석할 기준 |
| --- | --- |
| 실행 조건을 충족해 동기화를 실제 시작함 | 한 실행에 시작 이유를 한 번 붙인다. 정상 오프라인 저장, 실행을 건너뛴 호출, 한 실행 안의 HTTP 재시도는 새 동기화 시작으로 세지 않는다. |
| 로그인 검사나 동기화 준비 중 작업이 처음 격리됨 | 격리 상태가 저장된 뒤 한 번 기록한다. 기존 격리를 다시 읽어도 새 사건은 없다. 뒤의 정상 경비가 전송됐다면 격리는 한 건이고 큐가 막힌 일은 없다. |
| 전송 전에 로컬에서 작업이 중단됨 | 작업 종류와 확인된 단계를 기록한다. 전송 후 응답을 못 받은 경우는 응답 미확인이다. 서버는 이미 변경을 반영했을 수 있다. 시작만 기록된 채 앱이 꺼졌다면 결과는 미확인이다. |
| 서버가 거절하고 같은 큐 작업이 다음 실행에서도 실패함 | 작업 종류·응답 코드·뒤에 대기 중인 작업과 함께, 이번 시도 **이전**에 해당 큐 작업이 실패한 횟수(`sync.previous_failures`)를 본다. 처음 실패한 시도는 0이다. 선제 갱신이나 여행 요청의 401 이후 토큰 갱신 자체가 실패하면 `auth-refresh-failed`로 분류하며 여행 요청의 서버 거절로 세지 않는다. 한 실행의 HTTP 재시도, 여러 기기에서 비슷한 오류가 한 이슈로 묶인 횟수, 앱·서버 양쪽에 보이는 같은 시도를 중복 집계하지 않는다. |
| 앱 또는 서버의 예외 | 오류 이슈를 환경·릴리스와 함께 조사한다. 운영 화면의 수치는 SDK에 넘긴 뒤 실제 전달된 기록의 범위다. 오프라인 누락·샘플링·앱 중단이 있어 전체 사용자의 정확한 총계로 사용하지 않는다. |

Sentry의 오류 수집과 동기화 시작·결과 관측은 목적이 다르다. 시작과 정상적인 오프라인 동작은 오류 알림 대상에서 뺀다. 실명·계정 ID·여행이나 일정 ID·좌표·요청 본문·토큰·ID가 포함된 경로는 보내지 않는다. 기록에 필요한 정보는 시작 이유·작업 종류·단계·제한된 사유·횟수처럼 허용한 항목으로 좁힌다. 진단 전송 결과는 로그인·여행 저장·격리·전송·정리의 결과를 바꾸지 않아야 한다.

## 전달과 완료 확인

오프라인에서 여행 변경은 기존 SQLite와 `sync_queue`에 저장한다. 진단은 여행 큐 밖에서 Sentry SDK에 전달한다. 앱 종료와 로그아웃 뒤의 SDK 캐시 수명은 실제 빌드에서 확인할 대상이다. 아래의 로컬 확인과 운영 수신 확인은 각각 별개다. 계정 DB를 초기화해도 SDK 캐시가 함께 비워진다고 가정하지 않는다. 시작이나 마지막 단계가 사라져 운영자가 실제 미실행과 중단을 구별할 수 없다면 빠진 신호만 기기에 짧게 보관할지 판단한다.

1. 출시용 앱에서 오프라인으로 새 격리 한 건을 만든 뒤 앱을 완전히 종료한다. 재실행·재연결 후 격리가 한 번 관측되는지, 정상 작업은 전송되는지 대조한다.
2. 동기화 시작 후 전송 전 오류·응답 유실·응답 전 앱 종료를 구분해 마지막으로 확인한 단계와 미확인 결과를 본다. 서버 거절이 반복된 사례에서는 그 작업의 실패 횟수와 뒤 작업 대기가 보이고, 한 실패가 여러 오류로 중복 집계되지 않는지 확인한다.
3. 미보고 기록이 있는 채로 로그아웃하고 다른 계정으로 로그인한다. 무엇이 뒤늦게 도착하는지, 새 계정의 행동으로 귀속되지 않는지, 진단 장애 중에도 로그인·여행 변경·정리가 계속되는지 확인한다.
4. 실제 수신 내용에서 금지한 식별자와 본문이 제외됐는지 확인하고, 수신된 실행·오류의 범위와 누락 가능성을 남긴다. 사용자 안내는 Workspace 008에서 다룬다.

## 현재 상태

2026-11-09 사용자가 “그럼 기록할거 하고 진행해보자”라고 해 `feat/007-sentry-diagnostics` 브랜치와 별도 워크트리에서 앱·서버 연결 구현을 시작했다. 기준 커밋은 `4ef9f423`이다. Sentry 수집 주소(DSN)가 있는지 묻자 사용자는 “없는데”라고 답했다. 운영 DSN이 없는 기본 설정에서는 외부 전송을 끈다. 이때의 DSN 미설정 상태는 11월 10일 프로젝트 생성과 로컬 설정으로 갱신됐다.

앱은 JS 오류와 동기화 신호, 서버는 거절과 예외를 수집한다. 원문 노출 위험 때문에 네이티브 크래시·멈춤 자동 수집과 화면 녹화는 껐다. Xcode 26.5에서 기존 Sentry Cocoa 의존성 빌드가 실패해 앱 SDK를 6.22.0으로 바꿨다. iOS 시뮬레이터 Release 빌드, 앱 화면과 소스맵 debugId를 확인했다. 앱 테스트 694개와 변경 코드 lint, 서버 테스트 72개·타입 검사·빌드가 통과했다. 앱 전체 타입 검사의 기존 오류 7개는 남는다.

Release 앱에서 실제 동기화·인증 함수를 실행하고 로컬 수신기를 껐다 켜며 확인했다. 새 격리 1건이 앱 재시작 뒤 도착했고 정상 PUT 1건은 진행됐다. 강제 로그아웃으로 DB를 비워도 이전 진단 1건은 남았고 새 계정 식별 정보 없이 전달됐다. 전송 전 중단, 404 반복 거절, 응답 유실, 앱 종료로 시작만 남는 실행도 구별됐다. 자세한 조건과 수치는 [로컬 수신 확인 기록](../../../records/2026-11-09-01-sentry-local-receiver.md)에 있다.

2026-11-10 실제 Sentry에 앱·서버 프로젝트를 만들어 서버 시험 이슈와 앱 staging 경고의 수신을 확인했다. 앱 trace에서 시작·종료·막힘 기록을 연결해 봤고 iOS Hermes 소스맵을 업로드했다. 두 프로젝트의 새 오류·재발·급증용 기본 알림 규칙도 설정했다. 시험 앱 TypeError 화면에서 소스맵으로 원래 JS 파일·줄과 코드를 복원했다. 두 프로젝트의 IP 저장 방지 설정 후 신규 이벤트에서 IP는 표시되지 않았다. 사용자 정보 삭제 규칙까지 적용한 뒤에도 Geography에 도시가 남았다. [실제 이슈·설정과 확인 범위](../../../records/2026-11-10-01-sentry-staging.md)

Ticket은 진행 중이다. 남은 판단은 Sentry에서 계속 표시되는 도시 정보의 처리와 반복 동기화 Warning의 별도 알림 규칙이다. 현재 알림 규칙은 두 프로젝트의 Error 이상을 대상으로 하며 Warning 전용 규칙은 설정하지 않았다. 운영 앱·서버 배포와 EAS 비밀 설정은 별도로 남았다.

2026-11-10 개발 결과를 다시 검토해 여행 요청 전에 실패한 인증 갱신을 동기화 요청의 서버 거절로 분류할 수 있는 점과, 서버 거절 로그에서 환경·릴리스가 사라지는 점을 확인했다. 앱은 원래 갱신 오류를 유지하고 불필요한 여행 요청 재시도를 막았다. 서버는 최종 전송 로그에 허용한 값과 환경·릴리스를 보존했다. 양 플랫폼 Hermes 소스맵의 역매핑과 서버 배포 번들 시작 실패도 다시 확인했다. 최신 통합판에서 앱 테스트 702개·변경 lint, 서버 테스트 73개·타입 검사·빌드가 통과했다. 별도 검증자가 인증 갱신과 여행 요청 실패, 양 플랫폼의 실제 Hermes 이름·debugId 필터링, 서버 부팅과 로그 수신을 다시 확인했다. 앱 전체 타입 검사에는 기존 오류 7개가 남았다. 최종 수정판의 실제 Sentry staging에서 서버의 일정 PUT 500 오류와 404 거절 로그를 확인했다. 앱 Release 시험 진입점에서는 `auth-refresh-failed` 신호(503, 이전 실패 1회)를 전달했고 시작·중단·종료 세 항목이 같은 trace에 표시됐다. 실제 인증 실패의 단계 분류는 앞선 독립 재현에서 확인했다. 운영에 배포하지 않았다.
