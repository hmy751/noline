## 순서와 의존

- 01과 02의 코드는 서로 다른 파일(서버·앱)이므로 함께 진행할 수 있다. 문서는 겹친다. 둘 다 [데이터 수명](../../../../../../project/guidance/data-lifecycle/INDEX.md)의 push 상태표(48–55행)를 고치므로, 한쪽이 반영한 뒤 다른 쪽이 그 현재판에 이어 반영한다.
- 02가 운영에서 안전하려면 01이 먼저 운영 서버에 있어야 한다. 그래서 05에서 서버 배포가 build 13보다 먼저다.
- 03은 01·02가 모두 끝난 최신 판본을 확인한다.
- 04의 대응은 앱 변경 없는 외부 헬스체크로 정해 build 13을 막지 않았다. 효과 확인에서 앱 쪽 대응이 필요해지면 다음 빌드로 간다.
- 06과 07은 1단계와 출시 뒤에 진행한다. 07은 06의 운영 기록과 003 Ticket 13(경비 부모 확인)의 결과를 쓴다.
- 08은 원본도 검증된 소유자 기록도 없는 작업을 QUARANTINED로 보존한다. 새 DELETE는 삭제 시점에 기록한 소유자와 로그인 계정이 일치하면 원본이 없어도 전송한다. 따라서 소유자를 확인할 수 없는 삭제를 Ticket 07의 충돌 규칙으로 임의 전송하지 않는다. 서버에 남은 행이 pull로 다시 나타날 수 있는 비용은 Ticket 08 본문에서 확인한다.
- 사용자에게 보이는 표시와 복원 실패 화면의 문구는 [Workspace 008](../../../../008-exception-notice-rules/README.md)에서 정한다.

## Ticket으로 만들지 않은 것

- **여행별 큐 분리:** pull 보호가 생기거나 실제 막힘이 관찰될 때 다시 판단한다. 조건은 [Spec 05](../spec/05-constraints-design-assumptions.md)에 있다.
- **동기화 계기 확대(저장 직후, 앱 복귀):** 제품 결정이 먼저다. [state](../../state/index.md)의 열린 판단에 있다.
- **버전 사이 payload 호환 규칙:** Project 반영 후보다. [Spec 03](../spec/03-concepts-and-contracts.md#버전-사이-payload-호환-project-반영-후보)에 있다.
