# 04. 서버 기동 지연이 동기화를 실패시키는지 재고 대응 정하기

## 맡은 결과와 범위

운영 서버(Render 무료 플랜)가 잠든 상태에서 앱 시작 동기화가 실패하는지를 측정으로 확인한다. 그 결과로 대응을 정하고, 앱 쪽 대응을 골랐다면 build 13 전에 넣는다.

이 Ticket이 필요한 이유는 1단계의 효과가 이 측정에 달려 있기 때문이다. 1단계 뒤 일시 오류는 영구 정지가 되지 않는다. 하지만 오랜만에 연 앱의 동기화가 매번 잠든 서버에 걸리면 전송이 다음 앱 시작까지 계속 늦어진다.

## 실행 맥락과 접근

확인한 사실:
- 동기화 요청은 15초 timeout이다([api.ts](../../../../../../../apps/client/src/shared/services/sync/api.ts) 17행). 시간 초과는 HTTP 재시도 대상이 아니라 바로 FAILED가 된다(39–44행).
- 동기화 계기는 앱 시작과 연결·로그인 회복뿐이다. 실패한 뒤 같은 세션에서 다시 시도할 계기가 없다.
- 로그인·로그아웃은 진행 중인 동기화가 끝나기를 기다린다([session-lifecycle.ts](../../../../../../../apps/client/src/shared/services/auth/session-lifecycle.ts) 13행).
- 2026-11-02 운영 서버가 깨어나는 데 약 50초가 걸린 것을 한 번 관찰했다.

추정: Render 무료 플랜은 15분 동안 요청이 없으면 잠든다. 그래서 오랜만에 연 앱의 시작 동기화는 실패할 가능성이 크다. 아직 재 보지 않았다.

측정 방법(초안): 15분 넘게 요청이 없던 뒤 운영 `/api/health`에 첫 요청을 보내 응답 시간을 잰다. 가능하면 TestFlight 앱을 열어 시작 동기화의 결과도 본다. 운영에 보내는 읽기 요청이므로 실행 전에 사용자에게 알린다. 운영 DB는 읽지 않는다.

| 선택지 | 오랜만에 연 앱의 동기화 | 다른 화면의 API | 비용 | 부작용·구현 |
| --- | --- | --- | --- | --- |
| 그대로 | ✕ 실패하고 다음 앱 시작까지 늦어짐 | ✕ 일반 요청(10초 제한)도 실패할 수 있음 | 0 | 없음 |
| 동기화 timeout을 깨어나는 시간보다 길게 | ○ 늦게라도 성공 | ✕ 그대로 | 0 | 로그인·로그아웃이 진행 중인 동기화를 기다려 그만큼 늦어질 수 있음. build 13 필요 |
| 실패 뒤 1~2분 지나 한 번 더 | ○ 두 번째에 성공 | ✕ 그대로 | 0 | 새 자동 재시도 계기라 따로 정해야 함. build 13 필요 |
| 유료 플랜 (잠들지 않음) | ○ | ○ 같이 해결 | 월 비용 | 없음. Render 설정만 바꿈 |

현재 판단: 실패가 확인되면, 비용을 감수할 수 있으면 유료 플랜이 가장 단순하고 다른 화면 문제까지 함께 푼다. 비용을 피하려면 timeout 연장이 가장 작은 변경이다. 결정은 사용자가 한다.

## 완료 조건과 확인 방법

- 측정 방법·시각·결과를 records에 남긴다.
- 측정 결과에 따라 사용자가 대응을 정하고 그 이유를 남긴다.
- 앱 쪽 대응을 골랐다면 build 13 전에 구현하고 테스트한다. 대응이 바뀌어도 Ticket 02의 계약(FIFO, 한도 없음)은 유지된다.
