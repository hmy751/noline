# 04. 서버가 잠들어 동기화가 실패하는 일을 주기 헬스체크로 막고 확인하기

## 맡은 결과와 범위

운영 서버(Render 무료 플랜)가 잠든 상태에서 앱 시작 동기화가 실패하는 일을 막는다. 대응은 사용자가 정한 외부 주기 헬스체크다. 이 Ticket은 그 헬스체크가 서버를 실제로 깨워 두는지 확인하는 일을 맡는다.

이 Ticket이 필요한 이유는 1단계의 효과가 서버 응답에 달려 있기 때문이다. 1단계 뒤 일시 오류는 영구 정지가 되지 않는다. 하지만 오랜만에 연 앱의 동기화가 매번 잠든 서버에 걸리면 전송이 다음 앱 시작까지 계속 늦어진다.

## 실행 맥락과 접근

확인한 사실:
- 동기화 요청은 15초 timeout이다([api.ts](../../../../../../../apps/client/src/shared/services/sync/api.ts) 17행). 시간 초과는 HTTP 재시도 대상이 아니라 바로 FAILED가 된다(39–44행).
- 동기화 계기는 앱 시작과 연결·로그인 회복뿐이다. 실패한 뒤 같은 세션에서 다시 시도할 계기가 없다.
- 로그인·로그아웃은 진행 중인 동기화가 끝나기를 기다린다([session-lifecycle.ts](../../../../../../../apps/client/src/shared/services/auth/session-lifecycle.ts) 13행).
- 2026-11-02 운영 서버가 깨어나는 데 약 50초가 걸린 것을 한 번 관찰했다.
- 헬스체크 설정은 저장소에 없다. `.github/workflows`가 없고, 서버 코드에는 `/api/health` 경로만 있다(2026-11-03 확인). 외부 서비스에 둔 것으로 보며, 무엇을 어떤 주기로 부르는지는 확인하지 않았다.

추정: Render 무료 플랜은 15분 동안 요청이 없으면 잠든다. 아직 재 보지 않았다.

### 대응 결정 (2026-11-03)

처음 계획은 잠든 서버의 첫 응답 시간을 재고 아래 표에서 대응을 고르는 것이었다. 측정 전에 사용자가 방향을 정했다.

> "일단 이건 신경 써서 한다기보다 다른 걸로 해결해야될것 같아 주기적으로 헬스체크 하게 두긴 햇거든 지금은 확인 못하고"

그래서 측정과 앱 쪽 대응은 하지 않는다. build 13에도 이 Ticket의 변경은 들어가지 않는다.

| 선택지 | 오랜만에 연 앱의 동기화 | 다른 화면의 API | 비용 | 부작용·구현 |
| --- | --- | --- | --- | --- |
| 그대로 | ✕ 실패하고 다음 앱 시작까지 늦어짐 | ✕ 일반 요청(10초 제한)도 실패할 수 있음 | 0 | 없음 |
| **외부 주기 헬스체크 (채택)** | ○ 주기가 잠드는 기준보다 짧으면 | ○ 같이 해결 | 0 (무료 사용 시간 한도 안이면) | 앱 변경 없음. 저장소 밖 설정이라 멈춰도 아무 표시 없이 원래 문제로 돌아감 |
| 동기화 timeout을 깨어나는 시간보다 길게 | ○ 늦게라도 성공 | ✕ 그대로 | 0 | 로그인·로그아웃이 진행 중인 동기화를 기다려 그만큼 늦어질 수 있음. build 13 필요 |
| 실패 뒤 1~2분 지나 한 번 더 | ○ 두 번째에 성공 | ✕ 그대로 | 0 | 새 자동 재시도 계기라 따로 정해야 함. build 13 필요 |
| 유료 플랜 (잠들지 않음) | ○ | ○ 같이 해결 | 월 비용 | 없음. Render 설정만 바꿈 |

헬스체크가 제대로 돌면 유료 플랜과 같은 효과를 비용 없이 얻는다. 확인에서 문제가 보이면 timeout 연장이나 유료 플랜을 다시 고른다.

### 확인할 것

- **주기:** 잠드는 기준(추정 15분)보다 짧은가.
- **대상:** 운영 서버의 `/api/health` 같은 실제 HTTP 경로를 부르는가.
- **무료 사용 시간 한도:** Render 무료 플랜에 월 사용 시간 한도가 있다고 알고 있으나 확인하지 않았다. 서비스를 한 달 내내 켜 두면 약 720~744시간이다. 다른 무료 서비스도 함께 깨어 있으면 한도를 넘겨 월말에 서버가 멈출 수 있다.
- **효과:** 다음 중 하나로 본다.
  - Render 이벤트·로그에 잠든 기록(spin down)이 없다.
  - 아무도 쓰지 않은 시간대에도 `/api/health`가 바로 응답한다. 운영에 읽기 요청을 보내므로 실행 전에 사용자에게 알린다. 운영 DB는 읽지 않는다.

## 완료 조건과 확인 방법

- 사용자가 정한 대응과 그 이유를 남긴다. (2026-11-03 완료, 위 원문)
- 헬스체크의 주기·대상·사용 시간 한도와 효과를 확인하고 결과를 records에 남긴다.
- 확인에서 효과가 없으면 다른 대응을 다시 정한다. 앱 쪽 대응을 고르면 build 13 전에 구현하고 테스트한다. 대응이 바뀌어도 Ticket 02의 계약(FIFO, 한도 없음)은 유지된다.

## 현재 상태와 실제 결과

대응은 정해졌고(외부 주기 헬스체크), 확인은 하지 않았다. 사용자가 지금은 헬스체크 설정을 확인할 수 없다고 했다. 이 확인은 Ticket 05의 서버 배포를 막지 않는다. build 13도 기다리지 않는다. 확인 전에 build 13을 내고 나중에 앱 쪽 대응이 필요해지면 그 대응은 다음 빌드로 간다.
