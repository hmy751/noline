# 07. 충돌로 막힌 변경을 규칙으로 끝내기

## 맡은 결과와 범위

서버에 이미 이 변경보다 나중 상태가 있어서 다시 보내도 성공할 수 없는 변경을 합의한 규칙으로 끝낸다. 대표 예는 서버에서 이미 지운 기록을 고친 작업, 이미 지운 여행에 일정을 만든 작업이다. 끝난 뒤에는 화면·SQLite·서버가 같은 값에 도달해야 한다.

규칙에 따라 버리는 것은 서버가 나중 상태를 갖고 있고 pull이 그 상태를 내려 줘서 기기도 같은 결과가 되는 경우뿐이다. 우리 버그나 손상된 payload처럼 서버에 나중 상태가 없는 경우는 이 규칙으로 버리지 않는다.

## 실행 맥락과 접근

**먼저 정할 것**
- **충돌 규칙:** 후보는 "삭제가 이긴다"이다. 003 Ticket 12는 local 우선이나 server 우선을 미리 기정사실로 만들지 말라고 했다. 같은 기록의 미전송 생성·수정·삭제와 서버 수정·삭제의 조합을 재현한 뒤 정한다. 자동으로 처리할 정책과 사람이 골라야 하는 정책도 나눈다.
- **003 Ticket 12와의 범위:** Ticket 12는 pull 누락과 미전송 수정 덮어쓰기를 실행 전으로 맡고 있다. 이 Ticket을 실행할 때 다음 중 하나를 사용자가 정한다.
  - 그 범위(pull 보호, version 비교)를 007로 옮긴다.
  - Ticket 12의 결과를 받아 큐 쪽 정리만 맡는다.

**필요한 구현 요소**
- **서버의 명시적 응답:** 지금 404는 "없음·다른 사용자의 것·이미 삭제됨"이 같은 값이다. 자기 행이 이미 삭제된 경우를 따로 알려야 앱이 추측하지 않고 판단할 수 있다. Ticket 01의 삭제 재전송 처리와 같은 방식으로, 자기 행만 다시 확인한다.
- **앱의 정리 단위:** 기록이나 여행 단위로 정리한다.
  - **기록이 삭제됐으면:** 남은 수정은 버리고, 삭제는 성공으로 끝난다. 그 일정을 가리키는 경비 생성은 soft delete라 FK가 살아 있어 성공한다.
  - **여행이 삭제됐으면:** 그 여행에 남은 변경을 함께 버린다.
- **선행 결과:** 경비 생성은 지금 부모 여행을 확인하지 않아, 지운 여행에도 경비가 만들어진다. 그래서 '여행이 삭제됨' 규칙에는 003 Ticket 13의 경비 부모 확인이 먼저 필요하다.

**함께 볼 것**
- **늦게 도착한 수정이 새 수정을 덮는 문제:** PUT에 version 비교가 없다([schedules.ts](../../../../../../../apps/server/src/routes/schedules.ts) 224행). 한도를 없앤 뒤에는 늦게라도 도착하는 수정이 생긴다.
- **pull upsert:** 미전송 queue·version을 비교하지 않고 덮는다([데이터 수명](../../../../../../project/guidance/data-lifecycle/INDEX.md) 71행).
- **여행별 큐:** pull 보호가 생기면 이 Ticket 뒤에 다시 판단한다.

## 완료 조건과 확인 방법

- 조합 재현 결과와 채택한 규칙, 사람 선택이 필요한 경우를 기록한다. 미확정 정책이 결과를 막으면 구현 완료로 닫지 않는다.
- 서버가 자기 행의 '이미 삭제됨'을 다른 404와 구별해 응답하고, 다른 사용자에게는 여전히 존재를 드러내지 않는다.
- 채택한 규칙에서 막힌 큐가 풀리고, 후속 pull 뒤 화면·SQLite·서버가 같은 값에 도달함을 테스트와 실제 앱에서 확인한다.
- 우리 버그·손상 payload는 이 규칙으로 버려지지 않는다.
