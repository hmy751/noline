# 07. 충돌로 막힌 변경을 규칙으로 끝내기

## 맡은 결과와 범위

다른 기기에서 같은 일정·경비를 수정했거나, 기록·여행이 삭제된 동안 폰에 미전송 작업이 남은 경우를 다룬다. 해당 작업을 종결한 뒤 화면·SQLite·서버가 같은 값에 도달해야 한다.

서버가 판단한 최종 값을 기기에서도 확인할 수 있어야 한다. 우리 버그나 손상된 payload처럼 서버가 채택할 결과를 확인할 수 없는 실패에는 충돌 종결 규칙을 적용하지 않는다.

## 실행 맥락과 접근

### 확정한 일정·경비 UPDATE 규칙 (2026-11-10)

살아 있는 기록은 **실제로 편집한 항목끼리만** 병합한다. 일정의 제목·출발 시각·장소는 독립 항목이며 장소명·주소·좌표는 하나의 장소로 함께 바꾼다. 경비의 제목·지출액·분류·날짜·연결 일정도 독립 항목이며 금액·통화는 하나의 지출액으로 함께 바꾼다.

- **저장과 전송:** 사용자가 저장할 때 바뀐 항목의 새 값과 그 편집의 표식 `edit`을 확정한다. 저장 한 번당 한 건을 기존 FIFO에 넣고 재전송에도 같은 표식을 쓴다. 온라인 직접 수정도 같은 계약을 따른다.
- **표식의 순서:** `time`, `sequence`, `id` 순으로 비교한다. UTC로 비교할 수 있는 기기 시각을 기본으로 하되 같은 기기의 연속 저장과 이미 관찰한 값의 후속 편집에는 앞선 표식보다 큰 표식을 발급한다. 시계가 같거나 뒤로 가면 관찰·발급한 시각을 유지하고 순번을 올린다. 서로 독립적인 편집이 동률이면 저장 때 정한 고정 ID 순으로 결정한다. 연결이 끊긴 두 기기의 시계 오차 때문에 실제 편집 선후까지 보장하지는 못한다.
- **서버 판정:** 서버는 요청에 든 항목의 현재 표식과 새 표식을 비교해 더 뒤의 값과 표식을 함께 반영한다. 값이 이미 같아도 더 뒤의 표식은 보존한다. 같거나 앞선 표식의 재전송은 결과를 다시 바꾸지 않는다. 다른 항목은 그대로 둔다. 행 전체 `version`은 판본, 서버 `updatedAt`은 변경 조회용으로 유지한다. 두 값 모두 UPDATE의 승자를 결정하지 않는다.
- **기기 반영:** 서버가 결정한 값을 응답 또는 확인 가능한 조회로 받아 SQLite에 반영하고 해당 요청만 끝낸다. 후속 pull·화면 갱신에서도 같은 기록의 다른 미전송 편집을 보존한다.

**재현 예:** 폰이 오프라인에서 같은 경비의 지출액을 오전 9시 25 USD, 오전 11시 30 USD로 연속 저장한다. 태블릿이 정오에 금액을 다시 25 USD로 선택하고 폰이 오후 4시에 분류를 ‘교통’으로 바꾼다. 저녁에 FIFO를 보내거나 오전 9시 요청을 다시 보내도 최종 값은 **정오의 25 USD와 분류 ‘교통’**이다. 태블릿이 금액을 편집하지 않은 경우에는 30 USD가 남는다. [선택 이유와 검토 범위](../../../records/2026-11-10-01-update-conflict-policy.md)

### 기존 행과 구버전 UPDATE의 호환 방침

기존 일정·경비는 현재 값 그대로 읽는다. 과거 편집 이력이 없는 항목은 표식을 비워 두고, 새 형식으로 편집한 항목부터 표식을 기록한다. 행의 `updatedAt`이나 옛 요청의 서버 도착 시각을 각 항목의 편집 시각으로 채우지 않는다.

큐에서 미뤄진 요청과 온라인 직접 요청은 같은 서버 규칙을 따른다. 예를 들어 유효한 구버전 요청이 30 USD를 보내면 서버는 다음과 같이 판단한다.

| 서버에 있는 지출액 | 결과 |
| --- | --- |
| 20 USD, 표식 없음 | 기존 방식대로 30 USD를 반영하고 표식은 비워 둔다. |
| 이미 30 USD | 같은 값으로 완료한다. 기존 표식이 있으면 유지한다. |
| 25 USD, 새 편집 표식 있음 | 서버의 25 USD를 유지하고 충돌 결과를 반환한다. 옛 요청에는 수정하지 않은 항목까지 포함될 수 있어 30 USD가 실제로 더 나중 편집인지 판정할 수 없다. |

**여러 항목을 담은 구버전 UPDATE는 한 건 단위로 처리한다.** 요청에 포함된 값과 **같은 항목**의 서버 값이 다르고 그 서버 항목에 새 편집 표식이 있으면, 서버는 요청 한 건 전체를 보류한다. 충돌하지 않은 항목도 이 요청으로는 쓰지 않고 원래 입력 전체를 복구 가능하게 보존한다. 예를 들어 서버가 ‘기타 · 25 USD’이고 금액에 새 표식이 있으면, 옛 요청 ‘교통 · 30 USD’를 받아도 서버에는 ‘기타 · 25 USD’가 남는다. 구버전 앱이 부분 성공을 구별하지 못해 원래 입력을 잃는 일을 피하는 대신, 사용자가 원한 분류 변경도 보류된다. 이번 동의는 이 처리 단위에 관한 것이다(메시지 `msg_01a1c3a7-0658-7231-a6ba-d8bcba079f43`).

두 형식을 처리할 서버를 먼저 배포하고, 옛 큐를 읽는 새 앱을 다음에 배포한다. 새 앱은 충돌한 원래 입력을 복구 가능하게 보존한 뒤 자동 재시도만 끝낸다. 직접 요청에는 큐 사본이 없어 그 입력도 보존해야 한다. 구버전 앱에서는 성공 응답이면 큐 원본이 지워지고 실패 응답이면 전송이 멈춘다. 충돌한 큐는 앱 업데이트 전까지 막힐 수 있다는 비용을 받아들인다. [호환 결정의 원문 구간](../../../records/2026-11-10-02-legacy-update-compatibility.md)

### 새 앱에서 보류된 구버전 입력 확인과 정리

보류 사실을 발견한 순간에는 안내로 끝낸다. 앱은 옛 요청의 자동 재시도를 멈추고 다른 변경을 계속 동기화한다. 저장 중에 보류되면 그 자리에서 반영되지 않았음을 안내하고, 나중에 동기화하다 보류되면 사용자가 평소 보는 목록 등에서 해당 기록의 ‘수정 확인’을 발견할 수 있게 한다. 07은 이 동작과 해제 조건을 맡고, 실제 표시 위치와 문구는 [Workspace 008](../../../../008-exception-notice-rules/README.md)에서 기존 안내와 맞춘다.

| 사용자의 선택 | 원래 입력과 안내의 처리 |
| --- | --- |
| 안내만 보거나 확인한 뒤 닫기 | 아무 요청도 보내지 않는다. 원래 입력 전체와 해당 기록의 안내를 유지한다. |
| 이전 요청과 현재 값의 차이를 확인하고 원하는 항목만 다시 저장 | 선택한 항목으로 새 형식의 UPDATE를 만든다. 예를 들어 분류만 선택하면 금액은 그대로 둔다. 새 요청이 안전하게 저장된 뒤에만 옛 입력과 안내를 정리한다. 오프라인에서는 로컬 변경과 새 큐 기록이 함께 확정된 때가 그 시점이다. |
| ‘현재 값 유지’를 명시적으로 선택 | 새 변경을 보내지 않고 그 보류 입력과 안내를 정리한다. |

구버전 요청에는 사용자가 건드리지 않은 항목도 들어갈 수 있으므로 현재 값과 **이전 요청에 담긴 값**을 비교해 보여준다. 사용자가 당시 어떤 항목을 고치려 했는지는 추정하지 않는다. 사용자 합의는 메시지 `msg_01a1c3f4-ddc9-7c80-a7dd-5addf61a9ae8`에 있다.

### 자기 여행의 삭제가 확인된 경우

서버가 인증된 사용자 소유 여행의 삭제를 명시적으로 확인하면, 폰에서도 여행 삭제를 반영하고 **그 여행에 속한다고 확인된 일정·경비의 미전송 변경과 해당 전송 요청을 함께 정리**한다. 새로 만든 일정·경비, 기존 일정·경비에 남은 수정과 삭제 요청도 포함한다. 서버에는 삭제된 여행의 자식을 새로 등록하지 않는다. 삭제한 기기에서 보이지 않았던 다른 기기의 최종 입력까지 사라지며 사용자는 이를 나중에 되찾을 수 없다. 단순 404나 소유권·여행 귀속이 불명확한 요청에는 이 규칙을 적용하지 않는다. [Ticket 08의 격리 규칙](08-orphaned-queue-task-blocks-login.md)은 그 조건에 따라 유지한다.

경비에 대한 [첫 결정](../../../records/2026-11-10-03-deleted-trip-pending-expenses.md) 뒤 사용자는 “그 여행에 속한 미전송 일정도 경비랑 같이 정리하는 걸로 하자”라고 범위를 확정했다(메시지 `msg_01a1c386-9b9b-7b03-a434-3740d31c455d`).

현재 [여행 편집 화면](../../../../../../../apps/client/src/features/trip/update-trip/EditTripDrawer.tsx)과 [홈 여행 목록](../../../../../../../apps/client/src/screens/HomeScreen/TripsSection.tsx)의 삭제 전 확인창은 모두 “모든 일정과 경비도 함께 삭제됩니다.”라고 안내한다. 두 구현에서 문구를 확인했고, 이 결정에서 문구나 제품 코드를 변경하지 않았다. [결정 경위와 원문](../../../records/2026-11-10-03-deleted-trip-pending-expenses.md)

### 여행은 남고 연결한 일정만 삭제된 경우

사용자는 “일정만 삭제되면 경비는 그대로 두고 일정 연결만 푸는 걸로 하자”라고 결정했다(2026-11-10, 메시지 `msg_01a1c377-2fba-7851-9808-28f4dd553399`). 경비는 여행에 속하고 일정 연결은 선택이므로, 같은 여행의 경비 탭에서 원래 날짜와 금액으로 확인할 수 있어야 한다.

- **경비가 먼저 저장되면** 일정을 삭제할 때 그 일정에 아직 연결된 경비의 `scheduleId`를 비운다.
- **일정이 먼저 삭제되면** 뒤늦게 들어온 경비의 여행이 유효하고 그 일정이 같은 여행의 삭제된 일정임을 서버가 확인한 뒤, `scheduleId`를 비워 경비를 저장한다. 직접 요청과 큐 전송에 같은 처리를 적용한다.

두 순서 모두 빈 연결을 SQLite까지 반영하고, 오래된 경비 요청이 와도 삭제된 일정에 다시 연결되지 않아야 한다. 현재 [DB 외래 키](../../../../../../../apps/server/src/db/schema.ts)의 `ON DELETE SET NULL`은 행을 물리 삭제할 때 작동한다. [일정 삭제](../../../../../../../apps/server/src/routes/schedules.ts)는 행에 `deletedAt`을 기록하고 [경비 생성](../../../../../../../apps/server/src/routes/expenses.ts)은 요청의 일정 ID를 그대로 넣으므로, 현재 코드만으로 이 결과를 보장하지 않는다.

### 수정하려던 일정·경비 자체가 삭제된 경우

서버가 로그인한 사용자 소유의 일정 또는 경비가 이미 삭제됐음을 확인하면, 폰은 해당 삭제를 화면·SQLite에 반영하고 그 기록의 미전송 UPDATE를 종결한 뒤 다음 요청을 전송한다. 예를 들어 삭제된 일정의 출발 시간이나 삭제된 경비의 금액은 수정할 대상이 남지 않는다. 수정값은 서버에 반영되지 않으며, 늦은 편집 표식으로 기록을 되살리지 않는다. 원인을 구분할 수 없는 404만으로는 요청을 정리하지 않는다. 일정만 삭제되고 경비 자체는 남는 경우에는 위의 연결 해제 규칙을 쓴다.

일정의 시간 수정 종결을 확인한 뒤 사용자는 “그 좋아 경비도 같은 방식이겠네”라고 경비 자체에도 같은 기준을 적용했다(메시지 `msg_01a1c382-1bc9-74d2-a9d9-7abfc1380e65`).

### 003 Ticket 12와 확정한 구현 분담

**서버 변경 수신은 [003 Ticket 12](../../../../003-bug-investigation-and-fixes/current/memory/tickets/12-pull-consistency.md)가 맡는다.** 변경 누락을 막고, 서버 값을 SQLite에 반영할 때 아직 보내지 않은 편집을 보존한다. **수정 요청 전송은 이 Ticket이 맡는다.** 서버에서 같은 항목의 표식으로 최종 값을 결정하고, 폰에 결과를 반영한 뒤 처리된 요청만 종결한다.

예를 들어 서버 금액 25 USD를 받아올 때 폰에 미전송 30 USD가 남았다면 Ticket 12가 그 입력과 표시값을 보호한다. 이후 30 USD 요청이 서버에 도달하면 이 Ticket이 채택된 금액으로 수렴시키고 해당 큐 작업을 끝낸다. 기존 수신 책임을 유지하면서 두 경로가 같은 항목별 규칙을 따르도록 분담했다(사용자 결정 메시지 `msg_01a1c414-f511-7392-a511-c84697ab5dea`).

### 구현에서 구체화할 범위

- **구버전 보류 입력의 구현:** 충돌 응답 형식과 앱의 보존·복구 경로를 구현하고 실제 표시 위치·문구는 008의 안내 규칙과 맞춘다.
- **그 밖의 삭제 조합과 소유권:** 아직 결정하지 않은 미전송 생성·삭제 조합과 부모 소유권 확인은 별도로 다룬다.

**삭제 확인과 정리의 구현 과제**
- **서버의 명시적 응답:** 지금 404는 "없음·다른 사용자의 것·이미 삭제됨"이 같은 값이다. 자기 행이 이미 삭제된 경우를 따로 알려야 앱이 추측하지 않고 판단할 수 있다. Ticket 01의 삭제 재전송 처리와 같은 방식으로, 자기 행만 다시 확인한다.
- **선행 결과:** 경비 생성은 지금 부모 여행을 확인하지 않아, 지운 여행에도 경비가 만들어진다. 그래서 '여행이 삭제됨' 규칙에는 003 Ticket 13의 경비 부모 확인이 먼저 필요하다.

**함께 볼 것**
- **늦게 도착한 수정이 새 수정을 덮는 문제:** 현재 일정·경비 PUT은 항목별 표식을 비교하지 않는다. 구현할 때 저장 값과 표식의 비교·갱신을 같은 서버 연산으로 확정한다. [일정 수정](../../../../../../../apps/server/src/routes/schedules.ts), [경비 수정](../../../../../../../apps/server/src/routes/expenses.ts)
- **pull upsert:** 미전송 queue·version을 비교하지 않고 덮는다([데이터 수명](../../../../../../project/guidance/data-lifecycle/INDEX.md) 71행).
- **여행별 큐:** pull 보호가 생기면 이 Ticket 뒤에 다시 판단한다.

## 완료 조건과 확인 방법

- 조합 재현 결과와 채택한 규칙, 사람 선택이 필요한 경우를 기록한다. 미확정 정책이 결과를 막으면 구현 완료로 닫지 않는다.
- 연속 큐, 다른 기기의 독립 항목 수정, 같은 값으로의 되돌림, 응답 유실 후 중복 전송, 동률·역행 시계에서 이미 관찰한 편집의 순서를 검사한다. 전송 순서가 달라도 같은 값에 도달하며 다음 미전송 입력이 남는지 확인한다.
- 기존 행과 구버전 UPDATE의 위 세 경우를 큐·직접 요청에서 확인한다. 혼합 요청 보류 시 다른 항목까지 서버 값이 그대로인지, 원래 입력 전체를 복구할 수 있고 새 앱에서 나머지 큐가 진행되는지 확인한다.
- 확인 후 닫기에는 보류 입력과 안내가 남는지, 원하는 항목의 새 요청 저장 성공 또는 명시적인 ‘현재 값 유지’ 뒤에만 둘이 정리되는지 확인한다.
- 서버가 자기 행의 '이미 삭제됨'을 다른 404와 구별해 응답하고, 다른 사용자에게는 여전히 존재를 드러내지 않는다.
- 내 일정·경비 자체의 삭제가 확인되면 미전송 UPDATE를 종결하고 다음 작업이 전송되는지, 같은 조건에서 기록이 되살아나지 않는지 확인한다.
- 자기 여행 삭제가 확인되면 그 여행의 미전송 일정·경비와 생성·수정·삭제 요청이 함께 정리돼 다른 여행의 전송이 이어지는지 확인한다. 최초 생성과 응답 유실 뒤 재전송 모두 삭제된 여행이나 자식이 다시 화면에 나타나지 않아야 한다. 삭제 증거·귀속 근거가 없는 요청에 같은 정리가 실행되지 않는지도 확인한다.
- 같은 여행 안에서 경비 등록과 일정 삭제를 두 순서로 실행해 경비 금액·날짜는 남고 `scheduleId`만 서버와 기기에서 비워지는지, 옛 요청의 재전송이 삭제된 일정 연결을 복구하지 않는지 확인한다.
- 채택한 규칙에서 막힌 큐가 풀리고, 후속 pull 뒤 화면·SQLite·서버가 같은 값에 도달함을 테스트와 실제 앱에서 확인한다.
- 우리 버그·손상 payload는 이 규칙으로 버려지지 않는다.

## 현재 상태와 실제 결과

살아 있는 일정·경비 UPDATE, 구버전 요청의 보류·안내·선택적 재저장과 정리 조건을 확정했다. 자기 여행의 삭제가 확인되면 그 여행의 미전송 일정·경비도 정리하고, 일정만 삭제되면 경비는 보존하고 연결만 해제한다. 수정하려던 자기 일정·경비 자체의 삭제가 확인되면 그 UPDATE를 종결한다. 대화 중 새 형식의 전송 순서를 바꾼 모델에서 예상 결과를 확인했고, 여행 삭제 전 안내는 두 진입점의 코드에서 확인했다. 003 Ticket 12의 수신 보호와 이 Ticket의 전송·종결 분담은 확정했다. 제품 구현·배포와 DB·실제 앱 검증은 아직 수행하지 않았다. 003 Ticket 13의 부모 확인과 008의 안내 배치·문구를 연결하고, 기존 순서대로 1단계, 출시, Ticket 06 뒤에 구현한다.
