# 03. 막힌 큐가 실제 앱에서 풀리는지 확인

## 맡은 결과와 범위

01·02를 합친 최신 판본으로 다음을 확인한다. 실제로 막혀 있던 개발 앱이 다음 동기화에서 풀리고, 뒤 작업 전송과 pull까지 이어진다. 구현에 참여하지 않은 검증자가 01·02의 테스트·문서·동작 근거를 최신 판본에서 확인한다.

1단계 제품 Verify의 claim과 고정 argv도 이 Ticket에서 구성한다. Ticket을 만들 때 `verify.json`은 recover.json의 JSON 파싱만 확인했다.

## 실행 맥락과 접근

- 막힌 상태의 원본은 2026-11-02 시뮬레이터 개발 앱의 로컬 DB 백업이다. 큐 맨 앞에 FAILED·retryCount 3인 경비 CREATE가 있고, 뒤에 PENDING 작업이 있다. 위치와 해시는 [source](../../../source/index.md)에 있다. 임시 폴더라 지워질 수 있다.
- 백업이 없으면 같은 상태를 다시 만든다. 로컬 서버 DB에 경비 행을 넣고, 앱 큐에 같은 ID의 CREATE를 FAILED·retryCount 3으로 넣는다. IN_PROGRESS로 남은 작업도 하나 넣어 Ticket 02의 되돌림을 함께 본다.
- 관찰 사례에서는 큐 등록 뒤 약 57초 안에 실패가 3번 쌓였다. 동기화가 앱 시작·연결 회복 때만 돈다는 설명보다 잦다. 확인할 때 동기화가 몇 번 시작되는지도 로그로 센다. 결과가 [Spec 02](../spec/02-behavior-and-cases.md)의 헛요청 추정을 바꾸면 그 문장을 고친다.
- 실행 환경은 로컬 개발 서버·PostgreSQL과 iOS 시뮬레이터 개발 앱이다. 운영 서버와 운영 DB는 쓰지 않는다. 앱 실행은 [start-app](../../../../../../../.agents/skills/start-app/SKILL.md)의 조건을 따른다.
- 독립 검증은 [development 검증 상세](../../../../../../../.agents/skills/development/references/verification/INDEX.md)를 따른다. 별도 검증자를 쓸 수 없으면 Main이 확인하고 더 약한 근거임을 밝힌다.

## 완료 조건과 확인 방법

- 새 서버와 새 앱에서 첫 동기화 때 다음을 서버 로그와 큐에서 관찰한다.
  - 막혀 있던 CREATE가 200으로 끝난다.
  - 뒤의 PENDING 작업이 전송된다.
  - pull이 실행된다.
  - 큐가 빈다.
- 남은 IN_PROGRESS가 다시 전송되고 중복 행이 생기지 않는다.
- 검증자가 01·02의 완료 조건을 요구별로 "충족 근거 있음·불충족 근거 있음·미확인"으로 반환한다. 문서가 실제 동작과 맞는지도 포함한다.

## 현재 상태와 실제 결과

2026-11-03에 완료 조건을 충족했다. 근거와 로그 발췌는 [실제 앱 확인 기록](../../../records/2026-11-03-05-stage-one-real-app-verification.md)에 있다.

- **실제 앱:** 11-02의 막힌 DB와 IN_PROGRESS 일정 1건(서버에 같은 행 있음)으로 앱을 시작했다. 첫 동기화에서 세 작업이 `Success 200`으로 끝났고 pull이 돌았다. 큐는 비었고 서버 일정 행은 1개를 유지했다. 별도 검증자가 같은 준비로 다시 실행해 같은 결과를 얻었다.
- **독립 검증 (Sonnet medium):** 01·02·03의 완료 조건을 요구별로 "충족 근거 있음"으로 판정했다. 미확인은 "서버 수정을 되돌리면 실패"뿐이며 Main의 11-03 확인만 근거다. client typecheck 8건은 이전부터 있던 실패다.
- **동기화 시작 횟수:** 약 4분, 홈 복귀를 포함해 1번이었다. 실행 조건이 새로 갖춰질 때와 수동 실행에서만 시작한다. 이 관찰은 숨은 반복 실행이 없다는 것만 보여 주며, 연결이 자주 끊기는 실제 사용의 빈도는 모른다. 10-31의 1분 3회 원인도 미확인이다. 그래서 간격 재시도는 보류하고 빈도를 계속 지켜본다. 다시 볼 조건은 [Spec 02](../spec/02-behavior-and-cases.md)와 [데이터 수명](../../../../../../project/guidance/data-lifecycle/INDEX.md)에 반영했다.
- **제품 Verify:** claim을 서버 재전송 route 단위 테스트로 구성했다. 12:42Z `verification_passed`. 실제 PostgreSQL·앱 큐·실제 앱 경로는 claim 밖이다.
- **증명하지 않은 것:** 수정 전 서버와의 실제 앱 대조, 실제 앱의 실패·인증 오류 경로, 실제 응답 유실(서버 행을 미리 넣어 흉내 냈다).
