# 판단을 대조할 실제 사례

아래 사례는 분석의 출발점이며 미리 정한 원인이나 개선 목록이 아니다. 정확한 발화와 당시 근거는 [선별 원문](../../../../007-sync-failure-recovery/source/2026-11-12-stage-one-review-dialogue.md) 및 [판단 과정 기록](../../../../007-sync-failure-recovery/records/2026-11-12-11-stage-one-judgment-and-next-tickets.md)에서 찾는다.

- 저장 잠금: 하나의 act 안의 연속 fireEvent를 실제 사용자 중복 탭의 근거로 삼았다. 순차 userEvent·RHF 제출 상태·외부 폼 교체를 구별한 뒤 공통 잠금은 제거하고 늦은 응답 보호는 유지했다. 왜 최초 검토가 이 구별을 놓쳤는지 본다.
- 초기화: 현재 구조에서 reset이 필요하다는 설명에서 시작했지만, 부모 렌더링·key·실제 onClose·React 공식 동작을 대조한 뒤 폼 수명으로 초기화를 표현했다. snapshot과 해제 후 보호는 남고 불필요한 initializer/reset은 사라졌다. 기술명 확인과 구체적인 코드 선택 판단을 구별한다.
- 보존 범위: Local·큐에 저장한 미전송 입력의 보호를 모든 닫힌 폼 초안의 복원으로 넓히지 않았다. 성공 후 닫기라는 사용자 선택이 추가 상태·감지·자동 저장을 불필요하게 만들었다. 제품 합의와 AI가 더한 요구를 구별한다.
- 저장 계층·경로: prepare 중복, 폼의 경로 계산을 실제 호출자·표현·실행 시점·기존 유틸과 대조해 정리했다. 같은 모양의 parse·순서 제어·트랜잭션도 이유가 다르면 유지했다.
- 과정 종합: 사용자가 구체적인 검토 관점들을 예로 들었는데 Main이 관점 목록이나 미래 절차로 옮겼다. self-check는 같은 선택을 여러 근거로 대조한 연결이 빠졌다고 판단했다. 사용자의 마지막 아쉬움이 해소됐는지는 확인되지 않았다.

사례의 결론을 다른 코드에 그대로 적용하지 않는다. 원인에 관한 Main·감사자 해석도 근거와 반례로 재판단한다.
