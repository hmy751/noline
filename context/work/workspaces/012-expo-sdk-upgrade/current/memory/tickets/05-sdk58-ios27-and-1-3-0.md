# 05 — SDK 55→58·iOS 27로 올리고 1.3.0을 낸다

**상태:** 시작 전 (2026-11-17 확정). 1.2.0 출시 뒤 2월에 하고 3월 초에 1.3.0을 낸다. 가장 무거운 Ticket이라 아래 체크포인트 단위로 이어 간다. 범위는 02의 판정과 04의 결과로 바뀔 수 있다.

## 맡은 결과와 범위

Apple의 2027년 4월 요건(iOS 27 SDK 빌드)을 맞춘 1.3.0을 낸다. 앱은 SDK 58(RN 0.88, React 19.3)로 iOS 27에서 시작하고, 기존 사용자가 1.2.0에서 업데이트해도 데이터가 보존된다. 업그레이드 뒤 바뀐 사실을 Project에 반영해 다음 작업자가 찾을 수 있게 한다. 출시 2번 가운데 두 번째이며 이 Work의 목표 1을 이루는 출시다.

이 Ticket이 끝나면 다음이 성립한다.
- 1.3.0이 Xcode 27 이미지(iOS 27 SDK)로 빌드돼 업로드 경고 없이 심사를 통과했다.
- iOS 27.2.1 실기기에서 정상 시작한다(UIScene).
- 1.2.0 → 1.3.0 업데이트에서 로그인·여행 데이터·미전송 변경·오프라인 지도가 보존된다.
- OTA가 새 빌드에서 다시 동작한다.
- 테스트 도구가 최신(RNTL 14, jest 30)으로 옮겨졌고 검사가 기준선 수준 이상이다.
- Project의 버전·출시 서술이 업그레이드 뒤 사실과 맞다.

Spec과의 연결: [완료 판단](../spec/04-quality-and-completion.md)의 1(Apple 요건), 2(iOS 27 시작), 3·4·5·7을 1.3.0에서, 6·11(의존성 정합·중복 없음)을 SDK 58에서, 9(재발 방지 중 Project 반영)를 맡는다.

## 실행 맥락과 접근

**선행:** 04(1.2.0 출시). 1.2.0 뒤 1주일 Sentry 관찰에서 새 크래시가 없어야 1.3.0을 낸다.

**체크포인트.** 각 체크포인트가 끝날 때 아래 상태 절에 결과를 남겨, 중간에 끊겨도 다음 사람이 이어 갈 수 있게 한다.

1. **테스트 도구 먼저(1주일 관찰 동안, 앱은 그대로).** RNTL 14.1 + `test-renderer`, jest 30, 그에 맞는 jest-expo로 옮긴다. `render`·`fireEvent`·`act`가 비동기가 되고 `UNSAFE_*`가 사라져 테스트 파일 약 78개에 닿는다(69개는 이미 `@jest/globals`를 import). 앱 플랫폼과 따로 바꿔야 테스트 실패가 앱 문제인지 테스트 API 변경인지 가를 수 있다. **조건:** 02에서 RNTL 14가 SDK 54의 jest-expo와 동작하지 않는다고 나오면, 이 체크포인트는 SDK 58 단계(5)로 옮긴다. **2026-11-18 02 판정: 동작한다.** jest-expo 54.0.18 + jest 29.7.0 + RNTL 14.1.0 + test-renderer 1.3.1에서 비동기 render·press·입력 테스트 1개가 통과해 이 체크포인트를 1주일 관찰 기간에 둔다. 앱 테스트 78개 이전 비용과 jest 30 조합은 확인하지 않았다([02 판정 기록](../../../records/2026-11-18-06-ticket02-device-verification.md#테스트-도구와-목표-버전)).
2. **SDK 55.** 한 단계씩 올린다(Expo 권장 "one at a time"). 중간 SDK는 로컬 빌드와 검사로 확인한다.
3. **SDK 56.** 최소 iOS가 16.4가 된다(사용자가 수용함). expo-sqlite 56은 blob을 native ArrayBuffer로 돌려준다(조사 서브의 보고).
4. **SDK 57.**
5. **SDK 58과 iOS 27.**
   - RN 0.88·React 19.3, reanimated 4.7.1 + worklets 0.13.0, rnmapbox ≥10.3.10, react-native-maps 1.29.11, screens 4.30, expo-router 58(navigation 재작성, web 기본 server 출력), Sentry ~8.28
   - TS ~6.0(`strict` 기본, `types: []` 기본, `baseUrl` 폐기)과 typescript-eslint 8. RN 0.87부터 Strict TypeScript API가 기본이라 `react-native/Libraries/*` deep import가 타입 오류가 된다. ESLint 9 전환은 SDK 58이 요구할 때만 넣는다(Main 기본값).
   - EAS 이미지를 Xcode 27로 바꾼다. prebuild가 `SceneDelegate.swift`와 `UIApplicationSceneManifest`를 만든다.
   - fingerprint 기본 방식이 `balanced`로 바뀐다. runtime 계산과 발행 스크립트의 대조가 그대로 맞는지 본다.
   - 버전 근거는 [라이브러리 호환 조사](../../../source/library-compatibility-2026-11-17.md)의 SDK 58 열이며, 02에서 확정한 표를 우선한다.
6. **1.3.0 출시.** [출시 기준](../../../../../../project/guidance/app-release-and-ota.md)을 따르고, 출시하면서 `release/1.3`을 만든다(출시마다 release 브랜치).
7. **Project 반영.** 출시한 뒤 [출시 기준](../../../../../../project/guidance/app-release-and-ota.md)의 "1.1.4부터 최소 iOS 15.0" 같은 서술, 설치 규칙(`npx expo install`, `--check`), 버전 사실을 [Project 관리 계약](../../../../../../project/MAINTENANCE.md)에 따라 반영한다. 어디에 무엇을 남길지는 [선택한 Project 맥락](../project-context.md)을 참고한다.

**기존 사용자 업데이트 확인.** 04와 같은 방식으로 1.2.0 → 1.3.0을 실제 출시 빌드로 확인한다. 어느 앱에서 할지는 04에서 정한 것을 따른다.

**fmt consteval 우회(03에서 넣음).** `apps/client/plugins/with-fmt-consteval-off.js`는 RN 0.76–0.81과 Xcode 26 clang 조합에서 필요했다(SDK 54까지 확인). SDK 55–58 각 단계에서 등록을 빼고 빌드해 보고 없이 되면 지운다. Xcode 27 이미지로 바꾸는 SDK 58 단계에서도 다시 본다. React 19 때문에 넣은 Jest `fakeTimers.doNotFake: ['queueMicrotask']`도 체크포인트 1의 테스트 도구 이전 때 함께 본다. 경위는 [SDK 54·달라진 것 기록](../../../records/2026-11-18-08-ticket03-sdk54-and-plan-deviations.md)에 있다.

**실행하며 정할 것:** 체크포인트 1의 위치(02 결과), SDK 55–57에서 각각 확인할 범위, Project에 남길 위치.

## 완료 조건과 확인 방법

- 체크포인트마다 로컬 빌드·검사 결과가 남아 있고, 마지막 preview 빌드에서 실기기 점검표 6항목이 기준선과 같다.
- iOS 27.2.1 실기기에서 1.3.0 빌드가 정상 시작한다. 최소 iOS 16.4 근처는 iOS 16.4 시뮬레이터로 시작을 확인한다(Main 기본값).
- 1.2.0에 데이터와 지도를 넣은 상태에서 1.3.0을 덮어 설치해 보존된다.
- 1.3.0 빌드에서 OTA 받기·업데이트를 기다리지 않는 시작·롤백이 되고, 1.2.0 runtime과 분리된다.
- `npx expo install --check`가 SDK 58 기준으로 통과하거나 차이마다 이유가 있다. React·RN이 한 버전씩만 설치돼 있다.
- client·server·schema·ui 검사가 기준선과 같거나 더 낫다.
- 업로드 메일에 최소 iOS·SDK 경고가 없고 심사를 통과했다. `release/1.3`이 있다.
- Project의 출시 기준과 버전 서술이 갱신됐다.
