# 02 — 데이터 보존 선검증과 목표 확정

**상태:** 판정 완료 (2026-11-18). 기기 DB·지도 목록·지도 화면·저장 공간 네 판정이 모두 성공이라 멈춤 조건에 해당하지 않고 03으로 갈 수 있다. 04의 지도 대응은 필요 없다는 판정이다. 테스트 도구 선이전은 가능하다. 목표 버전 표의 확정과 기기 원복은 남았다(아래 결과).

## 맡은 결과와 범위

업그레이드에서 가장 큰 불확실성 두 가지를 구현 전에 실기기로 판정한다. 결과에 따라 03–05의 범위가 정해진다.

1. **기기 DB가 남는가.** expo-sqlite 14(1.1.4)에서 16으로 바뀐 앱이 덮어 설치됐을 때, 기존 DB를 같은 위치에서 열고 여행 데이터와 미전송 변경(`sync_queue`)이 그대로인가.
2. **오프라인 지도가 남는가.** native Mapbox v10(1.1.4)에서 받은 pack을 v11 빌드가 쓸 수 있는가. 판정 결과로 04에 지도 대응이 필요한지 정한다.
3. **목표 버전 표가 확정된다.** [라이브러리 호환 조사](../../../source/library-compatibility-2026-11-17.md)를 바탕으로 03·04·05의 목표 버전을 정하고 남은 미확인을 줄인다.
4. **테스트 도구 선이전 가능 여부가 정해진다.** RNTL 14가 SDK 54의 jest-expo와 함께 동작하는지 확인해, 05에서 테스트 도구를 1주일 관찰 기간에 먼저 옮길 수 있는지 정한다.

이 Ticket은 앱을 업그레이드하지 않는다. 검증용 최소 앱은 판정용이며 main에 병합하지 않는다.

**멈춤 조건(확정):** 기기 DB가 업데이트 뒤 그대로 열리지 않으면 03으로 가지 않는다. 보존 방법부터 다시 설계한다. 지도는 안내로 대응할 수 있지만 DB는 여행 데이터 자체라 그럴 수 없다.

Spec과의 연결: [완료 판단](../spec/04-quality-and-completion.md)의 3(기존 사용자 업데이트)을 먼저 확인하고, 5(위험 영역)의 확인 방법을 정한다. 04·05에서 실제 출시 빌드로 다시 확인한다.

## 실행 맥락과 접근

**선행:** 01과 병행할 수 있다. 실기기 점검표(01)가 먼저 정해져 있으면 1.1.4 상태 확인에 같은 항목을 쓴다.

**왜 이 방법인가.** 지도와 DB 모두 공식 문서에서 보존 여부를 찾지 못했다(조사 서브의 보고). 앱 전체를 올려 보기 전에, 바뀌는 부분(expo-sqlite 16, Mapbox v11, New Architecture)만 넣은 작은 앱으로 하루 이틀 안에 판정한다. 지도 문제의 구조와 대응 결정은 [재구성·지도 대응 기록](../../../records/2026-11-17-05-ticket-restructure-and-map-data-plan.md)에 있다.

**설치 순서**

1. **1.1.4 preview를 새로 빌드해 설치한다.** 기존 preview 빌드 `f610d9b5…`는 1.1.3/17이라 main과 맞지 않는다(011 Ticket 01의 주의). 2026-11-18 Ticket 01에서 `release/1.1`로 preview 빌드 `30c46ce2-39f7-450d-9c1c-bce9b4f2dff6`(1.1.4/18, `d160c7b5`)를 만들어 iPhone의 기존 1.1.3 위에 덮어 설치했다. 지금 기기의 preview 앱은 이 빌드에 깨끗한 코드의 업데이트 `0272f0e0`이 적용된 상태다. 덮어 설치 전 1.1.3 앱의 데이터가 남았는지는 보지 않았으므로, 2의 데이터는 이 1.1.4 앱에서 새로 넣는 것을 기준으로 한다. EAS preview 프로필은 `APP_VARIANT=development`로 `com.noline.dev` 앱을 만든다. iPhone 14 Pro는 ad hoc 프로필에 등록돼 있다(2026-12-30 만료).
2. **데이터를 넣는다.**
   - 로그인하고 여행을 만들어 활성화한다. 일정·경비를 몇 개 넣는다.
   - 비행기 모드에서 변경을 하나 더 만들어 `sync_queue`에 미전송 항목을 남긴다.
   - 도시 지도를 받는다. 비행기 모드에서 지도가 그려지는지 보고, pack 목록(디버그 화면의 `getPacks`)과 저장 공간 표시를 기록한다.
   - 비교용으로 DB의 표별 행 수와 `sync_queue` 내용을 남긴다. 방법은 실행하며 정한다.
3. **검증용 최소 앱을 만든다.** SDK 54, New Architecture, expo-sqlite 16, rnmapbox 10.3.x(native Mapbox v11)만 넣는다. 번들 ID는 같은 `com.noline.dev`, 서명은 같은 팀이어야 덮어 설치 때 앱 데이터가 이어진다. 앱이 하는 일은 셋이다.
   - 앱과 같은 DB 이름으로 `openDatabaseSync`를 열고 표별 행 수와 `sync_queue`를 보여 준다.
   - `offlineManager.getPacks` 결과를 보여 준다.
   - 받은 도시 범위의 지도를 그린다.
   어디에 만들지(버리는 브랜치, 별도 폴더)와 Mapbox 토큰 전달 방법은 실행하며 정한다.
4. **1.1.4 preview 위에 덮어 설치한다.** 삭제하고 새로 설치하면 데이터가 지워지므로 반드시 덮어 설치한다.
5. **판정한다.**

**판정 기준**

| 대상 | 성공 | 실패일 때 |
| --- | --- | --- |
| 기기 DB | 같은 위치에서 열리고, 표별 행 수와 `sync_queue` 미전송 항목이 2단계 기록과 같다 | **멈춤.** 03으로 가지 않고 보존 방법을 다시 설계한다 |
| 지도 목록 | `getPacks`에 2단계의 pack이 그대로 나온다 | 04에 지도 대응을 넣는다 |
| 지도 화면 | 비행기 모드에서 받은 범위가 실제로 그려진다. 목록에 있어도 화면이 비면 실패다 | 04에 지도 대응을 넣는다 |
| 저장 공간 | 옛 pack 파일이 쓸 수 없는 채로 공간을 차지하지 않는다. v11이 옛 파일을 못 보면 지울 수 있는지도 본다 | 04의 정리에 옛 파일 삭제를 넣는다. 지울 수 없으면 방법을 다시 찾는다 |

지도가 실패할 때 04에 넣을 대응은 확정한 방향이다. 새 지도 기록에 엔진 버전(`mapEngine`)을 남기고, 업데이트 뒤 첫 실행에 한 번 옛 기록의 `mapDownloaded`를 내려 "지도 다시 받기 필요"로 바꾸고 옛 파일을 정리한다. 첫 실행 즉시 안내하며, 활성 여행은 기존 재시도 경로로 지도만 다시 받고 비활성 여행은 다음 활성화 때 받는다. 상세는 [04](04-new-architecture-and-1-2-0.md)에 있다.

**목표 버전 표와 테스트 도구**
- [라이브러리 호환 조사](../../../source/library-compatibility-2026-11-17.md)의 표를 03·04·05의 목표로 확정한다. 남은 미확인 가운데 nativewind의 SDK 58 지원, @rn-primitives·react-native-calendars의 React 19·New Architecture 동작을 줄일 수 있는 만큼 줄인다. SDK 55–57 건너뛰기는 Expo 권장("one at a time")에 따라 한 단계씩 올리는 것으로 이미 정했다.
- RNTL 14 + jest-expo 54: React ≥19, RN ≥0.78, Node ^22.13 또는 ≥24가 RNTL 14의 조건이다(조사 서브의 보고). 검증용 앱이나 버리는 브랜치에서 jest-expo 54와 함께 몇 개 테스트를 돌려 판정한다. 방법은 실행하며 정한다.

**실행하며 정할 것:** 검증용 앱의 위치와 구성, DB 내용을 비교하는 방법, 테스트 도구 판정 방법.

## 완료 조건과 확인 방법

- DB·지도 목록·지도 화면·저장 공간 네 판정이 기기(iOS 버전), 빌드 ID, 비교한 값과 함께 남아 있다.
- 판정에서 나온 결정이 적혀 있다: 03 진행 여부(DB), 04 지도 대응 필요 여부와 범위(지도).
- 03·04·05의 목표 버전 표가 확정돼 있고, 남은 미확인과 그것을 확인할 Ticket이 적혀 있다.
- 테스트 도구 선이전 가능 여부가 근거와 함께 적혀 있다. 불가면 05에서 SDK 58 단계로 돌린다.
- 검증용 앱이 main에 들어가지 않았다.

## 현재 상태와 실제 결과

2026-11-18 사용자가 "Ticket 02 시작"을 골라 진행했다. 실기기는 사용자의 `/device-access-setup` 요청으로 Main이 USB로 직접 조작했고, 로그인과 비행기 모드 켜기·끄기는 사용자가 했다. 과정은 [판정 기록](../../../records/2026-11-18-06-ticket02-device-verification.md), 읽은 값은 [판정 원자료](../../../source/ticket-02-verification-2026-11-18.md)에 있다.

**실행하며 정한 것**
- 검증용 앱: 저장소 밖 scratchpad의 `verify-02`("Noline (판정)", `com.noline.dev`, 같은 EAS 프로젝트·팀). SDK 54, RN 0.81.5, React 19.1.0, New Architecture, expo-sqlite ~16.0.10, @rnmapbox/maps 10.3.18(native v11). 읽기만 한다. EAS 프로필 `verify02`는 채널이 없어 OTA 대상에 영향이 없다. 빌드 90 `3db6fe71-604f-48cc-9073-75aa922aaf14`, 빌드 91 `e9cfd75d-b81d-440f-8c87-dda010258122`(v11 pack `bounds` 파싱 수정).
- 데이터: 새 여행을 만들지 않고 계정의 여행 "도쿄, 일본"을 오프라인 활성화했다. 비행기 모드에서 경비 1건을 추가해 미전송 변경을 남겼다. 1.1.4 디버그 화면은 `__DEV__` 전용이라 `getPacks` 대신 프로필 저장 공간 표시(272 KB·196.3 MB)로 비교했다.
- 설치: `.ipa`를 `xcrun devicectl device install app`으로 USB 덮어 설치. 새 빌드는 첫 실행에 iOS가 온라인으로 개발자 신뢰를 확인해야 해 비행기 모드를 잠시 껐다(판정용 앱에는 동기화 코드가 없다).
- 시뮬레이터는 시도했다가 사용자 확인으로 중단했다(운영 번들로 잘못 빌드됨, 비행기 모드가 없어 지도 화면 판정 불가).

**결정:** 03 진행 가능(DB 성공, 멈춤 아님). 04 지도 대응 필요 없음(지도 세 판정 성공). 한계는 rnmapbox 10.3.18 한 조합, 기기 1대, 도시 하나다. 1.1.4 자체의 오프라인 일정 지도에서 육지 배경은 지도 조작이 안 돼 보지 못했다.

**테스트 도구:** 선이전 가능. 저장소 밖 `rntl-check`에서 jest-expo 54.0.18 + jest 29.7.0 + RNTL 14.1.0 + test-renderer 1.3.1(React 19.1.0, RN 0.81.5)로 render·press·changeText·waitFor 비동기 테스트 1개가 통과했다. 앱 테스트 78개를 옮기는 비용과 jest 30 조합은 보지 않았다.

**목표 버전:** rnmapbox 10.3.18이 SDK 54 + New Architecture 단계에서 오프라인 보존을 만족한다. nativewind 4.2.7, @rn-primitives 1.5.x, react-native-calendars 1.1314.0은 npm peer에 React·RN 제한이 없다(공식 지원 보장은 아니며 03·04 빌드에서 확인). 그 밖의 버전은 [라이브러리 호환 조사](../../../source/library-compatibility-2026-11-17.md)의 표를 그대로 목표로 쓰며, 이번에 표 전체를 다시 확정하지는 않았다.

**별도 발견:** `offline_cities`가 0행이다. 업데이트 손실이 아니라 1.1.4가 행을 쓰지 않은 것으로 Main이 판단했다(원인 미확인, `download.ts`의 등록 트랜잭션 확인 필요). 1.1.4의 기존 문제 후보이며 어느 Ticket에서 다룰지는 정하지 않았다.

**완료 조건 대비:** 네 판정과 기기·빌드 ID·비교 값, 03·04 결정, 테스트 도구 판단과 근거, 검증용 앱이 main 밖에 있음은 충족한다. "03·04·05의 목표 버전 표 확정"은 위 범위까지만 했다. 

**판정 뒤 기기 상태:** Noline Dev 자리에 판정용 앱(빌드 91)이 있고 비행기 모드가 켜져 있다. 미전송 경비는 DB에 남아 있다. 원래 앱으로 되돌리려면 1.1.4 preview(`30c46ce2`)를 다시 설치해야 하고, 그때 온라인이면 미전송 경비가 서버로 간다. DeviceKit 제어 서버는 이 세션의 백그라운드 작업으로 실행 중이다. 둘 다 어떻게 할지는 정하지 않았다.
