# 2026-11-17 — Ticket 5개로 재구성하고 지도 데이터 대응을 정했다

원문 줄 번호는 Main 대화 `cf346e87-7dfb-4441-ae53-cf37d3cefece`(JSONL 로그) 기준이다. 이 기록은 4개 구성이 5개로 바뀐 이유, 지도 문제의 설명과 대응 결정, 최종 구성의 보완을 남긴다. 확정한 Ticket은 [Ticket 색인](../current/memory/tickets/index.md)에 있다.

## 4개 구성을 다시 판단한 계기

Main은 라이브러리 점검 결과를 보고하면서(602행) Ticket 02에서 오프라인 지도와 DB 위치를 실기기로 먼저 확인하자고 했다. 이어 "그래 좋아"로 4개 구성을 확정받았다고 적었다. 사용자는 이렇게 답했다(640행).

> "그래 좋아는 이전 메시지 고 그럼 이전에 분석으로 티켓을 좀 변경해야하지 않을까? 다시 판단해봐"

"그래 좋아"는 점검 전 메시지(434행의 2회 출시·4개 구성)에 대한 답이었고, 점검 결과를 반영해 구성을 다시 보라는 뜻이다. 출시 2번은 이후에도 바뀌지 않았다.

## 4개 구성의 문제 세 가지 (669행)

1. **가장 큰 위험을 너무 늦게 확인한다.** New Architecture 단계에서 Mapbox 엔진이 v10에서 v11로 바뀌고 RN 0.88에서는 v11밖에 쓸 수 없다. 받아 둔 오프라인 지도가 남는지 공식 근거가 없는데, 4개 구성에서는 이 사실이 Ticket 03 한가운데에서야 드러난다. 지도가 사라진다면 1.2.0 범위 자체가 바뀐다.
2. **Ticket 03이 너무 크다.** SDK 54, React 19, 기기 DB, New Architecture, reanimated 4, Mapbox v11, 출시가 한 Ticket에 있어 완료를 판단할 근거가 하나로 모이지 않는다.
3. **테스트 도구를 바꾸는 시점이 위험하다.** SDK 58 단계에서 RNTL 14(테스트 78개)를 앱 플랫폼과 같이 바꾸면, 테스트가 실패했을 때 앱이 깨진 것인지 테스트 API가 바뀐 것인지 구별할 수 없다.

Main은 Expo 업그레이드 안내를 다시 읽어 SDK를 한 단계씩 올리라는 권장을 확인했다(650–653행).

> "We recommend upgrading SDK versions incrementally, one at a time." — [Expo SDK 업그레이드 안내](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/), 2026-11-17 확인

그래서 54에서 58로 건너뛰지 않고 Ticket 안에서 한 버전씩 올리기로 했다. 중간 버전은 로컬 빌드로 확인하고 EAS preview 빌드는 Ticket 끝에만 돌려 빌드 횟수를 아낀다. 이전 기록에서 미확인으로 남겼던 "SDK 55–57 건너뛰기"는 이것으로 해소됐다.

**5개 구성으로 바뀐 점.** 02는 문서 조사에서 실제 빌드로 하는 데이터 보존 확인이 됐다. 기존 03은 03(SDK 54, Legacy, 출시 안 함)과 04(New Architecture와 1.2.0)로 나뉘었다. 테스트 도구는 앱이 안정된 1.2.0 관찰 기간으로 옮겼다. 이미 어긋난 정리(tailwind-merge 2.6, ui peer 전환, 안 쓰는 패키지 삭제)는 03에 넣었다. 597·632행의 질문은 이것으로 답이 났다.

## 지도 문제 (695행)

사용자가 "지도문제가 뭔지 다시 설명해줘봐"라고 물었다(674행). Main의 설명 요지다.

- **구조:** 앱의 오프라인 지도는 JS 라이브러리 `@rnmapbox/maps`와 그 아래 Mapbox 네이티브 엔진 두 층이다. `offlineManager.createPack`을 부르면 엔진이 자기 방식으로 기기에 pack을 저장한다. 앱은 파일을 직접 다루지 않고 `getPacks`·`deletePack`만 요청한다.
- **v11을 피할 수 없는 이유:** 2025-11에 rnmapbox 10.2.6과 New Architecture로 올렸다가 문제가 나 10.1.33과 Legacy로 되돌렸다(`7ed7ac54`, 커밋에는 "버전과 최신 아키텍처 문제"만 있고 오류 내용은 없다). rnmapbox 10.2부터 기본 엔진이 v11이고 10.3.0에서 v10과 Legacy가 빠졌다. SDK 55부터 New Architecture가 필수이고 RN 0.88에는 rnmapbox 10.3.10 이상이 필요하다.
- **걱정 1, 다시 깨지는가:** 2025-11에 깨진 조합으로 다시 간다. rnmapbox가 그 사이 New Architecture와 RN 0.87·0.88 문제를 여러 번 고쳤지만 이 앱에서 되는지는 빌드해 봐야 안다.
- **걱정 2, 받아 둔 지도가 남는가(더 심각):** v10으로 받은 pack을 v11이 읽는지 공식 문서에 없다. 앱은 지도 보유를 자기 DB에 `mapDownloaded=true`로 따로 기록하고, 화면의 "준비됨" 배지는 실제 pack이 아니라 이 값만 본다([Project 지도 기준](../../../../project/guidance/offline-maps-and-routes/INDEX.md)). 엔진이 바뀌며 pack만 사라지면 앱은 "오프라인 준비됨"을 보여 주고, 사용자는 해외에서 비행기 모드로 빈 지도를 보게 된다. 오류 없이 오프라인 약속이 깨진다.

## 사용자의 지도 대응안과 다듬은 결과

사용자 원문(700행):

> "그럼 v11을 피할수 없는건 해봐야 알고 시도해봐야지 그때는 앱 개발이 급해서 그랫던거고
> 그럼 데이터 문제인데 이전 v10에서 받은 데이터가 어떻게 나오는지 확인하고 잘되면 냅두고 안된다면 새 데이터부터 뭔가 구별할 값을 넣어서 그걸 가지고 구분하는거지 이전 데이터는 안내를 해서 못한다 하고 싶으면 나중에 다시 활성화 해라 이런식으로 어때?"

Main은 방향에 동의하고 두 가지를 정확히 했다(719행). 2025-11 실패는 원인이 기록되지 않았고 급해서 되돌린 것이니 다시 시도할 만하다. 다만 v11로 가는 것 자체는 정해져 있어서, 해봐야 아는 것은 "v11이 이 앱에서 제대로 도는지"다.

그리고 세 곳을 다듬었다.

1. **"잘된다"의 기준(02에서 판정):** `getPacks`에 지도가 그대로 나온다. 비행기 모드에서 지도가 실제로 그려진다(목록에 있어도 화면이 비면 실패). 옛 파일이 공간을 차지한 채 남지 않는다.
2. **구별 값은 지도 엔진 버전(안 될 때만 04에서):** 새로 받는 도시 지도 기록에 `mapEngine: v11` 같은 값을 남긴다. 다음에 엔진이 또 바뀌어도 같은 방식으로 구별할 수 있다. 업데이트 뒤 첫 실행에 한 번, 이 값이 없는 옛 기록의 `mapDownloaded`를 내리고 "지도 다시 받기 필요" 상태로 바꾼다. 이 정리가 없으면 "준비됨인데 빈 지도" 문제가 그대로 남는다. 같은 과정에서 옛 파일도 지운다. v11이 옛 파일을 아예 못 보면 지울 수 없을 수 있어 이것도 02에서 확인한다. DB 구조를 바꾸는 일이라 OTA로는 못 내지만 1.2.0은 스토어 출시라 괜찮다.
3. **안내는 "다시 활성화"가 아니라 "지도만 다시 받기":** 비활성화는 기기 사본 정리와 미전송 변경 보호 규칙까지 건드려 지도 하나 때문에 여행 데이터 전체를 움직인다. 지도 다운로드 재시도 경로가 이미 있다(`apps/client/src/shared/services/offline-map/download.ts`). 활성 여행은 그 자리에서 지도만 다시 받고, 비활성 여행은 다음 활성화 때 새로 받는다고 안내한다.

**안내 시점:** 앱스토어 자동 업데이트는 숙소 와이파이에서도 일어나므로, 업데이트 뒤 첫 실행에 바로 알려 온라인일 때 다시 받게 한다. 출시 노트에도 적는다.

**DB는 다르다.** 기기 DB(expo-sqlite)도 같은 방법으로 확인하지만 여행 데이터 자체라서 "안 되면 안내"로 넘길 수 없다. 반드시 보존되는 방법을 찾아야 한다.

지도가 그대로 읽히면 대응은 필요 없다. 그때 엔진 버전 표시만 남겨 다음을 대비할지는 04에서 정한다.

## 최종 구성과 보완 (737행)

사용자가 "이러면 되겠어 티켓구성?"이라고 묻자(724행) Main은 구성을 Spec 완료 기준과 하나씩 대조해 빠진 기준이 없다고 답하고 보완 세 가지를 더했다.

1. **출시마다 release 브랜치를 새로 만든다.** `release/1.1`만 있으면 1.2.0을 낸 뒤 main에서 05(SDK 55–57)를 진행하는 동안 1.2.0 버그를 고칠 곳이 없다. 1.2.0을 낼 때 `release/1.2`를 만든다.
2. **02의 멈춤 조건:** 기기 DB가 업데이트 뒤 그대로 열리지 않으면 03으로 가지 않고 보존 방법부터 다시 설계한다.
3. **04는 인증서 갱신 뒤:** 멤버십 갱신(2026-12-18)과 인증서 만료(2026-12-30)가 04의 스토어 빌드보다 먼저다. Ticket이 아니라 선행 조건이며 멤버십 갱신은 사용자가 직접 한다.

**Spec 완료 기준을 맡는 Ticket(737행의 대조):** Apple 요건·iOS 27 시작은 05. 기존 사용자 업데이트는 02에서 먼저, 04·05에서 실제 출시 빌드로 다시. 오프라인 약속은 모든 Ticket의 실기기 점검표. 위험 영역은 02에서 확인 방법을 정하고 03–05에서 확인. 의존성 정합과 React·RN 중복 없음은 03·05. OTA는 04·05(SDK 58의 fingerprint 기본 방식 변경은 05). 검사 기준선과 Node 일원화는 01. 재발 방지는 03(`expo install --check`, `engines`)과 05(Project 반영).

**그 밖에:** 05가 가장 무거우므로 Ticket 안에 단계별 체크포인트를 둔다. 테스트 도구 선이전은 RNTL 14가 SDK 54의 jest-expo와 함께 동작해야 가능하며 02에서 확인하고, 안 되면 05의 SDK 58 단계로 돌린다.

**일정:** 11월에 01·02, 12월에 03, 인증서 갱신 뒤 1월에 04(1.2.0), 2월에 05, 3월 초에 1.3.0.

사용자는 "확정·작성 진행"을 골랐다(742행). 위 구성·보완·지도 대응 방향·일정을 채택으로 본다.

## preview 앱으로 하는 업데이트 확인의 범위

Main은 기존 사용자 업데이트를 운영 앱 대신 preview 앱(`com.noline.dev`)으로 확인하는 것을 기본값으로 두었고, 635행에서 아직 확인받지 못했다고 밝혔다. 그 뒤 확정한 02의 방법은 1.1.4 preview를 설치하고 같은 번들 ID의 검증용 앱을 덮어 설치하는 것이다(669·695·737행). 그래서 **02의 검증을 preview 번들 ID로 하는 것은 채택됐다.** 반면 04·05는 737행에서 "실제 출시 빌드로 다시 확인"이라고만 했고 어느 앱에서 할지는 말하지 않았다. 04·05의 업데이트 확인을 preview 앱으로 할지는 아직 Main 기본값이며 Ticket을 시작할 때 정한다.
