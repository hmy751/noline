## Project 출시 기준 반영 (8074–8241행)

[직전 기록](2026-11-20-01-ticket04-main-merge-and-push.md)은 Project 출시 기준의 "지금은 SDK 51이라 `eas fingerprint:compare`를 쓸 수 없다"가 낡았다는 점을 반영 필요로 Main에게 넘기며 끝났다. Main은 병합 보고(8074행)에서 그 문장과 함께 "1.1.x용 OTA는 release 브랜치에서 낸다"는 안내가 출시 기준에 없다고 알렸다. 사용자의 "012만 커밋"(8085행)으로 직전 기록 8개 파일만 `a44f1993`으로 커밋했고, 사용자의 "고쳐줘"(8101행)로 Main이 context-update로 [출시 기준](../../../../project/guidance/app-release-and-ota.md)을 고쳤다.
- 새 절 [이미 낸 버전의 수정은 release 브랜치에서 낸다](../../../../project/guidance/app-release-and-ota.md#이미-낸-버전의-수정은-release-브랜치에서-낸다): runtime이 바뀐 main에서는 스토어 빌드 사용자에게 OTA를 낼 수 없으므로 스토어에 낸 버전마다 `release/<주.부>`를 만들고, 1.1.x OTA는 `release/1.1` worktree(Node 20.18.1, env 파일 3개)에서 낸다. production 채널에 1.2.0 빌드가 생기면 `release/1.1` 발행도 거부되고, preview 채널도 최신 빌드 하나만 기준이다. release 브랜치의 수정을 main으로 옮기는 방법은 정하지 않았다고 적었다.
- 고친 낡은 문장: `fingerprint:compare` 제한은 SDK 54로 풀렸을 것으로 보되 써 보지 않았다는 점, SDK 54에서 runtime 대조가 맞는지는 1.2.0 첫 빌드와 발행에서 확인한다는 점, preview 최신 빌드가 `f8e97f99`라 main도 preview 시험 전에 새 빌드가 필요하다는 점, production dry-run은 `release/1.1`에서 통과하고 main에서는 거부된다는 점.
- 사용자의 "커밋"(8224행)으로 이 문서만 `69bfa8eb`로 커밋했다. `a44f1993`·`69bfa8eb`는 push하지 않아 main이 origin보다 2커밋 앞서 있다(Main 안내: push하면 문서만이어도 Render가 재배포하므로 다음 서버 변경과 함께 올려도 된다). 이 기록 시점에도 push하지 않았다.

## iPad 시험 데이터 준비 (8341–8752행)

- **제어 서버:** iPad Air 4(iPadOS 26.6.2)가 USB로 연결돼 있어(`devicectl` available, iPhone은 unavailable) DeviceKit iPad용 제어 서버를 이 세션의 백그라운드 작업으로 다시 띄웠고("Server is ready", 8413행), `mobilecli`로 앱 실행·탭·입력·스크린샷을 했다. 반복 조작용 셸 스크립트(`m.sh`, `t.sh`)는 세션 scratchpad에 있다.
- **진입 경로를 코드에서 먼저 찾음(8381–8411행):** `OfflineMapView`는 `PolicyBasedMapView`가 정책의 지도 제공자가 Mapbox일 때, 곧 오프라인 활성 여행에서 장소 결과가 있을 때만 그린다. 오프라인에서는 장소 검색이 꺼지므로 Main은 온라인에서 검색해 결과를 띄워 둔 뒤 비행기 모드로 바꾸는 경로를 잡았다. 첫 일정에 좌표가 없는 날은 일정이 없던 2/2에 일정을 만들어 재현하기로 했다.
- **시험 일정 2개(계정의 도쿄 여행 2/2):** 09:00 "T04 nocoord"(장소 직접 입력 "T04 manual place", 좌표 없음), 10:00 Shibuya Station(검색으로 선택, 좌표 있음). 홈 카드의 일정이 5개가 됐다.
- **중간에 생긴 일:** Control Center가 열려 빈 곳을 눌러 닫았다. iPad 설정 앱이 열린 것을 Main이 보고 아무것도 누르지 않고 Noline으로 돌아왔는데(8564행), 사용자가 "내가 잠깐 열었어 계속 진행해"(8579행)라고 했다. Main의 조작이 아니었다.
- **오프라인 활성화:** 도쿄 여행을 오프라인 준비해 "준비 완료"가 됐고 프로필에 오프라인 지도 196.3 MB가 나왔다(8752행). Main은 저장 데이터를 272 KB로 봤다고 기록 담당자에게 전했다(원문 텍스트에는 없고 스크린샷 관찰).
- 이어 일정 추가 화면에서 온라인으로 "Tokyo Tower"를 검색해 결과를 Google 지도에 띄운 뒤, 비행기 모드는 사용자가 직접 켜야 해서 멈췄다(8779–8782행).

사용자가 비행기 모드를 "켰어"(8787행).

## 1.1.4 출시 확인과 Ticket 01 점검표 (9118–9135행)

Main이 공개 App Store 조회(`itunes.apple.com/lookup?bundleId=com.ham.noline&country=kr`)로 현재 버전 1.1.4, `currentVersionReleaseDate` 2026-11-17T22:22:51Z(KST 2026-11-18 07:22), 릴리스 노트("업데이트 방식을 개선")를 확인했다(9120행). 1.1.4는 심사를 통과해 출시됐다. Ticket 01과 012 state가 기다리던 "1.1.4 심사 결과"는 끝났다.

점검표 6항목은 실행하지 않았다. iPhone이 연결돼 있지 않고 로그인은 사용자가 직접 해야 해서다(9135행 근처 Main 판단). Main은 기록 담당자에게 다음 판단을 전했다(원문의 사용자 대상 메시지에는 아직 나오지 않음). 1.1.4의 오프라인 시작·활성 여행 조회·변경·동기화·오프라인 지도·경로는 Ticket 03·04에서 iPad에 1.1.4 preview를 깔고 만든 기준선에 근거가 있고, 점검표에서 남는 고유 항목은 운영 앱의 Google·Apple 로그인과 iPhone(iOS 27)에서의 1.1.4 동작이라는 것이다. 그 iPad 근거를 점검표로 인정할지는 사용자가 정한다. 그 기준선은 preview 앱(`com.noline.dev`)·iPad 한 대·iPadOS 26이라는 한계가 있다.

## main용 preview 빌드를 12월로 미룬 판단 (8782행)

Main은 이번 달 EAS 빌드가 이미 16건이고 월 한도가 15회(사용자가 앞서 알려 준 수치)이며, main용 preview 빌드가 1.2.0 전까지 꼭 필요하지 않아 12월에 하는 쪽으로 본다고 알렸다. 사용자는 이 문장에 따로 답하지 않고 "켰어"로 진행했다. 빌드 건수는 Main의 말이며 기록 담당자가 EAS에서 다시 세지 않았다. 이 빌드가 없으면 main(New Architecture)에서 preview OTA 시험을 할 수 없다는 점은 출시 기준과 Ticket 04에 있는 그대로다.

## 브랜치·worktree 정리 (9136–9159행)

정리 전 Main이 확인한 것: worktree `012-sdk54`(`35b21093`)·`012-newarch`(`c5fdbbdc`)에 미커밋 변경이 없었고, 두 worktree의 env 파일(server `.env.development`, client `.env.production`·`.env.development.local`·`.env.development`)은 main 작업 트리의 같은 파일과 `cmp`로 같았으며, ipa 같은 빌드 산출물은 없었다(크기 1.5 GB, 1.9 GB). `git branch --merged main`에 `feat/012-sdk54`, `feat/012-newarch`, `chore/012-node24`, `docs/012-sdk-upgrade-split`가 있었다.

Main은 `git worktree remove`로 두 worktree를 지우고 `git branch -d`로 네 브랜치를 지웠다(`feat/012-sdk54` 35b21093, `feat/012-newarch` c5fdbbdc, `chore/012-node24` c60224ee, `docs/012-sdk-upgrade-split` 3895d44f). 모두 main에 병합된 브랜치라 커밋은 main 이력에 남는다. 원격에는 이 브랜치들이 없었다.

`release/1.1` 브랜치와 worktree `.claude/worktrees/012-release-1.1`은 1.1.x OTA·핫픽스를 내는 경로라 남겼다(Main 판단, 8782행에서 사용자에게 알림). 사용자의 "쭉 다해줘"가 정리 승인이었고, 남길 것의 선택은 Main이 했다.
