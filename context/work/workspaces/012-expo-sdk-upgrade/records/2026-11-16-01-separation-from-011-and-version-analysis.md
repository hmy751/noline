# 2026-11-16 — 011에서 분리한 이유와 버전 분석

## 쟁점

Work 011(expo-updates)을 재개하던 중 사용자가 SDK·라이브러리 업그레이드를 함께 맡을지 물었다. 과거 사례를 찾아 현황과 비교해 분석해 달라는 요청이었다(원문 213행, [발췌](../source/version-history-evidence.md#2026-11-16-이-work를-만든-대화)). Main은 "앱 버전"을 Expo SDK·React Native·라이브러리 버전으로 이해했고, 그 가정을 답변에 밝혔다.

## 과거 사례에서 본 패턴

커밋 7개와 2026-11-02 세션, Work 007 기록에서 다음 세 가지를 읽었다. 원문은 [버전 이력 발췌](../source/version-history-evidence.md)에 있다.

1. **최신을 받고, 문제가 나면 내렸다.** expo-sqlite 16, expo-asset 12, Mapbox 10.2.6은 모두 SDK 54 세대이거나 New Architecture를 전제한 버전이었다. 빌드 실패나 크래시(expo-asset, 빌드 4)가 나면 SDK 51 버전으로 내렸다. SDK를 올리는 선택지는 쓰지 않았다.
2. **Xcode가 오를 때마다 개별로 땜질했다.** Xcode 27 RC에서 빌드가 깨지자 이미지를 26.2로 고정했다. Sentry 5.24가 Xcode 26.5에서 컴파일되지 않자 6.22로 올렸다. 매번 그 자리에서는 맞는 판단이었지만 SDK 51과의 거리는 계속 벌어졌다.
3. **미룬 결정이 대화에만 남았다.** 2026-11-02 "근본 해법은 Expo SDK를 올리는 것, 이번 배포를 끝낸 뒤 별도 작업으로"라는 추천에 사용자가 "그래 일단 니 추천대로 해봐"로 동의했고, 같은 날 한 번 더 상기됐다. 그러나 Work·Ticket으로 만들지 않아 이후 재개 경로에서 사라졌다. 사용자가 "안한게 꽤 있다"고 한 직접 이유로 보았다. 이 Work를 만든 목적 중 하나가 이 결정을 다시 잃지 않는 것이다.

archive에는 업그레이드 계획이 없었다.

## 현황

`npx expo install --check`의 어긋남 10개를 "일부러 벗어난 것"(Sentry 6.22, react 18.3.1)과 "섞여 들어온 것"(dev-client, splash-screen, safe-area-context, screens, svg, netinfo, @types/react)으로 나눴다. 앞의 것은 이유가 있어 단순히 SDK 51 기대로 되돌리면 다시 깨진다. SDK 51(2024-05)은 최신 SDK 58(2026-10-15, RN 0.88)과 일곱 세대 차이이고, 앱은 Legacy Architecture(`newArchEnabled: false`)다.

## 판단을 바꾼 외부 조건

이 분석 전까지 업그레이드는 "언젠가 할 개선"이었다. 다음 조건을 확인하면서 마감이 있는 일로 바뀌었다.

- Apple은 2027년 4월부터 iOS 27 SDK로 빌드한 앱만 받는다.
- iOS 27 SDK로 빌드하면 UIScene 생명주기가 없는 앱은 시작하지 못한다. SDK 51 / RN 0.74에는 이 구조가 없다. Expo는 SDK 58에서 기본으로, SDK 57은 설정으로 맞춘다.
- SDK 55부터 New Architecture만 쓸 수 있다. Noline은 Mapbox 때문에 이 구조를 끈 이력이 있다.
- SDK 56–58의 최소 iOS는 16.4다. 011이 1.1.4에 넣는 iOS 15.0 설정은 업그레이드 뒤 의미가 없어진다.
- SDK 58은 Node 22.13 이상이 필요하다.

그래서 2027년 4월 이후에는 SDK 51로 새 스토어 빌드를 내기가 사실상 어렵다고 판단했다. 배포 대상 13.4는 고칠 수 있지만 UIScene 전환은 RN 0.74의 네이티브를 직접 패치해야 한다. 이 경로는 시도하지 않았다. 이미 설치된 앱과 OTA는 계속 동작한다고 보았으므로, 막히는 것은 새 스토어 빌드다.

## 011과 합치지 않고 나눈 이유

| 비교 | 011에 합치기 | 012로 나누기(선택) |
| --- | --- | --- |
| 목표·완료 기준 | OTA(작은 일)가 큰 플랫폼 이전과 같은 완료 기준에 묶인다 | 각자 완료 기준을 갖는다 |
| OTA가 나오는 시점 | 업그레이드가 끝날 때까지 늦어진다 | 1.1.4로 먼저 나온다 |
| 업그레이드 릴리스의 안전 | OTA와 업그레이드가 함께 처음 나간다. 업그레이드 버그를 고칠 OTA가 검증되지 않은 상태다 | OTA가 운영에서 검증된 뒤 업그레이드가 나가므로, 업그레이드 버그를 심사 없이 고칠 수 있다 |
| 심사 횟수 | 1번 | 2번 |
| SDK 51에 하는 일 | dev-client를 4.0.x로 내릴 필요가 없다 | dev-client 정렬을 해야 하고, 업그레이드 뒤 OTA를 다시 확인해야 한다 |

나누는 쪽의 비용(심사 2번, OTA 재확인, SDK 51에서의 dev-client 정렬)을 받아들였다. 011의 채널·발행 스크립트·절차는 SDK와 무관하게 이어진다는 점이 비용을 줄인다.

나누는 선택에는 조건이 있다. 011 1단계에서 SDK 51용 expo-updates·dev-client 4.0.29가 Xcode 26에서 빌드되지 않으면(Sentry 선례처럼 오래된 네이티브 코드가 깨질 수 있다), SDK 51에 더 투자하지 않고 OTA를 이 Work에 합치는 쪽으로 다시 판단한다.

사용자는 이 추천에 "그래 분리해서 진행하자 더 버전에 대해 자세한건 012에서 더 논의한다고 기록해주고"라고 답했다(원문 560행). 분리는 채택했고, 아래 버전 상세는 이 Work에서 논의하기로 했다.

## 추천했지만 정하지 않은 것

- **대상 SDK 58:** iOS 27 SDK를 기본으로 맞추고 지원 기간이 가장 길다. 라이브러리 지원을 확인한 뒤 확정한다.
- **단계 51→54→New Architecture→58:** 버전 상향과 아키텍처 전환의 위험을 나눈다. SDK 54는 Xcode 27 빌드 근거가 없어 4월 요건을 혼자 맞추지 못하므로 중간 단계로만 의미가 있다. 중간 단계를 출시할지는 미정이다.
- **일정:** 인증서 갱신(2026-12-30) 뒤, 2027년 3월 심사 제출을 목표로 추천했다.
- **재발 방지:** 설치는 `npx expo install`로 하고, `expo install --check`를 검사에 넣는 방향을 추천했다. 형태는 미정이다.

## 확인 범위와 한계

- Main이 직접 실행한 것: 커밋·브랜치·stash 검색, archive와 Work 문서 검색, 이전 세션 원문 추출, `npx expo install --check`, import 사용처 계산, 웹 문서 확인.
- 외부 자료는 웹 검색 요약과 문서 일부를 읽은 것이다. Apple TN3187 본문 전체와 각 라이브러리의 호환표는 읽지 않았다.
- 빌드·설치는 하지 않았다. 011에서 잠깐 설치한 expo-updates는 되돌렸다(011 기록 참고).
