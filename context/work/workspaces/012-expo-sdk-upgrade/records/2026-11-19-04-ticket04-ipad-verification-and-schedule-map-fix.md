# 2026-11-19 — Ticket 04 iPad 실기기 확인과 거기서 찾은 일정 지도 수정

원문 줄 번호는 Main 대화 `6cf742c7-a162-4a57-981d-2258485e4b19`(JSONL 로그) 기준이며, 사용자의 "usb 연결했어 진행해줘"(6140행)부터 Main의 완료 보고(7671행)까지다. 화면 관찰은 Main이 iPad 스크린샷으로 본 것이고, 스크린샷은 세션 임시 폴더에 있어 사라질 수 있다. 아래는 그 관찰의 의미를 남긴다.

## 무엇을 확인하려 했나

[04 코드 작업 기록](2026-11-19-02-ticket04-newarch-code-and-review.md)까지는 시뮬레이터에서만 봤다. 남은 것은 실기기 비행기 모드의 오프라인 지도와 1.1.4 위 덮어 설치였다. Main은 Ticket 03 때와 같은 순서를 잡았다(6254행). iPad의 SDK 54 시험 앱을 지우고 1.1.4 preview를 새로 깐다. 도쿄 여행을 오프라인 활성화하고 비행기 모드에서 미전송 경비를 만든다. 그 위에 New Architecture 빌드를 덮어 설치해 남은 것을 보고, 비행기 모드에서 지도를 본 뒤 온라인으로 서버 전송을 본다. 도쿄 여행은 온라인 전용이라 서버에 데이터가 있어 앱을 지워도 잃는 것이 없다는 점이 이 순서의 전제였다. 비행기 모드 전환은 사용자가 직접 했다.

## 준비하며 생긴 일

- **제어 서버:** 사용자가 잠금이 "풀려있는데?"(6259행)라고 했는데도 캡처가 비었다. USB를 다시 꽂으며 DeviceKit 제어 서버가 화면 연결을 잃은 것으로 보고 Main이 서버를 껐다 다시 띄웠다(6267·6301행). 지금도 이 세션의 백그라운드 작업으로 실행 중이다.
- **디스크:** 첫 `eas build --local`이 "No space left on device"로 실패했다. 남은 공간이 124 MB였다(6466행). Main은 다시 빌드하면 새로 생기는 Noline의 Xcode DerivedData(`NolineDev-*`, `Noline-*`, `clientDev-*`, 약 37 GB)와 실패한 빌드의 임시 폴더만 지웠다. 다른 프로젝트 캐시와 devicekit 캐시는 남겼고 여유 공간은 39 GB가 됐다(6626·6682행).

## 1.1.4 기준선

1.1.4 preview는 `2814ad7f` ipa를 썼다. Main은 ipa의 프레임워크 구성(옛 빌드에만 있는 `crsqlite.framework` 등)으로 옛 빌드임을 확인했다(6322행). 기기 키체인에 로그인 정보가 남아 있어 다시 로그인하지 않고 열렸다(6325행). 도쿄 여행 오프라인 준비가 "준비 완료"가 됐고, 프로필은 앱 버전 1.1.4, 저장 데이터 208 KB, 오프라인 지도 196.3 MB였다(6413행).

196.3 MB는 iPhone에서 받은 크기와 같다. 그래서 Main은 지도를 끝까지 받은 것으로 봤고, 지난번 iPad의 77.3 MB는 덜 받은 상태였을 수 있다고 추정했다. 1.1.4의 오프라인 일정 지도는 거리 타일, 실선 경로(11.6 km·2시간 21분), 마커 안 번호 "1"이 기준선이다. 비행기 모드에서 경비 "T04 114 offline" JPY 400(쇼핑)을 만들어 합계가 JPY 2812에서 JPY 3212가 됐다(6682행).

## New Architecture 빌드 덮어 설치

`feat/012-newarch`의 `fb73bb25`로 로컬 preview를 만들었다. ipa에 `RCTNewArchEnabled` true가 있고 iPad가 서명 프로필에 들어 있다(6696행). 비행기 모드에서 덮어 설치했지만, Ticket 03 때처럼 첫 실행에 인터넷으로 개발자 서명을 확인해야 해 열리지 않았다. 사용자가 비행기 모드를 잠깐 껐다(6718·6723행).

그래서 "덮어 설치 뒤 미전송 경비가 남았다"는 두 가지로 확인했다. 앱에서 합계 JPY 3212가 그대로인지와, 나중에 서버에도 그 경비가 있는지다. 앱을 열자 로그인 유지, "준비 완료", 일정 3개, JPY 3212.00, 저장 데이터 208 KB, 오프라인 지도 196.3 MB가 덮어 설치 전과 같았다(6765행). Mapbox v10에서 받은 pack을 v11이 그대로 인식한 것이다. 앱 버전 표시는 번호를 올리지 않아 1.1.4로 나온다.

## 비행기 모드와 온라인 확인

- **콜드 스타트:** 비행기 모드에서 처음 앱을 완전히 껐다 켰을 때 프로세스는 떠 있는데 검은 화면이 1분 가까이 이어졌다(6788·6801행). 로그를 받으며 다시 실행하니 두 번 모두 4초 안에 열렸고, 이후 한 번 더 열어 모두 세 번 정상이었다(6829·7054행). 다시 만들지 못했고 원인은 모른다. `devicectl --console`로 띄운 실행은 콘솔을 끊으면 앱도 같이 종료된다(6842행).
- **경비:** 새 빌드에서 비행기 모드로 "T04 newarch offline" JPY 500(숙박)을 추가해 JPY 3712가 됐다. 1.1.4에서 만든 경비는 JPY 400.00으로 표시됐다. Main은 서명 확인 때 온라인으로 열리며 서버를 다녀온 흔적으로 봤다(7054행, 추정).
- **오프라인 지도:** 확대하면 거리·건물·지명과 1.1.4와 같은 실선 경로가 보였다. 다만 iPad의 iPhone 호환 창에서는 mobilecli의 핀치·두 번 탭 확대가 먹지 않았고 카드 넘기기는 됐다(6898행).
- **온라인:** Google 일정 지도에 마커 번호 "1"이 보였다. 내 위치 버튼(reanimated)을 누르면 "권한 필요" 모달이 떴다. 위치 권한을 거절한 상태라 이전과 같은 반응이다.
- **`OfflineMapView`:** 오프라인의 일정 추가 화면에서는 검색이 꺼져 지도가 나오지 않는다. 그래서 `fb73bb25`로 스타일을 고친 이 화면은 실기기에서 보지 못했다.

## 실기기에서 찾은 일정 지도 차이

오프라인 일정 지도(`MapboxScheduleMapView`)가 1.1.4와 두 가지 달랐다(7054행).

- 마커 안의 순서 번호가 그려지지 않고 초록 원만 보였다.
- 1.1.4는 선택한 일정 위치를 확대해 열었다(코드상 zoom 15). 새 빌드는 그날 일정 전체(도쿄 2곳과 오사카 1곳)가 들어가게 약 200 km 축척으로 멀리 축소된 채 열렸다. 카드를 넘기면 그때부터 일정 위치로 이동했다.

## 수정과 독립 검증

**첫 수정(임시 커밋 `ae097b24`, 7269행).** Main이 본 원인은 두 가지다. 기존 `PointAnnotation`은 자식 React 뷰를 한 번 이미지로 찍어 붙이는데 번호가 그려지기 전에 찍혔다. 처음 위치(전체 범위)는 Camera의 일반 prop으로 넘겨 렌더마다 새 값이 되어 다시 보내질 수 있었다. 그래서 마커를 뷰를 그대로 그리는 `MarkerView`로 바꾸고, 처음 위치를 한 번만 쓰는 `defaultSettings`로 넘겨 선택한 일정에서 시작하게 했다. 새 테스트 3개는 예전 코드에서 모두 실패하고 고친 코드에서 통과했다. 이때 전체 Jest 80 suites / 926 tests가 통과했고, 타입 오류는 기존 4건뿐이었으며 lint는 기준선과 같았다.

**독립 검증(7306·7428행).** 코드를 쓰지 않은 검증자가 다음을 짚었다.
- P1은 없었다.
- P2는 첫 수정이 만든 회귀다. 날짜를 바꿨는데 그날 첫 일정에 좌표가 없으면 카메라가 이전 날 위치에 남아, 새 날의 마커가 화면 밖에 있을 수 있었다.
- P3는 예전부터 있던 문제다. 이동 수단 버튼이나 경로 조회 갱신으로 다시 그려지면 사용자가 옮겨 둔 지도가 선택 일정으로 되돌아갔다.
- 주석이 원인을 "New Architecture 때문"으로 단정했다. 1.1.4와 지금 빌드는 아키텍처와 rnmapbox 버전(10.1→10.3)이 함께 바뀌었으므로 단정할 수 없다.

**두 번째 수정(임시 커밋 `b2bfb0cb`).** 카메라 규칙을 `getCameraTarget` 하나로 모았다. 좌표가 있는 선택 일정이면 그 일정 중심 zoom 15, 아니면 그날 좌표가 있는 일정 전체 범위를 보여 준다. 처음 열 때와 날짜·선택이 바뀔 때 모두 이 규칙을 쓰고, 위치 값으로 만든 key가 바뀔 때만 카메라를 옮겨 같은 값의 재렌더는 지도를 건드리지 않는다. 주석은 "New Architecture·rnmapbox 10.3 빌드에서 관찰"로 낮췄다.

**검사.** 새 테스트 파일 `schedule-map-markers-camera.test.tsx`의 5개는 `fb73bb25` 코드에서 모두 실패했다. 첫 수정(`ae097b24`)에서는 재렌더·좌표 없는 날 2개가 실패했고, 지금 코드에서는 모두 통과한다(7405행). 두 번째 수정 뒤에는 `tests/shared/components` 11개 통과, `packages/ui` 밖 타입 오류 없음, 바꾼 파일 lint를 봤다(7386·7391행). 완료 보고(7671행)의 "전체 Jest 926개 통과"는 첫 수정 때 결과였다. 이 기록의 첫 판에서 그 차이를 짚자 Main이 최종 커밋에서 다시 돌렸다(7686–7720행). `129e5321`에서 전체 Jest 80 suites / 928 tests 통과, client typecheck 4(기존 ui 경로)였다. client lint는 12 errors로 기준선 11보다 하나 많았고, 늘어난 하나는 새 테스트 파일의 prettier 형식 오류였다. Main이 그 파일을 prettier로 고친 뒤 lint 11 errors(기준선), `tests/shared/components` 11개 통과를 확인했다. 제품 파일은 prettier가 바꾸지 않았다. 이 테스트들은 컴포넌트가 Mapbox에 넘기는 값을 보며, 실제로 그려진 번호는 실기기로 확인했다.

**커밋.** 임시 커밋 두 개를 `fb73bb25` 위에서 `129e5321` "fix(client): 일정 오프라인 지도의 마커 번호와 처음 위치를 1.1.4와 같게 한다 (Work 012 Ticket 04)"로 합쳤다. Main이 `b2bfb0cb`와 diff해 실기기에서 본 빌드와 내용이 같음을 확인했다(7575–7583행). 위 prettier 수정을 같은 커밋에 넣어 해시가 `c5fdbbdc`로 바뀌었다. 메시지는 같고 바뀐 것은 테스트 파일 형식뿐이며, 제품 코드는 `b2bfb0cb`와 같다(기록 담당자가 `git diff`로 확인). main에는 병합하지 않았다.

## 수정 빌드의 실기기 재확인

- **첫 수정 빌드(7466행):** 비행기 모드 콜드 스타트에서 마커 안에 "1"이 보이고, 선택한 일정(Sakurashinmachi)에서 거리가 보이는 수준으로 열렸다. 카드를 넘기면 선택 마커가 "2"(Tokyo Tower)로 커지고 지도도 이동했다.
- **마지막 빌드(7586행):** 처음 위치와 마커 번호가 정상이었다. 지도를 옮겨 놓고 도보에서 자전거로 바꿔도 위치가 그대로였고, 경로 정보만 12.4 km·47분으로 바뀌었다. 2/2는 일정이 없어 "지도에 표시할 일정이 없어요"가 뜨고, 2/1로 돌아오면 1번 일정 위치에서 열렸다. 이 빌드도 첫 실행에 서명 확인이 필요해 사용자가 비행기 모드를 잠깐 껐다 다시 켰다.
- **실기기로 보지 못한 것:** 첫 일정에 좌표가 없는 날로 바꾸는 경우는 시험 데이터가 없어 테스트로만 확인했다. Android와, 마커가 많을 때 `MarkerView`의 겹침·성능도 보지 않았다.

## 서버 전송과 마친 뒤 상태

온라인에서 오프라인 해제를 했다. 기기 사본과 지도는 지워지고 서버 데이터는 남는다. 서버 기준 합계가 JPY 3712이고 두 시험 경비가 모두 있었다(7591·7671행). 1.1.4에서 미전송으로 만든 경비가 덮어 설치를 거쳐 서버에 간 것이다.

지금 iPad의 도쿄 여행은 온라인 전용이고, Noline Dev 자리에는 `c5fdbbdc`와 제품 코드가 같은 New Architecture 빌드가 있다. 시험 경비 JPY 400·500은 계정의 도쿄 여행에 남아 있다.

## 이 확인이 덮지 않는 것

이번 확인은 preview 로컬 빌드로 iPad 한 대에서 한 것이다. 1.2.0 출시 빌드의 덮어 설치, OTA(받기·기다리지 않는 시작·롤백), iPhone 실기기, Android, Apple 로그인은 남아 있다. 1.2.0 스토어 빌드·제출은 멤버십(2026-12-18)·인증서(2026-12-30) 갱신 뒤다.
