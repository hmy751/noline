# 2026-11-17 — Ticket 구성 초안과 출시·브랜치·최소 iOS·기기 결정

## 쟁점

사용자가 서버 Node 포함을 반영하라고 하면서 이렇게 덧붙였다(원문 212행).

> "이게 버전 의존성 문제 때문에 앱이 깨지고 그래서 확인하고 되게 중요한 작업인데 이런 안정성과 순서를 고려해서 티켓 구성도 논의해보자"

Main은 Ticket 구성안 8개와 모든 Ticket에 적용할 공통 규칙을 냈다(283행). 사용자가 "더 구체화 하거나 나한테 질문할거 있어?"라고 묻자(333행), Main은 자신이 정할 수 없는 네 가지를 물었고(343행) 사용자가 답했다(344행). 원문은 Main 대화 `cf346e87-7dfb-4441-ae53-cf37d3cefece`(JSONL 로그)의 줄 번호다.

## 구성안의 바탕이 된 사실

Main이 저장소에서 확인한 것이다.

- `apps/client/ios`·`android`는 gitignore 대상이라 빌드마다 새로 생성된다. 네이티브 코드를 직접 병합하는 부담은 없다. 대신 config plugin과 `expo-dev-menu` patch가 깨질 수 있다.
- 테스트 파일은 client 78개, server 19개다. 자동으로 돌리는 CI는 없어서 단계마다 직접 돌리고 결과를 남겨야 한다.
- 사용자 데이터가 기기에 있다. 가장 위험한 실패는 화면 오류가 아니라 업데이트 뒤 기기 DB나 아직 보내지 않은 변경을 잃는 것이다.

## 공통 규칙 초안 (Main 제안, 확정 전)

1. 한 단계에서 하나만 바꾼다. Node, SDK 버전, New Architecture, iOS 27 SDK를 따로 바꿔 깨졌을 때 원인을 바로 좁힌다.
2. 매 단계 같은 확인을 한다. 자동 검사는 기준선 대비 lint·test·typecheck다. 실기기 점검표는 오프라인 시작, 활성 여행 조회·변경, 동기화, Google·Apple 로그인, 오프라인 지도, 경로 표시다.
3. 패키지는 `npx expo install`로만 넣는다. 각 SDK 단계는 `expo install --check`를 통과하거나 차이마다 이유를 남겨야 끝난다.
4. 스토어에 내는 단계마다 기존 사용자 업데이트를 확인한다. 이전 빌드에 데이터를 넣은 기기에 새 빌드를 설치한다.
5. 1.1.x 핫픽스 경로를 살려 둔다. 업그레이드가 출시되기 전까지 SDK 51 상태로 1.1.4 사용자에게 OTA와 빌드를 낼 수 있어야 한다.

다른 선택지는 "54+New Arch 한 번에"(심사 2번), "최종만 출시"(심사 1번, 바뀐 범위가 커짐), "긴 업그레이드 브랜치"(중간 출시를 안 할 때 맞음), "통계 먼저 확인"이었다.

중간 출시 선택지의 문구가 "54 출시 → New Arch 출시 → 58 출시"를 명시하므로, 대상 SDK 58과 51→54→New Architecture→58 단계도 이 선택으로 채택된 것으로 기록 담당자가 해석했다. 목표 Node 24와 Node 순서는 이 질문에 들어 있지 않아 여전히 추천이다.

**테스트 기기 해석.** 사용자는 다중 선택에서 "iPhone 14 Pro"와 "시뮬레이터만 추가"를 고르고, 기타 입력에 "27.2.1"을 적었다. "iOS 27 기기 있음"은 고르지 않았다. Main은 이를 iOS 27.2.1이 설치된 iPhone 14 Pro 실기기 1대와 나머지는 시뮬레이터로 해석했다. iPhone 14 Pro의 iOS 버전을 기타에 적어 달라는 선택지 설명에 맞는 해석이지만, 사용자가 문장으로 확인한 것은 아니다.

이 해석대로라면 두 가지가 실기기로 확인 가능해진다.
- 업그레이드한 빌드가 iOS 27에서 시작하는지([완료 판단](../current/memory/spec/04-quality-and-completion.md) 2번)
- 이미 설치된 SDK 51 빌드가 iOS 27 기기에서 그대로 동작하는지(지금까지 Apple 문서 해석으로만 둔 가정)

둘 다 아직 확인하지 않았다. 구형·iOS 16대 기기는 없으므로 최소 iOS 근처는 시뮬레이터로 본다.
