# 2026-11-22 — OTA 발행 점검이 로컬 빌드와 예전 버전 빌드를 다루게 고쳤다

원문 줄 번호는 Main 대화 `6cf742c7-a162-4a57-981d-2258485e4b19`(JSONL 로그) 기준이다. 이번 구간은 사용자의 "1.2.0을 OTA 대상으로 만드는 방법 정하기 이건 뭐야"(10541행)부터 Main이 이 기록을 맡긴 지점(11653행)까지이고, 후속 호출로 세 브랜치 push와 사용자의 기록 마무리 질문(11870행)까지 더했다. 그 사이 10583–10632행(빌드 20 Apple 로그인 확인)은 이미 `f7a0a80f`로 기록돼 다시 다루지 않았다. 직전 기록이 반영하지 않은 2026-11-20 push(10433–10536행)를 앞선 맥락으로 함께 읽어 맨 끝에 보완했다. 독립 검증자의 보고 세 번(11288·11460·11577행)은 원문을 읽었다. 결과 커밋은 `git log`·`git show`로, 현재 기준은 Project [출시 기준](../../../../project/guidance/app-release-and-ota.md)(`e8e53692`)으로 대조했다.

스크립트의 현재 동작(받을 빌드 목록, 등록 규칙, `--older-build`, release 브랜치 경로)은 Project 출시 기준의 [발행 절차](../../../../project/guidance/app-release-and-ota.md#ota는-발행-스크립트로만-낸다)와 [release 브랜치 절](../../../../project/guidance/app-release-and-ota.md#이미-낸-버전의-수정은-release-브랜치에서-낸다)이 소유한다. 이 기록은 그 결론에 이른 질문·선택·검증 과정과, Work 012에 남은 것을 맡는다.

## 질문에서 "스크립트를 고친다"는 결정까지

**처음 질문과 설명(10541–10669행).** Main이 남은 일로 적은 "1.2.0을 OTA 대상으로 만드는 방법 정하기"를 사용자가 "이건 뭐야"라고 물었다. Main은 발행 스크립트(`apps/client/scripts/ota/checks.mjs`)를 읽고 이렇게 설명했다. OTA는 채널과 runtime이 같은 앱에 가므로 로컬 빌드여도 Expo 쪽에서는 전달된다. 막는 것은 우리 발행 스크립트다. 스크립트는 EAS 빌드 목록에서 채널의 최신 빌드를 골라 지금 코드의 runtime과 같아야 발행하는데, 1.2.0은 `--local`로 만들어 그 목록에 없다. 그래서 스크립트는 여전히 1.1.4(`0367b72f…`)를 최신으로 보고 1.2.0 코드의 발행을 거부한다. 바뀐 파일 검사도 1.1.4 커밋을 기준으로 하게 된다. 1.2.0이 나간 뒤 OTA로 급히 고칠 일이 생길 때만 문제가 되고, 그 전에는 영향이 없다고 했다.

이때 Main이 낸 선택지는 셋이었다.
1. 스크립트에 대상 빌드(runtime `c4fc18bb…`, 커밋 `92c1766c`)를 직접 넘기는 옵션을 넣는다. 사람이 넘긴 값이 맞는지는 우리가 책임진다.
2. 12-01 EAS 횟수가 다시 생기면 같은 커밋을 클라우드로 빌드만 하고 제출하지 않는다. runtime이 같을 것으로 예상하지만 확인이 필요하다.
3. 스크립트를 건너뛰고 `eas update`를 직접 실행한다. 안전 점검이 빠지므로 권하지 않았다.

Main의 추천은 "로컬 빌드가 잦으면 1, 이번 한 번뿐이면 2"였다. 사용자가 "내가 OTA도 잘 몰라서 자세히 설명해줘봐"(10637행), "아직 이해가 안가는데?"(10685행)라고 해 Main은 두 층(네이티브·JS 번들), 채널·runtime, 스크립트의 다섯 단계를 설명하고, 다시 "EAS 장부에는 클라우드에서 만든 앱만 적힌다"는 비유로 줄여 설명했다(10669·10704행).

**사용자의 판단(10716행).**

> 근데 보면 이건 계속 일어날 수 있는 상황이니까 맞게 스크립트를 고쳐야 하는 당연한 사항 아니야? 맞다면 어덯게 할지 고민해봐 어떨때는 로컬로 빌드 할수도 잇고 하는 상황인거잖아 결국?

사용자는 로컬 빌드를 일회성 예외가 아니라 반복될 조건으로 봤고, 그래서 1회성 우회(12월 클라우드 빌드)가 아니라 스크립트가 그 조건을 다루는 것이 맞다고 했다. Main도 "이번 한 번만 넘길 문제가 아닙니다"라고 동의했다.

**Main의 설계안(10730–10777행).** 스크립트를 다시 읽고 문제의 뿌리를 둘로 정리했다.
- 로컬 빌드가 EAS 장부에 적히지 않는다.
- 스크립트가 채널의 최신 빌드 하나만 대상으로 삼는다. 그래서 1.2.0을 어떤 방식으로든 장부에 올리면 `release/1.1`에서 1.1.4 사용자에게 보내는 OTA가 거부된다. Main은 지금 1.1.4에 OTA를 보낼 수 있는 것이 "1.2.0이 장부에 없어서 생긴 우연"이라고 했다. 출시 기준에도 이미 적힌 한계였다.

그래서 세 가지를 제안했다.
1. 저장소에 로컬 빌드 장부를 두고, 로컬 빌드 뒤 `pnpm ota:register-local-build <ipa>`로 ipa에서 버전·빌드 번호·runtime·채널을 읽어 적는다. 지금 코드의 runtime과 같을 때만 적고, git에 커밋되므로 다른 기기·세션에서도 보인다.
2. 발행 점검은 EAS 목록과 로컬 장부를 합쳐서 본다.
3. 최신 빌드 하나가 아니라 지금 코드와 runtime이 같은 빌드를 대상으로 고르고, 그 빌드가 최신이 아니면 `--older-build` 같은 확인 플래그를 요구한다. 3을 하지 않으면 1로 1.2.0을 등록하는 순간 `release/1.1` 경로가 막히므로 함께 고치길 권했다.

고려했지만 고르지 않은 것은 `eas upload`(로컬 빌드를 EAS에 올리는 명령)다. 올린 빌드에 채널·커밋이 남는지 모르고, 시험하면 계정에 기록이 남으며, 된다고 해도 3의 문제는 그대로라는 이유였다. 처음 선택지 1(발행할 때마다 대상 값을 손으로 넘김)은 이 설계에서 "한 번 등록해 커밋하는 장부"로 바뀌었다.

**선택(10783행).** 사용자는 "3번까지 고쳐줘"를 골랐다(Main이 붙인 버튼 문구). 여기서 "3번"은 설계안의 세 번째 항목(runtime으로 대상을 고르고 예전 버전에는 `--older-build`)이다. 처음 선택지의 3번(`eas update` 직접 실행)이 아니다. 다른 버튼은 "로컬 빌드만"(1·2만)이었다.

## 구현과 첫 확인

**runtime에 영향이 없는지 먼저 봤다(10805–10848행).** fingerprint source 목록과 ipa를 대조해, 장부를 `apps/client/scripts/ota/` 안에 둬도 runtime이 바뀌지 않는다고 판단했다. 그 뒤 main의 runtime은 계속 `c4fc18bb…`였다. 빌드 20 ipa의 `EXUpdates.bundle/fingerprint`도 `c4fc18bb…`, `Expo.plist`의 채널은 `production`이었다.

**`e7d94641`**("feat(client): OTA 발행 점검이 로컬 빌드와 예전 버전 빌드를 다루게 한다", 10882–10952행). `builds.mjs`(EAS 목록과 장부를 합친 목록, main·`release/*`의 로컬·origin 장부를 모두 읽음), `register-local-build.mjs`(등록 명령), `checks.mjs`의 대상 선택, `publish.mjs`의 `--older-build`, 루트 `package.json`의 `ota:register-local-build`가 들어갔다. 장부를 모든 release 브랜치에서 읽는 이유는 어느 브랜치에서 발행해도 다른 브랜치에서 등록한 더 새 버전을 알아야 "예전 버전" 판단이 맞기 때문이다.

**`47704e25`**(10959–10975행). 빌드 20을 `--commit 92c1766c`로 등록했다. 장부 기록은 `com.ham.noline` 1.2.0(20), production, runtime `c4fc18bb…`, 커밋 `92c1766c`다. main에서 `pnpm ota:publish production --dry-run --skip-install`이 "업데이트를 받을 빌드: 로컬 빌드 (1.2.0 / 20)", "OTA를 막는 변경 없음 (기준: 빌드 커밋 92c1766c)"으로 통과했다. `30c0ae03`은 dry-run 안내 문구만 다듬었다.

**예전 버전 경로(11053행).** main 코드의 `selectTargetBuilds`에 1.1.4 runtime을 넣어 부르니 플래그 없이는 "1.2.0보다 예전 버전" 이유로 거부, `--older-build`로는 1.1.4(`d160c7b5`) 대상으로 통과했다. 1.2.0 runtime은 1.2.0/20(`92c1766c`)으로 통과, 없는 runtime은 거부했다. 실제 `release/1.1` 코드로 끝까지 통과한 것은 아니다(아래).

## `release/1.1`에서 runtime이 1.1.4와 맞지 않았다

`e7d94641`·`30c0ae03`을 `release/1.1`(worktree `.claude/worktrees/012-release-1.1`)에 옮겨 dry-run하니, 로컬 runtime이 1.1.4의 `0367b72f…`가 아니라 `7192b529e051a0eb780a1caa010466410c890ddb`였다(11024–11031행). 그래서 `--older-build`를 붙여도 "어떤 빌드와도 같지 않습니다"로 멈췄다. 2026-11-18 같은 worktree의 dry-run은 `0367b72f…`로 1.1.4와 맞았다([`release/1.1` 확인 기록](2026-11-18-03-release-1-1-build-and-ota-check.md)).

Main이 확인한 것은 다음과 같다.
- worktree에 설치된 expo는 51.0.39로 브랜치의 SDK 51과 맞다(11039–11047행).
- gitignore 대상인 `apps/client/ios`가 남아 있었다(main 쪽은 `com.ham.noline`, release/1.1 쪽은 11-18에 만든 `com.noline.dev`). 이를 잠시 치우고 계산해도 `7192b529…`였고, 폴더는 되돌렸다(11129–11146행).
- EAS production 환경값은 마지막 변경이 11-17(일부 11-14)이라 11-18 이후 바뀌지 않았다(11154행).
- fingerprint source 중 `node_modules` 밖의 것은 아이콘·`.gitignore`·`eas.json`·autolinking 설정·`expoConfig`·`package:react-native`·`packageJson:scripts`였다(11170행). 11-18의 source 목록은 남아 있지 않아 어느 항목이 달라졌는지는 비교하지 못했다.

Main은 낡은 설치가 runtime을 바꿨을 가능성을 보고, 받을 빌드를 깨끗한 재설치 뒤에 고르도록 순서를 바꿨다(`89184f23` "fix(client): OTA 받을 빌드를 깨끗한 재설치 뒤 runtime으로 고른다", 11101–11121행). 이전 흐름의 4단계 "runtime 재확인"은 대상 선택이 재설치 뒤로 옮겨지며 필요 없어져 지웠다. 비용은 변경 규칙에 걸리는 발행도 재설치 시간만큼 늦게 멈춘다는 것이다(출시 기준에 적힘). 그러나 `release/1.1`에서 깨끗한 재설치를 포함해 다시 돌려도 `7192b529…`였다. 원인은 찾지 못했고, Main은 더 파지 않고 검증으로 넘어갔다.

**기록 담당자가 원문에서 찾은 차이(원인으로 확인하지 않음).** 11-18에는 `.nvmrc`(20.18.1)에 맞춰 Node 20.18.1로 설치했다(11-18 기록, 600–614행). 11-22의 `release/1.1` 명령에는 Node를 바꾸는 단계가 없었고, 같은 worktree에서 실행한 `node`의 오류 출력에 Node.js v24.22.3이 찍혔다(11047행). 깨끗한 재설치(11120행)도 그 셸에서 돌았으므로 지금 worktree의 `node_modules`는 Node 24로 다시 설치된 것으로 보인다. 출시 기준의 release 브랜치 절도 "그 브랜치의 `.nvmrc`에 맞는 Node로 설치"하라고 적고 있다. Node 버전이 fingerprint에 영향을 줬는지는 확인하지 않았다.

**Main이 Node 20으로 다시 확인했다(원인 아님).** 기록 담당자의 보고를 받은 뒤 Main이 `release/1.1` worktree에서 PATH 앞에 Node 20.18.1(nvm 설치본)을 두고 `node -v`가 v20.18.1, `pnpm`·`eas`도 v20.18.1 경로인 것을 확인한 다음, 깨끗한 재설치를 포함해 `pnpm ota:publish production --dry-run --older-build`를 돌렸다. 재설치 뒤 runtime은 여전히 `7192b529…`였고 "어떤 빌드와도 같지 않습니다"로 멈췄다. Node 버전은 원인이 아니다. 지금 그 worktree의 `node_modules`는 Node 20으로 설치된 상태다. 원인은 여전히 모른다.

이 문제는 이번 수정이 만든 것이 아니다. 옛 스크립트도 같은 runtime으로는 1.1.4 대상 발행을 거부한다. 다만 지금 상태로는 `release/1.1`에서 1.1.4 사용자에게 OTA를 낼 수 없다.
