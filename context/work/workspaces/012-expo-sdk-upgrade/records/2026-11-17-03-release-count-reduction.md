# 2026-11-17 — 스토어 출시를 3번에서 2번으로 줄이는 안

[앞 기록](2026-11-17-02-ticket-composition-and-release-decisions.md)에서 사용자는 중간 단계를 각각 출시하기로 골랐다(심사 3번). 이 기록은 그 직후 Main이 낸 7개 구성과 기본값, 사용자가 출시를 줄이라고 한 뒤 나온 2회 출시·Ticket 4개 안을 남긴다. 원문 줄 번호는 Main 대화 `cf346e87-7dfb-4441-ae53-cf37d3cefece`(JSONL 로그) 기준이다.

## Main이 낸 7개 구성과 기본값 (374행)

출시를 각 단계 Ticket에 넣어 8개를 7개로 줄인 구성이다. 04·05·06이 각각 출시를 맡고 버전을 1.2.0·1.3.0·1.4.0으로 붙였다. 앞 기록의 7개 표와 같은 구성이며, 374행에는 다음이 더 있었다.

- 01은 `release/1.1`에서 핫픽스 빌드와 OTA를 낼 수 있는지까지 확인한다. 03은 54에서 58로 바로 갈지, 중간 SDK를 거칠지도 정한다.
- **기존 사용자 업데이트 확인은 preview 앱(`com.noline.dev`)으로 한다.** 실기기가 1대뿐이라 운영 앱 위에서 확인하다 새 빌드가 기기 DB를 깨뜨리면 사용자 본인의 여행 데이터가 사라질 수 있기 때문이다. 이전 preview 빌드에 데이터를 넣고 그 위에 새 preview 빌드를 설치한다. 운영 앱에는 심사를 통과한 빌드만 올린다.
- 최소 iOS 16.4는 Xcode의 iOS 16.4 시뮬레이터로 확인한다.
- Main이 "기본으로 정해 둔 것"으로 밝힌 것: 각 출시 뒤 1주일 동안 Sentry에 새 크래시가 없어야 다음 출시, 버전 번호 1.2.0/1.3.0/1.4.0, ESLint 9는 SDK 58이 요구할 때만. Node 24는 "이의가 없으셨으니 확정으로 보겠습니다"라고 했다. 사용자가 이 말을 따로 확인하지는 않았다.
- 일정 초안: 11월 01–03, 12월 04 개발, 멤버십·인증서 갱신 뒤 1월 초 1.2.0, 1월 말 1.3.0, 2월 말–3월 초 1.4.0.

## 사용자의 반응 (411행)

> "근데 버전은 이미 1.4인가 그럴거고 단계 출시를 7번 승인 신청한다는건가? 더 줄일수 있음 줄이고"

두 가지가 사실과 달랐다. Main이 `apps/client/app.config.js`를 확인한 결과 현재 버전은 1.1.4, 빌드 번호는 18이다(415–416행). 1.4는 374행이 붙인 마지막 출시 번호였다. 7개 구성에서도 심사는 04·05·06의 3번이었다. 사용자는 Ticket 수를 심사 횟수로 읽은 것으로 보인다(Main의 판단).

그래도 지시는 분명하다. 줄일 수 있으면 줄이라는 것이다. 그래서 앞 기록에서 채택으로 적은 "중간 단계 각각 출시(심사 3번)"는 더는 채택 상태가 아니다. `release/1.1`, 최소 iOS 16.4, 대상 SDK 58은 이 발화와 무관하게 그대로다.

## 2회 출시·Ticket 4개 안 (Main 제안, 사용자 확인 전)

이 안은 Main이 기록 담당자에게 보낸 과업(419행)과 사용자에게 보인 확인 질문(431행)에서 확인했다. 431행 시점에 Main의 설명 답변 본문은 로그에 아직 없다.

**원칙: 변경 단계와 출시 횟수를 나눈다.** 개발은 계속 한 번에 하나만 바꾸고 단계마다 preview 빌드로 검증한다. 스토어 출시만 2번으로 줄인다. 안정성의 근거는 출시 횟수가 아니라 단계별 검증에 둔다는 뜻이다.

| 출시 | 내용 | 버전 |
| --- | --- | --- |
| 1 | SDK 54 + New Architecture | 1.2.0 |
| 2 | SDK 58·iOS 27 | 1.3.0 |

서버 Node 배포는 Render로 나가 심사가 없다. 1주일 관찰은 출시 1과 2 사이에만 둔다.

| # | 맡는 결과 |
| --- | --- |
| 01 | 준비: 기준선, `release/1.1`, 서버·로컬 Node 24 |
| 02 | 위험 라이브러리 조사·시험 업그레이드 |
| 03 | SDK 54 → New Architecture를 각각 preview로 검증한 뒤 1.2.0 출시. EAS Node 24, `expo install --check` 검사, `engines` 포함 |
| 04 | SDK 58·iOS 27 출시(1.3.0)와 Project 반영 |

**1회 출시(58만 출시)를 버린 이유.** 기기 DB 변경(expo-sqlite 14→16), 구조 전환, iOS 27을 한꺼번에 사용자에게 내보내게 된다. 스토어 빌드는 되돌릴 수 없어서, 문제가 나면 원인을 가르기 어렵고 데이터 손상이 퍼질 수 있다. 431행의 질문은 "2번·4개로 확정"과 "1번 출시로 더 줄이기"를 선택지로 두었다.

**함께 확인 전인 기본값.** preview 앱(`com.noline.dev`)으로 기존 사용자 업데이트 확인, 출시 1 뒤 1주일 동안 Sentry 새 크래시 없음. 둘 다 Main이 정한 기본값이다.

- preview 앱 확인과 1주일 관찰 기본값
- 목표 일정(2회안 기준으로 다시 짜야 한다)
