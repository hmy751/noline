# 012 — SDK 업그레이드를 이어갈 때

2026-11-17 버전 설정을 전수 조사했고, 서버 Node를 범위에 넣었다. 대상 SDK 58, 핫픽스는 `release/1.1`, 최소 iOS 16.4는 정했다. 출시는 2번(1.2.0 = SDK 54 + New Architecture, 1.3.0 = SDK 58·iOS 27)이고, Ticket 5개로 확정해 문서를 만들었다. 구현 전에 기기 DB와 오프라인 지도가 남는지 먼저 판정하고(02, DB가 남지 않으면 멈춤), SDK는 한 버전씩 올린다. 2026-11-18 Ticket 01을 시작해 기준선·`release/1.1`(원격, 빌드·OTA 확인)·Node 24 설정 변경(main 병합·push, Render가 Node 24.16.0으로 배포)·설치 절차(`pnpm exec expo install`)까지 했고, 운영 앱 확인까지 마쳤다. 1.1.4는 2026-11-17 출시됐고(2026-11-20 App Store 조회), 01의 남은 일은 실기기 점검표다. 운영 서버는 `render.yaml`이 아니라 Render 대시보드 설정과 `.nvmrc`로 배포된다. 02 판정도 마쳤다. 기기 DB와 오프라인 지도가 SDK 54·New Architecture·Mapbox v11 앱으로 덮어 설치한 뒤에도 남아, 03을 시작할 수 있고 04의 지도 대응은 빠졌다. 2026-11-18 03을 시작해 SDK 52·53·54를 작업 브랜치 `feat/012-sdk54`(worktree `.claude/worktrees/012-sdk54`)에 커밋했다. 2026-11-19까지 검사 장치·EAS preview·iPad 실기기 확인을 마치고 main에 병합해(`ae97809e`, 2026-11-19 push, Render 재배포 health 200) 03을 끝냈다. 2026-11-19 04(New Architecture와 1.2.0)의 코드 작업을 앞당겨 시작해 작업 브랜치 `feat/012-newarch`(worktree `.claude/worktrees/012-newarch`)에 커밋했다. 같은 날 iPad 실기기에서 1.1.4 위 덮어 설치와 비행기 모드를 확인했고, 거기서 찾은 일정 지도 차이(마커 번호·처음 위치)를 고쳐 `c5fdbbdc`로 커밋했다(함께 찾은 `createPack` 완료 시점 문제는 Work 008로 넘겨 012에서 고치지 않기로 했다). 2026-11-20 사용자의 "병합하고 push"로 `feat/012-newarch`를 main에 병합해(`6d34c44b`) push했다. 같은 날 사용자의 "쭉 다해줘"로 iPad에서 `OfflineMapView` 오프라인 화면과 첫 일정에 좌표가 없는 날을 확인했고, 병합된 012 worktree 2개(`012-sdk54`, `012-newarch`)와 브랜치 4개를 지웠다. 직전에 Project 출시 기준에 release 브랜치 OTA 절을 넣었다(`69bfa8eb`, push 안 함). 이어 사용자가 Render 배포가 "돌고 있고" Ticket 01 점검표를 "인정"한다고 답해 01을 완료로 닫았다(로그인 항목은 11-18 운영 앱 확인으로 채움, Apple 로그인 구별과 iPhone iOS 27은 04로 넘김). 같은 날 사용자가 1.2.0을 왜 멤버십 갱신 뒤에 내야 하는지 물었고, "04는 갱신 뒤"가 1월 일정에서 따라온 순서일 뿐이라는 Main의 답에 "그래 다 진행하자 할거"라고 해, 1.2.0(빌드 19)을 버전 커밋 `3ff9832c`(push 안 함)에서 로컬 production 빌드(EAS 11월 횟수 초과)로 만들어 `eas submit`으로 App Store Connect에 올렸다. 사용자가 TestFlight 빌드 19로 iPhone 로그인을 확인하고 "제출 해줘"라고 맡기면서 Apple 로그인 중 로딩이 Google 버튼에 뜨는 문제를 짚었다. 1.1.4부터 있던 이 버그를 고치고(`378287a6`), 1.2.0이 아직 OTA 대상이 아니라 나중에 OTA로 고칠 수 없다는 Main 판단으로 빌드 번호를 20으로 올려(`92c1766c`, 로컬 `release/1.2`도 이리로 옮김) 빌드 20을 만들어 올렸다. App Store Connect 1.2.0에 사용자가 승인한 출시 노트를 넣고 빌드 20을 연결해 같은 날 오후 7:13 심사에 제출했다(심사 대기 중, 통과하면 자동 출시). 이 과정에서 빌드 번호만 바꿔도 runtime이 바뀐다는 것을 다시 확인해 빌드 19와 20의 runtime이 다르다(Main이 앞서 한 "runtime도 같습니다"는 사용자에게 정정). 같은 날 사용자의 "push해줘"로 main(`8b45fea6`까지)과 `release/1.2`(`92c1766c`)를 push했다. 멤버십은 1.2.0과 별개로 12-18까지 사용자가 갱신한다. 로컬 빌드는 EAS 빌드 목록에 남지 않아 OTA 발행 스크립트가 1.2.0을 몰랐다. 2026-11-22 사용자가 로컬 빌드는 반복될 상황이니 스크립트를 고치는 게 맞다고 해, Main이 발행 점검에 로컬 빌드 장부(`pnpm ota:register-local-build`)와 runtime 기준 대상 선택(예전 버전이면 `--older-build`)을 넣고 빌드 20을 등록했다. 독립 검증 세 번을 거쳐 main·`release/1.1`·`release/1.2`에 커밋했고, 같은 날 사용자의 "push 해줘"로 세 브랜치를 push했다(main `113ff1db`, `release/1.1` `0c6c7855`, `release/1.2` `3aa5f7f0`). main의 production dry-run이 1.2.0(빌드 20)을 받을 빌드로 고르지만 실제 발행은 아직 없다. 같은 과정에서 `release/1.1`의 runtime이 1.1.4와 다르게(`7192b529…`) 계산되는 문제가 드러났고 원인은 모른다. Sentry 소스맵 업로드도 확인하지 못했다. main은 이제 SDK 54·New Architecture라 1.1.4 사용자에게 보낼 OTA·핫픽스는 `release/1.1`에서만 낸다(main push는 OTA 발행이 아니다). 1.2.0/20이 장부에 있어 그 OTA에는 `--older-build`가 필요하고, 지금은 위 runtime 불일치로 막혀 있다. 03에서 넣은 fmt consteval 우회는 New Architecture에서 필요 없어져 지웠다. 버전이 어긋나면 앱이 깨지는 일이라 단계마다 원인을 가르고 확인할 수 있는 순서가 핵심이다. 마감이 있다는 점을 놓치지 않는다.
