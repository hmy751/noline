# 품질과 완료

## 첫 조사에서 확인할 것

자료가 있는 범위를 넓게 살피고 실제 읽은 범위를 드러낸다. 002·004·005·기존 Project·`.claude`의 자료뿐 아니라 루트·앱·패키지의 `CLAUDE.md`, `AGENTS.md`, README 등 분산된 컨텍스트도 함께 검토한다. 각 문서에서 유지·보완·통합·이관할 내용과 연결 관계를 드러내고, 저장소의 다른 문서 후보도 탐색한다. 알려진 몇 가지 결함만 후보로 삼지 않는다. 파일 수나 후보 수가 많다는 사실은 조사 품질을 증명하지 않는다.

주요 후보마다 무엇을 이해하게 만들지, 현재 설명과 어떤 차이가 있는지, 근거와 추가 검증은 무엇인지, 어떤 선택이 필요한지 설명할 수 있어야 한다. 조사로 전체 재구성을 완료했다고 주장하지 않는다.

## 주제별 재구성에서 확인할 것

- 채택한 의미와 현재 구현의 관계를 원자료·코드·후속 결정으로 대조하고 확인 범위와 남은 불확실성을 드러낸다.
- 기존 문서를 새 구조나 형식에 맞췄는지만 확인하지 않는다. 기존 설명 자체가 현재 코드·유효한 계약·사용 목적에 맞는지, 새 구성이 유효한 선택 이유나 받아들인 비용을 약화하지 않았는지 함께 판단한다. 유용한 의미는 복원하되 낡은 전제까지 되살리지 않는다.
- 최종 Project 설명이 목적·이유·관련 책임·조건·예외와 필요한 선택 이유를 충분히 전달한다. 링크 추가나 문장 축약만으로 보완을 끝내지 않는다.
- 현재 가이드·본문·형성 자료만 따라가도 현재 의미를 이해할 수 있고, `.claude/context`, `.claude/decisions` 등의 옛 제품 문서나 그 아카이브로 돌아가는 읽기 연결이 없다.
- 옛 자료가 일반 읽기 경로에서 제외되도록 아카이브로 격리되거나 제거되어 경쟁 정본이나 우회 Owner로 남지 않는다. 물리 위치와 삭제 여부 자체를 완료 조건으로 삼지 않는다.
- 대표 개발 질문으로 Project 진입점과 관련 작업 진입점에서 읽어 실제 판단에 필요한 답을 얻는지 확인한다. 경로 검사, 의미 검토와 옛 문서 의존 제거를 구분한다.

주제별 결과에는 옛 문서의 유효한 의미를 어디에서 설명하는지, 현재 참조를 어디로 전환했는지, 원본을 어떻게 격리하거나 제거했는지를 남긴다. 다른 Ticket에 속한 읽기 의존이 남으면 담당 Ticket과 해소 시점을 명시하고 해당 범위의 이관 완료를 선언하지 않는다. 전체 읽기 점검은 주제별 정리를 대신하지 않으며 마지막에 누락을 확인한다.

## 후속 Ticket의 내용 판단과 리뷰

기존 문서와 새 구성을 모두 검토 대상으로 둔다. 새 형식·파일 배치에 맞는지를 정답으로 삼지 않고, 실제 제품 이해·개발 장면에서 어느 설명의 깊이와 구성이 더 적합한지 비교한다. 기존 방식이 더 잘 전달하던 이유·조건·비용은 유지하거나 복원할 수 있고, 현재 구성이 더 낫다면 줄어든 이해 부담과 새로 생긴 관리 부담을 함께 설명한다. 의미 있는 이득이 없으면 재분할·병합·서식 변경을 하지 않는다.

내용뿐 아니라 문서의 역할에 맞는 구성도 판단한다. 원래의 표·목록·체크리스트·코드 예시가 현재 사용 조건에서 유용하면 그대로 가져올 수 있다. 형식이 다르다는 이유로 바꾸거나 기존에 있었다는 이유만으로 유지하지 않는다. 판단이 필요한 기준은 언제 무엇을 확인·수행하는지 가까이 쓰고, 구조 설명·선택 이유·원문 근거·진행 기록은 각 역할에 맞게 구성한다. Project의 작성 형식을 Work나 역사 자료에 일괄 적용하지 않는다.

변경 문서 전체에서 옮긴 내용과 주변 설명을 함께 살핀다. 어떤 부분은 재구성하고 어떤 부분은 유지할지 이유를 판단하며, 한 체크리스트 삭제나 제목 변경으로 전체 검토를 대신하지 않는다. 재배치 뒤에는 원문의 조건·예외·이유·규칙 강도와 예시의 범위가 남았는지, 새 제목으로 진입하는 링크와 현재 상태가 맞는지 확인한다. 이 판단은 실제 변경의 결과와 함께 남기되 매 문서에 같은 서식·전수 대조표를 만들지는 않는다.

원문을 충실히 옮겼다는 확인과 그 원문 자체가 현재에도 맞는다는 확인을 구별한다. 특히 작업 지시의 API·타입·필드·소비 경로는 실제 코드에서 찾고, 상태·저장·공개·완료를 여러 경계에 걸쳐 설명한 주장은 관련 소비자와 후속 결정까지 대조한다. 구현과 채택된 약속의 차이는 드러내며 코드를 근거로 약속을 자동 변경하지 않는다. 선택 이유를 복원할 때는 받아들인 비용도 남기되 낡은 전제·과장·미채택 예제를 함께 되살리지 않는다.

리뷰 의뢰에도 기존 설명의 적합성과 새 구성의 개선 효과를 함께 묻는다. 검토자는 원자료·현재 산출물·실제 코드를 직접 확인하고, Main은 발견의 타당성과 제안한 해법을 따로 판단해 수정·유지·후속 선택으로 잇는다. 테스트·링크 검사는 그 입증 범위로 사용하며 설명의 정확성·충실성·구성 적합성 판단을 대신하지 않는다. 결과에는 판단을 가른 근거, 반영한 개선과 유지한 장점, 남은 미확인을 남긴다.

이 기준이 필요한 실제 사례는 [Ticket 02 내용 재리뷰](../../../output/ticket-02-content-review.md)에 있다. 존재하지 않는 타입 지시, 약해진 기록 우선의 이유·비용, 기준과 구현의 혼동, 역할 판단 없이 가져온 체크리스트를 단계적으로 확인한 사례다. 후속 Ticket은 이 사례의 고정 목차를 복제하는 대신 해당 주제의 실제 지시·사용 조건·선택 이유를 대조한다.

## Work 전체의 완료 장면

수집한 주요 후보에 대한 처리 판단이 있고, 채택한 주제는 검증·본문 재구성·선택 이유 복원·참조 전환·옛 문서 읽기 경로 분리까지 완료되어야 한다. 보류 항목은 이유와 후속 조건을 밝힌다. 어려운 항목을 보류했다고만 적어 목표 달성을 주장하지 않는다. 재구성된 본문과 남은 범위를 사용자에게 제시하고 전체 목표의 수락을 별도로 확인한다.

완료 판단에는 실제 Project 산출물, 대표 질문의 읽기 결과, 근거 대조, 현재 경로에서 옛 문서를 읽지 않는다는 확인과 남은 범위가 필요하다. Ticket 종료·링크 검사·Harness 통과만으로 전체 목표 달성을 대신하지 않는다.

## 초기 기계 검증의 한계

생성 시 `verify.json`은 `recover.json`이 표준 JSON으로 읽히는지만 검사하는 초기 계약이다. Workspace schema는 explicit Recover로 별도 확인한다. 본문 내용의 충실성, 이관의 정합성, 제품 동작이나 Work 완료를 이 검사로 증명하지 않는다. 주제별 결과의 지속 Verify가 필요해지면 실제 claim·기준 본문·읽는 입력과 명령을 다시 구성한다. 현재 제품 Verify receipt는 없다.
