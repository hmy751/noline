# 자료의 권위와 이관 계약

## 서로 다른 근거를 대조한다

사용자의 현재 합의는 이 Work의 목표·범위와 작업 우선순위를 정한다. Project의 채택된 제품 의미·관리 계약은 현재 기준을, 코드·테스트는 실제 구현과 확인 범위를 설명한다. 과거 결정·대화·작업 기록은 선택 이유와 당시 상황의 근거다. 가장 최근 파일이나 구현이라는 이유만으로 모든 충돌의 승자로 삼지 않는다.

002의 source 분석은 그때 조사한 범위의 자료이며 전체 제품의 현재 검증을 대신하지 않는다. 004의 열린 질문은 후속 변경 뒤에도 열려 있는지 재판정한다. 005의 수정 결과는 재사용 후보지만 사용자의 전체 목표 수락을 뜻하지 않는다. 원자료의 사실, 당시 제안, 채택된 결정, 이번 해석과 미확인을 구분한다.

## 수집과 현재 본문의 책임

`source`는 선택 원문·접근점·확보 범위를 보존하고, 분석·비교·선택 이유는 `records`, 실행 정의와 최신 판단은 Spec·Ticket·state가 맡는다. 전체 자료를 Workspace에 복제하지 않는다. 정확한 발화나 일시적인 자료가 판단의 근거일 때는 링크뿐 아니라 필요한 원문을 보존한다.

Project의 common/current/guidance는 각각 지속 의미, 현재 구현·지원 관계, 관련 작업의 계약·판단 기준을 맡는다. 모든 주제를 세 문서로 쪼개거나 기존 구조를 그대로 채우지 않는다. 본문의 역할과 이해에 맞춰 내용을 배치하고 필요한 선택 이유를 Decision과 연결한다.

## 문서 이관과 책임 전환

이 Work는 문서 중심의 검증·이관과 기존 Project 본문 재구성을 다룬다. 실제 본문을 바꾸기 전에 [Project 관리 계약](../../../../../../project/MAINTENANCE.md), [내용 정책](../../../../../../CONTENT-POLICY.md), [작성 형식](../../../../../../WRITING-FORMAT.md)을 적용한다. 현재 의미를 옮기면 새 본문, 이전 Owner의 역할, 관련 진입점이 함께 일치해야 한다.

Project 경로·책임·권위를 바꾸는 주제에서는 [live consumer 계약](../../../../README.md)에 따라 active/default와 현재 명시적으로 연결된 Workspace 등 영향받는 실제 소비 경로를 확인한다. 역사 Workspace를 전부 최신화하지 않는다. 스킬·설정 개편이 필요해지는 혼합 문서는 그 구체적 영향을 제시하고 별도로 논의한다.

새 제품 약속이나 충돌하는 제품 선택은 사용자 판단으로 연결한다. 이미 합의한 범위의 사실 정정·내용 복원·본문 재구성은 근거를 확인해 진행하며, 모든 문장 변경을 새 승인 절차로 만들지 않는다.
