# 요구 결과와 대표 장면

## 수집에서 다음 작업을 고를 수 있다

첫 결과는 파일명 목록을 넘어, 어떤 내용이 어디에 있고 왜 다음 작업에 필요한지 보여 주어야 한다. 자료별로 읽은 범위와 미확인 부분을 구분하고, 제품 질문이나 설명 주제로 묶어 현재 Project의 대응 내용과 비교한다. 빠진 내용뿐 아니라 기존 내용을 더 잘 설명할 기회도 후보에 넣는다.

각 주요 후보에는 현재 설명의 부족함, 보완했을 때 달라질 이해·판단, 근거 접근점과 필요한 검증, 권장 처리 및 열린 선택을 제시한다. 이를 바탕으로 사용자가 우선순위와 후속 Ticket 묶음을 판단할 수 있어야 한다. 조사 전에 최종 주제 수·Ticket 수를 고정하지 않는다.

## 오래된 설명을 현재 사실로 바꾸어 읽을 수 있다

과거 문서에 있던 문제나 제안이 지금도 남아 있는지 코드·후속 기록으로 확인한다. 예를 들어 004 당시의 날짜 관련 질문은 이후 002에서 바뀐 입력·전송 표현과 구분해 대조해야 한다. 과거 문제가 있었다는 기록만으로 현재 결함이나 미결 제품 선택을 확정하지 않는다.

구현 사실을 설명하는 문장이 낡았으면 사실에 맞춰 보완한다. 채택된 제품 계약과 코드가 충돌한다면 둘을 구분해 드러내고, 코드를 그대로 새 제품 약속으로 올리지 않는다. 새로운 제품 선택이 필요할 때에는 구체적인 선택지·차이·영향을 논의한다.

## 기존 본문에서 의미와 이유를 함께 이해한다

다음 작업자는 Project 진입점에서 주제의 본문을 찾아 그 기능이 필요한 이유, 관련 책임 사이의 관계, 적용 조건과 예외, 현재 구현의 차이를 이해한다. 여러 과거 Workspace를 복구하거나 링크를 모두 따라가야 기본 뜻을 조립하는 상태를 줄인다. 상세 코드와 원자료는 추가 확인 경로로 연결한다.

예를 들어 활성 여행과 네트워크 제한을 설명한다면 각각의 이름만 나열하지 않고, 데이터 보존과 온라인 서비스 제한이 사용자 장면에서 어떻게 함께 작동하는지 필요한 깊이로 풀어 쓴다. 이 예시는 품질 판단 장면이며 이 주제를 첫 실행 Ticket으로 확정한 것은 아니다.

## 이관 뒤에도 근거와 현재 기준을 구별한다

이관한 주제는 Project 본문을 현재 기준으로 찾을 수 있어야 한다. 기존 문서에는 현재 정본으로 오해할 설명을 남기지 않고, 필요한 역사·형성 근거와 이동 경로를 보존한다. 실제 아카이브 배치와 호환 경로는 해당 주제의 소비 경로를 확인해 정한다. 링크 검사의 성공과 본문 이해의 성공을 따로 확인한다.
