# Ticket 01 — 자료와 실질적인 보완 후보를 넓게 펼치기

상태: 착수 전. Workspace 생성 과정의 경로 확인은 이 Ticket의 조사 완료가 아니다.

## 얻으려는 결과

사용자가 자료와 개선 기회를 한눈에 비교하고 다음 주제별 작업을 고를 수 있는 지도를 만든다. 어떤 파일을 이동할지가 아니라, 어떤 의미·이유·경험을 Project에서 더 잘 이해할 수 있게 할지가 중심이다. 범위가 이미 알려진 로그인·저장 용량·네트워크·Form에 머물지 않도록 실제 자료에서 후보를 찾는다.

## 조사 순서와 먼저 보여 줄 결과

먼저 `.claude`의 문서 지도와 현재 Project의 진입점·실제 본문을 대조한다. 제품 주제별로 기존 자료와 현재 본문의 대응, 이관할 의미와 보존할 근거, 중복·충돌·설명 부족, 역할이 애매한 문서를 드러낸다. 이 대응·이관 지도를 첫 결과의 앞부분에 둔다.

그다음 002의 전체 작업 축적과 004의 제품 질문·이관 결과를 연결해 보완 후보를 확장한다. 005의 결과와 저장소의 다른 자료도 함께 확인한다. `.claude`의 기존 항목에 맞지 않는 중요한 내용은 새로운 후보로 제시하고, 조사 중 연결된 기록이 현재성을 판단하는 데 필요하면 그 자리에서 읽는다. `.claude` 전체의 검증이나 이관을 먼저 완료할 필요는 없다.

## 자료별 접근점과 읽을 이유

- [기존 문서 지도](../../../../../../../.claude/README.md), [Project 진입점](../../../../../../project/README.md): 원자료의 역할과 현재 본문을 비교한다. 기존 Project 본문을 직접 읽고 부족한 내용과 재구성 기회를 찾는다.
- [002 산출물](../../../../002-code-readability-refactoring/output/index.md), [Ticket 색인](../../../../002-code-readability-refactoring/current/memory/tickets/index.md), [원자료 지도](../../../../002-code-readability-refactoring/source/index.md): 전체 수행 범위·분석 자료·후속 작업을 펼친다. 색인의 일부 요약만 읽고 전체 범위라고 단정하지 않는다.
- [004 제품 계약 논의](../../../../004-project-context-contracts-and-guidance/current/memory/tickets/01-product-contract-agreements.md), [004 산출물](../../../../004-project-context-contracts-and-guidance/output/index.md): 제품 질문과 선택지를 구체적으로 나열했던 방식, 이미 이관한 의미와 당시 미결 사항을 확인한다. 현재 미결 여부는 후속 기록과 대조한다.
- [005 산출물](../../../../005-context-based-code-improvement/output/index.md): 이미 작성한 내용과 근거를 재사용할 수 있는지 검토한다. 기존 분류를 새 작업 계획으로 고정하지 않는다.
- [사용자 방향](../../../source/user-direction.md): 후보 선정이나 제외가 사용자의 기대를 좁히는지 판단할 때 대조한다.

위 자료는 시작점이다. 저장소의 다른 문서·README·결정·기록도 탐색하고 발견한 자료의 의미와 조사 범위를 지도에 추가한다. 관련 코드·테스트·커밋은 후보의 현재성을 확인할 때 선택한다.

## 조사 결과에 담을 판단

자료 지도는 출처와 역할, 읽은 범위·시점, 중요한 내용을 찾는 경로를 보여 준다. 주요 보완 후보는 제품 주제나 실제 질문으로 묶고 다음을 설명한다.

- 자료에 어떤 의미·선택 이유·경험이 있고, 다음 작업자가 왜 알아야 하는가.
- 현재 Project에서 누락·충돌·중복되거나 설명이 약한 부분은 무엇인가. 기존 본문을 어떻게 더 충분히 설명하거나 재구성할 수 있는가.
- 현재 사실을 확인한 근거와 아직 대조할 코드·기록은 무엇인가. 과거 제안과 채택된 기준은 구별되는가.
- 복원·재작성·통합·이관·유지 등 권장 처리는 무엇이며, 별도 논의할 제품 선택이나 혼합 문서의 경계는 무엇인가.
- 어떤 주제를 먼저 묶어 실행하면 이해와 후속 작업에 도움이 되는가. 우선순위와 묶음의 이유는 무엇인가.

같은 고정 표의 빈칸을 모든 파일에 채우는 것으로 대신하지 않는다. 주요 후보의 내용과 이유를 충분히 풀어 쓰고, 빠르게 비교할 개요와 필요한 상세를 연결한다. 세부 분석은 날짜별 records, 선택한 자료·후속 작업 지도는 output의 실제 산출물과 색인으로 남긴다.

## 완료 기준과 다음 판단

첫 결과에서 `.claude` 문서와 현재 Project의 대응·이관 관계를 찾을 수 있고, 여기에 002·004의 축적이 어떻게 연결되거나 새로운 보완 후보를 더했는지 설명되어야 한다. 005와 다른 발견 자료까지 검토한 범위가 드러나고, 주요 보완 후보를 내용·효과·근거·필요 검증·열린 판단으로 비교할 수 있어야 한다. 현재 코드 대조를 하지 않은 후보는 가설로 표시한다. 전체 이관 가능성을 모두 확정할 필요는 없지만 실제 본문을 읽지 않은 파일 목록만으로 끝내지 않는다.

결과와 권장 우선순위·후속 Ticket 묶음을 사용자에게 제시한다. 이 Ticket은 자료 수집과 작업 구체화를 맡으며, 실제 Project 본문 재구성·Owner 이동·코드 수정은 후속 실행의 범위로 연결한다. 조사 완료는 Work 전체 완료가 아니다.
