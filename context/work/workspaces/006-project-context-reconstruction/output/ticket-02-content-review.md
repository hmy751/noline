# Ticket 02 내용의 적합성과 개선 재리뷰

2026-10-31, 사용자는 “잘 맞게 가져온건지 그리고 개선 하려면 어떻게 해야하는지도 물어보고”라고 요청한 뒤 “지금 형식에 맞는지만 물어보지말고 기존에 게 적합한건지도 균형있게 생각해달라고”라고 범위를 명확히 했다. 이 문서는 현재 대화의 발췌와 실제 검토·채택·수정·확인 결과를 남긴다.

현재 결과는 아래 [문서 역할과 구성 재검토](#문서-역할과-구성-재검토)까지 포함한다. 내용의 정확성을 확인한 것과 구성의 적합성을 판단한 것은 별도이며, 이전 단계의 좁은 검증을 전체 검토로 확대하지 않는다.

## 앞선 내용 검토의 판단

새 구성을 유지할 이득은 있지만 이전 이관 검증이 충분했다고 단정할 수는 없었다. 현재 코드에 없는 타입을 수정하라는 낡은 지시가 옛 문서에서 그대로 따라왔고, 기존 설명의 유효한 선택 이유도 일부 약해졌다. 독립 검토자는 기존 문서와 새 구성 모두를 현재 사용 목적·코드·채택된 결정에 대조했다. 형식 준수나 옛 링크 제거를 내용의 적합성으로 대신하지 않았다.

원문과 대조한 주요 사용자 발췌·한정 FSD 선택·보류 상태에는 왜곡을 찾지 못했다. 시뮬레이터 관찰을 실제 단절 성공으로 바꾸지 않은 점도 유지한다. ‘발견 없음’은 모든 원자료와 전체 제품의 완전성을 보장하지 않는다.

## 확인한 범위

독립 검토자는 옛/새 제품·Policy·관련 결정과 002 기록, Policy·Router·TripRepository·Local 반영·공통 조회·경비 일정 연결을 대조했다. 기록 우선의 적합성을 판단하기 위해 일정 제출·지도·수정 소비자로 탐색을 확장했다. Main도 실제 타입·정책표와 일정 제출·마커 필터·수정 검색 조건을 직접 확인한 뒤 수정했다.

수정에 참여하지 않은 별도 검증자는 두 변경을 다시 대조했다. 좌표 미선택의 null 제출, 두 좌표가 있는 일정만 마커 전달, 장소명 존재·위도 없음의 안내와 `searchMode === 'api'` 검색 조건, 사용자 선택 후 저장을 통한 보완 설명이 코드와 맞다고 확인했다. 다른 여행의 오프라인 저장이나 자동 좌표 복구·지도 준비 성공으로 확대하지 않았으며 추가 필수 수정은 없었다.

Main은 이번 재리뷰에서 기존 설치된 Jest로 다음 7개 suite를 직접 실행했다. 결과는 **7 suites·146 tests 통과**다.

- `router-network.test.ts`, `trip-lifecycle.test.ts`, `useAppPolicy-network.test.ts`
- `network.test.ts`, `read-query.test.tsx`, `read-query-consumers.test.tsx`, `trip-list-refresh.test.tsx`

실행은 `apps/client`에서 root의 `node_modules/jest/bin/jest.js`, 기존 `jest.config.cjs`와 `--runInBand`를 사용했다. MainTripSection·UpdateScheduleDrawer의 React act 경고 두 건과 Node SQLite experimental 경고가 있었다. 임시 실행 원본은 `/tmp/noline-006-content-review-tests.log`이며 주요 결과·범위는 여기 보존했다.

이 검사는 Router·목록·Policy·관측·Query·화면 연결의 보조 근거다. 문서의 타입명·이관 충실성은 별도 직접 대조로 확인했고, 146개 통과가 폼·지도 전체 동작이나 실기기 단절·실서버 sync 성공을 입증하지 않는다. 제품 코드는 변경하지 않아 문서 보완 뒤 같은 제품 검사를 반복하지 않았다. 문서 링크와 `git diff --check`는 수정 후 통과했다.

## 이후 적용할 판단

이번 재리뷰로 필요한 것은 새 서식의 추가가 아니라 내용별 판정이었다. 후속 이관도 기존 설명의 뜻을 보존하는 확인과 그 설명 자체가 현재 코드·유효한 계약에 맞는지 확인하는 일을 구별해야 한다. 특히 작업 지시의 실제 API·타입·소비자, 선택 이유와 받아들인 비용을 대조하고, 옛 설명이 더 유용한 부분은 복원하되 낡은 전제까지 함께 가져오지 않는다.

위 두 보완은 이 단계에서 반영했다. 이후 발견과 구성 교정은 아래에 이어 구분하며, 현재 실행 상태는 [Ticket 02](../current/memory/tickets/02-product-activation-and-travel-access.md)를 따른다. 03 이후의 이관과 006 전체 완료·제품 검증은 별도다.

## 변경분 재검토에서 추가로 확인한 차이

같은 날 사용자가 “난 좀 아직 우려인 부분이 있는데 다시 변경분 확인해봐 context쪽”이라고 요청했다. 새 독립 검토자는 변경된 Project 본문과 새 travel-access 전체를 기존 원자료·현재 소비자에 다시 대조했고, Main도 해당 분기와 테스트 범위를 직접 확인했다. 이전 두 수정의 검증을 문서 전체의 정확성 확인으로 확대할 수 없다는 사례를 찾았다.

**추가 발견:** 제품 본문과 여행 접근은 열린 일정·경비 생성/수정의 기본 입력이 계속 보인다고 일반화했지만, [UpdateScheduleDrawer](../../../../../apps/client/src/features/schedule/update-schedule/UpdateScheduleDrawer.tsx)는 `policy.schedule.update.allowed === false`에서 Drawer 전체를 제한 안내로 반환한다. 비활성 여행의 일정 수정 중 offline/unknown 전환은 입력 표시 계약과 충돌한다. 폼 hook은 이 분기보다 앞에 있어 입력값 삭제까지 확인된 것은 아니다. 옛 Policy 본문에도 같은 일반 설명이 있었지만, 원문 보존은 현재 구현 검증의 대체 근거가 되지 않는다.

제품 기준·여행 접근의 표와 작성 계약·형성 맥락을 수정해 보존 기준과 구현 차이를 구분했다. 좌표 재검색 설명에도 수정 정책이 허용돼야 한다는 조건을 추가했다. 구현 차이에 맞춰 제품 약속을 축소하지 않았고 제품 코드는 변경하지 않았다. [입력 수명 후보](source-map-and-candidates.md#5-입력값초안선택창저장값의-수명)에 예정 06의 연결 전환·입력 표시·내부 값·복귀 후 재저장 확인을 남겼다.

**검증 한계:** `read-query-consumers.test.tsx`의 생성/수정 네 화면 공통 검사는 보조 조회의 제한·복귀를 확인한다. 입력값 보존 검사는 경비 생성에 있으며 일정 수정의 입력 표시를 증명하지 않는다. 앞서 146개 테스트 통과나 좌표 재검색 조건 대조로 이 사례까지 검증했다고 말할 수 없다. 이 추가 검토는 코드·문서 정적 대조이며 앱 실행 관찰은 아니다.

새 검토자는 Router·목록·Policy·화면 복구를 가까이 둔 구성, 사용자 장면과 기록 우선의 이유 보존은 유용하다고 판단했다. 옛 설명 전체 복원이나 현재 본문의 추가 분할은 권하지 않았다. 이 판단은 위 구현 차이를 인정한 상태에서의 구성 판단이며 전체 이관의 무결성 보장은 아니다.

수정 후 같은 독립 검토자가 위 문단·표·형성 맥락과 테스트 원문을 좁게 재확인해 남은 필수 오류를 찾지 못했다. Main은 이번에 수정한 문서 6개의 로컬 링크 대상 존재와 `git diff --check`를 확인했다. 이 검사는 전체 Harness의 과거 링크 실패를 해소했다는 뜻이 아니다.

## 문서 역할과 구성 재검토

사용자는 체크리스트를 포함한 옛 형식을 현재 역할에 맞는지 판단해 가져왔는지 물었고, 변경 문서 전체를 현재 기준으로 수정하며 이 관점을 후속 Ticket에 남기도록 요청했다. 이어 “기존 형식이 적합하면 가져오는건 상관없는데 … 판단이 빠지거나 뭔가 놓친건 문제가 있어보여”라고 정정했다. 형식의 재사용 금지나 체크리스트 일괄 삭제가 요구가 아니다. 정확한 발췌와 선택은 [구성 판단 기록](../records/2026-10-31-04-document-role-and-format-review.md)에 보존한다.

### 의미 보존과 읽기 확인

Main은 이번 수정 직전 판본을 별도로 보존해 대조했고, 독립 검토자는 Project 재구성과 주변 `.claude` 정정을 확인했다. 첫 검토에서 사용자 안내에 내부 구현명을 노출하지 않는 조건이 재배치 중 빠진 점을 찾았다. 오류·제한 절에 복원했으며, 새 제목에 따른 output 링크 변경과 역사 record의 앵커 보존도 재확인했다. 이 좁은 재확인에서 남은 필수 수정은 없었다.

대표 읽기에서는 화면 기능 변경이 첫 작업표에서 책임·Policy·표시 계약으로, 비활성 여행의 연결 단절이 목록·읽기·작성 계약의 서로 다른 보존 조건으로 이어지는지 확인했다. 일정 수정의 현재 불충족을 모든 폼의 완료 동작으로 읽지 않도록 본문 앞의 장면과 상세를 함께 맞췄다. 새 Service 권한을 추가하는 독자는 타입·정책표·소비자 확인을 찾을 수 있다. 이 확인은 문서 적용과 정적 대조이며 제품 실행 검증을 새로 한 것은 아니다.

Work의 별도 검토자는 수정 직전 판본과 비교해 기준 강도·이유·현재 상태의 일관성을 확인했고 남은 필수 보완을 찾지 못했다. Main은 이번 교정에서 바뀐 문서 19개의 로컬 파일·앵커 링크와 `git diff --check`를 검사해 통과했다. `python3 -B -m context.work.harness recover 006-project-context-reconstruction`도 성공했고, 구성 판단 기준·02 완료 범위·03 대기가 복구된 본문에 포함된 것을 확인했다. Recover는 문서 재진입 확인이며 전체 Harness의 역사 링크 실패나 제품 동작을 검증한 결과가 아니다.
