## 비교와 수정한 판단

development는 구현 순서뿐 아니라 요청 해석, 작업 중 맥락 재선택, 역할 배정, 수정·검증, 완료·설명과 지속 문서 반영 연결을 맡는다. 본문의 책임 선언과 형성 기록에서 이를 확인했다. 맥락을 읽고 갱신하는 일을 개발 중 자연스럽게 연결하려는 기존 선택을, 루트의 새로운 수행 절차로 이중 관리할 이유가 없다.

그렇다고 루트를 링크 목록으로만 만들면 Noline의 정체성·코드 경계·기준 선택을 독자가 여러 문서에서 다시 조립해야 한다. development도 root와 경로별 가이드에서 Noline의 제품 기준을 선택하도록 연결돼 있다. 따라서 필요한 프로젝트 설명·접근점과 적용 연결은 남기고, 공통 개발 수행의 재서술은 제외하는 안으로 좁혔다.

Context의 USAGE는 읽기·대조·재사용 방법을, Personal·Project·Work의 각 계약은 내용·권한·갱신을 소유한다. development는 개발 중 그 계약을 적용하고 후속 수행에 연결한다. 루트는 이 위치와 관계를 안내하며 맥락 읽기·수정의 독립 워크플로를 만들지 않는다. 설명·문서 갱신 같은 직접 요청에는 해당 스킬을 찾을 수 있어야 하고 development 전체를 선행 조건으로 만들지 않는다.

## 확인한 수정 후보와 보존할 의미

Main이 현재 문서·대표 코드·package scripts에 대조해 보고한 후보는 다음과 같다. 이 조사는 수정 결과나 실제 앱 실행 검증이 아니다.

- 모든 agent의 report-only 일반화는 development의 구현 위임과 맞지 않는다. 문장을 제거하되 새 일반 역할 규칙을 루트에 추가하지 않고 기존 역할 계약·배정을 따른다.
- 코드와 충돌하면 guide만 고치는 문장은 문서의 낡은 사실과 구현의 계약 위반을 구별하지 못한다. 기존 Project 관리 계약으로 연결한다.
- 활성/비활성의 저장 위치 요약을 모든 여행 작업에 적용하면 계정 전체 목록과 새 여행 생성의 별도 분기를 놓친다. 제품 정체성 설명은 유지하되 범위와 상세 Owner를 맞춘다.
- client·server package scripts에 존재하는 테스트·타입 검사 명령이 하위 가이드에 빠져 있다. 변경에 맞는 검증 진입을 보완하며 모든 명령의 일괄 실행을 새 규칙으로 만들지 않는다.
- 로컬 DB는 실제 Drizzle을 쓰므로 Drizzle-style이라는 불명확한 표현을 재검토한다. 긴 자료를 archive로 보낸다는 포괄 기준도 자료의 현재 역할로 고친다.
- 하위 가이드에는 최근 반영된 앱 실행·데이터·날짜·schema 경계가 있다. 전체를 낡았다고 분류하지 않고 유효한 내용을 보존한다.

선택한 계획은 기존 Owner가 충분히 맡는 중복을 제거하고 고유한 안내를 현행화하는 것이다. 새 관리 README나 공통 workflow로 내용을 옮기지 않는다. 중복을 줄이면 초기 읽기에서 상세 링크를 따라갈 필요는 남으므로, 대표 작업에서 필요한 기준·조건을 찾을 수 있는지 확인해야 한다. 줄 수 감소만으로 개선을 판정하지 않는다.
