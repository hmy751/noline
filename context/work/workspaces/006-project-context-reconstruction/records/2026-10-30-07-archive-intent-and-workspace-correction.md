# 아카이빙 의도와 006 Workspace 교정

## 정정의 이유와 범위

첫 조사 뒤 Ticket 02에서 제품 본문과 여행 접근 Owner를 Project에 구성했다. 그러나 Main은 옛 Policy 호환 문서와 결정·아카이브로 향하는 현재 연결을 남긴 채 이관 완료라고 판단했다. 사용자가 최종 제거를 지적하자 근거를 반드시 `.claude` 밖에 보존하고 내부 아카이브까지 삭제해야 한다는 조건을 추가했다. 두 판단 모두 사용자의 목적을 제대로 반영하지 못했다.

사용자는 “더이상 .calude/context를 안보게 하는거였어 decisiosn등도 그렇고”라고 정정했고, 아카이브 격리와 제거를 가능한 방법으로 제시했다. 정확한 발화는 [사용자 원문](../source/user-direction.md#이관-완료와-아카이빙의-뜻에-대한-정정)에 보존했다. 이어진 “006d 워크스페이스” 교정 요청은 대화에서 진행하던 `006-project-context-reconstruction`을 뜻하는 것으로 해석했다.

완료 기준은 현재 가이드와 Project 안에서 필요한 의미·이유를 충분히 얻고 옛 제품 문서를 일반 읽기 경로에서 제외하는 것이다. 현재 형성 자료가 ‘과거 근거’라는 이름으로 옛 결정이나 아카이브를 계속 연결하는 구성도 이 기준을 충족하지 않는다. 원본은 명시적인 역사 조사·복구용으로 격리하거나 제거할 수 있다. 물리 위치와 삭제 자체를 일괄 요구하거나 읽기 권한을 차단하는 새 장치를 만드는 목표는 아니다.

## 반영한 내용과 남은 실행

006의 README, Spec, Project 선택 안내, Ticket 02·03과 색인, state, 조사표와 결과 안내를 같은 기준으로 맞췄다. ‘조사 착수 전’, ‘후속 Ticket 미생성’, 호환 문서 유지 권고처럼 실제 상태와 다른 안내를 교정했다. 원자료에는 새 발화를 추가했으며 기존 원문과 날짜별 기록을 덮어쓰지 않았다.

Ticket 02는 진행 중이다. 실제 본문에서 확인한 Selective Activation·경비 초안 결정·오류 가이드·Policy 아카이브 연결을 구체적인 남은 일로 적었다. 새로 `.claude/decisions`에 만든 이관 결정과 Policy 호환 문서도 정리 대상에 포함했다. 02가 맡는 접근·복구를 먼저 정리하고 저장·준비·폼 등 다른 주제는 03·04·06·07에 연결한다. 08의 전체 읽기 점검은 주제별 정리 후 누락을 확인한다. 후속 Ticket을 기다리는 의존은 담당을 남기며 006 전체 완료로 표시하지 않는다.

이번 실행은 Workspace 교정이다. Project 제품 문서의 추가 재구성, 옛 문서의 실제 격리·삭제, 제품 코드나 실행층 변경을 수행한 것으로 기록하지 않는다. 조사 source와 결과의 옛 문서 링크는 이관 조사 근거이며 최종 개발 읽기 경로로 재사용하지 않는다.

## 확인 결과

- `python3 -B -m context.work.harness recover 006-project-context-reconstruction --json`이 성공했다. 006 id와 현재 Spec·state·산출물 안내의 선택을 확인했다. Project 선택 본문에는 아직 옛 문서 연결이 남아 있어 이관 완료의 증거는 아니다.
- `git diff --check`가 통과했다.
- `node scripts/check-harness.mjs`는 기존 002·003의 역사·조사 자료 링크 오류 8건으로 실패했다. 이번 006 교정에 대한 신규 경로 오류는 보고되지 않았다.
- 현재 기준에서 ‘필수 연결만 없애면 된다’는 축소 해석, 의무적인 외부 보존·삭제 조건, 생성 당시의 미착수 안내가 남지 않았는지 대조했다. 철회한 판단은 결과와 이 기록에서 경위로 구별했다.

이 확인은 Workspace의 재진입과 실행 정의 교정에 대한 것이다. 이전 Ticket 02의 제품 테스트를 재실행하거나 이관의 의미적 완료를 검증한 것은 아니다.
