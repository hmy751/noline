# 개발 판단의 공통 관점

코드를 만들거나 고칠 때는 **누가 무엇을 맡기고, 무엇을 알아야 하며, 어떤 결과를 믿고 다음 행동을 하는지**를 본다. 같은 책임을 이해하는 데 필요한 맥락은 모으고, 서로 다른 지식·변경 이유를 가진 책임은 구별한다. 실제로 줄어드는 호출·읽기·변경 부담과 새로 생기는 연결·호환 비용으로 판단한다.

기존 도구에 맡긴 책임도 출발점에 포함한다. 폼이 입력을, 요청 도구가 진행 상태를 이미 관리하는 경우라면 새 기능 단위가 추가로 소유할 일이 무엇인지 확인한다. 기능을 한 단위로 제공하는 것, 내부 책임을 나누는 것, 파일을 나누는 것은 각각 판단한다.

**가능한 한 별도 설명 없이 코드에서 의도와 동작을 이해할 수 있게 만든다.** 이름·타입·책임 배치·제어 흐름으로 드러낼 수 있는 내용을 주석으로 매번 풀어주는 데 머물지 않는다. 설명은 코드만으로 드러내기 어려운 선택 이유·외부 제약·비자명한 계약을 보완한다. 설명이 있어 올바르게 쓸 수 있다는 것과 코드 자체가 충분히 명료하다는 것은 따로 평가한다.

**기준은 채택한 뒤에도 현재 조건에 적용해 판단한다.** 요구·사용처·비용을 대조해 유지·수정·보류를 고른다. 현재 코드가 기준의 예시와 다른 모양이라는 사실만으로 수정하지 않으며, 실제 버그가 없어도 읽기·변경 부담을 줄이는 구조 개선은 검토할 수 있다.

제품 목적과 이번 목표, 보존할 동작에서 변경 범위를 정한다. 이번 문제와 같은 업무 흐름의 반복·책임 배치가 직접 관련된다면 함께 개선할 수 있다. 개선 뒤 무엇을 덜 알아도 되는지와 실제로 보존할 동작을 나눠 확인한다. 작은 실험 제품에서는 작은 수정이 적합할 수 있지만, 현재 지원 범위 안의 정확성 문제까지 없던 일로 만들지는 않는다.

검토 결과는 ‘공통화가 부족하다’ 또는 ‘이름이 모호하다’에서 끝내지 않는다. 어떤 사용처가 무엇을 알아야 하는지, 바꾸면 어떤 부담이 줄고 어떤 동작을 보존해야 하는지 설명한다. 판단의 차이가 없다면 새 계층·새 이름을 만드는 대신 현재 구성을 유지할 수 있다.

이 본문은 설계·계약·표현의 공통 판단을 다룬다. 코드 묶음·배치·주석·진단의 개인 기준은 [코드 표현과 진단](code-expression/INDEX.md)이 소유한다. 실제 formatter·logger·제품별 표현 규약과 검증 방법은 현재 Project의 가이드를 함께 적용한다.

이번 쟁점에 맞는 본문과 사례는 [주제 안내](README.md)에서 고른다. 이 문서는 개인의 공통 판단을 설명하고, 각 주제의 세부 기준은 해당 본문이 소유한다.
