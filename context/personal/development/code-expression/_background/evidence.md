# 코드 표현 기준의 근거

[현재 본문](../INDEX.md)과 [형성 맥락](context.md)의 핵심 근거를 보존한다. 사용자 발화, 기존 가이드의 문장, 이번 작성자의 구체화를 구별한다. 아래 발췌로 핵심 판단을 재검토할 수 있으며 바깥 설계 기록을 읽어야 본문을 사용할 수 있는 구성은 아니다.

## 개인 기준과 제품 기준의 구별

2026-10-18 개발 체계 설계 대화의 보존 기록 `78-code-guides-comparison-and-applicability`에서 확인한 사용자 발화:

> 코드 가이드도 프로젝트에 맞는 그런가이드가 있을거고 완전 내 개인적인 그런 가이드도 있을텐데 그러니까 if문 중괄호는 프로젝트에 관련된게 아니지만 뭐 음 통화나 그런 코드 가이드는 프로젝트 관련이잖아? 이런것도 구분하는건 어떨까?

이 발화는 적용 범위를 나누려는 의도를 뒷받침한다. 기존 Noline 가이드의 모든 항목을 모든 Project에 채택했다는 발화로 확대하지 않는다.

## 보존 가이드에서 이어받은 판단

원자료는 Noline `context/project/guidance/code-readability.md`의 보존 사본이다. 사본은 2026-09-25에 이전 작업의 사용자 합의를 통합했다고 설명하며, 개발 체계 설계 저장소 `a26d2f95` 판본에서 2026-10-29에 대조했다. 당시 대화 전문을 이번에 다시 확인한 것은 아니다. 아래는 가이드 자체의 발췌다.

> **중괄호는 항상 쓴다.** 짧은 guard에도 적용한다.

> **빈 줄은 처리 목적이 바뀌는 곳에 둔다.** 같은 조건을 준비하거나 한 결과를 구성하는 코드는 붙이고, 준비·거절·외부 작업·결과 적용은 필요에 따라 나눈다.

> **전체 동작에서 세부 구현으로 읽히게 배치한다.** 공개 동작과 helper 사이를 여러 번 오가야 하면 조정한다. 고정 public/private 순서나 배치를 위한 새 함수·파일 분리는 요구하지 않는다.

> 긴 장식 구분선은 간소화하되 요약·예시·단계 번호라는 형식만으로 금지하지 않는다.

> 실패 처리부터 정하고 로그의 필요를 판단한다.

> 중복을 합칠 때 필요한 작업 식별·실패 맥락은 보존한다.

중괄호의 적용을 JS/TS 제어문으로 한정한 것은 이번 작성자의 범위 구체화다. 주석은 코드 재서술·이유/계약·탐색 안내를 구별한 기존 표의 의미를 이어받았다. 복구에 성공해도 진단이 필요할 수 있다는 본문의 설명은 실패 처리와 기록 목적이 다르다는 기준을 풀어 쓴 것이다. 이 문장 각각을 과거 사용자가 직접 선택했다고 기록하지 않는다.

기존 주제에 보완한 내용도 같은 원자료에 있다.

> 현재 값이 같아도 변경 이유가 다른 상수는 나눌 수 있다.

> **`catch`의 범위는 분류할 실패에 맞춘다.** 단순 기록·재전파와 복구·분류·후처리를 구별한다.

> `void`는 결과를 사용하지 않겠다는 표현이며, Promise의 실패를 처리하거나 작업 완료를 기다려 주지 않는다.

> `await`는 뒤 작업의 선행 조건인지를 보고 사용한다.

[이름·완료](../../naming-and-completion/INDEX.md)에는 상수의 의미·변경 이유를, [계약·수명](../../contracts-and-lifetime/INDEX.md)에는 catch·void의 실패 책임을 보완했다. 대기 범위 판단은 기존 이름·완료 본문을 사용한다. 제품의 인증·네트워크·저장 계약은 일반 규칙의 사례만으로 바꾸지 않는다.

## 프로토타입 적용 요청

2026-10-29, 기존 코드 표현 기준을 Personal의 새 ‘코드 표현과 진단’ 주제와 기존 이름·계약 본문으로 나누는 문안·배치안을 제시한 뒤 사용자가 요청했다.

> 프로토 부터 적용해봐

이 요청에 따라 prototype에 반영한다. Reference·Noline 적용, 모든 코드의 정리, 품질 기준 전체 티켓의 마감이나 실제 사용 효과의 확인까지 승인·완료된 것으로 확대하지 않는다.

## 본문 읽기에 대한 피드백

2026-10-29, prototype의 서술형 본문을 적용한 뒤 사용자 발화:

> 서술적이어서 그런가 뭔가 눈에 확 안들어오네

작성자는 핵심 기준과 조건·제약이 긴 문단에 섞인 구성 문제로 해석해 항목·표·짧은 코드 대비로 재구성했다. 사용자가 기준의 내용 자체를 철회하거나 모든 문서를 표로 바꾸라고 요청한 것은 아니다. 이후 사용자는 “그래 더 보기좋네”라고 답했다. 현재 본문의 보기 편함에 대한 수용이며 실제 개발에서의 반복 효과까지 확인한 것은 아니다.

## 빈 줄 기준을 구체화한 선택

2026-10-29, 사용자는 같은 목적이면 붙이는 본문의 범위를 다시 짚었다.

> 한줄 개행은 좀 같은 조건이라도 무조건 붙이는것보다 띄는게 나을 것 같긴해 아닌가? 붙이는건 뭐 유사한 변수나 이런건 붙이는데

Airbnb의 현행 JavaScript 가이드를 같은 날 확인했다. [19.7](https://github.com/airbnb/javascript#whitespace--after-blocks)은 블록 뒤 다음 문장 앞에 빈 줄을 두도록 명시하고, [13.3](https://github.com/airbnb/javascript#variables--const-let-group)은 const끼리·let끼리 묶는다. [13.4](https://github.com/airbnb/javascript#variables--define-where-used)의 예시에는 변수 선언과 if 사이 빈 줄도 있지만 모든 if 앞을 띄우라는 일괄 규칙은 아니다. 이 비교는 빈 줄의 위치를 구체화하는 참고로 썼으며 Airbnb 가이드 전체를 채택하지 않았다.

작성자는 “관련 변수나 짧은 연속 처리는 묶되, 같은 목적이어도 선언·조건 검사·실행의 경계는 빈 줄로 구별한다”는 문안과, 입력 변수·guard·로그인 요청·결과 반영을 나눈 예시를 제안했다. 사용자는 다음과 같이 응답했다.

> 그래 좋아 이게 더 나아보이긴한다

이 선택에 따라 본문과 예시를 수정했다. 요청과 결과 반영 사이 간격까지 포함한 현재 예시는 개인 기준의 구체화이며 Airbnb의 명시 규칙을 그대로 옮긴 것으로 설명하지 않는다.
