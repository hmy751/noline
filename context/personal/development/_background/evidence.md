# 공통 관점의 형성 근거

[형성 맥락](context.md)과 [공통 본문](../INDEX.md)의 관계를 확인할 최소 발췌다. 2026-10-20에 작성 기록을 직접 읽었다. 아래 사용자 원문은 당시 기록이 발화로 보존한 구간이며 전체 대화 원본을 다시 수집한 것은 아니다. 코드 관찰·Main의 해석·사용자 선택은 같은 강도의 증거가 아니다.

## 초대 예제에서 비교한 책임 배치

출처: 2026-10-13, 「코드 기준의 역할 구분과 책임 분리 인터뷰」의 ‘실제 사례의 질문과 Main의 비교안’, ‘사용자의 판단과 조건’. 당시 기록은 [Frontend Fundamentals의 구현 상세 추상화 예제](https://frontend-fundamentals.com/code-quality/code/examples/login-start-page.html)를 같은 날 공식 본문에서 확인했다고 남겼다. 아래는 그 기록에 보존된 관찰이며, 2026-10-20 보완에서 웹 원문을 새로 확인하거나 실행한 결과는 아니다. 당시 페이지의 고정 판본은 확보하지 않았다.

| 비교의 출처 | 당시 비교한 내용 |
| --- | --- |
| 외부 예제의 FriendInvitation | 동의창·전송 처리를 InviteButton에 모아 페이지가 한 번에 읽는 맥락을 줄이고 버튼과 클릭 처리를 가까이 둔다. |
| Main이 만든 변형 | 동의창 상세는 `askInvitationConsent`로 나누지만 동의 후 전송하는 순서는 페이지의 `handleInvite`에 남긴다. 외부 예제나 사용자 프로젝트에서 확인한 구현이 아니다. |

이 비교 뒤 **사용자 원문**:

> 음 근데 이 예시가 애매하네 페이지에 얼마나 다른 로직들이 있나도 다를거고 그런걸 고려하면 버튼이 가지는게 나아보이고 아님 페이지 안에 로직이 별로없고 저것만 메인이면 또 다를거고 뭐 그렇네

이는 책임을 모으는 방향에 대한 동의와 구체 배치의 조건을 구별할 근거다. 버튼으로의 추출·특정 함수명·모든 기능의 파일 분리를 채택한 원문은 아니다. 뒤의 Dialog·도구 논의는 별도의 비교와 정정이다.

## 책임과 함께 읽을 맥락

출처: 2026-10-13, 「코드 기준의 역할 구분과 책임 분리 인터뷰」의 ‘사용자의 판단과 조건’, ‘역할과 패턴에 관한 후속 정정’.

**보존된 사용자 원문:**

> 일단 토스 자료 보면 나도 동의해 응집도가 높아야 읽는 맥락이 같은 책임 아래 집중돼서 나도 좋거든 합성형도 UI수정은 자유로우면서 해당 로직이 각 맡은 바에 집중하기도 좋고 뭐 아무튼 난 책임 분리가 확실한걸 좋아해

**길이 중심 해석에 대한 후속 정정의 발췌:**

> Dialog는 합성형이고 하나에서 보고 부품들 파악하고 보통 그러기도 하니까 그게 편했고

같은 절에서 사용자는 짧다는 이유만으로 페이지·컴포넌트를 모을 가능성을 우려했다. 이 근거는 같은 책임을 파악할 맥락과 독립 책임의 경계를 함께 보게 한다. 짧은 코드의 합치기나 많은 파일의 선호를 확정하지 않는다.

## 기존 도구에 맡긴 책임

출처: 같은 기록의 ‘기존 도구의 책임과 기능 Hook 내부 분리’.

**보존된 사용자 원문:**

> 리액트 쿼리 훅이 있으면 데이터는 거기에 맡기고 왜냐면 그 책임 포인트가 있으니 근데 정말 복잡한 로직경우 쿼리 훅까지 포함해서 하는경우도 있고

Main이 요청·진행 상태를 맡는 새 Hook을 비교하던 상황의 정정이다. 특정 라이브러리의 일괄 도입이나 업무 Hook 금지로 확대하지 않는다. 새 기능 단위가 추가로 소유할 일이 무엇인지 묻는 현재 표현은 이 발화를 일반화한 설명이다.

## 일반 기준과 판단 질문

출처: 2026-10-16, 「기준의 조직·표현·판단 질문을 전체 체계 안에서 논의한다」의 ‘사용자 요청과 재개에서 바로잡은 연결’.

**보존된 사용자 원문:**

> 일단 구체적 사례 분만 아니라 뭔가 추상? 일반적인? 그런 가이드? 아님 원칙 지침도 있으면 좋아보여 뭔가 지금 나눈 코드들은 다르지만 기준들은 뭔가 있는것 같거든 그리고 기준도 뭔가 구체화 해야할것 같고 어떤 기준으로 고민을 하는지 생각할지 그리고 또 하나 생각나는건 전달할 때 질무을 전달해야할 것 같아 기준에 대한 질문? 그래야 작업자나 검토자가 그걸 고려할거고 이건 뭔가 AI를 잘다루는 감각이 필요해보이고 일단 러프하게 말해봤어

사용자는 러프한 생각으로 제안했다. 일반 기준·질문을 함께 제공할 방향의 근거이며, 현재 목차·질문 수·모든 답안 출력·모든 질문을 사용자에게 되묻는 절차를 선택한 원문은 아니다.

## 일반 기준과 사례의 구성에 사용한 외부 비교

2026-10-17 「형식 설계를 위한 외부 자료의 가져오기·조정·보류 비교안」, 2026-10-18 「원칙·사례를 구별하고 후속 판단으로 이어지는 시안을 보완한다」 및 「짧은 공통·이름과 가독성 절을 기존 시안에 반영」, 2026-10-19 「이전 결정의 반영 범위와 현재 본문 평가」를 대조해 복원했다. 형식 제안에서 실제 시안에 이어 쓴 참고와 전체 철학·운영 채택을 구별한다. 아래 설명은 **당시 조사·적용 기록의 재구성**이며 이번 웹 원문 직접 재확인이나 저자의 원문 인용이 아니다.

2026-10-18 적용 기록은 의미·조건의 근접성, 상황·질문에 따른 구별, 필요한 자료의 선택적 읽기를 이 비교에서 이어 썼다고 명시한다. 현재 주제 수·파일명·문장 전체를 외부 자료가 정했다는 뜻은 아니다. 일반 기준·질문을 함께 전달하자는 사용자 요청과 이를 구체화한 작성자의 선택을 함께 보아야 한다.

현재 본문을 수정할 때는 이 표만으로 외부 규칙을 새 의무로 적용하지 않는다. 특정 권고의 정확한 문구·판본 차이가 새 판단에 중요하면 해당 원문을 다시 확인하고, 아직 확인하지 못한 부분은 한계로 남긴다. 당시 적용과 이후 주제 복원의 관계는 [구성 기록](records/2026-10-19-topic-restoration.md)에 있다.

## 빠진 주제의 복원

출처: 2026-10-19, 「빠진 기존 판단의 반영과 같은 코드의 이름 비교」의 ‘사용자 요청과 실제 범위’.

**보존된 사용자 원문:**

> 그래 그럼 빠진 기존 판단부터 현재 프로토타입에 반영하자. 결정된 것과 유보된 건 구분하고, 이름 유지에 설명만 보완한 안과 개명한 안도 같은 코드로 나란히 보여줘. 왜 그렇게 반영했는지도 같이 설명해줘.

같은 기록은 공통 제공·사용처 선택과 계약·수명 두 주제를 일반 기준·상세 사례로 추가했다고 남겼다. 이는 실제 문서 작성의 기록이다. 새 API 채택·제품 적용·본문 전체 수용으로 확대하지 않는다.

## 이미 보존한 공통 논의

출발 목적, 채택 뒤 조건별 적용, 코드 명료함, 개인 기준의 갱신 책임은 이름 주제의 [근거 발췌](../naming-and-completion/_background/evidence.md)에 먼저 보존돼 있다. 해당 절의 발화·해석·한계를 그대로 참조하며 동일 원문을 여기 다시 보관하지 않는다. 각 주제의 실제 사례 근거는 [공통화 형성 자료](../shared-boundaries/_background/README.md)와 [계약·수명 형성 자료](../contracts-and-lifetime/_background/README.md)가 맡는다.
