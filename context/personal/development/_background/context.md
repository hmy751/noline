# 공통 관점이 형성된 맥락

[공통 관점](../INDEX.md)이 책임·계약·코드 명료함을 함께 다루는 이유를 설명한다. 현재 적용할 기준의 요약을 다시 만드는 대신, 코드 선호를 실제 판단으로 바꾸는 과정에서 무엇을 바로잡았는지 남긴다.

## 책임을 파악하는 기준이 필요했던 이유

출발점은 결정된 작업을 더 좋은 구현으로 이어 가기 위해 작업자가 받을 컨텍스트·코드 기준·절차를 구체화하려는 요구였다. 이름 기준에 이미 보존한 [목적 발화](../naming-and-completion/_background/evidence.md#목적)가 이 공통 배경을 설명한다. 기존 코드에 대한 불만은 사용자의 경험이며, 이 발화만으로 개별 코드의 결함 원인을 확정한 것은 아니다.

책임 분리의 초기 비교에는 토스의 초대 페이지 예제를 사용했다. 그 예제는 동의창과 전송 처리를 버튼에 모았고, 작성자는 동의창 상세만 분리하고 전송 순서는 페이지에 남기는 변형도 제시했다. 사용자는 같은 책임의 맥락을 모으는 방향에 동의하면서도 페이지에 다른 일이 얼마나 있는지, 초대가 주된 일인지, 확장이 예상되는지에 따라 배치가 달라진다고 설명했다. 외부 예제의 배치를 그대로 개인 규칙으로 채택한 과정은 아니다. [실제 참고와 비교 조건](evidence.md#초대-예제에서-비교한-책임-배치)

책임 분리를 탐색하면서 사용자는 같은 책임의 맥락을 함께 파악하고 싶다고 밝혔다. 그러나 Main이 이를 길이와 성장 가능성 위주로 설명하자, 독립된 페이지·컴포넌트까지 짧다는 이유로 합칠까 우려했다. Dialog의 관련 부품을 함께 보는 이유는 한 합성형 UI의 구성을 파악하는 편의였다. 따라서 지금의 공통 관점은 책임을 이해할 단위와 그 안의 파일 배치를 같은 결정으로 보지 않는다. [당시 전환](records/2026-10-13-responsibility-and-tools.md)과 [사용자 발화](evidence.md#책임과-함께-읽을-맥락)를 대조할 수 있다.

이 과정에서 확인한 것은 책임과 맥락의 관계를 먼저 보려는 방향이다. 모든 기능을 Hook으로 빼거나 특정 패턴을 일괄 적용하라는 선택은 없었다. 한곳에 둬도 이해하기 충분한 작은 기능과, 여러 책임이 섞이거나 확장이 예상되는 기능의 선택 여지는 남았다.

## 이미 맡긴 책임에서 출발한다

기능 Hook을 비교할 때 Main은 요청·진행 상태를 새로 묶는 안을 제시했지만, 사용자는 React Query 같은 기존 도구에 맡긴 책임이 빠졌다고 정정했다. 책임 분리는 빈 상태에서 새 단위를 만드는 문제가 아니라 현재 누가 무엇을 관리하는지부터 읽는 문제로 보완됐다. [정정 발화](evidence.md#기존-도구에-맡긴-책임)

이 관점은 폼의 값·검증과 요청 상태를 중복 소유하지 않도록 판단할 근거가 된다. 복잡한 업무 흐름이 기존 Hook을 포함해 조율할 수 있다는 여지도 함께 유지한다. 기존 도구를 무조건 도입하거나 사용처에 그대로 노출하라는 규칙은 아니다. 공통 UI가 무엇을 제공할지와 그 내부를 외부 도구로 구현할지 직접 구현할지도 구별한 논의였다.

## 서로 다른 코드에서 같은 판단을 찾는다

Field·Container·fetcher·Toast·주문·이벤트 Hook을 살펴본 뒤, 사용자는 개별 사례뿐 아니라 여러 코드에 적용할 일반 기준과 판단 질문을 함께 전달하자고 제안했다. 목적은 작업자와 검토자가 필요한 관점을 실제 판단에서 고려하게 하는 데 있었다. [제안 원문](evidence.md#일반-기준과-판단-질문)

이 요청을 구체화할 때 외부 형식도 비교했다. Matt의 개념·질문·코드 대비와 필요한 때 읽는 안내, Vercel의 기준·이유·작업 연결, pstack의 조건·질문, Anthropic의 판단에 충분한 구체성을 참고했다. 이 비교는 일반 의미를 설명하고 사례에서 조건에 따른 선택 차이를 보여 주는 구성에 사용했다. 좋은 코드 하나를 정답으로 모방시키거나 질문마다 답안을 제출시키는 방식, 저자의 설계 철학·역할·파일 분할 전체는 가져오지 않았다. [자료별 기여와 한계](evidence.md#일반-기준과-사례의-구성에-사용한-외부-비교)

현재처럼 공통 관점과 주제를 나눈 문장·배치는 작성자가 구체화한 결과다. 이후 이름·완료 중심으로 좁아졌던 본문에서 빠진 기존 판단을 복원하며 공통화와 계약·수명 주제를 추가했다. 공통화는 사용처의 선택·교체·업무 흐름을, 계약·수명은 같은 호출 모양 안에서 달라지는 오류·시간·종료 의미를 소유하도록 구별했다. [복원 과정](records/2026-10-19-topic-restoration.md)

이 때문에 공통 본문은 모든 사례의 결론을 다시 담는 대신 필요한 판단의 출발점을 제공한다. 질문도 일률적인 답안 제출 목록으로 채택된 것이 아니다. 특정 사례와 코드 모양이 같은지보다 그 선택을 가른 목적·사용처·비용이 현재 작업에도 성립하는지 보도록 돕는다.

## 조건별 적용과 코드 명료함의 범위

‘나중에 기준을 다듬을 수 있음’과 ‘채택한 기준도 현재 조건에 대입함’은 다른 문제라는 정정이 있었다. 현재의 유지·수정·보류는 초안 단계에만 허용되는 예외가 아니다. 이 논의의 [당시 기록](../naming-and-completion/_background/records/2026-10-18-conditional-application.md)과 [발췌](../naming-and-completion/_background/evidence.md#조건별-적용)는 기존 보존 위치를 사용한다.

코드 명료함의 우선순위는 이름 유지와 개명 비교 뒤 사용자가 “되도록 설명이 필요없는 코드”를 지향한다고 밝히며 보완됐다. 본문은 이 지향을 이름·타입·책임·흐름으로 풀어 썼다. 그 전부의 효과가 실험으로 입증됐거나 사용자가 모든 문장을 직접 선택한 것은 아니다. [명료함 기록](../naming-and-completion/_background/records/2026-10-19-clarity-and-renaming.md)과 [발화·해석의 경계](../naming-and-completion/_background/evidence.md#코드가-드러내는-의미)를 함께 본다.

## 확인 범위와 열린 판단

이 자료의 근거는 개인 개발 기준을 설계한 대화와 당시 외부 자료 비교의 보존 기록이다. 실제 UI 템플릿을 읽었던 관찰과 사용자의 의도 설명·회고, 작성자의 가상 비교를 구별해 가져왔다. 이번에는 외부 템플릿 원본이나 제품을 실행하지 않았다.

확인한 방향을 지금의 본문에 담았지만, 문장·질문·주제 분할 전체가 최종 수용됐거나 낯선 작업에서 효과를 입증한 상태는 아니다. 여러 저장소의 기준 배포·동기화, 세부 코드 스타일, 검토 운영 방식까지 이 공통 관점이 결정하지 않는다. 새로운 작업에서 읽기·변경 부담이나 계약 충돌이 확인되면 해당 주제의 조건과 근거부터 다시 비교한다.

## 표현·진단 주제를 추가한 이유

2026-10-29, 기존 제품 가이드 안의 개인 표현 기준을 이어받아 코드 묶음·배치·주석·진단을 네 번째 주제로 구성했다. 이름·완료와 계약·수명에는 각 질문에 해당하는 보완만 두었다. [새 주제의 형성 맥락](../code-expression/_background/context.md)과 [근거·prototype 적용 요청](../code-expression/_background/evidence.md)에 분리 대안과 적용 범위를 남겼다. 공통 관점이 특정 제품의 도구 설정을 결정하지 않는다는 경계는 유지한다.
