# 공통화 기준이 형성된 맥락

[공통 제공과 사용처 선택](../INDEX.md)의 목적과 선택 이유를 설명한다. 공통 관점의 출발점과 조건별 적용은 [공통 형성 자료](../../_background/context.md)가 소유하며, 여기서는 Field·Container·주문 비교가 현재 기준에 남긴 차이를 다룬다.

## Field와 Container의 서로 다른 목적

Field 논의는 사용처에서 입력과 오류를 반복 연결하는 코드를 더 짧게 만드는 비교에서 시작했다. 사용자는 디자인이 바뀔 때의 유연성을 위해 의도적으로 부품을 나눴다고 설명했다. 이 설명으로 기존 연결을 덜 끝난 공통화로 보는 해석을 바로잡았다. 이후 자동 연결안에는 폼 도구 종속성과 다른 입력으로의 교체 가능성이 빠져 있다는 질문이 이어졌다. [원문과 당시 조건](evidence.md#field의-분리와-교체-질문)

이 과정에서 배치 순서를 바꾸는 자유와 값·이벤트·ref·오류의 연결을 유지하며 입력을 교체하는 자유가 다르다는 판단을 얻었다. 합성형 UI와 상태 연결 공유는 함께 사용할 수 있으므로, 직접 연결과 일체형 부품만을 양자택일로 두던 비교도 충분하지 않았다. 현재 본문이 실제 교체 계약을 확인하게 하는 이유다. [당시 정정·미선택](records/2026-10-14-composition-and-common-form.md)

반면 Container는 당시 필요한 공통 디자인 형식이 있었기 때문에 만든 것이었다. 같은 조회·목록에 Container와 Hook 직접 연결을 대입하니, 공통 상태 표시를 반복하지 않는 편의와 표시 정책이 달라질 때의 부담이 드러났다. 사용자는 필요가 사라지고 재사용 가치가 낮아지면 Container를 없앨 수도 있다고 설명했다. [당시 의도 설명](evidence.md#container를-제공한-이유)

이 두 사례는 묶음과 분리 중 하나를 정답으로 고르지 않게 했다. 함께 원할 형식이 있는지, 어떤 차이를 사용처가 표현해야 하는지를 먼저 보아야 두 선택을 일관되게 설명할 수 있었다. Hook과 Container도 이미 함께 존재하며 감지 재사용과 기본 화면 구성을 각각 제공했다.

## 요청이 같은지에서 업무가 같은지로

주문 비교의 출발 코드는 제품 기능이 아닌 Markdown 예제였다. 성공 콜백이 캐시 무효화·장바구니 정리·이동을 함께 호출했다. 다른 화면에서도 요청한다는 조건을 넣자 같은 API를 공유하는 것과 같은 장바구니 구매를 공유하는 것이 달랐다.

사용자는 같은 업무 흐름인지 보고 공통 범위를 정한다는 기준에 동의했다. [주문 근거](evidence.md#같은-api와-같은-업무-흐름) 이 때문에 현재 본문은 화면 근처에서 호출한다는 이유만으로 업무 처리를 각 화면에 남기지도, 같은 API라는 이유로 모든 후처리를 묶지도 않는다. 같은 요청 뒤 어떤 데이터·업무 규칙·완료 표시가 함께 달라져야 하는지가 판단의 근거다.

## 유지 판단에 관련 개선의 조건을 보완함

앞선 사례에서 목적에 맞는 구조를 유지할 조건은 여러 번 확인했지만, 현재 작업에서 실제 개선으로 넘어갈 조건은 덜 다뤘다. 이를 보완하려고 같은 장바구니 구매를 제공하는 세 화면의 쿠폰 누락을 가정했다.

사용자는 같은 흐름이고 이번 수정과 직접 관련된다면 함께 공통화하는 안을 좋게 보았다. 동시에 변경 범위·기존 동작·작은 실험 제품의 투자 필요를 조건으로 남겼다. [가정과 선택 기록](records/2026-10-16-workflow-and-related-improvement.md#관련-공통화를-함께-할-조건) 현재 본문이 유지뿐 아니라 관련 개선의 긍정 조건을 설명하는 이유다.

작은 제품에서 줄일 수 있는 것은 구조 개선 투자라는 해석을 남겼으며, 요구한 정확성까지 생략한다는 의미로 확대하지 않았다. 구체 제품의 수정 권한은 별개다. 당시 대화는 기준 설계였고 실제 제품 수정은 요청하지 않았다.

## 열린 선택과 확인 한계

Field 연결 API, 주문 Hook API, Container의 새 슬롯·합성 API는 선택하지 않았다. 주문의 실제 상품 캐시 영향, 부분 구매, 주문 중 장바구니 변경 정책도 예제에 없었다. 사용자가 설명한 의도와 작성자가 추가한 비교 조건을 구별해야 한다.

이번 형성 자료는 보존된 코드 읽기와 대화 기록을 대조한 결과다. 현재 본문·사례의 문장은 그 판단을 구체화한 산출물이며, 실제 리팩터링·컴파일·제품 동작·장기 유지 비용의 개선을 확인한 결과가 아니다. 새로운 사용처의 정책·교체 계약·보존 비용이 달라지면 해당 조건으로 공통 범위를 다시 판단한다.
