# 공통 경계를 바꾸면 사용처에서 무엇이 달라지는가

Field의 배치 변경, 무한 스크롤의 오류 표시, 주문 성공 처리를 비교한다. 같은 코드를 함께 쓴다는 사실에 더해, 사용처가 같은 동작을 원하는지와 필요한 차이를 어디서 표현할 수 있는지를 본다. 다른 작업에 적용할 기준은 [공통 제공과 사용처 선택](INDEX.md)에 있다.

## Field의 배치를 바꾸는 일과 입력을 교체하는 일

UI 템플릿의 Field는 제목·입력 배치·라벨·설명·메시지를 조합할 부품을 제공한다. 확인한 사용 예에서 이름은 입력 하나로, 이메일은 입력과 선택창 두 개로 구성돼 있었다. 폼값·검증은 React Hook Form이 맡고, 사용처가 입력과 메시지 표시를 연결한다.

다음은 이름 입력의 실제 코드 발췌다. 필수값 검증을 등록하고, 같은 오류 상태를 입력의 오류 표시와 메시지에 각각 전달한다.

```tsx
<Input
  {...register("name", { required: true })}
  isError={errors?.name && "필수 항목입니다."}
/>
<Field.Message>{errors.name && "필수 항목입니다."}</Field.Message>
```

디자인이 바뀌어 오류 메시지를 입력 위에 놓아야 한다고 가정해 보자. 아래는 두 요소의 순서만 바꾼 설명용 코드다. 외곽 Field와 레이아웃은 생략했다.

```tsx
<Field.Message>{errors.name && "필수 항목입니다."}</Field.Message>
<Input
  {...register("name", { required: true })}
  isError={errors?.name && "필수 항목입니다."}
/>
```

이 변경은 사용처에서 표현할 수 있다. 입력값과 검증 연결을 바꾸거나 공통 Field에 `messagePosition` 같은 새 옵션을 추가할 필요가 없다. 이미 이메일처럼 두 입력을 한 Field 안에 놓는 사용처도 있으므로, ‘입력 하나와 아래쪽 메시지’를 고정하는 일체형 부품으로 모두 바꾸면 그 구성을 별도로 지원해야 한다. 연결 코드가 짧아지는 만큼 무엇을 고정하게 되는지가 비교 대상이다.

그러나 이 배치의 자유만으로 다른 입력으로의 교체까지 해결되지는 않는다. 예를 들어 교체할 입력이 이벤트 객체 대신 새 값을 `onValueChange`로 돌려주거나, 체크 상태를 `checked`로 받는다고 가정하자. 기존 `register` 결과를 그대로 펼쳐 넣을 수 있는지는 그 입력의 계약에 달려 있다. 자동 연결 부품을 도입하더라도 같은 확인이 필요하다.

| 교체할 때 확인할 연결 | 이 Field에서 필요한 판단 |
| --- | --- |
| 값 | 폼이 가진 값을 입력의 `value` 또는 `checked`에 어떤 타입으로 전달하는가? |
| 변경 이벤트 | 입력이 내보내는 이벤트나 새 값을 폼 상태에 어떻게 반영하는가? |
| ref | 폼이 참조해야 하는 실제 입력 요소까지 연결할 수 있는가? |
| 오류 | 입력이 받는 오류 표현과 `Field.Message`에 보여 줄 문구를 각각 어떻게 정하는가? |

현재의 명시적 연결은 이 선택들을 사용처에 남긴다. 같은 연결을 반복한다면 폼 도구 전용 연결 부품으로 줄일 수도 있지만, 범용 Input·Field 전체가 그 도구를 알아야 하는 것은 아니다. 배치는 계속 조합하도록 열어 두고 상태 연결만 공유하는 방법도 가능하다.

따라서 이 사례에서 지킬 것은 **필요한 배치와 입력 교체를 실제 계약으로 확인하는 것**이다. 자동 연결을 도입할지는 교체 대상과 반복되는 연결을 확인한 뒤 정한다. 여기서는 특정 연결 API를 구현하거나 선택하지 않았다. 발췌에 있는 문자열 `isError`의 표현 문제는 [이름 사례](../naming-and-completion/INDEX.cases.md#문자열-iserror를-유지한-판단)에서 따로 다룬다.

## Container의 오류 표시를 바꾸면 목록은 어떻게 되는가

UI 템플릿의 `InfiniteScrollContainer`는 조회 결과를 받아 페이지 배열을 펼치고, 로딩·오류·빈 목록과 하단 추가 조회 상태를 표시한다. 감지는 독립된 `useInfiniteScrollObserver` Hook이 맡으며 Container가 이를 연결한다. 조회 API와 목록 안의 Grid·Card 구성은 사용처가 결정한다.

아래 코드는 기존 인터페이스로 사용 구조를 줄여 쓴 예다. `ProductList`는 실제 Grid·Card 목록 JSX를 생략한 설명용 이름이다. 조회 결과 변수는 앞에서 호출한 `useInfiniteQuery`에서 받는다고 놓았다.

```tsx
return (
  <InfiniteScrollContainer<Product>
    data={data}
    isLoading={isLoading}
    isError={isError}
    hasNextPage={!!hasNextPage}
    isFetchingNextPage={isFetchingNextPage}
    fetchNextPage={fetchNextPage}
    loadingComponent={<p>불러오는 중...</p>}
    errorComponent={<p>조회에 실패했습니다.</p>}
    emptyComponent={<p>상품이 없습니다.</p>}
    endComponent={<p>모든 상품을 봤습니다.</p>}
  >
    {products => <ProductList products={products} />}
  </InfiniteScrollContainer>
);
```

이 Container는 오류 상태이면 `errorComponent`만 반환한다. 이제 **추가 조회가 실패해도 이미 받은 상품은 계속 보여 주고, 목록 아래에 오류를 표시하라**는 변경을 가정하자. 오류 문구만 바꿔서는 목록이 함께 나오지 않는다. 오류 컴포넌트 안에 목록을 다시 넣을 수는 있지만, 그러면 페이지 펼치기와 목록 렌더링을 사용처에서도 맡게 된다.

독립 Hook을 직접 연결하면 표시 분기를 사용처에서 바꿀 수 있다. 다음은 기존 Hook 계약을 사용하는 설명용 변경안이다. 조회 설정과 목록 내용은 같게 두고, 오류로 전체 화면을 대체하는 조건을 바꿨다.

```tsx
const { loadMoreRef } = useInfiniteScrollObserver({
  hasNextPage: !!hasNextPage,
  isFetchingNextPage,
  fetchNextPage,
  enabled: !isLoading && !isError && !!hasNextPage,
});

const products = data?.pages.flatMap(page => page) ?? [];

if (isLoading) return <p>불러오는 중...</p>;
if (isError && products.length === 0) return <p>조회에 실패했습니다.</p>;
if (products.length === 0) return <p>상품이 없습니다.</p>;

return (
  <>
    <ProductList products={products} />
    {isError && <p>조회에 실패했습니다.</p>}
    <div ref={loadMoreRef} style={{ height: '1px', padding: '2rem 0' }}>
      {isFetchingNextPage && <p>불러오는 중...</p>}
      {!isFetchingNextPage && !hasNextPage && <p>모든 상품을 봤습니다.</p>}
    </div>
  </>
);
```

처음 로딩이 끝난 상태에서 두 코드의 분기를 비교하면 다음 차이가 생긴다. 실행 결과를 측정한 표가 아니라 위 조건에 따른 표시 비교다.

| 조회 상태 | 기존 Container | Hook 직접 연결 변경안 |
| --- | --- | --- |
| 오류가 없고 상품이 있음 | 목록 표시 | 목록 표시 |
| 오류가 있고 상품이 없음 | 오류만 표시 | 오류만 표시 |
| 오류가 있고 이미 받은 상품이 있음 | 오류만 표시 | 목록을 남기고 아래에 오류 표시 |

이 분기는 오류의 종류 대신 남아 있는 데이터의 유무로 표시를 정한다. 오류일 때 감지를 끄는 기존 `enabled` 조건은 유지한다. 얻는 자유는 표시 정책을 바꾸는 데 있다. Hook의 상태·함수 입력과 `HTMLDivElement` ref 계약까지 없어지는 것은 아니다. Container가 요구하는 `pages: T[][]` 형태도 직접 연결안에서는 화면이 해석하고, Hook에는 감지에 필요한 상태와 함수만 전달한다.

기본 표시 정책이 모든 화면에 맞으면 Container가 유리하다. 페이지 펼치기, 상태별 우선순위, 하단 감지 요소의 배치를 한곳에서 관리하므로 화면마다 다시 조립할 필요가 없다. 한 화면만 다른 오류 표시를 원한다면 Hook 직접 조합을 검토할 수 있고, 같은 새 정책을 여러 화면이 원한다면 Container의 제공 범위를 바꾸는 안과 비교한다. 이번 대비만으로 새 슬롯이나 합성 API까지 정한 것은 아니다.

초기 로딩과 추가 로딩도 비슷하게 살필 수 있다. 현재 Container는 같은 `loadingComponent`를 두 위치에서 사용한다. 사용처가 `isLoading`에 따라 prop을 계산할 수 있으므로 다른 UI가 불가능한 것은 아니지만, 별도 두 슬롯을 제공하는 구조는 아니다. 실제로 달라져야 하는 표시와 그 변경을 표현하는 부담을 보고 범위를 정한다.

## 같은 주문 API를 써도 함께 묶을 동작은 달라진다

주문 성공 뒤 장바구니를 비워도 되는지는 주문 API의 이름만으로 결정할 수 없다. 장바구니를 주문했는지, 장바구니와 무관하게 바로 구매했는지에 따라 달라진다. 반대로 여러 화면이 같은 장바구니 구매를 제공한다면 요청과 장바구니 정리를 화면마다 반복할 이유도 줄어든다.

다음은 UI 템플릿의 Markdown 문서에 있던 주문 성공 처리 예제다. 완성된 주문 제품의 구현은 아니며, 아래 두 사용 조건과 쿠폰 문제는 설명을 위한 가정이다.

```ts
onSuccess: response => {
  queryClient.invalidateQueries({ queryKey: ['orders'] });
  queryClient.invalidateQueries({ queryKey: ['catalog'] });
  clearCart();
  navigate(`/order-complete?orderId=${response.orderId}`);
}
```

이 예제는 주문·상품 캐시 무효화, 장바구니 정리, 완료 화면 이동을 한 콜백에서 호출한다. `clearCart`와 `navigate`의 내부 구현은 제시돼 있지 않으므로 아래 비교에서는 각각 이 역할을 수행한다고 놓았다. 이 네 동작이 항상 함께 필요한 한 화면을 위한 코드라면 성공 처리에 모아 두는 것도 자연스럽다. 별도 Hook이나 파일이 없다는 사실만으로 고칠 부분이 생기지는 않는다.

### 장바구니 구매와 바로 구매가 함께 사용한다면

같은 주문 API를 두 곳에서 사용한다고 가정하자. 장바구니 구매는 주문 뒤 장바구니를 비우고 완료 화면으로 이동한다. 바로 구매는 장바구니를 건드리지 않고 모달을 닫은 뒤 자기 화면에 완료를 표시한다.

| 성공 뒤 동작 | 장바구니 구매 | 바로 구매 | 함께 맡길 범위 |
| --- | --- | --- | --- |
| 바뀐 데이터의 캐시 무효화 | 필요 | 같은 데이터가 달라진다면 필요 | 두 흐름에서 같은 데이터가 바뀌는 범위 |
| 장바구니 정리 | 필요 | 하지 않음 | 장바구니 구매 흐름 |
| 완료 표시 | 완료 화면으로 이동 | 모달 닫기와 화면 내 표시 | 실제로 다르므로 각 사용처가 선택 |

전체 성공 처리를 공통으로 묶으면 바로 구매도 장바구니를 비우게 된다. 반대로 모든 처리를 사용처에 복사하면 같은 요청 계약과 캐시 규칙까지 각 화면이 관리하게 된다. 따라서 요청·응답 처리를 공유하고, 같은 데이터 변경에 대응하는 캐시 처리도 함께 맡길 수 있는지 확인한다. 장바구니 정리는 장바구니 구매 흐름에 남기고, 다른 완료 표시는 각 사용처가 고르게 한다.

동작이 화면 가까이에 있는지가 소유 위치를 정하지는 않는다. `clearCart`는 화면에서 호출되지만 장바구니 구매의 규칙일 수 있다. 그런 구매가 여러 화면에 반복된다면 공통 구매 흐름이 맡을 수 있다. `navigate`도 모든 호출이 같은 완료 화면으로 가는 전용 흐름이라면 함께 묶을 수 있다.

### 세 화면이 모두 장바구니 전체를 주문한다면

이번에는 조건을 바꾸자. PC 주문 페이지, 모바일 주문 페이지, 빠른 주문 모달이 모두 현재 장바구니 전체를 주문한다. 요청·캐시 무효화·장바구니 정리가 세 곳에 복사되어 있고, 화면 이동과 모달 완료 처리만 다르다.

이때 ‘사용한 쿠폰이 목록에 남는다’는 문제를 고치게 됐다. 원인은 세 곳 모두 아래 처리를 빠뜨린 것으로 확인됐다고 가정한다. 긴급 장애는 아니며 기존 동작을 확인할 여유가 있다.

```ts
queryClient.invalidateQueries({ queryKey: ['coupons'] });
```

| 수정안 | 이번에 해결하는 것 | 남는 부담과 필요한 확인 |
| --- | --- | --- |
| 세 곳에 쿠폰 무효화만 추가 | 현재 누락을 작은 변경으로 고친다. | 다음 구매 규칙 변경도 세 곳에 반영해야 한다. |
| 같은 구매 흐름을 묶으며 쿠폰 무효화 추가 | 현재 누락을 고치고 함께 바뀌어야 할 규칙의 수정 위치를 모은다. | 세 화면의 연결을 바꾸고 기존 성공·실패·로딩·완료 처리를 보존해야 한다. |

이 조건에서는 두 번째 안을 권한다. 요청만 같은 것이 아니라 장바구니 정리까지 같은 업무 흐름이고, 이번 누락도 그 공통 규칙에 관한 변경이기 때문이다. 화면마다 다른 완료 처리는 그대로 남긴다. 이번 수정부터 여러 곳에 같은 규칙을 맞춰야 하는 부담을, 세 화면의 연결 변경과 보존 확인 비용에 비교할 수 있다.

작은 실험 제품이고 이후 같은 구매 규칙을 바꿀 필요가 낮거나 현재 연결 변경을 충분히 확인할 여력이 없다면 첫 번째 안도 타당하다. 그 경우에도 쿠폰 누락은 고친다. 달라지는 것은 정확성을 확보할지 여부가 아니라, 공통 구조에 지금 투자할 만큼의 이득이 있는지다.

### 공통으로 옮기면서 완료 시점까지 바꾸지는 않는다

원래 예제는 캐시 무효화가 끝나기를 기다리지 않고 장바구니 정리와 화면 이동을 호출한다. 공통 함수로 옮기면서 대기를 추가하면 다음 처리의 시점도 달라진다. 이 사례의 공통화 판단만으로 대기를 추가하지 않는다. 최신 조회 결과가 준비된 뒤 이동해야 한다면 완료 시점과 로딩 동작을 별도로 정한다.

실제 적용 전에 확인할 조건도 남아 있다. 주문이 `catalog`를 바꾸는지, 일부 상품만 주문할 때도 전체 장바구니 정리가 맞는지, 주문 중 장바구니가 바뀌면 무엇을 남겨야 하는지는 이 예제에서 정해지지 않았다. 조건이 달라지면 ‘같은 장바구니 구매 흐름’이라는 판단부터 다시 보아야 한다. 구체적인 Hook API와 파일 배치는 이 경계와 보존할 동작을 확인한 뒤 정한다.

Field·Container의 변경안과 주문 비교는 읽어 확인한 코드 또는 명시한 가정에서 도출한 설명이다. 제품 코드 적용이나 실행 검증을 완료한 결과로 사용하지 않는다.
