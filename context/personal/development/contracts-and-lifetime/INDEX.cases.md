# 공통 계약·수명·지원 범위를 판단하는 사례

같은 오류 타입, 같은 `duration`, 같은 `null`도 처리 경계에 따라 다른 결과를 만든다. 이 문서는 [일반 기준](INDEX.md)을 실제 코드의 흐름과 조건별 비교에 대입한다. 관찰 대상은 UI 템플릿의 fetcher·Toast·이벤트 Hook과 별도 앱의 오류 서비스다. 코드에서 도출한 동작이며 제품 실행으로 재현한 결과는 아니다. 추가한 상황과 비교 코드는 해당 위치에서 설명용임을 밝힌다.

## fetcher의 오류 형태와 의미

작은 공통 fetcher는 기본 URL·헤더·HTTP 요청·10초 timeout·본문 해석·오류 변환을 제공했다. 사용처는 API의 입력과 결과 가공을 맡았다. 실제 상품 목록 예제도 이 구별을 따른다.

```ts
const response = await fetcher.get<{ products: Product[] }>(
  `products?skip=${(pageParam - 1) * 20}&limit=20`
);
return response.products.map(p => ({ ...p, name: p.title, price: `${p.id * 100}` }));
```

이 호출의 제네릭은 기대하는 응답 타입이다. 서버 본문이 실제로 그 형태인지 검사한 결과는 아니다. 그렇다고 모든 API의 데이터 검증을 fetcher가 맡아야 한다는 뜻도 아니다. 여기서는 **공통 오류 처리를 사용처가 믿을 수 있도록 정비한다**는 작업을 가정하고, HTTP 요청과 본문 처리에서 생기는 실패를 본다.

### 파싱 실패를 잡는 것과 올바르게 분류하는 것은 다르다

확인한 구현은 지역 `try` 안에서 `return handleResponse(response)`를 사용했다. `handleResponse`는 비동기로 본문을 읽고 해석한다. 이 Promise를 바로 반환하면 호출자는 최종 실패를 받지만, 그 뒤에 발생한 rejection은 반환한 함수의 지역 `catch`를 통과하지 않는다. 지역 `catch`가 모든 실패를 공통 오류로 바꾼다는 설명과 실제 경로가 달라진다.

```ts
// 관찰한 반환 경계
return handleResponse(response);

// 같은 try 안에서 비동기 실패까지 받으려는 변경
return await handleResponse(response);
```

두 번째 표현으로 바꾸면 비동기 실패도 지역 `catch`에서 받을 수 있다. 그러나 기존 `catch`는 Abort가 아닌 일반 Error를 네트워크 실패로 바꿨다. 따라서 200 응답을 받았지만 JSON이 깨진 상황도 연결 실패라는 뜻으로 전달될 수 있다. `await`는 실패를 받는 위치를 바꾸며, 그 실패를 어떻게 설명할지까지 해결하지 않는다.

| 요청·응답 조건 | 하나로 뭉개면 잃는 정보 | 정비 뒤에도 구별해야 할 결과 |
| --- | --- | --- |
| 응답을 받기 전에 요청이 실패함 | 실제로 HTTP 응답을 받았는지 알 수 없음 | 요청 단계의 실패이며, 확보하지 못한 HTTP 상태를 만들어 내지 않는다. |
| 200 응답을 받았지만 JSON이 깨져 있음 | 네트워크 실패로 바꾸면 응답을 받았다는 사실과 해석 실패가 가려짐 | 응답은 받았으나 본문을 해석하지 못한 실패로 전달한다. |
| 500 응답을 받았고 오류 본문도 깨져 있음 | 본문 파싱 오류만 전달하면 원래 HTTP 500이 사라짐 | HTTP 실패 상태를 보존하고, 본문 해석에도 실패했다는 근거를 함께 남긴다. |
| HTTP 오류 본문이 유효한 JSON `null`임 | `body.message` 접근이 새 TypeError를 만들면 원래 HTTP 실패가 가려짐 | 본문에 오류 필드가 없어도 확보한 상태로 오류를 전달할 수 있어야 한다. |
| 본문을 읽는 중 내부 timeout으로 중단됨 | 일반 파싱 오류로 바꾸면 시간 제한 때문에 끝났다는 뜻이 사라짐 | 시간 초과를 본문 해석 실패와 구별하고 이미 받은 응답 정보는 가능한 범위에서 보존한다. |

이 구분은 호출자가 모든 경우에 서로 다른 UI를 보여야 한다는 뜻이 아니다. 같은 오류 안내를 쓰더라도 진단에 필요한 원인과 HTTP 상태를 잃지 않을 수 있다. 구체적인 오류 코드나 클래스 체계는 이 사례가 정하지 않는다.

### 타이머는 어디까지의 시간을 제한하는가

본문이 필요한 호출에서 헤더를 받았다는 사실만으로 요청 도구의 일이 끝난 것은 아니다. 예를 들어 헤더는 1초 안에 도착했지만 본문 전송이 10초를 넘기는 상황을 가정하자. 헤더 수신 직후 타이머를 지우면 본문을 기다리는 동안 기존 10초 제한이 더 이상 작동하지 않는다.

요청부터 본문 처리 종료까지 타이머를 소유하려면 성공·실패 모두 그 경계를 지난 뒤 정리해야 한다. 아래는 **정리 시점만 보여 주는 설명용 코드**다. 오류 분류·HTTP 상태 보존은 생략했으므로 완성된 fetcher 수정안은 아니다.

```ts
try {
  const response = await fetch(url, requestOptions);
  return await handleResponse(response);
} finally {
  clearTimeout(timer);
}
```

이 코드에서 `await`를 빼면 `finally`는 본문 Promise의 완료를 기다리지 않고 실행된다. 같은 `finally`가 있어도 정리 시점이 달라진다. 반대로 타이머를 유지했더라도, 본문 읽기를 중단한 오류를 무조건 파싱 실패로 바꾸면 시간 초과의 의미가 손상된다. 정리 시점과 오류 분류를 함께 확인해야 하는 이유다. 이 타이머는 동기식 JSON 파싱을 실행 중간에 강제로 멈추는 장치까지 제공하지 않는다.

### 이 작업에서 유지하고 고칠 범위

오류 계약 정비라는 목표에서 보면 정상 호출 API와 제품별 후속 처리를 크게 바꿀 이유는 없다. 동시에 작은 도구라는 이유로 공통 오류 변환을 빠져나오는 경로를 남겨 둘 수도 없다.

| 범위 | 이 사례에서의 판단 | 판단을 가르는 이유 |
| --- | --- | --- |
| 기존 호출과 정상 결과 | get/post/put/delete, JSON·문자열 반환, 기본 URL·헤더·10초 제한, 하나의 fetcher와 APIError 구조를 유지한다. | 지금의 요청 기능을 제공할 수 있고, 문제는 오류 전달과 정리 경계에 있다. |
| 실패 전달과 정리 | 비동기 본문 실패의 전달, 요청·본문 실패의 구별, HTTP 상태 보존, 예상 밖 오류 본문의 처리, timer 정리를 함께 고친다. | 모두 이번에 신뢰할 수 있게 만들려는 공통 계약에 직접 영향을 준다. |
| 새로운 공통 기능 | 자동 재시도·인증 이동·공통 토스트·모든 응답 스키마 검증·대규모 오류 계층 도입은 별도 요구로 판단한다. | 이 기능을 추가하지 않아도 앞의 계약 빈틈은 고칠 수 있다. 상품 가공·페이지 규칙·화면 대응도 현재 사용처의 책임이다. |
| 호출자 취소 | 외부 signal이 내부 controller의 signal로 덮이는 제한은 별도로 다룬다. | 내부 timeout 정리와 호출자 취소 지원은 다른 계약이다. 호출자 취소가 요구되는 작업이라면 입력·중단·오류 의미까지 포함해 범위를 다시 정한다. |

이 표는 가정한 작업의 판단안이다. 실제 변경·검증이 끝난 상태를 나타내지 않는다. 적용한다면 정상 JSON·문자열, 정상 오류 본문의 status·code, 200/500의 깨진 JSON, `null` 오류 본문, 본문 읽기 중 timeout, 성공·실패 뒤 timer 정리를 확인한다. 지금 사용처가 어떤 오류 정보를 소비하는지도 함께 대조해야 새 표현으로 바꾸면서 호환을 깨뜨리지 않는다.

### 등록 처리기와 silent의 적용 순서

오류 의미를 전달한 뒤 공통 서비스가 화면 대응까지 맡으면, 사용처 옵션이 어느 처리에 적용되는지도 계약이 된다. 비교한 별도 앱의 오류 서비스는 등록 처리기를 먼저 실행하고, 해당 처리기를 쓰지 않을 때 toast·dialog·silent 등의 대체 동작을 적용했다. 핵심 순서는 다음과 같다.

```ts
if (!bypassRegisteredHandlers && error instanceof AppError) {
  const handler = this.registeredHandlers.get(error.constructor as AppErrorConstructor);
  if (handler) {
    handler(error);
    return;
  }
}
if (errorFallbackOptions.type) {
  this.displayUI(error, errorFallbackOptions);
} else {
  throw error;
}
```

ErrorBoundary는 `type: 'silent'`를 전달했고 등록 처리기를 우회하는 인자는 전달하지 않았다. 이 호출을 위 코드에 대입하면 다음 결과가 나온다.

| 전달된 오류 | 실행 경로 | `silent`에서 기대할 수 있는 범위 |
| --- | --- | --- |
| 등록 처리기가 있는 AuthError | 등록 처리기가 인증 안내 토스트와 `/user` 이동을 실행한 뒤 반환 | 뒤의 대체 표시가 실행되지 않으므로 `silent`가 이 효과를 억제하지 않는다. |
| 등록 처리기가 있는 NetworkError | 등록 처리기가 네트워크 토스트를 실행한 뒤 반환 | 이 토스트도 `silent` 분기 전에 실행된다. |
| 적용할 등록 처리기가 없는 오류 | 대체 표시에서 `silent`를 적용 | 대체 UI 표시는 생략하지만, 그것이 서비스의 모든 처리를 생략한다는 뜻은 아니다. |

공통 인증·네트워크 대응을 유지하고 대체 표시만 생략하려는 호출이라면 이 순서가 맞을 수 있다. ErrorBoundary에서 모든 토스트와 이동을 막아야 한다면 이 옵션만으로는 요구를 충족하지 못한다. 이미 있는 우회 경로를 사용할지, 옵션의 범위나 공통 정책을 바꿀지는 그 요구와 다른 사용처의 의존을 보고 고른다. 로컬 옵션을 항상 먼저 적용하는 정책은 여기서 정하지 않는다.

`silent`를 더 구체적인 이름으로 바꾸면 이 순서를 설명하는 데 도움이 될 수 있다. 그러나 모든 표시 억제가 필요한 상황에서 이름만 바꿔도 결과는 그대로다. 표현의 문제와 제공할 동작의 선택을 구별해야 한다.

## Toast의 표시 수명과 데이터 만료

**알림의 3초는 언제부터인가?** 아래와 같은 호출을 받아도 타이머의 위치에 따라 답이 달라진다.

```ts
addToast({ title, description, duration: 3000 });
```

확인한 구현에서 store는 알림 목록·ID 생성·추가·삭제를 맡고 타이머는 만들지 않았다. 목록을 표시하는 `ToastItem`의 effect가 `duration` 뒤 삭제를 예약했다. 아래는 이 관계를 보여 주는 설명용 축약 코드다.

```ts
useEffect(() => {
  const timer = setTimeout(() => removeToast(id), duration);
  return () => clearTimeout(timer);
}, [id, duration, removeToast]);
```

정리는 타이머만 취소하므로 표시 컴포넌트가 사라져도 목록의 항목은 남을 수 있다. 이에 대비하는 설명용 대안은 `addToast`가 타이머를 만들고 store가 ID별로 관리하는 방식이다. 이 대안의 `removeToast`는 타이머 취소·관리 목록 제거·알림 삭제를 함께 맡는다. 제품에 적용한 대안은 아니다.

| 조건 | 확인한 ToastItem 방식 | 설명용 store 대안 |
| --- | --- | --- |
| 3초의 시작 | 항목의 effect가 시작된 시점 | addToast가 호출된 시점 |
| 표시 컴포넌트가 없음 | 목록은 추가되지만 표시·타이머가 시작되지 않음 | 표시되지 않은 항목도 만료됨 |
| 만료 전에 표시 컴포넌트가 사라짐 | 타이머는 취소되고 항목은 남음 | 같은 앱 실행 안에서 타이머가 계속됨 |
| 다시 표시함 | 남은 항목의 타이머를 새 duration으로 시작 | 아직 만료되지 않은 항목만 남음 |
| 수동 삭제 | 목록 삭제와 표시 해제에 따른 effect 정리가 연결됨 | removeToast가 타이머와 목록의 정리를 함께 수행해야 함 |

차이를 시간에 대입해 보자. 0초에 알림이 추가되고 표시됐고, 1초에 표시 컴포넌트가 사라졌다가 2초에 다시 나타난다고 가정한다. ToastItem 방식은 처음 예약을 취소한 뒤 새 3초를 주므로 제거 예정 시점이 5초로 바뀐다. store 대안은 처음 예약을 유지하므로 3초에 제거할 예정이다. 두 방식 모두 같은 `duration: 3000`을 받지만 다른 수명을 제공한다. 이 숫자는 타이머 지연이 없다는 설명용 시간 비교이며 권장 기본값이나 실제 측정값이 아니다.

표시 컴포넌트를 앱 공통 위치에 하나 두고 안정적으로 유지하며, 렌더링된 항목에 새 표시 시간을 주려는 요구라면 현재 방식이 단순하고 맞을 수 있다. 반면 화면이 사라져도 추가 시점부터 만료되어야 한다면 store가 타이머를 소유할 이유가 생긴다. 표시 전에 만료되어 사용자가 알림을 보지 못할 수 있다는 결과도 그 선택에 포함된다.

어느 방식도 숨겨진 탭을 제외한 실제 가시 시간을 정밀하게 누적하지 않는다. store 대안 역시 브라우저 종료를 넘는 영속 만료를 제공하지 않으며, 여러 Toast가 같은 목록을 중복 표시하는 문제는 타이머를 옮겨도 남는다. 전체 초기화·store 폐기를 제공한다면 남은 타이머도 그 경로에서 정리해야 한다.

따라서 타이머 이전은 호출 문법이 같은 내부 정리로만 다룰 수 없다. 선택할 것은 표시 시작과 추가 시점 중 어떤 수명을 약속할지다. 이 사례에서는 이전을 결정하지 않았으며, 현재 방식의 적합성도 실제 배치·화면 전환 조건과 비교해 판단한다. 일반 호출자는 공개한 `duration` 의미를, 표시 컴포넌트를 배치하는 쪽은 그 수명 조건을 알아야 한다.

## 이벤트 Hook의 입력 조건과 지원 범위

### null을 만나면 멈출 것인가, 그 영역만 건너뛸 것인가

Dropdown은 메뉴를 Portal에 표시하므로 메뉴와 root를 함께 내부 영역으로 전달했다. 닫는 동작은 Dropdown이 정하고, Hook은 document의 mousedown·touchstart 연결과 해제, 영역 포함 판별을 맡았다.

```ts
useClickOutsideEffect([menuElement, rootRef.current], () => setIsOpen(false));
```

확인한 Hook은 **대상 하나라도 `null`이면 그 이벤트의 판별 전체를 중단**했다. 아래는 이 분기를 DOM 요소 배열 기준으로 줄인 설명용 코드다. 실제 Hook이 처리하는 RefObject 입력은 생략했다.

```ts
// 확인한 분기: 모든 대상이 준비됐을 때만 바깥 입력을 판별한다.
for (const element of elements) {
  if (!element) return;
  if (element.contains(event.target as Node)) return;
}
handler(event);
```

`null`인 항목만 건너뛰려면 첫 `return`을 `continue`로 바꾸는 식의 대안이 가능하다. 짧은 변경이지만 ‘아직 판별하지 않음’을 ‘존재하는 영역을 기준으로 판별함’으로 바꾼다. root는 준비됐다고 가정하고 같은 입력을 비교하면 차이가 보인다.

| 입력 조건 | 현재의 전체 판별 중단 | 준비된 영역만 판별하는 대안 |
| --- | --- | --- |
| 메뉴와 root가 있고 메뉴 안을 누름 | handler를 호출하지 않음 | handler를 호출하지 않음 |
| 메뉴와 root가 있고 두 영역 밖을 누름 | handler를 호출함 | handler를 호출함 |
| 메뉴는 null이고 root 안을 누름 | 준비되지 않았으므로 판별하지 않음 | root 내부이므로 handler를 호출하지 않음 |
| 메뉴는 null이고 root 밖을 누름 | 준비되지 않았으므로 판별하지 않음 | 존재하는 영역 밖이므로 handler를 호출함 |

현재 Dropdown은 닫힌 동안 메뉴를 렌더링하지 않아 `menuElement`가 null일 수 있다. Hook에는 `isOpen`이나 `enabled` 인자가 없고 배열이 비어 있지 않으면 리스너를 연결하므로, 이 null 분기는 닫힌 동안의 판별 생략에도 영향을 준다. 이때 대안은 이미 닫힌 상태에서도 `setIsOpen(false)`를 호출할 수 있다. 그것이 실제 화면 결함이나 성능 문제였다는 실행 근거는 없다.

반대로 열린 UI에 선택적으로 존재하는 두 번째 영역을 전달하는 상황을 가정하면, 그 영역의 부재 때문에 전체 바깥 클릭 판별을 멈추는 것은 요구와 맞지 않을 수 있다. 핵심은 null이 필수 영역의 준비 전 상태인지, 있어도 없어도 되는 영역의 부재인지다. 관찰한 코드만으로 과거 의도를 확정할 수는 없으며, 이 비교만으로 null 정책 변경이나 새 활성화 옵션을 선택하지 않는다.

### Dropdown 위치를 계산하는 범위와 그 안의 정확성

연결된 위치 Hook은 실제 trigger·menu DOM과 `isOpen`을 받아 좌표를 계산했다. Menu는 열린 때만 Portal에 렌더링하고 반환된 스타일을 적용했다. Hook의 실행 조건과 이벤트 수명을 줄이면 다음과 같다. 리스너 정리는 실제 코드에서 확인한 흐름이며 아래 표현은 설명용으로 단순화했다.

```ts
if (!isOpen || !triggerElement || !menuElement) return;

calculatePosition();
window.addEventListener('resize', calculatePosition);
window.addEventListener('scroll', calculatePosition, true);
return () => {
  window.removeEventListener('resize', calculatePosition);
  window.removeEventListener('scroll', calculatePosition, true);
};
```

계산은 기본 아래 배치, 아래 공간이 부족하면 위 배치, 버튼 왼쪽 정렬과 최소 너비를 제공한다. 버튼의 viewport 좌표에 scrollX/Y를 더해 문서 기준의 absolute 좌표를 만들기 때문에, 호출하는 쪽은 그 좌표가 맞는 Portal·배치 환경에 스타일을 적용해야 한다. Hook의 `isOpen=false`가 DOM을 숨기는 것은 아니다. 표시 여부는 Menu의 조건부 렌더링이 맡는다.

이벤트 수명과 위치 계산이 한 Hook에 있다는 사실만으로 분리가 필요하지는 않다. 같은 위치 기능을 위해 함께 바뀌는 코드이며, 직접 사용처가 맡아야 할 DOM·열림 상태·스타일 적용과 Hook이 맡는 계산·재계산·정리가 구별된다.

| 조건이 달라지는 장면 | 확인한 구현의 범위 | 검토할 차이 |
| --- | --- | --- |
| 창 크기나 스크롤이 바뀜 | resize·scroll에서 재계산하고 cleanup에서 리스너 해제 | 현재 지원하는 동작이므로 변경 뒤에도 계산과 정리가 이어져야 한다. |
| 열린 메뉴의 동일 DOM에서 내용만 늘어남 | 그 높이 변화 자체를 감지하는 ResizeObserver는 없음 | 실제 Dropdown 요구에서 위치가 어긋난다면 현재 기능 안의 정확성 문제로 다룬다. 이 사례가 화면 결함을 재현한 것은 아니다. |
| Portal을 없애고 positioned 부모 안으로 옮김 | 문서 기준 좌표를 그대로 반환 | 좌표 기준과 적용 환경이 달라지므로 같은 스타일을 그대로 사용할 수 있다고 가정하지 않는다. |
| 툴팁·팝오버의 수평 넘침, 위아래 모두 좁은 배치까지 요구함 | 모든 방향의 넘침을 푸는 일반 배치 엔진은 아님 | 새 지원 범위에 맞춰 계약과 구현을 확장할지 판단한다. 기존 Dropdown의 결함으로 자동 판정하지 않는다. |

현재 목적에 필요한 정확성과 새로운 사용처를 지원하는 확장은 이렇게 구별할 수 있다. 범위가 작다는 사실은 유지할 이유가 될 수 있지만, 그 범위 안에서 필요한 동작까지 생략할 이유는 되지 않는다.
