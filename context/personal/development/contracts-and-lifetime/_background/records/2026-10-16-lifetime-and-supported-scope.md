# 시간의 시작점과 지원 범위를 구별한 논의

[계약·수명 본문](../../INDEX.md)의 Toast·이벤트 Hook 판단을 형성한 과정을 보존한다. 2026-10-16 작성 기록을 2026-10-20에 대조했다. 발췌는 [Toast 근거](../evidence.md#toast의-수명)와 [Hook 회고](../evidence.md#null과-지원-범위의-회고)에 둔다.

## Toast의 두 시간 기준

실제 Storybook 호출과 구현을 읽으니 일반 호출부는 알림과 duration을 주고 store는 목록을, 표시 컴포넌트는 삭제 타이머를 소유했다. 표시가 없으면 타이머가 시작하지 않았고 unmount에서는 timer만 취소됐다.

사용자는 같은 호출을 두고 표시 컴포넌트 방식과 store 타이머 대안을 비교해 달라고 요청했다. 전자는 표시 effect 시작부터의 시간, 후자는 추가부터의 만료를 제공했다. 호출 모양은 같아도 시간의 시작·종료 조건이 바뀌므로 단순한 코드 이동이 아니었다.

사용자는 원하는 수명에 따라 판단하며 현재 방식도 목적에 맞으면 유지할 수 있다고 확인했다. store 이전은 선택하지 않았다. 실제 가시 시간 측정, 브라우저 종료를 넘는 만료, 여러 표시 컴포넌트의 중복 문제까지 해결한 것으로 보지 않았다. 일반 호출자의 공개 계약과 앱 통합부의 배치·수명 지식을 구별한 판단도 남겼다.

## null과 지원 범위의 회고

외부 입력 Hook은 대상 하나가 null이면 전체 판별을 중단했다. 준비된 대상만 검사하는 대안과 비교하자 사용자는 모든 대상이 준비된 뒤 동작한다는 의도였던 것 같다고 회고하면서 다른 대안도 가능한 선택으로 봤다. null 정책 변경이나 enabled 옵션 추가는 선택하지 않았다.

위치 Hook의 실제 호출·계산·이벤트 정리를 읽은 뒤에는 Dropdown·MultiSelect 정도를 생각했던 것 같다는 회고가 있었다. 일반 툴팁·팝오버의 모든 배치를 지원하지 않는다는 관찰을 곧바로 결함으로 보지 않는 이유가 됐다.

이 회고는 과거 요구 전체의 복원이 아니다. 현재 Dropdown의 실제 요구 안에서 틀린 위치가 생긴다면 별도의 정확성 문제로 보아야 한다는 적용 조건은 남겼다. 내용 변화 감지·다른 Portal 배치·새 UI 유형이 요구되면 입력과 좌표·재계산·정리 계약을 다시 판단한다. 당시 제품 실행·성능 측정·구현 변경은 없었다.
