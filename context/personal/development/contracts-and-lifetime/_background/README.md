# 계약과 수명의 형성 자료

이 폴더는 [계약·수명 본문](../INDEX.md)을 만든 목적과 배경, 오류·시간·지원 범위를 판단한 논의와 선택, 필요한 원문·관찰을 보존한다. 현재 내용이 왜 남았는지 이해하고 수정·재검토할 때 사용한다. 현재 적용할 기준과 사례는 [주제 안내](../README.md)에서 찾는다.

| 확인하려는 것 | 읽을 범위 |
| --- | --- |
| 왜 공통 오류 타입뿐 아니라 의미와 처리 순서를 보는가 | [형성 맥락](context.md#사용처가-믿을-계약에서-출발함), [오류 비교·판단 기록](records/2026-10-16-error-contract-and-review.md), 직접 동의와 관찰은 [오류 근거](evidence.md#공통-오류의-형태와-의미) |
| 작은 fetcher를 유지하면서 오류·타이머를 고치려 한 이유는 무엇인가 | [수정 범위의 이유](context.md#작은-구조의-유지와-책임의-빈틈-수정을-함께-판단함), [당시 판단과 수용](records/2026-10-16-error-contract-and-review.md#유지수정보류-판단의-수용), [수용 범위](evidence.md#fetcher-판단의-수용) |
| 왜 Toast 타이머를 store로 옮기는 것을 필수 개선으로 보지 않는가 | [수명의 현재 설명](context.md#같은-호출이어도-시간의-뜻은-달라질-수-있음), [수명 비교 기록](records/2026-10-16-lifetime-and-supported-scope.md#toast의-두-시간-기준), [사용자 판단](evidence.md#toast의-수명) |
| null 처리와 새 UI 지원을 왜 무조건 고치지 않는가 | [범위의 구별](context.md#회고한-지원-범위와-그-안의-정확성), [Hook 논의 기록](records/2026-10-16-lifetime-and-supported-scope.md#null과-지원-범위의-회고), [회고 원문](evidence.md#null과-지원-범위의-회고) |
| 실제 실행한 결과와 확인하지 못한 것은 무엇인가 | [근거의 한계와 열린 판단](context.md#근거의-한계와-열린-판단) |

context는 현재 이유를, records는 당시 조건·대안·선택을, evidence는 발화·관찰·출처를 맡는다. 미선택 대안과 당시 표현을 현재 요구로 적용하지 않는다. 책임과 조건별 적용의 공통 배경은 [개발 공통 형성 자료](../../_background/README.md)에 연결한다.

2026-10-20에 접근 가능한 작성 기록을 직접 읽어 구성했다. 실제 제품 실행이나 원래 코드 전체의 현재 상태를 확인한 자료는 아니다. 구성·보존·갱신은 [공통 관리 원칙](../../../../CONTENT-POLICY.md)을 따른다.

- [조건부 기준의 통합](records/2026-10-23-conditional-criteria.md): 개발 workflow 합의에서 기존 Personal 본문으로 이어진 보완과 경계.
