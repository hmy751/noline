# 값은 뜻과 원천을 정하고 쓴다

**언제 쓰나:** 색·글자·간격·radius·shadow·겹침 순서를 정하거나 고칠 때, 토큰을 추가하거나 이름을 바꿀 때, class를 쓸 수 없는 경로로 값을 넘길 때.

**핵심 규칙:** 토큰의 가치는 이름을 맞추는 데 있지 않고 **값을 바꿀 때 무엇이 함께 바뀌어야 하는지를 정하는 데** 있다. 앱에 있는 값을 먼저 쓰고, 없는 값은 새 뜻이 있는지 판단한다.

시작 본문은 [UI 결정을 맡을 책임에 두고 쌓는다](INDEX.md)다. 토큰은 여러 프로젝트를 건너 계속 가져간 구조다. 웹의 CSS 변수에서 같은 이름 집합을 유지했고, 모바일 앱에서는 역할 theme로 바꿔 이어졌다.

## 값의 종류를 구별해 쓴다

| 값의 종류 | 예 | 쓰는 판단 |
| --- | --- | --- |
| Palette | `gray-200` | 원재료다. 역할이 없을 때 쓴다. 쓰임이 반복되면 역할을 붙일지 본다. |
| 역할 | `primary`, `text-secondary`, `error`, `z-dialog` | 화면과 부품은 뜻이 같으면 역할을 쓴다. 함께 바뀌어야 할 쓰임을 묶는다. |
| 크기 | `space-4`, `font-lg` | 간격과 글자의 단계를 맞춘다. 부품의 상호작용 규격까지 모두 토큰으로 만들 필요는 없다. |

## 역할 이름은 값을 바꿔도 뜻이 유지되는지 확인한다

역할처럼 보이는 이름도 사용처가 특정 색감에 묶여 있을 수 있다. 테마를 바꿀 때 변수 몇 줄과 일부 CSS를 고치고 다음 날 variant 사용을 다시 조정한 경험이 있다. `secondary`가 진한 색에서 밝은 색으로 바뀌었는데 흰 글자가 남아 대비가 낮아 보이는 것은 화면이 아니라 코드로 읽은 판단이다.

- **값을 바꿀 때:** 그 토큰의 사용처에서 함께 쓰는 글자색과 대비가 그대로 맞는지 본다.
- **이름을 지을 때:** `gray-very-light`처럼 모양을 묘사하거나 `#333`처럼 값 자체를 키로 쓰면 뜻을 담지 못한다. 쓰임이 정해진 값은 역할로 묶는다.
- **변경이 예상되지 않을 때:** 작은 제품에서 모든 값을 역할로 올릴 필요는 없다. 변경할 일이 생기면 그때 묶어도 된다.

**미정:** 이름 체계(`space-4`, t-shirt 크기 등)는 Project가 정한다. hover를 별도 색으로 둘지 filter로 처리할지도 양쪽 방식을 다 써 봤고 일반 기준은 없다.

## 값이 흩어지는 영역은 원천을 만든다

- **겹침 순서:** 값을 올려 가며 해결하면 체계 없는 값이 쌓인다. 값이 수십 개 쌓인 코드와 header·overlay·dialog·toast 역할로 정리한 코드를 모두 겪었다. 겹침 순서는 역할 토큰으로 두고, 근본 해결은 [떠 있는 표면](INDEX.overlays.md)에서 찾는다.
- **간격:** 토큰이 없어도 값은 몇 개로 몰린다. 이름 없는 단계가 이미 있다면 토큰으로 정리하기 쉽다.
- **빠진 역할:** 경고색 토큰이 없으면 같은 안내에 팔레트 색이 반복된다. 같은 쓰임이 반복되면 역할을 더할지 본다.
- **shadow와 radius:** 토큰이 있으면 부품과 화면에서 그것을 쓴다. 플랫폼 때문에 style로 넣어야 하면 값의 원천을 맞춘다.
- **쓰지 않는 토큰:** 쓰임이 없는 breakpoint, dark 값, z-index는 있다고 작동한다는 뜻이 아니다. 사용처를 확인하고 쓴다.

## 앱의 값을 먼저 지키고 새 값은 테마에 더한다

1. 기존 역할이 맞는 자리면 그 토큰을 쓴다. 비슷한 값을 새로 만들지 않는다.
2. 일부러 다른 값을 고른 이유가 있으면 쓸 수 있다. 그 이유를 결과에 밝힌다.
3. 새 값이 필요하면 테마에 더하고 어떤 역할인지 정한다.
4. 애매하면 사용자에게 묻는다.

아주 단순한 사이드 프로젝트처럼 테마가 없으면 색을 바로 쓸 수 있다. 문제는 테마가 있는데 확인조차 하지 않는 것이다.

스타일 방식이 섞여 있어도 이번 앱의 기본 방식(className, StyleSheet 등)을 따른다. 같은 앱에서 화면마다 다른 방식으로 값을 정하면 토큰을 바꿔도 함께 바뀌지 않는다.

## class를 쓸 수 없는 경로도 같은 원천에서 가져온다

**신호:** 아이콘 색을 hex로 넘기거나, 버튼 글자색을 부품의 맵에 다시 적는다. 값 옆 주석에 토큰 이름이 있다.

**할 일:** 플랫폼이 값을 명시하게 요구하는 일과 값을 새로 소유하는 일을 구별한다. theme 값을 코드에서 읽어 쓸 수 있는지 본다. [값 이중 소유 사례](INDEX.cases.md#같은-색을-두-곳이-소유하면)에 선택 조건이 있다.

## 틀린 토큰은 드러나지 않을 수 있으니 쓴 사람이 확인한다

여러 프로젝트에서 같은 일이 있었다. 이름을 바꾼 뒤 남은 CSS 변수, 테마에 없는 글자 class, `View`에 준 글자 class는 오류 없이 무시될 수 있다.

- **토큰 이름을 쓰면:** 정의돼 있는지 찾아본다. 비슷한 앱에서 본 이름을 그대로 쓰지 않는다.
- **이름을 바꾸면:** 옛 이름의 사용처를 함께 찾는다.
- **class 병합 함수를 쓰면:** 커스텀 토큰이 지워지거나 양쪽이 모두 남는지 실행해서 확인한다. `twMerge`는 설정 없이 커스텀 글자 크기 class와 글자색 class를 같은 그룹으로 보고 하나를 지운 경우가 있었다.

**미정:** 토큰을 점검하는 lint의 도입 여부는 Project가 정한다. 조사할 때 확인한 프로젝트에서는 찾지 못했다. 이후 Noline에 직접 쓴 색을 경고로 넣었으나 효과는 아직 확인하지 못했다.
