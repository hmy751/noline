# UI 결정을 맡을 책임에 두고 쌓는다

**언제 쓰나:** 화면·폼·목록·떠 있는 메뉴를 만들 때, 위치·간격·겹침·색·상태 표시 문제를 고칠 때, 공통 부품이나 토큰을 추가·변경할 때.

**핵심 규칙:** 코드를 쓰기 전에 앱에 이미 있는 값·배치·부품·조합을 찾는다. 있으면 쓰고, 맞지 않으면 고칠지 이번에만 벗어날지를 이유와 함께 정한다. 없으면 그 결정이 어느 책임에 있어야 하는지 정해 그 자리에 둔다. 중심 질문은 **이 UI 결정은 어느 책임에 있어야 하는가**다.

**이 문서의 성격:** 정답의 원천이 아니라 사용자의 생각과 지식을 최대한 담은 것이다. 모든 상황에 대응하지 못한다. 이 문서를 확인해도 애매하면 사용자에게 묻는다.

**범위:** 프론트 구현에서 UI를 쌓는 판단을 다룬다. 브랜드, 디자인 도구의 자산, 조직 운영은 다루지 않는다. 금지 목록이 아니다. absolute, 고정 숫자, z-index는 쓸 수 있는 수단이고, 볼 것은 그 결정이 맞는 자리에 있는지다. 예시의 이름과 코드 모양은 의무가 아니다. 실제 토큰·컴포넌트와 제품별 규약은 Project가 소유한다.

**지위 표시:** 표시가 없는 규칙은 여러 프로젝트의 구조와 직접 고친 경험에서 일반화한 판단이다. **미정**은 판단을 정하지 않은 것, **목표**는 지향하지만 충분히 해 보지 않은 것, **외부 참고**는 외부 자료의 권고다. 미정과 목표를 사용자 기준처럼 말하지 않는다.

## 책임 지도로 결정의 자리를 찾는다

위아래 계단이 아니라 책임별 의존 관계다. 값은 다른 UI에 의존하지 않고, 배치·기본 부품·떠 있는 동작은 필요한 것을 서로 조립하며, 조합과 앱 연결이 그것을 사용한다. 모든 Project가 일곱 책임을 별도 단위로 갖출 필요는 없다. 새 결정을 둘 자리를 찾을 때 쓴다.

| 책임 | 맡는 결정 | 몰라야 할 것 | UI 템플릿의 대응 |
| --- | --- | --- | --- |
| 값과 기본 환경 | 색·글자·간격·겹침 순서의 역할과 원천 | 화면, API, 열림 상태 | `variables.css`, reset |
| 배치 규칙 | 자식 사이의 간격·흐름·컬럼 | 항목 데이터, 카드 내부 | Grid |
| 기본 표현·입력 | 부품 내부의 모양과 단일 상호작용 | 제출 API, 바깥 여백, 업무 기본값 | Text, Button, Input, Checkbox, Spinner |
| 떠 있는 동작 기반 | 렌더 표면, 측정, 실제 좌표, 바깥 닫기 | 업무 의미, 특정 헤더 높이 | Portal, `useFloatingPosition`, `useClickOutsideEffect` |
| 선택·대화 상호작용 | 트리거·내용·열림 상태의 결합 | 서버·전역 업무 상태 | Dropdown, MultiSelect, Dialog |
| 시각·입력 조합 | 역할 사이의 관계와 사용 장면 | 데이터 취득, 저장 정책 | Field, Card, FormSection 스토리 |
| 상태 연결과 앱 표면 | store·폼·요청 상태의 연결, 앱 공통 화면 틀 | 아래 부품이 이 정책을 역으로 알지 않게 한다 | Toast의 store 구독, 폼 연결, 무한 스크롤 Container |

## 앱에 있는 체계를 먼저 찾고 벗어나면 이유를 남긴다

새 UI를 쓰기 전에 Project 지침과 실제 사용 예에서 다음을 찾는다.

- **값:** 색·글자·간격·radius 토큰과 그것을 쓰는 방식(className, style, theme 객체)
- **배치:** 공통 배치 단위와 화면 틀(앱 헤더, 안전 영역, 스크롤 컨테이너)
- **부품과 조합:** 입력·버튼·메뉴와, 제목·입력·오류를 묶는 Field 같은 조합
- **상태 표현:** 앱이 로딩·오류·빈 상태를 보여 주는 방식

| 찾은 결과 | 할 일 |
| --- | --- |
| 맞는 것이 있다 | 그대로 쓴다. 같은 앱의 새 화면이 한 앱처럼 보이고, 값을 바꿀 위치가 늘지 않는다. |
| 있지만 이번 요구에 모자란다 | 공통 쪽을 넓힐지, 이번 화면에서만 벗어날지 비교한다. 벗어나면 무엇이 모자랐는지 결과 보고에 적는다. |
| 없다 | 책임 지도에서 어디에 둘지 정한다. 한 화면에서만 쓰면 그 화면에 둘 수 있다. 파일 위치보다 다음 변경을 어디서 감당하는지 확인한다. |
| 있는 것이 어울리지 않는 특수 화면이다 | 이유를 밝히고 다르게 만든다. |

**옆 화면의 코드는 참고하되 선례로 단정하지 않는다.** 기존 코드에는 개발 중 놓친 것도 있다. 공통 부품과 옆 화면이 어긋나면 코드가 많은 쪽이 아니라 같은 모양과 책임인지 본다.

| 찾은 상황 | 할 일 |
| --- | --- |
| 공통과 같은 모양을 손으로 썼다 | 공통을 쓴다. 옆 화면을 따르지 않는다. |
| 공통으로 안 되는 실제 차이가 있다 | 다르게 만들고 이유를 말한다. |
| 같은 요구인데 공통이 모자라 여러 곳이 비켜 간다 | 공통이 틀린 신호로 보고, 아래 절의 기준으로 고칠지 정한다. |

기존 화면까지 옮길지는 새 화면과 따로 아래 절의 기준으로 정한다.

## 공통 부품은 이유를 댈 수 있을 때 고치고 애매하면 묻는다

공통 부품의 결함을 발견했거나 공통에 새 옵션이 필요해 보이면, 조용히 우회하지도 이유 없이 공통을 키우지도 않는다. 상황마다 답이 달라 정답을 고정하지 않는다. 대신 **이 변경을 공통에 둘 이유를 실제 코드로 말할 수 있는지** 변경마다 확인한다.

| 볼 것 | 공통에 둘 이유 | 이유가 아닌 것 |
| --- | --- | --- |
| 사용처 | 같은 결함이나 요구가 있는 사용처를 지금 코드에서 이름으로 댈 수 있다. 범용 부품의 API라면 잘 만든 라이브러리가 같은 선택을 제공하는 것도 이유가 된다. | 근거 없이 앞으로 쓸지 모른다. 코드 모양이 비슷하다. |
| 책임 | 특정 화면과 업무를 몰라도 설명되는 결정이다. 측정과 실제 좌표가 그 예다. | 이 화면의 구조나 업무에서만 나온 옵션이다. 그럴 때는 화면 구조를 먼저 의심하고, 필요하면 기능에 둔다. |
| 변경 범위 | 이 결함을 고치는 데 필요한 변경이다. | 함께 넣은 모양 변경의 이유를 따로 말하지 못한다. 이유가 없으면 뺀다. |

이유가 있어도 호출부 수만으로 정하지 않는다. AI가 코드를 옮길 수 있으므로 고칠 곳이 많다는 것 자체는 안 바꾸는 이유가 아니다. 대신 **얻는 이득과 사람이 다시 봐야 할 양을 견준다.** 사람이 봐야 할 양은 코드를 고치지 않은 사용처까지 포함해 달라지는 동작 중 테스트로 잡지 못하는 부분이다.

| | 볼 양이 적다 | 볼 양이 많다 |
| --- | --- | --- |
| **이득이 크다** | 바꾼다. | 단계로 나눠 바꾼다. |
| **이득이 작다** | 바꿔도 된다. | 공통은 두고 사용처에서 해결한 뒤 보고한다. |

**애매하면 먼저 레퍼런스를 보고, 그래도 갈리면 사용자에게 묻는다.** 부품의 API나 책임이 애매하면 책임 분리와 디자인 자유도가 잘 고려된 라이브러리(Radix 등)가 같은 문제를 어떻게 풀었는지 본다. 앱의 제약까지 같다고 단정하지는 않는다. 이득과 볼 양이 비슷해 결론이 갈릴 때, 달라지는 동작을 확인할 수 없을 때, 되돌리기 어렵거나 다른 화면의 의미가 달라질 때는 묻는다.

바꾸기로 했다면 이 순서로 진행한다.

1. 이번 화면처럼 한 곳에서 먼저 확인한다.
2. 나머지 사용처를 옮기고 실제 화면으로 확인한다.
3. 다 옮기지 못하면 옛 방식이 남은 곳과 이유를 보고한다. 두 방식을 말없이 남기지 않는다.

결과 보고에는 항상 선택한 이유, 달라지는 사용처, 실제로 확인한 범위를 적는다.

관련 개선의 범위를 넓힐지는 [이번 수정과 직접 관련된 개선](../shared-boundaries/INDEX.md#이번-수정과-직접-관련된-개선은-이득과-보존-비용으로-판단한다) 기준을 함께 쓴다. [메뉴 위치 사례](INDEX.cases.md#메뉴의-위치를-누가-아는가)가 이 선택을 비교한다.

## AI 작업에서 자주 나타나는 어긋남을 피한다

같은 앱에 새 화면 세 개를 맡긴 시험에서 금지하려던 absolute 덧대기는 나오지 않았고, 다른 모습의 덧대기가 나왔다. 표본은 작업당 한 번이라 경향의 단서로만 본다.

- 앱의 토큰과 스타일 방식을 확인하지 않고 그 자리에서 색·글자 크기·간격을 새로 정한다.
- 앱의 입력 부품이 있는데 raw 입력을 다시 꾸민다.
- 조합 부품이 있는데 제목과 오류를 손으로 반복한다.
- 정의되지 않은 토큰 이름을 쓴다.
- 안전 영역 같은 보장을 담은 앱의 헤더를 쓰지 않아 화면마다 다른 앱처럼 보인다.
- 좋은 해결을 기능 폴더에 만들고 공통 부품의 결함은 말하지 않는다.
- 라이브러리 API나 경로를 기억으로 단정한다. 설치된 버전의 타입과 공식 문서로 확인한다.

반대 방향의 어긋남도 있다. 작은 요구에 새 Provider, 여러 겹의 Root·Boundary, 쓰지 않을 variant를 제안하는 일이다. 그럴 때는 기존 부품의 단순한 조합으로 되는지 먼저 보인다. 덧대기와 과한 구조는 둘 다 지금 필요한 책임을 보지 않은 결과다.
