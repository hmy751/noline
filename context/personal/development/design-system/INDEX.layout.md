# 배치는 요소의 관계와 그 지식을 가진 곳으로 정한다

**언제 쓰나:** 요소를 배치할 때, 간격·겹침·잘림을 고칠 때, 안전 영역·헤더·스크롤의 책임이나 화면 폭 대응을 정할 때.

**핵심 규칙:** 눈에 맞는 값을 찾기 전에 **내용이 길어지거나 화면이 좁아지면 주변이 밀려나야 하는지**를 묻는다. 그 답으로 수단을 고르고, 같은 위치 지식이 여러 곳에 생기지 않게 한다.

시작 본문은 [UI 결정을 맡을 책임에 두고 쌓는다](INDEX.md)다. 구체 비교는 [제목과 액션](INDEX.cases.md#제목과-액션의-자리를-누가-나누는가), [한 화면과 여러 화면](INDEX.cases.md#한-화면의-겹침과-여러-화면에-퍼진-위치-지식) 사례에 있다.

## 요소의 관계로 수단을 고른다

| 요소의 관계 | 웹 수단 | React Native 수단 |
| --- | --- | --- |
| 순서대로 놓이고 서로 밀어낸다 | 일반 흐름, flex + gap | flex + gap |
| 행과 열을 맞춘다 | grid | 행마다 flex, `FlatList`의 `numColumns`, `flexWrap` |
| 겹치지만 부모 크기에 함께 반영돼야 한다 | 같은 grid 칸 | 크기를 정하는 요소를 흐름에 두고 나머지를 absolute로 채운다 |
| 겹치고 부모 크기에 영향이 없어야 한다 | absolute | absolute |
| 다른 요소에 붙어 뜬다 | popover, anchor positioning, 측정 기반 위치 | 측정 후 `Modal` 표면에 배치 |
| 화면 기준으로 뜬다 | fixed, dialog | `Modal`, 화면 최상위의 absolute |

- **겹치는 것이 목적이면 absolute를 쓴다.** 배경 위 내용, 지도 위 컨트롤, 바닥 시트, 측정한 메뉴가 해당한다.
- **서로 비켜야 하면 흐름에 둔다.** absolute로 띄운 뒤 상대에 여백을 더해 비키면, 두 곳이 같은 크기를 알게 된다.

**외부 참고:** 같은 칸 겹치기는 [Thoughtbot](https://thoughtbot.com/blog/absolute-positioning-with-css-grid), [PQINA](https://www.pqina.nl/blog/css-grid-position-absolute-alternative/), 다른 요소에 붙이기는 [MDN Anchor Positioning](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_anchor_positioning/Using)을 참고할 수 있다. 사용 전에 지원 범위를 확인한다.

## 부품 사이 간격은 부모가, 부품 안은 부품이 정한다

재사용 부품은 놓일 환경을 가정하지 않는다. 제목 부품이 가지던 바깥 여백을 걷어 내고 섹션이 gap으로 간격을 갖게 바꾼 경험이 있고, 이후 프로젝트들도 대체로 이 구조를 유지했다.

- **부품을 만들 때:** 루트에 바깥 margin과 화면 위치를 두지 않는다. 항상 맞는 이유가 있으면 넣고, 그 이유가 코드에서 보이게 한다.
- **화면을 조립할 때:** 부모의 gap이나 앱의 배치 단위로 간격을 준다. 같은 영역에서 gap과 형제 margin을 섞으면 간격을 바꿀 위치가 갈라지므로 한쪽으로 맞춘다.
- **부품 내부 구조의 간격:** 제목과 입력 사이처럼 부품의 내부 구조면 부품이 가진다. 이것은 이 규칙의 예외가 아니다.

**외부 참고:** [Braid](https://seek-oss.github.io/braid-design-system/foundations/layout/)는 컴포넌트에 바깥 여백을 두지 않고 레이아웃 컴포넌트가 간격을 맡는다. [Margin considered harmful](https://mxstbr.com/thoughts/margin)은 간격을 부모가 정해야 하는 이유를 설명한다. [Every Layout](https://every-layout.dev/rudiments/composition/)과 [CUBE CSS](https://cube.fyi/composition.html)는 한 가지 일만 하는 레이아웃의 조합을, [Space in Design Systems](https://eightshapes.com/articles/space-in-design-systems/)는 inset·stack·inline 어휘를 준다.

## 배치 책임을 단위로 빼는 것은 기준으로, 세트는 미정으로 둔다

같은 간격·흐름 결정이 화면마다 반복되면 배치 단위로 빼는 쪽을 검토한다. 항목 데이터와 카드 내부는 그 단위가 몰라야 한다.

**미정:** 어떤 프리미티브를 갖출지는 정하지 않았다. 해 본 것은 웹의 Grid(story 범위)와 모바일 앱의 Stack·Container(실제 화면)다. 대부분의 프로젝트는 flex와 gap을 직접 썼고 그것이 문제였다는 근거도 없다. [Aksel](https://aksel.nav.no/grunnleggende/kode/layout-primitives)처럼 프리미티브를 토큰과 연결하는 방식은 **외부 참고**다.

앱의 단위가 안전 영역이나 앱 공통 표시처럼 빠지면 동작이 달라지는 보장을 담고 있으면 쓰고, 못 쓰면 이유를 보고한다. 방향과 간격을 줄여 쓰는 단위를 반드시 쓸지는 **미정**이다. 이때 지킬 것은 부모가 앱의 값으로 간격을 정하는 것이다. 없다고 새 프리미티브 세트부터 만들지 않는다.

## 자리는 관련된 요소를 모두 아는 쪽이 나눈다

간격을 부모가 정하는 것과 같은 이유다. 한 요소가 다른 요소의 크기나 위치를 몰래 알면, 한쪽이 바뀔 때 다른 쪽이 조용히 어긋난다. 숫자나 absolute 자체가 문제가 아니라 **그 값을 누가 알고 있는가**를 본다.

| 요소의 관계 | 할 일 |
| --- | --- |
| 서로 비켜야 한다. 제목과 메뉴가 그 예다. | 부모가 행으로 나눈다. 제목이 버튼 크기를 여백으로 알게 하지 않는다. |
| 일부러 겹친다. 이미지 위 표시나 배경이 그 예다. | absolute를 쓸 수 있다. 반복되면 위치를 부품 슬롯 안에 두어 호출자가 모르게 한다. |
| 다른 부품의 크기를 숫자로 안다. | 아래 절에 따라 값의 출처를 찾아 모은다. |
| 부품 자신의 규격이다. 입력 높이가 그 예다. | 숫자로 둘 수 있다. |

## 같은 크기와 위치를 여러 곳이 숫자로 알면 원천을 모은다

**신호:** 호출부마다 다른 부품 높이를 숫자로 넣는다(`bottom: 220`). 카드 폭과 캐러셀 간격이 서로 다른 파일에 있다(`330`과 `346`). 주석에 "날짜 선택 아래로"처럼 다른 요소의 자리가 적혀 있다.

**할 일:** 그 값을 아는 곳을 모두 찾고, 한쪽을 바꾸면 다른 쪽이 깨지는지 본다. 깨지면 흐름으로 바꾸거나, 측정하거나, 같은 상수를 공유한다.

부품 안의 상호작용 규격은 숫자로 둘 수 있다. 입력의 최소 높이나 휠 선택기의 행 높이와 선택 띠처럼 같은 상수를 함께 쓰는 경우가 해당한다. 숫자가 있느냐보다 **출처가 갈라졌느냐**를 본다.

## 서로 밀어내는 자리는 조합이 나누고 슬롯으로 연다

- **본문과 액션:** 제목 옆 메뉴처럼 서로 비켜야 하면 조합이 행으로 나눈다.
- **입력 안의 아이콘:** 입력에 자리가 없으면 사용처마다 absolute와 왼쪽 여백, raw 입력을 행으로 감싸는 방식이 함께 생긴다. 반복되면 입력에 슬롯을 여는 쪽을 검토한다.
- **카드의 모서리 표시:** 네 모서리 슬롯을 부품이 제공하면 호출자는 absolute를 몰라도 된다. 위치 지식이 한곳에 남는다.
- **화면에 붙는 내용:** 검색 결과처럼 내용 조합이 `bottom: 0`까지 정하면 다른 자리에 쓸 수 없다. 재사용할 내용이면 내용과 부착 표면을 나눈다. 특정 화면 전용이면 그 이름과 책임으로 남겨도 된다.

## 화면 틀의 책임은 위치 수정 전에 확인한다

안전 영역, 헤더, 전역 안내, 스크롤, 넘침은 화면 하나의 문제처럼 보이지만 지식이 여러 화면에 퍼지기 쉽다. 여러 프로젝트에서 같은 종류의 문제가 나타났다.

**신호와 할 일**

| 신호 | 할 일 |
| --- | --- |
| 상단 안전 영역을 헤더, 배너, 화면이 각자 비운다 | 같은 지식이 있는 곳을 나열하고, 안내가 추가될 때 무엇이 겹치는지 본다. |
| 같은 안내가 화면마다 헤더 앞이나 뒤에 놓인다 | 렌더 순서의 약속이 있는지 확인한다. 위치 값을 옮기기 전에 순서부터 맞춘다. |
| 고정 헤더를 margin과 `calc`로 보정한다 | 모든 화면 폭의 헤더 높이가 같은 값에서 오는지 확인한다. |
| 넘침 처리를 섹션, 페이지, 레이아웃 사이에서 옮겨 다닌다 | 넘침의 원인과 영향을 받는 범위를 찾고, 그 범위를 맡는 곳에 둔다. |
| 위치 수정을 반복해도 다른 화면에서 다시 나타난다 | 국소 수정을 멈추고 화면 틀의 책임으로 다룬다. |

**미정:** 화면 틀 컴포넌트를 둘지는 정하지 않았다. 공용 Layout이 항상 답도 아니다. 전역 상태로 페이지 여백을 켜던 공용 Layout을 없애고 페이지가 Header·Main·Footer를 직접 조합하게 바꾼 경험도 있다. 판단할 것은 지식이 어디에 있어야 하는지이며, 원인이 한 화면 안에 있으면 그 자리에서 고쳐도 된다.

## 긴 내용과 스크롤은 처음부터 자리를 정한다

| 내용 | 판단 |
| --- | --- |
| 한 줄이어야 하는 제목 | 말줄임을 쓰고 전체 내용을 볼 경로가 필요한지 본다. |
| 본문·설명 | 줄바꿈을 허용하고, 주변이 밀려나도 되게 흐름에 둔다. |
| 버튼 글자 | 고정 높이에서 잘리는지 큰 글꼴로 확인한다. 고정 높이 대신 최소 높이나 내용 크기 size를 검토한다. |
| 대화창·시트의 내용 | 내용 영역만 줄어들고 스크롤되게 해서 확인·취소 버튼에 닿을 수 있게 한다. |
| 넓은 표 | 줄바꿈과 가로 스크롤 중 고르고, 스크롤은 그 섹션 안으로 좁힌다. |
| 높이가 달라지는 목록 | 고정 높이보다 최대 높이를 쓴다. |

줄임 prop을 만들면 실제로 동작하는지 확인한다. 타입과 클래스만 있고 CSS가 빠진 경우가 있었다.

## 화면 폭 대응은 기준을 하나로 두고 CSS를 먼저 쓴다

- **기준값:** breakpoint는 원천을 하나로 둔다. 기준이 여러 벌이면 CSS와 JS가 같은 폭에서 다르게 판정한다.
- **수단:** 흐름과 CSS로 풀 수 있으면 CSS를 쓴다. 열 수처럼 값을 prop으로 넘겨야 할 때 JS 분기를 쓴다. 습관적인 기기 분기가 쌓이면 어느 것이 꼭 필요한지 구별이 어려워진다.
- **위치:** 공통 부품은 화면 폭 판단을 되도록 갖지 않고, 앱과 페이지 쪽에 둔다.
- **요소 숨기기:** 좁은 화면에서 공간을 위해 요소를 숨기면 그 기능에 닿을 다른 경로가 있는지 본다.
- **쓰지 않는 기준:** 모바일 앱처럼 폭 분기가 없다면 쓰지 않는 breakpoint를 정의해 두지 않아도 된다.
