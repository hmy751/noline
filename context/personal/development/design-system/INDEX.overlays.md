# 떠 있는 표면은 위치, 호출, 보장을 나눠 정한다

**언제 쓰나:** 메뉴·선택 목록·대화창·바닥 시트·토스트를 만들거나 고칠 때, 겹침 순서 문제를 만날 때, 라이브러리에 맡길지 직접 만들지 정할 때, 터치와 포커스 문제를 다룰 때.

**핵심 규칙:** 호출부는 기준 요소와 의도를, 측정 기반은 실제 좌표를, 상호작용 부품은 열림과 선택을 맡는다. 라이브러리에 맡기든 직접 만들든 **어떤 보장을 누가 지는지 적고 빠지는 것을 밝힌다.**

시작 본문은 [UI 결정을 맡을 책임에 두고 쌓는다](INDEX.md)다.

## 표면의 뜻을 먼저 구별한다

같은 "떠 있는 것"이라도 동작과 보장이 다르다.

| 표면 | 뜻 | 주의 |
| --- | --- | --- |
| 명령 메뉴 | 수정·삭제 같은 행동을 고른다 | 선택값이 없다. 선택 목록 모델로 다루지 않는다. |
| 선택 목록 | 값을 고른다 | 값은 부모가 가지고, 선택 상태를 전달한다. |
| 대화창 | 흐름을 멈추고 확인이나 입력을 받는다 | 닫기, 포커스, 역할을 함께 본다. |
| 바닥 시트 | 모바일에서 선택이나 내용을 띄운다 | 내용 영역 스크롤, 뒤로가기, 안전 영역을 본다. |
| 토스트 | 흐름을 멈추지 않고 알린다 | 놓쳐도 되는 내용인지 본다. [상태 표현](INDEX.states.md) 참고. |

## 겹침 문제는 값을 올리기 전에 쌓임 구조를 본다

**신호:** z-index를 2, 10, 100으로 올리고 있다. 다른 표면과의 순서 때문에 값을 조정했다는 주석이 생긴다.

**할 일:** 표면이 어느 쌓임 맥락과 overflow 안에 있는지 본다. 그 안에서 벗어나야 하면 표면으로 옮긴다(웹은 body portal, RN은 `Modal`). z-index를 올리다 portal로 옮긴 뒤에 위치 계산과 바깥 클릭을 별도로 분리한 경험이 있다. 비슷한 구조가 UI 템플릿에도 있다. 값은 [역할 토큰](INDEX.tokens.md)으로 둔다.

**표면이 겹칠 때:** 표면 안에서 다른 표면을 열면 플랫폼에 따라 동작이 달라질 수 있다. 모달 안에 모달이 겹치는 문제를 슬롯으로 푼 경험이 있다. 전역 표면 관리자는 만들어 보지 않았고 **미정**이다.

## 위치는 측정 기반이 맡고 바뀌는 조건까지 다룬다

- **호출부:** 기준 요소와 배치 의도를 준다. 화면마다 위치 숫자를 다시 쓰지 않는다.
- **측정 기반:** 기준 요소, 표면 크기, 화면 경계, 안전 영역으로 좌표와 뒤집기를 계산한다.
- **범용 메뉴:** 특정 트리거 높이나 화면 여백을 숫자로 갖지 않는다.
- **갱신:** 스크롤, 크기 변경, 회전, 글꼴 변화에서 좌표를 다시 계산하거나 닫는다. 열릴 때만 계산한 코드도 있었고, UI 템플릿의 Hook은 스크롤과 크기 변경에 다시 계산한다.
- **오래된 측정:** 다른 항목에서 다시 열 때 이전 좌표가 남지 않게 한다.
- **어느 항목의 메뉴인지:** 메뉴가 트리거와 떨어지면 대상이 드러나도록 한다.

[메뉴 위치 사례](INDEX.cases.md#메뉴의-위치를-누가-아는가)에 코드가 있다.

## 맡기거나 직접 만들 때 보장을 적는다

Headless 라이브러리와 직접 구현 중 어느 쪽이 기본값인지 **정하지 않았다**. 라이브러리에 맡긴 경우와 직접 구현으로 바꾼 경우를 모두 겪었다. 다만 API와 책임이 애매하면 Radix처럼 책임 분리와 디자인 자유도가 잘 고려된 라이브러리를 먼저 본다. 직접 구현으로 바꾸면서 역할과 포커스 관리가 빠진 경우가 있고, 라이브러리를 쓰면서도 감싸는 방식 때문에 보장이 줄어든 경우가 있다.

| 보장 | 확인할 것 |
| --- | --- |
| 키보드 | 항목 이동, 선택, 닫기 |
| 포커스 | 열릴 때 이동, 닫힐 때 복원, 대화창 안 가두기, 표시가 보이는가 |
| 역할과 이름 | 역할, 제목·설명 연결, 상태 전달, 라이브 영역 |
| 위치 | 측정, 화면 충돌, 갱신 |
| 닫기 | 바깥 터치, ESC, Android 뒤로가기 |

- **라이브러리를 감쌀 때:** `all: unset`, 트리거 요소 교체, 내부 상태 제거가 맡긴 보장을 깎지 않는지 본다. 라이브러리 설명을 그대로 믿지 말고 감싼 결과로 판단한다.
- **직접 만들 때:** 위 표에서 빠지는 것을 결과에 적는다. API 모양을 유지했다고 동작 보장까지 유지된 것은 아니다.
- **교체할 때:** 무엇을 얻고 무엇을 잃는지 적어 둔다. 이전 교체는 이유 기록이 남지 않아 지금 판단할 수 없다.

**목표:** 접근성은 지향하지만 부품마다 수준이 다르다. 실제 범위는 [경험과 지위](INDEX.experience.md)에 있다.

## 선언형과 명령형 호출은 호출하는 쪽의 사정으로 고른다

| 조건 | 선택 |
| --- | --- |
| 트리거와 내용이 한 화면 안에 있다 | 선언형 합성 (`Dialog.Trigger`, `open` 제어) |
| 여러 업무 흐름이나 React 밖에서 띄운다 | store 호출 + 앱에 놓인 표면 하나 |
| 호출한 곳에서 사용자의 답을 기다려야 한다 | Promise 방식을 검토한다. 작은 규모에서는 과할 수 있다. |

표면과 store의 경계도 정한다. Toast는 store를 직접 구독하고, Dialog는 store를 모른 채 앱의 adapter가 잇는 구조를 함께 써 왔다. 공통 부품이 store를 알면 다른 앱으로 옮기기 어렵고, adapter를 두면 연결 코드가 늘어난다. 여러 앱에 가져갈 공통 부품은 store를 모르게 하고 앱의 adapter가 잇는 쪽을 기본으로 본다. 한 앱 안에서 단순함이 더 크면 직접 읽을 수 있고, 그때는 이유를 밝힌다. 과거의 두 방식은 의도적으로 정리한 기준이 아니었다.

**조합 판단**

| 조합 | 이럴 때 쓴다 | 이건 아니다 | 확인할 것 |
| --- | --- | --- | --- |
| 트리거에 붙은 선택 (값 + 열림 + 측정 위치) | 값 선택이 트리거와 떠 있는 목록으로 이뤄진다 | 수정·삭제 같은 명령을 선택값 listbox로 다룬다 | 선택값은 부모가, 열림은 상호작용 부품이, 위치는 측정 기반이 맡는가 |
| 앱에서 요청하는 확인 대화 (앱 adapter + Dialog) | 여러 업무가 같은 확인 표면을 쓰고 callback은 업무가 정한다 | Dialog가 삭제 API나 업무 캐시를 안다 | 비동기 완료를 기다려 닫아야 하는가. 호출 뒤 바로 닫으면 완료를 보장하지 않는다. |

## 겹친 상호작용 영역은 구조로 푼다

**신호:** 카드 전체가 눌리는데 그 안에 메뉴 버튼이 있다. 이벤트 전파 막기가 반복된다.

**할 일:** 눌리는 영역과 내부 버튼을 형제로 분리할 수 있는지 본다. 전파를 막는 것은 쉽지만 스크린리더와 포커스에서는 여전히 겹친다. 카드 메뉴를 터치 영역에서 분리하면서 접근성 이름도 함께 정리한 사례가 있다. 스크롤 제스처를 뺏지 않으려면 배경 터치 영역을 시트의 조상에서 형제로 옮기는 구조도 검토한다.

## 입력 장치 차이는 부품이 맡고 동작을 확인한다

- **hover:** 터치 기기에는 없다. hover 메뉴를 터치에서는 click으로 바꾼 경험이 있고, 이 분기를 테스트로 고정했다.
- **분기가 늘면:** click과 hover를 한 부품의 분기로 둘지 파일을 나눌지 비교한다. 나누면 중복이 남는다.
- **hover 틈:** 트리거와 메뉴 사이의 간격에서 메뉴가 닫히지 않는지 본다.
- **모바일 앱:** 눌림 상태, 터치 영역, 뒤로가기를 대신 확인한다.
