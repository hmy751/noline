# 부품은 실제 변형 축과 변경 이유가 있을 때 키운다

**언제 쓰나:** 공통 부품·variant·슬롯을 추가할 때, 부품 API를 정할 때, 부품을 어느 위치에 둘지 정할 때, 외부 UI 라이브러리를 감쌀 때.

**핵심 규칙:** 개수나 재사용 횟수가 아니라 **사용처들이 실제로 갈리는 축과 서로 다른 변경 이유**로 판단한다. 쓰는 쪽이 알아야 할 전제는 API에서 드러낸다.

시작 본문은 [UI 결정을 맡을 책임에 두고 쌓는다](INDEX.md)다. 공통화의 이득과 사용처의 자유는 [공통 제공과 사용처 선택](../shared-boundaries/INDEX.md)이 소유하며, 여기서는 UI 부품에서 달라지는 판단만 다룬다.

## 변형은 용도가 아니라 독립된 축으로 나눈다

- **좋은 축:** variant(위계), size(크기), fullWidth(놓인 공간), isLoading(진행 표시와 입력 차단)처럼 서로 독립적으로 고르는 축. 이 구조는 여러 프로젝트를 건너 유지됐다. [Button 축 사례](INDEX.cases.md#button의-축은-무엇을-드러내는가)
- **한 값에 두 축이 섞이면 나눈다.** size 안의 `full`은 크기와 폭을 섞은 것이다.
- **용도 이름으로 분기하면 신호로 본다.** 값이 화면과 함께 늘고, 위치나 바깥 여백까지 값에 들어가면 공통 부품이 정착하지 못하고 사용처가 따로 만들기 시작한다.
- **축을 더할 때:** 이번 사용처가 실제로 갈리는지, 기존 축의 조합으로 표현되지 않는지 본다. 추가한 공개 항목마다 이번 사용처가 있어야 한다. 범용 부품의 API라면 잘 만든 라이브러리가 같은 선택을 제공한다는 근거로 대신할 수 있다.

## 서로 다른 이유로 바뀌는 것을 한 단위에 묶지 않는다

- **모양과 데이터:** 공통 카드에 조회, 측정, 인증이 들어오면 카드가 쓰이는 범위가 그 조건에 묶인다. 그 값은 위에서 계산해 props로 넘기거나, 도메인 카드로 위치를 옮긴다.
- **업무 규칙:** 파일 업로드와 업무 기본값을 가진 입력을 공통 패키지에 만들었다가 앱으로 내린 경험이 있다. 공통에 맞지 않는다는 신호가 보이면 내려도 된다.
- **프레임워크 의존:** 공통 패키지가 앱 프레임워크에 묶이면 다른 곳에서 쓸 수 없다. 그럴 계획이 없다면 일부러 끊을 필요는 없다.
- **숨은 계약:** 첫 자식을 이미지로, 마지막 자식을 버튼 묶음으로 가정하는 Card는 배치 규칙이 아니라 자식 순서를 아는 시각 조합이다. 그 계약을 이름이나 API로 드러낸다.

## 글자 표현은 뜻과 생략의 책임을 정한다

웹에서는 `as`, `size`, `weight`, `color`, `truncate`, `lines`를 가진 Text가 가장 많이 쓰인 공통 부품이었고 다음 프로젝트로 이어졌다. 모바일 앱에서는 Text 부품 없이 역할 class를 썼다.

- **어느 쪽이든:** 글자 크기와 색의 원천이 토큰에 있고, 생략 방식이 정해져 있으면 된다.
- **Text 부품이 있으면:** 타입에 있는 값이 실제 스타일로 동작하는지 확인한다. 태그 스타일이 size에 덮이거나 클래스가 빠져 조용히 적용되지 않은 경우가 있었다.

## 스타일 확장 방식을 정해 두고 그 범위를 제한한다

사용처마다 조금 다른 모양이 필요할 때 부품을 여는 방식이다. 같은 라이브러리 안에서 `className`, css 조각 prop, `width` 문자열이 섞인 경험이 여러 번 있다.

| 방식 | 맞는 경우 | 비용 |
| --- | --- | --- |
| variant·size | 같은 변형을 여러 곳에서 고른다 | 새 값을 더할 때 공통 부품을 고친다 |
| `className` 전달 | 사용처의 배치나 작은 조정 | 내부 스타일과 충돌할 수 있고 병합 동작을 확인해야 한다 |
| css 조각 prop | 메뉴처럼 화면마다 모양이 크게 다르다 | 모양이 공통화되지 않는다 |
| 합성 부품 교체 | 구조까지 달라진다 | 사용처 코드가 길어진다 |

**미정:** 기본 방식은 Project가 정한다. 새 부품은 앱에 이미 쓰는 방식을 따른다. 나중에 필요할 때 `className`과 나머지 속성 전달을 더한 경험이 여러 번 있으므로, 처음부터 모든 확장을 열어 둘 필요는 없다.

## 값과 열림 상태는 알아야 하는 쪽이 가진다

- **값:** 저장, 제출, 검증에 쓰여 폼이나 부모가 알아야 하면 그쪽이 가진다.
- **열림·포커스 같은 표시 상태:** 사용처가 알 필요가 없으면 부품 안에 둔다. 값은 제어, 열림은 내부 상태인 Select가 그 예다. store나 비동기 작업이 열고 닫아야 하는 대화창은 `open`을 밖에서 받는다.
- **제어와 비제어 둘 다:** 대화창 같은 범용 부품은 둘 다 지원할 수 있다. 상황, 라이브러리, 디자인, 그 부품을 쓰는 컴포넌트마다 필요한 방식이 달라서다. Radix Dialog도 `open`, `onOpenChange`, `defaultOpen`을 함께 제공한다. 한 앱의 특정 화면만 쓰는 부품이면 지금 쓰는 방식으로 충분하다.
- **애매할 때:** 책임 분리와 디자인 자유도가 잘 고려된 라이브러리가 같은 문제를 어떻게 풀었는지 본다. 다만 API를 따라 직접 구현하면 접근성 같은 보장은 따라오지 않으므로 따로 챙긴다.
- **ref:** 폼 도구나 측정, 포커스가 실제 요소에 닿아야 하면 끝까지 전달한다. 기본 입력에서 ref가 끊기면 폼 도구 전환 때 걸린다.
- **임시 값:** 확인을 눌러야 반영하는 picker는 임시 값과 확정 값을 나눈다. 자세한 내용은 [폼과 입력](INDEX.forms.md)에 있다.

## 합성은 책임이 실제로 갈라질 때 쓴다

합성형을 선호해 온 이유는 UI를 자유롭게 고치면서 각 부품이 맡은 일에 집중할 수 있고, 한곳에서 어떤 부품이 있는지 파악하기 쉽기 때문이다. 다만 모든 부품에 적용하지 않는다. 작은 규모에서 과할 수 있으며, 복합적인 구성을 요구 없이 제안하지 않는다.

| 조건 | 선택 |
| --- | --- |
| 자리와 구성이 사용처마다 달라진다 | 합성 |
| 대부분 같은 구성이고 소수만 다르다 | 합성과 함께 기본형을 제공한다 |
| 항목 모양이 같고 데이터로 정해진다 | 데이터 배열을 검토한다 |
| 한 곳에서만 쓰고 구성이 고정이다 | props로 충분하다 |

**미정:** 합성과 데이터 배열의 경계. 비슷한 시기에 드롭다운은 배열로, 선택 목록은 합성으로 반대 방향으로 간 경험이 있지만 그 이유를 기준으로 정리하지 못했다.

구현할 때는 다음을 확인한다.

- **Context:** 부품들이 실제로 상태를 공유할 때 둔다. 소비자 없는 Provider가 남은 경우가 있었다.
- **자식 타입 검사:** 자식을 타입으로 찾아 배치하면 감싸거나 조건부로 렌더할 때 깨질 수 있다. 사용처가 순서를 직접 쓰게 하는 쪽을 먼저 본다.
- **표기:** `Object.assign`으로 묶는 점 표기와 이름 붙인 export 모두 써 봤다. 같은 패키지 안에서 맞춘다.

## 공통으로 올리기 전에 사용처로 확인한다

- **올린 경로:** 헤더 전용 메뉴를 만들고, 실제 요구로 위치와 터치 대응을 넣고, 스타일 책임을 호출자로 넘긴 뒤 공통으로 올린 경험이 있다. 이 순서에서는 공개 API가 실제 사용으로 다듬어진다.
- **먼저 만든 경로:** 사용처 없이 먼저 만든 Dropdown과 Carousel은 쓰이지 않고 남았다. 시범이나 준비 목적이면 그 사실을 밝히고, 제품 코드로 세지 않는다.
- **정착 확인:** 공통 부품이 있는데 사용처가 따로 만들면, API가 맞지 않는 신호로 본다.

실제 화면에 적용하면서 API를 고치는 것을 기본으로 한다. 처음 만든 대화창 API가 실제 폼에 쓰면서 바뀐 경험이 있다.

## 부품의 위치는 설명할 수 있는 기준으로 정한다

| 위치 | 둘 것 |
| --- | --- |
| 기본 UI 패키지 또는 공통 폴더 | 업무를 모르는 표현·입력·표면 |
| 앱 공통 | 여러 화면이 쓰는 조합, 앱 표면, 앱의 상태 연결 |
| 도메인 | 그 도메인의 데이터 의미를 아는 카드와 표시 |
| 페이지·기능 | 그 화면에서만 쓰는 조합 |

- **처음에는 가까이 둔다.** 바로 공통으로 쓸 요소가 보일 때 공통 폴더를 만든다.
- **모든 UI를 UI 패키지에 넣지 않는다.** 모바일 앱은 기본 부품만 패키지에 두고 조합은 앱에 뒀다.
- **기준을 말할 수 있어야 한다.** 폴더 구조는 프레임워크 문서가 아니라 이 Project의 기준으로 설명한다.
- **예외를 적어 둔다.** 공통 위치의 지도 부품이 도메인 조회를 쓰는 것처럼 불가피한 예외는 이름이나 Project 지침에 밝혀 번지지 않게 한다.

## 외부 UI 라이브러리를 감쌀 때는 무엇을 바깥으로 내보낼지 본다

- **얇은 래퍼:** 라이브러리 props를 그대로 상속하면 호출부 전체가 라이브러리에 묶인다. 자체 variant로 바꾼 뒤에야 교체할 수 있었다.
- **Headless 래핑:** 모양은 소유하고 동작은 맡기는 방식이다. 맡긴 보장은 [떠 있는 표면과 상호작용](INDEX.overlays.md)에서 확인한다.
- **도구 선택:** 스타일 도구의 선택과 이유는 Project가 소유한다. 이 사용자의 전환 경험은 [경험과 지위](INDEX.experience.md)에 있다.
