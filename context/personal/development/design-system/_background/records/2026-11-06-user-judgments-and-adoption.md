# 사용자 판단으로 본문을 고치고 채택한 기록

[디자인 시스템 판단](../../INDEX.md)의 규칙을 사용자에게 물어 고친 과정과 측정 없이 채택한 결정을 보존한다. 현재 적용할 내용은 본문에서 찾는다. 이 기록에는 철회한 제안도 들어 있다.

## 묻는 방식을 바꿨다

첫 질문은 공통 부품의 결함을 어디까지 고칠지였고 작성자는 네 선택지로 물으며 기존 동작을 유지하는 수정을 권했다. 사용자는 선택지가 맞지 않다고 답했다.

> 이건 하냐 안하냐 보다 트레이드오프를 비교해서 결저애햐하는거 아닌가?

이후 작성자가 사용자의 작업 자료에서 판단을 재구성해 제시하고 사용자가 고치는 방식으로 바꿨다. 사용자도 그렇게 요청했다. 그래서 아래 판단의 표와 일반화 다수는 작성자의 것이고 사용자는 동의하거나 고쳤다.

## 질문별 결과

| 질문 | 작성자가 처음 쓰거나 권한 것 | 사용자의 답 | 결과 |
| --- | --- | --- | --- |
| 공통 부품 변경 | 조건 표, 기존 동작을 유지하는 수정 | 무조건 안 바꾸는 것은 답이 아니다. 고칠 곳이 많다는 것은 AI에게 이유가 아니지만 사소한데 볼 곳이 많으면 달리 판단한다. 이유 없는 공통화가 문제다. 애매하면 묻는다. | 이유의 세 축, 이득 대 사람이 볼 양, 진행 순서 |
| 옆 화면과 공통 부품 | 기존 폼이 raw 입력인 이유 불명 | "그냥 놓친거지 개발하다가" | 옆 화면을 선례로 단정하지 않는 절 |
| 헤더와 배치 단위 | 세 단위 모두 안 쓰면 규칙 위반으로 봄 | 부모가 간격을 맡는 것은 맞다. 모바일을 잘 몰라 `Stack`, `Container`는 정하지 못한다. | 보장을 담은 단위와 미정을 나눔 |
| 위치 숫자와 자리 | 신호별 처방 | "넣고 다음으로" | 자리는 관련 요소를 모두 아는 쪽이 나눈다 |
| 값과 열림 상태 | 제어와 비제어는 쓰는 곳을 먼저 본다, 관성일 수 있다 | 상황이 달라 레퍼런스를 보고 고른 판단이다. Radix를 잘 만들었다고 본다. 비제어와 `Controller`는 트레이드오프다. | 범용 부품은 둘 다 지원 가능, 애매하면 레퍼런스 |
| 앱에 없는 값 | 한 화면의 일회성 값은 화면에 둔다 | primary를 쓸 자리면 토큰을 지키고, 새 색은 테마에 더하고, 애매하면 묻는다. 테마가 없는 단순한 프로젝트는 다르다. | 네 단계와 예외 |
| 공통 부품과 store | 미정 | 정하지 않고 작성자에게 물음 | 작성자의 기본값 |

## 작성자가 고친 사실

- 공통 입력과 같은 값의 raw 입력을 사례 예시로 쓰고 있어 공통 입력으로 바꿨다.
- 테마 변경 사례의 "끝날 것 같았지만"은 근거 없는 심정 서술이어서 뺐고, 대비는 코드로 읽은 판단이라고 밝혔다.

## 채택

고친 초안 전체를 사용자와 한 문장씩 검토하지는 않았다. 값, 표면, 상태, 검증, 플랫폼 본문은 작성자가 다시 읽어 어긋난 곳을 고치고 질문이 필요한 곳만 물었다. 사용자는 완벽할 수 없는 문서라고 했다.

> 그래 결국 이것도 정답 원천은 아니니까 다 대응되진 않고 최대한 내 생각과 지식을 담는거라 완벽할수 없어

스킬 문단을 고친 뒤 작성자는 목록과 메뉴만 다시 측정하자고 권했으나 사용자는 "측정 없이 채택"을 택했다. 그래서 고친 스킬 문단의 효과는 시험하지 않았다. 쓰면서 어긋나면 고친다.

## Noline에 lint 경고를 더함

채택 뒤 작성자가 lint를 설명하고 경고로 넣기를 권했다. 오류로 두면 기존 코드 때문에 바로 실패하기 때문이다. 사용자는 "그래 경고로 추가하자"고 답했다.

이 결정은 Noline에 한정한다. 다른 Project의 도입 여부는 정하지 않았다. 일부러 다른 값을 쓰는 경우는 lint가 구별하지 못하므로 주석에 이유를 남기게 했고, 사용자가 납득한다고 한 예외와 맞췄다. 공통 부품 변경과 자리 같은 판단은 lint로 잡지 않는다.
