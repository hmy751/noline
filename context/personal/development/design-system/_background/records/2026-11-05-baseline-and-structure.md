# 기준선 시험과 본문 구성을 바꾼 과정

[시작 본문](../../INDEX.md)의 핵심 규칙과 영역별 구성이 정해진 과정을 보존한다. 2026-11-05 작성 대화와 시험 관찰을 같은 날 대조했다. 관찰 요약은 [기준선 근거](../evidence.md#기준선-시험)에 둔다.

## 기준선 시험

같은 커밋의 Noline 사본 세 개에서 새 세션이 목록, 폼, 메뉴 작업을 각각 수행했다. 기존 Project 지침과 Personal은 그대로 두고 새 design-system Personal만 없는 조건이었다. 다른 작업의 미커밋 변경을 피하려고 별도 사본을 썼고 원격은 제거했다.

Main은 코드를 읽고 웹 미리보기 375px로 일부 확인했다. 사용자는 네이티브 확인은 하지 않기로 했다. 그래서 회전, 큰 글꼴, 실제 키보드는 확인하지 못했다. 시험에 쓴 모델과 추론 수준 기록이 없어 재측정 전에 확인해야 한다.

**본문에 준 영향:** absolute 금지는 겨냥할 행동이 약했고, 앱의 체계를 찾지 않는 것이 더 큰 차이로 보였다. 앞머리 규칙을 그쪽으로 잡았고 공통 결함 우회의 판단을 더했다. 기존 지침에 Field 조합이 있었는데도 목록 작업이 따르지 않았으므로, 문서를 읽고 적용하는지 도달 확인이 필요하다고 판단했다.

## 1차 초안에서 영역별 본문으로

**1차 구성:** `INDEX.md` 하나와 사례, 구성 안내. A~F 후보와 조합 판단 5개를 시작 본문에 담았다. 시작 본문은 176줄이었고 Main은 길이를 위험으로 보고했다.

**사용자 지적:** 파일 하나에 써야 한다는 선입견이 있는 것 같고, 논의와 참고 자료에 비해 적게 나왔다고 했다.

**대조 결과:** 9개 영역 중 스타일 기술, 개발·검증, 운영, AI 협업은 거의 없었다. 화면 틀, `X.Loading`, 안내 장치, 제어와 ref, 공통 승격, 반응형, 입력 장치, 외부 자료가 빠지거나 한 줄로 줄어 있었다. 사용자가 우선하기로 한 Text와 Field도 사례가 없었다.

**원인으로 본 것:** 독립 검토의 제안 "`INDEX.md` 60~90줄"을 사용자가 정한 적이 없는데 기준처럼 썼다. 후보표를 전체 범위로 읽었다. 근거 기준과 공개 제약을 표현 방식이 아니라 내용을 빼는 쪽으로만 적용했다.

**선택:** 사용자가 구성안을 택했다. 시작 본문은 입구로 줄이고 작업별로 파일을 고르게 했다.

**고른 이유와 검토한 대안:**

| 안 | 판단 |
| --- | --- |
| 시작 본문 하나를 더 길게 | 작업과 무관한 내용까지 매번 읽게 된다. 택하지 않았다. |
| 영역별 하위 폴더와 각각의 형성 자료 | 근거와 조사 경위가 하나라 같은 내용이 나뉜다. 변경 이유가 갈라질 때까지 택하지 않았다. |
| 한 주제 안의 `INDEX.<이름>.md` | CONTENT-POLICY가 허용하는 분할이고 형성 자료를 하나로 유지한다. 택했다. |

**새 위험:** 파일을 나누면 맞는 본문까지 읽지 않을 수 있다. 재측정과 도달 확인에서 본다.

## 형성 자료를 뒤로 미뤘다가 함께 씀

1·2차 초안을 쓸 때 Main은 `_background`를 채택 때 쓰기로 혼자 정했다. 사용자가 CONTENT-POLICY대로 채우지 않았는지 물었다. 대조해 보니 그 정책은 새 본문에 목적과 판단 근거를 함께 남기고, 기록을 나중으로 미루지 말라고 정한다. 미룰 근거가 없었으므로 2차 초안과 함께 썼다. 본문 쪽 입구에도 두 층의 역할과 읽기 경로를 더했다.

## 남은 기준

이 구성은 채택 전이다. 재측정에서 도달이나 적용에 문제가 드러나면 구성을 다시 판단한다. 파일 수를 유지해야 한다는 결정은 아니다.
