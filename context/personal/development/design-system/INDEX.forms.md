# 폼은 입력, 표현 틀, 폼 연결의 책임을 나눠 조립한다

**언제 쓰나:** 폼을 만들 때, 입력 부품이나 Field를 고칠 때, picker나 오류·저장 상태를 연결할 때.

**핵심 규칙:** 기본 입력은 폼 도구를 모르고, Field는 제목·입력행·설명·오류의 자리를 맡으며, 연결 코드가 폼 도구의 이벤트 계약을 잇고, 제출 Hook이 부작용을 맡는다. 앱의 입력 부품과 Field가 있으면 그것으로 조립한다.

시작 본문은 [UI 결정을 맡을 책임에 두고 쌓는다](INDEX.md)다. 배치와 입력 교체를 구별하는 일반 판단과 Field 코드는 [공통 제공과 사용처 선택](../shared-boundaries/INDEX.md)과 [Field 사례](../shared-boundaries/INDEX.cases.md#field의-배치를-바꾸는-일과-입력을-교체하는-일)에 있다. 여기서는 그 외의 폼 판단을 다룬다.

## 세 책임을 나누면 폼 도구와 입력을 따로 바꿀 수 있다

| 책임 | 맡는 일 | 몰라야 할 것 |
| --- | --- | --- |
| 기본 입력 | 값 표시, 입력 이벤트, ref, 오류 모양 | 폼 도구의 타입, 제출 API |
| 표현 틀(Field) | 제목, 입력행, 설명, 오류의 자리와 관계 | 입력의 종류, 검증 규칙 |
| 폼 연결 | 값·변경 이벤트·ref·오류를 잇는다 | 화면의 다른 영역 |

Field는 여러 프로젝트를 건너 합성으로 이어졌다. 처음에는 props 한 덩어리였다가, 전화번호처럼 한 필드에 입력이 둘인 경우 때문에 합성으로 바꾼 경험이 있다. 한 프로젝트에서는 단일 래퍼로 단순하게 쓴 적도 있으므로, 복합 입력행이 없는 앱이면 단순한 형태도 된다.

기본 입력이 폼 도구의 타입을 import하면 책임을 나눠도 경계가 샌다. 직접 만든 폼 Hook을 폼 라이브러리로 바꾼 경험이 있으며, 이 경계가 그런 교체의 수정 범위를 정한다.

## 앱에 있는 조합과 입력을 먼저 쓴다

**신호:** 제목과 오류를 손으로 반복한다. 앱의 입력 부품이 있는데 raw 입력에 테두리와 글자 크기를 다시 정한다.

**할 일:** Project의 입력 부품과 Field 사용 예를 찾아 조립한다. 앱의 기존 폼도 raw 입력을 쓰고 있다면, 이번에 어느 쪽을 따를지 근거와 함께 정한다. 입력 부품으로 표현되지 않는 조건(키보드 종류, 여러 줄 등)이 있으면 부품을 넓힐지 비교한다.

## 복합 입력행은 Field 안에서 조립한다

| 이럴 때 쓴다 | 이건 아니다 | 확인할 것 |
| --- | --- | --- |
| 한 의미의 필드가 입력 여러 개나 picker로 이뤄진다 | 입력 종류까지 고정한 큰 FormField에 업무별 옵션을 계속 더한다 | 각 입력의 접근성 이름이 있는가. 오류를 어느 입력에 표시할지 정했는가 |

`FormField`처럼 흔한 조합을 묶은 부품이 앱에 있으면 쓸 수 있다. 다른 구성이 필요한 사용처를 위해 Field로 직접 조립하는 경로를 남긴다.

## 오류의 자리와 상태 표현을 정한다

- **오류 자리:** 비어 있어도 높이를 유지하면 오류가 나타날 때 레이아웃이 밀리지 않지만 평소 빈 공간이 생긴다. 있을 때만 그리면 공간은 아끼지만 밀린다. 폼의 밀도와 필드 수를 보고 고른다. 둘 다 해 봤고, 고정 자리를 쓴 코드에는 높이를 맞춘 숫자가 들어갔다.
- **상태 스타일:** 오류·포커스·기본 테두리 규칙을 입력 종류마다 쓰지 않고 한곳에서 공유하면 나중에 바꿀 때 한 파일만 고치면 된다. 오류가 포커스보다 앞서는 우선순위도 거기서 정한다.
- **검증 오류와 제출 실패:** 필드 오류는 필드 옆에, 제출 실패는 폼 전체의 표현으로 구별한다.
- **만진 상태:** 만지기 전후의 배경 같은 제품 고유 상태를 공통 입력에 넣으면 API에 남는다. 공통으로 필요한지 먼저 본다.

## picker는 임시 값과 확정 값을 나눈다

취소할 수 있는 picker는 **폼 값을 바로 바꾸지 않는다.** picker 부품은 폼 도구를 모르는 임시 선택만 맡고, 연결 부품이 확인 때 폼 값을 쓴다.

```tsx
// 연결 부품이 폼 값과 picker의 열림을 함께 잇는다. 확인만 값을 쓰고 닫기는 임시 값을 버린다.
<TimePicker
  visible={visible}
  initialTime={value || '09:00'}
  onClose={() => setVisible(false)}
  onSelectTime={(time) => {
    form.setValue(name, time, { shouldValidate: true });
    setVisible(false);
  }}
/>
```

확인할 것은 취소 시 값 유지, 확인 시 검증 시점, 다시 열 때의 초기값이다.

## 제출 동작은 보이는 상태와 실제 상태를 구별한다

- **저장 중:** 버튼에 진행 표시를 하고 입력을 막아 중복 제출을 방지한다. 어디까지 비활성화할지 함께 정한다.
- **비활성 표시:** 눌렀을 때 오류를 보여 주려면 색만 비활성처럼 두고 실제로는 누를 수 있게 둘 수 있다. 보이는 상태와 실제 상태가 다르다는 점을 알고 택한다.
- **키보드:** 키보드가 열린 작은 화면에서 마지막 필드와 저장 버튼에 닿는지 확인한다.

## 연결 방식은 입력의 계약에 맞춘다

웹 입력은 ref와 DOM 이벤트로 `register`에 연결되기 쉽다. 체크박스나 커스텀 입력처럼 값 계약이 다르면 `Controller`를 쓴다. React Native 입력은 `onChangeText`로 값을 내보내므로 `Controller` 연결이 맞는다. 어느 쪽을 의무로 정한 것은 아니며 실제 입력의 계약으로 판단한다.

연결 방식에는 트레이드오프가 있다. 비제어는 리렌더링이 적지만 값을 직접 제어하기 어려운 경우가 있고, `Controller`는 그 반대다. 상황마다 다르므로 입력의 계약을 먼저 보고, 리렌더링은 실제로 문제가 될 때 함께 본다.

라벨 연결은 플랫폼마다 수단이 다르다. [플랫폼 대입](INDEX.platforms.md)을 본다.
