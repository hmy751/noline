# 이름에서 맡은 일과 끝난 일을 알 수 있게 한다

**언제 쓰나:** 함수·Hook·상태·반환값·완료 알림을 설계할 때. 또는 지금 표현 때문에 사용처가 동작을 잘못 예상할 때.

**핵심 규칙:** 가능한 한 이름·타입·책임 배치·제어 흐름만으로 맡은 일과 끝난 일을 이해할 수 있게 한다. 설명을 읽으면 사용할 수 있는 수준에서 멈추지 않고, 설명에 맡긴 의미를 코드가 직접 드러낼 수 있는지 먼저 본다.

**첫 갈림길**

| 지금 코드가 | 할 일 |
| --- | --- |
| 필요한 동작을 이미 한다 | 유지·설명 보완·개명 중 이득과 비용을 비교해 고른다([유지·설명 보완·개명·동작 수정을 고른다](#유지설명-보완개명동작-수정을-고른다)). |
| 필요한 결과를 내지 않는다 | 동작을 고친다. |
| 둘 중 어느 쪽인지 헷갈린다 | [같은 인증 코드의 두 표현과 저장 완료 사례](INDEX.cases.md)를 본다. |

이 문서의 예시 이름과 코드 모양은 판단을 보여 주는 예시다. 실제 선택은 각 절의 조건에 대입해서 정한다.

## 바깥 이름은 맡기는 기능을, 안쪽 이름은 각 부분의 일을 말한다

- 호출자가 기능 하나를 통째로 맡긴다면, 순서 조율은 기능 안에서 한다.
- 사용처마다 달라지는 선택(대상 계산, 후속 처리 등)은 사용처에 남긴다.
- 기능 단위, 내부 책임, 파일 배치는 각각 따로 정한다. 책임마다 파일을 만들 필요는 없다.
- 어떻게 나누든, 실제로 맡긴 역할이 이름과 구성에서 이어지게 한다.

예시: 여러 이메일을 검증하고 초대 결과를 반영한다. 오류 처리와 재전송 정책은 생략했다.

```ts
// 사용처는 초대 기능을 맡긴다.
const invitation = useMemberInvitation();
await invitation.submit();

// 기능 내부에서는 대상 계산·요청·결과 반영을 구별한다.
async function submit() {
  const prepared = prepareSubmission(rows);
  setRows(prepared.rows);
  if (prepared.targets.length === 0) {
    return;
  }

  const results = await invitationMutation.mutateAsync(prepared.targets);
  setRows(current => applyInvitationResults(current, results));
}
```

- 호출자가 초대 전체를 맡기므로 `submit`이 순서를 조율한다.
- 입력 검증을 `prepareSubmission`에 직접 넣을지, 기존 폼 도구에 맡길지도 같은 기준으로 정한다.
- 폼 도구가 이미 입력값·검증 오류를, 요청 도구가 pending·error를 갖고 있다면, 같은 상태를 다시 만들기 전에 의미가 같은지 확인한다. 요청 하나의 진행 상태와 이메일별 초대 결과처럼 다른 정보라면 별도 상태로 둘 수 있다.

## 이름·타입·가까운 계약이 같은 역할을 말하게 한다

"가까운 계약"은 그 코드의 역할과 완료 조건을 확인할 때 함께 읽을 타입 선언·주석·문서 설명을 말한다.

| 수단 | 드러내는 것 |
| --- | --- |
| 이름 | 역할 |
| 타입 | 받는 값과 돌려주는 값 |
| 함수의 책임과 흐름 | 처리 사이의 관계 |
| 주석·설명 | 코드로 드러내기 어려운 선택 이유, 외부 제약, 비자명한 실패 조건 |

- 주석으로 역할이나 완료 시점을 되풀이해 설명하고 있다면, 이름·타입·구성으로 더 분명하게 만들 수 있는지 먼저 본다. 주석의 상세 판단은 [코드 표현 기준](../code-expression/INDEX.md#주석은-이유와-필요한-탐색을-돕는다)을 따른다.
- 이름·타입·구성으로 역할을 드러내되, 흔한 실수 두 가지를 피한다.
  - 내부 단계나 계약의 모든 정보를 긴 이름에 몰아넣는다.
  - 주석을 없애려고 필요한 계약까지 감춘다.
- 상수는 현재 값뿐 아니라 의미와 변경 이유로 판단한다.
  - 두 대기 시간이 같은 숫자여도 각각 끝내는 작업과 바뀌는 이유가 다르면 별도 상수로 나눌 수 있다.
  - 같은 약속을 표현하는 값은 함께 관리할 수 있다.
  - 값이 같은지, 사용처가 다른지만 보고 정하지 않는다. 합칠지 나눌지는 의미와 변경 이유로 정한다.
- 입력에서는 상태인지, 처리할 값인지, 출력할 문구인지를 구별한다.
  - 새 API는 처음부터 의도한 값의 종류가 드러나게 만든다.
  - 기존 API는 더 선명해지는 이득과 실제 사용 방식을 비교해서 고칠지 정한다. 오류가 없어도 개선할 수 있다. ([문자열 `isError` 사례](INDEX.cases.md#문자열-iserror를-유지한-판단))
- 반환인지 예외인지를 호출자가 구별할 수 있게 한다. `handleError`가 오류를 변환해 돌려주는지 직접 던지는지에 따라 호출 형태가 달라진다.

구현을 생략한 두 계약:

```ts
// 변환한 오류를 반환한다.
function toRequestError(cause: unknown): RequestError { /* 변환 */ }
throw toRequestError(cause);

// 함수 안에서 오류를 던진다.
function throwRequestError(cause: unknown): never { /* throw */ }
throwRequestError(cause);
```

- 이름과 호출 형태가 분명해도 오류의 의미가 틀리면 해결된 것이 아니다. 예: 응답 해석 실패를 네트워크 실패로 분류하면 호출자는 잘못된 대응을 고를 수 있다.
- 옵션은 이름과 함께 실제로 어느 처리에 적용되는지를 확인한다. ([등록 처리기와 `silent` 옵션의 적용 순서 사례](../contracts-and-lifetime/INDEX.cases.md#등록-처리기와-silent의-적용-순서))

## 같은 방어 코드가 반복되면 상태 표현을 바꿀지 검토한다

**신호:** 여러 값의 조합과 단계별 전제 때문에 같은 방어 코드가 여러 곳에 반복된다.

**할 일:** 가능한 상태와 허용할 전이가 표현에 드러나게 바꿀 이득을 검토한다.

1. **먼저 구별한다.** 동시에 참일 수 없는 '처리 중'과 '완료'를 따로 관리해서 모순이 생기는가? 아니면 실제로 독립된 두 사실인가?
2. **비교한다.** 줄어드는 것(잘못된 조합, 누락, 사용처의 추론)과 늘어나는 것(새 구조를 이해하고 바꾸는 비용)을 견준다. 작은 국소 조건이면 지금 표현이 더 분명할 수 있다.
3. **바꿨다면 확인한다.** 실제 전이와 실패·복구 경로가 계약을 지키는지 본다.

개선 여부는 2번의 비교로 정한다. 상태 머신·특정 타입·라이브러리는 그 비교에서 고를 수 있는 선택지 중 하나다.

## 완료 표현은 호출자의 다음 행동과 맞춘다

**질문: 함수가 성공하거나 callback이 불린 직후, 호출자는 무엇을 해도 되는가?**

반환·알림 시점에 끝난 일과, 소비자가 이어서 하는 행동을 함께 본다.

| 성공 시점에 끝난 일 | 그것만으로는 보장되지 않는 결과 | 확인할 다음 행동 |
| --- | --- | --- |
| 작업을 큐에 접수함 | 실행·저장 완료 | 접수 직후 결과 파일을 읽는가 |
| 저장을 마침 | 후속 조회 완료 | 성공 알림 뒤 최신 조회 결과를 읽는가 |
| 조회 결과를 받음 | 화면 전환·렌더링 완료 | callback을 화면 준비 완료 알림으로 쓰는가 |

- 핵심 결과는 이름과 반환형에 드러내고, 중요한 비대기·실패 조건은 가까운 계약에 적는다. 예: `requestRefresh`는 요청만 하고, `refreshAndRead`는 조회 결과까지 돌려준다.
- **기다릴지는 다음 행동에 필요한 결과로 정한다. 실패 범위와는 따로 판단한다.**
  - 저장 뒤 조회가 실패해도 저장은 끝났을 수 있다.
  - 호출자에게 최신 데이터가 필요하면 조회까지 기다리면서 저장 성공과 조회 실패를 따로 전달할 수 있다.
  - 조회 실패가 저장을 취소하지 않더라도, 다음 행동에 최신 데이터가 필요하면 기다린다.
- 성공·실패 문구도 같은 경계를 따른다.
  - 후속 조회 실패를 전체 저장 실패로 알리면, 이미 저장한 내용을 다시 제출하게 만들 수 있다.
  - 조회가 진행 중인데 화면 갱신까지 끝났다고 알리면, 아직 준비되지 않은 결과를 쓰게 만들 수 있다.

## 유지·설명 보완·개명·동작 수정을 고른다

먼저 확인한다.

1. 요구와 공개한 계약에서 필요한 결과는 무엇인가?
2. 실제 반환·알림 시점의 상태와 사용처는 어떤가?
3. 사용처는 약속된 결과를 쓰는가, 아니면 이름을 보고 더 큰 결과를 추론했는가?

현재 구현은 "지금 이렇게 동작한다"의 근거다. "이렇게 동작하는 게 맞다"의 근거는 요구와 공개한 계약에서 찾는다.

| 확인한 조건 | 선택 | 이유와 주의 |
| --- | --- | --- |
| 필요한 동작을 하고, 이름·타입·구성에서 역할과 주요 완료 범위가 드러난다. | **유지** | 더 길거나 잘게 나눈 표현이 실제 이해를 더 돕지 않으면 지금 코드를 둔다. |
| 코드가 역할은 드러내지만, 선택 이유·외부 제약·비자명한 실패 조건을 알아야 쓰거나 바꿀 수 있다. | **설명 보완** | 코드에 담기 어려운 근거와 계약을 찾기 쉬운 곳에 쓴다. 이미 성립하는 약속을 그 범위 그대로 설명한다. |
| 가까운 설명을 읽어야 역할이나 완료 범위를 구별할 수 있고, 그 의미를 코드로 더 잘 드러낼 수 있다. | **개명·타입·책임 배치 개선** | 설명 의존을 줄이는 쪽을 우선 검토한다. 공개 호환성이나 변경 위험이 크면 이름을 유지하고 설명을 보완할 수 있다. 이 선택은 남는 읽기 부담과 비용을 감수하는 절충이다. |
| 필요한 결과나 공개한 완료 약속을 구현이 제공하지 않는다. | **동작 수정** | 반환 시점·실패 전달·호출 연결 중 부족한 결과를 만드는 부분을 고친다. 기존 소비자의 요구는 유지한다. 이름만 좁혀서 요구를 지우지 않는다. |
| 요구·문서·사용처가 서로 다른 결과를 기대한다. | **충돌부터 밝힌다** | 기존 약속이 빠진 것인지 새 요구인지 확인한다. 호출자가 잘못된 진입점을 불렀다면 맞는 진입점으로 연결할 수 있다. 피호출 함수의 책임을 곧바로 넓히지 않는다. |

- 선택은 겹칠 수 있다. 동작을 고치면서 이름을 바꿀 수 있고, 이름을 유지하면서 설명을 보완할 수 있다.
- 이름과 설명이 서로 다른 결과를 약속하면 둘을 맞춘다. 주석을 덧붙여 덮는 것으로는 부족하다.

### 개명을 비교할 때

- 같은 동작, 같은 소비자, 같은 수준의 설명을 두고 비교한다. 개명 안에만 자세한 주석을 달면 이름의 효과와 설명의 효과가 섞인다.
- 그다음 설명을 보지 않고 코드만으로 이해되는 범위와, 바꿔야 할 참조를 비교한다.
- 두 안 모두 올바르게 쓸 수 있어도 지향하는 명료함은 다를 수 있다. ([인증 코드 A/B](INDEX.cases.md#같은-동작에서-이름-유지와-개명-비교))
- 비교용으로 맞춰 둔 주석은 비교 조건이다. 실제 코드에는 필요한 주석만 남긴다.

### 검토 의견을 쓸 때

- 무엇을 다시 알아내야 하는지(또는 어떤 결과가 부족한지), 선택한 조치가 줄이는 부담, 보존하는 동작을 이어서 쓴다.
- 실제로 일어난 오류와 예상되는 혼동을 나눠 쓴다.
- 필요한 호출·반환·사용처만 확인하고, 결과에는 판단에 필요한 것만 쓴다.
- 새 소비자나 공개 호환 요구처럼 조건이 바뀌면 이전의 유지·개명 판단도 다시 한다.
