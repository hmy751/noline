# 이름·완료 기준을 형성한 근거 발췌

[형성 맥락](context.md)의 해석을 확인할 때 읽는 자료다. 현재 적용할 판단은 [기준 본문](../INDEX.md)이 소유한다.

아래는 **개인 개발 기준과 AI 개발 워크플로를 설계한 실제 대화의 기록**에서 골랐다. Noline demo 제품에서 발생한 사건이나 팀의 합의를 기록한 것이 아니다. ‘사용자 원문’과 ‘Main 설명’은 당시 기록이 발화로 보존한 구간이며, ‘기록 본문’은 Main이 작성한 정리다. 발췌의 띄어쓰기·표현은 보존했고, 각 절의 해설은 기존 데모를 작성할 때 재구성한 설명이다. 전체 대화나 모든 형성 근거를 수집한 문서는 아니다.

2026-10-20에는 데모 안에 있던 발췌를 이 위치로 옮겼다. 아래 발화·비교표·출처 표기와 당시 확인 한계는 보존했고, 바깥 작업의 전체 대화나 원기록을 새로 열람하지 않았다. 형성 기록은 이 발췌를 재구성한 자료이며 원자료와 독립된 추가 증거는 아니다. 이후 같은 날 문자열 `isError`의 유지 판단 누락을 보완하며 해당 작성 기록은 직접 대조했다. 아래 새 항목은 그 확인 범위를 따로 밝힌다.

## 목적

출처: 2026-10-13, 「작업 단계의 시스템을 먼저 구체화한다」의 ‘사용자 원문’. 사용자는 작업을 논의해 결정하는 단계와 구현하는 단계를 구별한 뒤, 참고 강연에서 가져오고 싶은 것을 설명했다.

**기록에 보존된 사용자 원문:**

> 첫번재 질문에 답하자면 레퍼런스를 보고 가장 와닿은건 작업 단계 시스템이나 그런거였어 어떤 컨텍스트를 주고 또 강연 보면 알겠지만 코드를 잘 구현하고 해야 ai 슬롭을 줄일수 있다고 하잖아? 그런 시스템 구축

이 발화는 구현자가 받을 컨텍스트·코드 기준·작업 절차를 구체화하려는 출발점이다. 이름 기준은 그중 코드를 읽고 고칠 때 개인의 판단을 제공하는 부분으로 발전했다. 특정 이름 체계나 코드 모양을 먼저 표준으로 정하려는 요청은 확인되지 않았다.

같은 발화에서 사용자는 기존 코드에 만족하지 않았으며 충분한 컨텍스트를 주지 않았다는 경험도 말했다. 이것만으로 개별 코드의 결함이나 불만의 원인을 확정하지는 않는다. 강연에 대한 사용자의 인상을 보존한 것이므로 강연 자체의 효과를 검증한 근거도 아니다.

## 조건별 적용

출처: 2026-10-18, 「원칙의 적용 방식과 선택 근거를 보완한 시안」의 ‘직전 기록 이후 확인한 뜻과 사용자 요청’. 사용자가 ‘나중에 기준을 다듬을 수 있다’는 뜻인지 묻자 Main은 기준의 수정 가능성과 실제 적용 방식을 구별했다.

**기록에 보존된 Main 설명, 두 문단 발췌:**

> 즉, **원칙을 특정 코드 모양에 맞추라는 명령으로 읽지 않고, 현재 목적과 조건에 대입해 판단하도록 설명하자**는 제안이야.

> 내가 ‘기준 후보’라는 말을 앞세워 헷갈리게 설명했어. 이 적용 방식은 나중에 기준을 채택한 뒤에도 똑같이 필요한 부분이야.

**이 설명 뒤의 사용자 원문:**

> 아 그 뜻이면 알겠어. 그럼 리뷰에서 나온 세 가지 반영해서 시안 보완해줘. 방금 설명한 내용도 기록에 같이 남기고.

사용자는 설명의 뜻을 확인하고 시안 보완을 요청했다. 조건별 적용은 ‘아직 후보이니 그대로 따르지 않아도 된다’는 임시 단서가 아니라, 채택한 기준을 사용하는 방식으로 구체화됐다. 이 응답이 모든 기준·사례·파일 배치의 최종 채택을 뜻하지는 않는다.

## 문자열 isError의 유지 판단

출처: 2026-10-16, 「앞서 본 template 코드의 네이밍·가독성 보완 검토」의 ‘확인 결과’, ‘isError 비교에 대한 사용자 판단’. 2026-10-20 누락 보완에서 당시 기록을 직접 대조했다. 외부 UI 템플릿의 현재 코드나 전체 대화 원본을 새로 조사한 것은 아니다.

당시 관찰은 Input·Select가 string `isError`를 스타일 조건으로 사용하고 문구는 Field.Message가 출력하며, MultiSelect.Trigger의 같은 이름은 boolean이라는 것이었다. boolean으로 바꾸려면 값뿐 아니라 입력 타입·표시 계약도 맞춰야 한다. 코드 변경은 하지 않았다.

**비교 뒤 사용자 원문:**

> 음 여기서 불리언이 더 명확하긴 한데  메시지 자체가 오류룰 발생시킬 우려는 없어서 괜찮아 보여 이렇게 했어 음 뭐 크게 크리티컬해보이지는 않네

더 명확한 표현과 당시 필수 수정 여부를 구별한 판단이다. 실제 오사용 빈도·공개 호환 비용을 조사했거나 모든 문자열의 안전성을 검증한 발화는 아니다. 모든 `is` 이름에 문자열을 허용하는 규칙도 아니다. [현재 사례](../INDEX.cases.md#문자열-iserror를-유지한-판단)는 이 관찰과 판단을 설명용 코드로 재구성한다.

뒤의 [코드 명료함 발화](#코드가-드러내는-의미)는 별도 시점의 일반 지향이다. 확인한 기록에서 이 유지 사례를 명시적으로 취소한 발화는 찾지 못했다. 현재 맥락이 둘을 함께 설명하는 방식과, 사용자가 각 시점에 직접 말한 것은 구별한다.

## 개선의 이득과 비용

출처: 2026-10-19, 「유지·설명 보완·개명·동작 수정의 본문 구체화」의 ‘실제 문장을 어떻게 다듬었나’. 아래 문장은 사용자 발화가 아니라, 당시 기록의 비교표가 보존한 본문 변경이다.

| 기록에 보존된 이전 본문 | 기록에 보존된 수정 본문 |
| --- | --- |
| “내부 사용처를 함께 고칠 수 있으면 개명하고” | “내부 사용처를 함께 고칠 수 있다는 사실은 전환 비용의 근거이며, 그것만으로 개명을 결정하지 않는다.” |
| “기존 API에서는 실제 혼동·오사용·변경 범위에 비춰 개선 이득을 판단한다.” | “혼동·오사용뿐 아니라 역할을 파악하고 수정 영향을 찾는 부담도 개선 이득에 포함한다.” |

첫 변경은 ‘바꿀 수 있다’를 ‘바꾸면 좋아진다’의 근거로 쓰던 설명을 바로잡은 것이다. 내부 호출을 함께 고칠 수 있거나 사용처가 적다는 조건은 전환 비용을 판단하게 한다. 이름 때문에 무엇을 다시 알아내야 하는지, 개명이 어떤 읽기 부담을 줄이는지는 별도로 확인해야 한다.

두 번째 변경은 실제 오류가 발생해야만 개선할 수 있다는 좁은 해석을 피하려는 구체화였다. 역할과 수정 영향을 파악하는 부담도 개선 이유에 포함하되, 더 명료하게 만들 수 있다는 사실만으로 모든 기존 API의 필수 수정을 결정하지 않았다.

같은 기록의 ‘상세 사례는 필요한 결과와 선택 이유를 보여 준다’에는 Main이 추가한 접수 식별자·결과 조회 등의 조건을 **설명용 가정**으로 명시했다. 이 비교표와 사례는 기존 합의를 Main이 본문에 풀어 쓴 결과이며, 사용자가 정확한 문장과 가상 조건을 각각 결정했거나 실제 개명 효과를 측정한 근거는 아니다.

## 코드가 드러내는 의미

출처: 2026-10-19, 「코드 자체의 명료함을 우선하는 판단 보완」. 같은 동작을 이름 유지안과 개명안으로 비교하던 중, Main은 가까운 설명을 읽으면 두 안 모두 사용할 수 있다는 점을 강조했다.

**기록에 보존된 사용자 원문:**

> 근데 난 되도록 설명이 필요없는 코드가 지향되어야 할 코드라고 생각해

이 발화는 사용할 수 있는 코드와 지향할 코드 품질을 구별하게 한 직접 근거다. 이름·타입·책임 배치·제어 흐름이 의미를 드러내도록 우선 살피고, 코드에 담기 어려운 이유와 제약을 설명으로 보완한다는 현재 표현은 Main이 이 지향을 구체화한 것이다.

**같은 기록 본문에 남긴 해석의 한계:**

> ‘되도록’이라는 방향을 모든 주석 제거, 이름에 모든 정보 나열, 기존 공개 API 즉시 개명으로 확대하지 않는다. B도 최선의 이름·구성으로 확정하지 않는다. 이번 비교는 이름의 차이를 보여 주므로 타입·책임·제어 흐름까지 개선·검증했다고 보고하지 않는다.

이 한계 문장은 사용자 원문과 구별되는 Main의 정리다. 사용자에게 직접 확인한 것은 코드 자체의 명료함을 지향하는 방향이며, 모든 구체 문구·비교 방식·이름이 최종 수용됐거나 실제 이해 속도가 개선됐다는 뜻은 아니다.

## 개인 기준의 소유

출처: 2026-10-19, 「Personal·Project·Work의 갱신 책임 정리」의 ‘사용자 요청과 셀프체크’. 앞선 개인 기준 보완에서 Project 가이드까지 바뀌자 사용자가 관리 책임을 확인했다.

**기록에 보존된 사용자 원문:**

> 근데 이건 내 개인 코드 기준인데 Project 가이드까지 바꾼 이유가 뭐야? Personal이랑 Project의 역할이 섞인 건 아닌지 한번 봐봐. 일부러 의도 된건가?

**관리 기본값 검토 뒤 반영 요청:**

> 그래 그럼 그 기준으로 정리해줘

**같은 기록의 ‘이번에 반영한 기본값’에서 발췌한 Main 정리:**

> 개인 기준이 달라지면 Personal 본문과 적용 중인 Work의 판단을 살핀다. Project에는 그 제품의 계약·규약·현황이나 필요한 설명이 실제로 달라질 때 반영한다. Project 자체의 코드 품질 기준도 이유·범위가 있으면 둘 수 있다. 자기 문서를 이해하는 데 필요한 짧은 설명의 중복은 허용하며, 같은 문장을 맞추는 것이 갱신 목적이 되지 않게 한다. 새 일괄 승인 절차를 추가하지 않는다.

이 과정은 개인 판단의 변경과 제품 자체의 지속 기준 변경을 구별하게 했다. Personal에는 여러 Project에 가져갈 판단의 의미와 조건을, Work에는 이번 조건에서의 선택을, Project에는 자기 제품의 의미·계약·규약·현재 사실을 두는 이유가 여기에 있다. Project에 비슷한 설명이 있다는 사실 자체를 오류로 판정한 것은 아니다.

당시 검토는 사용자 원문·변경 기록·현재 문서를 근거로 했다. 이전 Main 답변 전체와 직전의 별도 변경 내역은 회수되지 않아 당시 정확한 설명 의도와 모든 문장의 변경 시점은 확정하지 못했다. 관리 기본값을 정리해 반영한 사실과 장기 운영 효과를 확인한 사실은 구별한다.
