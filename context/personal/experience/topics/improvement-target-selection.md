# 개별 보완의 완료와 개선 루프의 목적

**지위: 2026-10-30 Noline에서 관찰한 경험과 후순위로 보류한 개인 판단 개선 후보.** 기존 세 prototype 주제와 달리 이번 Project에서 실제 수행한 장면이다. 새 개인 기준이나 실행 절차로 채택한 것은 아니다. 현재 실행은 Project Context 보완이며 이 주제의 일반화·추가 개선은 나중에 다룬다.

## 관찰한 장면과 반대 근거

사용자는 새 Context를 기반으로 이전 Workspace 02의 기록과 코드를 대조해 개선하는 새 Workspace를 요청했다. Main은 기록의 주제를 16개 Ticket 후보로 나열했다. 사용자가 “왜이렇게 많지? 작업한게 많은거야? 아님 기록을 바탕으로 판단한거야? 뭐지?”라고 묻자, Main은 실제 개선 필요를 전부 확인한 목록이 아니었다고 정정했다. 이후 당시 설계 선택과 결과를 한 Ticket에 묶는 안을 제시했고 사용자가 승인했다.

첫 대상으로 저장 용량 Hook을 고른 이유는 초기의 얕은 정리·사용자 정정·최종 책임 분리·검사가 작은 범위에 연결돼 있기 때문이었다. Main은 당시 기록과 현재 코드·소비자·테스트를 대조해 책임 분리는 유지하고 함수 배치·검사 두 가지를 보완하자고 제안했다. 사용자는 “그래 그 두 부분 보완하고 테스트까지 해봐”라고 승인했다. 보완과 확인 뒤 사용자는 다음과 같이 물었다.

> 근데 지금 이 작업을 왜하는거지?

Main은 기존 설계 재확인과 작은 보완이라는 목적 연결을 설명했다. 사용자는 이어 improvement-loop를 호출하며 다시 판단해 달라고 했다.

> 루프 관점에서 이게 적절한가? 다시 생각해봐 뭔가 너무 지엽적이고 이거 왜한느지 모르겟어

새 테스트는 기존 두 동작의 검사 공백을 메웠고 보호 처리를 제거한 복사본에서 실패했다. 코드 보완의 유효성과 실행 권한은 있다. 사용자 승인 없이 잘못된 코드를 고쳤거나 모든 수행이 무가치했다고 판단할 근거는 아니다. 반면 이 보완이 원래 루프에서 우선할 만큼 중요한 결과였다는 근거와 이후 작업의 개선 효과는 확인되지 않았다.

## 현재 해석

Main은 개선할 문제를 선별하기 전에 코드 영역을 실행 목록으로 만들었다. 16개에서 세 Ticket으로 재구성하면서 단위는 좋아졌지만, 지금 무엇을 바꾸면 이득이 큰지에 관한 선택은 약했다. 작은 사례로 첫 적용을 확인하는 선택 자체는 가능하지만, 그 사례에서 알아내려는 것이 무엇이며 결과가 다음 선택을 어떻게 바꿀지 충분히 정하지 않았다. 현재 코드에 더할 수 있는 국소 보완을 찾아 마치는 흐름으로 좁아졌다는 것이 이번 Main의 판단이다.

[Project 리팩터링 기준](../../../project/guidance/behavior-preserving-refactoring.md)은 02의 Ticket 01–05에서 이미 얻은 선택을 포함하고, 저장 용량의 최종 책임 분리도 그 사례다. 이를 같은 Hook에 대조한 결과는 기존 계약 확인에는 유효하지만, 새 Context가 새로운 판단이나 더 큰 개선을 만든다는 근거로 확대할 수 없다. 새 Personal 기준이 읽기 순서 판단에 쓰인 사실과 그 적용의 전체 효용도 구별한다.

02 저장 용량의 초기안은 좁은 완료 판단 뒤 사용자가 개선 깊이를 여러 차례 보완했던 사례다. 이번 005에서는 승인된 국소 보완을 끝냈지만 사용자가 전체 작업의 목적을 다시 물었다. 결과 단위의 완료와 상위 기대의 어긋남이라는 유사성이 있다. 두 사건의 원인이 완전히 같거나 02 전반의 패턴이라고 확정한 것은 아니다. 02 사건의 근거는 [당시 재확인 기록](../../../work/workspaces/002-code-readability-refactoring/records/2026-09-12-01-ticket-03-initial-scope-reanalysis.md)이며 이번에 당시 전체 runtime 대화를 재열람하지는 않았다.

현재 improvement-loop·development·reconsider-work에는 목적, 실제 이득·부담, 기존 기준의 충분성과 수행을 대조하라는 내용이 이미 있다. 이번 근거만으로 스킬에 같은 지침을 더하는 것이 해결책이라고 볼 수 없다. 직전 Main의 “목적 설명이 부족했다”는 진단은 작업 선택·성과 판단의 문제를 충분히 다루지 못했다.

## 열린 제안과 선택할 차이

추천은 005에서 코드별 순회에 앞서 02의 재작업·사용자 개입·판단 전환이 컸던 장면과 잘된 대조 사례를 보고, 현재까지 남은 문제와 개선 이득을 선별하는 것이다. 당시 요구·AI가 실제로 사용한 기준·수행·결과를 현재 Context와 비교해 코드, 작업 정의, 실행 방식, 기준 내용 중 어느 대상의 변경이 필요한지 고른다. 코드 대조는 실제 결과를 확인하는 근거로 계속 사용한다. 모든 경험을 하네스 수정으로 전환하는 제안은 아니다.

같은 저장 용량 사례라면 함수 순서를 더 정리하는 것보다, 초기의 좁은 완료 판단이 현재 수행에서도 생기는지와 무엇이 그 선택을 달리하게 할지를 검토할 수 있다. 기존 지침으로 충분하면 지침 추가 없이 해당 수행을 바꾸는 안도 비교한다. 성공 여부는 다음 관련 작업에서 필요한 범위·책임을 처음부터 다뤘는지와 사용자가 같은 방향 정정을 다시 해야 했는지 같은 실제 결과로 판단할 수 있다. 이 관찰은 아직 수행하지 않았으며 고정 평가표나 상시 추적을 제안하지 않는다.

다른 선택은 005를 순수 제품 코드 재감사로 명확히 한정하는 것이다. 이 경우에는 현재 결함·유지보수 부담의 크기로 대상을 고르고, Context·협업 체계의 개선 효과를 별도 성과로 주장하지 않는다. 지금 사용자의 루프 요청에는 첫 안이 더 적합하다는 것이 Main의 추천이다. 어느 쪽도 큰 변경을 반드시 만들어야 한다는 뜻은 아니다.

사용자는 이어 “그래 다시 파악해봐 그리고 context 보완 관련도”라고 요청했다. 이에 큰 정정·재작업·판단 전환과 좋은 대조 사례에서 출발하는 재조사를 수행했다. 002의 네트워크 품질 개선 원복, 인증 복잡도·소비자 재검토, 일정 생성 책임 검토를 현재 코드·Context와 대조했다. 기록에 보존된 발췌를 확인했으며 002 전체 runtime 대화를 새로 읽은 것은 아니다. 상세 근거와 후보는 [005의 재조사 기록](../../../work/workspaces/005-context-based-code-improvement/records/2026-10-30-07-impact-and-context-reassessment.md)이 소유한다.

이번 대조에서는 과도한 기능 확장, 기능 검사 결과를 구조 평가로 확대하는 판단, 현재 인증 계약의 흩어진 설명을 구별했다. 모든 문제를 검토 깊이 부족이나 문서 부족 하나로 묶을 수 없다. 작성 중 입력 보존은 현재 정책 본문에 이미 있고, 조회 공통화는 당시 사용자가 Project보다 Work에 먼저 남기기로 했던 내용이다. 복구 토스트를 현재 필요에 비춰 추가하지 않기로 한 좋은 사례도 확인했다. 재작업만 모아 더 많은 규칙이나 구현을 만드는 접근을 제한하는 근거다.

이 재조사 뒤 Main은 인증 Context 복원을 우선 추천했다. 사용자는 “아니 근데 02에서 그렇게 작업을 많이 했는데 context 보완이 로그인 하나라고?”라고 다시 정정했다. 별도 self-check는 큰 재작업 사례를 고르는 방식이 제품 의미·좋은 구현·현재 제약 전반을 대신했고, 기준 한 문장의 존재를 해당 주제 내용의 충분성과 혼동했다고 지적했다. Main은 이 판단을 대화와 대조하고 적용했다. 인증 공백은 유지하되 단독 우선 추천은 철회했다.

이어 002의 실제 수행과 계획을 구별해 [현재 Context 대응](../../../work/workspaces/005-context-based-code-improvement/records/2026-10-30-08-context-coverage-reassessment.md)을 보완했다. 앱 준비·종료, 네트워크 수명, DB 작업 조율, Query와 화면 표현, 폼·선택창·Places 관계에 공백이나 낡은 설명이 있고, 시간대·경비 관계·여행 목록·초기 API 기준에는 상당한 반영이 있었다. Personal에서도 TimeField·홈 요약·foreground처럼 기존 조건과 사례를 구체화할 실제 경험을 함께 봐야 한다. 이 대응은 새 Ticket 목록이나 개인 일반 기준 채택이 아니다.

이후 사용자는 “컨텍스트 기준으로 다시 구성하고 먼저 작업하자”, “개인 판단 그거 같은데 그건 나중에 하게”라고 선택했다. 이에 005의 Spec·Ticket을 앱 실행·데이터 보존, 네트워크·조회·복구, 작성·장소·날짜 입력의 Project Context 보완으로 재구성했다. [선택과 재구성 기록](../../../work/workspaces/005-context-based-code-improvement/records/2026-10-30-09-project-context-ticket-reconstruction.md)이 현재 작업 범위의 근거다. 개인 판단·협업·스킬 개선 후보는 후순위로 보류하며 이번 실행 목록에서 제외한다.

Project 본문 보완은 아직 시작 전이고 기존 코드 보완은 유지한다. 이 상태 정리는 개인 기준을 새로 만드는 작업이 아니다. 조사·기록·Ticket 구성이 이후 수행 개선의 효과를 입증하지는 않는다. 실제 다음 실행은 [현재 상태](../../../work/workspaces/005-context-based-code-improvement/current/state/index.md)에서 이어간다.
