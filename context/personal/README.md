# Personal context — 개인의 판단 기준과 협업 경험

여러 작업에 가져올 개인의 판단 기준·이유·적용 조건과, 사람과 AI가 일하며 얻은 경험·현재 이해·열린 개선 후보를 제공한다. 기준의 채택 권한은 사용자에게 있고 Main 또는 지정 담당자가 허용된 범위를 관리한다. 경험을 보존했다는 사실이 새 기준의 채택은 아니다. 코드 품질뿐 아니라 설계·접근법·선택을 판단할 관점을 담을 수 있다. 제품 요구·팀의 계약·현재 구현은 해당 Project가, 이번 작업의 선택과 진행은 Work가 소유한다. 개인 기준은 그 내용을 읽고 판단할 관점을 제공한다.

## 필요한 본문

- 현재 적용할 개발 판단은 아래 개발 본문에서 고른다.
- 협업 경험과 아직 반영하지 않은 관련 후보는 [경험 길잡이](experience/README.md)에서 주제·미분류 기록을 찾는다. 사용자 요청 루프에서는 길잡이를 훑고 관련 상세를 읽으며, 일반 작업에서 모든 후보를 실행 지침으로 읽지 않는다. 저장·다음 조회·채택 후 연결은 [경험 관리](experience/MAINTENANCE.md)가 소유한다.

이 범위 확대와 구성 이유를 재검토할 때는 [형성 자료](_background/experience-collection/README.md)를 읽는다.


현재 적용할 개발 기준은 [개발 판단](development/README.md)이며 이번 쟁점에 맞는 본문을 고른다. 공통화할 범위, 계약·수명, 이름·완료, 코드 표현·진단의 네 주제가 있다. 이 네 주제가 Personal 전체의 영구적인 범위를 정하지는 않는다. 일반 기준은 다른 작업에도 적용할 관점과 조건을 설명한다. 상세 사례는 코드와 사용 조건을 대조해 선택이 왜 달라지는지 보여 준다. 일반 기준으로 충분히 판단할 수 있다면 사례를 모두 읽을 필요는 없다.

질문별 원문 선택·유효한 읽기 재사용·실제 대상과의 대조는 [공통 사용 방법](../USAGE.md)을 사용한다. 현재 의미를 더 정확히 이해하거나 형성 의도를 확인할 때도 해당 주제의 형성 자료에서 필요한 부분을 고를 수 있다. 개인 기준과 그 적용 조건의 내용은 각 본문이 계속 소유한다.

## 이번 제품에 적용할 때

현재 목적·사용처·변경 비용에 대입해 유지·수정·보류를 고른다. 사례와 코드 모양이 다르다는 이유만으로 바꾸지 않는다. 예컨대 공통 주문 처리의 범위는 같은 API인지뿐 아니라 같은 구매 흐름인지에 달려 있고, 완료 이름은 다음 소비자가 어떤 결과를 필요로 하는지와 함께 판단한다.

제품 요구와 개인 선호가 충돌하면 무엇이 달라지는지 드러내고 이번 작업의 권한 안에서 선택한다. 제품의 명시된 완료 약속을 이름만 좁혀 없애거나, 한 사례의 Hook·클래스·타이머 위치를 모든 Project에 강제하지 않는다. 작업에 사용한 기준과 그 조건은 Work에 남긴다.

Noline에 적용할 때는 [Project 진입점](../project/README.md)에서 제품 계약과 현재 구현을 함께 찾는다. 타입·명명·중괄호·진단 출력은 [TypeScript 규약](../../.claude/context/typescript.md), 폼은 [React Native Form](../../.claude/context/form.md), UI 공통화는 [컴포넌트 가이드](../../.claude/context/components.md)와 [UI package 지침](../../packages/ui/CLAUDE.md)을 대조한다. Personal의 일반 기준이 기존의 더 엄격한 제품 규약을 해제하지 않는다.

오류 반환·전파와 재시도/UI 책임은 [API 계약](../project/guidance/api-contracts.md)과 해당 구현에서 확인한다. 일반 비동기 예시만으로 모든 함수에 catch·로그·null 반환을 도입하지 않는다. 서버 오류 정책의 열린 선택도 이 기준 추가만으로 확정하지 않는다. 동작 보존 변경에서는 [Noline 리팩터링 기준](../project/guidance/behavior-preserving-refactoring.md)을 함께 적용한다.

## 기준을 고치는 경우

기존 설명으로 판단하기 어려운 조건이 드러나면 어떤 전제가 달라졌는지 확인한다. 여러 Project에 가져갈 개인 판단의 의미·조건이 바뀌었다면 이 본문을 고치고, 그 기준을 사용 중인 Work에서 현재 선택에 미치는 영향을 살핀다. 특정 제품의 요구나 이번 작업의 변경 비용이 달라진 경우에는 해당 Project나 Work가 그 내용을 관리한다. 한 작업의 함수명이나 선택을 개인 공통 의무로 곧바로 올리지 않는다.

기준의 새 채택과 이미 정한 뜻의 반영을 구별한다. 현재 권한으로 해결할 수 없는 새 선택은 사용자 또는 해당 결정권자에게 연결하며, 편집 담당이 됐다는 이유로 채택권을 얻지는 않는다. 허용된 반영은 [context-update](../../.claude/skills/context-update/SKILL.md)의 방법으로 필요한 본문·형성 자료·읽기 경로를 맞춘다. 사용 중인 Work의 실제 갱신은 그 책임자에게 연결한다. 본문과 영향받은 진입에서 바뀐 의미·조건·이유를 근거에 맞게 이해할 수 있어야 반영을 마친다. 실제 사용 효과까지 확인됐다고 확대하지 않는다.

네 주제와 개발 공통 관점에는 현재 내용을 쓰는 본문과 그 내용을 형성한 의도·배경·선택·근거를 보존하는 자료를 구별해 두었다. [개발 판단 안내](development/README.md)에서 현재 적용할 본문을 고르고, 의미·조건이나 구성을 바꾸려면 해당 안내의 형성 자료를 읽는다. 이 상위 본문이 설명하는 독립 책임과 로컬 위치는 [context 형성 자료](../_background/README.md), 조건별 적용은 [적용 방식의 근거](development/naming-and-completion/_background/evidence.md#조건별-적용), 갱신 기본값은 [소유 관계의 근거](development/naming-and-completion/_background/evidence.md#개인-기준의-소유)에서 복원한다. [공통 관리 원칙](../CONTENT-POLICY.md)에 따라 필요한 관계를 함께 맞춘다.

이 폴더는 현재 프로젝트에서 읽는 개인 기준과 경험·판단 자료다. 여러 저장소 사이의 배포·동기화는 구현되어 있지 않다.
