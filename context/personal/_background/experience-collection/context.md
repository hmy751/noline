# 기준만으로 정리되지 않는 경험을 Personal에서 이어 읽는다

[Personal](../../README.md)의 범위와 [경험 관리](../../experience/MAINTENANCE.md)를 형성한 선택이다.

사용자는 AI와 일하면서 생긴 판단과 좋은 사례를 Work·records에 흩어두면 다시 구분하고 적용하기 어렵다고 보았다. Personal의 의미를 넓혀 우선 이 경험을 보존하되 Work를 제한하거나 새 분류를 한꺼번에 확정하지 않기로 했다. 후보가 아직 기준이 아니라는 이유로 원문 속에만 묻어두지 않고, 현재 이해와 열린 질문을 함께 읽게 한다.

날짜별 경험함과 후보함을 따로 만들면 쓰기는 쉬워도 다음 판단에서 관계를 재조립해야 한다. 그래서 주제가 보이면 하나의 상세에서 사실·해석·후보·이후 선택을 구별하고, 길잡이가 짧은 진입만 맡는다. 분류가 아직 어려운 장면은 길잡이에 남긴다. 모든 경험을 과제로 바꾸거나 주제마다 빈 파일 세트를 만드는 부담을 피한다.

현재 Personal 개발 본문은 그대로 적용할 기준을 소유한다. 경험 모음은 아직 채택되지 않은 내용을 평소 기준으로 실행시키지 않는다. 채택하면 실제 기준·스킬·제품 대상이 현재 내용을 소유하고 경험 주제는 판단 근거와 연결을 남긴다. `_background`는 해당 본문의 형성 이유이고 아직 어디에도 채택되지 않은 경험을 모두 모을 위치가 아니다.

사용자 요청 루프에서 다시 읽고, 일반 작업에서는 관련된 채택 기준을 읽는다. 이 구별을 Personal·USAGE와 실행 스킬에 연결했다. 모음을 유지하는 규칙이 특정 스킬 안에만 있지 않아 실행 수단이 바뀌어도 경험과 근거를 이어 쓸 수 있다. 저장소 간 배포·동기화와 실제 host 설치는 이번에 구현하지 않았다.

Personal 범위 확대와 Work 등록 정정을 확인할 때는 [직접 근거](evidence.md)를 읽는다. 현재 구성으로 바뀐 이유와 당시 선택은 [관리 책임 정정 기록](records/2026-10-29-ownership.md)에 보존했다.

한정 시도로 선택된 내용은 아직 일반 기준은 아니지만 해당 작업에서 실행할 내용이다. 경험 주제는 왜 골랐는지·어느 작업에 연결했는지·실제 결과가 무엇인지를 이어 보존하고 실행 지시 전문은 해당 작업이 소유한다. 이 구별은 후보 전체를 평소 입력으로 만드는 부담 없이 선택과 다음 사용을 잇기 위한 것이다.
