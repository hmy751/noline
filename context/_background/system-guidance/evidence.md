# 체계 지침의 구별과 선택 근거

[현재 본문](../../SYSTEM-GUIDANCE.md)과 [형성 맥락](context.md)의 범위를 재검토할 때 필요한 발화·문서 설명을 보존한다. 아래 발췌는 2026-10-20 데모 설계 대화의 사용자 발언과 같은 날 직접 읽은 참고 문서다. 전체 대화나 실제 제품 운영 결과의 기록은 아니다.

## 진입 본체와 분할에 관한 요청

사용자는 기존 진입 문서를 새 폴더 안으로 옮기는 것에 대해 다음과 같이 설명했다.

> 원래 의도가 저 위치에서 진입점으로 본체 같은 역할을 했잖아?

> 이런건 뭔가 컨벤션이 대문자로 두면 좋아보여

같은 성격의 예시로 DOCUMENT-WRITING을 제시하면서 수정 대상이 아님을 명시했다.

> 이것도 어찌보면 예시인데 이걸 건드리자는건 아니고 그냥 단순 참조해서 보라고 언급한거고 이것도 이거와 같은 층위야

상세 분할에 대해서는 다음과 같이 말했다.

> 그리고 `REFERENCE/composition.md` 사례 처럼 이렇게 세분화 하는것도 가능하다고 생각해 나도

이 발화는 현재 이름·본체 역할의 중요성과 분할 가능성, 대문자에 대한 선호를 지지한다. 모든 지침의 같은 파일 형태나 영구 경로를 확정한 발언으로 읽지 않는다.

## 명칭과 범위의 정정

‘운영 지침’을 제안받은 뒤:

> 흠 운영 지침이라 하니까 이게 정말 앞으로 모르는 세션한테도 잘 구별될까? 싶기도 한데 더 아이디어를 도출할수 없어?

개발 작업을 중심으로 한 정의에 대해:

> 근데 개발 작업이라는 시맨틱은 좀 안맞아보여 문서 체계일수도 있고 한데 그건 좀 아닌것 같고 뭐 없나 너가볼때 뭐가 나아보여?

진입 역할을 다시 물었을 때:

> 그럼 체계 진입 지침은? 진입이 안맞는건가?

현재 명칭과 독립 문서 작성의 선택:

> 그래 체계 지침으로 가고 이건 CONTENT-POLICY 여기 말고 독립문서로 만들자
> 그럼 만들기전에 여기에 관련한 대화 논의 읽고 잘 만들어봐

마지막 발화는 명칭과 독립 문서 작성을 채택한다. 영어 파일명·세부 문장·모든 문서의 분류까지 사용자가 직접 정한 것으로 올리지 않는다.

## 현재 범위

> work 는 냅두고 이미 구성한게 있잖아? current 등

> 4번은 다음 티켓이니까 이번에선 안 다룰거고

당시 4번은 워크플로·스킬의 입력 선택, 구현·검토·최종 확인 책임 구체화를 뜻했다. 이번 명명·본문 작성은 Work의 재편이나 그 후속 구현을 포함하지 않는다.

## 문서 작성 지침의 참고 예시

사용자가 지정한 읽기 전용 예시는 `reference-project/context/work/workspaces/DOCUMENT-WRITING.md`다. 2026-10-20에 확인한 제목은 ‘Workspace 문서 작성과 갱신’이며, 역할을 다음과 같이 설명한다.

> 이 문서는 Workspace를 이해하고 작업을 이어 갈 사람이 읽는 글의 내용·구성·갱신 기준을 소유한다. 문서를 읽은 사람이 필요한 의미를 이해하고, 근거를 찾아 판단·수정·다음 지시를 할 수 있게 하는 것이 목적이다.

본문은 설명의 충분성, 자료와 해석의 구별, 이유·조건의 보존, 읽기 흐름, 기존 문서 갱신과 작성 뒤 확인을 다룬다. 절차 연결뿐 아니라 문서의 내용 품질을 판단하는 지침도 이 역할에 포함될 수 있음을 보여 준다. 원본의 전체 규칙이나 Reference 운영 체계를 이 데모에 이식한 것은 아니다. 이 발췌만으로 역할 비교를 이해할 수 있으며 원본 경로는 현재 데모의 필수 읽기 경로가 아니다.
