# 담당자의 질문에서 직접 읽는 방법을 공유한 이유

[USAGE](../../USAGE.md)의 형성 맥락이다. 이 prototype은 Main이 필요한 정보를 요약해 전달하고 담당자가 그 요약만 수행하는 관계를 목표로 하지 않았다. Main은 목적·범위·접근점을 연결하고 담당자는 관련 원문과 실물을 직접 대조한다. 처음 질문이 구현·검토 중 달라질 수 있으므로 선택한 자료도 다시 고를 수 있어야 했다.

기존 read-project-context도 질문별 선택·유효한 읽기 재사용·작업 적용·원래 과업 복귀를 이미 다뤘다. 이를 한 번 Work에 가져오는 기능으로만 설명하면 새 workflow와의 관계를 잘못 판단하게 된다. 공통화한 것은 이 반복 가능한 방법이며 제품 계약·개인 판단·이번 Work의 선택을 합친 새 내용 정본이 아니다.

일반 읽기는 개발 중 수시로 일어나고, 읽기만 요청했을 때도 같은 방법을 쓸 수 있다. 이 때문에 매번 독립 스킬이나 새 담당자를 거치게 하기보다 공통 참조에서 방법을 공유했다. 능동적 본문 반영은 쓰기 범위와 끝나는 결과가 있으므로 [context-update](../../../.claude/skills/context-update/SKILL.md)에 두었다. 읽던 Main이 근거를 이어 사용해 반영할 수 있고, 두 문서를 서로 다른 사람이 순서대로 처리해야 한다는 뜻은 아니다.

사용자는 참조와 반영 스킬로 나뉘는 형태에 완전히 납득하지는 않은 채 잠정안으로 이어가자고 했다. 따라서 USAGE와 context-update는 실제 연결을 확인하는 prototype의 구성이다. 중복 읽기·입력 재작성·불필요한 호출이 생긴다면 파일 묶음을 다시 판단할 수 있다. 담당자 직접 읽기·영역별 내용 책임·Main의 전체 연결까지 다시 미정으로 돌리지는 않는다.

Work current는 이 읽기를 대신하는 원문 복사본이 아니다. 이번 목표에서 어떤 기준을 어떻게 적용했는지, 어떤 선택과 제한이 생겼는지, 현재 무엇이 남았는지를 보존한다. 다음 담당자는 그 현재 의미에서 시작해 필요한 원문을 직접 확인한다. 읽기 자체가 저장을 요구하지 않으며, 현재 요청의 중심과 부수 발견을 구별하는 판단은 Main과 개발 절차가 맡는다.

외부 자료에서는 Matt의 기존 domain 문서 소비와 능동적 구체화의 구별, Lauren의 담당자 직접 원칙 읽기와 상위 흐름·한정 수행의 구별을 참고했다. [근거와 적용 제한](evidence.md)에 판본을 남겼다. 정확한 파일 구성의 우월성이나 장기 효과가 그 자료로 입증된 것은 아니다.

사용자 요청의 경험 개선은 루프 스킬의 수행 계약으로 연결한다. 공통 읽기는 그 순서를 다시 정의하지 않고 평소 질문별 선택 읽기와 후보·채택 기준의 구별을 맡는다. [Personal 경험 모음의 형성 맥락](../../personal/_background/experience-collection/context.md)에서 경계와 선택 이유를 찾는다.

평소 읽기가 채택 기준만 본다고 표현하면 이미 선택한 한정 시도가 빠질 수 있다. 따라서 해당 작업의 기존 재개 지시에서 적용·종료 범위를 읽도록 연결했다. 시도의 선택·연결·종료 절차는 improvement-loop가 맡고 공통 읽기는 열린 후보 전수 조회로 확장하지 않는다.
