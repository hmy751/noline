## 대표 질문으로 다시 읽은 결과

Main이 원본과 보정본을 각각 읽어 다음 조건에서 선택이 달라지지 않는지 확인했다. 실제 제품 실행이나 새 AI 세션의 결과 비교는 아니다.

| 질문 | 양쪽에서 찾은 판단 |
| --- | --- |
| 문자열 isError를 boolean으로 바꿀 수 있으면 반드시 바꾸나 | 새 API와 기존 API를 구별한다. 기존 API는 명료함의 이득·실제 사용·비용으로 판단하며 가능성만으로 필수 변경이 되지 않는다. |
| 저장은 끝났지만 바로 최신 조회 결과가 필요한 소비자가 있다면 | 조회까지 기다릴 범위와 저장 실패 여부를 따로 판단한다. 저장 성공·조회 실패는 따로 전달할 수 있다. |
| 방어 코드가 반복되면 상태 머신을 도입해야 하나 | 모순과 독립 사실을 구별하고 이득·비용을 비교한다. 작은 국소 조건이면 기존 표현을 유지할 수 있다. |
| 같은 숫자를 쓰는 두 대기 시간을 합쳐야 하나 | 의미·끝내는 작업·변경 이유로 판단한다. 다른 이유면 분리할 수 있고 같은 약속이면 함께 관리할 수 있다. |
| 기능이 약속한 결과를 내지 않는데 이름을 좁혀도 되나 | 기존 소비자의 요구를 지우지 않고 부족한 결과를 만드는 동작을 고친다. |

## 적용 범위와 남은 확인

[형식 기준](../../../WRITING-FORMAT.md)은 실제 갈림길·순서·비교에 맞춰 표·번호를 선택하게 했다. 예시의 공통 범위와 국소 조건을 구별하고, 필요한 사례 링크는 해당 판단 가까이에 남긴다. 파일명이 기준 본문의 역할을 대신하지 않는다. 제품 설명·사례·체계 지침·스킬로의 일괄 확대와 Work 적용은 하지 않았다.

형식만 옮긴 이름 기준의 background는 보존했다. 형식 지침 자체의 선택·보완은 이 묶음의 맥락·근거에 남겼다. 새 형식을 읽은 AI의 신규 작성과 독립 세션 간 판단 동등성, 반복 사용 효과는 미확인이다. 문서 대조·표시 사본 검사와 그 시험을 구별한다.
