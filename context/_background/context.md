# 내용의 독립성과 작업 연결을 함께 둔 이유

이 문서는 [context 본문](../README.md)의 Personal·Project·Work 구별을 현재 이해할 형성 맥락이다. 개인 기준의 배포 방식이나 실제 제품의 설치 완료를 설명하지 않는다.

개인의 개발 판단과 제품 계약을 함께 쓰려는 목적에서 시작했지만, 초기 시안은 Project가 개인 기준의 원문을 직접 참조하고 채택·갱신까지 관리하게 했다. 그러면 제품을 이해하는 독자가 다른 주체의 기준을 알아야 하고, 개인 판단이 바뀔 때 제품 약속도 따라 바뀌는 듯한 관계가 생긴다. 사용자는 Project가 자기 문서를 독립적으로 담당하고, 둘을 연결하는 일은 워크플로나 스킬이 맡아야 한다고 정정했다. 이는 [직접 발화](evidence.md#독립-책임)로 확인한 방향이다.

그래서 현재는 Personal이 여러 제품에 가져갈 판단의 의미·조건을, Project가 제품의 의미·계약·지속 규약·현재 사실을 충분히 설명한다. Work는 이번 목표·사용처·비용에 두 입력을 대입해 선택과 결과를 남긴다. 이 관계가 필요한 까닭은 문장 중복을 없애려는 데만 있지 않다. 어떤 이유로 무엇을 고칠지를 각 내용의 책임에서 판단하려는 것이다. 자기 문서를 이해시키는 설명 중복은 가능하며, 개인 기준 변경만으로 Project를 함께 고치지 않는 기본값은 [후속 소유 정정](../personal/development/naming-and-completion/_background/records/2026-10-19-personal-ownership.md)에서 구체화됐다.

물리 위치도 따로 정정됐다. 앞선 시안은 개인 기준을 별도 ai-workspace 모형에 두었지만, 사용자는 대상 로컬 context 안에 관리·축적·수정할 층을 원했다. [로컬 위치 발화](evidence.md#로컬-context-위치) 뒤 세 영역을 demo context 아래에 두었다. 같은 부모 폴더는 읽는 위치를 가깝게 하지만 내용 소유를 합치지 않는다. 실제 Noline에 Personal이 원래 존재했다는 관찰로 소급하지도 않는다.

이 과정은 데모를 설계한 대화이며 Noline 팀의 제품 합의가 아니다. 현재 본문을 읽고 수정할 이유는 설명할 수 있지만, 저장소 간 배포·동기화·자동 읽기·장기 유지 효과는 확인하지 않았다. 초기 추천의 정확한 수락 범위와 이전 Main 답변 전체가 회수되지 않은 한계도 [기록](records/2026-10-19-ownership-and-local-context.md)에 남긴다.
