# 작업 이해안

구현을 시작하기 전에 이번 작업으로 무엇이 달라져야 하고 무엇을 잃지 않아야 하는지 사용자와 함께 맞춘다. 사용자가 필요하다고 판단해 직접 호출하는 예방적 보강이며, 일반 작업 대화에서 자동으로 끼어들거나 사용자가 이미 하던 인터뷰와 구체화를 대체하지 않는다. Code와 자료가 답할 사실은 먼저 조사하고, 결과를 바꾸는 선택만 사람이 판단할 수 있게 만든다.

## 시작

1. 실제 적용 프로젝트의 root AI 지침(예: `AGENTS.md`, `CLAUDE.md`)과 그 지침이 안내하는 관련 맥락 위치를 확인하고 필요한 기존 문서를 읽는다.
2. 공통 [`설명과 근거 기준`](../../../context/project/guidance/explanation-and-evidence-criteria.md)을 읽고 현재성·근거 범위·사람 판단 경계를 적용한다.
3. 사용자가 가리킨 Work, 현재 대화에서 이미 정한 내용, 관련 Workspace의 Spec과 필요한 Ticket을 확인한다. Spec·Ticket의 위치와 유지 방식, Main·Maintain의 역할은 root AI 지침이 안내하는 해당 프로젝트의 운영 기준을 따른다.
4. 현재 구현 사실이 선택을 바꿀 수 있으면 관련 source·configuration·test·사용 위치를 직접 조사한다. 사용자가 답할 수 없는 repository 질문으로 돌려보내지 않는다.

## 논의를 만드는 방법

먼저 다음을 구분한다.

- 사용자가 실제로 받고 싶은 결과. 기능 구현이면 요구 동작을, 코드 개선이면 개선할 구조와 보존할 동작을 함께 본다.
- 현재 code·문서·환경에서 확인된 사실과 그 기준 상태
- 반드시 보존할 제품 의미·제약·negative requirement
- 구현 결과를 실제로 갈라놓는 사람의 선택
- Current source를 보며 구현자가 열어 둘 세부

원하는 결과나 완료 경계가 추상적이고 여러 방식으로 해석될 수 있으면, 같은 대표 입력이나 사용 장면에서 사용자가 받을 결과와 겉보기에는 비슷하지만 부족한 결과를 대비한다. 특정 구현 방식의 이름만으로 충분·부족을 가르지 말고, 사용자가 받을 결과에서 무엇이 빠지는지 설명한다. 이미 정한 차이는 이해안에 남기며, 모든 작업에 사례나 별도 acceptance 문서를 추가하지 않는다.

이미 정해진 것을 열린 질문으로 되돌리지 않는다. 선택이 필요하면 선행관계가 있는 것부터 한두 개씩 묻고, 각 선택이 최종 결과에 만드는 차이와 추천 이유를 함께 설명한다. 대표 장면이 있으면 결과·불확실성·부담 중 선택으로 달라지는 점을 그 장면에서 비교한다. 현재 결과를 바꾸지 않는 질문은 만들지 않되, 중요한 선택을 피로 감소라는 이유로 삭제하지 않는다. 내부 module, class와 task를 미리 전부 결정해 사용자가 구현 세부까지 설계하게 만들지 않는다.

구현 전에 사람이 정해야 할 선택이 남아 있으면 먼저 선택 round를 제시한다. 그 응답을 `최종 작업 이해안`이라고 부르지 않는다. 사용자가 선택한 뒤, 또는 그런 열린 선택이 없을 때 최종 결과를 만든다. 실제 수행을 봐야 알 수 있는 내용은 현재 가정과 확인할 점으로 남긴다. 이미 충분한 선택과 사실이 있으면 의례적인 질문 round 없이 바로 최종안을 만든다.

## Work의 정의를 Spec으로 구체화한다

Work당 하나의 Spec에 해결할 문제와 이루려는 결과, 그 결과를 판단할 기준을 둔다. 여러 실행이 함께 지킬 의미·계약·제약과 현재 설계·가정을 담으며, 기능 구현과 코드 개선 모두에 사용한다. 코드 개선에서는 현재 구조의 문제와 바꾸려는 책임 배치, 보존할 동작과 개선 효과의 확인 기준을 구체화한다. 모든 내부 구현을 미리 결정하지는 않는다.

Spec의 문제·목표·범위, 요구 동작·대표 사례, 개념·입출력 계약, 품질·완료 판단, 제약·현재 설계·가정을 Work를 충분히 이해하고 정의하기 위한 관점으로 검토한다. 조사와 논의를 통해 목표·동작·계약·완료 기준을 더 분명하게 만드는 내용을 적극적으로 구체화한다. 지금 쓸 내용이 없다는 사실만으로 그 관점을 다룰 가치가 없다고 판단하지 않는다. 대표 사례를 함께 만들며 요구를 발견하거나, 입출력 관계를 정리하며 빠진 책임을 확인할 수 있다.

확인한 사실, 채택한 선택, 제안과 미확정을 구별한다. 검토 결과 이번 Work에 새로 정할 내용이 없거나 기존 계약을 그대로 따를 수 있으면 그 관계를 짧게 밝힌다. 필요한데 아직 모르는 내용은 확인할 가정이나 열린 판단으로 남긴다. 항목을 채우는 것 자체를 목적으로 무관한 내용이나 근거 없는 결정을 만들지는 않는다. Spec의 파일 구성은 기존 운영 기준을 유지하며, 내용이 적다는 이유로 필수 파일을 생략하지 않는다.

먼저 Spec으로 Work를 구체화하고, 이어 실행할 일을 나눌 때 그 내용을 바탕으로 Ticket을 분해한다. 분해 중 빠진 요구나 불분명한 관계가 드러나면 Spec을 보완하며 이어간다. 모든 미확정을 닫거나 이 skill에서 Ticket 분해까지 마쳐야 논의를 끝낼 수 있는 것은 아니다.

### Ticket으로 이어갈 때

Ticket은 Spec의 목표와 기준 안에서 확인 가능한 결과를 만들도록 범위를 묶은 실행 단위다. 무엇을 끝내서 넘기는지, 그 범위의 결과를 확인할 수 있는지, 나누는 방식 때문에 핵심 수행이 계속 뒤로 밀리지는 않는지 판단한다. 기능 구현은 필요한 계층을 연결하는 좁은 동작을 우선하고, 구조 개선은 동작 보존과 개선 효과를 확인할 수 있는 범위를 잡는다. API 자체가 전달 결과라면 그 계약과 완료 근거로 판단한다. 기반 작업을 따로 맡기면 완료의 한계와 실제 수행을 이어 갈 후속 작업을 드러낸다.

Ticket을 구체화할 때는 다음 네 부분을 한 문서에 두는 기본 구성을 사용한다. 정확한 제목·순서·세부 필드는 기계적으로 강제하지 않으며, Spec의 공통 내용을 복제하기보다 이번 실행에 필요한 구체성을 더한다.

- **맡은 결과와 범위:** 이번 실행으로 달라지는 것, 관련 Spec 요구와 필요한 제외·후속 범위.
- **실행 맥락과 접근:** 필요한 Spec·원자료·코드·앞선 결과, 선행 작업과 막힘, 현재 설계와 선택 이유, 확인할 가정과 실행 중 정할 부분. 링크만으로 의미가 이어지지 않으면 핵심 내용도 남긴다.
- **완료 조건과 확인 방법:** 관찰할 결과와 확인 방법. 코드 개선에서는 기존 동작의 보존과 구조 개선의 근거를 각각 정한다. 보존 조건은 변경 전부터 통과할 수 있다. 다른 Ticket이 맡은 결과를 이번 완료 조건으로 삼지 않는다.
- **현재 상태와 실제 결과:** 실제 수행·확인 근거와 보고받은 내용, 막힘·남은 일·미확인. 실행 전에는 짧게 두고 진행에 따라 채우며, 앞의 확인 계획과 실제 결과를 구별한다. 필요한 상세 이력은 기존 records에 연결한다.

유용한 내용은 적극적으로 구체화하되 아직 결정하지 않은 구조나 파일별 할 일을 억지로 만들지 않는다. Ticket 안에서는 필요한 여러 세부 작업과 설계를 이어갈 수 있으며 API task 같은 별도 관리 계층을 추가하지 않는다. 이번 실행 안의 설계와 이유는 Ticket에 두고, 여러 실행이 함께 지킬 계약·설계나 Work의 기준에 영향을 주는 판단은 Spec으로 연결한다. 문서 갱신과 다음 실행의 연결은 아래 Main·Maintain 관계를 따른다.

## 실제 결과

결론을 먼저 둔 `작업 이해안 — <작업>`을 돌려준다. 대상에 필요한 만큼 다음 관계가 보여야 한다.

- **이번에 만들 결과:** 작업이 끝났을 때 사용자·제품·system에서 실제로 달라지는 것
- **확인한 현재 사실:** AI가 확인한 source와 기준 상태, 아직 다시 확인해야 하는 사실
- **지킬 경계:** 보존할 의미·제약·하지 않을 것과 대체 완료로 인정하지 않을 것
- **정한 선택:** 사용자가 고른 선택과 그 결과. 선택이 없으면 억지로 만들지 않는다.
- **열어 둘 구현:** 실제 code를 보며 정할 수 있지만 위 경계를 약화하면 안 되는 부분
- **바로 이어갈 행동:** 구현 전에 필요한 마지막 확인 또는 첫 실행 범위

항목을 빈 형식으로 모두 출력하지 않는다. 짧은 작업이면 결론과 경계를 자연스러운 문단으로 합친다. 사용자가 구현에 들어갈 수 있고 대체 완료로 삼으면 안 되는 것이 보이면 끝내되, 중요한 위험이나 예외를 인지피로 감소라는 이유로 삭제하지 않는다.

이 관계를 Spec의 해당 내용과 연결해 돌려준다. 기존 Spec이 있다면 무엇을 유지하고 새로 구체화하거나 바꾸려는지 드러내며, 같은 작업 정의를 별도 장기 문서로 중복 유지하지 않는다.

## 결과의 효력

작업 이해안은 현재 대화의 이해·선택 산출물이며, 반환했다는 사실만으로 Spec·Ticket의 실제 반영까지 끝난 것은 아니다. Main은 공유한 내용을 바탕으로 같은 대화의 후속 논의나 이미 허용된 작업 분해·실행을 이어갈 수 있다.

Spec·Ticket과 관련 Workspace 문서 갱신은 기존 운영 범위의 Maintain에 맡긴다. Main은 채택한 내용·이유·남은 확인을 Maintain이 받는 최종 응답에 드러내고, 길어진 근거는 정확한 로컬 결과 문서로 연결할 수 있다. 다른 실행자의 결과도 Main이 검토해 이 입력으로 연결해야 하며, 도구나 서브 대화를 Main이 읽은 것만으로 전달됐다고 보지 않는다. 위임할 때는 결과와 근거를 Main에게 반환하도록 하고 같은 Spec·Ticket을 중복 수정하지 않게 역할을 정한다.

다른 실행자나 새 세션이 문서를 기준으로 시작하는 등 다음 작업이 문서에 의존할 때는 Main이 필요한 내용의 실제 반영을 확인한 뒤 사용한다. 비동기 접수와 문서 준비를 구별하되 매 응답마다 기다리거나 별도 인계문·승인 절차를 만들지는 않는다.

이 skill은 이해안을 만들기 위한 read-only 조사를 할 수 있다. 구현은 사용자가 허용한 범위에서 이어가며, 설명·논의 요청만으로 실행 권한을 넓히지 않는다. Maintain의 기존 문서 관리도 별도 운영 계약을 따르며 이 skill이 그 허용 경로를 넓히지 않는다.

## 하지 않을 것

- 피로를 줄인다는 이유로 정확성, 예외, 위험과 결과를 바꾸는 선택을 없애지 않는다.
- 이미 정한 요구를 다시 인터뷰하지 않는다.
- Codebase에서 확인할 수 있는 사실을 사용자 취향 질문처럼 묻지 않는다.
- 작은 구현 조각을 사용자에게 필요한 전체 결과와 같은 완료로 놓지 않는다.
- 사용자가 고르지 않은 선택을 채택된 결정처럼 쓰지 않는다.
