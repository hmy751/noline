# 독립 목표를 이어 갈 상태로 만드는 이유

이 자료는 [create-context-workspace](../SKILL.md)의 목적과 현재 구성 이유를 설명한다. 목표를 새로 나누는 선택과, 이미 요청한 새 목표의 상태를 실제로 구성하는 수행을 구별하기 위해 생성 과업을 유지했다. 같은 목표를 다른 대화에서 이어가는 것만으로 새 Work를 만들면 현재 상태가 갈라지고 기존 근거를 반복해서 옮겨야 한다. 반대로 독립 목표를 오래된 Work의 다음 행동으로만 붙이면 무엇을 마쳐야 하는지와 확인 범위가 섞인다.

기존 생성 원형에도 새 current가 필요한 의미를 직접 소유하고 이전 상세를 단방향으로 참고하는 방향이 있었다. 이 prototype은 그 책임을 유지한다. 바뀐 부분은 당시 설치된 Harness·두 번째 이후 Workspace·기계 계약·activation을 전제하던 수행을 현재 수동 demo의 진입·읽기·목록 선택에 맞춘 것이다. 새 관리 스킬이 context 전체를 맡게 하거나 실행기를 흉내 내는 것이 목적은 아니다.

내용의 정체성·필수 의미·원본 보호·인수와 전환 기준은 [Work 계약](../../../../context/work/workspaces/CREATE-AND-TRANSITION.md)이 소유한다. 스킬은 이를 찾아 수행하고 결과를 반환한다. 이 분리로 스킬의 이름이나 실행 수단을 바꾸더라도 같은 Work 계약으로 수동 작업을 이어갈 수 있다. 반대로 Work 구조가 바뀌면 생성·재개에서 그 계약을 사용하는 경로를 함께 확인해야 한다.

사용자는 기존 스킬을 그대로 유지하거나 억지로 새 스킬을 늘리기보다 전체 workflow와 연결된 책임·유지를 판단하라고 요청했다. 생성은 독립 요청·쓰기 범위·인수 결과가 있어 별도 수행을 유지했다. `create-context-workspace`는 기존 책임을 이어 붙이는 prototype 이름이며, 실제 배포·호환 진입의 최종 이름을 결정한 근거는 아니다. 읽기 공통 참조와 반영 스킬의 잠정 구성도 생성의 내용 소유를 바꾸지 않는다.

완료·중단·재개의 검토에서는 새 Work 생성이 이전 요구의 완료를 뜻하지 않는다는 점과, 늦은 결과의 원 Work 귀속이 과거 쓰기 권한을 고정하지 않는다는 점을 명료화했다. 이 차이는 진행 중 담당자가 같은 파일을 수정하는 상황에서도 기존 의미를 이어받으면서 최신 배정·공유 상태를 지키기 위한 것이다.

Matt의 목적에 맞춘 handoff와 Lauren의 이전 결과를 활용하는 pickup은 인계에 필요한 정보만 잇고 끝난 일을 무조건 다시 하지 않는 참고점이었다. 우리 Work의 정체성·현재 의미 직접 계승·기본 선택·생성 권한은 기존 사용자 논의와 Work 계약에서 정했다. 외부의 임시 인계 파일·자동 commit·전체 mode 실행을 가져오지 않았으며, 자세한 출처·판본과 한계는 [근거](evidence.md)에서 찾는다.
