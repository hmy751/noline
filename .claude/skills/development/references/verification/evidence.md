# 검사와 관찰이 주장을 뒷받침하는지 판단한다

현재 대상에 관한 결론을 어떤 검사·관찰이 어느 범위까지 지지하는지 판단한다. 검증자는 [검증 수행](INDEX.md)의 기본 검사·적절성 판단·추가 실행에서 사용하고, Main·조사 담당·구현자도 기존 결과를 해석하거나 자기 확인을 구성할 때 직접 적용한다. 이 상세를 읽었다는 사실이 별도 검증을 맡겼거나 독립 확인을 마쳤다는 뜻은 아니다.

주장에 맞는 기대 결과·관찰·유효성을 연결하는 방법이 이 문서의 범위다. 검증 의뢰·권한·실행 공백의 담당·전체 완료는 검증 수행과 [development](../../SKILL.md)가, 제품별 실행 방법·데이터·환경은 대상 Project가 소유한다. 이미 유효하게 확인한 내용은 재사용하며, 필요한 판단을 마치면 원래 구현·조사·검증·설명으로 돌아간다.

## 주장과 기대 결과를 먼저 연결한다

이번 요구·유효한 정정·제품 계약·사용처에서 어떤 조건에 어떤 결과가 필요한지 잡는다. 정상 결과와 함께 중요한 실패·상태 보존도 본다. 작성자가 언급하지 않았더라도 요구에 필요한 결과는 포함한다. 현재 구현·출력·새 설명 문서는 이 기대와 대조할 대상이며, 그 내용만 되풀이해 기대값을 만들지 않는다.

기대값은 요구·유효한 계약·독립된 사례가 지지해야 한다. 구현의 상수·계산식을 검사 안에서 다시 실행해 같은 값을 얻는 것은 같은 가정을 반복할 수 있다. 반대로 기존 기대값이 원요구와 어긋난다면 그 근거를 먼저 바로잡고 무엇이 달라졌는지 밝힌다. 통과시키기 위해 계약을 낮추거나 명확히 도출할 수 있는 기대 결과를 사용자에게 다시 정하게 하지 않는다. 자료가 더해지면 기대를 보완할 수 있으며 별도 명세서나 엄격한 열람 순서를 만들 필요는 없다.

## 검사가 실제로 지나간 경계와 관찰을 읽는다

검사 이름·통과 요약에서 관련 근거를 찾은 뒤, 주장을 가르는 실제 입력·실행 경로·assertion을 대조한다. 명령 성공만으로 검사가 실행됐다고 보지 않는다. 필요한 테스트가 선택됐고 의도한 산출물·환경을 실행했는지 확인한다. 모든 검사 본문을 읽는 것이 목적은 아니며, 기계가 확실하게 판별한 동일 항목을 자연어로 다시 판별하는 데 시간을 쓰지 않는다.

공개 인터페이스와 소비자가 받는 결과를 우선해 무엇을 관찰했는지 본다. 저장·외부 부작용 자체가 계약이면 DB·파일·로그 관찰도 사용한다. 내부 함수가 호출됐다는 확인이 사용자가 필요한 결과나 실제 의존 연결을 확인하는지 대조한다. 구조에 묶인 assertion이 깨진 것과 약속한 동작이 달라진 것도 구별한다.

mock·fake·test mode가 어느 경계를 대신했고 어떤 실패를 생략했는지 확인한다. 대체 자체를 금지하거나 그 결과를 버리지 않고, 실제 통과한 범위와 남은 범위를 나눈다. 예를 들어 저장을 기다리는 순서를 메모리 어댑터로 확인했다면 그 순서의 근거로 쓸 수 있다. 디스크의 부분 기록·프로세스 재시작 뒤 복구까지 결론 내려면 그 경계의 근거가 더 필요하다. 같은 테스트가 한 주장에는 충분하고 더 넓은 주장에는 부족할 수 있다.

## 기존 결과가 현재 대상에도 유효한지 판단한다

원본 실행 결과와 그 조건을 현재 대상에 대조한다. 대상 판본뿐 아니라 검사 코드·설정·데이터·의존 조건·기대 결과도 결과의 유효성에 영향을 준다. 현재 주장과 관련된 차이가 어느 확인에 영향을 주는지 판단한다.

- 관련 조건이 유지되고 원본이 현재 주장에 필요한 경계를 확인했다면 재사용한다. 이미 충분한 자동 E2E를 수동으로 똑같이 반복하거나 전체 suite를 항상 재실행하지 않는다.
- 원본이 없거나 실제 실행 산출물·조건이 다르거나 중요한 실패가 빠졌다면 필요한 재실행·추가 확인을 한다. 결과가 불안정하면 한 번 성공할 때까지 반복해 통과시키지 않고 조건을 좁히거나 다른 관찰을 찾는다.
- 일부가 달라졌다면 유효한 부분은 유지하고 영향받은 경계를 다시 확인한다. 영향이 불분명하면 이를 해소할 만큼 넓힌다. 새 커밋이라는 이유만으로 모두 폐기하거나 같은 기능이라는 이유만으로 이전 통과를 유지하지 않는다.

예를 들어 호출 순서를 지키는 코드는 같아도 저장 어댑터가 바뀌었다면 기존 순서 검사의 관련 근거는 남을 수 있다. 새 어댑터의 저장 확정·실패 뒤 상태·재시작 결과는 이전 메모리 검사의 통과로 이어받을 수 없다. 무엇이 바뀌었는지와 주장 범위를 함께 보면 유지할 확인과 새로 필요한 확인을 나눌 수 있다.

## 주장에 필요한 관찰을 고른다

아래는 근거를 선택하는 관점이며 모든 작업에 같은 검사 묶음을 추가하는 목록이 아니다.

| 확인할 주장 | 근거를 고르는 기준 |
| --- | --- |
| 버그가 해결됐다 | 원래 조건의 재현과 수정 뒤 결과를 잇는다. 가능하면 같은 조건의 수정 전 실패도 비교한다. |
| 기능·통합이 작동한다 | 실제 사용자·호출자 진입부터 결과와 필요한 저장·외부 효과를 잇는다. 함수 성공만으로 설정·권한·실제 의존 연결을 확인했다고 하지 않는다. |
| 리팩터링이 동작을 보존한다 | 공개 계약·소비자·중요한 실패·상태 수명과 부작용의 전후를 대조한다. 구조에 묶여 깨진 검사와 실제 회귀를 구별한다. |
| 성능·접근성·권한·데이터 보존을 충족한다 | 이번 요구나 영향받은 약속의 실제 조건에서 확인한다. 한 수치나 정상 경로의 통과로 다른 약속까지 충족 처리하지 않는다. |
| 문서·스킬이 원하는 판단을 이끈다 | 링크·형식 검사, 의미 대조, 필요할 때 대표 요청의 실제 수행을 구별한다. 호출·읽기 성공이나 한 번의 응답을 일반 효과로 올리지 않는다. |

검사가 중요한 결함을 잡는지 의심되면 원래 재현·실패 사례·좁은 대조로 확인한다. 불변식·입력 조합·순서가 중요한 공백을 만들면 속성 기반 검사·모델 대조·형식 검증을 조건부로 비교한다. 모델과 실제 코드의 대응·반례·가정·유지 비용을 확인하며 작은 모델의 통과를 앱 전체의 보장으로 확대하지 않는다. 새 도구·전수 mutation test·모든 변경의 TDD 재작성을 기본으로 요구하지 않는다.

다음 확인은 사용자 결과에 대한 영향, 남은 근거 공백과 실패를 발견·복구할 가능성으로 고른다. 새 확인이 중요한 미확인을 구별하면 수행하고, 새 변화·실패·의문 없이 같은 사실만 반복하면 그 확인은 끝낸다. 실행이 막혔으면 [실행 공백의 처리](INDEX.md#실제-경로와-실행-공백을-다룬다)로 담당·준비를 연결한다. 필수 경로의 공백은 다른 검사의 통과로 해소되지 않는다.

## 근거가 지지하는 범위로 원래 판단을 잇는다

어떤 주장에 어떤 대상·조건·기대와 실제 결과가 대응하는지, 재사용한 원본·직접 실행·새 사례·추론·미확인이 무엇인지 연결한다. 고정된 긴 보고서가 필요하지는 않다. 설명에 한계를 적는 것으로 수행 가능한 중요한 추가 확인을 대신하지 않고, 미확인을 곧바로 제품 결함으로 바꾸지도 않는다.

이 판단은 구현자의 자기 확인, Main·조사 담당의 결론, 검증자의 요구별 판정에 쓰인다. 별도 검증을 맡았다면 [반환과 충분성](INDEX.md#반환-시점과-완료에-필요한-충분성을-구별한다)까지 이어 수행한다. 일부 근거의 적절성을 확인했다는 사실만으로 Work 전체·운영 설치·사용자 수락의 완료를 선언하지 않는다.
