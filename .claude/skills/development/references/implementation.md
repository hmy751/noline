# 구현을 완성하고 판단할 근거를 넘긴다

구현을 맡았거나 검토·검증 뒤의 수정을 배정받았을 때 읽는다. 맡은 요구를 구체 설계와 실제 사용 경로로 완성하고, 자기 확인과 중요한 선택의 근거를 Main에게 연결하는 수행 상세다. Main이 직접 구현할 때도 같은 책임을 적용한다. 전체 역할 배치·수정 담당·완료 판단은 [development](../SKILL.md)가 소유한다.

후속 검토가 첫 결과의 품질을 대신하지 않는다. 구현자는 현재 근거로 적절하다고 판단하는 결과를 완성하되, 가능한 모든 대안의 열등함이나 모든 외부 환경의 동작까지 입증해야 인계할 수 있다고 요구하지 않는다. 아래 내용은 구현과 수정 중에 적용하며 마지막에 별도 전체 검사를 한 번 더 수행하는 고정 순서가 아니다.

## 맡은 결과를 설계와 사용 경로에 연결한다

현재 배정의 목표·범위·보존 조건과 실제 대상 판본을 확인한다. 질문에 필요한 원문 선택·추가 탐색·유효한 이해의 재사용은 대상 context의 공통 방법을 따른다. 이 Project에서는 [USAGE](../../../../context/USAGE.md)를 사용한다. Main의 접근점과 요약에서 출발하되 관련 요구·기준·계약을 직접 읽고 실제 코드·사용처와 대조한다.

읽은 내용을 이번 설계에 어떻게 적용할지 판단한다. Personal의 기준, 제품의 약속, 이번 Work의 선택, 현재 구현 사실을 같은 종류의 지시로 취급하지 않는다. 문서와 코드가 다르면 이번 결과가 지켜야 할 약속과 고쳐야 할 사실을 구별한다. 범위 안에서 확인할 수 있는 사실은 직접 살피고, 목표·보존 계약이나 수정 권한을 바꿔야 하는 선택은 이유·영향과 함께 Main에게 연결한다. 중요한 충돌이나 막힘은 최종 인계까지 숨기지 않는다.

맡은 요구를 사용하는 호출부·설정·연결과 필요한 설명까지 완성한다. 함수나 파일을 추가한 사실만으로 사용 가능한 결과가 됐다고 보지 않는다. 한편 의도적으로 부분 단위를 맡았다면 그 경계를 완성하고 남은 통합을 드러낸다. 전체 제품 연결이 다른 담당의 책임이라는 이유로 맡은 단위를 미완성으로 남기거나, 부분 배정을 전체 제품 구현으로 확대하지 않는다.

필요한 설명의 소유와 수정 권한도 구별한다. 코드 안의 설명·배정된 사용 안내는 맡은 결과에 맞추고, 지속할 Personal·Project 본문이나 공유 Work를 바꿀 필요가 보이면 아래의 제안·인계로 연결한다. 코드 구현을 맡았다는 사실만으로 그 정본의 편집 권한까지 생기지는 않는다.

## 실제 사용과 변경 장면으로 자기 설계를 판단한다

관련 기준의 이름을 따랐다는 설명에서 멈추지 않고, 실제 사용처에서 호출 순서·상태·수명·실패·변경 위치를 따라간다. 호출자와 유지보수자가 무엇을 알아야 올바르게 사용할 수 있는지, 여러 곳을 함께 바꿔야 하는 이유가 무엇인지 살펴 자기 선택의 적절성을 판단한다. 기존 패턴을 재현했다는 사실이나 설명을 붙였다는 사실이 그 판단을 대신하지 않는다.

예를 들어 초기화 책임을 한곳에 모으는 변경이라면, 재시도 때 호출자가 여전히 내부 상태 조합을 초기화해야 하는지, 후속 작업을 하나 추가할 때 어느 책임을 함께 고쳐야 하는지 본다. 목표로 삼은 이해·변경 부담이 실제로 줄었는지 확인하고 필요한 경우 자기 설계를 다시 고른다. 이는 구조 개선을 판단하는 가상 장면이며 특정 초기화 구조를 모든 작업에 요구하는 기준은 아니다.

비교의 깊이는 이번 목표·영향·불확실성에 맞춘다. 중요한 선택과 절충을 설명할 만큼 대조하되 대안의 개수나 별도 설계 문서를 채우는 것을 목표로 삼지 않는다. 구현 중 새 사용처나 실패가 설계 질문을 바꾸면 관련 근거를 추가하고, 이미 적용한 가정과 확인 중 무엇이 영향을 받는지 함께 본다.

## 구현 중부터 자기 확인과 관찰을 준비한다

대상 Project의 필수 lint·타입·빌드·관련 자동 테스트를 구현 중부터 활용하고 변경에 맞게 반복한다. 자동 앱 E2E도 기계 검사에 포함한다. 필요한 실패 주입·특수 데이터·전후 기준선·실제 어댑터 관찰은 Main과 구현자가 구현 중 준비한다. 검토나 별도 검증 단계에서 처음으로 확인 수단을 찾도록 남기지 않는다. 이 준비와 자기 확인이 이후의 독립 판정을 대신하지는 않는다.

기대 결과는 요구·제품 계약·독립된 사례에서 가져온다. 구현의 분기·계산이나 현재 출력을 그대로 기대값으로 옮겨 같은 가정을 두 번 확인하지 않는다. 기존 검사로 어떤 주장을 뒷받침할 수 있는지와 결과의 유효성을 판단할 때는 [검증 근거의 적절성·재사용](verification/evidence.md)을 적용한다. 그 상세를 사용했다고 별도 검증 역할을 수행한 것으로 세지 않는다.

자기 확인은 변경 목적에 이어져야 한다. 기능은 요구한 사용 경로와 중요한 실패 조건을, 버그는 원래 실패 조건에서의 수정 결과를, 리팩터링은 보존할 동작과 줄이려던 이해·변경 부담을 대조한다. 예를 들어 ‘저장이 끝난 뒤 성공 화면으로 이동한다’는 요구라면 성공 반환값만 보기보다 저장 지연·실패 때 화면 이동이 어떻게 되는지 확인한다. 이 예시는 가정한 요구에 대한 판단 방법이며 실제 제품의 검증 결과가 아니다.

스스로 발견한 범위 안의 누락·결함은 고치고 영향받는 확인을 갱신한다. 앞서 얻은 근거가 후속 변경에도 유효하면 재사용하고, 무효가 된 부분은 다시 확인한다. 접근이 막힌 실행은 무엇을 확인하지 못했는지와 그 영향으로 구별하며, 가능한 확인은 계속한다. 외부 실행이 실제로 필요한데 준비가 부족하면 [실행 공백의 연결](verification/INDEX.md#실제-경로와-실행-공백을-다룬다)을 따라 Main에게 필요한 담당·접근·결정을 알린다.

## 후속 수정을 맡으면 바뀐 과제와 근거를 잇는다

개선 의견이나 검증 결과를 받은 뒤에는 Main이 배정한 수정 범위·기대 이득·보존 조건·권한을 확인한다. 의견의 모든 대안을 자동 채택하거나 검토자라는 역할만으로 공유 산출물의 수정 담당을 바꾸지 않는다. 같은 담당자가 이어 수행하더라도 바뀐 요구·계약·공유 상태와 이전 근거의 유효 범위를 확인한다. 담당·판본·병행 변경의 운용은 [실행 배치](execution.md)를 따른다.

검증자가 만든 재현·입력·기대 결과가 있으면 이를 이어받아 문제를 수정하고 같은 조건에서 자기 확인한다. 필요한 지속 테스트와 영향받은 검사를 갱신하며, 구현·검사·설정·데이터·의존 조건의 변화로 더 이상 근거가 되지 않는 이전 결과를 구별한다. 반환에는 해결한 문제, 실제 수정과 자기 확인, 얻은 개선과 새 부담, 남은 한계를 연결한다. 재검토·별도 재검증의 배정과 전체 종료는 Main이 판단한다.

## 완성한 범위와 남은 일을 구별해 인계한다

| 현재 결과 | 반환할 의미와 이어갈 일 |
| --- | --- |
| 맡은 결과와 필요한 자기 확인을 마쳤고 현재 근거로 선택이 적절하다고 판단한다 | 검토할 구현 결과로 인계한다. 더 나은 선택이 있을 가능성 자체는 인계를 막지 않는다. |
| 구현 결과는 있으나 외부 접근·환경 제약으로 중요한 확인이 남았다 | 결과와 확인한 범위, 시도한 확인, 막힌 조건과 남은 영향을 함께 반환한다. Main은 가능한 검토를 이어갈 수 있지만 미확인을 요구 충족으로 처리하지 않는다. |
| 알려진 필수 요구 미충족이나 설계·계약 충돌이 남았다 | 완료 인계가 아닌 진행 중 문제로 알린다. 맡은 권한으로 해결할 수 있으면 계속 처리하고, 배정 밖 선택은 대안·추천·영향과 함께 연결한다. |

필수 기능의 미구현과 외부 확인의 부재를 섞지 않는다. 실패 처리가 요구인데 구현하지 않은 상태는 맡은 결과의 미완성이다. 처리와 로컬 확인을 마쳤지만 실제 서버에 접근할 수 없는 상태는 통합 확인의 한계다. 어느 쪽도 ‘테스트 통과’나 ‘외부 검증 대기’라는 표현으로 감추지 않는다.

Main이 다시 조사해 조립하지 않고 판단할 수 있게 실제 결과·대상·근거를 연결한다. 무엇이 달라졌고 어느 요구에 답했는지, 선택을 가른 기준·이유·절충, 실제 확인과 그 한계, 남은 문제·다음 판단이 드러나야 한다. 코드·diff·검사 원본의 접근점과 기준 판본·포함한 미커밋 변경을 현재 작업에 필요한 만큼 식별한다. 모든 읽기 목록·기준별 준수표·고정 제목이나 새 인계 파일을 요구하지 않는다.

지속 본문에 반영할 변화가 확인되면 바뀔 의미·적용 범위·직접 근거·미확인을 기존 반환에 붙여 제안한다. 아는 본문 위치나 문안은 도움이 되지만 Project 전체 재조사나 별도 제안서는 전제하지 않는다. 코드가 바뀌었다는 이유만으로 문서 갱신을 제안하거나 한 작업의 선택을 지속 기준으로 올리지 않는다. Main의 전체 검토·실제 반영으로 이어지며, 별도로 문서 편집까지 배정받았다면 그 범위와 대상 관리 계약을 따른다.

구현자의 선택 이유와 자기 평가는 다음 판단자가 대조할 근거다. 동의해야 할 결론이나 검토 범위의 상한으로 쓰지 않는다. Main이 직접 구현했다면 현재 결과와 근거를 검토에 연결할 수 있으면 되며 자신에게 별도 인계 보고를 쓰지 않는다. 구현 반환, 검토·검증의 종료와 작업 전체 완료는 [development의 연결 책임](../SKILL.md#선택을-수정과-종료로-잇는다)에 따른다.

이 상세의 목적·책임을 이해하거나 수정할 때는 development의 [형성 자료](../_background/README.md)를 사용한다. 구현 방법을 보완하는 일과 Personal·Project의 기준·제품 약속을 채택하는 일은 구별한다.
