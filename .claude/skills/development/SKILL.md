# Development — 맥락을 판단과 결과로 연결한다

요구에 맞고 사용자가 이해하고 유지할 수 있는 개발 결과를 만든다. 관련 기준으로 첫 결과를 만들고, 의미 있는 다른 선택을 독립적으로 살피며, 필요한 수정과 확인을 실제 결과·사용자 판단·다음 작업으로 잇는다.

Main은 현재 사용자와 대화하는 전체 작업 담당자다. 별도 lead를 하나 더 만드는 역할이 아니다. 이 본문은 Main의 공통 수행 계약과 전체 흐름·역할·완료와 기록 연결을 소유한다. Work 문서의 실제 갱신 담당·허용 경로는 [기존 Work 관리 계약](../../../context/work/workspaces/spec-and-tickets/MAINTENANCE.md)이 소유한다. 구현·수정을 맡은 담당자는 [구현 상세](references/implementation.md)에서 설계·완성·자기 확인·인계를 이어 수행한다. [검토 상세](references/review.md)는 더 나은 선택의 비교와 Main의 채택 판단을, [검증 상세](references/verification/INDEX.md)는 요구 충족의 확인·공백·반환·재검증을 설명한다. 담당자를 배정하거나 세션을 이어 쓸 때는 [실행 배치](references/execution.md)를 읽어 모델·입력·재사용·판본 조건을 맞춘다. 역할 구분을 매번 같은 수의 에이전트를 호출하는 순서로 적용하지 않는다.

## 구현부터 검증·완료까지 연결한다

이번 요청이 포함하는 단계부터 수행한다. 구현 중 자기 확인, 개선 선택의 판단, 최종 요구 충족의 검증을 구별하되 각 결과를 다음 담당자에게 연결한다.

| 흐름 | 수행과 인계 |
| --- | --- |
| 요구·맥락과 구현 | Main이 목표·보존 조건·관련 맥락을 연결한다. 구현자는 실제 사용 경로까지 완성하면서 Project의 기계 검사를 활용하고 관찰 경로를 준비한다. |
| 개선 검토와 수정 | 개선 검토자가 현재 선택과 의미 있는 대안을 비교한다. Main이 채택·담당을 정하고 수정자가 자기 확인과 영향받은 검사를 갱신한다. |
| 최신 결과의 별도 검증 | 검증자가 필요한 기본 검사의 실행·유효성, 요구에 대한 검사 적절성, 중요한 공백의 추가 실행을 잇고 근거를 반환한다. 이 세 수행을 별도 agent로 나누지 않는다. |
| 문제 해결과 재검증 | Main이 제품·검사·환경·요구 문제에 맞게 담당을 연결한다. 수정자의 자기 확인 뒤 검증자가 원래 재현·필요한 원래 사용 경로와 영향받은 조건을 다시 확인한다. |
| 전체 완료·설명·기록 | Main이 최신 근거·남은 공백으로 전체 상태를 판단하고 사용자에게 결과를 설명하며 해당 Owner의 관리 계약으로 기록과 실제 반영을 연결한다. |

의미 있는 동작·계약·통합 변경에는 구현·수정에 참여하지 않은 별도 검증자 한 명을 기본으로 한다. 오탈자·의미 없는 형식 변경처럼 정해진 검사와 직접 대조로 충분하면 Main 확인으로 줄인다. 파일 수나 자신감으로 생략하지 않는다. 검토의 호출·축소는 [검토 상세](references/review.md#main은-검토-시점과-입력을-정한다), 검증의 시작·축소·입력은 [검증 상세](references/verification/INDEX.md#main은-확인-가능한-최신-결과를-넘긴다)를 따른다. 독립적으로 완성한 단위의 조기 검증과 전체 통합 확인도 구별한다.

## 이번 요청에서 시작한다

사용자가 원하는 결과, 유지할 목표·제약·계약, 현재까지 만들어진 결과와 미정을 구별한다. 이어 하는 작업이면 대상의 진입 지침에서 지정한 Workspace와 Spec/Ticket·현재 상태·산출물을 읽는다. 과거 기록의 다음 행동을 현재 지시로 취하지 않는다.

요청한 일에 맞춰 참여한다. 구현 요청에서는 설계와 자기 확인을 포함한 결과를 만들고, 검토 요청에서는 기존 결과의 판단 근거를 반환한다. 재개에서도 이번 요청이 원하는 결과를 기준으로 참여한다. 현황·배경 이해를 요청하면 현재 선택의 이유·상태·남은 판단을 복원해 설명하고, 실행까지 맡겼다면 해당 작업을 이어간다. 어떤 경우에도 스킬을 읽었다는 이유로 이미 끝난 단계를 다시 수행하거나 요청받지 않은 수정을 시작하지 않는다.

목표를 정하는 데 실제로 필요한 선택은 Main이 기존 대화와 원자료를 확인해 구체화한다. [작업 논의](../work-discussion/SKILL.md)는 사용자가 직접 호출했을 때만 사용하며, 목표가 불명확하다는 이유로 자동 호출하지 않는다. 충분한 작업 정의를 매번 다시 쓰지 않는다. 무엇을 만들지의 선택과 어떻게 구현할지의 기술 선택을 구별하며, 기존 위임 안의 판단은 Main이 맡는다.

## 맥락의 소유와 현재 적용을 구별한다

대상 Project의 진입점에서 아래 정본을 찾는다. 이 스킬의 위치를 제품 코드나 Workspace의 위치로 가정하지 않는다. 이 Project의 실제 맥락은 [context](../../../context/README.md)에 있으며, 아래 관계는 특정 로그인 작업에 한정되지 않는다.

| 입력 | 소유하는 의미 | 이번 작업에서 사용하는 방법 |
| --- | --- | --- |
| Personal | 여러 작업에 가져오는 개인의 판단 기준·조건과 협업 경험·열린 후보 | 현재 설계·접근법·표현·선택에 관련된 기준을 고른다. 현재 본문이 개발 예제 중심이라고 Personal 전체를 코드 품질 규칙으로 한정하지 않는다. |
| Project | 제품의 의미·약속, 지속할 개발 규약, 현재 구현에 관한 사실 | 이번 결과가 지킬 계약과 실제 사용 환경을 확인한다. 계약과 현재 구현이 일치한다고 가정하지 않는다. |
| Work | 이번 목표·제약·선택·진행·입력·결과·기록 | Spec/Ticket과 현재 상태에서 작업 범위를 복원하고, 선택과 확인 결과를 이어간다. |
| 실제 산출물·실행 근거 | 현재 존재하는 코드·문서·동작과 확인한 사실 | 문서의 약속·작성자의 설명과 대조한다. 존재하는 구현은 증거이며 자동으로 올바른 선례가 되지는 않는다. |

Personal의 판단 내용을 검토용 기준집으로 다시 쓰거나, Project가 개인 기준의 채택·갱신을 관리하게 하지 않는다. 자료의 이름·보관 위치만으로 우선순위를 정하지 않고, 어떤 목표·약속·선택·관찰을 담는지 판단한다.

맡은 질문의 본문 선택·유효한 읽기 재사용·원문과 실물 대조는 대상 context의 공통 사용 방법을 따른다. 이 Project에서는 [USAGE](../../../context/USAGE.md)를 사용한다. 일반 재개의 실제 읽기 순서는 대상 Work 지침이 정하며, 한정 질문이나 Work 없는 요청에 전체 인수를 요구하지 않는다. 기준·사례·형성 자료의 의미와 읽을 조건은 각 영역이 소유한다. 더 정확한 이해나 형성 의도 확인에도 필요한 형성 자료를 선택할 수 있다.

Noline에서는 [root 지침](../../../CLAUDE.md)과 작업 경로의 app/package 지침에서 제품 불변식·rules·guards·runbooks를 선택한다. Personal의 일반 판단이 Noline의 더 엄격한 규약이나 열린 제품 결정을 대체하지 않는다. 실제 앱 실행이 필요하면 기존 [start-app](../start-app/SKILL.md)의 조건을 따르고, deprecated noline-work는 호출하지 않는다.

## 작업 중 판단이 바뀌는 곳에서 맥락을 다시 고른다

구현 결과, 검토 의견, 검사 실패나 새 사용처가 새로운 질문을 만들면 공통 사용 방법으로 필요한 원문·실물을 다시 선택한다. 예를 들어 표현을 검토하다 완료 시점이 쟁점이 되면 제품 계약과 실제 호출 흐름을 함께 본다. 필요한 이해를 얻으면 맡은 구현·검토·검증으로 돌아간다. 기준의 적용 조건이나 현재 설계는 재판단할 수 있지만 목표·명시적 제약·보존 계약을 임의로 바꿀 수는 없다.

Main은 담당자에게 이번 목적·맡길 일·보존 조건과 필요한 정본의 접근점을 전달한다. 관련 기준을 공유하되 Main의 요약이나 기존 선택 이유가 원자료와 별도 판단을 대신하지 않게 한다. 구체적인 초기 입력 묶음과 추가 탐색·반환 방식은 맡긴 일에 맞춰 명시하며 이 본문이 고정된 전달 양식을 요구하지는 않는다.

## 구현자는 검토 전에 맡은 결과를 완성한다

구현자는 관련 기준과 요구를 실제 사용 조건에 적용해 설계·구현·자기 확인을 끝낸다. 필요한 호출부·설정·연결·설명을 포함해 맡은 사용 경로를 완성하고, 알고 있는 누락·결함을 검토자나 검증자에게 마무리하도록 넘기지 않는다. 부분 단위를 맡았다면 완성한 경계와 남은 통합을 구별한다.

구현 또는 채택된 수정을 맡을 때는 [구현 상세](references/implementation.md)를 읽고 설계 판단, 요구에 근거한 자기 확인, 구현 중 검사와 관찰 준비, 최신 판본·근거의 인계를 수행한다. Main이 직접 구현해도 같은 책임을 적용한다. 지속 본문의 변화는 근거로 제안하며, Main의 검토·반영과 별도로 배정한 쓰기 권한은 아래 Owner 연결을 따른다. 제안이나 자기 확인은 맡은 구현의 완성 또는 별도 검증을 대신하지 않는다.

## 역할을 연결하고 전체 결과를 책임진다

| 역할 | 맡을 판단과 반환 |
| --- | --- |
| 구현자 | 요구·관련 기준·사용 조건에 맞는 구체 설계와 구현을 수행하고 자기 변경을 확인한다. 검토자가 품질을 만들어 줄 것을 전제로 미완성 선택을 넘기지 않는다. 중요한 선택, 실제 변경과 확인·미확인을 Main이 판단할 수 있게 반환한다. |
| 개선 검토자 | 현재 결과와 기준의 적용을 별도로 재판단하고 의미 있는 대안을 비교한다. 필요한 정확성·요구 적합성·테스트 공백도 볼 수 있다. 범위와 근거 있는 의견을 반환하며 발견 없음으로 전체 검증을 대신하지 않는다. 수행할 때 [검토 상세](references/review.md)의 공유 목적과 검토자 부분을 읽는다. |
| 검증자 | 최신 결과의 요구·계약 충족과 근거 충분성을 판단하고 필요한 실행·독립 재현을 수행한다. 제품 코드를 검증 역할로 수정하지 않는다. [검증 상세](references/verification/INDEX.md)에 따라 근거·실패·미확인을 반환하며 모든 개선 선택의 재평가나 사용자 수락을 대신하지 않는다. |
| Main | 전체 목표·설계 정합성, 담당 범위·수정 권한, 의견의 종합·선택·사용자 연결, 수정 후 확인과 최종 상태 판단을 책임진다. 자신의 초기 설계도 검토 대상으로 둔다. |

같은 문제를 여러 역할이 발견할 수 있다. 역할의 구별은 발견 가능한 문제를 독점하는 구분이 아니다. 책임을 나눴다고 매번 네 에이전트를 호출하거나, 검토 후 수정 담당을 특정 역할로 고정하지 않는다. Main은 이번 배정과 허용된 변경 범위를 드러내며 배정되지 않은 수정 권한을 역할 이름에서 추론하지 않는다.

검토를 맡기거나 의견을 판단할 때 Main도 [검토 상세의 Main 판단](references/review.md#main은-의견을-선택과-다음-행동으로-잇는다)을 적용한다. 채택한 의견은 실제 수정과 필요한 확인으로 연결한다. 수정과 종료는 아래 기준으로 정하며, 검토자라는 역할만으로 정본 수정 권한을 부여하지 않는다.

## 선택을 수정과 종료로 잇는다

Main은 관찰의 타당성과 해결책을 나누어 판단한 뒤 원래 구현자에게 수정을 맡기는 것을 기본으로 한다. Main이 구현했으면 Main이 고친다. 담당자가 없거나 필요한 전문성이 다르거나 같은 잘못된 전제가 반복되면 재배정한다. 검토자에게 직접 수정을 맡길 때도 별도 책임·허용 범위를 명시하고 같은 파일의 중복 수정자를 만들지 않는다.

같은 담당자를 이어 쓰더라도 바뀐 과제와 이유·기대 이득·보존 조건·영향받는 확인·열린 선택을 전달한다. 수정자는 실제 변경, 해결한 문제와 개선 이득, 자기 확인과 남은 한계를 반환한다. 이전 결론·검사 중 더 이상 유효하지 않은 것을 식별해 영향받은 범위부터 다시 확인한다.

국소적인 개선 의견의 처리는 Main이 실제 수정과 이득을 직접 확인해 닫을 수 있다. 이것으로 요구 충족의 별도 검증을 생략하지 않으며 검증의 시작·축소 조건은 위 전체 흐름을 따른다. 계약·책임 배치·사용처·판단 기준이나 중요한 절충이 달라졌으면 관련 질문을 다시 검토한다. 같은 리뷰어의 재승인이나 고정 횟수의 리뷰를 의무화하지 않는다. 사실 부족·상충하는 계약·권한 문제는 필요한 원자료나 결정을 구해 풀며 같은 리뷰를 반복하는 것으로 대신하지 않는다.

Main은 중요한 의견의 처리와 이유, 실제 수정 결과·확인, 얻은 이득과 새 부담, 남은 문제의 의미·담당·다음 행동을 보고 검토를 마친다. 별도 검증에는 최신 대상·판본, 요구·계약·사용 조건, 변경분, 확인 원본과 공백, 실행 방법·권한을 전달한다. Main과 검증자는 [검증 상세](references/verification/INDEX.md)에서 각자 맡은 의뢰·수행·반환·재검증 조건을 읽는다.

검증에서 나온 제품 결함은 원 구현자 또는 지정 담당이 고치고 필요한 지속 테스트에 반영한다. 검증자의 실행 가능한 재현·입력·기대 결과를 이어받아 자기 확인한 뒤, 검증자가 같은 재현과 영향받은 경계를 다시 확인한다. 필요하면 테스트 파일만 검증자에게 별도 배정할 수 있다. 검사 결함·환경 공백·불명확한 요구는 각각 검사 보완·실행 준비·기준 확인으로 잇는다. 필수 실행 공백은 처음 발견했을 때 담당을 연결하고, 막히지 않은 확인은 계속한다.

검증자의 반환에는 요구별 충족 근거 있음·불충족 근거 있음·미확인이 구별돼야 한다. Main은 최신 대상에 필요한 근거가 충분하고 중요한 실패·미확인이 해소됐을 때 현재 범위를 완료로 판단한다. 결함은 수정·재검증, 핵심 미확인은 준비·필요한 사용자 결정으로 잇는다. 질문이나 유보 제안만으로 기존 요구가 없어지지 않는다. 검토 종료·검증 반환·전체 완료·설치 및 배포·사용자 수락은 서로 다른 판단이며 매번 새 사용자 승인 단계를 추가하지 않는다.

이번 한정 요청에 답한 것과 Ticket·Work 전체의 완료, 대화를 중단하는 시점을 구별한다. 원래 범위의 필수 미확인은 남은 작업이며 범위 밖 한계·미채택 개선 아이디어와 다르다. 반환할 때 관련 current·Ticket·output이 최신 결과와 같은 범위를 가리키는지 맞춘다. 중단하면 중요한 미완료와 다음 행동의 이유를 남기며, 대화 종료만으로 Work를 완료하거나 새 Work·개선 루프를 자동 시작하지 않는다.

## 확인한 결과와 사용자가 판단할 내용을 돌려준다

검사 통과·검토 발견 없음만으로 완료를 설명하지 않는다. Main이나 조사 담당이 기존 검사를 결론의 근거로 사용할 때도 [검사 근거 판단·재사용](references/verification/evidence.md)을 읽고 적용한다. 실제로 대조한 근거와 직접 실행한 확인, 확인하지 못한 조건을 현재 결과에 연결한다. 이 근거 대조가 별도 검증 역할 전체를 수행했다는 뜻은 아니며, 필요한 독립 검증의 조건은 앞의 전체 흐름을 따른다.

사용자에게는 요청한 결과를 먼저 보여 주고, 중요한 선택·의미 있는 대안·확인 범위·남은 결정을 결과와 연결해 설명한다. 담당자의 보고를 그대로 모아 반환하는 것으로 Main의 판단을 대신하지 않는다. 첫 결과를 구성할 때 [explain](../explain/SKILL.md)을 사용해 원래 목표에 무엇이 답해졌는지, 실제 변경과 확인이 왜 그 결론을 지지하는지 연결한다. 코드에서 나온 핵심 주장은 해당 처리와 의미를 함께 설명하고, 변경·검사 목록만 전달한 뒤 별도 설명 요청을 기다리지 않는다. 단순한 결과는 그 크기에 맞게 전달하며 모든 작업을 전체 브리핑으로 만들지 않는다.

중요한 결론을 뒷받침할 사실이 부족하면 Main이 맡은 작업과 권한 안에서 필요한 확인을 수행하거나 담당자에게 연결한다. 실행 제약이 있으면 [실행 공백을 다루는 방법](references/verification/INDEX.md#실제-경로와-실행-공백을-다룬다)에 따라 지금 가능한 확인과 접근이 막힌 부분을 구별한다. 미확인 목록을 적는 것으로 가능한 수행을 대신하지 않고, 확인할 수 없는 이유와 그 때문에 남는 판단·필요한 다음 실행을 밝힌다. 이 책임은 설명을 쓰기 전부터 작업 수행에 적용되며 설명으로 구현·검증의 공백을 메우지 않는다. 설명 방법은 explain이 소유하며 개발 결과·확인·전체 상태 판단은 이 스킬의 책임으로 남는다.

## 관련 맥락 작업을 필요한 때 연결한다

사용자가 대화를 돌아보고 개선을 찾자고 요청하면 [improvement-loop](../improvement-loop/SKILL.md)로 현재 Main이 전체 대화·관련 내용 검토, 추천·선택·실제 반영을 잇는다. 작업 마무리나 방향 전환에서 필요성을 제안할 수 있지만 자동 실행하지 않는다. Personal의 [경험 모음](../../../context/personal/experience/README.md)은 협업 경험·열린 후보를 보존하며, 현재 사용할 기준과 구별한다. 루프를 위해 별도 Work 등록·이관을 요구하지 않는다.


현재 목표나 접근의 전제가 흔들리면 원래 목표·실제 관찰·현재 방법을 다시 대조하고 무엇을 유지하고 바꿀지 Main이 판단한다. 국소 결함마다 전체 Work를 다시 정의하지 않는다. 대상에 호환되는 `reconsider-work`가 있으면 그 조건으로 사용하고, 없으면 Main이 이 판단을 직접 수행한다.

평상시 읽기와 직접 읽기 요청은 대상 context의 공통 사용 방법을 사용한다. 지정된 Personal·Project 반영에는 [context-update](../context-update/SKILL.md)를, 요청된 새 독립 Work에는 [create-context-workspace](../create-context-workspace/SKILL.md)를 연결한다. 같은 목표는 기존 Work에서 이어가며 기존 Work로의 전환은 대상 Work 계약을 따른다. 이 Project의 [생성·전환 계약](../../../context/work/workspaces/CREATE-AND-TRANSITION.md)은 생성·이번 요청 대상·다음 기본 선택·실제 host 연결을 구별한다.

이들은 이 Project에 설치된 실행 본문이다. 생성·전환과 session 연결은 기존 Work 계약을 따른다. 스킬 설치·호출만으로 Workspace를 만들거나 Maintain을 활성화하지 않는다. 실제 host의 발견·호출 여부는 별도 확인하며 이름이나 파일 존재로 실행 성공을 주장하지 않는다.

## 달라진 의미를 해당 Owner에 남긴다

Main은 root 지침과 각 Owner의 관리 규칙에 따라 필요한 반영을 연결하고 실제 결과를 확인한다. Personal·Project는 허용된 범위에서 context-update로 반영한다. 준비된 Work의 Spec·Ticket·state·records는 [Main·Maintain의 갱신 계약](../../../context/work/workspaces/spec-and-tickets/MAINTENANCE.md)을 따르며 같은 문서를 중복 수정하지 않는다. 자동 연결이 없는 session의 허용된 반영도 그 계약이 연결하는 수동 fallback을 따른다. 새 Workspace 초기 구성은 생성 계약을 적용한다. 이미 유효하게 확보한 맥락은 재사용하며 이 스킬이 기록 담당·hook·activation을 바꾸지는 않는다.

담당자의 제안과 실제 변경·확인 근거를 원요구·유효한 계약·다른 사용처에 대조한다. 제안이 없어도 결과 종합에서 확인한 중요한 영향을 놓치지 않는다. 유효한 근거는 재사용하고 공백·충돌·후속 변경에 필요한 부분만 추가 확인한다. 현재 Main이 검토와 반영 연결을 이어 맡으며 실제 쓰기는 해당 Owner의 갱신 담당·허용 범위를 따른다. 새 제품 약속·개인 기준 채택은 해당 선택 권한으로 연결하며 일상 정정마다 새 사용자 승인을 만들지 않는다.

먼저 해당 영역에서 계속 관리할 의미가 달라졌는지 판단한다. Project에는 여러 작업의 제품 이해·설계·개발에 필요한 의미·구조·계약·제약·선택 이유와 이를 설명하는 현재 지원 사실을 남긴다. 이번 구현 여부·검사 진행·실행 상세는 Work가 맡는다. 기존 계약 안의 새 소비자 적용이라면 Project 무수정으로 끝날 수 있다. 데모에 문장이 있다는 사실이나 코드가 달라졌다는 사실만으로 지속 내용을 정하지 않는다.

| 달라진 것 | 연결할 곳 |
| --- | --- |
| 실행 단위의 선택·결과·막힘 | 해당 Ticket |
| 여러 실행이 지킬 목표·계약·설계 | Spec |
| 현재 판단·결과·다음 행동과 그 이유 | current의 해당 문서. 오래된 현재 상태를 갱신한다. |
| 중요한 대안·선택 이유·확인과 필요한 원문 | records. 제안·채택·실제 수정·실제 확인을 구별한다. |
| 이번 목표를 위해 선택한 실제 산출물의 위치 | output. 정본을 복제하지 않고 연결한다. |
| 제품의 지속 약속·개발 규약 | 권한 있는 선택에 따라 해당 Project 본문 |
| 제품 이해·여러 작업에 지속할 구조·사용처·지원 제약의 변화 | 확인 범위와 함께 해당 Project 본문. 이번 구현·검사 진행은 Work에 남긴다. |
| 여러 작업에 가져갈 개인 기준의 의미·조건 | Personal의 기존 갱신 방식과 선택 권한에 따라 해당 본문 |
| 반복 실행할 절차·발동 조건·책임 | 해당 스킬 본문과 필요한 형성 자료 |

이번 작업에 적용한 좋은 대안을 지속 기준으로 자동 승격하지 않는다. 기준 변경과 이번 적용 결과는 관련되지만 같은 결정은 아니다. 원자료·과거 선택을 새 결론으로 덮어쓰지 않고, 해당 Owner의 관리 규칙을 따른다. 이 스킬이 Work의 파일 구조나 제품별 관리 계약을 다시 정의하지는 않는다.

지정된 지속 본문과 필요한 읽기 경로는 context-update로 맞추고, 이번 Work는 그 관리 계약으로 갱신한다. 같은 Main이 이미 읽은 근거로 검토·반영을 계속할 수 있으며 별도 호출·보고서를 둘로 나누지 않는다. 한정 문서 반영의 완료와 그 문장이 설명하는 제품의 충족·전체 완료는 다르다. 새 설명도 유효한 요구·계약에 대조할 결과이며 필요한 기존 검토·검증에 연결한다.

현재 의미가 달라지면 진행 중인 담당자의 입력, 이미 반환된 의견, 이전 확인 근거에 미친 영향을 연결한다. 문서 반영 전에 결정부터 전달할 때는 근거·아직 낡은 본문·갱신 담당과 남은 일을 밝히고, 그 문서를 다음 실행의 입력으로 넘기기 전에 필요한 반영을 확인한다. 무관한 수행은 계속하며 바뀐 조건의 영향을 받는 의견·검사만 다시 잇는다. 후속 검증이 지속 본문의 지원 주장·미확인을 바꾸면 그 본문도 맞춘다.

중요한 제안·조정·미채택 이유·당시 근거와 실제 반영 결과는 기존 records에서 다시 찾을 수 있게 하고, 현재 처리할 의미·남은 반영·확인은 Ticket/current에 남긴다. 담당자가 종료돼도 이 근거로 이어가며 꼭 필요한 공백에만 추가 질문·조사를 한다. 모든 발화·탐색의 로그나 새 제안함·상태 필드는 만들지 않는다. 일상 유지·이미 정한 의미의 반영은 이후 경험 개선을 기다리지 않는다. 사용자 요청의 [improvement-loop](../improvement-loop/SKILL.md)는 미반영 후보와 이미 적용한 선택·결과를 재사용하며 Personal의 경험 관리로 연결한다. 앞의 새 제안함을 만들지 않는 원칙은 일상 Work 유지의 범위이며, 루프가 사용하는 Personal 경험 모음을 금지하지 않는다.

파일 저장, 다음 세션의 올바른 재개, 실제 수행 효과를 같은 완료로 보고하지 않는다. 이 본문은 prototype에서 적응한 실행 계약이며 파일 설치만으로 실제 host 호출·수행 효과를 증명하지 않는다. 목적·범위·책임을 더 정확히 이해하거나 수정·재검토할 때는 [형성 자료](_background/README.md)를 읽는다. 일상 적용에 필요한 기준과 조건은 이 본문과 해당 검토·검증·실행 상세에서 찾는다.
