# 왜 개발 절차를 하나의 스킬로 구성했는가

사용자는 자신의 기준을 이해한 첫 구현을 얻고, 별도의 검토를 통해 기존 선호·지식이 놓친 의미 있는 다른 선택도 비교하고 싶어 했다. 매번 더 큰 개선이나 다른 결론을 요구하는 것이 아니라 현재안 유지와 변경을 실제 차이로 판단하려는 목적이다. Main이 그 결과를 종합하며, 사용자와 중요한 대안·절충을 이해하는 대화도 작업의 일부다.

처음에는 검토자에게 Personal을 덜 주는 안을 논의했다. 그러나 기준을 읽지 않으면 조건·비용·사용자 이해를 놓칠 수 있고, 정보를 줄인 것만으로 독립성이 생기지 않는다. 관련 기준을 공유하되 현재 선택과 적용 조건을 다시 판단하는 방향을 선택했다. 따라서 검토자는 기준 준수만 확인하는 역할이 아니며 Main의 초기 선택도 다시 볼 수 있다.

## 판단 내용과 수행 방법을 나눈 이유

Personal은 여러 작업에 가져갈 개인의 판단 기준·이유·조건을 소유한다. 현재 예제가 개발·코드 중심이어도 그 상위 역할을 코드 품질로 한정하지 않는다. development는 현재 개발 작업에 필요한 개인 기준과 Project·Work 맥락을 함께 사용한다. 제품의 약속·현재 사실, 이번 목표·선택은 서로 다른 Owner를 유지한다.

검토용으로 좋은 코드 원칙을 다시 만들면 Personal과 의미·예외를 이중 관리하게 된다. 반대로 링크만 제공하면 어떻게 독립적으로 판단할지 사라진다. 현재 구성은 기준의 의미는 기존 Owner에 두고, 검토에서는 적용 재판단·대안 비교·주장별 근거·강도와 Main 연결을 설명한다. 짧은 적용 예시는 가능하지만 두 번째 원칙집이 되지 않게 한다.

새 관점은 이번 판단에 쓸 수 있고, 지속 Personal 기준으로 채택할지는 별도 판단이다. 이를 ‘부족함을 입증한 뒤에만 사용’하는 방식으로 만들지는 않았다. 현재 근거로 효과·비용·적용 조건을 판단할 수 있으면 선택하고, 실제 수정 결과가 요구를 충족하는지는 따로 확인한다.

## 진입점과 상세를 함께 옮긴 이유

기존 DEVELOPMENT는 Work 안에서 공통 절차와 로그인 데모의 적용을 함께 설명했다. 사용자는 절차를 development 전용 스킬로 만들고 관련 상세가 함께 쌓이는 구성을 원했으며 진입점의 이전도 제안했다. 현재 [SKILL.md](../SKILL.md)는 Main이 이번 요청을 끝까지 연결하는 본문이고 [review.md](../references/review.md)는 공유 목적과 검토자·Main의 판단을 구별한 상세다.

계층은 읽는 목적과 변경 책임에 맞춰 만든다. 최초에는 공통 본문과 검토 상세로 시작했고, 후속 합의로 실행 배치와 검증 상세를 구체화했다. 빈 역할 파일부터 만드는 대신 실제로 구별해 읽고 관리할 책임이 생겼을 때 나눴다. 검토자·검증자가 Main의 전체 배정·완료 책임까지 받는 것도 아니다.

이후 사용자는 기존의 작은 구성을 유지하려고 필요한 계층 확장을 억제하지 않아도 된다고 보완했다. 처음 비어 있던 구현 상세는 이미 구체화됐고, 검사의 근거 판단은 검증자 외 Main·조사 담당도 사용하게 됐다. [구현 상세](../references/implementation.md)는 구현 담당의 설계·완성·자기 확인·인계를, [검사 근거 상세](../references/verification/evidence.md)는 주장·기대 결과·실행 범위와 기존 결과의 유효성을 설명한다. 본체의 전체 흐름과 검증 본문의 역할 연결을 유지하면서 읽기·수정 목적이 다른 부분을 나눴다. [당시 발화와 선택](records/2026-10-26-detail-expansion.md)을 보존한다.

검증 수행과 근거 상세는 `references/verification/` 안에 함께 둔다. `INDEX.md`가 검증의 실질적인 진입 본문을 맡고 `evidence.md`가 필요한 판단 상세를 맡는다. 최초 분할에서는 본체 파일을 폴더 밖에 유지했지만, 사용자가 떨어진 구성을 지적하고 INDEX 진입을 선택해 함께 묶었다. 기존 경로 보존보다 책임 단위를 읽고 관리하기 쉬운 배치를 택했으며, 상세를 직접 읽는 Main·조사 담당의 경로와 역할은 유지한다. [구조 선택 기록](records/2026-10-26-detail-expansion.md#검증-본문과-상세를-한-폴더로-묶었다)에서 당시 선택을 확인한다.

로그인 작업의 계약·코드·선택은 기존 Work와 [적용 장면](/Users/hammyeong-yeon/Desktop/ai-workspace/context/workspaces/014-ai-development-workflow-design/records/prototypes/development-workflow/walkthrough.md)에 남는다. 스킬을 교체하더라도 Personal·Project·Work의 지속 의미와 결과가 유지되도록 그 정본을 흡수하지 않는다. 기존 DEVELOPMENT 원문은 [보존판](evidence/development-before-skill.txt)으로 남겼으며 현재 실행 진입점으로 사용하지 않는다.

## 현재 구체화한 것과 이어서 정할 것

재개에서는 Work에 남은 문제가 이번 요청의 결과를 대신하지 않게 한다. 기존 본문에도 요청 범위 존중이 있었지만, ‘재개 요청에서는 남은 일부터 이어간다’는 설명만으로는 현황·배경 이해를 위한 재개와 실제 실행을 맡은 경우의 차이가 잘 드러나지 않았다. 2026-10-26에는 실제 재개 대화와 당시 잠정 구조 판단을 대조하고 이 문장을 명료화했다. 목표·참여 범위는 Main·development, 복원 경로는 Work 지침, 필요한 원문 선택·대조는 공통 읽기 방법의 책임으로 유지한다. 새 단계·보고서·스킬은 추가하지 않았고 수행 효과는 아직 확인하지 않았다. [발화와 근거](evidence.md#재개-요청의-결과를-구별한-보완--2026-10-26)를 함께 본다.

검토의 목적, 보존 조건·재판단 범위, 역할별 공통 책임, 검토 방식·강도, Main의 선택과 사용자 참여는 본문에 반영했다. Main은 초기 맥락 선택뿐 아니라 작업 중 재탐색·의견 종합·수정 후 확인·결과 전달과 Owner별 갱신까지 연결한다. 이를 고정된 순서나 매번 같은 역할 수로 바꾸지 않는다.

구현 완성·인계, 검토 입력·추가 탐색·권한·호출, 수정·재검토·종료, 실행 배치와 기록 책임은 후속 합의에 따라 본문·검토 상세·실행 배치에 반영했다. 일반 재개와 범위를 정한 위임은 실제 root·Work 지침에서도 구별했다. 최초 연결과 한계는 [실행 통합 기록](records/2026-10-23-execution-integration.md)에 남겼다. 후속 맥락 연결에서는 공통 읽기·지정 본문 반영·요청된 생성의 실행 본문을 이 prototype에 구성했다. 실제 대상에서 접근·계약이 다르면 해당 관리 지침으로 수행하며 보존 원형의 존재를 설치로 취급하지 않는다.

이번 초안은 실행 지침의 구성과 내용 적용이다. 실제 여러 작업에서의 효과나 자동 호출·운영 설치까지 확인한 것은 아니다. 이 경계 때문에 초안 작성을 미루거나 이미 합의한 판단을 다시 후보로 되돌리지는 않는다. 근거와 전환 과정은 [발췌](evidence.md)와 [기록](records/2026-10-23-development-skill.md)에서 찾는다.

## 첫 결과의 설명 연결 — 2026-10-24

explain 재구체화에서 첫 결과를 구성할 때 목표·실제 변경·확인을 결론으로 잇도록 호출을 명시했다. 기존의 ‘관계나 이유 설명이 필요하면’이라는 연결은 이미 맡은 결과 설명을 나중의 별도 코드 설명으로 미룰 여지를 남겼다. 개발 결과의 책임은 그대로 두고 설명 수행만 explain에 맡겼다. 설명 자료가 있어도 답이 요약에 머문 관찰이 있으므로 호출 명시만으로 효과를 보장하지 않는다. 단순 결과는 그 크기에 맞게 전달하며 별도 agent나 전체 브리핑을 의무화하지 않았다. [선별·채택의 근거](../../explain/_background/records/2026-10-24-selective-improvement-adoption.md)에서 사용자 요청과 범위·확인 한계를 이어 본다.

## 검증을 구체화하며 연결한 책임

사용자는 코드·설계의 더 나은 선택은 이미 개선 검토자가 다루므로, 검증자에게 채택한 개선 전체의 재평가를 맡기면 혼란스럽다고 보았다. 검증은 최종 요구·제품 계약과 실제 결과, 이를 지지하는 검사·실행 근거의 충분성으로 구체화했다. 검증자가 원인·재현을 능동적으로 찾되 제품 수정과 지속 테스트의 통합은 기존 담당이 이어받는 선택은 독립 판단과 수정 책임을 함께 유지하기 위한 것이다.

처음 방법 선택을 중요한 미확인 중심으로 설명했을 때 사용자는 기계 검사 활용과 단계 구분이 보이지 않는다고 정정했다. 현재는 구현 중 저렴한 검사, 개선 수정 뒤 갱신, 별도 검증의 기본 검사 유효성·검사 적절성·추가 실행을 연결한다. 기존 근거를 무조건 재실행하지도, 통과 요약만 믿지도 않는다. 이러한 단계·층위·책임 구별은 검증에 한정한 서식이 아니라 이후 본문을 구체화할 때도 적용할 관점이다.

[verification](../references/verification/INDEX.md)은 검증 시작·수행·반환·재검증의 현재 방법을 소유한다. Main의 전체 흐름·완료·기록은 본체에 남고 execution은 세션 배치를 맡는다. 제품의 기대 결과와 실제 명령은 Project, 이번 선택·재현·관찰은 Work에 유지한다. 따라서 별도 검증 방식이나 Verify 도구를 교체해도 제품 계약과 작업 근거가 그 안에 갇히지 않는다. Verify는 선택적인 실행 근거 보존이며 의미 판정 장치가 아니다.

실제 반영과 근거는 [검증 통합 기록](records/2026-10-24-verification-integration.md)에 있다. 본문 연결·대표 장면의 의미 대조와 메모리 기반 예제 실행을 확인했으며, 새 역할 배치 전체를 여러 agent가 수행한 실험이나 실제 제품의 효과 검증으로 보지 않는다.

## 조사·보고에서 기존 근거를 사용하는 담당의 확인

2026-10-26 종합 UX 제한 수행은 코드·과거 화면을 조사하고 실제 기기 미확인을 구별했지만, 검사 이름 검색에서 본문의 대체 구성·실제 확인 항목 대조까지 이어지지 않았다. 기존 검증 상세에는 검사 적절성과 한 실행이 막혀도 가능한 확인을 계속하는 방법이 있었다. 이 사건을 새 원칙의 부재나 모든 조사의 실패로 보지 않고, Main·조사 담당이 기존 근거로 결론을 내릴 때에도 필요한 상세를 적용하도록 연결했다.

결론을 바꿀 공백에서 가능한 확인을 수행하고, 실행 불가 부분은 이유·남는 판단·다음 실행으로 잇는다. 검사 본문을 더 읽거나 미확인 목록을 늘리는 것이 목적은 아니며, 영향·비용을 보고 충분한 근거를 재사용한다. 이번 시험에는 앱 조작·설치가 없었으므로 원사건의 실앱 추가 검토 책임 전체를 평가한 것으로 확대하지 않는다.

이 수행은 설명 직전만의 절차가 아니라 작업 담당의 책임이다. 검증 상세의 해당 방법을 쓰는 것과 별도 검증자가 독립 수행하는 것은 구별한다. 개선 대안 검토·제품 수정·사용자 수락을 검증의 새 책임으로 옮기거나 explain에 조사 절차를 복제하지 않았다. [반영 기록](records/2026-10-26-investigation-evidence-adoption.md)과 [근거](evidence.md#조사-수행과-근거-적용의-보완--2026-10-26)를 함께 본다.

## 맥락 사용과 반영을 실제 수행에 연결했다

기존 read/update를 별도 요청에서만 사용하면 담당자가 작업 중 얻은 의미와 현재 문서 사이가 끊길 수 있다. 질문별 선택·대조는 공통 사용 방법으로, 지정된 Personal·Project의 반영은 한정 과업으로 펼치고 development에는 언제 필요한지와 누가 판단·반영하며 후속 수행을 어떻게 잇는지를 남겼다. 같은 근거를 다시 모으거나 읽기·편집마다 새 담당자를 만들기 위한 구분은 아니다.

구현자가 전체 맥락을 충분히 알지 못할 수 있다는 사용자 우려에 따라, 구현자는 근거 있는 제안을 반환하고 현재 Main이 전체 맥락에서 검토·반영한다. Main의 제안 검토와 실제 반영은 독립 검증이 아니며, 새 문서도 원요구·유효한 계약에 대조할 결과다. Project에 계속 관리할 내용인지 먼저 선별해 이번 구현·검사 진행은 Work에 남긴다.

완료 시점에는 실제 결과와 Work의 현재 의미를 맞추고 다음 대화가 남은 판단에서 이어가게 했다. 같은 목표의 재개와 요청된 새 Work 생성, 생성과 전환의 결과를 구별한다. 사용자 요청의 [improvement-loop](../../improvement-loop/SKILL.md)는 이 제안·선택·결과를 재사용하며 현재 Main이 이어 수행한다. 일상 유지의 선행 단계나 별도 Work 등록을 요구하지 않는다. [사용자 발화와 통합 이유](records/2026-10-26-context-integration.md)에 후속 선택·유보·적용 범위를 보존했다.

이 책임 배치와 Personal 경험의 연결 이유는 [루프 형성 맥락](../../improvement-loop/_background/context.md), 형식·소유 경계를 다시 대조한 경과는 [구조 정정 기록](../../improvement-loop/_background/records/2026-10-29-integration.md)에서 찾는다.
