# Development의 선택 근거

현재 구성의 근거를 사용자 요청, 외부 원문, 독립 리뷰와 실제 적용으로 구별한다. 긴 설계 대화 전체를 이 폴더에 복제하지 않고 선택을 재검토하는 데 필요한 최소 원문과 출처를 보존한다. 아래 사용자 발화는 같은 설계 대화에서 발췌했으며 오탈자를 유지했다.

## 독립 개선 리뷰와 Main의 선택

2026-10-23 Astra high 리뷰어에게 사용자 발동 원문·구성 제안과 실제 prototype·합의·외부 원문의 접근점을 제공했다. 읽기 전용 설계 리뷰이며 Main의 파일 구성을 기각할 수 있게 했다. 반환은 전체 구조 적합, 다음 네 보완이었다.

1. Personal 전체와 이번 개발 작업이 소비하는 기준을 구별한다.
2. SKILL.md에 맥락 재선택·종합·전달·갱신까지 Main의 전체 책임을 드러낸다.
3. 한 상세 파일 안에서도 공유 목적·검토자·Main의 독자를 구별한다.
4. 공통 수행 계약과 특정 로그인 데모의 적용을 구별해 이전한다.

Main은 네 보완을 모두 채택해 사용자에게 추천했고 위 적용 요청을 받았다. 리뷰어가 현재 실행 실패를 발견했거나 새 구조의 효과를 시험한 것은 아니다. 고정 호출·수정 권한·모델 등은 후속 설계로 남겼다.

## 조사 수행과 근거 적용의 보완 — 2026-10-26

사용자는 explain의 두 부족을 배경과 종합한 뒤 “본체랑 상세, _background까지 반영해봐. 기존 의미 잘 유지됐는지 확인하고 2번이랑 4번 다시 6.0 sol 미디엄으로 테스트해보자”라고 요청했다. 최초 네 사례·원응답은 Workspace014 `records/experiments/explain-four-problems-60medium-2026-10-26/`에 있다.

4번은 development에서 시작해 종합 UX 검토를 수행했다. 코드·이미지 조사를 했고 실행 한계를 밝혔으나 테스트는 주로 이름 검색에서 파악했으며 본문의 대체 구성·assertion까지 읽은 기록은 없다. explain·verification 상세 열람도 기록에 없었다. 읽기 누락을 품질 부족의 단일 원인으로 확정하지 않으며 실제 조사를 하지 않았다고 평가하지 않는다.

Main의 추가 대조에서 일정 생성 검사는 날짜·시간 선택창을 `() => null`로 대체했다. 해당 검사의 입력 유지·단일 폼 확인은 유효한 근거로 남고 선택창 조작까지 보장하지는 않는다. 원대화에 선택창·키보드 미확인이 이미 있었으므로 이를 새 제품 결함 발견으로 세지 않는다. 과거 보고서의 사용자789는 “추가 검토는 왜 안한거야? 정말 어렵거나 사유가 있으면 몰라도 […] 디테일하게 계속 파고들란건 아니고”라고 했다. 이 원래 목적은 검사 코드 열람 하나보다 넓다.

시험은 파일 조사·가능한 로컬 확인을 허용했지만 DB·시뮬레이터·설치 의존성이 없고 앱 조작·설치를 제외했다. 따라서 보완은 가능한 확인과 외부 실행의 구별이며, 제한된 시험으로 실제 기기 검증 책임 전체의 실패를 확정하지 않는다. 원래 검증의 세 수행·독립성·수정 책임과 공통 근거의 소유도 유지한다.

Main의 제안과 배경 종합은 `records/2026-10-26-ticket04-02-choice-and-investigation-improvement-proposal.md`, 반영 후 두 최초 수행은 `records/experiments/explain-choice-investigation-60medium-revised-2026-10-26/`에 보존한다. 형성 근거는 시험 생성자에게 제공하지 않으며 특정 결함·정답을 알려 주지 않는다. 새 독립 설계 리뷰를 수행한 것으로 소급하지 않는다.

## 재개 요청의 결과를 구별한 보완 — 2026-10-26

실제 보존 장면의 첫 요청은 “여기 작업 이어갈거야 최근 기록 한거 보고 현황 파악하자”였다. 담당자는 배경·잠정 상태를 설명한 뒤 두 버그의 기대 동작부터 정하자고 제안했고, 사용자는 “지금 구조랑 배경을 더 파악해봐 마지막 문제 2가지는 아직 그렇게 중요한건 아니고”라고 정정했다. 당시 기록에는 폼 소유 대안의 우월성이 미확인이며 앞선 구조 검토의 결론이 확인 범위보다 넓었다고 남아 있었다. 기록 부재나 모든 재개의 구조 우선 원칙으로 해석하지 않는다.

04-03의 새 독립 리뷰는 기존 책임 배치를 유지하고 이번 요청의 결과와 실제 재개 사례를 연결할 것을 권했다. 사용자가 “틀렸다기보다 이해가 잘 안돼 이게 어디에 어떻게 적용되고 될지 감이 안와”라고 하자, Main은 development의 기존 재개 문장을 구체화하고 Work의 복원 경로·공통 읽기·기록 책임은 유지하는 적용 위치를 설명했다. 후속 사용자 발화는 “좋아 그럼 진행하면 될까?”였다. 이 범위에서 기존 문장을 보완했으며 네 안 전체나 새 스킬 구성을 일괄 승인받은 것으로 보지 않는다.
