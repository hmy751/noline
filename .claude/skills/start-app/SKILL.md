# Start App

Noline 개발 환경에서 필요한 DB·API 서버·Expo 클라이언트를 실행하고, 선택한 실행 대상에서 실제 연결을 확인한다. 사용자가 지정한 플랫폼과 범위를 우선한다. 별도 지정이 없으면 현재 켜진 시뮬레이터·기기를 확인해 적절한 대상을 고른다.

## 실행 조건

- 사용자가 `$start-app`, 앱 실행, 서버와 클라이언트 연결 등을 직접 요청하면 실행한다.
- 다른 작업 중 실제 앱 화면이나 기기·서버 연동을 확인해야만 요청을 완료할 수 있으면 실행한다. 단순히 실행해 볼 수도 있다는 이유로 켜지 않는다.

## 실행과 확인

1. 루트와 대상 workspace 가이드를 확인한 뒤, 시뮬레이터·기기에 먼저 접근해 현재 상태를 파악한다. 앱이 켜져 있으면 실제 화면과 연결 상태를 보고 재사용할지 복구할지 정한다. 꺼져 있으면 실행 대상과 개발 앱 설치 여부를 확인해 시작을 준비한다. 이 단계에서 파악한 상태가 이후 실행 범위를 정한다.
2. 앞서 확인한 실행·연결 상태를 기준으로 필요한 구성요소를 정한다. 기존 Docker 컨테이너와 서버·Metro 포트, `apps/server/docker-compose.yml`과 양쪽 개발 환경 파일의 **필요한 설정값만** 확인한다. 환경 파일 전체나 비밀값을 출력하지 않는다.
3. 이미 정상 실행 중인 구성요소는 재사용한다. 필요한 경우 PostgreSQL을 Compose로 시작하고 건강 상태를 확인한다. 기존 DB를 내리거나 초기화하지 않는다. 서버는 개발 설정으로 시작해 DB 연결과 `/api/health`를 확인한다.
4. 클라이언트 API 주소가 선택한 실행 대상에서 서버에 닿는지 확인한다. iOS 시뮬레이터의 localhost, Android 에뮬레이터의 호스트 주소, 실제 기기의 LAN 주소는 서로 다르다. 필요한 설정 변경은 선택한 대상에 한정한다.
5. 필요하면 Expo 개발 서버와 해당 개발 빌드를 연다. 완료를 판단할 때는 시뮬레이터·기기의 실제 앱 화면에 접근해 초기화가 끝났고 오류 화면이나 로딩에 머물러 있지 않은지 확인한다. 서버 연결은 실제 API 요청과 클라이언트의 응답·데이터로 확인한다. 화면에 접근할 수 없으면 로그로 확인한 실행·연결 상태와 화면 미확인을 구분해 보고한다.
6. 실행 중인 프로세스와 접속 주소, 확인한 연결 범위, 남은 오류를 간단히 보고한다. 사용자가 앱을 계속 쓰려는 요청이면 프로세스를 실행 상태로 둔다.

## 실행 장애 처리

개발 환경은 현재 `package.json`의 개발 스크립트와 이미 설치된 의존성으로 실행한다. 필요한 `tsx`와 Expo CLI가 설치돼 있으면 스크립트의 작업 디렉터리·환경 변수·인자를 유지해 해당 실행 파일을 직접 사용하고, `pnpm` 래퍼의 자동 재설치 경로를 거치지 않는다. 래퍼가 재설치나 `node_modules` 제거를 요구하더라도 이를 앱 실행에 필요한 작업으로 받아들이지 말고, 기존 설치로 실행 가능한지 확인한다.

사용자가 요청한 앱 실행 범위에서 필요한 Docker·서버·클라이언트·시뮬레이터 실행은 사용자에게 다시 확인하지 않고 진행한다. Docker 소켓·시뮬레이터 접근·로컬 서버 실행에 도구 권한이 필요하면 실제 사용자 요청과 실행 대상을 근거로 해당 권한 절차를 사용한다. 사용자가 이미 승인한 실행 범위를 확인해 해결할 수 있는 문제는 직접 처리하고, 도구의 실제 거부 등으로 사용자 판단이 필요한 차단이 남을 때만 그 지점을 묻는다.
