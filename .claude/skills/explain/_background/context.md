# 하나의 설명 진입점으로 바꾼 이유

## 목적과 현재 선택

사용자가 AI의 답을 다시 요청한 뒤에야 뜻과 판단 이유를 이해하는 부담을 줄이고, 현재 질문의 의미와 실제 대상·근거를 연결해 자기 판단을 이어갈 수 있게 한다. 재질문을 없애는 것이 목표는 아니다. 보존된 인터뷰에서는 학습을 위해 질문을 이어간 경우도 있었고, 추가 질문 자체를 실패로 보지 않았다.

현재 선택은 `explain` 본체, 설명 작성 상세, 앞선 발화 대조 상세다. 본체가 질문 범위·자료 확인과 판단·설명 구성·충분성·권한을 직접 맡고, 실제 대응을 만드는 긴 방법과 예시를 상세에 둔다. 코드·문서·개념은 설명 대상이고, 첫 설명·결과 전달·후속 질문은 대화의 조건이다. 이를 각각 별도 실행 모드로 만들지 않는다.

이전 두 실행 스킬의 제거를 전제로 한다. 단, 제거에 대비한다는 이유로 모든 옛 조항을 이식하지 않는다. 사용자가 이 점을 재차 정정했다. 새 구성만으로 현재 목적을 수행할 수 있어야 하며, 과거 조항의 수나 본체 분량이 충분성 기준은 아니다. [직접 발화](evidence.md)에 생성 승인과 이 정정을 함께 보존했다.

## 원래 구분에서 가져온 것과 달리 정한 것

이전 브리핑은 작업물의 부분 설명이 전체 역할·실제 연결·확인 범위로 이어지지 않는 문제를 다뤘다. 이전 복구는 사용자가 가리킨 실제 발화의 뜻을 복원하고, 뜻을 설명하는 것과 그 주장이 옳다고 인정하는 것을 구별했다. 당시에는 입력·조사 범위·대화 수명의 차이로 두 진입점을 유지했다. 원형·품질 보강·공동 적용의 경과는 이전 두 형성 자료가 소유한다.

지금 source에서는 코드 동작 설명에 문법·책임·선택 이유가 함께 들어가고, 앞선 설명에 대한 이의도 실제 구현이나 관찰을 확인해야 풀리는 경우가 있다. 두 진입점을 선택한 뒤 다시 조합하기보다 공통 작성 방법을 두는 편이 적절하다고 판단했다. 이 관찰은 통합과 양립하지만 ‘분리가 실패 원인’이라는 인과를 입증하지는 않는다.

원래 분리의 이유를 고정 제약으로 삼지 않는다. 짧은 질문이어도 필요한 사실 확인이 깊어질 수 있고, 전체 작업 설명도 관계가 단순하면 짧게 끝날 수 있다. 이전의 작은 복구 원칙은 불필요한 부담을 피할 참고이며 모든 후속 질문을 짧게 제한하는 규칙이 아니다.

## 반복 보완에서 이번에 바꾼 것

기존 브리핑에도 실제 역할·코드·값·조건을 연결하는 방법이 있었다. 인증 사례의 한 비교에서는 국소 개선을 관찰했지만, 최신 여행 비교에서는 양쪽 모두 코드 발췌 없이 역할 표·문장·링크로 설명했다. 더 엄밀한 시험이나 요구 문구 추가만으로 핵심 수행을 안정시키지 못한 상태에서 사용자가 구성·방법을 다시 열었다.

따라서 이번 차이를 ‘이전에는 방법이 없었다’고 설명하지 않는다. 본체는 이해할 관계와 실제 대상을 연결하는 수행을 소유하고, 작성 상세는 무엇을 골랐는지뿐 아니라 왜 그 부분이 필요한지와 실제 짧은 설명을 함께 보여 준다. 좋은 완성 답을 다시 만드는 것과, 그 답을 만드는 과정의 예시를 제공하는 것은 다르다.

통합 뒤06 첫 보고를 같은 입력으로 비교했지만6.0-sol medium에서는 핵심 개선이 드러나지 않았고6.1-sol high에서는 기존 브리핑이 전후 구현과 이유를 더 잘 연결했다. 새 스킬도 상세를 읽었으므로 파일을 나눈 것 때문에 방법을 못 읽었다고 볼 수 없다. 각 조건 한 번의 응답이며 문구·모델·생성 변동의 인과를 확정하지 않는다.

이에 사용자 요청으로 기존 두 본문과 배경을 다시 검토했다. 통합 중 전후 조사, 응답 안의 구현 대응, 목표별 개선 근거, 목적별 충분성이 일반화된 부분을 구체화했다. 전체 역할에서 대표 사건을 통해 핵심 처리로 내려가는 방식과 읽기·수정 부담의 비교도 연결했다. 복구의 핵심은 유지돼 있어 이미 설명한 내용과 현재 용어를 잇는 부분만 보완했다. [재검토·반영 기록](records/2026-10-24-explanation-revision.md)에 바꾼 것과 중복 추가하지 않은 것을 구별했다. 통합 구조를 유지한 선택과 이 수정의 실제 효과는 별도다. 이후 수정판과 기존판을6.0-sol high로 비교하자 수정판이 Provider·Router의 전후 코드를 직접 읽었지만, 응답은 여전히 요약 중심이어서 구현 대응·목표별 개선 이유의 뚜렷한 향상은 확인하지 못했다. 사용자도 두 답이 비슷하다고 평가했다. 같은 설정의 수정 전후 explain 비교는 없어 마지막 수정의 인과 효과를 분리하지 못하며, 모델만의 문제로도 단정하지 않는다. [후속 관찰의 근거](evidence.md)를 함께 읽는다.

독립 개선 리뷰에서는 관계·동작과 이유·근거를 처음부터 별도 상세로 나누면 자료 선정·조건 비교가 겹친다고 지적했다. 이를 한 작성 상세에 필요한 절로 묶었다. 앞선 발화 대조는 원래 의미와 현재 타당성을 별도로 확인하는 특수 작업이 있어 분리했다. 파일 두 개를 고정한 규칙은 아니며, 앞으로 실제 수행·수정 책임이 달라질 때 다시 판단한다.

## 반복 비교 이후의 선별과 수행 재구성

수정판도 요약 중심이라는 관찰 뒤 문구를 조금씩 강화하고 같은 비교를 반복하는 접근을 멈췄다. 기존 본문에도 필요한 기준은 상당 부분 있었다. 원래 목적·사용자 회고·직접 장면·외부 자료를 다시 대조한 뒤, 사용자 요청으로 독립 개선 리뷰를 받아 질문의 범위와 실제 빠진 연결을 구별하는 방향을 선택했다. 사용자는 이 종합 판단을 바탕으로 스킬 구체화와 반영을 요청했다.

현재 본체는 전체 질문을 대표 한 대목으로 축소하지 않고, 실제 대상에서 결론까지 필요한 연결을 응답에 만드는 일을 중심으로 재구성했다. 핵심 주장이 코드에서 나오면 첫 결과 전달에서도 해당 처리와 의미를 설명한다. 작성 상세는 일반 원칙의 반복과 기존 저장·조회 긴 예시를 교체하여, 전체 인증 코드와 후속 값 질문의 차이, 실제 동기화 요약에서 빠진 처리·시간·반환 연결, 여행의 역할 설명과 실패·복구를 비교하는 선택 판단을 보여 준다. 보고서의 원래 질문·관찰·결론 연결은 유지한다. 앞선 발화의 원뜻·현재 타당성을 대조하는 상세는 이번 부족함의 주된 원인으로 보지 않아 그대로 둔다.

Matt에서는 공통 수행과 조건부 상세·완료 조건의 배치를, pstack에서는 작업이 요구하는 설명 결과와 이유를 만드는 방법을, Vercel에서는 요청 범위·필요한 reference·확인을 잇되 기계 검사와 판단을 구별하는 관점을 가져왔다. 다른 호스트의 호출 방식, 숙련 개발자를 전제로 한 설명 수준, 사례별 스킬·상시 설명 agent·모든 항목의 필수화는 가져오지 않았다. 단일 입구와 두 상세를 유지한 것은 현재 책임 구분에 따른 선택이며 성능 우위의 증거가 아니다.

[반영 기록](records/2026-10-24-selective-improvement-adoption.md)은 채택·교체·유지와 확인 범위를, [근거](evidence.md)는 실제 발화·관찰과 외부 판본을 보존한다. 새 비교 응답을 생성하지 않았고, 과거 시험을 이번 판본의 효과로 쓰지 않는다.

## 코드와 함께 읽는 설명·표현의 보완

03·04의 첫 다섯 비교 뒤 사용자는 C가 핵심을 짚은 느낌은 있지만 충분히 이해한 것은 아니며, 반복한 코드 동반 요구와 서술 중심 표현의 부담이 남았다고 말했다. Main은 그 차이를 주로 설명 성향으로 정리하고 기존 요구의 충족을 따로 평가하지 않은 누락을 정정했다. 추가 이득 미확인 관찰은 유지하지만, 설명 방식의 요구를 해결하지 않은 채 호출 시점 시험으로만 옮기는 권고는 유보했다.

기존에도 실제 코드·의미 대응과 읽기 쉬운 형식 조항이 있었다. 이번에는 코드 제시가 필요한 요청, 역할이 드러나는 처리 단위, 코드와 해설의 인접 배치와 비중, 결과를 마치는 판단을 함께 맞췄다. 구체적 예시는 새 정답을 늘리지 않고 인증·동기화·여행의 기존 사례를 실제 코드·값 대비·위임 관계에 맞게 편집했다. 핵심을 잘 잡는 것과 사용자가 실제 구현을 함께 따라 읽을 수 있는 것은 별도로 확인한다.

독립 개선 리뷰의 역할·위임, 비중·대비·도식, 작은 함수 전체와 의미 있는 재표현 허용을 반영했다. 단일 본체·두 상세와 기존 권한·기록 책임은 유지하며, 모든 질문에 코드·표·도식을 요구하지 않는다. [적용 기록](records/2026-10-25-code-presentation-adoption.md)은 이번 변경과 이후 비교의 한계를 구별한다.

## 전체 설명 구성과 국소 해설의 연결

코드·표현 보완 뒤03-C에서 실제 코드와 인접 해설이 나타났고 사용자는 보기 편하다고 했지만 동작 설명 같다는 유보를 남겼다.04의 차이는 작다고 했다. Main이 ‘상태 구별을 먼저’라고 권고했으나 C에는 이미 상태 표와 국소 이유가 있어 그 처방만으로 부족했다. 역할·이유 조항의 부재가 아니라, 전체 연결이 설명 순서·발췌를 결정하는 방법과 구체 예시가 맞지 않은 공백을 재검토했다. 생성 결과의 단일 원인이나 사용자의 내적 혼동을 확정한 진단은 아니다.

본체에서는 사건·주고받는 것·조건에 따라 설명을 구성하고, 등록과 실행·계속되는 관측과 선택적 작업처럼 실제 대상에서 중요한 관계를 구별하게 했다. 상세의 인증 예시는 한 문단의 전체 안내 뒤 catch로 내려가던 구성에서, 실제 등록부·요청·401 재시도·공유 갱신을 코드와 연결한 전체 예시와 그중 세션 실패를 묻는 후속으로 바꿨다. 범위별 마무리도 맞췄다. 동기화의 국소 보완, 여행의 역할과 선택 판단, 보고서의 질문과 결과 연결은 유지한다.

모든 설명에 설계 평가나 비동기 흐름 도식을 요구하지 않는다. 일반 흐름의 기능상 이유와 배치의 적절성 판단은 구별하며 작은 질문·복구의 범위와 사실 확인·권한은 유지한다. 새 설명 유형·agent·라우터를 만들지 않았다. 인증 예시 완성·원문 대조와 새 상황에서의 응답 효과는 다른 확인이며 [적용 기록](records/2026-10-25-composition-adoption.md)에서 구별한다.

## 도입 관계를 본문에서 따라 읽게 하는 편집

전체 구성 보완 뒤 새 코드 비교에서 사용자는 직전판A를 전반적으로 선호하면서 수정판B의 접수부터 시작하는 흐름은 좋다고 했다. 이후A의 구분되는 문단이 가독성을 지킨 느낌이라고 직접 설명했다. B에도 문단은 있었으므로 제목이나 문단의 유무로 단순화하지 않고, 본문에서 무엇을 설명하는 묶음인지 찾아야 하는 부담을 대조했다.

Main 선검토와 개선 리뷰1회 뒤 기존 표현 절의 묶음·전환 기준과 마무리를 교체했다. 전체 연결을 잡는 절까지 비슷한 지시를 추가하지 않고, 인증 예시에서 요청의 세션/대기 후 검사, 응답의 성공/401, 공유/각 요청 복귀/정리·오류를 실제로 나눠 배치했다. 실패 조건은 결과와 대비하고, 원천·발췌 안내와 예시의 구성 이유는 실제 답의 앞뒤로 구별했다. 오류 전파처럼 현재 코드의 뜻을 바꾸는 설명은 보조라는 이유로 멀리 보내지 않았다.

도입 관계·코드·깊이를 유지하면서 필요한 대목을 찾게 하는 편집이다. A의 목차나 인증 예시를 모든 답의 양식으로 고정하지 않는다. 짧은 질문·앞선 말 복구·다른 예시의 책임은 유지한다. [적용 기록](records/2026-10-25-flow-readability-adoption.md)은 실제 코드와의 대조 및 같은 두 사례 재시험의 범위를 구별한다. 각1회 응답과 공통 실행 스타일의 영향을 분리하지 않았으므로 특정 문구가 차이의 원인이라는 결론은 내리지 않았다.

## 본체의 책임별 정리와 기존 예시의 분리

후속 논의에서 사용자는 본문을 계속 이어 붙이지 말고 구조를 정리하되 형성 맥락을 보존하라고 요청했다. Main은 긴 인증 예시를 별도 파일로 나누는 안도 제시했고 사용자는 처음에 보류했다. 이후 새 예시 작성이 아니라 기존 예시의 분리라는 뜻을 확인하고 분리를 요청했다. 본체 안의 책임 위치를 정리하고, 기존 인증 전체 설명과 같은 코드의 후속 예시를 내용 그대로 `references/examples/auth-flow.md`에 함께 옮겼다. 작성 상세에는 일반 구성 방법과 읽기 조건을 남겼으며 동기화·여행·첫 결과의 짧은 예시는 그 방법 가까이에 유지했다.

첫 절에 섞였던 질문 범위와 전체 설명 구성, 근거 절의 사실 확인과 선택 판단, 종료 절의 충분성과 권한을 구별했다. 반복된 작은 질문·정정·대표 경로의 조건은 해당 행동 가까이로 모았다. 본체가 직접 실행 기준을 소유하고 상세를 조건에 따라 읽는 구성은 유지한다. 전체 설명에서는 구성 방법과 분리한 대비 예시를 함께 읽으므로, 파일 이동이 기존 읽기 책임을 약화하지 않는다. 핵심 코드·조건을 줄이거나 새 응답 양식을 지정하는 변경은 아니다. [반영 기록](records/2026-10-25-body-organization.md)에 의미 대조와 확인 범위를 남겼다. 이번 정리가 생성 답의 품질을 높였다는 시험 근거는 아직 없다.

## 첫 전달과 다른 책임의 관계

보고서 source에는 표현뿐 아니라 추가 확인의 부족도 있었다. 결과를 설명하려고 원래 질문과 관찰을 연결할 때 사실의 공백이 드러날 수 있다. 이를 사용자의 재질문 뒤로 미루지 않도록, 작업 담당자가 첫 결과를 구성할 때 explain을 사용하고, 답에 필요한 사실이 부족하면 기존 권한 안에서 확인을 수행하거나 담당자에게 연결하게 했다.

개발·조사·검증·제품 수락의 책임을 설명 스킬로 옮긴 것은 아니다. 설명이 없어져도 작업 담당자의 결과 책임은 development 등 실제 작업 흐름에 남는다. 설명 스킬을 교체·제거한다면 그 호출과 설명 방법의 Owner만 맞추고, 제품 계약·Work 상태·공통 근거 기준을 다시 만들 필요가 없어야 한다.

`work-discussion`도 사용하는 근거·현재성·판정 경계는 [공통 기준](../../shared/explanation-and-evidence-criteria.md)에 남긴다. 과거 스킬에 있던 고정 Main·Maintain 기록 연결은 옮기지 않고 실제 대상의 관리 규칙을 따르게 했다. 별도 이해 상태 저장소·agent·hook·자동 호출 설정은 만들지 않았다.

## 적용 지위와 다시 볼 조건

2026-10-26 네 사례의 최초 수행 뒤, 선택 질문의 응답은 실제 내부 구조를 설명했지만 과거 반환 제안과의 일관성을 근거로 복원을 추천했다. 사용처의 필요와 대안 부담은 충분히 비교하지 않았다. Main의 최초 보완 예시도 현재 적용 화면만으로 내부 유지를 추천해, 원래 요청한 폼·단독 데이터 소비의 유연성까지 평가하지 못했다. 배경과 원대화를 다시 대조한 뒤 적용 범위를 줄인 것과 설계 목표를 줄인 것을 구별했다.

현재 선택 절은 실제 사용처와 명시된 지원 조건을 같은 기준으로 놓고 현재안·대안의 가능한 결과와 부담을 비교한다. 반환 항목의 일반 예시는 어떤 소비가 어떤 정보와 결정을 필요로 하는지에서 시작하도록 구체화했다. 기존 여행 복구 사례·전체 인증·앞선 발화 정정은 유지한다. 특정 반환 형태를 정답으로 넣거나 모든 선택을 설계 전체 검토로 확대하지 않는다.

이전에도 상세·전후 코드를 읽고 충분한 판단으로 잇지 못한 관찰이 있으므로, 상세 읽기 연결은 수행을 돕는 수단으로 본다. 파일 열람 자체를 품질 보장으로 삼지 않는다. 종합 UX 조사에서 가능한 확인을 수행하는 책임은 development에 남겼다. [이번 반영](records/2026-10-26-choice-judgment-adoption.md)과 [근거](evidence.md#선택-질문과-배경-종합-뒤의-보완--2026-10-26)에 선택·정정·효과 확인의 범위를 구별한다.

사용자가 리뷰 반영 구성으로 생성과 기존 연결 정리를 요청해 prototype에 반영했다. 이전 두 실행 본문은 바이트 그대로 보존했다. 후속 삭제 요청으로 기존 폴더를 없애고 배경·원문을 이 스킬의 `_background/legacy/`로 옮겼다. 형성 자료·실험 원응답·원자료는 과거 근거로 유지한다. 전역이나 실제 제품에 운영 설치한 상태는 아니다.

실제 질문에서 자료 선정과 설명의 연결이 다시 빠지거나, 상세 선택이 과한 부담을 만들거나, 한 상세가 다른 수행 책임까지 섞어 갖게 되면 해당 사례의 질문·근거·응답을 대조해 수정한다. 반복 생성으로 원하는 답을 찾거나 모든 과거 조항을 다시 쌓는 방식을 기본으로 두지 않는다. 구조·링크 확인과 실제 설명 효과는 별개다.
