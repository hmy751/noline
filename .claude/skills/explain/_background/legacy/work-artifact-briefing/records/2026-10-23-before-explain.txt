# 작업물 이해 브리핑

이미 존재하는 작업물이 **전체에서 무슨 역할을 하고, 실제로 어떻게 연결되며, 무엇까지 확인됐는지** 설명한다. 사용자가 그 의미와 근거를 이해해 다음 질문이나 지시를 만들 수 있게 한다.

최근 코드 변경, 현재 구조와 동작, 특정 시점의 과거 상태, 문서·분석·review 결과와 코드 외 산출물을 다룬다. 파일 목록·diff 통계·test 숫자를 나열하는 것으로 설명을 대신하지 않는다.

목적·선택 이유를 확인하거나 스킬의 의미를 바꿀 때는 [형성 자료](../../../../../../../../context/workspaces/014-ai-development-workflow-design/records/prototypes/development-workflow/skills/explain/_background/legacy/work-artifact-briefing/records/_background/README.md)에서 관련 배경과 근거를 읽는다. 현재 요청의 실행 기준은 이 본문과 해당 조건의 실행 자료를 따른다.

## 시작

1. **질문과 필요한 설명 깊이를 잡는다.** 설명할 대상·시점과 함께, 현재 질문과 앞선 대화에서 사용자가 이해하려는 역할·관계와 구별해야 할 상태·책임을 확인한다. 이를 설명의 중심으로 삼아 필요한 세부를 고른다. 전체 구조 이해에도 실제 코드가 필요할 수 있으며, 코드 제시와 문법 해설의 깊이는 따로 판단한다. 문법 질문에 이어 코드를 붙이거나 코드·흐름이 어렵다고 하면 표현과 실행을 함께 읽도록 돕고, “코드와 함께 자세히”라는 추가 요청을 기다리지 않는다. 이미 밝혀진 내용을 되묻지 않는다.
2. **관련 기준을 찾는다.** 실제 프로젝트의 root AI 지침과 그 지침이 안내하는 관련 맥락, 필요한 기존 문서와 공통 [설명과 근거 기준](../../../../../../../../context/workspaces/014-ai-development-workflow-design/records/prototypes/development-workflow/skills/explain/_background/legacy/work-artifact-briefing/shared/explanation-and-evidence-criteria.md)을 읽는다.
3. **답을 바꾸는 기준 상태를 확인한다.** 현재 대상이면 branch·HEAD·working tree·관련 runtime 설정을, 과거 대상이면 commit·날짜·산출물 생성 시점과 당시 원자료를 확인한다. 현재성을 확인하지 못하면 설명의 효력 범위를 밝힌다.
4. **질문에 필요한 원자료를 조사한다.** 관련 Project 정본과 source·진입점·사용처·설정·실제 연결·test를 확인한다. 실제 동작이 중요하면 허용된 범위에서 trace·log·실행 관찰도 확인한다.

### Work의 목표·진행을 설명할 때

관련 Spec·Ticket에서 다음을 골라 실제 코드·산출물·검증 결과와 연결한다.

| 자료 | 확인할 내용 |
| --- | --- |
| Spec | 이루려는 결과와 공통 기준 |
| Ticket | 맡은 결과·범위, 실행 맥락·접근, 완료 조건·확인 방법 |
| 실제 결과 | 보고된 진행과 실제 수행, 확인할 계획과 이미 확인한 결과의 차이 |

전체 Spec·모든 Ticket을 기본 입력으로 삼지 않는다. 문서의 존재나 완료 표시만으로 실제 수행·검증 또는 전체 목표 충족을 인정하지 않는다. 코드 개선에서는 **기존 동작을 보존했다는 근거**와 **책임·중복·변경 부담을 개선했다는 근거**를 구별한다.

## 대상에 맞춰 조사한다

### 방금 또는 특정 변경

- 사용자가 정한 base가 있으면 따른다. 없으면 현재 working tree·staged change·관련 commit history를 보고 비교 기준을 밝힌다.
- Diff와 함께 변경 후 source, 실제 사용처와 호출 경로를 확인한다.
- 전후 변화가 전체 역할·대표 흐름·상태·외부 효과에 어떤 차이를 만드는지 연결한다.

### 현재 구조와 동작

- 사용자 입력이나 대표 사건의 진입점에서 결과·외부 효과까지 따라간다.
- 각 component의 책임·경계·호출·소비 관계를 정확한 file·symbol·사용 위치와 연결한다.
- Interface나 type의 존재와 실제 runtime provider·설정·연결을 구별한다.

### 과거 코드나 작업물

- 당시 commit·보존 문서·대화·review·산출물 중 필요한 원자료에 시점을 고정한다.
- 당시 보고, source로 확인한 사실, 현재의 해석을 구별한다.
- 과거 상태를 현재 working tree에도 그대로 유효하다고 확대하지 않는다.

### 문서·분석·review 결과

- **질문과 결과를 연결한다.** 어떤 질문과 기준에 답하려던 산출물인지 확인하고, 현재 설명할 결과가 그 질문의 어느 부분에 답하는지 연결한다.
- **후속 자료의 맥락을 잇는다.** 이전 문제를 다시 확인한 자료라면 당시 문제·그 뒤 변경·이번 확인의 관계 중 현재 결론을 바꾸는 부분을 함께 설명한다.
- **근거의 간극을 다룬다.** 직접 확인한 finding과 작성자의 해석·미확인을 구분한다. 확보한 근거가 현재 질문에 답하지 못하면 그 간극을 밝히고, 답에 필요한 사실은 허용된 범위에서 더 확인한다. 새 진단·review나 실행이 필요하면 현재 설명으로 확인한 범위와 이어서 수행할 일을 구별한다.
- 문서가 가리키는 live code·test·설정이 중요하면 현재 사실을 소유한 원자료까지 내려가 대조한다.

## 이해할 수 있는 결과로 설명한다

**현재 질문의 결론과 대상의 전체 역할을 먼저 보여 주고, 이해의 중심이 되는 관계를 대표 흐름에 연결해 필요한 세부로 내려간다.** 같은 입력·사건에서 각 역할과 조건이 어떤 결과 차이를 만드는지 이어 설명한다. 사용자가 이름과 호출 순서를 혼자 조립해 역할을 추측하게 하지 않는다.

| 설명할 내용 | 연결하는 방법 |
| --- | --- |
| 핵심 이름과 책임 | 중요한 이름을 처음 쓰는 자리에서 가리키는 데이터·책임과 사용자가 하려는 일에서의 역할을 설명한다. 기존 file·symbol 이름은 실제 위치를 찾을 수 있게 남긴다. |
| 실제 연결과 변화 | 대표 입력·사건이 component와 상태 변환을 거쳐 결과가 되는 과정을 보여 준다. 변경 설명이면 전후 차이가 그 과정에 미치는 영향을 연결한다. |
| 중요한 주장과 근거 | 무엇을 확인했는지와 해당 source 위치를 주장 가까이에 둔다. source상 가능한 동작, 실제 연결·관찰, test·compiler의 보장 범위를 구별한다. |
| 미완성과 열린 판단 | stub·mock·hard-coded·미연결·미구현·미확인 중 답의 의미를 바꾸는 것을 드러낸다. AI 해석과 사람이 결정할 부분, 더 확인할 위치도 구별한다. |

### 질문에 필요한 세부를 펼친다

- **역할이 드러나는 코드:** 코드의 구조·역할·동작을 이해하는 데 필요한 처리 단위를 골라 실제 코드와 그 의미를 함께 보여 준다. 책임의 관계가 중요하면 어디서 판단하고, 어떤 일을 다른 코드에 맡기며, 무엇을 반환하거나 외부에 반영하는지가 드러나는 부분을 고른다. 파일 위치·함수 이름을 알려 주거나 동작을 요약하는 것만으로 이 대응을 대신하지 않는다.
- **코드와 실행의 연결:** 선택한 부분이 어떤 값을 다루고 다음 처리로 어떻게 이어지는지 설명한다. 문법 때문에 실행을 따라가기 어렵다면 그 표현의 뜻을 해당 동작과 연결한다. 분기 조건, 대기 전후 상태, 반환·오류 전달 중 현재 질문을 푸는 데 필요한 관계를 펼친다.
- **값과 조건의 차이:** 이름이나 동작 요약만으로 결과를 따라가기 어려우면 대표 장면의 입력·중간 값·결과를 이어 보여 준다. 중요한 조건에 따라 결과가 달라지면 그 차이를 같은 흐름에서 비교한다. 코드 설명에서는 선택한 코드의 해당 처리와 대응시킨다.
- **예시의 근거:** 실제 확인한 값인지 설명용 값인지 밝히고, source에서 재구성한 동작·관찰한 실행·제안한 동작을 구별한다.

코드는 설명할 관계가 드러나는 단위로 발췌한다. 전체 역할·연결을 묻는 요청을 모든 줄의 해설로 넓히지 않고, 코드 읽기 요청에서도 관련 없는 문법·모든 분기까지 나열하지 않는다. 코드·사례의 개수보다 현재 질문을 푸는 데 필요한 범위로 고른다.

### 구조의 이유나 다음 선택을 이해하려 할 때

- 중요한 구조 선택이 **무엇을 쉽게 만들고 어떤 제약을 남기는지** 현재 질문과 연결한다.
- 당시 선택 이유는 보존된 근거로 확인할 때만 말한다. 현재 구조에서 도출한 효과와 구별한다.
- 모든 구조의 장단점·선택 이력을 기본으로 조사하거나 일반 동작 설명을 전체 architecture review로 확대하지 않는다.

### 읽기 쉬운 형식을 고른다

- 핵심 답과 판단을 가르는 조건은 먼저 보이게 하고, 이유와 상세 근거는 해당 내용 가까이에 둔다.
- 비교할 조건·전후 차이·책임 대응은 표나 목록으로, 인과와 선택 이유는 짧은 문단으로 연결한다.
- 중심 관계를 설명하는 중에 여러 분기·구현 세부·검사 내역을 같은 비중으로 나열하지 않는다. 결론을 바꾸는 조건은 해당 설명 가까이에 두고, 나머지 보강은 소제목·문단·표로 구별해 찾을 수 있게 한다. 분량을 줄이기 위해 중요한 전제·값·한계를 삭제하지 않는다.
- 직접 호출에서는 `작업물 이해 브리핑 — <대상>`을 기본 제목으로 쓰고, 자연어로 선택된 짧은 답에서는 생략할 수 있다. 고정 목차·줄 수·표 개수를 요구하지 않는다.

## 관계를 구조로 보여 줄 때

결론과 전체 역할을 말한 뒤, 관계·분기·상태 변화를 문장만으로 계속 되짚어야 하고 그 관계를 놓치면 답의 의미가 달라질 때 **현재 질문에 필요한 가장 작은 부분 구조**를 보여 준다.

실행·상태 변화에는 flow, 책임·소유·의존에는 tree나 map, 전후 차이·정확한 대응에는 delta 표현이나 table을 고려할 수 있다. 고정 대응은 아니며 문장이나 짧은 목록이 더 명확하면 그것을 쓴다.

| 확인할 것 | 표현 기준 |
| --- | --- |
| 중심 관계 | 한 구조에서는 실행 순서·의존·역사·근거 강도 중 현재 질문의 중심 관계 하나를 우선한다. |
| 관계의 근거 | Node뿐 아니라 화살표·묶음·방향도 호출·시간·데이터 이동·소유·의존에 관한 주장이다. source·설정·실행 관찰·당시 산출물·설계·review 근거가 지지하는 관계만 표시한다. 설명을 위해 도출한 묶음은 설명용임을 밝힌다. |
| 활성·완성 상태 | 기본·opt-in·disabled·stub 등의 차이가 결론을 바꾸면 구분한다. 미확인은 근거 한계로 남긴다. |
| 재구성과 실제 실행 | source·설정으로 재구성한 흐름은 그 범위와 live trace가 아니라는 점을 밝힌다. 관찰된 실제 실행은 trace·log·실행 관찰이 있을 때만 말하며, 근거가 섞이면 연결이나 구간별로 구분한다. |
| 생략 범위 | 대표 경로나 질문 관련 부분만 보였다면 전체 architecture처럼 보이지 않게 범위를 밝힌다. 중요한 부분은 정확한 source·사용 위치·필요한 실행 근거로 내려간다. |

## 근거와 판정 경계

- 설계 의도·현재 source·실행 관찰·test·compiler·rule·AI 해석이 답하는 질문을 섞지 않는다.
- 직접 확인한 불일치와 그 때문에 제한되는 설명 범위를 드러낸다. 변경의 영향을 설명하는 데 필요한 source·history·test는 이 스킬 안에서 더 조사한다.
- 요구 위반·위험 수용·최종 acceptance를 설명 속에 몰래 확정하지 않는다. 그 판정까지 요청받았다면 확인 근거와 열린 선택을 보여 주고 판정 책임을 밝힌다.
- 기본 행동은 read-only 조사와 설명이다. 설명 요청만으로 code·문서·review 결과·Workspace 상태의 수정으로 확대하지 않는다.

## 끝낼 때

**시작에서 파악한 이해 목적에 답했는지** 확인하고, 대상의 역할·실제 변경이나 연결·결론을 바꾸는 근거 한계와 미확정이 드러나면 현재 브리핑을 끝낸다.

| 사용자의 목적 | 답에 필요한 마무리 |
| --- | --- |
| 전체 역할·구조 파악 | 구성요소의 책임과 연결, 중요한 상태·책임의 구별이 대표 사건의 결과에 어떤 차이를 만드는지 설명했는지 확인한다. 코드가 설명 대상이면 그 관계를 보여 주는 구현과 대응했는지도 본다. |
| 코드의 표현·동작 따라 읽기 | 사용자가 해당 코드로 돌아가 주요 처리가 왜 그 결과로 이어지는지 따라볼 수 있도록 설명했는지 확인한다. |
| 진행·남은 일·다음 선택 판단 | 무엇이 해결·미해결·판단 대기인지와 그것이 다음 행동에 갖는 의미까지 연결한다. |

추가 세부는 현재 질문에 필요한 부분부터 펼친다. 모든 file·symbol·branch·history·설정·test를 전부 조사할 필요는 없다. 기준 source·runtime·산출물이 바뀌면 결론도 달라질 수 있을 때만 재확인 조건을 남긴다.

### 확인한 차이와 기록 연결

- Main은 설명 중 확인한 차이·정정과 근거 한계를 최종 응답에 드러낸다. 서브가 설명했다면 그 내용을 Main에게 반환한다.
- Spec·Ticket·Workspace 문서 갱신은 root AI 지침이 안내하는 상위 운영 계약에 따라 Maintain에 맡겨 중복 수정을 피한다. 다음 실행이 문서에 의존하면 필요한 실제 반영을 확인한다.
- 설명을 제공한 사실만으로 새 요구나 작업 완료를 확정하지 않는다.
