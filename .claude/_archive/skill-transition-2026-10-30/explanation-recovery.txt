# 설명 복구본

어려운 응답을 짧거나 쉬운 말로 바꾸는 데서 멈추지 않는다. 사용자가 어디서 이해의 연결을 잃었는지 찾아, 이미 공유한 맥락에서 원래 뜻까지 다시 이어 준다. 뜻을 묻는 것과 주장에 이의를 제기하는 것을 구별하고, 한 질문에 둘 다 있으면 함께 답한다. 작업 중·작업 후 대화뿐 아니라 일반 대화의 AI 응답에도 사용할 수 있다.

## 시작

1. 사용자가 가리킨 실제 응답과 바로 앞의 필요한 대화를 확인한다. 막힌 문장이 명확하면 같은 질문을 다시 시키지 않는다.
2. 대화만으로 뜻을 복구할 수 있으면 repository나 긴 reference를 먼저 읽지 않고 바로 답한다.
3. Project 사실·근거 범위·오래된 용어의 현재성이 설명의 뜻을 바꿀 때만 실제 적용 프로젝트의 root AI 지침(예: `AGENTS.md`, `CLAUDE.md`)과 그 지침이 안내하는 관련 맥락 위치를 찾아 필요한 canonical·source와 공통 [`설명과 근거 기준`](../../../context/project/guidance/explanation-and-evidence-criteria.md)을 확인한다.

복구 대상은 **그 단어가 일반적으로 가질 수 있는 뜻이나 codebase 안의 같은 이름이 아니라, 사용자가 가리킨 실제 응답에서의 뜻**이다. 앞선 응답이 code component를 가리키지 않았다면 같은 이름의 symbol을 찾아 그 뜻으로 바꾸지 않는다. 필요한 앞선 문장이 현재 context에 없고 가능한 뜻에 따라 답이 달라지면, 어느 문장을 가리키는지 한 번만 묻거나 가장 가능성 높은 해석임을 명시한다.

Work에 관한 말의 범위나 근거를 확인해야 한다면 root AI 지침이 안내하는 관련 Spec·Ticket을 읽는다. Spec의 목표·범위·기준과 Ticket에 정의된 실행·보고된 진행을 질문에 필요한 만큼 확인하며, 모든 Spec·Ticket을 기본 입력으로 삼지 않는다. 현재 문서의 내용으로 과거 발화의 원래 뜻을 바꾸지 않는다. “완료됐다”는 말이 문제라면 기록된 완료 범위와 실제 산출물·검증으로 확인한 범위, Spec의 전체 목표를 구별해 설명한다.

## 무엇이 끊겼는지 찾는다

다음 중 실제 원인을 고른다.

- 처음 나온 용어의 뜻과 실제 가리키는 대상이 빠졌다.
- `이것`, `그 결과`, `현재 상태`처럼 지시 대상이 불분명하다.
- 전제나 중간 인과를 생략해 결론이 갑자기 나왔다.
- 여러 의미를 한 문장에 과도하게 압축했다.
- 확인한 사실, AI 해석, 추천과 사람의 판단이 섞였다.
- 표현이 아니라 답을 만들 사실 자체가 부족하다.
- 사실은 충분하지만 앞선 주장에 모순이나 잘못된 추론이 있다.

막힘 후보가 여러 개라 복구 방향이 실제로 달라질 때만 짧은 질문 하나를 한다. 그 외에는 가장 가까운 끊김을 잡고 바로 답한다.

## 작은 복구에서 시작한다

1. 사용자가 묻는 말의 직접 답을 먼저 준다.
2. 그 답만으로 연결이 복구되지 않으면 마지막 공유 지점에서 빠진 전제나 중간 이유까지 잇는다.
3. 사용자가 이미 이해한 표현과 현재 유효한 Project 용어에서 시작한다.
4. 새 용어는 동의어만 붙이지 말고 실제 대상·역할·현재 대화에서의 의미를 함께 설명한다.
5. 사실·AI 해석·미확정·사람 판단을 섞어 더 강한 결론으로 오해할 때만 그 차이를 드러낸다.
6. 사실 부족이나 의심되는 사실 오류가 현재 답을 바꿀 수 있을 때만, 대화로 확인할 수 없는 부분을 관련 source에서 조사하고 확인한 범위와 미확인을 말한다.

원래 뜻을 복원하는 일과 그 주장이 현재도 타당하다고 인정하는 일을 구별한다. 읽은 대화나 근거에서 실제 오류·모순·잘못된 추론이 보이면 문제가 된 주장이나 연결을 구체적으로 짚고, 무엇을 유지·정정·철회하거나 아직 판단하지 못하는지 밝힌다. 재설명하면서 결론이나 제안의 의미가 달라지면 그 차이를 드러내고, 바뀐 뜻을 원래부터 했던 말처럼 쓰지 않는다. 원인은 확인한 발화·사실·추론에서 설명하며 AI의 숨은 의도를 만들어내지 않는다.

직접 답, 끊겼던 연결과 결론을 바꾸는 조건이 보이면 더 넓은 배경까지 펼치지 않는다. 사용자가 전체 흐름·영향이나 더 깊은 이유를 요청하거나 생략된 전제가 여러 단계일 때만 범위를 넓힌다.

실제 응답에서는 `설명 복구본` 제목을 생략할 수 있다. 고정 목차보다 끊긴 연결을 자연스럽게 잇는 것이 우선이다.

## 끝낼 때

원래 응답의 직접 뜻과 가장 가까운 누락, 결론을 바꿀 조건이 있다면 그 조건까지 답했으면 현재 복구를 끝낸다. 이의 제기나 정정이 있었다면 그에 대한 답과 유지·정정·유보한 부분도 보여야 한다. 제목, 전체 근거 분류, repository 조사, 이해 확인 질문을 기본으로 붙이지 않는다. 사용자의 내부 이해를 추측해 완료 판정으로 저장하지 않는다.

Spec·Ticket과 관련 Workspace 문서에 반영할 차이·정정이 확인됐다면, Main은 확인한 내용·근거·미확인을 최종 응답에 드러낸다. 서브로 설명을 수행했다면 그 내용을 Main에게 반환한다. 문서 갱신은 root AI 지침이 안내하는 상위 운영 계약에 따라 Maintain에 맡겨 중복 수정을 피하고, 다음 실행이 문서에 의존할 때 필요한 실제 반영을 확인한다. 설명을 복구한 사실만으로 새 요구나 작업 완료를 확정하지 않는다.

## 하지 않을 것

- 마지막 문장만 더 쉬운 동의어로 바꾸지 않는다.
- 앞선 응답의 뜻을 같은 이름의 현재 code 개념으로 바꾸지 않는다.
- 원뜻의 조건과 한계를 빼서 이해한 것처럼 만들지 않는다.
- 새 비유, 새 taxonomy와 더 많은 이름으로 막힘을 덮지 않는다.
- 친숙하지만 현재 사실과 충돌하는 Project 표현을 그대로 반복하지 않는다.
- 혼란만으로 앞선 응답을 오류로 단정하거나, 설명에 필요한 정정을 과거 전체 감사·구현이나 문서 수정·작업 범위 재합의로 자동 확대하지 않는다.
- Quiz, 자기 말로 다시 말하기나 형식적 승인을 기본 종료 조건으로 요구하지 않는다.
