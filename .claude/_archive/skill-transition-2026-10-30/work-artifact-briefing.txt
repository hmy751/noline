# 작업물 이해 브리핑

이미 존재하는 작업물이 전체에서 무슨 역할을 하고, 실제로 어떻게 연결되며, 무엇까지 확인됐는지 사용자가 다음 질문이나 지시를 만들 수 있는 형태로 설명한다. File 목록, diff 통계와 test 숫자를 다시 읽어 주는 보고가 아니다.

이 skill은 최근 code 변경, 현재 codebase의 구조와 동작, 특정 commit·시점의 역사 상태, 문서·분석·review 결과와 code 외 산출물을 모두 직접 다룬다.

## 시작

1. 실제 적용 프로젝트의 root AI 지침(예: `AGENTS.md`, `CLAUDE.md`)과 그 지침이 안내하는 관련 맥락 위치를 확인하고, 필요한 기존 문서와 공통 [`설명과 근거 기준`](../../../context/project/guidance/explanation-and-evidence-criteria.md)을 읽는다.
2. 설명 대상과 사용 목적을 잡는다. 사용자가 이미 대상·시점·질문을 밝혔다면 되묻지 않는다.
3. 답을 바꿀 때만 기준 상태를 고정한다. 현재 대상이면 branch·HEAD·working tree와 관련 runtime configuration을, 과거 대상이면 commit·날짜·artifact 생성 시점과 당시 원자료를 확인한다.
4. Local instruction과 관련 Project canonical을 읽고, 사용자의 질문에 필요한 source·entry·consumer·configuration·wiring·test만 직접 조사한다. 실제 동작이 중요하면 허용된 범위에서 trace·log·runtime observation도 확인한다.

현재성을 확인하지 못했으면 현재라고 단정하지 않고 브리핑의 효력 범위를 밝힌다.

Work의 목표·진행과 작업물의 관계를 설명할 때는 root AI 지침이 안내하는 관련 Spec·Ticket을 읽는다. Spec에서 Work가 이루려는 결과·공통 기준을, Ticket에서 맡은 결과·범위, 실행 맥락·접근, 완료 조건·확인 방법과 보고된 진행·실제 결과를 확인한다. 확인할 계획과 실제 확인한 결과를 구별한다. 질문에 필요한 항목과 Ticket을 골라 실제 코드·산출물·검증 결과에 연결하며, 전체 Spec이나 모든 Ticket을 기본 입력으로 삼지 않는다. Spec의 존재나 Ticket의 완료 표시만으로 실제 수행·검증 또는 전체 목표 충족을 인정하지 않는다. 코드 개선에서는 기존 동작이 보존됐다는 근거와 책임·중복·변경 부담이 개선됐다는 근거를 구별한다.

## 대상에 맞춰 조사한다

### 방금 또는 특정 변경

- 사용자가 정한 base가 있으면 그 기준을 사용한다.
- 기준이 없으면 current working tree, staged change와 관련 commit history를 확인해 비교 기준을 명시한다.
- Diff만 읽지 않고 변경 후 source와 실제 consumer·호출 경로를 확인한다.
- 무엇이 전후로 달라졌고 그 변화가 전체 역할·대표 흐름·상태·외부 effect에 어떤 차이를 만드는지 연결한다.

### 현재 구조와 동작

- 사용자 입력이나 대표 사건이 들어오는 entry point에서 결과·외부 effect까지 따라간다.
- 각 component의 책임, 경계, 호출·소비 관계와 정확한 file·symbol·사용 위치를 연결한다.
- Interface나 type의 존재와 실제 runtime provider·configuration·wiring을 같은 상태로 취급하지 않는다.

### 과거 코드나 작업물

- 당시 commit, 보존 문서, 대화·review·artifact 가운데 질문에 필요한 원자료에 시점을 고정한다.
- 당시 보고, source로 확인한 사실과 현재의 해석을 구분한다.
- 과거 상태를 현재 working tree에도 그대로 유효하다고 확대하지 않는다.

### 문서·분석·review 결과

- 어떤 질문과 기준을 대상으로 만든 산출물인지 먼저 확인한다.
- 직접 확인한 finding과 작성자의 해석, 아직 확인하지 않은 범위와 후속 판단을 구분한다.
- 문서가 가리키는 live code·test·configuration이 중요하면 현재 Owner까지 내려가 대조한다.

## 실제 결과

결론, 전체 역할과 대표 흐름을 먼저 보여 준다. 중요한 이름은 처음 쓰는 자리에서 사용자가 하려는 일, 그 이름이 가리키는 데이터나 책임과 연결해 설명한다. 기존 file·symbol 이름은 실제 위치로 내려갈 수 있게 남기되, 이름을 더 만들거나 호출 순서만 나열해 역할 설명을 대신하지 않는다. 중요한 주장에는 무엇을 확인했는지와 해당 source 위치를 가까이 두고, source·wiring·test·미완성은 필요한 깊이로 펼친다.

추상적인 설명만으로 동작이나 근거 한계의 의미를 놓치기 쉬우면, 대표 입력·사용 장면의 입력·중간 값·결과 중 필요한 값을 연결해 무엇이 왜 달라지는지 보여 준다. 실제 확인한 값을 쓰거나 설명용 값임을 밝히며, source에서 재구성한 동작·관찰한 실행·아직 제안한 동작의 지위를 유지한다. 대표 흐름만으로 결과를 오해하기 쉬울 때는 결과가 달라지는 중요한 조건을 함께 비교한다. 모든 브리핑에 사례를 추가하거나 모든 실패 경로를 펼치지는 않는다.

다음 변경이나 선택을 위한 브리핑이면, 중요한 구조 선택이 무엇을 쉽게 만들고 어떤 제약을 남기는지 현재 질문에 필요한 부분에서 연결한다. 당시 선택 이유는 보존된 근거로 확인할 수 있을 때만 말하고, 현재 구조에서 도출한 효과와 구분한다. 모든 구조의 장단점이나 선택 이력을 기본으로 조사하지 않으며, 이 조건만으로 일반 동작 설명을 architecture review로 확대하지 않는다.

직접 호출에서는 `작업물 이해 브리핑 — <대상>` 제목을 기본으로 쓰고, 자연어 상황에서 자동 선택된 짧은 답에는 제목을 생략할 수 있다. 고정 목차나 줄 수 제한은 없으며 아래 항목은 빈칸을 채울 template이 아니다.

### 관계를 구조로 보여 줄 때

결론과 전체 역할을 말한 뒤, 문장만으로 관계·분기·상태 변화를 계속 되짚어야 하고 그 관계를 놓치면 답의 의미가 달라질 때만 현재 질문에 필요한 가장 작은 부분 구조를 보여 준다. 실행·상태 변화에는 flow, 책임·소유·의존에는 tree나 map, 전후 차이나 정확한 대응에는 delta 표현이나 table을 고려할 수 있지만 고정 mapping은 아니다. 문장이나 짧은 목록이 더 명확하면 구조를 만들지 않는다.

- 한 구조에는 실행 순서, dependency, 역사, 근거 강도 가운데 현재 질문의 중심 관계 하나를 우선한다.
- Node뿐 아니라 화살표·묶음·방향도 호출·시간·데이터 이동·소유·의존에 관한 주장으로 본다. 현재 질문의 source·configuration·runtime observation·당시 artifact·design·review evidence가 뒷받침하는 관계만 표시하고, AI가 설명을 위해 도출한 grouping은 설명용임을 밝히며 확인된 구조처럼 제시하지 않는다.
- 관계가 무엇으로 확인됐는지 또는 AI가 도출한 것인지, 경로가 기본·opt-in·disabled·stub 중 어떤 활성·완성 상태인지가 결론을 바꿀 때만 각각 구분한다. 미확인은 근거 한계로 둔다.
- Source·configuration만으로 재구성한 흐름은 그 범위와 live trace가 아니라는 점을 항상 밝힌다. `관찰된 실제 실행`은 trace·log·runtime observation이 있을 때만 사용하고, 서로 다른 근거가 한 흐름에 섞이면 edge나 구간별로 구분한다.
- 대표 경로나 질문 관련 부분만 보였다면 전체 architecture처럼 보이지 않게 생략 범위를 밝힌다. 중요한 부분은 exact source·사용 위치와 필요한 실행 근거로 내려간다.

- **무엇이며 현재 어느 상태인가:** 대상의 정체, 기준 상태와 가장 중요한 결론
- **전체 역할:** 사용자·제품·system에서 맡는 책임과 경계
- **실제 변경 또는 현재 구조:** 전후 차이 또는 지금 연결된 구성
- **대표 흐름:** 입력이나 사건 하나가 component와 상태 변환을 거쳐 결과가 되는 과정
- **책임과 위치:** 핵심 component의 책임·관계와 exact file·symbol·사용 위치
- **근거와 미완성:** source상 가능한 동작, 실제 wiring·관찰, test·compiler가 보장한 조건, stub·mock·hard-coded·미연결·미구현·미확인
- **남은 판단과 drill-down:** AI 해석, 사람이 결정할 부분, 더 자세히 볼 위치와 다시 확인할 조건

“온전한 설명”은 모든 file과 symbol을 나열하거나 branch·history·configuration·test를 매번 전부 조사한다는 뜻이 아니다. 대상의 역할, 실제 연결과 답의 의미를 바꾸는 근거 한계를 다른 skill 없이 따라갈 수 있으면 현재 브리핑을 끝낸다.

## 근거와 판정 경계

- 설계 의도, current source, runtime observation, test·compiler·rule과 AI 해석이 답하는 질문을 섞지 않는다.
- 직접 확인한 불일치와 그 때문에 제한되는 설명 범위는 숨기지 않는다.
- 변경의 영향을 설명하기 위해 필요한 source·history·test를 이 skill 안에서 더 조사한다.
- 요구 위반, 위험 수용과 최종 acceptance를 설명 속에 몰래 확정하지 않는다. 사용자가 그 판정까지 요청했다면 확인 근거와 열린 선택을 보여 주고 판정 책임을 명시한다.

## 끝낼 때

대상의 역할, 실제 변경이나 연결, 중요한 근거 한계와 미확정이 보이면 현재 브리핑을 끝낸다. 추가 세부는 현재 질문에 필요하거나 사용자가 요청한 부분부터 펼친다. 기준 source·runtime·artifact가 바뀌면 결론도 달라질 수 있을 때만 재확인 조건을 남긴다.

이 skill의 기본 행동은 read-only 조사와 설명이다. 설명 요청만으로 code, 문서, review 결과나 Workspace 상태를 직접 수정하는 작업으로 확대하지 않는다.

설명 중 확인한 차이·정정과 근거 한계는 Main의 최종 응답에 드러낸다. 서브로 설명을 수행했다면 그 내용을 Main에게 반환한다. Spec·Ticket과 관련 Workspace 문서 갱신은 root AI 지침이 안내하는 상위 운영 계약에 따라 Maintain에 맡겨 중복 수정을 피하고, 다음 실행이 문서에 의존할 때 필요한 실제 반영을 확인한다. 설명을 제공한 사실만으로 새 요구나 작업 완료를 확정하지 않는다.
