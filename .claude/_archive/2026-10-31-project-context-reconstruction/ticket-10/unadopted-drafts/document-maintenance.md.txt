# 개발 중 문서 확인·논의·갱신

개발 결과가 기존 설명을 바꿨거나 문서 점검·정리를 요청받았을 때, 필요한 의미를 현재 담당 본문에 반영하는 진입 절차다. 상세 수행은 각 스킬과 대상 관리 계약이 소유한다. 문서를 남길지 여부는 바뀐 의미와 이후 필요한 판단으로 정하며, 변경 줄 수·키워드 개수·주기나 커밋 유무로 정하지 않는다.

## 요청에서 담당 흐름을 고른다

| 지금 할 일 | 수행과 책임 |
| --- | --- |
| 구현·수정 중 설명이나 기준이 달라졌다 | [development](../skills/development/SKILL.md)의 결과 확인·Owner 연결을 따른다. 관련 코드·요구·기존 본문에서 바뀐 의미와 확인 범위를 가리고, 지속할 Project 내용이면 Main 또는 배정된 담당이 [context-update](../skills/context-update/SKILL.md)로 반영한다. |
| 제품 설명·계약의 오류·누락을 바로잡거나 승인된 내용을 통합한다 | context-update와 [Project 관리 계약](../../context/project/MAINTENANCE.md)으로 근거·권한·본문·소비 경로를 함께 맞춘다. 읽기·검토만 요청받았으면 발견과 근거를 반환하고 편집 범위를 임의로 넓히지 않는다. |
| 구현 전에 결과·범위·선택을 함께 정한다 | 명시적으로 `work-discussion`을 호출했다면 [해당 스킬](../skills/work-discussion/SKILL.md)의 사실 조사·기존 정의 대조·선택·Spec/Ticket 연결을 따른다. 일반 개발 대화는 development 안에서 필요한 논의를 이어가며 이 스킬을 자동 호출하지 않는다. |
| 이미 나눈 논의·채택 이유·미정을 작업에 남긴다 | 현재 Work의 [기록 계약](../../context/work/workspaces/spec-and-tickets/MAINTENANCE.md)에 연결한다. 준비된 Workspace는 Main이 의미·근거를 전달하고 Maintain이 반영한다. 기록 요청을 새 목표 인터뷰나 별도 Session 생성으로 바꾸지 않는다. |
| 결과·코드·선택의 뜻을 설명하거나 기존 설명을 검토한다 | [explain](../skills/explain/SKILL.md)으로 실제 대상·근거·질문을 대조한다. 설명·추천과 수정·채택은 구별한다. |
| 실제 결과 때문에 현재 접근을 다시 판단한다 | [reconsider-work](../skills/reconsider-work/SKILL.md)의 조건에 따라 목표·선택 이유·결과를 대조한다. 단순 사실 정정마다 전체 작업을 재정의하지 않는다. |

문서 작업을 위해 새 Workspace를 만들거나 자동 연결을 가정하지 않는다. Work가 있으면 기존 기록·연결 계약을 사용하고, 없으면 요청된 산출물과 해당 Owner의 관리 범위에서 마친다. 새 독립 Workspace는 생성 요청이 있을 때 [생성·전환 계약](../../context/work/workspaces/CREATE-AND-TRANSITION.md)으로 연결한다.

## 변경 영향과 기록 위치를 확인한다

1. 이번 요청·변경분과 관련 기존 설명을 대조한다. 커밋된 변경은 비교 기준을 정하고, 아직 커밋하지 않은 변경은 작업 트리·추가 파일을 포함해 범위를 구별한다. 다른 작업의 변경을 이번 결과로 섞지 않는다. [USAGE](../../context/USAGE.md)에 따라 질문에 필요한 원문을 고르며 전체 정책 사전을 먼저 만들지 않는다.
2. 코드·실행에서 확인한 사실, 채택된 계약, 새 제안·열린 결정을 구별한다. 문서와 코드가 다르면 어느 쪽을 고쳐야 하는지 요구·결정·실제 소비자를 대조한다. 검색어와 패턴 일치는 조사 단서이며 자동 위반 판정이나 일괄 치환의 근거가 아니다. 예를 들어 datasource의 직접 DB 접근과 repository의 Activation Router 우회는 역할이 다르다.
3. 계속 사용할 제품 의미·구조·제약은 Project의 주제별 본문에, 이번 작업의 선택·진행·검증은 Work에 연결한다. 중요한 제품 선택은 [Project decisions 기준](../../context/project/decisions/README.md)을 따르고, 하네스 구조·운영의 전환은 [하네스 변경 기준](../harness/README.md#하네스-변경-규칙)을 따른다. 루트 가이드는 상세 정책 저장소로 늘리지 않는다.
4. 논의나 결정을 남길 때는 선택한 이유, 의미 있는 대안과 기각 이유, 받아들인 비용, 아직 열려 있는 조건을 보존한다. 핵심 발화의 정확한 문구가 판단 근거라면 최소 발췌와 출처를 함께 남긴다. 원문·과거 record는 새 결론으로 덮어쓰지 않고 현재 의미와 당시 판단을 구별한다.

## 반영과 확인을 끝까지 잇는다

선택한 Owner의 관리 계약으로 기존 본문에 통합하고, 주변 설명·참조·실제 소비자까지 필요한 범위에서 맞춘다. Personal·Project에는 그 영역의 관리·작성 기준을, Work에는 [Workspace 문서 작성 기준](../../context/work/workspaces/DOCUMENT-WRITING.md)을 적용한다. 같은 체크리스트나 형식을 모든 문서에 확장하지 않는다.

작성 뒤에는 원래 요청과 근거에 대조해 조건·예외·이유·강도가 보존됐는지 보고, 독자가 실제 진입점에서 필요한 판단을 할 수 있는지 확인한다. 링크·형식 검사는 이 내용 판단과 별도로 수행한다. 개발 요구 충족의 독립 검증은 development가, 문서 자체의 반영 확인은 context-update와 해당 관리 계약이 맡는다. 문서 수정으로 제품 결함이 해결되거나 사용자 수락이 끝난 것으로 기록하지 않는다.

반영한 의미와 확인·미확인, 남은 담당·행동을 원래 작업에 반환한다. 기록 접수와 실제 반영을 구별하고 Main이 같은 Work 문서를 중복 편집하지 않는다. 기록을 위해 커밋을 먼저 만들거나 코드·문서 두 번의 커밋을 강제하지 않는다. 커밋이나 PR 작성이 요청되면 실제 변경과 사용자 범위에 맞추며, PR 본문은 [PR 작성 절차](pull-request.md)를 따른다.

옛 문서 명령에서 무엇을 받아들이고 제외했는지는 [절차 통합 결정](../decisions/2026-10-31-development-document-workflow-integration.md)에 남긴다. 일상 실행에는 위 현재 본문을 사용한다.
