# 경비 날짜의 공유 계약과 저장 전 정규화

2026-10-02. 현재 기준은 [날짜와 시각](../../context/project/common/date-and-time.md)이 소유한다.

사용자는 기존 서버 직렬화 합의를 지적하며 “서버에서 이미 한다고 했으면서 … 여기서 왜 맞춰야 하는지”를 물었다. 서버 serializer는 저장 후 응답을 만들지만 datetime 수정 요청은 그 전에 date-only 검증에서 거부됐으며, 이 불일치는 직렬화 공통화 이전에도 존재했다. 직접 수정 HTTP 함수에만 추가했던 보정은 별도 HTTP 경로를 사용하는 Local 동기화를 해결하지 못했다.

사용자가 일관성과 응집성을 기준으로 위치를 물었고, Main은 날짜 규칙을 공유 schema가 소유하며 Repository의 Local/Remote 분기 전과 서버 요청 경계에서 같은 규칙을 적용하는 안을 제시했다. 폼은 날짜만 만들고 서버 serializer는 기존 응답 책임을 유지한다는 설명 뒤 사용자가 “그럼 수정해봐”로 실행을 요청했다.

경비 날짜는 기존 API entity의 YYYY-MM-DD를 기준으로 맞춘다. 기존 offset 포함 datetime의 호환 변환은 기존 서버 serializer와 동일한 UTC 날짜를 사용한다. date-only를 현지 시간으로 재해석하지 않는다. 예를 들어 2026-10-02T01:00:00+09:00는 2026-10-01로 수용하며, 이미 올바른 날짜는 변하지 않는다. 이 기준은 과거 입력자의 현지 날짜를 역추정하거나 결제일·사용일을 새로 정하는 결정이 아니다.

서버만 변환하면 활성 여행의 Local 저장이 다르고, 직접 HTTP 함수만 변환하면 동기화가 빠진다. 같은 schema를 양쪽 입력 경계에서 적용해 별도 변환 사본을 없앤다. 기존 Local row는 표시·수정 시 읽고 기존 큐는 서버 요청 시 수용하므로 일괄 데이터 migration을 추가하지 않는다. PostgreSQL timestamp와 응답 serializer는 유지한다.

검증은 실제 공유 schema, Repository 양쪽 분기, 폼 날짜 선택과 기존 값 표시, sync 전송 payload, Express 요청 검증·DB에 넘긴 날짜·응답을 확인한다. DB·인증 대역을 사용한 route 검사는 실제 PostgreSQL·JWT·실기기 동기화의 증거로 확대하지 않는다.
