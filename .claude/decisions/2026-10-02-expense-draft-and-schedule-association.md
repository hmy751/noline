# 경비 초안 보존과 일정 연결의 독립성

2026-10-02 사용자 논의에서 확정한 제품 선택이다. 현재 제한·소비 기준은 [Policy Architecture](../context/policy-architecture.md), 여행 데이터 관계는 [제품 기준](../../context/project/common/product.md)이 설명한다. 이 기록의 채택 상태는 구현·검증 완료나 사용자 acceptance를 뜻하지 않는다.

## 연결의 의미를 먼저 정했다

기존 경비 생성은 활성 여행의 offline 상태에서 별도 수동 폼으로 교체되어 일정 연결을 숨겼다. 생성·수정의 일정 후보도 경비 날짜와 같은 날로 한정했다. 그러나 Schedule과 Expense는 같은 여행에 속한 Data Entity이고, 활성 여행의 일정은 이미 Local에 있다. Expense의 `date`와 `scheduleId`도 서로 다른 저장 필드다.

사용자는 “당연히 활성 여행에서는 오프라인 일정 연결 변경할 수 있어야 하고”라고 요구했다. 날짜 독립성을 확인한 뒤 “일정을 연결할 수 있는건 말그대로 일정에 연결을 할거냐 안할거냐”라고 정리했고, 같은 여행의 모든 날짜 일정을 표시하는 방향에 “그래 그렇게 정하자”라고 승인했다. 따라서 오프라인을 이유로 Local 일정 연결을 막거나 같은 날짜로 후보를 한정하는 기존 동작을 대체한다.

연결은 같은 여행 일정 하나에 대한 선택적 관계다. 선택한 일정의 제목·날짜·시간을 보여 주고, 명시적인 연결 해제를 제공한다. 경비 날짜 변경은 연결을 초기화하지 않는다. 후보는 날짜·시간순으로 보여 주며 처음에는 경비 날짜 그룹에 접근하기 쉽게 한다.

## 작성과 데이터 공개를 따로 다룬다

이미 열린 생성·수정 초안은 네트워크 변화에도 입력을 계속 표시한다. 비활성 여행의 offline/unknown에서는 일정 목록 조회·새 선택과 서버 저장을 제한하지만 기본 입력과 기존 연결 설명·해제는 남긴다. 목록·상세의 읽기 제한과 cache 보존은 계속 유지한다. 제한 사유와 실패는 각각 해당 기능 영역에 보여 주고, 복구 뒤에는 사용자의 명시적인 재시도를 기다린다. 최종 쓰기 권한과 Local/Remote 선택은 Activation Router가 맡는다.

일정 생성에서 먼저 적용한 입력 수명·기능별 제한 기준을 경비에 적용하되 장소 검색과 Local 일정 연결은 서로 다른 기능임을 보존한다. 별도 수동 경비 폼이나 전체 화면 교체는 이 기준을 충족하지 못하므로 하나의 작성 폼으로 통합한다.

## 남은 선택과 재검토 조건

경비 날짜를 결제일·사용일 중 무엇으로 정의할지와 모든 경계의 date-only/datetime 통일은 결정하지 않았다. 현재 Remote 수정 계약에 맞춘 HTTP 경계 보정은 이 장기 의미의 채택으로 해석하지 않는다. 날짜 계약의 확인된 차이는 [날짜와 시각](../../context/project/common/date-and-time.md)이 소유한다.

활성 여행이 여러 개로 바뀌거나, 연결 후보가 다른 여행까지 확장되거나, 일정 삭제·접근권 변경이 기존 연결에 미치는 제품 의미를 새로 정할 때 이 기준을 다시 검토한다. 이번 선택만으로 서버의 같은 여행·소유권 검증이 완비됐다고 판단하지 않는다.


후속으로 사용자가 날짜 규칙의 공유 위치와 Local/Remote·서버 입력 경계를 맞추는 작업을 승인했다. 날짜 표현과 기존 datetime 호환의 현재 결정은 [경비 날짜 경계](2026-10-02-expense-date-boundaries.md)를 따른다. 결제일·사용일의 의미는 계속 열려 있다.
