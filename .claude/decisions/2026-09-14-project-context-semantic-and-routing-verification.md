# Project context 갱신의 의미·사실·진입 경로 검증

날짜: 2026-09-14

## 배경

[주제 구성과 읽기·갱신 기준](2026-09-14-project-context-authoring-and-reading.md)을 적용한 첫 초안은 파일 구성과 일부 설명을 개선했지만, 기존 통화 의미 누락, Expense 날짜의 사실 범위 확대, 기존 runbook 연결 누락, `current`의 일회성 실행 이력 누적을 함께 남겼다. 기존 기준에는 원자료 통합, 코드 대조, 읽기 경로, current의 추가 효용이 이미 있었으므로 각 사례의 금지문을 더하는 것만으로는 같은 종류의 실패를 막기 어렵다.

원실행의 도구 기록은 남아 있지 않아 실행자가 무엇을 읽고 어느 판단을 생략했는지는 확정하지 않는다. 확인된 문제는 기존 원칙이 초안 전 대조 기준과 초안 후 관찰 가능한 확인 행동으로 충분히 이어지지 않았다는 점이다.

## 선택

큰 Project 갱신과 승인된 주제별 Owner 이동은 다음 관계를 구별해 확인한다.

- 쓰기 전에 기존 Owner에서 보존할 의미, 직접 확인할 사실과 구현 경계, 새 결정이 필요한 열린 선택, 변경으로 영향받는 실제 진입점을 대조 기준으로 잡는다.
- 초안 뒤에는 기존 의미가 보존·갱신·의도적 제외 중 어디에 놓였는지 확인한다. 문서가 짧아졌거나 구조가 좋아진 사실은 의미 보존의 증거가 아니다.
- 여러 경계를 하나의 사실로 설명하면 각 경계를 확인하거나 문장을 확인한 범위로 좁힌다. 구현 차이와 채택할 제품 의미를 구별한다.
- Project README뿐 아니라 같은 작업을 시작시키는 대표 active runbook·workspace guide·호환 문서·skill에서 현재 Owner까지 따라간다.
- `current`의 구현·검증 설명은 다음 판단을 어떻게 바꾸고 어떤 변화에서 다시 확인할지 연결한다. 그 관계가 없는 실행 수치·당시 도구 오류·미실행 항목은 Work 기록에 둔다.

이 확인을 고정 양식, 모든 링크의 일괄 순회, 매번의 독립 reviewer로 만들지는 않는다. Project의 관리·구성·읽기 본문이 기준을 소유하고 읽기·갱신 skill은 실행 동작만 맞춘다.

## 재시험

제품 초안이 없던 기준 commit `2937c252a735ecc6edbe1d3516659fcf459da970`의 격리 worktree에 수정한 지침 다섯 개만 적용하고, 별도 Codex 실행에 Workspace 002 Ticket 01–05의 지속 의미와 승인된 Owner 이동을 요청했다. 예상 파일명과 앞선 네 실패의 정답은 prompt에 주지 않았으며 제품 코드·Workspace·과거 record·machine 상태 수정과 commit을 금지했다.

유효한 재시험은 `gpt-6-astra`, high reasoning의 ephemeral 실행이었다. 앞선 두 시도는 executable 경로 오류와 reasoning 설정 오류로 산출물 생성 전에 중단했으며 지침 효과의 결과로 세지 않는다.

재시험 결과는 네 관찰에서 개선을 보였다.

- 새 통화 본문은 Trip 기본 통화뿐 아니라 Expense별 통화 선택, 오프라인 입력의 필수 통화, 금액과 통화 코드·기호의 동시 표시를 이어받았다.
- 날짜 본문은 entity, create/update request, form, local 저장, server 저장·response, activation을 분리했고 현재 구현의 서로 다른 표현과 미정인 제품 선택을 구별했다.
- 기존 API·날짜·통화 runbook과 client/server/schema guide, 호환 문서에서 새 Owner로 이어지는 경로를 맞췄다.
- `current`에는 다음 변경에서 단위·route·SQL·기기 검사를 고르는 관계와 재확인 조건을 남기고, 이전 실패의 테스트 개수·EPERM·Docker 미실행을 복제하지 않았다.

실행은 21개 active 문서를 수정하고 Project 본문 5개를 만들었다. 이 수는 적정 구조의 보장이나 모든 제품 문서의 수락을 뜻하지 않는다. 다만 허용된 문서 범위, 344개 local link, `git diff --check`, Workspace 001·002와 기본 Recover를 자체 확인했고 제품 코드·Workspace·record·machine 상태·HEAD는 보존했다. `harness:check`는 기준 tree에 이미 있던 `.claude/README.md`의 `settings.local.json` 누락 링크에서 실패했으며, 제품 검사는 다시 실행하지 않았다.

재시험 산출물은 지침 효과 확인용이므로 현재 제품 초안에 복사하지 않는다. 제품 의미의 실제 수락과 본문화는 Workspace 004의 별도 제품 계약 Ticket이 맡는다.

## 다시 볼 조건

다음 독립 갱신에서도 기존 의미 누락, 확인하지 않은 경계의 일반화, Project README 밖의 실제 진입 경로 누락, 판단 효용 없는 실행 이력 누적이 반복되면 문구 보강이 아니라 실행 단계의 검증 배치와 독립성 필요를 다시 판단한다. 문서 수가 많거나 적다는 사실만으로 이 결정을 성공·실패로 판정하지 않는다.
