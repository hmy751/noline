# 여행 도시 시간대와 UTC 저장 유지

2026-10-06 채택. 현재 의미의 Owner는 [Project 날짜와 시각](../../context/project/common/date-and-time.md)이다. 이 문서는 선택 이유와 재검토 조건을 보존한다.

## 선택한 기준

여행을 서울에서 계획하고 현지에서 열어도 같은 여행 날짜·예약 시각을 보도록, Trip이 도시의 IANA `timeZone`을 소유한다. 여행 기간과 Schedule 시각의 기존 ISO datetime 저장·전송은 유지한다. 폼에서 도시의 날짜·시각을 UTC로 바꾸고 표시·묶기·기간 계산에서는 같은 도시 시간대로 읽는다. Expense의 기존 `YYYY-MM-DD`는 그대로 보존하며 기본 날짜와 연결 일정 날짜만 도시 기준으로 얻는다.

사용자는 “기존에 데이터 utc 저장이나 이런건 일관성을 유지하고 여행, 일정, 경비 등 해당 도시의 타임존을 고려해서 해당 로컬의 시간을 기준으로 … 저장하고 표시”하는 방향을 선택했다. Trip 기간까지 date-only로 바꾸는 방안은 이번 변경에 채택하지 않았다. 저장 형태의 일괄 개편 없이 기준 시간대를 명시해 홈과 목록의 날짜 차이를 해결할 수 있기 때문이다.

## 책임과 호환

도시 조회는 시간대를 확인하고, Trip은 저장하며, shared datetime helper가 변환·달력 계산을 맡는다. 폼·화면은 해당 Trip 시간대를 전달하고 기존 Repository·Activation Router·transaction·sync 경로를 유지한다. 기기의 기본 시간대나 임의 고정 offset을 새 저장값의 기준으로 삼지 않는다.

기존 Trip에는 시간대가 없고 과거 폼의 의도를 timestamp만으로 확정할 수 없다. nullable field 추가로 데이터와 큐를 보존하고, 미확정 상태를 드러낸 뒤 도시 좌표로 확인해 기존 수정 경로로 저장한다. 시간대 확인만으로 기존 timestamp를 이동하지 않는다. 과거 값의 날짜 교정은 사용자의 명시적인 기간 편집으로 구별한다.

종료일은 마지막 포함 날짜다. 활성화 유예는 그날 이후 도시 달력 7일을 온전히 보장하는 경계로 계산한다. 기존의 종료일 자정 + 7일 계산에서 마지막 날을 온전히 포함하도록 기준을 명확히 한 변경이며, 별도 soft-delete 보존 기간이나 대기 큐 보호를 바꾸는 것은 아니다.

시간대 조회 가능 여부는 `canResolveTimeZone`, 여행 생성·수정 가능 여부는 `policy.trip.create/update`로 구별한다. 공개 도시 조회가 가능해도 서버 인증이 만료되면 새 여행 생성과 비활성 여행 수정은 제한되며, 활성 여행의 Local 수정은 유지된다. 시간대 조회 성공을 저장 권한으로 간주하지 않는다. 별도 권한 시스템 없이 기존 정책표와 인증·unknown·활성 확인 제약을 사용한다. 시간대 준비 여부와 조회 상태 표시는 폼이 소유한다.

시간대 요청은 실제 관측 기준, 폼의 버튼·제한 안내는 기존 display 정책을 따른다. 저장 시 최신 조건과 Debug 쓰기 차단은 Router가 확인한다. 정책이 반환하는 pending·재확인 행동을 문구로 축소하지 않고 기존 인라인 안내로 연결하며, 연결 전환이나 저장 실패로 초안을 버리지 않는다.

## 다시 판단할 때

한 Trip에서 여러 도시, 항공편의 서로 다른 출발·도착 시간대 또는 DST 반복 시각 선택을 지원하게 되면 Trip 단일 시간대의 충분성을 다시 본다. 이때 일정별 시간대가 필요한 이유를 정의하고 기존 시점의 의미를 보존한다. 기존 timestamp의 의도가 확인되는 신뢰할 수 있는 원자료가 생기면 해당 데이터의 복원 범위만 별도로 판단한다.
