# 필요한 자료와 판단의 흐름을 잇는 재개 안내

2026-11-04. 이 기록은 record-work가 Workspace의 `recover.md`를 갱신 대상으로 포함한 선택의 근거다. 재개 안내의 작성·사용 기준은 Work 지침이 소유하고, 스킬은 그 기준에 따라 기록 변경과 읽기 안내를 연결한다.

## 선택에 이른 이유

사용자는 직접 읽기로 재개할 수 있다는 설명만으로는 충분하지 않다고 보았다.

> “워크스페이스 다 읽으면 당연히 좋긴하지 근데 양이 엄청 많아질수 있잖아? 중요한건 그것같아 다른 대화세션으로 넘어가도 흐름이나 뉘앙스나 이런게 잘 유지되는 기준”

이어 별도 파일을 두는 방향을 선호하되 JSON 자체를 고정하지 않았다.

> “난 recover.json같은 파일은 두는건 좋은것 같은데? 근데 다만 지금 형식에 맞추는걸 꼭 고려한느걸로 그러면 꼭 json이지 않아도 되고 뭐 이런건 고민하고 결정하면 되는거고”

구성 기준을 발견하는 위치도 논의했다.

> “좋아 더 논의하거나 구체화 할건? 그리고 구성은 지침을 두는게 나아 보이긴 하네 진입 문서처럼 아님 스킬에 두던가 등”

공통 지침과02의 안내 예시를 대조한 뒤, Workspace 루트의 Markdown `recover.md`, Work 진입 지침의 공통 기준, README 연결과 기존 current의 내용 소유, 생성 담당의 초기 구성과 기록 담당의 조건부 갱신안을 제시했다. 사용자는 “그래 그럼 그 안으로 프로토타입부터 적용해봐”라고 적용을 요청했다.

출처 식별: 설계 대화 `01a185c9-de03-7111-8615-110dd6ca1122`, 원문 파일 `rollout-2026-10-29T12-52-41-01a185c9-de03-7111-8615-110dd6ca1122.jsonl`, 사용자 발화 L1791·L1813·L1826·L1899·L2019·L2033과 그 사이 제안. 위 발췌는 문서량·뉘앙스·별도 파일·형식 유보·지침 배치와 적용 요청을 재검토할 최소 근거다. 첫 인용은 L1791 발화의 후반부이며 나머지 인용은 해당 발화 문구를 유지했다.

## 스킬에 연결한 범위

- record-work의 사람용 수정 범위에 `recover.md`를 명시했다. 안내의 의미가 유효하면 호출마다 갱신하지 않는다.
- 담당자는 현재 판단·조건·미정을 관련 current에 충분히 남기고, 읽기 안내에는 자료 선택에 필요한 짧은 뜻과 범위를 연결한다. 기본 읽기 문서 수나 모든 Work의 동일 양식을 만들지 않는다.
- 생성 스킬은 새 안내를 구성하고 README에서 연결한다. 생성 뒤 인수 확인은 그 진입과 안내를 사용한다.
- development는 대상의 재개 기준을 사용한다. 기록 스킬이 개발 목표나 검증 책임을 대신 결정하지 않는다.

이번 범위는 prototype 실행 문서의 연결이다. Reference의 기존 JSON/runtime 전환과 실제 새 세션의 재개 효과는 해당 적용·검증 결과로 따로 판단한다. 원문 입력 구간과 기록 담당 재사용 방식은 기존 계약을 유지한다.
