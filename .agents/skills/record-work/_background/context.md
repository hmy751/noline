# 필요할 때 호출하는 작업 기록 담당자

사용자는 기존 Maintain 방식의 비효율과 토큰 소모 때문에 상시 자동 점검을 없애고 스킬로 보완하려 했다. 비용 문제는 사용자 판단이며 비교 측정 결과가 아니다. 호출된 서브가 대화 원문을 읽고 기록할 의미를 판단하며 직접 수정하는 A를 선택했다. Main이 미리 기록 내용을 판단해 전달하는 B는 제안됐으나 선택되지 않았다.

마무리나 필요 시 호출하고 같은 대화에서 두세 번 쓸 수 있는 담당자를 바로 종료하지 않는 방향을 택했다. 재사용은 이전 이해를 활용하려는 선택이며 호출 사이에 자동 추적하거나 다른 세션에서도 생존을 보장한다는 뜻이 아니다. 원문은 직전 반영 이후를 기본으로 하고 필요한 앞선 대화를 탐색할 자유를 둔다.

Work 기록과 관련 컨텍스트 반영은 기존 워크플로에 맞춰 나눴다. development의 전체 영향 판단, improvement-loop의 사용자 요청·개선 선택, context-update의 지정 Personal·Project 반영을 유지한다. 기록 담당자의 기본 수정 책임은 Work이며 같은 서브가 별도 반영을 맡아도 책임과 권한을 새로 배정한다.

기존 Workspace 문서 작성·Spec/Ticket 갱신 기준에 내용 충분성·이유·조건·중복·원문·검증 지위가 이미 있다. 새 스킬은 이를 참조하고 호출·입력·재사용·직접 수정·반환을 맡는다. 기존 read-only 판단과 guarded apply의 기계 집행은 직접 수정하는 agent·host 권한과 다른 방식이다. 동일한 기계 보장을 주장하지 않는다.

재개에서는 전체 Workspace를 읽게 하는 방식의 비용과, 자료를 임의로 줄였을 때 판단의 흐름·뉘앙스가 빠질 가능성을 함께 보았다. 사용자는 별도 재개 안내 파일을 두고 현재 문서 구성에 맞추는 방향을 선택했다. `recover.md`는 필요한 자료·이유·조건을 연결하며 현재 판단의 상세는 기존 current가 유지한다. 초기 안내는 생성 담당자가 구성하고 기록 담당자는 방향·단계·중심 과제·경로가 바뀌어 안내도 달라져야 할 때 갱신한다. 재개 안내 관리가 매 응답 호출이나 전체 상태 복제의 이유가 되지는 않는다. [선택 근거와 적용 경계](records/2026-11-04-recovery-guide.md)를 함께 본다.

skill-creator의 필요에 따른 상세 분리와 기존 prototype 스킬 관리 정책을 적용했다. Main과 서브의 수행 상세를 나누되 SKILL.md가 공통 실행 계약을 유지한다. 원문 접근 방법은 improvement-loop와 공유하고 전체 검토와 증분 기록의 범위는 각각 둔다. 실제 host별 원문 접근·재호출·파일 반영 효과는 사용 장면으로 확인해야 하며 지침 작성만으로 입증되지 않는다.

## 기록에서 다음 행동의 우선순위를 다시 보는 이유

2026-11-06. 기록에 앞선 리뷰의 발견 사항과 사용자의 선택이 모두 있어도 배치에 따라 다음 세션은 리뷰의 추천부터 실행할 수 있다. 실제 재개에서 사용자는 “마지막 문제 2가지는 아직 그렇게 중요한건 아니고 일단 문제 배경이랑 잘 확인해봐 코드랑 면밀하게”라고 순서를 바로잡았다. 발견 사항은 나중에 쓸 가치가 있었고, 사용자는 그보다 먼저 현재 구현의 구조와 배경을 살피려 했다.

정정 전 자료로 기록 작성을 다시 비교했을 때 두 작성자 모두 미커밋 구현과 잠정 기준을 보존했다. 첫 행동을 대조한 작성자는 리뷰의 추천이 아직 채택되지 않았다는 점까지 문안에 직접 남겼다. 그 문안을 읽은 독자는 Ticket·변경 내역·앞선 대화를 추가로 본 뒤 화면 흐름부터 살피겠다고 했다. 조건별 한 번의 관찰에서 확인한 이점은 추천과 선택의 구별이었다. 재개 시간이나 읽기량 절감은 확인하지 못했다.

정정 뒤의 비교에서는 작성 지침에 구체적인 예시를 넣자 독자의 첫 행동도 예시에 제시한 장면과 같아졌다. 사용자는 “경비 예시는 빼고 확인 문장만 record-work에 넣자”라고 선택했다. [기록 담당자 지침](../references/maintainer.md)에 작성자가 자기 문안과 사용자 우선순위를 대조하는 방식으로 반영했다. 상세 비교는 설계 Workspace 014의 기록 `2026-11-06-ticket02-record-work-next-action-check.md`에 있다.
