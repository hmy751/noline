# 재개 안내를 사용하고 기존 검증 책임을 유지한다

2026-11-04. 사용자 요청에 따라 prototype의 재개는 Work 지침과 Workspace의 `recover.md`를 연결하고, 검증 실행은 Project의 직접 검사와 기존 도구를 사용하도록 맞췄다. 새로운 재개·검증 스킬은 만들지 않았다.

## 재개에서 바꾼 관계

사용자는 전체 Workspace를 읽는 비용을 줄이면서 다른 세션에서도 판단의 흐름과 뉘앙스를 유지할 기준을 원했다. 별도 안내 파일과 공통 Work 기준을 선택한 근거는 [재개 안내 연결 기록](../../../record-work/_background/records/2026-11-04-recovery-guide.md)에 있다.

development는 현재 요청의 목표·참여 범위를 판단하고, Work의 안내에서 필요한 자료를 선택한다. 읽을 경로·충분성과 안내의 관리는 Work가 소유한다. 현재 요청을 과거의 다음 행동보다 우선하는 기존 기준과 한정 위임의 입력 선택은 유지한다.

## Verify를 별도 검증 책임으로 두지 않은 이유

사용자는 “뭔가 development와 겹치지 않으면서 필요한걸 남겨야 하는데 잘 안 떠오르네 난”이라고 했고, 다음으로 비교를 요청했다.

> “그래 그럼 Verify 없앴을 때 실제로 곤란한 기능이 있는지 기존 도구로 되는 거랑 비교해서 확인해봐”

비교 뒤 아카이빙 방향을 정하면서 적용 전 구체화를 요청했다.

> “그래 그럼 Verify는 아카이빙하는 방향으로 하고, recover는 논의한 재개 안내 방식으로 프로토타입부터 적용해봐 아 적용전에 더 구체화하거나 결정할건?”

Main이 재개 안내의 이름·형식·배치·관리 책임과 prototype 우선 적용안을 제시한 뒤 사용자는 “그래 그럼 그 안으로 프로토타입부터 적용해봐”라고 승인했다. 앞선 아카이빙 방향 선택과 마지막 적용 승인을 구별한다.

출처 식별: 설계 대화 `01a185c9-de03-7111-8615-110dd6ca1122`, 원문 파일 `rollout-2026-10-29T12-52-41-01a185c9-de03-7111-8615-110dd6ca1122.jsonl`, 사용자 발화 L1911·L1923·L2019·L2033. 기능 대조의 보존 위치는 Workspace014의 `records/2026-11-04-verify-removal-tool-comparison.md`다. 그 검토에서 동일 제품 검사 7개가 직접 실행으로 통과했고, 실패 코드·출력 저장과 파일 해시 비교를 확인했다. 유한한 자식 프로세스 비교에서는 Python의 직접 프로세스 timeout 뒤 자식이 완료 표시를 남겼지만 Verify의 프로세스 묶음 종료 뒤에는 남기지 않았다. 기존 도구의 응답 대기도 강제 종료를 뜻하지 않았다. 이 차이는 전체 Verify 역할을 유지할 필수 근거와 구별했으며, 특정 실행 환경의 한정 확인을 모든 host의 동등한 보장으로 확대하지 않았다.

제품 검사 선택·충분성·이전 근거 재사용은 기존 development에 있다. 검증 담당은 실제 근거와 접근점을 반환하고, Main이 연결한 record-work가 필요한 Work 기록을 남긴다. 기존 선택적 Verify 권고를 제거하고, 별도 Verify 실행이나 기계 상태 갱신을 완료 조건으로 추가하지 않도록 했다. 시간·출력 제한이 필요한 검사에서는 실제 실행 도구의 범위를 확인하도록 남겼으며, 새 실행기·기계 상태·영구 로그 의무를 만들지 않았다.

이 prototype에는 Verify runtime이 없었다. 따라서 이번 변경은 실행 본문의 연결이며 Reference 코드·기존 증거의 아카이빙 완료나 모든 host의 동등한 실행 보장을 뜻하지 않는다. 과거 Verify 선택의 기록은 당시 근거로 유지한다.
