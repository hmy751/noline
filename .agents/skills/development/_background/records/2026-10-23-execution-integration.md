# 개발 실행 계약의 통합

2026-10-23, 개발 workflow의 설계 항목1~15를 합의한 뒤 사용자가 실제 실행 본문과의 대조·반영을 요청했다. 이는 Noline 제품 사건이 아니라 이 prototype의 설계·편집 작업이다.

## 직접 요청과 선택

> 좋아 그럼 1~15번 합의한 내용이랑 실제 실행 본문을 대조해서 반영해보자 더 구체화 하고 논의할건 없지?

직전 기록 책임에 관한 발화:

> 음 근데 maintain 얘기했었는데 연결은 안하고 추후 스킬로 보완할까 생ㄱ가인데 어쨋든 main이 맡는거니까 딱히 방향성이 내가 생각한거랑 달라보이진 않아서 괜찮아 보여 그래도 뭐 지침이나 이런건 따를거고 그래야 work project등의 구성을 알고 할테니까 일단 메모정도 하고 맞다면 15번도 합의하고 기록하자

Main은 대상 지침·관리 계약을 이해하고 직접 기록하는 방향으로 해석해 반영했다. 미래 스킬 보완은 아이디어이며 현재 신규 스킬·Maintain 연결의 승인이 아니다.

## 실행 본문에서 달라진 것

공유 기준·독립 재판단·Main의 종합은 기존 내용을 유지했다. 구현자의 맥락 이해·적용, 자기 설계 비교·독립된 기대 결과·완성 인계는 development 본문에 구체화했다. 검토 상세에는 실제 입력·추가 탐색·권한·호출을, development에는 원래 구현자 수정 기본값·필요한 재검토·종료·검증 인계를 연결했다.

모델·추론·상속·재사용은 [실행 배치](../../references/execution.md)로 분리했다. Main의 배정 때 필요한 내용을 모든 검토자에게 기본 완독시키지 않기 위한 선택이다. GPT-6.1-sol medium과 검토자 한 명은 합의한 시작점이며 실제 환경 지원·입력과 함께 판단한다.

work-discussion의 명시 호출 조건과 자동 호출하던 development 문구의 충돌을 제거했다. work-discussion의 Maintain 전제는 Main의 실제 지침 기반 갱신으로 바꿨다. read/update/reconsider/create-context 스킬의 보존 원형은 그대로 두고 실제 설치·계약 적합성이 있을 때만 연결한다. 필요한 맥락 선택·재판단·갱신은 Main이 본문에서 직접 수행할 수 있다. 새로운 기록 스킬을 만든 것은 아니다.

Personal의 오류·계약에는 증상 대응과 원인 수정·필요한 복구의 구별을, 이름·타입에는 모순된 상태 조합·반복 방어와 새 구조 비용의 비교를 통합했다. 내용의 소유를 workflow로 옮기거나 특정 표현 기법을 의무화하지 않았다.

## 확인 경계

이번 반영은 실행 지침과 진입·관리 경로의 통합이다. 도구 호출 성공이나 정적 문서 검사만으로 실제 장기 효과·제품 요구 충족·운영 설치를 주장하지 않는다. 과거 기록·보존 원문과 별도 진행 중인 explain 작업은 이번 결론으로 덮어쓰지 않는다.

독립 대조에서6번의 실제 사용 경로 완성 조건이 압축돼 약해졌다는 의견을 받았다. Main은 원래 합의를 대조해 호출부·설정·연결·설명과 의도적 부분 인계의 경계를 본문에 복원했다. 나머지 주요 합의 변형·권한 충돌은 보고되지 않았다. 이는 문서 대조이며 실제 제품 수행 효과의 검증은 아니다.
