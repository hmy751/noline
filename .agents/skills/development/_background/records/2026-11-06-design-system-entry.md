# UI 작업을 디자인 시스템 판단으로 잇는 문구

이 기록은 [개선 검토](../../references/review.md)의 호출 판단에 공통 변경을 더한 이유와, UI 작업의 읽을 곳을 [development](../../SKILL.md)에 넣어 보다가 뺀 경위를 보존한다. UI 판단의 의미는 [디자인 시스템 판단](../../../../../context/personal/development/design-system/INDEX.md)이 소유한다.

## 문제

같은 앱의 UI 작업을 비교 사본에서 세 번 측정했다. 선택 표에 입구 한 줄만 두었을 때는 목록 작업이 Project의 UI 문서에서 멈췄다. 앱 가이드가 UI 작업을 그 문서로 안내하고, 세션이 Personal 안내를 열지 않았기 때문으로 보인다. 측정의 관찰은 [본문의 근거](../../../../../context/personal/development/design-system/_background/evidence.md#재측정)에 있다.

## 첫 문구와 결과

구현 상세에 두 문장을 넣었다. 코드를 쓰기 전에 본문을 고르고 앱의 값과 부품을 열어 본다는 문장과, 벗어난 곳과 이유를 반환에 드러낸다는 문장이다.

- **첫 문장:** 5개 세션이 모두 그 파일을 읽었지만 2개는 묶음 출력의 중간이 잘려 문장을 보지 못했다. 문장이 보인 3개는 모두 코드를 쓰기 전에 본문을 읽었고, 보이지 않은 2개는 읽지 않았다. 설계된 대조가 아니고 표본도 작다.
- **둘째 문장:** 5개 세션이 모두 받았지만 벗어난 곳과 이유를 적은 보고가 없었다.

## 자리를 옮긴 이유

세 측정의 Main 세션 11개에서 코드를 쓰기 전에 출력에 보인 자리를 세션 로그로 셌다.

| 자리 | 보인 세션 |
| --- | --- |
| `SKILL.md` 앞부분과 "맥락의 소유와 현재 적용을 구별한다" 절 | 11/11 |
| `implementation.md` 첫 절 | 9/11 |
| `SKILL.md` "구현자는 검토 전에 맡은 결과를 완성한다" 절 | 7/11 |

Personal의 역할을 설명하는 맥락 절이 뜻에도 맞아 먼저 그 표 뒤에 문단으로 두었다. Codex의 출력 한도에서 나온 값이며 다른 도구에서는 달라질 수 있다.

## 검증 항목을 더하지 않은 이유

작성자는 공통 변경을 검증 담당이 확인하는 항목을 더하자고 제안했다. 사용자가 지적했다.

> 근데 애매한게 이렇게 적용 안됐다고 검증담당도 보게하는것보다 애초에 personal을 검증담당자가 보는게 지금 현재 아닌가?

대조해 보니 기준의 적용을 다시 판단하는 책임은 이미 [개선 검토](../../references/review.md)에 있고 Main이 관련 Personal의 접근점을 넘기게 되어 있다. 측정에서 공통에 옵션을 더한 세션과 공통 결함을 우회한 세션은 모두 개선 검토를 호출하지 않았다. 유일하게 호출한 세션의 검토자도 본문을 읽지 않았다. 규칙이 없는 것이 아니라 연결이 작동하지 않은 것으로 봤다. 그래서 새 책임을 만들지 않고, 공통 부품을 바꾸거나 우회했을 때 개선 검토를 맡기고 본문을 넘긴다는 시점만 더했다. 효과가 없던 보고 문장은 뺐다. 결과 설명은 기존 흐름에 맡긴다.

## 채택과 한계

작성자는 목록과 메뉴만 다시 측정하자고 권했으나 사용자는 "측정 없이 채택"을 택했다. 이어서 문단을 본 사용자가 다듬기를 요청했다.

> 근데 development 본문에 넣은게 뭔가 살짝 뜬금없어보인다 해야하나? 그것만 좀 고려해서 다듬는다면?

이 스킬은 영역을 가리지 않는 절차이고 앱의 값과 부품을 확인하라는 내용은 이미 본문 첫머리에 있다. 그래서 별도 문단을 없애고 두 곳으로 나눴다. 읽을 곳은 맥락 표의 Personal 행에 한 문장으로 넣고, 앱을 확인하라는 문장은 스킬에서 뺐다. 공통을 바꾸거나 우회한 결과는 UI에 한정할 이유가 없어 개선 검토의 호출 판단에 넣었다. Main이 넘길 관련 Personal은 그 절의 기존 문장이 맡는다.

Personal 행의 문장에도 사용자는 다음과 같이 답했다.

> 뭔가 이상한데 그냥 본문스타일상 뭔가 안 어울려

대조해 보니 이 스킬과 상세는 개발 판단의 특정 주제를 이름으로 가리키지 않는다. 그래서 읽을 곳을 스킬에서 뺐다. 작업별 읽을 곳은 Personal 선택 표와 Project 안내가 맡는다. 측정에서 Project 앱 가이드의 UI 행은 11개 세션 모두에 보였으므로, 대상 Project에는 그 행에 입구를 두는 것이 후보다.

사용자는 Personal 쪽 안내에 진입점이 있으므로 충분하다고 판단했다.

> 애초에 personal 쪽에 리드미에 진입점 쪽에 있어서 괜찮을 것 같으데

**남는 한계:** 측정에서 Personal 선택 표의 입구만으로 닿지 않은 세션이 있었다. 사용자의 판단을 따르며 실제 사용에서 어긋나면 다시 본다. Noline 앱 가이드의 수정과 기계 검사는 다루지 않았다. 공통 변경의 호출 문장은 효과를 시험하지 않았고, Main이 공통을 우회했다고 스스로 알아차려야 하며, 개선 검토 상세를 읽지 않는 세션도 있다.

## Noline에 적용하며 바꾼 것

위 내용은 Reference에 반영할 때의 기록이다. Noline에 옮길 때는 위 후보대로 [앱 가이드](../../../../../apps/client/CLAUDE.md)의 UI 행에 본문 링크를 더했다. 스킬에는 여전히 읽을 곳을 두지 않는다. 기계 검사는 스킬이 아니라 앱의 lint 경고로 넣었고 [UI 안내](../../../../../context/project/guidance/development-boundaries/ui.md)가 설명한다.
