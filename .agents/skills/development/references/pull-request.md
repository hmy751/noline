# PR 제목과 본문을 작성한다

PR 제목·본문을 작성하거나 갱신하는 요청에서 사용한다. 리뷰어가 이번 변경의 목적·결과와 확인 근거를 이해하도록 실제 비교 범위를 정하고 최종 변경을 설명한다. 개발 수행과 완료 판단은 [development](../SKILL.md)의 기존 책임을 따른다.

## 비교할 범위를 정한다

사용자가 지정한 범위나 기존 PR의 대상 브랜치를 먼저 확인한다. 지정이 없으면 저장소의 PR 관례·기본 브랜치와 현재 작업 맥락으로 대상을 정하고, 결과를 바꿀 모호함이 남으면 확인한다. `main`을 고정하거나 현재 브랜치의 upstream을 곧바로 PR 대상이라고 가정하지 않는다.

현재 브랜치·HEAD, 작업 트리 상태와 선택한 대상 ref를 확인한다. 대상 브랜치 이름뿐 아니라 로컬 ref가 원격의 어느 상태를 나타내는지도 구별한다. 최신 원격 상태를 확인하지 못했다면 사용한 ref와 한계를 밝힌다.

선택한 대상에 아직 포함되지 않은 커밋과 공통 조상 이후의 최종 diff를 함께 읽는다. 예를 들어 대상 ref를 `target_ref`에 두었다면 `git log "$target_ref"..HEAD`와 `git diff "$target_ref"...HEAD`로 같은 기준을 사용한다. 커밋 메시지는 의도와 경과를 파악하는 자료이며, 되돌리거나 대체한 변경까지 현재 결과로 나열하지 않는다.

미커밋·미추적 변경은 브랜치의 커밋된 diff에 포함되지 않는다. 사용자가 그 변경까지 초안을 요청했다면 포함할 범위를 별도로 대조하고 아직 PR에 포함되지 않은 초안임을 밝힌다. 관계없는 작업을 끼워 넣거나 작성 범위를 맞추기 위해 자동으로 커밋하지 않는다.

## 리뷰어에게 필요한 내용을 쓴다

저장소의 PR 템플릿·기여 지침이 있으면 적용 범위를 확인한다. 제목은 최종 변경의 중심 목적과 결과를 짧게 표현하고, 본문은 해결하려던 문제와 변경 후 동작을 먼저 설명한다. 범위가 바뀌었다면 제목과 본문도 최종 결과에 맞춰 다시 쓴다.

리뷰 판단에 필요한 만큼 다음을 연결한다. 단순 변경에는 짧은 설명과 검증 결과로 충분하며, 커밋 수·변경 줄 수로 목차나 분량을 강제하지 않는다.

- 실제 달라지는 동작·계약과 중요한 선택 이유. 필요하면 변경 전후의 구체적인 사용 예를 든다.
- 실제 수행한 검증, 그 대상·결과와 중요한 미확인. 기존 실패가 남으면 이번 변경과의 관계를 구별하며, 미수행 검사를 통과한 것으로 표시하지 않는다.
- 실제 호환성·데이터·배포 영향이 있을 때 필요한 조치와 적용 순서. 파일명이나 Schema·Router 같은 단어만으로 migration 안내를 만들지 않는다.

작업 대화, 폐기한 시도, 파일·커밋 통계는 선택의 이유나 검토에 필요한 경우에만 담는다. 독자가 접근할 수 없는 로컬 경로·개인 기록을 근거 링크로 쓰지 말고, PR에서 볼 수 있는 코드·검사 결과나 필요한 설명으로 전달한다.

## 범위와 근거를 대조해 반환한다

제목·본문의 주장을 선택한 최종 diff와 검증 근거에 다시 맞춘다. 관련 이슈는 실제 관계와 종료 의도를 확인해 연결한다. 비교 기준·초안 포함 범위·중요한 확인 한계가 있다면 리뷰어가 오해하지 않게 함께 전달한다.

제목·본문 작성만 요청받았다면 작성 결과를 반환한다. commit·push·원격 PR 생성이나 갱신은 해당 행동이 요청·위임된 범위에서 수행하며, 글 작성 자체를 그 권한으로 취급하지 않는다.
