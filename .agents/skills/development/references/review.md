# 구현 단계의 독립 검토와 Main의 판단

관련 Personal·Project·작업 요구를 사용해 만든 결과를 독립적으로 다시 판단하고, Main이 유지하거나 의미 있는 대안을 선택할 근거를 제공한다. 기준을 공유한다는 사실이 현재 선택에 동의한다는 뜻은 아니다. 검토는 Personal 문서를 매번 보완하는 일도, 개선안을 반드시 하나 만드는 일도 아니다.

공유 목적과 판단 범위는 검토자·Main이 함께 사용한다. 아래 검토자 절은 독립 판단과 반환을, Main 절은 종합·선택·후속 연결을 맡는다. 전체 작업의 조율은 [development 본문](../SKILL.md)이 소유한다. 검토자에게 Main의 전체 실행 책임을 그대로 넘기지 않는다.

## 공유할 목적과 재판단 범위

성공은 현재 선택과 기준의 적용을 실제로 다시 보고, 근거 있는 의견으로 유지·변경 판단을 돕는 것이다. 발견·대안·변경의 개수는 성공 조건이 아니다. 실질적인 차이가 작으면 현재 구성을 유지할 수 있다.

- 목표·명시적 제약·보존할 제품 계약은 지킬 조건이다. 전제의 문제를 제기할 수 있어도 검토자가 임의로 변경할 수는 없다.
- 현재 설계·구현 방법, 기준의 적용과 적용 조건, Main이 앞서 고른 해법은 재판단할 수 있다.
- 현재 사실과 가정은 필요한 근거로 확인한다. 특정 문서에 있다는 이유만으로 확정 사실·영구 제약·개인 선호로 일괄 분류하지 않는다.

Personal은 개인의 판단 내용·이유·조건을, Project와 Spec/Ticket은 해당 제품의 약속과 이번 요구를 제공한다. 이 문서는 그 내용을 복제한 개발 원칙집이 아니라 **현재 결과에서 적용·선택을 어떻게 재판단할지**를 소유한다.

## Main은 검토 시점과 입력을 정한다

위험과 의미 있는 선택의 성격으로 호출을 판단한다. 맡은 범위의 첫 결과가 완성됐고 목표 해석·책임·상태·구조에 중요한 선택이 있으면 개선 검토를 기본으로 고려한다. 공통 부품이나 공통 코드를 바꾸거나 그 결함을 우회한 결과도 여기에 든다. Main의 자신감이나 미리 떠올린 대안의 유무를 호출 기준으로 삼지 않는다. 비용이 큰 방향을 일찍 가르거나 막힌 판단을 풀 필요가 있으면 미완성 범위를 밝히고 중간 검토를 맡길 수 있다. 국소적이고 결과가 명확한 수정은 생략·축소할 수 있지만 파일 수가 적거나 테스트가 통과했다는 이유만으로 판단하지 않는다.

Main은 목표·보존 조건, 실제 검토 대상과 사용처·판본·미커밋 범위, 관련 Personal·Project·Work의 본문 접근점과 선택 이유, 수행한 확인·공백을 전달한다. 중요한 대안과 구현 이유도 검증할 주장으로 제공한다. 문제 정의나 보존 범위 자체가 검토 대상이면 발단이 된 사용자 원문과 필요한 인접 맥락도 열어 둔다. Personal·사례를 일부러 숨겨 독립성을 만들거나 전체 대화·자료를 기본으로 넣지 않는다. 요약은 읽기를 돕지만 실제 원문 읽기를 대체하지 않는다.

여러 검토를 나눌 때는 범위·공통 판본·통합 질문을 정한다. 병렬 검토가 각자 국소적으로 타당한 의견을 냈다는 사실만으로 조합의 정합성이 확인된 것은 아니다. 인원·세션·모델과 실제 입력 조건은 [실행 배치](execution.md)를 따른다.

## 검토자는 현재 선택을 독립적으로 비교한다

맡은 범위의 요구와 원문, 변경 결과 및 이해에 필요한 주변 맥락을 직접 대조한다. 구현자가 기준을 반영했을 것이라는 추정이나 작성자의 설명만으로 충족·적절성을 선언하지 않는다. 전달된 요약과 구현 이유는 확인할 자료이며 기대 결론은 아니다.

질문별 본문 선택과 유효한 읽기 재사용은 대상의 공통 사용 방법(이 Project의 [USAGE](../../../../context/USAGE.md))을 따른다. 작업에서 수정한 Project 설명도 평가할 결과에 포함한다. 구현자나 Main이 쓴 새 문장을 자동으로 정답으로 받지 않고 원요구·유효한 계약·실제 사용처에 대조한다.

관련된 주요 선택에서 다음을 함께 본다. 모든 항목의 답안을 출력하거나 모든 부분을 같은 깊이로 점검할 필요는 없다.

- **적용의 적절성:** 기준의 이름을 따랐는지가 아니라 현재 목적·사용처·조건에서 그 선택이 맡은 역할을 해내는지 본다.
- **의미 있는 다른 선택:** 같은 목표·보존 조건에서 다른 책임 배치나 접근이 실제 부담을 줄이거나 요구를 더 잘 충족하는지 비교한다. 기존 결과에 결함이 있다는 증명이 있어야만 개선을 제시할 수 있는 것은 아니다.
- **조건의 재판단:** 기준이 유효해도 이번 적용이 잘못됐을 수 있고, 이번 조건에는 다른 기준·접근이 더 적절할 수 있다. 둘을 구별해 의견을 낸다.

필요하면 실제 호출자·피호출자·상태·테스트와 관련 계약을 따라 관찰을 확인한다. 변경 파일만으로 판단을 닫지 않되, 추가 탐색은 의견의 타당성이나 대안 비교에 필요한 질문을 해결하기 위한 것이다. 근거가 없거나 접근이 막힌 부분은 그 한계가 어떤 판단을 제한하는지 반환한다.

예를 들어 ‘책임을 나누라’는 원칙을 공유해도 새 함수가 실제로 다른 변경 이유를 분리하는지, 사용자가 알아야 할 연결만 늘리는지는 다시 판단해야 한다. 파일·함수 수나 기존 사례와 다른 모양만으로 좋은 변경이라고 보지 않는다. 이 예시는 판단 방법을 보여 주며 별도의 설계 규칙을 추가하지 않는다.

검토자는 실제 사용·변경 장면에서 자기 비교 질문을 세우고, 전달받지 않은 관련 원문도 필요한 만큼 찾는다. 자기 대안도 유리한 조건뿐 아니라 불리해지는 조건과 비용을 확인한다. 추가 탐색은 결정에 미치는 영향과 비용으로 끝낼 시점을 정하며 모든 파일을 다 읽는 것을 목표로 삼지 않는다.

기본 권한은 읽기·분석·허용된 검사·격리된 실험과 의견 반환이다. 허용된 검사에도 외부 부작용·공유 상태 변경이 있으면 기존 실행 권한을 확인한다. 제품 코드와 정본의 수정은 Main의 별도 배정을 따른다. 추가 원문 읽기에 매번 승인을 요구하지 않되 읽기 범위 확장을 수정 권한 확대로 해석하지 않는다. 접근 불가 자료·계약 충돌·권한 공백은 필요한 대상과 막힌 판단을 구체적으로 Main에게 반환한다.

## 주장에 맞는 근거와 깊이를 고른다

| 의견 | 판단에 필요한 근거 |
| --- | --- |
| 요구·계약이 충족되지 않음 | 어떤 약속이 어떤 실제 조건·경로에서 어긋나는지. 관찰한 것과 추론·재현하지 않은 것을 구별한다. |
| 현재안보다 적절한 대안이 있음 | 같은 목표·조건에서 얻는 효과와 줄어드는 이해·사용·변경 부담, 새 연결·전환·유지 비용. 다른 해법이 가능하다는 사실만으로 변경을 요구하지 않는다. |
| 기준이나 전제의 적용이 의문임 | 현재 조건과 원래 적용 이유의 차이, 이번 선택에 미치는 영향. 이번 적용 판단과 지속 기준 변경을 구별한다. |
| 확인 근거가 부족함 | 어떤 요구·경로가 기존 검사로 확인되지 않았고 왜 이번 판단에 중요한지. 미확인을 곧바로 실제 결함으로 부르지 않는다. |

검토 깊이는 관련성·영향·불확실성에 맞춘다. 제품 결과·보존 계약·변경 파급이나 이해·유지 부담을 크게 바꾸는 선택은 더 깊게 본다. 모든 관점·UI 상태·외부 체크리스트를 일괄 적용하지 않는다. 기계 검사가 판정한 동일 항목을 반복하기보다 그 검사로 확인되지 않은 의미와 조건을 살핀다.

Personal에 없는 관점도 이번 문제 발견과 대안 비교의 재료가 될 수 있다. 외부 권고를 사용했다는 이유만으로 기존 기준 위반이나 필수 변경으로 올리지 않으며, 새로운 지속 기준으로 채택하는 일과 이번 활용을 구별한다. 고정 행 수·극적 단순화·자동 공통화 같은 외부 처방을 이 검토의 기본 규칙으로 가져오지 않는다.

반환에는 Main의 선택을 바꾸는 발견과 대안, 그 근거·비용·중요한 가정과 미확인을 남긴다. 조사한 목록 전체를 보고 형식으로 복사하지 않는다. 현재안 유지가 적절하면 판단을 가른 이유를 설명한다. 발견 없음은 전체 요구 검증이나 Ticket 완료 판정이 아니다. 실제 변경은 이번 요청과 배정의 권한을 따르며, 의견 제출과 수정 실행을 구별한다.

지속 본문의 오류·누락이나 달라진 적용 의미를 발견하면 아는 위치·근거·확인 범위를 기존 반환에 붙인다. Main이 [내용 선별과 반영](../SKILL.md#달라진-의미를-해당-owner에-남긴다)을 이어 판단한다. 발견 자체로 정본 편집권을 얻거나 매 정정마다 별도 문서 검토자를 추가하지 않는다.

## Main은 의견을 선택과 다음 행동으로 잇는다

Main은 검토자의 결론을 승인하는 역할에 머무르지 않는다. **관찰·문제가 타당한지와 제안한 해결책을 채택할지는 따로 판단한다.** 문제를 받아들이면서 해결책을 조정하거나 일부만 적용할 수 있다. 연결되거나 충돌하는 의견을 함께 보고 최종 선택의 조합이 목표·계약·전체 설계에 맞도록 책임진다.

계약 문제는 어긋난 약속과 실제 조건을, 개선은 비교 이득과 비용을, 전제 의문은 현재 적용 조건을 본다. ‘이미 동작한다’, ‘Personal과 같다’, ‘Main이 오래 고민했다’는 이유만으로 의미 있는 대안을 기각하지 않는다. 반대로 차이가 작으면 사용자가 익숙한 기존 구성을 유지할 수 있다.

판단은 채택·조정 적용, 기각·현행 유지, 필요한 사실 확인, 후속 분리로 연결한다. 이 이름들은 선택의 설명이며 모든 의견에 부여할 의무 상태값이 아니다. 확인된 필수 요구 미충족을 후속 분리만으로 없애거나 완료로 처리하지 않는다.

추가 확인은 불확실성이 결정에 미치는 영향과 지금 확인할 비용을 함께 보고 선택한다. 현재 근거로 판단할 수 있으면 중요한 가정을 밝히고 진행한다. 확신을 높이는 것 자체를 반복 실험·보류의 이유로 만들지 않는다. 개선의 채택 판단과 실제 수정 결과의 요구 충족 확인은 구별한다.

## 사용자 결정과 함께 볼 가치가 있는 논의를 구별한다

기존 위임·합의만으로 결정할 수 없는 목표·제품 약속·중요한 우선순위나 투자·새 지속 기준의 선택은 사용자에게 연결한다. 원자료를 더 읽으면 풀 수 있는 사실 문제를 곧바로 선호 질문으로 넘기지 않는다. 선택이 필요하면 차이와 비용, Main의 추천과 이유를 준비한다.

Main이 결정 가능한 일이라도 사용자의 이해나 이후 판단에 도움이 되는 중요한 대안·절충은 공유하고 함께 살펴볼 수 있다. 이 논의를 모든 변경의 사전 승인으로 만들지 않는다. 사용자 선택이 필요한 부분만 기다리며 독립적으로 진행 가능한 일은 이어간다. 이미 위임받은 기술 선택이나 명백한 수정마다 다시 승인을 요구하지 않는다.

채택 뒤에는 담당 범위에 맞춰 수정과 필요한 확인을 연결하고 실제 결과·이득을 확인한다. 수정자는 영향받은 기계 검사도 갱신한다. 개선 검토 종료 뒤 최신 결과의 요구 충족은 [검증 상세](verification/INDEX.md)에 따라 별도로 확인하며, 검증자에게 개선 의견 전체의 재승인을 맡기지 않는다. 검증 뒤 국소 결함 수정은 재검증으로 잇고 책임·공개 계약·사용 방식·중요한 절충이 달라지면 관련 질문을 이 검토로 돌린다. 의견을 채택했다고 코드가 수정됐거나 검증이 끝났다고 기록하지 않는다. 이번 결과의 기록·정본 갱신은 [development의 Owner 연결](../SKILL.md#달라진-의미를-해당-owner에-남긴다)을 따른다. 수정 담당·재검토·종료는 [development의 수정과 종료](../SKILL.md#선택을-수정과-종료로-잇는다)를 따른다. 고정 반환 양식이나 발견 수를 만들지 않는다.
