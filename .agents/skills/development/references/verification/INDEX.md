# 요구 충족의 검증과 수정 후 재확인

검증자는 최신 결과가 이번 요구·제품 계약·사용 조건을 충족하는지, 그 결론을 말할 근거가 충분한지 판단한다. 개선 대안의 비교·채택·반영과 이득 확인은 [개선 검토](../review.md)와 Main·수정 담당의 책임이다. 같은 문제를 발견할 수 있지만 검증을 모든 개선 선택의 재승인으로 만들지 않는다.

Main은 검증을 의뢰할 때 시작·입력, 반환을 판단할 때 공백·종료, 수정 뒤에는 재검증 부분을 읽는다. 검증자는 이 수행 상세와 맡은 대상의 관련 원문을 읽는다. [development](../../SKILL.md)는 전체 흐름·역할·완료·기록을, [실행 배치](../execution.md)는 실제 담당자·세션·권한 설정을 소유한다. 제품별 명령·데이터·접근 경로는 대상 Project의 기존 안내와 도구에서 찾는다.

검사·관찰이 현재 주장을 뒷받침하는지 판단할 때는 [근거의 적절성과 재사용](evidence.md)을 함께 적용한다. Main·조사 담당·구현자도 그 상세를 직접 사용하며 검증 역할 전체를 시작할 필요는 없다. 실행 제약의 해결 담당과 반환은 아래 실행 공백 부분에서 연결한다. 필요한 근거를 직접 대조한 것과 별도 검증자의 독립 수행은 구별한다.

## Main은 확인 가능한 최신 결과를 넘긴다

구현자의 자기 확인과 개선 검토에서 채택한 중요한 수정이 끝난 결과로 시작한다. 알려진 결함이나 구현 누락을 검증자에게 마무리하도록 넘기지 않는다. 큰 작업의 독립적으로 확인 가능한 완성 단위는 먼저 검증할 수 있지만 전체 통합의 확인과 구별한다. 필요한 실패 주입·데이터·전후 기준선·실제 어댑터 관찰은 Main과 구현자가 구현 중 준비한다.

제품 동작·계약·통합에 판단이 필요한 의미 있는 개발 결과는 별도 검증자 한 명을 기본으로 한다. 오탈자나 의미 없는 형식 정리처럼 정해진 검사와 직접 대조로 충분하면 Main 확인으로 줄일 수 있다. 변경 줄 수나 자신감만으로 축소하지 않고, 축소한 수행을 독립 검증이라고 부르지 않는다.

첫 검증은 해당 구현·수정을 작성하지 않은 새 컨텍스트에서, 개선 검토와 다른 세션으로 시작한다. 부모 대화와 앞선 판단 이력 전체를 기본 상속하지 않는다. 다음 정보를 짧은 의뢰와 정확한 접근점으로 연결한다. 여섯 항목의 별도 문서나 긴 서식은 필요하지 않다.

| 입력 | 넘길 내용 |
| --- | --- |
| 요구와 보존 조건 | 현재 요구, 유효한 정정, 제품 계약, 지켜야 할 기존 동작 |
| 실제 대상 | 위치·판본·변경 범위·포함한 미커밋 변경과 병행 작업 |
| 사용 조건과 맥락 | 실제 호출자·사용 환경, 관련 Project·Work·Personal 본문과 적용 이유 |
| 기존 근거 | 실행 원본·검사 코드·재현 방법과 조건. 작성자의 완료 주장은 검증할 주장으로 전달 |
| 남은 공백 | 알려진 문제, 미실행·불확실성, 대체 환경이 생략한 경계 |
| 실행 방법과 권한 | 기존 명령·도구·준비 안내, 허용된 데이터·외부 실행·수정 범위 |

적용되는 root·로컬 지침과 관련 원문은 직접 읽는다. Personal은 이번 판단에 필요한 부분을 선택하며 전체를 필수 입력으로 만들지 않는다. 일반 Workspace 전체 인수 대신 맡은 목표·계약에서 출발하고, 부족한 원문·호출부·실행 근거를 추가로 찾는다. 자료 접근권은 제품 수정이나 외부 실행 권한을 뜻하지 않는다. Main의 요약·구현 이유를 예상 판정으로 받지 않는다.

본문 선택·읽기 재사용·실물 대조는 대상의 공통 사용 방법(이 Project의 [USAGE](../../../../../context/USAGE.md))을 따른다. 이번에 바꾼 설명 문서도 결과로 대조하며 새 문장만을 기대값의 근거로 삼지 않는다. 권한 있게 채택된 계약은 적용 조건을 확인하고, 그 약속이 문서에 반영된 것과 실제 구현이 충족하는 것을 구별한다.

## 요구와 기본 검사에서 시작해 중요한 공백을 확인한다

원요구·유효한 정정·제품 계약과 사용처에서 중요한 성공·실패의 기대 결과를 잡고, 작성자의 구현·검사·주장과 대조한다. 작성자가 언급하지 않았어도 이번 요구에 필요한 결과를 포함한다. [근거 상세](evidence.md)는 기대 결과의 근거, 실제 검사 범위, 기존 결과의 유효성을 판단하는 방법을 맡고, 이 절은 그 판단을 검증 수행으로 연결한다.

검증 안에서는 다음 세 수행을 구별한다. 같은 검증자가 이어서 맡으며 단계별 agent를 만들지 않는다.

1. **필요한 기본 검사의 실행·유효성 확인.** Project의 필수 검사와 변경 영향별 범위를 먼저 확인한다. lint·타입·빌드·단위·통합·실제 앱 E2E 등 기존 수단을 활용하며, 빠졌거나 현재 대상에 무효인 검사를 실행한다. 명령이 성공해도 테스트가 선택되지 않았거나 다른 산출물을 실행했다면 해당 결과의 근거가 아니다.
2. **검사 적절성 판단.** 근거 상세에 따라 요구에서 도출한 기대와 실제 입력·실행 경로·assertion·대체 경계를 대조한다. 그 결과가 이번 요구를 어디까지 지지하고 무엇을 남기는지 판단한다.
3. **중요한 잔여 공백의 추가 실행.** 사용자 결과의 영향·근거 공백·실패 발견과 복구 가능성을 보고 우선순위를 정한다. 기존 도구·추가 재현·실제 사용 경로에서 결론을 바꿀 미확인을 확인한다. 모든 예외 전수 검사나 매 작업의 새 검사 체계 설계가 목적은 아니다.

유효한 원본 근거는 재사용하며 [재실행·추가 확인의 조건](evidence.md#기존-결과가-현재-대상에도-유효한지-판단한다)에 해당하는 부분을 확인한다. 독립성은 같은 명령의 반복 횟수보다 요구와 근거의 관계를 별도로 판단하는 데 있다. 세 수행은 필요한 근거를 보완하며 오갈 수 있고, 별도 기대값 문서나 고정된 열람 순서를 요구하지 않는다. 실제 실행 경로·준비 공백은 다음 절에서, 결과 반환과 종료는 뒤의 각 절에서 이어간다.

## 실제 경로와 실행 공백을 다룬다

대상의 기존 실행 안내에서 올바른 판본·인스턴스, 준비 완료 상태·인증·데이터를 확인하고 실제 진입점에서 조작한다. 앱의 UI·API·기기 경로, 라이브러리의 공개 API, CLI의 명령 중 이번 요구가 통과하는 경계를 고른다. 행동·결과·계약상 부작용을 연결해 관찰하며 화면 한 장·프로세스 응답·내부 setter로 넣은 상태만으로 사용 성공을 주장하지 않는다. 모든 작업에 브라우저나 전체 앱을 붙이지 않는다.

어떤 요구를 무엇 때문에 확인할 수 없고, 무엇을 준비하면 확인할 수 있는지 좁힌다. 한 경로가 막혀도 결론을 바꿀 공백 중 독립적으로 확인 가능한 것은 수행한다. 예를 들어 실행 환경이 없어 재현하지 못해도 기존 검사와 호출부를 대조해 어떤 조건까지 뒷받침하는지는 확인할 수 있다. 그 대조를 실제 경로의 실행으로 세지는 않는다. 추가 확인은 이번 결론에 미치는 영향과 비용으로 고르며 확신을 높이기 위한 전수 조사로 늘리지 않는다. mock·test mode·대체 환경에서는 확인한 부분과 생략한 실제 경계를 명시한다.

| 공백 | 수행과 연결 |
| --- | --- |
| 기존 명령 확인·격리된 로컬 데이터·임시 관찰이 필요함 | 검증자가 기존 권한 안에서 직접 준비한다. 도구 이름이나 dry-run 표기만 믿지 않고 실제 부작용 범위를 확인한다. |
| 제품·지속 테스트·실행 도구 변경이 필요함 | Main이 원 구현자나 적합한 담당에게 범위·재현·필요 조건을 배정한다. |
| 계정 접근·외부 권한·사용자 선택이 필요함 | Main이 이미 있는 권한과 맥락을 먼저 확인하고 실제로 필요한 행동·결정만 사용자에게 연결한다. |
| 요구가 모호하거나 자료가 충돌함 | 원문과 유효한 계약을 먼저 대조하고, 해결되지 않는 선택과 영향을 Main에 반환한다. |

이번 요구에 필수인 첫 실행 준비는 이번 작업에서 담당과 범위를 정한다. 반복 실패가 쌓일 때까지 미루지 않는다. 여러 작업의 비용을 줄일 범용 도구 투자는 필요성과 유지 비용을 따로 판단한다. 기존 도구가 제공하는 실행·준비·기능 접근·조작·관찰·정리 경로를 재사용하고, 보완한 절차는 실제 실행으로 확인한다. Feature Map이나 새 CLI를 일률적으로 만들지 않는다.

## 검증자가 만든 재현을 수정 담당이 이어받는다

검증자는 필요한 실행 가능한 재현·검사를 직접 만들 수 있다. 제품 코드는 검증 역할로 수정하지 않는다. 제품 수정과 지속 테스트 체계의 통합·기존 기대값 변경은 원 구현자 또는 Main이 지정한 담당이 맡는다. 검증자가 만든 코드·입력·기대 결과를 이어받아 같은 검사를 새로 쓰는 왕복을 줄인다.

Main은 필요하면 테스트 파일만 검증자에게 별도로 배정할 수 있다. 범위·권한·다른 수정자를 명확히 하며 매번 사용자 승인 절차를 추가하지 않는다. 검증자가 제품 수정을 별도 배정받았다면 그 수정의 확인은 자기 확인이며 독립 검증으로 세지 않는다. 필요한 별도 확인을 다시 배치한다.

발견한 문제를 다음에도 기계적으로 잡을 수 있는지 판단한다. 재발 가능한 오류는 회귀 테스트, 안정적으로 판별할 규칙은 타입·lint·schema, 반복 실행의 공백은 기존 도구 보완으로 연결한다. 맥락에 따른 선택은 관련 지침·판단 역할에 남긴다. 모든 임시 probe를 영구 테스트로 만들지는 않는다.

## 검증자는 근거를 반환하고 Main은 다음 행동을 정한다

요구별로 **충족 근거 있음 / 불충족 근거 있음 / 미확인**을 구별한다. 대상·판본·조건, 기대와 실제 결과, 근거·한계·다음 행동을 연결하되 고정된 긴 보고서를 만들 필요는 없다. 기존 근거를 대조한 부분, 직접 재실행, 새 독립 사례, 미확인을 구별하며 추론을 관찰로 보고하지 않는다.

관찰한 실패는 원인·해결책이 확정되지 않았어도 반환한다. 확인한 사실과 원인 가설을 구별한다. 오류 발생만으로 제품 결함이라 판정하지 않고, 그 실패 조건에서 약속한 상태 보존·오류 전달·후속 행동을 확인한다. 예를 들어 인증 성공 뒤 조회가 실패해도 계약대로 인증을 보존하고 조회 오류를 별도로 알렸다면 그 실패 처리 요구에는 충족 근거다.

확인 결과가 지속 본문의 지원 주장·미확인을 바꾸면 해당 의미·범위·직접 근거를 반환해 Main의 [선별·반영](../../SKILL.md#달라진-의미를-해당-owner에-남긴다)으로 연결한다. 검사 진행·수치를 Project에 누적하거나 검증 역할에 정본 편집권을 추가하지 않는다.

Main은 관찰의 타당성과 해결책을 구별해 제품 결함은 제품 수정, 검사·기대값 결함은 검사 보완, 환경 공백은 준비 해결, 요구의 모호함은 기준 확인으로 잇는다. 기존 실패도 이번 요구를 막거나 영향이 커졌다면 처리하며 무조건 제외하지 않는다. 요구와 무관한 개선 아이디어는 별도 의견으로 남기고 그것만으로 검증 실패로 만들지 않는다. 중요한 미확인을 ‘통과+참고’로 묻지 않는다.

## 수정 뒤에는 원래 재현과 영향받은 경계를 다시 확인한다

수정 담당은 최신 대상, 원래 재현·입력·독립 기대 결과, 보존 조건과 무효가 된 근거를 받아 수정하고 자기 확인한다. 실패 assertion을 지우거나 기대값을 현재 출력에 맞춰 해결을 대신하지 않는다. 기대값 자체가 틀렸다면 요구·계약 근거부터 바로잡고 무엇이 왜 바뀌었는지 밝힌다.

검증자는 같은 조건에서 원래 실패가 해결됐는지 확인한다. 좁은 재현이 원래 사용자·호출 경계를 대신하지 못하면 그 경로도 다시 확인하고, 수정에 영향받은 정상·실패·상태 보존을 함께 본다. 같은 재현을 수정 전후에 연결하며 재현이나 기대값을 바꾸면 이유와 근거를 남긴다.

Main과 검증자는 재검증 때 마지막 확인 대상과 현재 대상의 차이에 [기존 근거의 유효성과 재사용 기준](evidence.md#기존-결과가-현재-대상에도-유효한지-판단한다)을 적용한다. 그 판단으로 이어 쓸 근거와 다시 확인할 범위를 정해 현재 재검증에 연결한다.

좁은 후속은 기존 검증자를 이어 쓰되 최신 변경·수정자의 확인·바뀐 가정·무효인 근거를 전달한다. 교체·재배정의 실제 기준은 [실행 배치](../execution.md#이어-쓸지-바꿀지-판단한다)를 따른다. 국소 결함은 수정·재검증으로 잇고, 책임 배치·공개 계약·사용 방식·중요한 절충이 바뀌면 관련 설계 질문을 [개선 검토](../review.md)로 돌린다. 매번 전체 리뷰나 같은 리뷰어의 재승인을 요구하지 않는다.

## 반환 시점과 완료에 필요한 충분성을 구별한다

필요한 기본 검사 결과가 유효하고, 중요한 요구·실패·보존 조건을 실제로 뒷받침하며, 결론을 뒤집을 중요한 공백·모순이 남지 않았으면 검증에 충분하다. 다음 검사가 중요한 미확인을 구별할 수 있으면 실행하고, 새 변화·실패·의문 없이 같은 사실만 반복하면 끝낸다. 테스트 수·커버리지 비율만으로 충분성을 정하지 않는다. 필수 실제 경로를 확인하지 못했다면 다른 검사가 통과해도 그 요구는 미확인이다.

검증자는 충분한 확인을 마쳤을 때뿐 아니라 수정할 문제를 확인했거나 준비·결정 때문에 더 확인할 수 없을 때도 반환한다. 중요한 실패는 모든 검사를 마칠 때까지 미루지 않으며 독립적으로 가능한 확인은 계속한다. 수정·준비로 넘긴 반환은 전체 완료가 아니다. 불안정한 실행을 한 번 성공할 때까지 반복해 통과시키지 말고 조건을 좁히거나 다른 관찰을 찾으며 중요한 불확실성을 남긴다.

Main은 최신 대상에 충분한 근거가 있고 중요한 실패·미확인이 해소됐을 때 현재 범위의 완료를 판단한다. 그 외에는 수정·재검증 또는 필요한 준비·사용자 결정을 연결한다. 질문을 보냈거나 범위 축소·유보를 제안했다는 사실로 기존 요구가 사라지지 않는다. 개발 완료·검증 결과·설치 및 배포·사람의 수락을 확인한 범위대로 구별하고 모든 작업 끝에 새 승인 단계를 추가하지 않는다.

## 근거와 실행 방법은 기존 소유 위치에 남긴다

검사는 대상 Project의 직접 실행 명령과 기존 도구로 수행한다. 결과의 의미·충분성과 재사용은 이 검증 기준으로 판단한다. 시간이나 출력의 제한이 필요한 검사에서는 실행 도구가 실제로 제공하는 범위를 확인한다. 도구의 응답 대기를 제한한 것과 검사·자식 프로세스를 종료한 것은 구별한다.

Main은 [development의 Owner 갱신](../../SKILL.md#달라진-의미를-해당-owner에-남긴다)에 따라 이번 대상·선택·재현·관찰·한계·수정 결과·다음 행동을 기존 Work에 남긴다. 제품의 약속은 Project 계약, 반복 실행의 방법은 Project 안내·로컬 도구가 소유한다. 유용한 재현과 수정 전후 관찰을 보존한 뒤 자기 임시 자원을 정리하며 유일한 근거를 지우지 않는다. 전 로그 보존이나 모든 probe의 영구화는 요구하지 않는다. 검증 담당자는 필요한 실제 근거와 접근점을 반환하고 Work의 지속 기록은 Main이 연결하는 [record-work](../../../record-work/SKILL.md)가 맡는다. 별도 Verify 실행이나 기계 상태 갱신을 완료 조건으로 추가하지 않는다. explain은 확인된 결과의 설명 방법을 맡는다.
