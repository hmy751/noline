# 담당자와 실행 입력을 배치한다

Main이 개발 작업을 위임하거나 담당 세션을 이어 쓸 때 읽는다. [development](../SKILL.md)의 책임을 실제 실행 환경에 연결하며 관련 기준·제품 계약의 내용을 새로 소유하지 않는다.

## 역할에 맞춰 시작한다

Main은 현재 사용자와 대화하는 세션이다. 내부 담당자의 초기 기본값은 **GPT-6.1-sol, medium**이며 개선 검토자는 한 명부터 시작한다. 다른 전문성이나 독립 범위의 이득이 있을 때만 추가한다. 이 값은 현재 선택한 시작점이지 모든 환경의 고정 성능 보장이 아니다.

첫 개선 검토는 부모 대화 전체를 상속하지 않은 새 세션에서 시작하고 관련 Personal·원자료·실물은 직접 읽게 한다. 대화 상속을 줄였다는 이유만으로 편향이 제거됐다고 주장하지 않는다. 요구 충족 검증은 해당 구현·수정에 참여하지 않은 새 컨텍스트에, 개선 검토자와 다른 세션으로 맡긴다. 내부 담당 시작값은 위와 같고 의미 있는 결과의 검증자는 한 명부터 시작한다. 앞선 판단 이력 전체를 기본 입력으로 넘기지 않는다. 검증 호출·축소와 첫 입력은 [검증 상세](verification/INDEX.md#main은-확인-가능한-최신-결과를-넘긴다)를 따르며 필요한 요구·변경·원본 근거·공백·실행 방법은 제공한다.

역할 이름만으로 수정 권한을 추론하지 않는다. 구현·검토·검증 담당에게 실제로 허용한 작업 범위와 도구 권한을 확인한다. 별도 Work 계약을 따르는 기록 담당자의 권한은 이 배정으로 확장하지 않는다.

## 입력이 실제로 어떻게 들어가는지 확인한다

짧은 요청문만을 전체 입력으로 보지 않는다. 자동 주입되는 root·로컬 지침, 사용 스킬, 부모 대화 상속, 접근 가능한 문서와 파일, 도구 권한을 함께 확인한다. 일반 작업 재개와 범위를 정해 위임한 작업은 root·Work 진입 지침에서도 구별해야 한다. 위임받은 담당자는 적용 지침과 맡은 범위의 목표·계약·원문부터 확인하며 전체 Workspace 인수를 자동으로 수행하지 않는다.

현재 실행 도구가 모델·추론 수준·상속을 실제로 설정할 수 있는지 확인하고 사용 가능한 조합을 고른다. 예를 들어 부모 대화 전체 상속이 모델·추론 설정도 상속하는 환경에서는 별도 설정과 충돌시키지 않는다. 지원되지 않는 설정은 사용한 것처럼 기록하지 않고 실제 배치와 차이를 밝힌다. ‘읽기 전용’ 역할 지시는 실제 파일·도구 권한을 제한하는 장치와 다르므로 둘을 혼동하지 않는다.

대상 경로·기준 판본·포함한 미커밋 변경과 다른 담당자의 작업 범위를 알려 준다. 공유 파일을 읽거나 수정하기 전에 현재 상태를 대조하고 다른 변경을 되돌리지 않는다. 판본이 달라졌으면 이전 의견·검사의 유효 범위를 확인한다.

최초 접근점은 탐색의 출발점이다. 담당자는 대상 context의 공통 사용 방법(이 Project의 [USAGE](../../../../context/USAGE.md))으로 질문에 필요한 원문을 추가 선택하고 맡은 수행으로 돌아간다. 반영할 변화가 확인되면 기존 반환에 의미·범위·근거·미확인을 연결한다. 읽거나 제안했다는 사실은 지속 본문의 수정 권한이 아니며, 별도 갱신 배정이 없다면 [Main의 검토·반영](../SKILL.md#달라진-의미를-해당-owner에-남긴다)으로 잇는다.

반환을 수용할 때 대상·요구·계약의 중요한 변경을 대조한다. 당시 근거를 현재판까지 확인하지 못했다면 유효한 판본·조건을 한정한다. Work 전환 뒤 늦은 결과는 원래 Work와 실제 사용한 판본에 귀속하며, 계속 수정할 권한은 최신 배정과 공유 상태를 따른다. 같은 산출물을 새 Work에서도 수정하면 Main이 겹치는 범위·순서를 조정한다. 전환만으로 모든 담당자를 취소하거나 관련 없는 결과까지 기다리지 않는다.

## 이어 쓸지 바꿀지 판단한다

원래 구현자는 수정을 이어 맡기는 것을 기본으로 하고, 검토자는 필요한 좁은 후속 질문에서 재사용할 수 있다. 문제 정의가 바뀌거나 다른 전문성이 필요하거나 같은 잘못된 전제가 반복되면 새 담당자를 고려한다. 세션을 유지해도 갱신된 과제·이유·보존 조건·변경된 가정과 권한·대상·무효가 된 기존 확인을 명시한다. 전체 자료를 다시 읽히기보다 영향받은 근거를 다시 연결한다.

좁은 후속 재검증은 기존 검증자가 이어가는 것을 기본으로 한다. 최신 대상·변경·수정자의 자기 확인·바뀐 가정·무효인 근거를 제공한다. 요구·계약·주요 책임의 변화, 충분한 입력에서도 반복되는 잘못된 전제, 다른 전문성의 필요, 검증자의 제품 수정 참여로 독립 확인이 필요해진 경우에는 Main이 담당·범위를 다시 배정한다. 개선 검토로 돌아갈지는 별도 설계 질문으로 판단하며 모든 수정마다 새 검증자나 전체 리뷰를 만들지 않는다. 실제 재검증 범위는 [검증 상세](verification/INDEX.md#수정-뒤에는-원래-재현과-영향받은-경계를-다시-확인한다)를 따른다.

입력 누락·원문 접근 실패·오래된 전제라면 먼저 입력과 접근을 고친다. 자료량·범위 문제라면 일을 나누거나 추론 수준을 조절한다. 충분한 입력에서도 비교·추론이 부족하면 Main이 직접 판단하거나 더 적합한 모델·추론 수준으로 올린다. 원인을 구별하지 않은 반복 호출이나 무조건적인 모델 상향을 기본 대응으로 삼지 않는다.

처음 적용한 결과는 호출 성공·자료 읽기 여부만으로 평가하지 않는다. 실제 요구 해석, 맥락 적용, 제안의 이득과 비용, 수정·확인의 연결, Main이 다시 해야 했던 일을 살핀다. 제한된 실행 결과와 일반적인 효과 보장을 구별한다.
