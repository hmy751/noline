# Improvement Loop — 작업 체계를 살펴 더 나은 선택을 반영한다

현재 사용자와 대화하는 Main이 이 세션의 맥락을 유지하며 수행한다. 대화를 요약하는 데서 끝내지 않고, 현재 목적에 맞게 내용과 일하는 방식을 더 좋게 만들 선택을 찾아 가능한 반영까지 잇는다. 별도 세션·상설 리뷰어·자동 수집기를 전제하지 않는다.

사용자 요청으로 실행한다. 작업 마무리·방향 전환 등 경험을 함께 돌아볼 가치가 있는 시점에는 이유와 함께 실행을 제안할 수 있지만, 제안만으로 시작하지 않는다. 이미 허용된 일상 갱신은 루프를 기다리지 않는다. 설계 설명이나 프로토타입 작성 요청을 실제 사용자 기준의 채택 요청으로 바꾸지 않는다.

## 대화 전체에서 출발하고 관련 내용 전체를 살핀다

이번 세션의 시작부터 현재까지 사용자·AI 대화를 시간 순서로 훑는다. 목표와 판단의 변화, 정정·마찰, 잘된 경험, 반복 패턴, 좋은 아이디어와 아직 풀리지 않은 것을 찾는다. 마지막 작업이나 실패 장면만으로 범위를 닫지 않는다. 모든 발화를 같은 깊이로 분석하는 것은 아니다.

현재 문맥에 전체 대화가 없거나 요약·압축이 섞였다면 [대화 원문 확인](references/conversation.md)을 적용한다. 요약은 위치를 찾는 단서이며 정확한 발화나 전체 검토의 증거가 아니다. 확보한 범위와 공백을 구별하고, 중요한 공백은 복구하되 독립적으로 판단할 수 있는 부분은 계속한다.

### 관련 경험과 실제 대상 본문을 연결한다

대상 context 입구에서 실제 Personal·Project와 관리 기준을 찾는다. 이 Project에서는 [공통 읽기](../../../context/USAGE.md)와 [Personal 경험 길잡이](../../../context/personal/experience/README.md)를 사용한다. 길잡이의 모든 주제 요약과 아직 묶지 않은 기록을 짧게 훑고, 이번 대화와 의미·조건이 연결되는 상세·이전 선택·반례를 읽는다. 단어가 일치하는 후보만 검색하지 않는다.

발견과 관련된 본문·실제 결과·기준 **전체의 내용 충분성**을 본다. 예를 들어 API 가이드라면 목적·내용 지침에 맞는 핵심 설명·이유·조건·예외·사례·연결 관계를 살핀다. 변경된 줄·구성·표현·형성 자료만 보는 것으로 대신하지 않는다. 내용이 나뉘어 있으면 해당 주제를 이루는 본문까지 연결한다.

협업에서 사용자의 문제 제기·질문·판단·위임과 AI의 조사·설명·실행, 도구·자료 접근·검사 환경, 기존 기준·구조 자체와 새 방법·역할의 기회도 관련된 만큼 살핀다. 검사 부족을 발견하면 기존 테스트·린트·기계 검사 단계와 사람이 대신 해준 확인을 대조해 연결 개선, 도구 보완, 설명·사례 보완 중 무엇이 필요한지 판단한다. 이 목록의 각 칸에서 발견을 만들어내지는 않는다.

### 충분한 근거에서 후보 제시로 넘어간다

유효하게 읽은 내용은 재사용하고 바뀐 대상·부족한 이해는 다시 확인한다. 과거 경험의 당시 판본과 지금 고칠 판본을 구별한다. 의미 있는 다른 선택이나 결론을 바꿀 공백을 따라 범위를 넓힌다. 외부 조사는 필요할 때 하며 중요한 사용자 판단만 묻는다. 무관한 전체 자료 감사나 고정 시간·문서 수 제한은 두지 않는다. 후보의 근거·반대 조건·대상·미확인을 설명할 수 있으면 제시로 넘어간다.

## 관찰을 개선 선택으로 만든다

판단을 실제 장면에 대입해 선택 차이와 반영 대상을 구체적으로 볼 때는 [적용 사례](references/application.md)를 읽는다. 경험의 보존·관리는 Personal이, 채택된 내용은 실제 대상이 맡는다.

실제로 있었던 일과 해석을 나눈다. 반복은 단서이고 반복 수가 채택 조건은 아니다. 단발 성공의 구체화나 새로운 방법도 제안할 수 있다. 기존 체계의 결함 입증만을 새 기회의 조건으로 삼지 않는다.

| 가능한 결과 | 선택할 때 살필 것 |
| --- | --- |
| 경험·현재 이해를 보존 | 다시 판단할 가치가 있으나 지금 규칙이나 실행 과제로 만들 근거는 부족한가? |
| 좋은 방법의 조건·사례를 구체화 | 무엇이 도움을 주었고 언제 달라지는지 설명할 수 있는가? 기존 사례와 합칠 수 있는가? |
| 기존 내용·기준·수행을 개선 | 내용 자체, 찾는 경로, 실제 적용, 도구·배치 중 어디를 바꾸어야 이득이 나는가? |
| 새 방식·역할·도구를 제안 | 어떤 판단·수행이 좋아지며 도입·운영 부담은 무엇인가? 작은 한정 시도가 유효한가? |
| 유지·보류·접기 | 현행으로 충분하거나 아직 근거가 없거나 비용이 이득을 넘는가? 다시 볼 조건이 달라졌는가? |

이 결과는 함께 선택할 수 있으며 필수 승격 단계가 아니다. 현재 기준이 있다는 이유만으로 검토를 끝내지 않고, 행동이 부족했다는 이유만으로 지침부터 늘리지 않는다. 삭제·통합·조건 축소도 비교한다. 이전 변경의 실제 사용과 효과를 판단할 때는 [사용과 효과 판단](references/effects.md)을 읽는다.

추천과 이유를 먼저 보여주고 다른 후보도 볼 수 있게 한다. 각 선택에서 좋아질 점, 관찰·근거와 한계, 실제 바꿀 대상·내용, 반영·유지 부담을 연결한다. 같은 목적에서 현행과 각 안이 실제 수행을 어떻게 달리하는지 비교하되, 모든 후보에 같은 대안 묶음이나 새 도구를 요구하지 않는다. 겹치는 후보는 합치되 다른 조건·반례는 남긴다. 살핀 범위·중요한 유지 판단·남은 공백도 짧게 보여준다. 고정 점수·후보 수·출력 양식은 두지 않는다.

## 함께 선택한 가능한 개선을 실제로 반영한다

새 개선은 사용자가 고른 범위에서 수행한다. 한정 시도라면 상황·행동·기대 변화와 다시 볼 계기를 이해할 수 있게 남기고, 이를 일반 기준으로 읽히게 하지 않는다. 명확한 직접 보완에 한정 시도를 의무화하지 않는다. 이미 허용된 반영·일상 정정에 반복 승인을 요구하지 않는다.

| 실제 대상 | 수행 연결 |
| --- | --- |
| Personal·Project 본문 | 대상 관리 기준과 [context-update](../context-update/SKILL.md)로 의미·중복·충돌·근거·읽기 경로를 맞춘다. |
| 협업 경험·해석·열린 후보 | [Personal 경험 관리](../../../context/personal/experience/MAINTENANCE.md)에 따라 관련 주제 또는 아직 묶지 않은 기록에 남긴다. |
| 스킬·코드·검사·도구·워크플로 | 해당 대상의 작성·수정·검증 계약으로 수행한다. context-update의 쓰기 권한을 확대하지 않는다. |

Main이 같은 근거로 이어 수행할 수 있다. 파일이나 책임이 나뉘었다고 새 담당자·호출·보고서를 강제하지 않는다. 범용 개선 리뷰어를 필수로 만들지 않으며 필요한 검토는 해당 대상의 기존 조건을 따른다.

반영은 실제 대상에서 수행한다. 실행 중 자연스럽게 생기는 Work 기록과 아래 한정 시도의 재개 지시·종료 정리는 [기존 Work 갱신 계약](../../../context/work/workspaces/spec-and-tickets/MAINTENANCE.md)을 따른다. Main은 적용·종료할 내용과 근거를 연결하고 실제 반영을 확인하며, 연결된 Maintain과 같은 문서를 중복 수정하지 않는다. 자동 연결이 없으면 같은 계약의 수동 fallback을 따른다. 이 스킬로 session을 자동 연결하거나 기록 담당을 교체하지 않는다. 선택한 것을 다시 Work에 등록·이관하거나 새 Ticket으로 만드는 공통 단계를 넣지 않는다. 별도 작업이 실제 필요한 경우 남은 목표와 연결을 밝히되 링크 생성만으로 실행 완료라고 하지 않는다.

### 선택한 한정 시도를 실행할 곳과 끝나는 범위에 연결한다

현재 대화에서 이어 수행할 수 있으면 바로 한다. 특정 다음 작업에서 수행한다면 그 작업이 실제로 읽는 기존 지시·재개 본문에 적용 상황·행동·끝나는 범위와 Personal 경험 주제를 연결한다. 기존 Work의 상태나 Ticket을 쓸 수 있지만 시도를 위해 Work를 새로 만들거나 등록하지 않는다. 자세한 실행 내용은 한 곳이 소유하고 다른 진입에서는 필요한 요약·링크만 둔다. 실행할 작업이나 읽을 지점을 아직 정하지 못했다면 Personal에 선택 의사와 미정 범위를 남기되 실행 연결 완료로 표시하지 않는다.

시도를 잇는 Main은 범위가 끝나면 수행자가 임시 지시를 종료·제거하고 실제 사용 여부·도움·부담·미확인을 같은 경험 주제에 남기도록 연결한다. 현재 Main이 이어 수행하면 해당 Owner의 허용된 갱신 경로로 정리를 마치고, 다른 수행자가 맡으면 기존 재개 지시에서 이 마무리 책임도 찾을 수 있게 한다. 시도 종료 정리는 다음 루프를 기다리지 않는다. 적용 기회가 없었다면 미사용으로 남기고 범위 연장을 자동 결정하지 않는다. 한 번의 수행 완료와 효과 확인, 지속 기준으로의 채택은 구별하며 이후 사용자 요청의 관련 루프에서 필요한 다음 선택을 판단한다.

## 보존·직접 확인·다음 판단을 잇고 마친다

변경 목적에 맞는 직접 확인을 한다. 내용이면 근거·중복·조건·실제 진입에서의 이해, 제품이나 도구면 필요한 실행·검사까지 확인한다. 다음 사용을 관찰한다는 이유로 지금 필요한 확인을 미루지 않는다.

경험과 후보의 현재 상태는 Personal의 관련 주제에서 갱신하고 길잡이는 해당 요약·진입만 맞춘다. 채택된 기준·실행 지침은 실제 대상이 정본이고 경험 주제에 전문을 복제하지 않는다. 반영됐으면 열린 후보로 계속 표시하지 않는다. 원자료·당시 선택을 최신 해석으로 덮지 않는다.

선택한 즉시 반영과 필요한 확인을 마치고, 실제 반영·한정 시도·채택했지만 남은 실행·미결·유지/기각과 중요한 공백의 다음 경로를 구별해 반환한다. 필요한 반영·검사가 남으면 부분 완료다. 새 후보 없음·무수정 유지도 유효하다. 저장·직접 확인·다음 실제 사용 효과는 별개로 말한다.

다음 **사용자가 요청한** 관련 루프에서 길잡이와 관련 경험을 다시 읽고 실제 도움·부담을 대조한다. 상시 추적·정기 평가·대화 전체 재실행은 기본으로 만들지 않는다. 일반 작업은 필요한 채택 기준과 그 작업에 이미 선택된 한정 시도의 적용·종료 범위를 읽으며 모든 열린 후보를 읽거나 실행하지 않는다.

이것은 prototype에서 이 Project의 관리 계약으로 적응한 실행 지침이다. 목적·선택 이유·자료와 한계를 재검토할 때 [형성 자료](_background/README.md)를 읽는다. 저장만으로 실제 host 활성화나 운영 효과가 확인된 것은 아니다.
