# Context Update — 지속할 의미를 해당 본문에 반영한다

지정된 Personal·Project 본문이 근거가 지지하는 의미·적용 조건·한계를 설명하도록 맞춘다. 내용을 어디에 남기며 어떤 권한으로 바꿀지는 대상의 관리 계약이 소유한다. 이 스킬은 그 계약에 따른 한정 반영과 확인을 맡는다.

대상의 root·context 입구에서 실제 본문과 관리 지침을 찾는다. 스킬 위치로 대상 경로를 추정하지 않는다. Noline에서는 [context 입구](../../../context/README.md), [Personal 관리](../../../context/personal/README.md#기준을-고치는-경우), [Project 관리](../../../context/project/MAINTENANCE.md)가 그 경로다. 공통 선택·근거 재사용은 [USAGE](../../../context/USAGE.md)를 사용하고, 이미 유효하게 확보한 내용을 다시 전부 읽지 않는다.

개발 중 구현자가 근거로 제안하면 Main이 전체 맥락과 대상의 관리 권한을 검토해 반영한다. 별도로 맡긴 갱신 담당이 있다면 그 범위를 따른다. 직접 반영 요청이나 Main 자신의 작업에 인위적으로 별도 제안자를 만들지 않는다. Work의 Spec·Ticket·current는 [기존 운영 계약](../../../context/work/workspaces/spec-and-tickets/README.md)이 소유하며 이 스킬이 기록 담당을 바꾸지 않는다.

## 반영할 의미와 권한을 확인한다

현재 요청·변화·직접 근거와 대상 본문을 대조한다. 이전 제안의 유효한 근거는 사용하고, 공백·충돌·그 뒤 변경이 있는 부분만 추가 확인한다. 제안에 포함된 문안 자체가 정답이거나 반영 결정인 것은 아니다.

먼저 그 변화가 해당 영역에 계속 남길 내용을 바꾸는지 판단한다. Project에는 여러 작업의 제품 이해·개발에 필요한 의미·구조·계약·제약·선택 이유를 남기고, 현재 지원 사실도 그 공통 맥락을 설명할 필요가 있을 때 포함한다. 이번 구현 여부·검사 진행·실행 수치는 Work가 맡는다. 기존 Project 계약 안에서 새 소비자만 달리 적용했다면 Project를 편집하지 않고 끝날 수 있다. Personal에는 여러 작업에 가져갈 개인 판단의 의미·조건과 협업 경험·해석·열린 후보를 지위별로 남긴다. 경험 모음 반영은 [그 관리 계약](../../../context/personal/experience/MAINTENANCE.md)을 따르며 한 작업의 선택을 자동 일반화하지 않는다.

이미 권한 있게 정한 뜻의 반영, 확인된 사실 정정, 새 제품 약속·개인 기준의 채택을 구별한다. 유효한 요구와 현재 코드가 다르면 결함인지 설명 오류인지 새 선택이 필요한지 대조한다. 현재 동작에 맞춰 약속부터 바꾸지 않는다. 반영을 맡았다는 이유로 선택 권한을 얻지는 않으며, 이미 허용된 변경에는 반복 승인을 요구하지 않는다.

수정 전에는 보존할 뜻, 달라진 사실과 확인 범위, 열린 선택, 영향받는 본문·진입을 이해할 만큼 범위를 잡는다. 별도 양식은 필요 없다. 같은 파일의 사용자·병행 변경을 현재판에서 확인하고 제안 당시 문장으로 덮어쓰지 않는다. 범위 밖 결정이 있더라도 독립적으로 확정할 수 있는 반영은 이어 수행한다.

## 의미가 달라진 본문과 필요한 연결을 맞춘다

해당 영역의 구성·관리 기준으로 기존 본문에 통합할지 필요한 상세를 나눌지 판단한다. 의미·조건·이유를 본문에서 이해할 수 있게 하되 코드와 실행 기록을 복제하지 않는다. 새 약속은 채택·적용 조건·현재 구현 지원을 구별한다. 적용 중인 약속을 구현이 지키지 못하면 그 불충족을 밝히며 문서 편집만으로 해소했다고 쓰지 않는다.

다른 본문을 그대로 두면 독자가 어떤 낡은 사실·조건·이유로 판단하게 되는지를 기준으로 함께 고칠 범위를 정한다. 같은 현황이 계약·가이드에 적혀 있다면 의미를 유지하며 정정할 수 있다. 링크가 있거나 파일이 가깝다는 이유만으로 전체를 갱신하지 않는다.

본문·사례·형성 자료와 읽기 경로는 대상의 [CONTENT-POLICY](../../../context/CONTENT-POLICY.md) 같은 관리 기준을 따른다. 뜻이 같은 표현 수정에 모든 배경·날짜를 맞추지 않는다. 의미·적용 조건이 달라지면 관련 형성 이유와 필요한 근거도 확인·보완하고, 중요한 전환은 당시 조건과 함께 보존한다. 필요한 근거를 찾지 못했다면 의도를 만들어 채우거나 ‘자료 없음’ 안내만으로 완료하지 않는다.

승인된 이동·복원은 보존할 의미와 실제 진입을 대조해 해당 대상의 규칙으로 수행한다. 갱신 요청만으로 Owner 이동이나 구조 재편을 시작하지 않는다. source·과거 판단을 새 결론으로 덮어쓰지 않으며, 그 자료의 원문 역할은 유지한다.

이 과업의 쓰기 범위는 지정된 Personal·Project의 허용된 본문과 관련 안내·형성 자료다. Work current·제품 코드·테스트·machine 상태·새 Work 생성·다른 저장소 동기화는 포함하지 않는다. 관련 Work 선택·output이나 진행 중 담당자에 영향이 있으면 확인한 영향과 접근점을 Main에게 반환한다. 같은 Main이 다른 책임으로 이어 수정할 수 있지만, 이 스킬의 범위가 넓어진 것으로 취급하지 않는다.

## 실제 읽기와 직접 근거로 확인한다

대상 영역의 입구와 영향받은 기존 참조에서 대표 질문으로 읽는다. 주변 안내가 약속한 의미·조건·한계를 목적지 본문에서 복원할 수 있는지, 보존할 뜻이 빠지거나 주장 범위가 넓어지지 않았는지 직접 근거와 대조한다. 링크 존재·편집된 파일 수만으로 충분하다고 판단하지 않는다.

변경된 문서도 원요구·유효한 계약·결정에 대조할 결과다. 필요한 기존 개선 검토·검증에 연결하되, 새 문장만을 제품 검증의 기대값으로 쓰지 않는다. 문서 정정마다 독립 검토자나 전체 제품 재시험을 새로 요구하지 않는다.

**요청된 의미와 필요한 설명·읽기 경로를 맞추고 확인한 범위에서 문서 반영을 마친다.** 실제로 필요한 설명·근거·경로가 남았다면 그 부분은 미완료다. 원래 범위 밖의 내용, 판단해 제외한 것, 필요한데 못 한 것을 구별하며 미완료를 이름만 바꿔 제외하지 않는다. 이미 반영된 내용이거나 해당 영역에 남길 변화가 없으면 대조 결과를 반환하고 편집 없이 끝낼 수 있다.

문서가 ‘구현은 추가됐고 요구 검증은 남았다’고 정확히 설명하면 본문 반영은 끝날 수 있다. 그 문서가 설명하는 제품의 충족·작업 전체 완료·사용자 수락은 별도 판단이다. 제품 검사 결과가 이후 지속 주장이나 확인 한계를 바꾸면 같은 방법으로 해당 본문을 다시 맞춘다.

## 원래 작업에 결과와 남은 영향을 돌려준다

실제로 반영한 의미와 근거, 확인 범위, 미반영·열린 선택과 이유, 영향받는 작업·소비자 접근점과 남은 행동을 전달한다. 별도 보고서를 기본 생성하지 않으며 같은 Main이 수행하면 원래 결과 설명과 기존 Work 유지 경로로 이어간다. Main은 반영할 의미·근거를 기존 Maintain 경로에 전달하며 자동 연결이 없으면 Work 계약의 수동 fallback을 따른다. 담당자의 제안, Main의 채택, 실제 수정, 확인을 한 상태로 뭉치지 않는다.

중단되면 반영한 곳과 남은 검토·반영·확인을 Main에게 돌려주고 기존 Maintain 경로를 통해 Ticket·current에서 이어갈 수 있게 한다. 진행 중 Work가 있는 작업의 중요한 제안·조정·미채택 근거는 그 기존 기록 방식으로 잇는다. Personal 경험 반영이라면 해당 주제·길잡이에 처리 결과를 남기며 별도 Work 기록·새 제안함을 요구하지 않는다. 이미 확보한 근거로 이어갈 수 있으면 원 구현자를 일괄 재호출하지 않는다.

일상 사실 정정과 이미 정한 의미의 반영은 나중의 경험 개선 단계를 기다리지 않는다. 경험 검토·새 개선 선택은 별도 요청과 책임으로 다루며, 채택 결과가 Personal·Project 본문이면 이 방법을 사용할 수 있다. 채택 대상이 코드·스킬·도구이면 해당 수행으로 연결한다.

목적·범위·수행 방법을 수정하거나 이전 선택을 재검토할 때는 [형성 자료](_background/README.md)를 읽는다. 프로토타입에서 가져온 방법을 Noline의 기존 Work 기록 책임에 맞췄다. 실제 host의 자동 호출·일반적인 사용 효과까지 입증한 것은 아니다.
