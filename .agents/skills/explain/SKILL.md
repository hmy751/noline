# Explain — 실제 대상을 이해하고 판단할 수 있게 설명한다

사용자가 뜻·동작·구조·선택을 이해하고 자기 질문과 판단을 이어가도록 돕는다. 설명 방식을 다시 지시해야 하는 부담을 줄이는 것이 목적이다. 구조를 이해하거나 학습을 이어가는 것 자체도 유효한 목적이며, 모든 설명에 다음 행동을 붙이거나 모든 재질문을 없애려 하지 않는다.

이 본체는 질문의 범위, 자료 확인과 판단, 설명 구성, 충분성과 권한을 맡는다. [작성 상세](references/constructing-explanations.md)는 관계·조건·이유를 실제 설명으로 만드는 방법과 예시를, [앞선 발화 상세](references/prior-explanation.md)는 원래 말의 뜻과 현재 타당성을 대조하는 일을 맡는다. 필요한 상세를 함께 쓸 수 있으며 별도 유형·시점·출력 목차를 먼저 고르는 체계는 아니다. 목적·구성·이전 선택을 재검토할 때는 [형성 자료](_background/README.md)를 읽는다. 현재 실행에 필요한 내용은 이 본문과 해당 조건의 상세에 있다.

## 질문과 설명 범위를 정한다

현재 질문과 가까운 대화에서 무엇을 어느 범위까지 이해하려는지 정한다. 사용자가 이해했다고 밝힌 내용은 이어받고, 이미 있는 맥락을 되묻거나 혼동 원인을 먼저 진단해 달라고 요구하지 않는다. 지식을 고정된 수준으로 추정하지 않고 질문에서 필요한 깊이를 고른다.

역할을 묻는 질문과 그 책임 배치가 적절한지 묻는 질문을 구별한다. ‘왜 이렇게 했나’, ‘어디 갔나’에는 뜻과 선택에 대한 판단이 함께 있을 수 있다. 후속 질문이라는 이유만으로 설명 실패나 사용자 혼동을 단정하지 않는다.

앞선 말의 지시 대상·누락·모순·자기평가가 질문의 대상이면 [앞선 발화 상세](references/prior-explanation.md)를 읽어 실제 발화부터 대조한다. 이미 공유한 지점에 이어 표현을 바꾸고, 실제 오류는 주장과 달라지는 결론을 정정한다. 새 설명을 원래부터 했던 말로 꾸미지 않는다.

작업의 첫 결과를 전달할 때도 원래 목표·맡은 범위와 실제 결과를 연결해 무엇이 해결됐고 무엇이 남았는지 설명한다. 별도 설명 요청을 기다리지 않는다. 파일 목록·검사 결과는 답의 근거이며, 목표에 대한 답과 변화의 의미를 대신하지 않는다.

## 자료를 확인하고 판단한다

### 답을 바꿀 사실을 확인한다

자료가 부족하면 답을 바꿀 공백부터 확인한다. 프로젝트 사실은 실제 대상의 진입 지침·관련 맥락·원자료에서 찾고, 이 스킬의 위치를 제품 저장소로 가정하지 않는다. 익숙한 개념이나 대화 안의 뜻으로 답할 수 있으면 저장소 조사부터 시작하지 않는다. 현재성·실행 여부·검증 범위가 답을 바꾸면 [공통 설명과 근거 기준](../shared/explanation-and-evidence-criteria.md)을 읽고 적용한다.

설명을 만들 수 없는 이유가 사실 부족이면 필요한 확인으로 돌아간다. 이미 맡은 조사·검토가 있다면 그 책임과 권한 안에서 더 수행하고, 다른 담당의 일이면 공백과 답에 미치는 영향을 넘긴다. 확인할 수 없을 때는 이유와 결론의 한계를 밝힌다. 문장을 보완하는 일로 부족한 구현·조사·검증을 대신하거나, 확인 가능한 사실을 ‘미확인’으로 적는 데 그치지 않는다.

### 선택의 적절성과 변경의 이득을 대조한다

선택의 적절성을 물었다면 [작성 상세의 선택 판단](references/constructing-explanations.md#선택의-적절성과-변경의-이득을-판단한다)을 읽고, 현재안과 의미 있는 대안을 같은 요구·사용 조건에서 비교해 의견을 낸다. 실제 사용처와 함께 명시된 지원 목표도 판단 기준으로 삼는다. 일부에 먼저 적용했다는 사실만으로 설계 목표까지 줄이지 않고, 막연한 확장 가능성을 새 요구로 올리지 않는다. 각 선택이 필요한 결과를 어떻게 만들고 어떤 부담을 남기는지 확인한다.

동작을 이해시키는 기능상의 이유와 현재 배치가 더 적절하다는 평가는 구별한다. 앞선 AI 제안·채택된 요구나 계약·현재 구현을 대조하되, 과거 제안과의 일치나 현재 구현의 존재만으로 선택을 정당화하지 않는다. 당시 의도는 기록에서 확인한 범위로 말하고 현재 효과에서 추론한 이유와 구별한다. 역할을 설명할 수 있다는 사실이나 사용자의 이의만으로 유지·변경을 결정하지 않으며, 근거 있는 추천과 실제 변경의 권한도 구별한다.

‘달라졌다·개선됐다·유지했다’에는 비교 기준을 정하고 관련 전후 구현·사용처·관찰을 대조한다. 과거 상태는 당시 자료로 확인한다. 코드 개선의 동작 보존 근거와 읽기·변경 부담의 개선 근거는 구별하고, 동작도 바뀌었다면 그 차이와 영향을 설명한다. 변경의 구체적인 비교 방법도 위 작성 상세를 따른다.

## 설명을 구성한다

### 전체와 부분의 연결로 순서를 잡는다

여러 부분이 함께 작동하는 대상을 설명할 때는 결과를 만드는 부분들이 무엇을 주고받고, 어떤 사건이나 조건에서 연결되는지 확인한다. 그 연결을 이해하는 데 필요한 구별을 먼저 잡고, 이를 따라 설명 순서와 코드 발췌를 고른다. 전체 역할을 한 문장 소개한 뒤 파일 순서대로 해설하는 것으로 이 구성을 대신하지 않는다. 전체 설명에서는 [작성 상세의 구성 방법](references/constructing-explanations.md#여러-부분을-하나의-설명으로-구성한다)과 [전체·후속 대비 예시](references/examples/auth-flow.md)를 읽어 실제 자료를 한 답으로 잇는다.

흐름에 나중에 실행할 작업의 등록이 있다면 그 순간 실행되는 처리와 구별한다. 계속되는 관측과 선택적으로 시작되는 작업이 함께 있다면 그 차이를 구별한다. 서로 독립적으로 들어오거나 겹칠 수 있는 경로를 하나의 필수 순서로 설명하지 않는다. 이 관계가 이해를 좌우하면 작은 도식·호출부·등록부로 연결을 먼저 보여 주고, 같은 이름과 값을 유지해 필요한 구현으로 내려간다. 단순한 순차 처리라면 그 순서를 설명한다.

대표 상황은 전체를 따라가기 위한 출발점이다. 그 경로가 설명하지 못하는 주요 역할이나 결과를 바꾸는 다른 경로도 필요한 위치에서 잇는다. 한 대목의 자세한 해설로 전체 요청을 대신하거나 대표 경로를 전체 구조처럼 그리지 않으며, 전체 요청을 모든 줄·분기의 해설로 확대하지 않는다. 단순한 표현이나 이미 공유된 연결의 한 대목을 묻는다면 그 대목에서 바로 답한다.

### 실제 대상과 해설을 연결한다

직접 답을 먼저 주고, 그 답을 만드는 코드·값·관찰·앞선 문장을 골라 **왜 그 결과나 판단으로 이어지는지** 함께 풀어 쓴다. 중요한 이름은 처음 쓰는 자리에서 무엇을 가리키고 어떤 일을 맡는지 밝힌다. 실제 처리를 읽은 것과 그 처리를 사용자가 따라갈 수 있게 설명한 것은 별개다.

코드의 역할·구조·흐름·동작을 이해하려는 요청에는 핵심 관계가 구현된 실제 코드를 설명과 함께 제시한다. 코드 제시와 문법 해설의 깊이는 따로 정하며, ‘코드랑 같이’라는 재요청을 기다리지 않는다. 첫 결과 전달에서도 핵심 주장을 이해하는 데 코드의 처리가 필요하면 같은 기준을 적용한다. 선택의 적절성이나 근거를 묻는 질문은 실제 변경·검사와 판단의 연결로 충분할 수 있으며, 코드가 언급됐다는 이유만으로 코드 읽기 과제로 바꾸지 않는다.

각 부분의 해설은 앞에서 잡은 연결 중 무엇을 설명하는지 드러내고, 실제 호출·인자·분기·반환이 그 역할을 어떻게 수행하는지 잇는다. 조건문 뜻뿐 아니라 그 조건이 달라질 때 해당 연결이나 결과가 어떻게 달라지는지 설명한다. 이를 보여 줄 코드 단위는 다음처럼 고른다.

- 조건을 설명한다면 그 조건이 허용·차단하는 동작을, 보관하는 값을 설명한다면 뒤에서 읽거나 반환하는 지점을 함께 보여 준다. 역할 이름·비교식 몇 개·파일 링크만으로 독자가 핵심 처리를 다시 조립하게 두지 않는다.
- 한 표현의 뜻으로 답이 끝나면 문장 안의 표현과 짧은 해설로 답한다. 이미 제시된 코드의 한 표현만 묻는 경우도 같다. 여러 표현의 실행 관계가 답을 만들면 해당 관계를 볼 수 있는 코드 블록을 사용한다. 짧은 함수 자체가 의미를 보존하는 단위라면 전체를 보여 준다.
- 발췌는 원문을 유지하고 떨어진 대목의 연결과 생략을 표시한다. 생략 때문에 실행 조건이나 반환·오류 의미가 달라 보이지 않게 필요한 주변 처리도 설명한다. 실제 자료가 부족하면 확인으로 돌아가며 설명용 코드를 현재 구현처럼 제시하지 않는다.

여러 부분의 역할·실행을 연결하거나 요약만으로 처리·조건·이유가 잘 드러나지 않으면 [작성 상세](references/constructing-explanations.md)의 해당 절을 읽는다. 실제 처리·값·조건을 연결한 설명용 상황과 실제 관찰은 구별한다.

### 깊이를 유지하며 읽을 수 있게 배치한다

여러 부분을 설명할 때는 도입에서 잡은 연결을 본문에서 함께 풀 질문들로 나눈다. 각 묶음은 지금 설명할 역할·차이와 그 답을 먼저 드러내고, 이를 이해하는 데 필요한 코드·해설·조건을 가까이 둔다. 다른 질문으로 넘어가는 경계는 문단의 첫 문장, 제목·강조, 목록이나 표 가운데 내용에 맞는 방식으로 알아볼 수 있게 한다. 함수나 도식의 항목마다 한 절을 만드는 것은 아니다.

| 전달할 관계 | 표현을 고르는 기준 |
| --- | --- |
| 실행 순서·시간에 따른 변화 | 실제 처리 가까이에서 단계별로 잇는다. |
| 대조할 조건·상태·호출·전후 차이 | 같은 형식의 목록이나 표로 나란히 놓는다. |
| 인과·선택 이유 | 하나의 관계를 발전시키는 짧은 문단으로 연결한다. |
| 여러 부분의 소유·위임·합류 | 문장만으로 계속 되짚어야 한다면 필요한 범위의 도식을 보여 주고 구현과 연결한다. |

한 묶음 안에서도 서로 다른 설명을 한 문단에 쌓지 않는다. 같은 코드에서 값을 정하는 이유와 기다린 뒤 확인하는 이유를 설명한다면, 각각의 관계를 읽을 수 있게 문단을 나누되 같은 코드 가까이에 둔다. 결론을 바꾸는 조건은 해당 주장과 함께 남기고, 다른 경로로 넘어갈 때는 무엇이 달라지는지 밝힌다. 읽기 쉽게 만들기 위해 필요한 값·실패 조건을 생략하지 않는다.

각 표현이 맡을 일을 정한다. 구체적인 값으로 조건에 따른 결과 차이를 보여 줄 수 있고, 도식의 관계를 코드에서 다시 찾아 연결하는 데 필요한 반복은 사용한다. 같은 설명이나 결론을 그대로 반복하지 않는다. 사용자가 요청한 방식을 반영하며, 짧은 한 관계로 끝나는 답에는 불필요한 구분·형식·고정 목차를 붙이지 않는다.

## 답의 범위와 마무리를 지킨다

마치기 전에 실제 질문에 직접 답했는지 본다. ‘바꿔야 하는가’를 ‘다시 실행해야 하는가’처럼 가까운 다른 질문으로 옮기지 않는다. 설명 목적에 맞춰 필요한 연결이 답 안에 있는지 확인한다.

| 지금 설명할 것 | 답에서 확인할 연결 |
| --- | --- |
| 전체 코드·흐름·구조 | 주요 사건이 어디로 들어와 어떤 부분과 상태를 거쳐 결과가 되는지 찾을 수 있는가. 독립 경로·공유 작업이 중요하면 그 연결도 보이는가. |
| 특정 코드·표현 | 제시된 표현·값·조건과 후속 동작을 함께 따라 지금 묻는 결과를 이해할 수 있는가. |
| 선택·변경·작업 결과 | 사용자가 묻는 선택이나 원래 목표에 직접 답하고, 판단을 바꾸는 근거·조건을 연결했는가. |
| 앞선 말 | 원뜻과 지금 유지·보완·정정하는 주장, 그 때문에 달라지는 결론이 구별되는가. |

이 표는 답을 점검하는 기준이며 사용자에게 출력할 양식이나 시험이 아니다. 원래 파일에서 핵심 관계를 다시 찾아 조합해야 한다면 필요한 대목을 보완한다. 각 대목이 정확하거나 코드가 있다는 사실만으로 전체 설명이 충분하다고 판단하지 않는다.

각 대목이 무엇에 답하는지, 그 답을 바꾸는 조건이 어디 있는지 찾기 어렵다면 묶음과 배치를 고친다. 빠진 사실은 확인으로 돌아간다. 이는 현재 답의 부족을 보완하는 판단이며 모든 답을 두 번 작성하거나 점검표를 출력하라는 절차는 아니다. 핵심 답과 필요한 연결, 결론을 바꾸는 조건·한계가 드러나면 끝낸다. 학습을 위한 질문은 이어질 수 있다. 변경·수락·기록으로 이어질 때는 [권한과 다른 책임의 경계](#권한과-다른-책임을-구별한다)를 따른다.

## 권한과 다른 책임을 구별한다

설명을 제공한 사실과 사용자가 이해·동의한 사실은 다르다. 침묵으로 이해 완료를 선언하거나 quiz·재진술·형식적 승인을 기본으로 요구하지 않는다. 질문식 학습을 요청했다면 그 방식으로 돕는다.

설명에 필요한 확인과 근거 있는 추천은 할 수 있다. 설명 요청만으로 코드·문서·작업 결과를 수정하거나 제품 선택·최종 수락을 새로 확정하지 않는다. 별도 변경 요청이나 기존 위임은 그 권한을 따른다.

전체 작업 결과와 확인·상태 판단은 작업 담당자가, 지속 기록은 실제 대상의 관리 규칙과 담당자가 맡는다. 이 스킬은 별도 상태 저장소나 고정된 기록 담당을 만들지 않는다.
