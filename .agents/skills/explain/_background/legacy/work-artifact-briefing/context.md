# 왜 작업물 이해 브리핑을 만들었는가

## 이루려던 결과와 문제의 출발점

이 스킬은 사람이 AI의 완료 설명을 그대로 받아들이는 대신, 작업물이 무엇을 맡고 실제로 무엇이 연결돼 있으며 근거가 어디까지 말해 주는지 이해해 자기 질문과 판단을 만들 수 있게 하려는 것이었다. 당장 수정안을 고르는 요청뿐 아니라 현재 구조를 파악하고 싶은 요청도 온전한 사용 목적이다.

원래 TripProof 연구는 “처음부터 목적을 몰랐다”보다 **이미 확인한 목적이 구현·검증·완료 설명으로 넘어가면서 더 좁은 결과로 바뀌었다**고 진단했다. 당시 분석이 비교한 세 장면은 다음과 같다. 여기서는 당시 분석 문서의 관찰을 복원하며 제품의 현재 상태를 말하지 않는다.

| 원래 필요했던 결과 | 대신 충분한 것처럼 다뤄진 결과 | 사람이 다시 확인해야 했던 차이 |
| --- | --- | --- |
| LLM이 실제 판단을 수행하는 제품 기능 | 판단 후보를 만들 인터페이스와 regex 기반 처리 | 판단 기능을 연결할 자리가 있다는 것과 실제 LLM이 판단한다는 것은 다르다 |
| 서버 전체의 흐름을 읽고 수정하기 쉬운 구조 | 유효한 국소 리팩터링 세 번과 테스트56개 통과 | 해당 변경이 유효해도 전체 흐름에서 무엇이 여전히 얽혀 있는지는 별도 확인이 필요하다 |
| 사용자가 질문에 대한 답과 근거를 읽는 화면 | 내부 후보인 `facts[]`를 화면까지 전달하는 계획 | 자료가 도착해도 사용자가 직접 항목을 골라 답을 조립해야 한다면 답변 책임은 남는다. 이 계획은 실제 구현되지 않았다 |

인터페이스·리팩터링·테스트 자체를 무가치하게 본 것이 아니다. 이들이 입증하는 범위보다 완료 설명이 넓어지는 순간, 사용자가 다시 코드와 원래 목적을 대조해야 했다는 것이 문제였다. 사용자가 되물은 뒤 AI가 빠진 문제를 다시 찾았다는 관찰도 있었다. 자료가 저장돼 있다는 사실만으로 필요한 순간에 그 판단을 사용했다고 볼 수 없었다.

그래서 브리핑에는 “파일을 몇 개 고쳤다”에 더해 **이 작업물이 무엇을 맡고, 실제로 무엇을 연결했으며, 그 근거로 어디까지 말할 수 있는지**를 전달하는 책임이 생겼다. 다만 이 설명 책임과 새로운 제품 결함을 독립적으로 찾는 책임, 적절한 순간에 호출하는 책임, 수정된 판단을 뒤 작업에 전파하는 책임은 구별했다. 사람이 설명을 이해했다는 사실도 제품의 최종 수용과 같지 않다.

## 호출 시점을 포함해 검토했던 대안

당시 후보 비교는 이미 “사용자가 되물은 다음에만 작동하면 늦지 않은가”를 다뤘다. 다음은 그 비교의 내용이며, 네 장치가 모두 구현됐다는 뜻은 아니다.

| 후보 | 얻을 수 있는 것 | 해결되지 않는 부분과 당시 선택 |
| --- | --- | --- |
| 사용자가 이해를 요청할 때 호출 | 대상과 필요성이 드러나고 설명 깊이를 통제할 수 있다 | 사용자가 간극을 감지하지 못하면 시작하지 않는다. 이 범위를 실제 스킬의 출발점으로 삼았다 |
| 같은 AI가 중요하다고 판단하면 스스로 호출 | 별도 장치 없이 더 일찍 근거의 한계를 드러낼 수 있다 | 원래 목적을 놓친 AI에게 중요도·충분성을 다시 판단시킨다. 단독 예방 장치로 삼을 근거가 부족했다 |
| 완료 보고·범위 변경·인계 시점에 호출 | 호출 여부를 AI의 재량에만 맡기지 않는다 | 어떤 사건에 어떤 입력과 깊이를 요구할지 별도 설계가 필요하다. 호출 시점만으로 숨은 제품 불일치를 찾지는 못하며 당시 구현도 없었다 |
| 독립 검토자가 불일치를 찾고 브리핑이 설명 | 불일치 발견과 사람이 이해할 설명을 나눌 수 있다 | 검토 요청자·비교 기준·결과 인수자·비용을 정해야 한다. 설명 스킬만으로 이미 제공되는 기능은 아니었다 |

실제 채택에서는 두 설명 스킬을 이름으로 호출하는 것 외에도 사용자의 자연어 이해 요청으로 선택할 수 있게 했다. 이는 “사용자가 아직 말하지 않은 문제를 먼저 찾아 첫 보고 전에 개입한다”까지 채택한 것이 아니다. 따라서 앞으로 시점을 바꾸려면 기존 설명 문구의 보완인지, 호출과 입력의 책임을 새로 배치하는지부터 구별할 필요가 있다.

모든 응답에 같은 완성형 양식을 붙이는 안도 충분하지 않았다. 목적을 잘못 적고 국소 테스트를 근거 칸에 채워도 문서는 완성돼 보일 수 있고, 작은 질문까지 무거워진다. 사용자 이해를 AI가 추정해 장부에 저장하는 방식 역시 실제 이해를 관찰한 것이 아니며 오래된 추정이 남을 수 있었다. 필요한 의미와 근거를 보존하면서 질문에 맞게 설명하는 쪽을 택한 이유다.

## 설명 방식을 이렇게 정한 이유

역할·대표 흐름에서 중요한 코드와 실제 연결로 내려가게 한 것은, 사용자가 파일 이름과 호출 순서를 혼자 다시 조립하지 않게 하려는 선택이다. 2026-09-05 보강에서는 중요한 이름의 데이터·책임을 사용자 일과 연결하고, 추상 설명만으로 부족하면 입력·중간값·결과와 조건 차이를 보여 주도록 했다. 역할 설명은 최근04-02에서 처음 생긴 요구가 아니다.

구조 표현은 관계를 문장만으로 되짚는 부담을 줄일 후보였다. 연구가 참고한 영상의 탐색은 큰 의미 구조에서 필요한 부분을 펼치고 정확한 소스로 내려가는 방식이었다. 이를 정적인 도식의 보편 효과로 확대하지 않았고, 당시 분석은 원 영상의 화면·실행물을 독립 검증하지 못했다고 밝혔다. 현재 질문에 필요한 작은 관계만 보여 주고 화살표·묶음도 근거가 필요한 주장으로 다루도록 한 이유다. 이 행동은 브리핑 안에 두고 다른 스킬이나 공통 기준 전체에 강제하지 않았다.

2026-09-06에는 다음 변경·선택을 위한 요청에서 중요한 구조의 이득과 제약을 설명하도록 보강했다. 영향 설명을 모두 review로 간주해 막는 것도 부족하지만, 현재 구조의 효과를 설명할 수 있다는 이유로 당시 선택 이유까지 지어내거나 전체 설계를 수락해서도 안 됐다. 당시 이유와 현재 도출을 구별하는 조건은 이 두 문제를 함께 다룬다.

## 당시 예시가 보여 주려던 설명의 차이

2026-09-05 품질 대조는 기존 브리핑에 역할·대표 흐름·근거 구별이 **이미 있었다**고 확인했다. 기존 preview도 단순 파일 목록이 아니었다. 남은 문제는 세부 문단에 기술 이름이 연달아 나와, 그 단계가 사용자 질문의 답을 어떻게 바꾸는지까지 따라가기 어려운 점이었다. 그래서 기존 원칙을 삭제하거나 사례 의무를 추가하는 대신 중요한 이름의 뜻과 대표 값을 연결했다.

당시 작성자가 보강한 예시의 질문은 “지금 TripProof의 answer 생성 구조가 실제로 어떻게 이어지는지 작업물 이해 브리핑해줘”였다. 설명은 질문 접수, 근거 구성, 후보 생성, 검증과 상태 확정, API·화면 표시라는 다섯 의미 단계를 먼저 보여 줬다. 초기의 긴13단계 연결을 축약한 이유도 파일 개수보다 처리 책임의 관계를 먼저 잡게 하려는 것이었다.

그 안에서 `AnswerCandidate`는 **모델이 제안한 답의 값·인용 원문·확인 상태를 담는 중간 결과**이고, `certify`는 **그 인용과 값이 원문에 있는지 등을 검사하는 단계**로 설명했다. 이름과 호출 순서만 이해하는 것에서 다음 차이를 판단하는 것으로 이어지게 한 것이다.

| 설명용 입력 | 검사에 관해 알 수 있는 것 | 사용자가 판단해야 할 의미 |
| --- | --- | --- |
| 질문 “체크인은 몇 시부터야?”, 원문 “체크인15:00”, 후보 값15:00 | 값과 인용이 원문에 있다는 것을 확인할 수 있다 | 후보가 무엇을 담고 검사가 무엇을 대조하는지 이해할 수 있다 |
| 같은 체크인 질문에 원문·후보가 모두 “체크아웃11:00” | 원문 포함 여부 검사를 통과할 수 있어도 질문과 답의 의미는 별개다 | 원문에 있다는 보장을 질문에 맞는 답이라는 보장으로 읽으면 안 된다 |

두 번째 행은 관찰된 오답이 아니라 **검사 범위의 의미를 드러내기 위해 작성한 대비**다. 당시 기본 검사 코드가 질문 문장과 답의 의미를 대조하지 않는다는 확인에 근거했으며, 분리된 의미 판정 경로는 기본 설정에서 비활성이었다. 코드와 기본 설정에서 읽은 연결을 실행 성공처럼 표현하지 않는 이유가 여기 있다. 예시 전체와 당시 조건은 가까운 evidence에 보존했다.

같은 preview는 `accepted`가 요청 처리 완료이고 `supported`는 근거가 뒷받침하는 답의 상태라서 서로 바꿔 읽을 수 없다고 설명했다. `conflict` 역시 schema·화면에 존재하는 것과 기본 흐름의 최종 상태로 도착하는 것은 달랐다. 이런 조건은 사소한 구현 부연이 아니라 “현재 구조가 어디까지 작동한다고 이해해야 하는가”를 결정하는 정보였다.

2026-09-06에는 다음 변경을 준비하는 별도 가상 사례를 더했다. HTTP 변환·질문 처리 순서·실행 기록을 분리했다면 처리 순서를 읽을 때 다른 두 세부를 함께 읽지 않아도 된다. 그러나 근거 부족 때 답하는 기준이 여전히 답변 생성 함수 안에 있다면, 그 기준까지 분리·정리됐다고 말할 수 없다. **현재 구조에서 도출되는 이득과 남은 제약을 설명하되, 작성자가 당시 그 이유로 설계했다고 지어내지 않는 것**이 이 보강의 목적이었다. 모든 브리핑에 장단점 평가나 다음 행동 추천을 넣기로 한 결정은 아니다.

## 다른 책임과 함께 두기로 한 이유

설명 복구는 특정 앞선 말에서 시작하고, 브리핑은 기존 작업물과 그 원자료에서 시작한다. 입력·조사 범위·대화 수명이 달라 독립 스킬을 유지했다. 이후 reconsider-work와 함께 배포할 때도 같은 자료나 구조의 이득을 다룬다는 사실만으로 충돌이라고 보지 않았다. 브리핑의 이해 지원과 현재 방법·다음 행동을 다시 정하는 책임은 관련되지만 같은 작업은 아니다. 강제 호출 순서나 통합 스킬은 채택하지 않았다.

Spec/Ticket 연결은 작업의 원래 결과·기준과 보고된 진행을 실제 산출물에 대조할 근거를 더한 것이다. 기록된 완료를 실제 수행으로 간주하거나 모든 설명에서 모든 Ticket을 읽게 하려던 것이 아니다. Main이 설명에서 드러낸 차이·근거를 후속 실행에 이어가고 문서 갱신은 Maintain에 맡기는 방식도 당시 선택한 운영 연결이다. 이 선택은 모든 환경의 보편적 작성 금지가 아니며, 적용 환경의 상위 계약을 확인해야 한다.

## 현재 수정자가 구별할 지위

원래 연구의 정적 검토·예시는 스킬의 실제 호출 정확성이나 사람의 이해 개선을 입증하지 않았다. 이번에 복원한 것도 설계 의도와 선택의 근거다. 최신 Noline 첫 보고의 부족을 원래 스킬이 만들 때부터 실패한 증거로 소급하지 않는다.

04-02에서 먼저 만든 보류 후보는2026-10-22 코드 설명 깊이를 통합한 본문으로 교체했다. 원래 역할·값·근거 연결은 유지하되, 코드 읽기 도움을 원하는 맥락이 실제 코드와 설명의 대응 및 종료 판단으로 이어지게 했다. “같은Promise를공유한다”는 역할 요약과 해당 코드에서 값·반환·대기를 따라 읽는 설명을 구별하는 것이 이번 보완의 이유다.
